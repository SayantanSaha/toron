# REQ-110 - Bounded Memory Buffer Optimization via sync.Pool (SRC-05)

## 1. Description

Peer review audits of Paper 1 and Paper 2 (`SRC-05`, `ReviewTaskSummary.md`, `AER-001`, `AER-002`) identified severe memory allocation churn and Garbage Collection (GC) pressure in Toron's HTTP/1.1 message ingestion pipeline:

1. **Unpooled Heap Slice Allocations per Request Body**:
   In `pkg/httpparser/parser.go` (line 173), request body ingestion executes `bodyBuf := make([]byte, clInt)` directly on the Go heap for every mutating request (`POST`, `PUT`, `PATCH`). For requests up to the default 4 MB `MaxBodyBytes` ceiling, each request allocates large contiguous slices. At sustained loads of 5,000–10,000 requests per second, this generates gigabytes of transient heap allocations per minute, triggering aggressive GC scavenging cycles, CPU cache invalidation, and elevated tail latency percentiles (p99/p99.9).

2. **Ephemeral `strings.Builder` Allocation per Header Line**:
   In `pkg/httpparser/parser.go` (`readLineBounded`), every header line (including the initial request line and all subsequent header key-value pairs) instantiates a fresh `var buf strings.Builder`. During character-by-character reading from `bufio.Reader`, the builder dynamically resizes its internal backing array multiple times. For requests with 20–30 headers, 20–30 separate heap-growing allocations are incurred before header processing even begins.

3. **Deterministic Bounded Buffer Recycling**:
   To sustain high-throughput edge proxy operations with minimal GC overhead, Toron must introduce thread-safe memory reuse via `sync.Pool`:
   - Reusable `*bytes.Buffer` pool for `readLineBounded` header line parsing.
   - Reusable 64 KB byte buffer pool for standard request bodies ($0 < \text{clInt} \le 64\text{ KB}$), with transparent fallback to bounded one-off heap allocations for oversized bodies up to `MaxBodyBytes`.
   - Thread-safe, idempotent lifecycle recycling via an `io.ReadCloser` implementation (`pooledBodyReader`), guaranteeing that buffers are returned to the pool after the request handler completes without data races or memory corruption.

## 2. Acceptance Criteria

### AC-1: Header Line Buffer Pooling in `readLineBounded`
- In `pkg/httpparser/parser.go`:
  1. Define a package-level static `sync.Pool` supplying reusable `*bytes.Buffer` instances with a pre-allocated initial capacity (e.g. 1 KB).
  2. In `readLineBounded`, acquire a buffer from the pool via `lineBufferPool.Get().(*bytes.Buffer)`.
  3. Reset the buffer before use (`buf.Reset()`) and release it back to the pool on return via `defer lineBufferPool.Put(buf)`.
  4. Eliminate per-line `strings.Builder` allocations during header parsing.

### AC-2: Tiered Request Body Buffer Pooling in `ParseRequest`
- In `pkg/httpparser/parser.go`:
  1. Define a static `sync.Pool` managing fixed-capacity 64 KB (`maxPooledBodySize = 64 * 1024`) byte buffers (`*[]byte` or `[]byte`).
  2. For request payloads where $0 < \text{clInt} \le 64\text{ KB}$:
     - Acquire a pooled buffer from `bodyBufferPool`.
     - Ingest the body payload into the pooled slice using `io.ReadFull`.
     - Wrap the slice in a `pooledBodyReader` that implements `io.ReadCloser`.
  3. For large request payloads where $64\text{ KB} < \text{clInt} \le \text{opts.MaxBodyBytes}$:
     - Allocate a bounded heap slice `make([]byte, clInt)`.
     - Ingest via `io.ReadFull` and wrap in standard `io.NopCloser(bytes.NewReader(bodyBuf))`.
     - Do not place oversized buffers into `bodyBufferPool` to prevent pool bloat and unbounded memory retention.
  4. Payloads exceeding `opts.MaxBodyBytes` must continue to be rejected immediately with `ErrBodyTooLarge` (`413 Payload Too Large`).

### AC-3: Safe Lifecycle Management with `pooledBodyReader`
- In `pkg/httpparser/parser.go` (or `request.go`):
  1. Define `pooledBodyReader` implementing `io.Reader` and `io.Closer` (`io.ReadCloser`).
  2. Reading delegates to an internal `*bytes.Reader`.
  3. `Close()` must be idempotent via `sync.Once`, returning the underlying buffer to `bodyBufferPool` exactly once and nullifying references to prevent use-after-free.

### AC-4: Deterministic Server Loop Buffer Reclamation
- In `pkg/httpparser/request.go` & `pkg/server/server.go`:
  1. Add helper `func (r *Request) CloseBody() error` to `httpparser.Request`.
  2. In `pkg/server/server.go:handleConn`, ensure `req.CloseBody()` is executed at the end of each request processing cycle (after router dispatch and response serialization).
  3. Handlers reading `req.Body` to completion (e.g. via `io.ReadAll(req.Body)`) or calling `req.Body.Close()` directly shall not cause double-free panics or data corruption.

### AC-5: Automated Unit & Benchmark Test Suite (TC-110)
- In `pkg/httpparser/parser_test.go` and `pkg/server/server_test.go`:
  1. **Body Pooling Functional Test**: Verify bodies $\le 64\text{ KB}$ correctly read payload data, close cleanly, and recycle without data corruption across consecutive requests.
  2. **Large Body Fallback Test**: Verify bodies $> 64\text{ KB}$ and $\le 4\text{ MB}$ parse and read correctly without pool pollution.
  3. **Idempotent Close Test**: Calling `Close()` multiple times on `pooledBodyReader` does not cause panics or duplicate pool returns.
  4. **Concurrent Pool Race Test**: Multi-goroutine test parsing requests concurrently to verify zero data races under `-race`.
  5. **Allocation Microbenchmark**: `BenchmarkParseRequest_PooledBody` and `BenchmarkReadLineBounded_Pooled` verifying measurable allocation reduction in `B/op` and `allocs/op`.

### AC-6: Zero-Dependency & Race-Clean Invariant
- All changes must strictly use Go standard library packages (`sync`, `bytes`, `io`, `bufio`).
- Complete test suite (`go test -v -race -count=1 ./...`) must pass cleanly with zero data races.

---

## 3. Rationale

High-performance edge gateways and reverse proxies are characterized by allocation efficiency. Allocating fresh multi-megabyte heap buffers for every inbound body and instantiating dynamic string builders for every header line places severe GC pause pressures on the Go runtime. By establishing pre-warmed, bounded buffer pools using `sync.Pool`, Toron reduces memory churn by orders of magnitude for typical workloads ($\le 64\text{ KB}$), lowers p99 latency, and shields the server from heap exhaustion denial-of-service under sustained concurrency.

---

## 4. Constraints

- Pure Go standard library; zero third-party dependencies.
- Zero memory leakage: pooled buffers must be returned to the pool deterministically.
- Full API compatibility: `req.Body` continues to satisfy `io.Reader` and now also implements `io.ReadCloser`.
