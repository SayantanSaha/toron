# REQ-122 - Reverse Proxy Upstream Connection Pooling, Transport Optimization, and Zero-Allocation Response Pipeline

## 1. Description & Problem Statement

### 1.1 Problem Context & Root Cause Analysis
During empirical Docker benchmarking against NGINX, Traefik, Caddy, and HAProxy ([`REQ-121`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-121.md)), Toron exhibited lower throughput (~8,100–8,300 RPS vs. 25,000–33,000 RPS) and higher tail latency (P50 ~3.3ms vs. ~0.8ms) on high-throughput upstream origins (`fast`, `go`, `node`).

Deep profiling and source code audit identified five critical bottlenecks:
1. **Unset `MaxIdleConnsPerHost` in `http.Transport`**:
   Go's standard library defaults `MaxIdleConnsPerHost` to `2` when unset. Under 50+ concurrent requests to the same upstream backend, 48 out of 50 connections are immediately closed after every request, forcing continuous TCP 3-way handshakes (`SYN` $\rightarrow$ `SYN-ACK` $\rightarrow$ `ACK`) and connection teardowns on every request cycle.
2. **`http.ProxyFromEnvironment` Overhead**:
   On every request, `ProxyFromEnvironment` inspects environment variables (`HTTP_PROXY`, `NO_PROXY`), parses CIDRs, and acquires sync locks. Internal reverse proxy targets do not require environment proxy resolution.
3. **Implicit Decompression in Reverse Proxy Path**:
   `http.Transport` leaves `DisableCompression` as `false` by default, injecting `Accept-Encoding: gzip`, intercepting responses, and decompressing payloads in memory, wasting CPU cycles.
4. **Upstream Hop-by-Hop Header Leakage**:
   When copying upstream headers to `res.Header`, `hopByHopHeaders` (`Connection`, `Keep-Alive`, etc.) are copied without filtering. If an origin signals `Connection: close`, Toron's server loop closes the client keep-alive connection, dropping client connection reuse.
5. **Format Reflection Allocations in `res.Serialize`**:
   `fmt.Fprintf` reflection and repeated header sanitization string allocations in `pkg/httpparser/response.go` produce hundreds of thousands of heap allocations per second under saturation.

---

## 2. Functional Requirements

### REQ-122.1: High-Concurrency Upstream Connection Pooling
- `pkg/proxy/proxy.go` must configure `http.Transport` with:
  - `MaxIdleConns`: $\ge 10,000$
  - `MaxIdleConnsPerHost`: $\ge 1,000$
  - `MaxConnsPerHost`: `0` (unconstrained)
  - `IdleConnTimeout`: $90\,\text{s}$

### REQ-122.2: Zero-Overhead Reverse Proxy Transport
- Set `Proxy: nil` (direct socket dial without environment inspection).
- Set `DisableCompression: true` (verbatim payload forwarding without compression/decompression overhead).
- Set `WriteBufferSize: 64 * 1024` and `ReadBufferSize: 64 * 1024`.

### REQ-122.3: Upstream Hop-by-Hop Response Filtering
- Filter all RFC 7230 §6.1 `hopByHopHeaders` (`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailers`, `Transfer-Encoding`, `Upgrade`) when copying `outResp.Header` into `res.Header`.
- Ensure upstream connection state does not terminate client-to-proxy persistent keep-alive connections.

### REQ-122.4: Zero-Allocation Fast-Path in `res.Serialize`
- Replace `fmt.Fprintf` in `pkg/httpparser/response.go` with direct `buf.WriteString`.
- Implement fast-path zero-allocation check in `sanitizeHeader` using `strings.IndexByte`.
