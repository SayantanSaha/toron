# REQ-120 - Heterogeneous Multi-Hop Live Docker Harness Network Execution Architecture

## 1. Description & Problem Statement

### 1.1 Executive Summary & Problem Context
The Heterogeneous Multi-Hop Backend Origin Testbed ([`REQ-113`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-113.md), `BMK-03`) was introduced to evaluate Toron fronting three live, distinct backend HTTP runtime parsing engines:
1. **Node.js 20 LTS**: C-based `llhttp` parser engine.
2. **Python 3.11**: ASGI `uvicorn` / `h11` parser engine.
3. **Go 1.24**: Canonical standard library `net/http` parser engine.

The testbed was designed to execute a formal two-stage desynchronization evaluation protocol ($r_{\text{poison}} \,\|\, r_{\text{benign}}$) across 10 cross-protocol and HTTP request smuggling attack vectors (`VECTOR-01` through `VECTOR-10`), verifying that edge rejections prevent upstream connection pool poisoning and backend desynchronization.

However, during end-to-end master benchmark validation via:
```bash
./benchmarks/run_all.sh --auto-start --docker
```
(which invokes `benchmarks/multihop/run_multihop.sh --docker`), the test harness abruptly crashed with a fatal runtime panic:
```text
panic: runtime error: invalid memory address or nil pointer dereference at benchmarks/multihop/runner.go:687
```

### 1.2 Root Cause Analysis
Detailed source code inspection of [`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go) revealed four critical architectural flaws in the live containerized testbed path:

1. **Uninstantiated Backend Descriptors in Live Mode (`runner.go:687`)**:
   In `main()`, when executed in live mode (`-standalone=false -edge-addr <host:port>`), `TestbedEnvironment` is initialized with only `EdgeAddr` and `IsLive: true`. The backend descriptor fields (`NodeBackend`, `PyBackend`, `GoBackend`) remain `nil`. When `RunAllScenarios` iterates over `backends := []*SimulatedBackend{env.NodeBackend, env.PyBackend, env.GoBackend}`, accessing `b.Runtime` immediately dereferences a `nil` pointer on line 687.

2. **In-Memory Server Invocation on Non-Existent In-Process Server**:
   In `ExecuteScenario`, five vectors (`VECTOR-01` [H2.TE], `VECTOR-02` [H2.CL-Duplicate], `VECTOR-03` [H2.CL-Mismatch], `VECTOR-07` [CRLF-Header-Injection], and `VECTOR-08` [Pseudo-Header-Isolation]) directly invoke:
   ```go
   env.EdgeServer.HTTP2AdapterHandler().ServeHTTP(rec, req)
   ```
   In live Docker mode, Toron runs inside a separate container (`toron-edge-multihop`) on port `8080`. `env.EdgeServer` is `nil`. Calling `ServeHTTP` bypasses the network stack completely in standalone mode and crashes with a `nil` pointer dereference in live mode. It does not validate physical TCP framing, TLS/cleartext ALPN/h2c protocol negotiation, or socket lifecycle events over the wire.

3. **In-Memory Upstream Header Leakage Verification**:
   For `VECTOR-08` (Pseudo-Header Upstream Isolation), the harness verifies stripping of HTTP/2 pseudo-headers (e.g., `:protocol`, `:custom-pseudo`) by acquiring a mutex on `targetBackend.Mu` and reading `targetBackend.LastHeaders` from the in-process mock server struct. In live Docker mode, `targetBackend` does not host an in-memory server. The live backend containers (`backends/node/server.js`, `backends/python/server.py`, `backends/go/main.go`) already echo all received upstream headers in their JSON response body under the `"headers"` key, but the test harness does not parse or verify this response payload over the wire.

4. **Divergent Execution Semantics Between Standalone and Live Modes**:
   The standalone mode relies heavily on in-memory Go abstractions (`httptest.ResponseRecorder`, direct handler calls), whereas live mode requires real network operations over TCP/h2c. The test harness lacks a unified wire-level abstraction capable of evaluating both modes against the same 30 test scenarios (10 vectors $\times$ 3 backends) with consistent reporting schema and telemetry.

## 2. Technical Scope & System Architecture

The scope of this requirement covers the transformation of the multi-hop testbed runner into a true network-capable harness capable of dual execution modes:
1. **Standalone In-Process Mode (`--standalone`)**: Ephemeral, self-contained CI verification with zero external daemon dependencies.
2. **Live Multi-Container Mode (`--docker`)**: Real-world distributed verification fronting containerized Toron and containerized Node.js, Python, and Go backends across a Docker bridge network.

## 3. Functional Requirements

### FR-1: Live Mode Backend Descriptors
- **FR-1.1**: The runner shall define an explicit backend descriptor abstraction (`BackendDescriptor` or generalized `BackendTarget`) containing the required runtime evaluation metadata:
  - `Runtime`: Runtime platform name (e.g., `"Node.js 20 LTS"`, `"Python 3.11"`, `"Go 1.24"`).
  - `ParserEngine`: Canonical parser implementation (e.g., `"llhttp (C-based)"`, `"uvicorn / h11"`, `"net/http"`).
  - `Prefix`: Assigned routing prefix without leading slash (e.g., `"node"`, `"python"`, `"go"`).
- **FR-1.2**: In live mode (`-standalone=false -edge-addr <host:port>`), the harness shall instantiate valid, non-nil backend descriptors for all three runtime targets prior to test execution.
- **FR-1.3**: Iteration over backend descriptors in `RunAllScenarios` shall never encounter a `nil` pointer dereference, regardless of whether the harness operates in standalone mode or live Docker mode.

### FR-2: Wire-Level Protocol Execution for Live Edge Gateway
- **FR-2.1**: The test harness shall eliminate direct in-memory calls to `env.EdgeServer.HTTP2AdapterHandler().ServeHTTP(...)` during scenario execution.
- **FR-2.2**: All HTTP/2 attack and baseline vectors (`VECTOR-01`, `VECTOR-02`, `VECTOR-03`, `VECTOR-07`, `VECTOR-08`) must execute as real wire-level network requests transmitted over cleartext TCP/h2c to `env.EdgeAddr`.
- **FR-2.3**: For HTTP/2 requests, the harness shall utilize an h2c-capable client (e.g., Prior Knowledge HTTP/2 client via `golang.org/x/net/http2` or raw wire framing) capable of:
  - Transmitting HTTP/2 frames directly over an unencrypted TCP connection.
  - Delivering requests with custom, duplicate, or malformed headers (`Transfer-Encoding: chunked`, duplicate `Content-Length`, length mismatches, and CRLF byte sequences).
  - Accurately capturing HTTP edge status codes ($400\text{ Bad Request}$, $200\text{ OK}$, $500\text{ Internal Server Error}$) or protocol-level stream resets (`RST_STREAM`, `GOAWAY`).
- **FR-2.4**: For HTTP/1.1 requests (`VECTOR-04`, `VECTOR-05`, `VECTOR-06`, `VECTOR-09`, `VECTOR-10`), the harness shall continue to execute over raw TCP connections to `env.EdgeAddr`, validating fail-fast socket closures (`FIN`/`RST`) and status line responses.

### FR-3: Upstream Header Leakage Verification in Live Environment
- **FR-3.1**: For `VECTOR-08` (Pseudo-Header Upstream Isolation), header leakage verification must operate via network response inspection rather than in-process memory reflection.
- **FR-3.2**: Because all three backend origin servers (`backends/node/server.js`, `backends/python/server.py`, `backends/go/main.go`) and the in-process mock server echo received HTTP headers in the JSON response body under the `"headers"` key upon receiving a `POST /echo` request, the harness shall:
  1. Ingest the response body returned by the edge gateway for `VECTOR-08`.
  2. Parse the JSON structure and extract the `"headers"` map/dictionary.
  3. Verify that zero HTTP/2 pseudo-headers (headers starting with a colon `:`, such as `:path`, `:authority`, `:method`, `:scheme`, `:protocol`, or `:custom-pseudo`) are present in the echoed upstream headers.
- **FR-3.3**: If any colon-prefixed pseudo-header is detected in the echoed upstream headers, `VECTOR-08` shall be marked as failed (`res.Stage1Passed = false`) with an explicit failure reason detailing the leaked header field.

### FR-4: Dual Execution Mode Compatibility & Reporting Parity
- **FR-4.1**: The runner shall support two fully functional execution modes selectable via CLI flags:
  - `--standalone`: Bootstraps in-process loopback listeners for Toron and all three simulated backends, executing completely in memory and loopback sockets with zero external dependencies.
  - `--docker` (or `-standalone=false -edge-addr <host:port>`): Connects directly to a live containerized Toron edge gateway fronting containerized Node.js, Python, and Go backends.
- **FR-4.2**: Both execution modes must execute all 30 test scenarios (10 vectors $\times$ 3 backends) to completion.
- **FR-4.3**: Both execution modes must emit fully populated, schema-identical report files:
  - Machine-readable JSON: `benchmarks/results/multihop_report.json`
  - Publication Markdown: `benchmarks/results/multihop_report.md`
- **FR-4.4**: The report schema must preserve existing telemetry fields: `timestamp`, `target_edge`, `execution_mode`, `total_scenarios`, `passed_scenarios`, `failed_scenarios`, `overall_verdict`, `desynchronization_detected`, `pool_poisoning_detected`, `backends`, and `results`.
- **FR-4.5**: The `execution_mode` field in generated reports must indicate `"Standalone In-Process (Pure Go)"` or `"Live Multi-Container (Docker Compose)"` respectively.

## 4. Non-Functional Requirements

### NFR-1: Zero External Dependencies
- The multi-hop testbed runner (`runner.go`) and test suite must strictly use the Go standard library (`net`, `net/http`, `context`, `sync`, `time`, `encoding/json`, `fmt`, `bufio`, `strings`, `errors`, `syscall`) and `golang.org/x/net/http2` (already present and vendored in `go.mod`).
- No additional third-party dependencies, curl bindings, or external binaries may be introduced into `go.mod`.

### NFR-2: Bounded Socket Timeouts & Hang Prevention
- All network operations—including TCP dialing, h2c client handshakes, request transmission, and response body reads—must enforce bounded deadlines:
  - Connect/Dial timeout: $\le 2\text{ seconds}$.
  - Overall per-scenario probe timeout: $\le 3\text{ seconds}$.
- The test harness must never hang indefinitely on hung connections, dropped frames, or unacknowledged streams.

### NFR-3: Strict Historical Run Retention Compliance (REQ-119)
- Execution of `benchmarks/multihop/run_multihop.sh` (both `--standalone` and `--docker` modes) must fully comply with [`REQ-119`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-119.md):
  - Archive outputs in `benchmarks/results/history/<timestamp>/`.
  - Maintain latest canonical copies in `benchmarks/results/`.
  - Atomically update `benchmarks/results/history/manifest.json`.
  - Integrate cleanly with master benchmark orchestrator `benchmarks/run_all.sh`.

### NFR-4: Thread Safety & Concurrency Cleanliness
- The harness code and automated tests must pass `go test -race -count=1 ./benchmarks/multihop/...` with zero race condition detections.

### NFR-5: Deterministic Error Diagnostics
- When a probe or canary fails in live mode, the harness must record detailed diagnostic telemetry in `res.FailureReason` (including status code, raw error message, and response body snippet) to facilitate rapid triage.

## 6. Constraints, Assumptions & Open Questions

### 6.1 Constraints
1. **Zero External Dependencies**: Must not introduce third-party test runners, curl wrappers, or external npm/python packages into the Go runner.
2. **Prior Knowledge h2c Protocol**: Cleartext HTTP/2 (`h2c`) direct communication without TLS negotiation must be supported over standard TCP sockets.
3. **Container Network Isolation**: Docker Compose services run on an isolated bridge network (`multihop-net`), exposing edge gateway on port `8080` to the host test harness.

### 6.2 Assumptions
1. **Echo Contract**: All three backend origin services (`node`, `python`, `go`) consistently implement the `POST /echo` contract, returning a JSON response containing the `"headers"` object.
2. **Docker Availability**: When `--docker` is specified, the Docker daemon and Docker Compose plugin are operational on the host system.
3. **Port Availability**: Port `8080` is available on `127.0.0.1` for the duration of the multi-hop containerized run.

### 6.3 Open Questions & Clarifications
- *Question 1*: For `VECTOR-01`, `VECTOR-02`, and `VECTOR-03`, how should raw malformed HTTP/2 frames (which standard compliant HTTP/2 clients might refuse to serialize) be transmitted over TCP?
  - *Resolution Direction*: The harness can either construct raw HTTP/2 frames (Connection Preface + SETTINGS + HEADERS frame) directly using standard Go byte buffers / `golang.org/x/net/http2/hpack`, or configure `http2.Transport` with prior knowledge h2c. The detailed framing approach will be formally decided by the Architect in `ADR-120`.
