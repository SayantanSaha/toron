# TC-066 - Verification of Access Log CRLF Sanitization and Control Character Filtering

## Objective

Verify that text-mode Combined Log Format (CLF) access logging sanitizes all client-controlled fields (`User-Agent`, `Referer`, `ClientIP`, `Method`, `Path`, `Protocol`), eliminating carriage returns, line feeds, and non-printable control characters, thereby preventing CRLF log injection (CWE-117) and synthetic log entry forgery.

## Test Cases

### TC-066-01: Zero-Allocation Clean String Fast-Path
- **Setup**: Provide standard benign HTTP header values (e.g. standard Chrome User-Agent).
- **Action**: Pass string to `SanitizeLogField`.
- **Expected Outcome**:
  - Exact input string is returned unmodified.
  - Zero heap allocations (`0 B/op`, `0 allocs/op` on benchmark).

### TC-066-02: Control Character Stripping & Normalization
- **Setup**: Provide strings containing `\r`, `\n`, null bytes (`\x00`), bell (`\x07`), tab (`\t`), and delete (`\x7f`).
- **Action**: Invoke `SanitizeLogField`.
- **Expected Outcome**:
  - Control characters are replaced with space (`' '`).
  - No control characters or delimiters remain in the output string.

### TC-066-03: Multi-Line CRLF Log Forgery Prevention in LogAccess
- **Setup**: Initialize `LogManager` configured with text access logging.
- **Action**: Call `LogAccess` with an `AccessLogEntry` where `Method`, `Path`, `UserAgent`, and `Referer` contain embedded `\r\n` characters injecting a fake CLF log entry (`10.0.0.1 - - [05/Sep/2026:12:00:00 +0000] "GET /admin HTTP/1.1" 200 9999`).
- **Expected Outcome**:
  - Exactly one physical newline is written to the destination sink.
  - The access log file contains strictly 1 line.
  - Injected headers do not create a separate synthetic log entry or spoof HTTP response status.
