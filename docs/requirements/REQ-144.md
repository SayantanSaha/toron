# REQ-144 - AutoBanManager Lifecycle Synchronization Across Zero-Downtime WAF Hot Reloads

## 1. Description & Problem Statement

As documented in [`AN-005`](../analysis/AN-005.md), Toron's WAF engine and internal management API exhibit a split-brain state following zero-downtime configuration hot reloads (`config.yaml`).

When `WAFEngine.Reload()` executes:
1. It instantiates a new `AutoBanManager` instance and closes the previous one.
2. The internal management API (`/internal/api/security/*`) retains an orphaned pointer to the initial `AutoBanManager` instance established during startup.
3. Administrative unban operations (`POST /internal/api/security/unban`) modify only the orphaned instance, while incoming traffic enforcement checks the active instance.
4. Active sweeper background flushes periodically overwrite persistent disk storage (`banned_ips.json`), discarding unban changes and trapping client IPs in an unliftable ban state.

This requirement defines the lifecycle synchronization mechanisms required to guarantee that auto-ban state, administrative mutations, and hot reloads operate seamlessly without reference desynchronization or loss of in-memory strikes and active bans.

---

## 2. Functional Requirements

### 2.1 Dynamic Management API Resolution
- **REQ-144.1**: `InternalAPIConfig` in `pkg/server` MUST support a dynamic provider function `AutoBanManagerFunc func() *waf.AutoBanManager`.
- **REQ-144.2**: All internal security API handlers (`/internal/api/security/banned-ips`, `/internal/api/security/unban`, `/internal/api/security/ban`) MUST resolve the active manager dynamically via `cfg.GetAutoBanManager()`.
- **REQ-144.3**: `cmd/toron/main.go` MUST provide an `AutoBanManagerFunc` closure that queries `globalWafEngine.AutoBanManager()` on every request.

### 2.2 In-Place AutoBanManager Reconfiguration
- **REQ-144.4**: `AutoBanManager` MUST provide an `UpdateConfig(cfg AutoBanConfig, logger *AuditLogger)` method that updates thresholds, sliding window duration, ban duration, and IP whitelists without clearing active bans or strike records.
- **REQ-144.5**: In `WAFEngine.Reload()`, if an `AutoBanManager` already exists and auto-ban remains enabled, it MUST update the existing manager in place rather than creating a new instance and orphaning active goroutines or pointers.
- **REQ-144.6**: If auto-ban is transitioned from disabled to enabled, a new `AutoBanManager` MUST be initialized. If transitioned from enabled to disabled, the existing manager MUST be closed and set to nil.

---

## 3. Acceptance Criteria

1. Administrative unban requests (`POST /internal/api/security/unban`) MUST successfully lift bans on the live WAF engine even after one or multiple configuration hot reloads.
2. In-memory active bans and strike counters MUST be preserved across WAF configuration reloads that do not modify the persistence file.
3. No background goroutines or orphaned sweeper loops are leaked upon configuration reloads.
4. All existing WAF, auto-ban, and config tests pass without regression.
