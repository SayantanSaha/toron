# REQ-109 - Header Field-Name Token Grammar Hardening (RFC 7230 §3.2)

## 1. Description

Peer review audits of Paper 1 and Paper 2 (`SRC-04`, `ReviewTaskSummary.md`, `AER-001`, `AER-002`) identified a protocol grammar validation defect in Toron's HTTP/1.1 parser:

1. **Permissive Header Field-Name Validation**:
   In `pkg/httpparser/parser.go` (lines 98-101), the header parser extracts the field-name substring preceding the colon delimiter (`k := lineTrimmed[:colonIdx]`) and checks solely for empty keys and whitespace:
   ```go
   if k == "" || strings.ContainsAny(k, " \t\r\n") {
       return nil, fmt.Errorf("%w: whitespace in header field-name", ErrBadRequest)
   }
   ```
   The parser fails to validate that the field-name conforms to the strict ABNF token grammar mandated by RFC 7230 §3.2 and RFC 5234.

2. **Semantic Gap & Differential Attack Exposure (CWE-444 / CWE-113)**:
   Because non-token characters are not rejected, Toron currently accepts header field-names containing:
   - Delimiters: `"@"`, `"("`, `")"`, `","`, `"/"`, `";"`, `"<"`, `"="`, `">"`, `"?"`, `"["`, `"\"`, `"]"`, `"{"`, `"}"`, `"""`.
   - Control characters: NUL (`0x00`), ESC (`0x1B`), BEL (`0x07`), DEL (`0x7F`).
   - Non-ASCII / High bytes: Bytes in range `0x80` to `0xFF`.

   When Toron acts as an edge proxy or reverse gateway fronting upstream HTTP engines (e.g. Node.js `llhttp`, NGINX, Envoy, Python Uvicorn/Gunicorn, Go `net/http`), upstream servers that enforce strict RFC 7230 token grammar will reject or differentially interpret such headers. This discrepancy creates opportunities for:
   - **Parser Differential Attacks**: An attacker can smuggle hop-by-hop headers or security-sensitive routing tokens that bypass Toron's WAF or routing inspection but are parsed or normalized differently by upstream backends.
   - **Header Injection & Smuggling**: Downstream systems that strip or mutate invalid characters may introduce header splitting or variable overwrite vulnerabilities.

3. **RFC 7230 §3.2.6 Token Grammar Specification**:
   According to RFC 7230 §3.2:
   ```abnf
   header-field   = field-name ":" OWS field-value OWS
   field-name     = token
   ```
   And RFC 7230 §3.2.6 defines:
   ```abnf
   token          = 1*tchar
   tchar          = "!" / "#" / "$" / "%" / "&" / "'" / "*"
                  / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~"
                  / DIGIT / ALPHA
   ```
   Any character not explicitly in `tchar` is invalid in an HTTP/1.1 header field-name.

## 2. Acceptance Criteria

### AC-1: Strict RFC 7230 §3.2.6 Token Grammar Validation
- In `pkg/httpparser/parser.go`:
  1. Every character in header field-name `k` must strictly belong to the `tchar` character set:
     - `DIGIT` (`0`-`9`, ASCII `0x30`-`0x39`)
     - `ALPHA` (`a`-`z`, `A`-`Z`, ASCII `0x61`-`0x7A`, `0x41`-`0x5A`)
     - Special characters: `!`, `#`, `$`, `%`, `&`, `'`, `*`, `+`, `-`, `.`, `^`, `_`, `` ` ``, `|`, `~`
  2. Reject any header field-name containing:
     - Delimiters: `"@"`, `"("`, `")"`, `","`, `"/"`, `";"`, `"<"`, `"="`, `">"`, `"?"`, `"["`, `"\"`, `"]"`, `"{"`, `"}"`, `"""`
     - Whitespace: Space (`0x20`), Tab (`0x09`), CR (`0x0D`), LF (`0x0A`)
     - Control characters: ASCII `0x00`-`0x1F`, `0x7F`
     - Non-ASCII / High bytes: Bytes `0x80`-`0xFF`
     - Empty field-name (`len(k) == 0`)

### AC-2: Optimized Zero-Allocation Lookup Table
- In `pkg/httpparser/parser.go`:
  1. Character validation must be implemented using a precomputed static lookup table (`var validTokenTable [256]bool` or bitmask).
  2. Validation must execute in $O(N)$ time where $N = \text{len}(k)$, allocating 0 heap memory during validation.

### AC-3: Fail-Fast Rejection & Connection Teardown
- In `pkg/httpparser/parser.go`:
  1. If any non-token character is detected in `k`:
     - If the non-token character is whitespace, return `fmt.Errorf("%w: whitespace in header field-name", ErrBadRequest)` to preserve backward compatibility with existing whitespace error assertions.
     - Otherwise, return `fmt.Errorf("%w: invalid header field-name token grammar", ErrBadRequest)`.
  2. The returned error wraps `ErrBadRequest`.
  3. In `pkg/server/server.go`, receiving `ErrBadRequest` ensures an immediate `400 Bad Request` response with `Connection: close` and physical TCP socket teardown.

### AC-4: Pseudo-Header & Delimiter Boundary Isolation
- In `pkg/httpparser/parser.go`:
  1. In HTTP/1.1 wire requests, a header beginning with a colon (e.g. `:authority: example.com`) produces `colonIdx == 0`, meaning `k == ""`, which is rejected with `ErrBadRequest`.
  2. HTTP/1.1 request field-names are strictly validated as RFC 7230 tokens.

### AC-5: Automated Unit & Benchmark Test Suite (TC-109)
- In `pkg/httpparser/parser_test.go`:
  1. **Non-Token Delimiter Rejections**: Explicit test vectors verifying rejection of `@`, `(`, `)`, `,`, `/`, `;`, `<`, `=`, `>`, `?`, `[`, `\`, `]`, `{`, `}`, `"`.
  2. **Control Character Rejections**: Test vectors verifying rejection of NUL (`0x00`), ESC (`0x1B`), BEL (`0x07`), DEL (`0x7F`).
  3. **High Byte Rejections**: Test vectors verifying rejection of non-ASCII bytes (`0x80`, `0xFF`, UTF-8 sequences).
  4. **Valid RFC 7230 Headers**: Test asserting valid RFC 7230 headers with symbols (e.g. `X-Custom_Header.1!#$`, `Content-Type`, `Accept-Encoding`) parse successfully.
  5. **Microbenchmark**: `BenchmarkParseRequest_InvalidTokenRejection` verifying nanosecond-level fail-fast rejection without heap allocations.

### AC-6: Zero Third-Party Dependencies & Concurrency Safety
- All changes must strictly use Go standard library packages.
- All test suites must execute with zero data races under `go test -v -race -count=1 ./...`.

---

## 3. Rationale

HTTP header field-name token validation is a fundamental RFC requirement. Allowing arbitrary punctuation, control characters, or binary bytes in header keys creates severe semantic gaps between edge proxies and backend origin servers, opening vectors for HTTP request smuggling (CWE-444) and header injection (CWE-113). Enforcing strict RFC 7230 §3.2.6 token grammar at the HTTP parser boundary ensures robust ingress defense and guarantees consistent wire-level interpretation across heterogeneous upstream services.

---

## 4. Constraints

- Pure Go standard library; zero third-party dependencies.
- Zero allocation during header validation to preserve Toron's high-throughput characteristics.
- Complete backward compatibility with valid RFC 7230 headers.
