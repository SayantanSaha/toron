# REQ-141 - Modularization of Toron Gateway Observability Dashboard into Native ES Modules

## 1. Description & Problem Statement

### 1.1 Context & Background
The Toron Edge Gateway Control Center dashboard ([`public/app.js`](../../public/app.js)) delivers real-time observability across reverse proxy routes, traffic topology, security incidents, and upstream backend health. The frontend is served directly by the gateway at `/internal/dashboard/` and features pure vector SVG graphics and zero external runtime dependencies.

### 1.2 Identified Problems with Monolithic Architecture
Currently, the entire client application is encapsulated within a single monolithic script file ([`public/app.js`](../../public/app.js)) comprising 1,663 lines of code (88 KB). While performing efficiently at runtime, this single-file structure introduces significant software engineering and maintenance challenges:
1. **Tight Coupling & Lack of Encapsulation**: Utility functions, global state, telemetry adapters, algorithmic derivations (`buildDataModel`), SVG chart engines, drawer managers, and view rendering handlers all reside in a single scope.
2. **Review & Collaboration Bottlenecks**: Any modification to a specific view (e.g. upstreams or WAF alerts) requires modifying `app.js`, making code reviews difficult and creating git merge conflicts during concurrent development.
3. **Test Inefficiency**: Testing specific logic (such as subpath rollups or moving average rate smoothing) requires loading the entire 1,663-line file inside a Node.js VM context rather than importing discrete, isolated modules.

### 1.3 Solution Rationale: Native ES Modules without Framework Overhead
An evaluation of frontend frameworks (React, Vue, Svelte) concluded that introducing an external framework contradicts Toron's core principles by:
- Adding unnecessary Node.js build stages to [`Dockerfile`](../../Dockerfile) and [`Makefile`](../../Makefile).
- Increasing container appliance size beyond the target 15 MB boundary.
- Introducing third-party supply-chain dependencies into a security-critical edge proxy.

In contrast, modularizing `public/app.js` into **native browser ECMAScript Modules (`<script type="module">`)** achieves clean separation of concerns, high maintainability, and discrete testability while preserving zero build steps, zero third-party dependencies, and instant runtime performance.

## 2. Functional Requirements

### 2.1 Directory Structure & Modular Separation
- **REQ-141.1: Modular File Organization**:
  The dashboard codebase MUST be partitioned into dedicated, cohesive ES modules under `public/js/`:
  - `public/js/app.js`: Application entrypoint, routing orchestration (`go()`, `mountView()`), and global event listeners.
  - `public/js/state.js`: State machine (`state`), time range definitions (`RANGES`), and theme management.
  - `public/js/utils.js`: DOM helpers (`$`, `$$`), string escaping (`esc`), metric formatters (`fmt`), and datetime formatters (`dtFmt`, `ago`, `hms`).
  - `public/js/api.js`: Telemetry backend polling adapter (`fetchBackendData`) querying `/internal/api/*` via `Promise.allSettled`.
  - `public/js/model.js`: Telemetry data model constructor (`buildDataModel`), hierarchical subpath rollups, moving-average smoothing, upstream route pool disaggregation, and error tone escalation.
  - `public/js/components/`:
    - `icons.js`: Vector icon renderers (`ICON`, `pill`, `TI`, `TONE`).
    - `charts.js`: SVG sparklines (`spark`), time-series line charts (`chart`), and latency histograms (`histo`).
    - `sankey.js`: Vector SVG traffic flow ribbon visualizer (`flow`).
    - `drawer.js`: Slide-out inspector drawer controller (`openDrawer`, `closeDrawer`, `renderDrawer`).
  - `public/js/views/`:
    - `overview.js`: Gateway health banner, signals matrix, and traffic flow.
    - `routes.js`: Route catalog table, search filter, and SLO status.
    - `upstreams.js`: Disaggregated upstream pool cards with 48-tick probe history strips.
    - `logs.js`: Live tailing request log table, route filter, and waterfall trigger.
    - `certs.js`: ACME certificate status and expiration progress bars.
    - `modules.js`: Compiled engine reactors and Go runtime diagnostics.
    - `alerts.js`: WAF incident log and auto-ban IP management.
    - `console.js`: Interactive endpoint diagnostic runner (`/proxy-test`).

- **REQ-141.2: HTML Script Entrypoint**:
  [`public/index.html`](../../public/index.html) MUST load the modular dashboard using `<script type="module" src="./js/app.js"></script>` (or backward-compatible entrypoint).

- **REQ-141.3: 100% Behavioral & Visual Parity**:
  All 8 views, slide-out inspector drawers (Route detail and Request Trace waterfall), theme switching (light/dark with flicker prevention), live tailing pause/resume, and time-range selection MUST function identically to the pre-refactor state.

## 3. Non-Functional Requirements

- **REQ-141.4: Zero External Runtime & Build Dependencies**:
  - The frontend MUST NOT require any external JavaScript runtime framework or third-party npm libraries.
  - The build process MUST NOT require a JavaScript bundler (e.g., Vite, Webpack, Rollup, or esbuild).
  - [`Dockerfile`](../../Dockerfile) MUST remain a single-stage Go build that directly copies static assets.

- **REQ-141.5: Performance Budget**:
  - Total transferred JavaScript size across all modules MUST not exceed 100 KB uncompressed (~25 KB compressed).
  - Initial load execution time for module graph resolution and rendering MUST remain under 10 ms.

- **REQ-141.6: Automated Test Suite Compatibility**:
  - The existing test suite ([`tests/dashboard_telemetry_test.js`](../../tests/dashboard_telemetry_test.js)) MUST be updated or maintained to verify all TC-139 and TC-140 test cases against the modular components without regressions.

- **REQ-141.7: Strictly Relative Links**:
  - All documentation links and module import paths (`from './...'`) MUST strictly use relative links. Never use absolute filesystem paths or machine URIs.
