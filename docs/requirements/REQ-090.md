# REQ-090 - Hop-by-Hop Header Stripping and Protocol Compliance in REST-to-gRPC Transcoder

## Description

The Toron REST-to-gRPC Transcoding Engine ([`Engine`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L24)) MUST sanitize and strip all standard and dynamic connection-specific (hop-by-hop) headers from incoming HTTP/1.1 REST client requests prior to forwarding HTTP/2 requests to upstream gRPC backends. Furthermore, the engine MUST strictly enforce that the HTTP/2 `TE` header contains only `"trailers"` without client pollution, ensuring strict compliance with [RFC 7540 §8.1.2.2](https://datatracker.ietf.org/doc/html/rfc7540#section-8.1.2.2), [RFC 9113 §8.2.2](https://www.rfc-editor.org/rfc/rfc9113#section-8.2.2), [RFC 7230 §6.1](https://datatracker.ietf.org/doc/html/rfc7230#section-6.1), and [RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1). This completely remediates vulnerability [`SEC-29`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L402-L410) ([CWE-444](https://cwe.mitre.org/data/definitions/444.html), [CWE-436](https://cwe.mitre.org/data/definitions/436.html)), preventing upstream gRPC server rejections, HTTP/2 protocol errors (`PROTOCOL_ERROR` `RST_STREAM`), and unnecessary `HTTP 502 Bad Gateway` failures.

## Problem Statement

As documented in [`SEC-29`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L402-L410) and [`SR-081 Finding 7`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-081.md#L161-L170), [`Engine.HandleTranscode`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L89) in `pkg/transcoder/transcoder.go` blindly copies client request headers to the outgoing upstream gRPC HTTP/2 request:

### 1. Indiscriminate Header Forwarding ([`pkg/transcoder/transcoder.go:L200-L212`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L200-L212))
```go
grpcReq.Header.Set("Content-Type", "application/grpc")
grpcReq.Header.Set("TE", "trailers")

// Forward client headers
if req.Header != nil {
    for k, vv := range req.Header {
        if !strings.HasPrefix(strings.ToLower(k), "content-") {
            for _, v := range vv {
                grpcReq.Header.Add(k, v)
            }
        }
    }
}
```

### 2. Violations of HTTP/2 Specification (RFC 7540 §8.1.2.2 / RFC 9113 §8.2.2)
- RFC 7540 §8.1.2.2 states:
  > *"HTTP/2 does not use the Connection header field to indicate connection-specific header fields... An endpoint MUST NOT generate an HTTP/2 message containing connection-specific header fields; any message containing connection-specific header fields MUST be treated as malformed."*
- Prohibited connection-specific fields copied to upstream gRPC calls include:
  - `Connection` (e.g. `Connection: keep-alive`)
  - `Keep-Alive`
  - `Proxy-Connection`
  - `Transfer-Encoding`
  - `Upgrade`

### 3. TE Header Pollution & gRPC Malformation
- In gRPC over HTTP/2, the `TE` header must contain only `"trailers"` (RFC 7540 §8.1.2.2: *"when the TE header field is present, it MUST NOT contain any value other than 'trailers'"*).
- When a client sends `TE: gzip` or `TE: deflate`, `grpcReq.Header.Add(k, v)` appends the client's token, resulting in malformed multi-value `TE: trailers, gzip` headers.

### 4. Omission of Dynamic RFC 7230 §6.1 Connection Token Stripping
- Under RFC 7230 §6.1, any header names listed in the comma-separated `Connection` header value (e.g. `Connection: X-Dynamic-Hop, close`) are designated as hop-by-hop and must be stripped before forwarding. `pkg/transcoder` currently ignores `Connection` tokens.

### 5. Upstream gRPC Rejections & 502 Bad Gateway
- Standards-compliant gRPC servers (such as Go `google.golang.org/grpc`, Envoy, C-gRPC, and Netty) inspect HTTP/2 headers and immediately terminate requests containing connection-specific headers with `RST_STREAM (PROTOCOL_ERROR)`.
- Toron registers this reset as a network failure and returns `HTTP 502 Bad Gateway` to legitimate clients.

## Acceptance Criteria

### 1. Static Hop-by-Hop Header Sanitization
- Prior to forwarding request headers to the upstream gRPC HTTP/2 client in [`Engine.HandleTranscode`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L89), the transcoder MUST strip all standard hop-by-hop headers:
  - `connection`
  - `keep-alive`
  - `proxy-authenticate`
  - `proxy-authorization`
  - `te`
  - `trailer`
  - `trailers`
  - `transfer-encoding`
  - `upgrade`
  - `proxy-connection`
- Case-insensitivity MUST be enforced during header evaluation (matching lower-cased header keys).

### 2. Dynamic Connection Token Header Stripping (RFC 7230 §6.1 / RFC 9110 §7.6.1)
- If the incoming client request contains a `Connection` header:
  - The transcoder MUST parse all comma-delimited tokens in the header value.
  - Any header matching a token from the `Connection` header (case-insensitive, trimmed) MUST be discarded from the outgoing request.

### 3. Strict `TE: trailers` Invariant for gRPC
- The outgoing HTTP/2 gRPC request MUST strictly contain `TE: trailers`.
- Client-supplied `TE` headers (e.g. `TE: gzip`, `TE: deflate`) MUST be discarded and MUST NOT be appended or merged into the gRPC request headers.

### 4. Host Header Sanitization
- The incoming client `Host` header MUST NOT be forwarded to the outgoing `grpcReq.Header`.
- The outgoing `grpcReq` MUST rely on its target URL to establish the upstream `:authority` pseudo-header, avoiding upstream virtual-host mismatches.

### 5. Content Header Handling
- Existing exclusion of headers with prefix `content-` MUST be preserved, ensuring that client `Content-Length`, `Content-Type`, and `Content-Encoding` headers do not conflict with the generated `application/grpc` payload.

### 6. Full-Fidelity End-to-End Metadata Header Preservation
- All legitimate end-to-end request headers (such as `Authorization`, `X-Request-ID`, `Traceparent`, `B3`, `X-Custom-*`, `User-Agent`, `Accept`) MUST be preserved and forwarded to the upstream gRPC service intact.

### 7. Zero Third-Party Dependencies & Concurrency Safety
- Implementation MUST use strictly the Go standard library (`net/http`, `strings`, `sync`).
- Must be 100% race-clean and verified under `go test -race ./pkg/transcoder/...`.
