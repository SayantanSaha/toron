# SR-053 - Security Review of HTTP-to-HTTPS Redirection and Route-Level Exemption Overrides

## Executive Summary

The Security Analyst (AGENT-007) has conducted a comprehensive security review of the cleartext HTTP-to-HTTPS redirection and route-level exemption override mechanism implemented in Toron (`pkg/server/server.go`, `pkg/router/router.go`, `pkg/config/config.go`, `pkg/proxy/proxy.go`, and `cmd/toron/main.go`).

This review evaluates four primary security vectors:
1. **Open Redirect Vulnerabilities (CWE-601)**: Ensuring malicious clients cannot manipulate incoming `Host` headers to redirect unsuspecting users to untrusted external domains.
2. **HTTP Response Splitting & CRLF Injection (CWE-113)**: Validating that `Host` headers containing carriage returns (`\r`), line feeds (`\n`), tabs, spaces, backslashes, or control sequences cannot inject arbitrary HTTP headers or fabricate response bodies.
3. **Transport Protocol Boundary Enforcement & Route Isolation**: Verifying that routes lacking `redirect_http: false` cannot be accessed in cleartext, guaranteeing end-to-end transport layer security.
4. **Denial of Service (DoS) and Resource Exhaustion (CWE-400)**: Ensuring the auxiliary HTTP redirect listener enforces bounded timeouts, reuses the zero-allocation reactor thread pool, and terminates cleanly during application lifecycle shutdown.

Based on automated testing and threat model analysis, the implementation enforces robust defensive controls across all vectors and is **APPROVED**.

---

## Detailed Threat Vector Analysis

### 1. Open Redirect & Host Header Manipulation (CWE-601)

#### Threat Vector
In naive HTTP-to-HTTPS redirect implementations, servers often trust incoming `Host` headers verbatim:
```http
Location: https:// + req.Host + req.RequestURI
```
If an edge gateway accepts arbitrary `Host` values, attackers can trigger an Open Redirect by crafting requests like `Host: attacker.com`, enticing users into credential phishing or session hijacking.

#### Defensive Controls in Toron
Toron implements strict Host header validation in `serveHTTPRedirect`:
1. **Empty Host Rejection**: If the incoming `Host` header is missing, Toron halts redirect generation and immediately responds with `HTTP 400 Bad Request`.
2. **Character Whitelist / Blacklist Enforcement**:
   ```go
   if strings.ContainsAny(rawHost, "\r\n\t /\\") {
       res.SetStatus(http.StatusBadRequest)
       ...
   }
   ```
   Any Host header containing spaces, slashes, backslashes, tabs, or newlines is rejected before redirect URL generation.
3. **Port Stripping**: Explicit client port indicators (e.g. `example.com:80`) are safely split via `net.SplitHostPort` to avoid duplicate or forged port suffixes in the redirect `Location` header.

### 2. HTTP Response Splitting & CRLF Injection (CWE-113)

#### Threat Vector
If an attacker injects `\r\nSet-Cookie: malicious=payload` into the `Host` or `RequestURI` fields, an un-sanitized redirect response could split the HTTP stream and inject attacker-controlled headers or bodies into downstream caches.

#### Defensive Controls in Toron
1. **Pre-processing Guard**: `strings.ContainsAny(rawHost, "\r\n\t /\\")` immediately aborts any Host containing CRLF sequences.
2. **Serialization Guard**: `Response.Serialize` in `pkg/httpparser/response.go` independently sanitizes every outgoing header key and value via `sanitizeHeader` before writing bytes to the wire.

### 3. Cleartext Protocol Boundary & Route Isolation

#### Threat Vector
A misconfigured or loosely matched routing rule could accidentally expose sensitive internal APIs or authenticated endpoints over unencrypted HTTP.

#### Defensive Controls in Toron
1. **Explicit Opt-in Semantics**: By default, `redirect_http` evaluates to `true` for all routes. Cleartext HTTP access requires an explicit, deliberate override:
   ```yaml
   redirect_http: false
   ```
2. **Granular Matching**: `router.ShouldRedirectHTTP` performs exact host and path prefix matching before granting exemption. If an incoming HTTP request does not match an exempt route with `redirect_http: false`, Toron unconditionally returns `HTTP 301 Moved Permanently`.

### 4. Lifecycle & Resource Boundedness (CWE-400)

#### Controls
1. The HTTP redirect server leverages Toron's high-performance `reactor.Reactor` engine with non-blocking I/O, configurable `ReadTimeout`, `WriteTimeout`, and bounded worker pools (`WorkerPoolSize`).
2. Both the primary TLS listener and the auxiliary HTTP redirect listener register with the same `shutdownCtx`. When `SIGTERM` or `SIGINT` is received, both servers close listeners atomically and drain inflight connections within a 5-second graceful window.

## Conclusion & Sign-Off

The HTTP-to-HTTPS redirect engine and route-level exemption override mechanism satisfy all security requirements outlined in `REQ-057` and `ADR-052`. No security regressions were identified.

**Status**: APPROVED
