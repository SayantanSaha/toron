# REQ-073 - HTTP Header Field-Name Whitespace Rejection (RFC 7230 §3.2.4)

## Description

The Toron HTTP parser shall strictly validate header lines and reject any request where whitespace (space or tab) appears between the header field-name and the colon delimiter, in accordance with RFC 7230 §3.2.4.

No whitespace is permitted between the header field-name and the colon. Allowing whitespace before the colon permits attackers to conceal critical hop-by-hop or framing headers (such as `Transfer-Encoding : chunked`) from gateway validation while triggering chunked processing on downstream microservices.

## Acceptance Criteria

### 1. Strict Whitespace Detection Before Colon
- When parsing header lines in `httpparser.ParseRequest`, the header field-name token preceding the colon (`:`) shall be inspected for space (`0x20`), horizontal tab (`0x09`), carriage return (`0x0D`), or line feed (`0x0A`).
- If any whitespace character is found within or immediately preceding the colon in the field-name token (e.g. `Transfer-Encoding : chunked` or `Host\t: example.com`), the parser shall immediately terminate header parsing.

### 2. Immediate Error Response
- The request shall be rejected with `HTTP 400 Bad Request`.
- The connection shall not be reused for persistent keep-alive requests.

### 3. Protocol Guard Preservation
- The fix shall ensure that all framing headers (`Transfer-Encoding`, `Content-Length`) and connection control headers are parsed unambiguously without leading or trailing whitespace evasion.

## Rationale

Differences in whitespace tolerance between proxies and backend servers are a primary vector for HTTP request smuggling (CWE-444). RFC 7230 §3.2.4 explicitly mandates that servers reject received request messages containing whitespace between field-name and colon with a 400 status code.

## Constraints

- Zero external runtime dependencies; Go standard library only.
- Negligible performance overhead during header scanning.
