# TC-126 - Verification of Adaptive Socket Deadline Amortization and Activity-Refreshed Streaming Timeouts

## 1. Test Suite Overview & Architectural Objectives

### 1.1 Executive Summary & Problem Context
High-concurrency reverse proxy benchmarks under [`REQ-121`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-121.md) demonstrated that Toron achieves competitive throughput (~24.5k RPS per container). However, CPU profiling and kernel tracepoint analysis revealed substantial CPU consumption in operating system kernel transitions during steady-state HTTP/1.1 keep-alive request handling.

In [`pkg/server/server.go:199`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L199) and [line 352](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L352), Toron executes two operating system socket system calls on every HTTP transaction within persistent keep-alive connections:
```go
conn.SetReadDeadline(time.Now().Add(timeout))
...
conn.SetWriteDeadline(time.Now().Add(s.config.WriteTimeout))
```

At 24.5k RPS, this results in **~49,000 socket deadline system calls per second** (`setsockopt` / `SO_RCVTIMEO` / `SO_SNDTIMEO` or runtime netpoller timer descriptor manipulation via `runtime.addtimer` / `runtime.modtimer`). Each system call incurs:
1. User-space to kernel-space context switches (ring-3 to ring-0 transitions).
2. CPU instruction cache (I-cache) and data cache (D-cache) evictions.
3. Runtime netpoller mutex lock contention and timer heap overhead.

Simultaneously, architectural analysis of persistent streaming connections—such as Server-Sent Events (SSE `text/event-stream`), live telemetry feeds, chunked transfer streams, and direct socket proxying per [`REQ-125`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-125.md)—exposed a critical architectural tension:
- **Premature Disconnects**: A static write deadline (e.g. 5 seconds into the future) set prior to response emission terminates healthy, long-lived streams prematurely when their lifetime exceeds `WriteTimeout`.
- **Slow Read Denial of Service ([CWE-400](https://cwe.mitre.org/data/definitions/400.html))**: Completely removing `SetWriteDeadline` on streaming connections violates [`REQ-005 §2`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-005.md#L40), [`TASK-004 §3`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-004.md#L41), [`ADR-083`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-083.md), and test suites [`TC-087`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-087.md) / [`TC-088`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-088.md), allowing malicious or stalled clients to pin worker goroutines and socket file descriptors indefinitely.
- **Slowloris Connection Starvation**: Eliminating `SetReadDeadline` exposes persistent keep-alive connections to byte-dribbling header starvation.

### 1.2 The Amortization & Activity-Refreshed Paradigm
To eliminate redundant kernel calls while preserving 100% compliance with Slowloris and Slow-Read DoS defenses, [`ADR-126`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-126.md) defines a three-part architectural strategy:

1. **Adaptive Deadline Amortization**: Wrap persistent client connections in a tracker struct ([`connDeadlineTracker`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L102-L111)). If an active socket deadline is already established and more than half the timeout window remains ($R > \tau/2$), redundant calls to `SetReadDeadline` and `SetWriteDeadline` are safely elided in userspace.
2. **Strict Idle-State Transition Alignment**: When an HTTP transaction finishes and the connection transitions to idle waiting for the next request header (`br.Buffered() == 0`), Toron immediately applies an explicit `IdleTimeout` via [`ForceSetReadDeadline`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L233-L240) and clears the amortization cache ([`ResetReadAmortization`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L253-L258)).
3. **Activity-Refreshed Streaming Write Deadlines**: In the persistent streaming chunk loop (`res.StreamBody`) and bidirectional relay routines ([`relayStreams`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L683-L757)), Toron refreshes the socket write deadline upon each successfully transferred and flushed chunk (`ForceSetWriteDeadline(time.Now().Add(WriteTimeout))`). Active streams survive indefinitely while stalled clients are severed within `WriteTimeout`.

## 2. Test Setup, Topology & Environmental Requirements

### 2.1 Subsystem Architecture & Interaction Topology

The execution topology across the deadline amortization and activity-refreshed streaming test harness is structured as follows:

```
+-----------------------------------------------------------------------------------------+
|                               Downstream HTTP / TCP Client                              |
+-----------------------------------------------------------------------------------------+
                                      |
                     Keep-Alive Bursts / Stream Requests / Idle Stalls
                                      v
+-----------------------------------------------------------------------------------------+
|                               Server Engine (pkg/server)                                |
|  - Server.handleConnection: wraps socket in connDeadlineTracker                         |
|  - State 1: Active Burst Parsing -> tracker.SetAmortizedReadDeadline(ReadTimeout)       |
|  - State 2: Response Serialization -> tracker.SetAmortizedWriteDeadline(WriteTimeout)   |
|  - State 3: Idle Transition (br.Buffered() == 0) -> tracker.ForceSetReadDeadline(Idle)  |
|  - State 4: Stream Chunks -> tracker.ForceSetWriteDeadline(now + WriteTimeout)          |
|  - State 5: Bidirectional Tunneling -> relayStreams with tracker amortization           |
+-----------------------------------------------------------------------------------------+
                                      |
                           Socket Deadline Decisions
                                      v
+-----------------------------------------------------------------------------------------+
|                      connDeadlineTracker (pkg/server/deadline.go)                       |
|  - Mutex-guarded cached state: lastReadDeadline, lastWriteDeadline, timeouts            |
|  - Amortization Filter: Skip syscall if (D != 0 && remaining > timeout / 2)             |
|  - Forced Overrides: ForceSetReadDeadline, ForceSetWriteDeadline, ResetReadAmortization |
|  - Zero-Timeout Bypass: If timeout == 0, clear deadline and elide 100% of syscalls      |
+-----------------------------------------------------------------------------------------+
                                      |
                             Delegated System Calls
                                      v
+-----------------------------------------------------------------------------------------+
|                              Operating System Kernel Socket                             |
|  - net.Conn.SetReadDeadline / net.Conn.SetWriteDeadline                                 |
|  - Syscall executed ONLY when amortization filter returns false or forced               |
|  - Kernel TCP stack enforces write timeouts on full send buffers (Slow-Read DoS guard)   |
+-----------------------------------------------------------------------------------------+
```

### 2.2 Environmental Prerequisites & Dependencies
- **Go Toolchain**: Go 1.24+ with CGO enabled for `-race` validation.
- **Dependencies**: Strictly zero third-party Go dependencies outside standard library (`testing`, `net`, `net/http`, `net/http/httptest`, `sync`, `sync/atomic`, `time`, `io`, `bytes`, `strings`, `context`, `errors`, `fmt`) and internal packages ([`pkg/config`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go), [`pkg/server`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go), [`pkg/proxy`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/tcp.go), [`pkg/httpparser`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/response.go), [`pkg/router`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go)).
- **Timing & Concurrency Tolerances**:
  - Keep-alive burst: 1,000 requests over persistent TCP connection completed within $< 2.0\text{s}$ (well within $2.5\text{s}$ half-window for $5.0\text{s}$ timeout).
  - Idle timeout enforcement: $200\text{ms}$ configured idle timeout must trigger socket closure within $200\text{ms} \pm 50\text{ms}$.
  - Long-lived streaming survival: 8 chunks spaced $1.5\text{s}$ apart (total duration $12.0\text{s}$) must survive without disconnect under `WriteTimeout = 3.0s`.
  - Slow-read client disconnect: Client halting socket reads under `WriteTimeout = 200ms` must be severed within $200\text{ms} \pm 100\text{ms}$ of send buffer saturation.

### 2.3 Mathematical Model & Amortization Invariants
Let $\tau$ denote the configured timeout duration (e.g. `ReadTimeout = 5s`).
When a deadline is established at timestamp $T_{\text{applied}}$, the underlying operating system deadline is set to:
$$D = T_{\text{applied}} + \tau$$

At current timestamp $T_{\text{now}}$, the remaining valid deadline duration is:
$$R(T_{\text{now}}) = D - T_{\text{now}}$$

The amortization condition evaluated by [`connDeadlineTracker`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L102-L111) is:
$$\text{SkipSyscall} \iff \left( \tau == \tau_{\text{last}} \right) \land \left( D \neq 0 \right) \land \left( R(T_{\text{now}}) > \frac{\tau}{2} \right)$$

- **Guaranteed Security Margin**: The condition ensures that at least $50\%$ of the configured timeout window ($\tau/2$) remains active on the socket. For a 5-second timeout, at least 2.5 seconds of execution window are guaranteed. Since typical Toron HTTP transactions complete in $< 5\text{ms}$, 2.5 seconds represents $> 500\times$ the required request processing duration.
- **Syscall Elision**: Any sequential request arriving while $R(T_{\text{now}}) > \tau/2$ bypasses the kernel system call entirely. Under 20k+ RPS keep-alive traffic, this elides $> 99\%$ of deadline system calls.
- **Immediate State Transitions**: When transitioning to idle state or sending streaming chunks, `ForceSetReadDeadline` or `ForceSetWriteDeadline` bypasses the amortization check and directly updates the kernel socket deadline.

## 3. Detailed Test Case Specifications

### TC-126.1: Deadline Amortization & Syscall Reduction Verification
- **Identifier**: `TC-126.1`
- **Target Subsystem**: Server Connection Deadline Amortization ([`pkg/server/deadline.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go), [`pkg/server/server.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go))
- **Test Implementation**: `TestServer_DeadlineAmortization_SyscallReduction` in [`pkg/server/server_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server_test.go)
- **Objective**: Verify that under rapid keep-alive HTTP request bursts over a persistent TCP connection, redundant `SetReadDeadline` and `SetWriteDeadline` system calls are safely bypassed, achieving $> 80\%$ (typically $> 99\%$) reduction in system calls compared to naive per-transaction deadlines, while completing all requests with HTTP 200 OK.
- **Traceability**: [`REQ-126 §2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-126.md#L86-L101), [`REQ-126 §3.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-126.md#L128-L132), [`TASK-149 WP-1.2`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-149.md#L113-L150), [`TASK-149 WP-4.1`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-149.md#L279-L289), [`ADR-126 §2.2`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-126.md#L140-L225).
- **Setup & Preconditions**:
  - Toron server running with `ReadTimeout = 5 * time.Second`, `WriteTimeout = 5 * time.Second`, `IdleTimeout = 30 * time.Second`.
  - Registered fast HTTP handler: `GET /burst` returning `200 OK` with body `"OK"`.
  - Instrumented socket wrapper or atomic telemetry counters in [`connDeadlineTracker`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L102-L111) (`syscallCountRead`, `syscallCountWrite`).
- **Action**:
  1. Client dials Toron server over TCP (`net.Dial("tcp", srvAddr)`).
  2. Client issues 1,000 sequential HTTP/1.1 requests over the single persistent connection:
     ```http
     GET /burst HTTP/1.1\r\nHost: localhost\r\nConnection: keep-alive\r\n\r\n
     ```
  3. Client reads HTTP `200 OK` response for each request before transmitting the next.
  4. Measure total duration for all 1,000 transactions (assert duration is $< 2.0\text{s}$, less than the $2.5\text{s}$ half-window threshold).
  5. Inspect recorded socket system calls:
     - Record total number of `SetReadDeadline` system calls executed on the underlying socket.
     - Record total number of `SetWriteDeadline` system calls executed on the underlying socket.
  6. Calculate reduction percentage:
     $$\text{Reduction}_{\text{read}} = \frac{1000 - N_{\text{read}}}{1000} \times 100\%$$
     $$\text{Reduction}_{\text{write}} = \frac{1000 - N_{\text{write}}}{1000} \times 100\%$$
- **Expected Outcomes**:
  - All 1,000 HTTP requests succeed with `200 OK` and body `"OK"`.
  - Total `SetReadDeadline` system calls executed: $\le 2$ (initial set plus at most one renewal).
  - Total `SetWriteDeadline` system calls executed: $\le 2$.
  - System call reduction exceeds **$99.8\%$**, easily surpassing the $> 80\%$ acceptance threshold.
  - Zero data corruption or header parsing errors.

### TC-126.2: Deadline Renewal on Window Expiration ($R \le \tau/2$ Threshold)
- **Identifier**: `TC-126.2`
- **Target Subsystem**: Connection Deadline Tracker Core Heuristic ([`pkg/server/deadline.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go))
- **Test Implementation**: `TestDeadlineTracker_RenewalOnWindowExpiration` in [`pkg/server/deadline_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline_test.go)
- **Objective**: Verify that [`connDeadlineTracker`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L102-L111) renews the underlying socket deadline when the remaining time falls to $\le \tau/2$, renews immediately when the timeout duration changes, and clears deadlines when timeout is $\le 0$.
- **Traceability**: [`REQ-126 §2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-126.md#L96-L98), [`TASK-149 WP-1.2`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-149.md#L113-L150), [`ADR-126 §2.2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-126.md#L142-L154).
- **Setup & Preconditions**:
  - Mock `net.Conn` implementation tracking timestamp and invocation count for `SetReadDeadline` and `SetWriteDeadline`.
  - Wrap mock connection in `tracker := newConnDeadlineTracker(mockConn)`.
- **Action**:
  - **Subtest 2A (Initial Set & Amortization)**:
    1. Invoke `tracker.SetAmortizedReadDeadline(200 * time.Millisecond)`.
    2. Assert mock connection received `SetReadDeadline` with deadline $\approx \text{now} + 200\text{ms}$.
    3. Assert syscall count is $1$.
    4. Immediately invoke `tracker.SetAmortizedReadDeadline(200 * time.Millisecond)` ($5\text{ms}$ later, remaining $\approx 195\text{ms} > 100\text{ms}$).
    5. Assert mock connection did NOT receive another call; syscall count remains $1$ (amortized).
  - **Subtest 2B (Window Expiration Renewal at $\le \tau/2$)**:
    1. Sleep $110\text{ms}$ (remaining window $\approx 85\text{ms} \le 100\text{ms} = \tau/2$).
    2. Invoke `tracker.SetAmortizedReadDeadline(200 * time.Millisecond)`.
    3. Assert mock connection received a fresh `SetReadDeadline` with new deadline $\approx \text{now} + 200\text{ms}$.
    4. Assert syscall count is now $2$.
  - **Subtest 2C (Timeout Mutation Forces Immediate Renewal)**:
    1. Invoke `tracker.SetAmortizedReadDeadline(500 * time.Millisecond)` ($5\text{ms}$ after Subtest 2B).
    2. Assert mock connection received `SetReadDeadline` with deadline $\approx \text{now} + 500\text{ms}$ despite ample remaining time on the previous $200\text{ms}$ window.
    3. Assert syscall count is now $3$.
  - **Subtest 2D (Timeout $\le 0$ Clears Socket Deadline)**:
    1. Invoke `tracker.SetAmortizedReadDeadline(0)`.
    2. Assert mock connection received `SetReadDeadline(time.Time{})`.
    3. Assert `tracker.lastReadDeadline.IsZero() == true`.
    4. Invoke `tracker.SetAmortizedReadDeadline(0)` again; assert no redundant clear call is issued.
  - **Subtest 2E (Symmetric Write Deadline Validation)**:
    1. Repeat Subtests 2A through 2D using `tracker.SetAmortizedWriteDeadline`.
    2. Assert identical behavior for write deadlines.
- **Expected Outcomes**:
  - Syscall elision occurs strictly when remaining time $> \tau/2$ and timeout value is unchanged.
  - Fresh deadline is dispatched to the socket when remaining time $\le \tau/2$ or when timeout changes.
  - Zero-timeout clears socket deadline cleanly.

### TC-126.3: Strict Idle Timeout State Machine Alignment (`br.Buffered() == 0` Reset)
- **Identifier**: `TC-126.3`
- **Target Subsystem**: Server Connection Request Loop ([`pkg/server/server.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L185-L215), [`pkg/server/deadline.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go))
- **Test Implementation**: `TestServer_IdleTimeout_StrictEnforcement` in [`pkg/server/server_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server_test.go)
- **Objective**: Verify that when an active HTTP transaction completes and the connection enters the idle keep-alive state waiting for the next request (`br.Buffered() == 0`), Toron immediately applies an explicit `IdleTimeout` deadline via [`ForceSetReadDeadline`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L233-L240) and invalidates cached read amortization ([`ResetReadAmortization`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go#L253-L258)), ensuring that an active 10s `ReadTimeout` does NOT bleed into the idle state and allow slow connections to hang past `IdleTimeout`.
- **Traceability**: [`REQ-126 §2.2`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-126.md#L102-L107), [`TASK-149 WP-1.3`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-149.md#L151-L184), [`TASK-149 WP-4.4`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-149.md#L309-L317), [`ADR-126 §2.3`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-126.md#L227-L260).
- **Setup & Preconditions**:
  - Toron server configured with `ReadTimeout = 10 * time.Second` (long read deadline) and `IdleTimeout = 200 * time.Millisecond` (short idle deadline).
  - Fast handler `GET /ping` returning `200 OK`.
- **Action**:
  1. Client connects via TCP (`net.Dial("tcp", srvAddr)`).
  2. Client transmits `GET /ping HTTP/1.1\r\nHost: localhost\r\nConnection: keep-alive\r\n\r\n`.
  3. Client reads status line `200 OK` and complete response body.
  4. Request transaction is now finished. Server reader buffer is empty (`br.Buffered() == 0`).
