# SR-051 - Security Review of HTTP/3 Protocol Engine & QUIC Listener Integration

## Executive Summary

The Security Analyst (AGENT-007) has conducted a comprehensive security review and vulnerability assessment of the HTTP/3 protocol engine integration and QUIC listener implementation in Toron ([`pkg/server/server.go`](file:///Users/sneha/Developer/toron/pkg/server/server.go) and [`cmd/toron/main.go`](file:///Users/sneha/Developer/toron/cmd/toron/main.go)), addressing [`TASK-027`](file:///Users/sneha/Developer/toron/docs/tasks/TASK-027.md) and verifying [`REQ-027`](file:///Users/sneha/Developer/toron/docs/requirements/REQ-027.md) in accordance with [`ADR-022`](file:///Users/sneha/Developer/toron/docs/architecture/ADR-022.md).

The evaluation focused on five critical security vectors:
1. **TLS 1.3 Mandate & Cryptographic Security for QUIC (RFC 9000 / RFC 9114)**
2. **UDP Reflection & Amplification Mitigation (RFC 9000 Handshake Token Validation)**
3. **Socket & Resource Leak Prevention During Graceful Shutdown (`s.h3Server.Close()`)**
4. **Header Injection & `Alt-Svc` Advertisement Sanitization (RFC 7838 / CWE-113)**
5. **Error Handling & Information Disclosure (CWE-209 / CWE-200)**

Based on rigorous code inspection, cryptographic analysis, and unit test verification, the HTTP/3 integration satisfies strict enterprise security requirements and is **APPROVED**.

## Security Evaluation & Threat Modeling

### 1. TLS 1.3 Mandate and Cryptographic Security for QUIC (RFC 9000 / RFC 9114)

- **Standard Requirements**:
  - RFC 9000 § 5.2 and RFC 9114 § 3 explicitly require that QUIC transport operate exclusively over TLS 1.3 (or later). TLS 1.2 and earlier versions are strictly prohibited because QUIC packet protection and key derivation are inherently coupled to the TLS 1.3 key schedule (using HKDF-Expand-Label).
  - Perfect Forward Secrecy (PFS) and authenticated encryption with associated data (AEAD) are mandatory for all QUIC 1-RTT packets.

- **Implementation Analysis**:
  - In `pkg/server/server.go` (`ListenAndServeH3`), Toron constructs a `*tls.Config` via `CreateTLSConfig(s.config)` and injects it into `http3.Server{TLSConfig: tlsConfig}`.
  - The underlying transport engine (`github.com/quic-go/quic-go`) strictly validates and enforces TLS 1.3 protocol parameters at the QUIC handshake state machine. If a client attempts to negotiate TLS 1.2 or non-AEAD cipher suites, the handshake is aborted with a QUIC `CRYPTO_ERROR` transport code.
  - Development certificate generation in `pkg/server/tls.go` (`GenerateDevCert`) uses ECDSA with elliptic curve P-256 and entropy from `crypto/rand.Reader`, ensuring robust ephemeral keys for local development without hardcoded secrets.
  - For production environments, certificates loaded via `tls.LoadX509KeyPair` are passed through to the QUIC crypto engine, providing end-to-end cryptographic confidentiality and authenticity.

### 2. UDP Reflection and Amplification Mitigation

- **Threat Vector**:
  - Because UDP is connectionless and datagram source IP addresses can be spoofed by remote attackers, UDP servers can inadvertently be weaponized as reflectors in distributed denial-of-service (DDoS) amplification attacks.

- **Standard Requirements & Mitigations**:
  - RFC 9000 § 8.1 establishes the anti-amplification limit: an endpoint MUST NOT send more than three times (3x) the amount of data it has received from an unvalidated client IP address.
  - RFC 9000 § 14.1 mandates that all client `Initial` datagrams MUST be padded to at least 1,200 bytes, dramatically limiting the asymmetric ratio between request datagrams and response packets.
  - RFC 9000 § 8.1.2 defines address validation tokens issued via `Retry` packets or `NEW_TOKEN` frames to verify that the client can receive packets at the declared source address before allocating heavy connection resources.

- **Implementation Analysis**:
  - Toron delegates UDP socket management and datagram processing directly to `quic-go/http3.Server`.
  - `quic-go` adheres strictly to RFC 9000 anti-amplification rules: it tracks incoming byte volumes per remote address and enforces the 3x response byte cap prior to handshake validation.
  - Handshake tokens are generated using authenticated cryptographic tokens, preventing spoofed source addresses from triggering large response floods or exhausting server worker pools.

### 3. Socket & Resource Leak Prevention During Graceful Shutdown

- **Threat Vector**:
  - Incomplete socket teardown, unreleased UDP file descriptors, or dangling goroutines during service termination can cause port exhaustion, file descriptor leaks, or hang container shutdown sequences.

- **Implementation Analysis**:
  - In `pkg/server/server.go` (`Shutdown`), thread-safe access to the HTTP/3 server pointer is guarded by `s.mu.Lock()`:
    ```go
    s.mu.Lock()
    h3 := s.h3Server
    s.mu.Unlock()

    if h3 != nil {
        _ = h3.Close()
    }
    ```
  - `h3.Close()` cleanly shuts down the UDP listener socket, terminates active QUIC sessions, sends QUIC `CONNECTION_CLOSE` frames to connected peers, and cancels internal I/O loops.
  - When `h3.Close()` is invoked, `h3.ListenAndServe()` returns `http.ErrServerClosed`. Toron maps this to `server.ErrServerClosed` (`pkg/server/server.go:424`), which `cmd/toron/main.go:506` explicitly filters to prevent false-alarm error logs during shutdown.
  - In `cmd/toron/main.go:531-535`, graceful termination is bounded by a 5-second deadline context (`context.WithTimeout(context.Background(), 5*time.Second)`), ensuring that the process cleanly exits even under hostile network conditions or stalled streams.
  - Nil safety is verified: if `s.h3Server` is nil (e.g. HTTP/3 disabled), `Shutdown()` safely bypasses the HTTP/3 close call without nil-pointer dereferences (verified by `TestServer_HTTP3_Shutdown/Nil_Safety`).

### 4. Header Injection & Alt-Svc Advertisement Sanitization

- **Threat Vector (CWE-113 / HTTP Response Splitting)**:
  - If dynamic values or user input are incorporated into HTTP response headers without strict sanitization, attackers can inject CRLF (`\r\n`) sequences to manipulate response headers, forge cookies, or inject malicious payloads.

- **Implementation Analysis**:
  - In `pkg/server/server.go` lines 244–252 (HTTP/1.1) and lines 333–341 (HTTP/2 adapter):
    ```go
    if s.config.HTTP3Enabled && s.config.HTTP3AltSvcHeader {
        if res.Header.Get("Alt-Svc") == "" {
            h3Port := s.config.HTTP3Port
            if h3Port <= 0 {
                h3Port = 8443
            }
            res.Header.Set("Alt-Svc", fmt.Sprintf(`h3=":%d"; ma=2592000`, h3Port))
        }
    }
    ```
  - **Type Safety & CRLF Immunity**: `h3Port` is strictly typed as a signed integer (`int`) in `Config` and `AppConfig`. The header value is formatted strictly with integer formatting (`%d`), completely preventing any character injection, newline injection (`\r` or `\n`), or parameter manipulation.
  - **Safe Fallback**: If `h3Port <= 0`, it defaults safely to port `8443`.
  - **Header Preservation**: The guard `res.Header.Get("Alt-Svc") == ""` verifies whether an upstream backend, proxy target, or internal route handler has already supplied an `Alt-Svc` header, preventing Toron from overriding or duplicating application-level protocol policies.
  - **RFC 7838 Compliance**: The `ma=2592000` directive specifies a 30-day freshness window for client protocol cache retention, adhering to standard alternate service caching semantics.

### 5. Error Handling and Information Disclosure

- **Threat Vector (CWE-209 / CWE-200)**:
  - Verbose error messages, raw internal error traces, or memory addresses returned to untrusted clients leak architecture details and assist adversary reconnaissance.

- **Implementation Analysis**:
  - Request parsing and protocol error handling in `pkg/server/server.go` return sanitized, generic JSON error structures (e.g. `{"error":"400 Bad Request"}`, `{"error":"413 Payload Too Large"}`, `{"error":"431 Request Header Fields Too Large"}`).
  - Protocol-level errors within QUIC streams are handled by `quic-go/http3` using standard RFC 9114 application error codes (e.g. `H3_NO_ERROR`, `H3_GENERAL_PROTOCOL_ERROR`, `H3_STREAM_CREATION_ERROR`), preventing internal runtime panics or stack traces from traversing stream frames.
  - The router pipeline is wrapped with `router.RecoveryMiddleware()`, ensuring unexpected application panics are caught and converted into clean 500 status responses without client-side disclosure.
  - In `cmd/toron/main.go`, HTTP/3 server operational errors are logged to standard server logs with port context and do not expose TLS private keys, certificates, or session tokens.

## Positive Observations & Security Controls Verified

1. **Protocol Isolation**: HTTP/3 traffic routed through `http2AdapterHandler` reuses Toron's core `router.Router` pipeline, uniformly enforcing authentication, authorization, CORS policies, rate limiting, and WAF rules across HTTP/1.1, HTTP/2, and HTTP/3.
2. **Path Traversal Protection**: Request URIs received via QUIC streams are normalized and validated through Toron's router and `httpparser`, preserving strict path traversal guards.
3. **Graceful Draining & Clean Termination**: Active QUIC connections are terminated with standard `CONNECTION_CLOSE` frames upon `Shutdown()`, preventing connection state corruption or hung background routines.
4. **Injection-Safe Header Generation**: `Alt-Svc` header construction uses integer formatting, preventing CRLF injection vulnerabilities.
5. **Anti-Amplification Compliance**: Native delegation to `quic-go` guarantees adherence to RFC 9000 3x amplification limits and handshake address validation tokens.
