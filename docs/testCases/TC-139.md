# TC-139 - Test Specification for Disaggregated Upstream Route Pooling, Hierarchical Telemetry Aggregation, and Live Metric Derivation in Dashboard

## 1. Verification Scope & Objectives

### 1.1 Scope
This document specifies the verification strategy, test suites, execution procedures, and pass/fail criteria for the Toron Edge Gateway Control Center dashboard ([`public/app.js`](../../public/app.js)). It verifies the resolution of upstream route collapse, telemetry field mismatch, subpath fragmentation, polling dilution, sample oscillation, and volume visibility defects specified in [`REQ-139`](../requirements/REQ-139.md) (v1.1), designed in [`ADR-139`](../architecture/ADR-139.md) (v1.1), and implemented in [`TASK-162`](../tasks/TASK-162.md) (v1.1).

### 1.2 Verification Goals
1. **Upstream Route Disaggregation**: Ensure that distinct ingress proxy routes sharing a physical backend socket (`127.0.0.1:8080`) are rendered as isolated, independent pool cards without route conflation or omission.
2. **Exhaustive Route Coverage**: Ensure that unmapped proxy routes are created as independent fallback pools with passive health checking.
3. **Hierarchical Subpath Rollup**: Verify that request counts for nested subpaths (e.g. `/kite/api/v1/business`, `/kite/api/v1/trades`, `/kite/api/v1/auth`) are aggregated into their parent configured route prefix (`/kite/api`).
4. **Internal Polling Isolation**: Ensure that high-volume internal dashboard polling requests (`/internal/api/*` accounting for >90% of traffic) are excluded from the external throughput denominator, eliminating dilution of user route RPS.
5. **Moving Average Temporal Smoothing**: Ensure that instantaneous gateway RPS is calculated using a 5-sample moving average window (`avg(tsA.rps.slice(-5))`), eliminating alternating 0-to-6 RPS oscillations between 2-second polling intervals.
6. **Dual Rate and Cumulative Volume Display**: Verify that upstream pool cards render both live real-time rate and cumulative volume (e.g. `"${fmt.n(p.rps)}/s (${fmt.n(p.totalReqs)} total)"`), providing essential operational context for idle or low-traffic backends.
7. **Live Health Probe Latency & Percentiles**: Ensure instance rows bind directly to live probe latency (`u.latency_ms`) and pool headers dynamically derive p95 latency without static `2.5 ms` fallbacks.
8. **Health State & Circuit Breaker Visibility**: Ensure that probe degradation, 5xx HTTP responses, and `UNREACHABLE` statuses trigger visual tone escalation (`ok` $\rightarrow$ `warn` $\rightarrow$ `err`) and alert dispatch.
9. **Cross-View Visual Parity**: Guarantee rendering parity between the Upstreams card grid (`#/upstreams`), the Overview SVG Sankey traffic flow diagram (`#/overview`), and the Routes table (`#/routes`).
10. **Defensive Robustness & Performance Budget**: Verify sub-2ms model transformation ($\mathcal{O}(R + U)$) and zero runtime exceptions under cold-start, missing field, or zero-request conditions.

## 3. Comprehensive Test Case Specifications

### TC-139-01: Distinct Upstream Route Pool Rendering for Shared Target IP:Port
- **Test ID**: `TC-139-01`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-1, FR-2, FR-3), [`TASK-162`](../tasks/TASK-162.md) (3.1), [`ADR-139`](../architecture/ADR-139.md) (3.1)
- **Category**: Functional Verification / Data Adapter & DOM Component
- **Objective**: Verify that multiple proxy routes configured with the exact same backend socket (`http://127.0.0.1:8080`) produce distinct, isolated upstream pool cards and are not collapsed into the first declared route.
- **Preconditions**:
  - `rawApiRoutes` contains Fixture 1 (routes `/kite/callback`, `/kite/api`, `/kite/broker`, `/kite/auth`).
  - `rawApiUpstreams` contains Fixture 2 (probes for each of the 4 routes).
  - `rawApiStatus` contains Fixture 3.
- **Execution Procedure**:
  1. Initialize test environment and load `public/app.js` data adapter functions.
  2. Invoke `buildDataModel()`.
  3. Inspect `D.pools` array returned by the model builder.
  4. Invoke `upUpdate(D)` to generate the DOM tree inside `#poolGrid`.
- **Expected Results & Assertions**:
  1. `D.pools.length` MUST be $\ge 4$ (at least 4 pools for the 4 Kite routes, plus any unmapped routes).
  2. The pool map MUST contain 4 distinct keys: `_kite_callback`, `_kite_api`, `_kite_broker`, `_kite_auth`.
  3. Pool `_kite_callback` MUST NOT contain routes `_kite_api`, `_kite_broker`, or `_kite_auth` in its `routes` array. Each pool must isolate its specific route:
     ```javascript
     assert.strictEqual(poolCallback.routes.length, 1);
     assert.strictEqual(poolCallback.routes[0].id, '_kite_callback');
     assert.strictEqual(poolApi.routes.length, 1);
     assert.strictEqual(poolApi.routes[0].id, '_kite_api');
     assert.strictEqual(poolBroker.routes.length, 1);
     assert.strictEqual(poolBroker.routes[0].id, '_kite_broker');
     assert.strictEqual(poolAuth.routes.length, 1);
     assert.strictEqual(poolAuth.routes[0].id, '_kite_auth');
     ```
  4. In the rendered DOM (`#poolGrid`):
     - Distinct card containers MUST exist: `#pool-_kite_callback`, `#pool-_kite_api`, `#pool-_kite_broker`, `#pool-_kite_auth`.
     - Card `#pool-_kite_callback` header MUST display `Match: sayantansaha.in /kite/callback`.
     - Card `#pool-_kite_api` header MUST display `Match: sayantansaha.in /kite/api`.
     - Card `#pool-_kite_broker` header MUST display `Match: sayantansaha.in /kite/broker`.
     - Card `#pool-_kite_auth` header MUST display `Match: sayantansaha.in /kite/auth`.
  5. Route header chips MUST display their respective service tags (`X-Service=kite-callback`, `X-Service=kite-api`, etc.).
- **Pass/Fail Criteria**: Passes if all 4 pool cards render independently with discrete route metadata and zero route absorption.

### TC-139-02: Fallback Route Pool Creation for Unmapped Upstream Routes
- **Test ID**: `TC-139-02`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-4), [`TASK-162`](../tasks/TASK-162.md) (3.1), [`ADR-139`](../architecture/ADR-139.md) (3.1)
- **Category**: Functional Verification / Defensive Fallback
- **Objective**: Verify that any configured proxy route lacking an explicit probe entry in `/internal/api/upstreams/health` is automatically instantiated as an independent pool card during the secondary registration loop.
- **Preconditions**:
  - `rawApiRoutes` contains `/kite/orders` (`id: "_kite_orders"`, `type: "proxy"`, `targets: ["http://10.0.2.20:8080"]`).
  - `rawApiUpstreams` does NOT contain any probe entry for `/kite/orders` or `10.0.2.20:8080`.
- **Execution Procedure**:
  1. Execute `buildDataModel()`.
  2. Search `D.pools` for `id === '_kite_orders'`.
  3. Execute `upUpdate(D)` and inspect DOM.
- **Expected Results & Assertions**:
  1. `D.pools.some(p => p.id === '_kite_orders')` MUST evaluate to `true`.
  2. The generated fallback pool object MUST satisfy:
     ```javascript
     const p = D.pools.find(p => p.id === '_kite_orders');
     assert.strictEqual(p.displayName, 'sayantansaha.in /kite/orders');
     assert.strictEqual(p.path, '/kite/orders');
     assert.strictEqual(p.algo, 'Least-Connections');
     assert.strictEqual(p.hc, 'Passive health check');
     assert.strictEqual(p.insts.length, 1);
     assert.strictEqual(p.insts[0].a, 'http://10.0.2.20:8080');
     assert.strictEqual(p.insts[0].state, 'up');
     assert.strictEqual(p.insts[0].history.length, 48);
     ```
  3. DOM element `#pool-_kite_orders` MUST exist in `#poolGrid`.
- **Pass/Fail Criteria**: Passes if unmapped proxy routes are 100% visible in the Upstreams view with passive health check markers.

### TC-139-03: Hierarchical Subpath Rollup and Prefix Aggregation
- **Test ID**: `TC-139-03`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-5, FR-6), [`TASK-162`](../tasks/TASK-162.md) (3.2), [`ADR-139`](../architecture/ADR-139.md) (3.2)
- **Category**: Quantitative / Math Verification & Subpath Rollup
- **Objective**: Verify that route request counts aggregate all recorded subpaths under the route's configured prefix (`k === prefix || k.startsWith(prefix + '/')`), resolving the subpath fragmentation defect where exact matches returned 0.
- **Preconditions**:
  - `rawApiStatus.metrics.requests_by_route` contains:
    - `"/kite/api/v1/business"`: `1800`
    - `"/kite/api/v1/trades"`: `800`
    - `"/kite/api/v1/auth"`: `400`
    - `"/kite/api-v2/other"`: `500` (must NOT match `/kite/api`)
    - `"/kite/callback"`: `5000`
    - `"/kite/broker"`: `2000`
    - `"/kite/auth"`: `0`
- **Execution Procedure**:
  1. Call `buildDataModel()`.
  2. Inspect `r.totalReqs` for route `/kite/api`.
  3. Inspect `r.totalReqs` for routes `/kite/callback`, `/kite/broker`, and `/kite/auth`.
- **Expected Mathematical Calculations**:
  $$\text{aggregated\_requests}('/kite/api') = 1800 + 800 + 400 = 3000$$
  - Subpaths with `/` boundaries are included (`/kite/api/v1/...`).
  - Sibling prefixes without `/` boundaries (`/kite/api-v2/other`) are strictly excluded.
- **Expected Results & Assertions**:
  ```javascript
  const rApi = D.routes.find(r => r.path === '/kite/api');
  assert.strictEqual(rApi.totalReqs, 3000);

  const rCb = D.routes.find(r => r.path === '/kite/callback');
  assert.strictEqual(rCb.totalReqs, 5000);

  const rBr = D.routes.find(r => r.path === '/kite/broker');
  assert.strictEqual(rBr.totalReqs, 2000);

  const rAu = D.routes.find(r => r.path === '/kite/auth');
  assert.strictEqual(rAu.totalReqs, 0);
  ```
- **Pass/Fail Criteria**: Passes if `/kite/api` aggregates exactly 3,000 requests across its three subpaths without leaking sibling prefixes or returning 0.

### TC-139-04: Internal Telemetry Polling Isolation and Denominator Normalization
- **Test ID**: `TC-139-04`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-7), [`TASK-162`](../tasks/TASK-162.md) (3.2), [`ADR-139`](../architecture/ADR-139.md) (3.2)
- **Category**: Quantitative / Traffic Isolation & Filter Verification
- **Objective**: Verify that internal dashboard polling requests (`/internal/*`) are filtered out from the external requests denominator, preventing the 91%+ traffic dilution that drives external route live RPS down to 0.0/s.
- **Preconditions**:
  - Total requests recorded in gateway $= 58,500$.
  - Internal polling requests:
    - `/internal/api/status`: $25,000$
    - `/internal/api/routes`: $12,000$
    - `/internal/api/upstreams/health`: $11,000$
    - `/internal/api/logs`: $500$
    - Total Internal $= 48,500$ ($82.9\%$ of total requests).
  - External user route requests:
    - `/kite/callback`: $5,000$ ($50\%$ of external)
    - `/kite/api` (aggregated): $3,000$ ($30\%$ of external)
    - `/kite/broker`: $2,000$ ($20\%$ of external)
    - `/kite/auth`: $0$ ($0\%$ of external)
    - Total External $= 10,000$.
- **Execution Procedure**:
  1. Call `buildDataModel()`.
  2. Compute total external requests evaluated in adapter:
     $$\text{totalExternalRequests} = \sum_{k \notin \text{internal}} \text{count} = 10,000$$
  3. Validate proportional share $\text{routeRatio}$ for each route.
- **Expected Results & Assertions**:
  1. Denominator Calculation:
     - `totalExternalRequests` MUST equal $10,000$ (NOT $58,500$).
  2. Proportion Comparison:
     - Without internal filter: `/kite/api` share would be $\frac{3000}{58500} \approx 5.1\%$, diluting live RPS by nearly $6\times$.
     - With internal filter: `/kite/api` share MUST be $\frac{3000}{10000} = 30.0\%$.
     - `/kite/callback` share MUST be $\frac{5000}{10000} = 50.0\%$.
     - `/kite/broker` share MUST be $\frac{2000}{10000} = 20.0\%$.
  3. Boundary Condition:
     - If all recorded requests are internal (i.e. `totalExternalRequests === 0`), `routeRatio` MUST evaluate to `0.0` without throwing a divide-by-zero error or producing `NaN`.
- **Pass/Fail Criteria**: Passes if internal polling keys are completely excluded from the throughput denominator, preserving true external traffic shares.

### TC-139-05: Instantaneous RPS Temporal Smoothing via Moving Average Window
- **Test ID**: `TC-139-05`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-8), [`TASK-162`](../tasks/TASK-162.md) (3.3), [`ADR-139`](../architecture/ADR-139.md) (3.3)
- **Category**: Quantitative / Signal Processing & Anti-Oscillation
- **Objective**: Verify that the gateway throughput base uses a 5-sample moving average window (`avg(tsA.rps.slice(-5))`), eliminating alternating 0-to-6 RPS oscillations between 2-second dashboard polling cycles.
- **Preconditions**:
  - Time-series buffer `rawApiStatus.timeseries.A.rps` contains 5 samples: `[110.0, 130.0, 105.0, 135.0, 120.0]`.
  - Alternatively, in an oscillating low-traffic test: `[0.0, 6.0, 0.0, 6.0, 0.0]`.
- **Execution Procedure**:
  1. Test Scenario A (Active Traffic):
     - Moving average: $\text{avg}(110.0, 130.0, 105.0, 135.0, 120.0) = \frac{600.0}{5} = 120.0$ req/s.
     - Verify `smoothedRPS === 120.0`.
  2. Test Scenario B (Oscillating Bursty Polling):
     - Inject `rawApiStatus.timeseries.A.rps = [0.0, 6.0, 0.0, 6.0, 0.0]`.
     - Moving average: $\text{avg}(0.0, 6.0, 0.0, 6.0, 0.0) = \frac{12.0}{5} = 2.4$ req/s.
     - Verify `smoothedRPS === 2.4`.
