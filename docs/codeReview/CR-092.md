## Description

This code review evaluates the implementation of [`TASK-119`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-119.md) satisfying requirement specification [`REQ-096`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-096.md), architectural decision record [`ADR-096`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-096.md), header routing specification [`ADR-005`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-005.md), and test specification [`TC-096`](file:///Users/sneha/.gemini/antigravity-cli/brain/b0415125-34f8-42c9-b736-0f57f6fe7ed3/TC-096.md).

The change establishes full architectural parity between Toron's Kubernetes Ingress Controller and the OCI container discovery engine ([`ADR-095`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-095.md), [`CR-091`](file:///Users/sneha/.gemini/antigravity-cli/brain/a66ff311-fc9a-4bbc-bb45-70ab388f0c99/CR-091.md)), resolving five critical failure modes:

1. **Canary Target Pool Pollution & Traffic Bleed**:
   Previously, `pkg/ingress/controller.go` aggregated pod endpoints using a naive 2-tuple `routeKey{host, prefix}`. When operators defined a Canary Ingress and a Baseline Ingress for the same host and prefix, both pod sets were merged into a single target slice, causing standard production users to randomly hit unvalidated canary pods ($\approx 33\text{--}50\%$). The implementation partitions routes using a 4-dimensional `CompositeRouteKey = (Host, CleanPrefix, Method, CanonicalHeaders)`, keeping canary and baseline reverse proxy target pools strictly segregated.
2. **Missing Ingress Annotation Parsing**:
   Previously, `TranslateIngress` ignored all method and header annotations. The implementation introduces robust parsing for `toron.io/method`, `toron.io/header.<Name>`, `toron.io/headers` (CSV and JSON), and standard Ingress-NGINX Canary annotations (`nginx.ingress.kubernetes.io/canary*`).
3. **Route Shadowing & Non-Deterministic Discovery Order (CWE-284)**:
   Previously, `controller.go` installed routes in the arbitrary order returned by the Kubernetes API server. If the baseline route appeared before the canary route, linear first-match evaluation in `router.ServeHTTP` intercepted all traffic, completely shadowing the canary route. The implementation enforces ADR-005 specificity sorting on `specs` prior to installation, guaranteeing that canary routes are evaluated before fallback routes.
4. **Declarative Method Matching Support**:
   `PrefixRouteSpec.Method` is now populated from Ingress annotations and enforced at runtime, returning HTTP 405 Method Not Allowed or falling through to matching verb handlers on verb mismatches.
5. **Non-Destructive Scale-Down & Clean Teardown**:
   Scaling down pod replicas updates the target pool to surviving instances without dropping traffic. Deleting Ingress resources cleanly purges routes and invokes `proxy.Close()`, stopping active health check tickers and freeing socket descriptors (`EMFILE`).

### Finding 2: Telemetry Map Key Overwrite on Multi-Path Single-Service Ingresses

- **Severity**: Low
- **Location**: [`pkg/ingress/translator.go:223`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go#L223), [`pkg/ingress/controller.go:210`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L210)
- **Related Artifact**: [`REQ-094-AC-01`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-094.md#L120-L125), [`CR-090 Finding 1`](file:///Users/sneha/Developer/toron-research/toron/docs/codeReview/CR-090.md#L94-L121)
- **Description**:
  In `TranslateIngress`, `ContainerID` is generated as:
  ```go
  ContainerID: fmt.Sprintf("k8s-%s-%s-%s-%d", ing.Metadata.Namespace, ing.Metadata.Name, svcName, idx)
  ```
  If an Ingress defines multiple HTTP paths (e.g. `/v1` and `/v2`) pointing to the *same* backend Service, pod index `idx` produces identical `ContainerID`s across paths. In `controller.go:210`:
  ```go
  newRoutes[r.ContainerID] = r
  ```
  The second path's `DiscoveredRoute` overwrites the first path's entry in `newRoutes`.
- **Impact**:
  - **Runtime Routing**: Not impacted. Routing uses `targetsByKey` and `keyOrder` partitioned by `CompositeRouteKey`, which properly separates distinct path prefixes.
  - **Observability / Telemetry**: Callers of `ctrl.ActiveRoutes()` will observe fewer routes than actual active paths when multiple paths target the same Service in one Ingress.
- **Recommendation**:
  Incorporate the normalized path prefix into `ContainerID` generation:
  ```go
  cleanIDPrefix := strings.Trim(strings.ReplaceAll(cleanPrefix, "/", "-"), "-")
  if cleanIDPrefix == "" {
      cleanIDPrefix = "root"
  }
  ContainerID: fmt.Sprintf("k8s-%s-%s-%s-%s-%d", ing.Metadata.Namespace, ing.Metadata.Name, cleanIDPrefix, svcName, idx)
  ```

### Finding 3: Health Check Annotation Precedence Across Multiple Ingresses

- **Severity**: Low
- **Location**: [`pkg/ingress/controller.go:224-229`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L224-L229)
- **Related Artifact**: [`REQ-096-AC-04`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-096.md#L163-L169), [`ADR-096 §3.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-096.md#L260-L294)
- **Description**:
  In `syncIngresses`, health check options are aggregated as:
  ```go
  if healthCheckPathByKey[k] == "" && r.HealthCheckPath != "" {
      healthCheckPathByKey[k] = r.HealthCheckPath
  }
  if healthCheckIntervalByKey[k] == 0 && r.HealthCheckInterval > 0 {
      healthCheckIntervalByKey[k] = r.HealthCheckInterval
  }
  ```
  If multiple Ingress definitions share a `CompositeRouteKey` and specify conflicting health check paths or intervals, the first route processed sets the values for the combined proxy.
- **Impact**:
  Typically Ingress rules for a given service are defined in a single Ingress or with identical annotations. In misconfigured multi-ingress environments, the first processed Ingress determines health checking parameters.
- **Recommendation**:
  Log a warning if conflicting health check configurations are detected for the same `CompositeRouteKey`.

### 3. Annotation Parsing Correctness
- `toron.io/method`: Extracted, trimmed, and converted to uppercase.
- `toron.io/headers`: Parsed as JSON if enclosed in `{...}`; parsed as comma-separated `key=value` otherwise. Malformed JSON handled gracefully without panic.
- `nginx.ingress.kubernetes.io/canary*`: `canary-by-header` extracted; `canary-by-header-value` defaults to `"always"` if omitted.
- `toron.io/header.<Name>`: Overrides grouped/canary headers additively.
- Unannotated Ingresses: Defaults cleanly to `Method == ""` and `Headers == nil`.

### 4. `CompositeRouteKey` and Deterministic Header Canonicalization
- `canonicalizeHeaders`: Extracts keys, sorts them case-insensitively via `sort.Slice`, normalizes keys to lowercase, formats as `key=value`, and joins with `&`.
- Determinism tested across 100 iterations with 100% identical output.
- `makeCompositeKey` normalizes host to lowercase, prefix to leading slash without trailing slash, method to uppercase, and attaches canonical headers.

### 5. Multi-Pod Target Aggregation and Round-Robin Balancing
- `targetsByKey[k]` deduplicates pod endpoints via `seenTarget[k][targetURL]`.
- Targets sorted alphabetically via `sort.Strings(targetsByKey[k])`.
- Load balancer algorithm set to `proxy.AlgorithmRoundRobin`.
- Tested: 30 requests to a 3-pod service distribute exactly 10 requests to each pod ($33.3\%$ each).

### 6. Strict Canary vs Baseline Segregation
- Separate composite keys guarantee separate reverse proxy target pools.
- Requests with canary header route exclusively to canary pods; baseline requests route exclusively to baseline pods.

### 7. ADR-005 Specificity Sorting
- `router.SortPrefixRouteSpecs(specs)` sorts routes by prefix length $\to$ host specificity $\to$ header constraint count $\to$ method constraint $\to$ deterministic tie-break.
- Adverse discovery order test proves generic baseline routes cannot shadow canary routes.

### 8. Non-Destructive Scale-Down & Clean Proxy Teardown
- Stopping 1 pod updates targets to surviving pods with zero 404s.
- Deleting an Ingress purges routes and invokes `proxy.Close()`, stopping active health check tickers and releasing TCP sockets.

### 9. Thread Safety and Lock Discipline
- `c.syncMu` serializes reconciliation passes.
- `c.mu` protects active routes.
- `r.mu` handles route swaps.
- No lock inversions; high-concurrency race detector tests pass cleanly.

## Positive Observations

1. **Complete Architectural Parity**:
   The Kubernetes Ingress Controller now shares the exact same 4-dimensional `CompositeRouteKey` and ADR-005 specificity ordering model as the OCI container discovery engine, creating a unified routing architecture across bare-metal containers and Kubernetes clusters.
2. **First-Class Industry Standard Compatibility**:
   Supporting standard Ingress-NGINX Canary annotations (`nginx.ingress.kubernetes.io/canary*`) alongside native Toron annotations (`toron.io/*`) allows operators to migrate existing Kubernetes Canary workloads to Toron with zero manifest modifications.
3. **Resilient Annotation Extraction**:
   `TranslateIngress` cleanly handles mixed annotation formats, JSON object deserialization, comma-delimited key-value tokens, whitespace trimming, and override precedence without panics or error propagation.
4. **Out-of-Lock Resource Teardown**:
   Evicted reverse proxies have `Close()` invoked outside of write lock hold times, ensuring that active health check halts and socket closures do not introduce latency jitter for live HTTP traffic.
5. **Debounced Event Consumption**:
   `consumeEventsWorker` uses a 25ms debounce timer to coalesce rapid bursts of watch events into a single synchronization pass, preventing CPU thrashing during large cluster rollouts.

## Constraints

1. **Standard Library Only**: Pure Go standard library packages only; zero third-party packages added (`go.mod` and `go.sum` remain untouched).
2. **Canary Segregation Invariant**: Canary and Baseline pod targets must remain strictly isolated.
3. **Zero Downtime Invariant**: Pod scaling events must never drop or interrupt traffic to surviving healthy pods.
4. **Thread Safety & Race-Freedom**: All operations must remain 100% data-race-free under `go test -race`.
