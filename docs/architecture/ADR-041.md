# ADR-041 - Vendor-Agnostic OCI Container Discovery Architecture via Unix Socket REST Abstraction

## Context

To enable dynamic container auto-discovery without vendor lock-in to Docker Engine, Toron requires a container runtime discovery engine capable of operating across Docker, Podman, Finch, and Nerdctl while adhering to Toron's core principle of zero external runtime dependencies.

## Decision

1. **Provider Abstraction Interface**: Define `Provider` interface in `pkg/discovery/provider.go` to decouple routing logic from container runtime specifics.
2. **Unix Socket HTTP Transport**: Implement `UnixRESTProvider` using `net.DialContext("unix", socketPath)` and standard library `net/http`. This allows direct communication with Docker Engine REST API socket endpoints exposed by Docker, Podman, and containerd CLIs without importing 3rd-party SDKs.
3. **Automatic Socket Probing**: Support automatic fallback detection across `/var/run/docker.sock`, `/run/podman/podman.sock`, and user rootless sockets (`/run/user/$UID/podman/podman.sock`).
4. **Normalized Label Taxonomy**: Standardize on `toron.*` metadata keys (`toron.enable`, `toron.host`, `toron.prefix`, `toron.port`, `toron.weight`).

## Consequences

- **Positive**: Zero external dependencies added to `go.mod`. Instant boot times (<5ms) and tiny binary footprints (<30MB) preserved.
- **Positive**: Works seamlessly across Docker, Podman, Finch, and Nerdctl out of the box.
- **Negative**: CRI gRPC native transport for CRI-O requires optional secondary provider module.
