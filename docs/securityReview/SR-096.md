# SR-096 - Security Review of Composite Route Key Grouping, Multi-Pod Target Aggregation, and Specificity-Based Route Lifecycle in Kubernetes Ingress Controller

## Description

A comprehensive security review and vulnerability assessment of the Kubernetes Ingress Controller CompositeRouteKey architecture, multi-pod target aggregation, annotation-driven variant segregation, and specificity-based route lifecycle, implemented under [`REQ-096`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-096.md), [`ADR-096`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-096.md), [`TASK-119`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-119.md), and verified by automated test specification [`TC-096`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-096.md), with architectural continuity from [`SR-094`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-094.md) and [`SR-095`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-095.md).

This assessment provides an in-depth security evaluation of Toron's Kubernetes Ingress Controller ([`pkg/ingress/controller.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go)), route translation engine ([`pkg/ingress/translator.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go)), and core routing engine ([`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go)), confirming the complete elimination of:
- **Routing Dimension Blindness & Canary Target Pool Contamination**: Co-mingling of Canary and Baseline pod endpoints into a shared load balancer pool, which caused baseline production users to randomly receive unvalidated pre-release canary traffic.
- [CWE-284: Improper Access Control](https://cwe.mitre.org/data/definitions/284.html) (**Route Shadowing**): Non-deterministic Ingress discovery ordering where generic baseline Ingress routes shadowed header-constrained Canary Ingress routes in the core router table.
- [CWE-400: Uncontrolled Resource Consumption / DoS](https://cwe.mitre.org/data/definitions/400.html) (**Pod Starvation**): Single-pod traffic monopolization and uneven request distribution across backend pod replicas.
- [CWE-775: Missing Release of Resource after Effective Lifetime](https://cwe.mitre.org/data/definitions/775.html): Unclosed reverse proxy connection pools and lingering background health check ticker goroutines (`EMFILE` socket descriptor exhaustion) upon Ingress deletion or path reconfiguration.
- [CWE-20: Improper Input Validation](https://cwe.mitre.org/data/definitions/20.html): Potential panics or bypasses from malformed JSON or invalid syntax in Ingress annotations (`toron.io/headers`, `toron.io/header.*`, `nginx.ingress.kubernetes.io/canary*`).
- **Control Plane Concurrency Hazards**: Data races and mutex lock inversion between Kubernetes watch event handlers, 30-second resync loops, and runtime HTTP request dispatching.

## Executive Vulnerability Assessment

### Remediation Status: 100% Resolved (Approved)

The Kubernetes Ingress Controller CompositeRouteKey implementation has been **comprehensively reviewed, audited, and approved**. All architectural decisions outlined in [`ADR-096`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-096.md) and requirements specified in [`REQ-096`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-096.md) are correctly implemented with zero security flaws or regressions.

Prior to this implementation, the Ingress Controller suffered from five critical failure modes:
1. **Canary Target Pool Pollution**: Ingress routes were grouped solely on a 2-tuple `routeKey{host, prefix}`. When an operator configured a baseline Ingress and a canary Ingress for the same host and prefix, pod IPs from both Ingresses were lumped into the same `Targets` slice. Baseline users without canary headers received unvalidated canary traffic ($\approx 33\text{--}50\%$), invalidating deployment safety controls.
2. **Missing Ingress Annotation Parsing**: `TranslateIngress` parsed only basic host, path, and port fields. It completely ignored HTTP method constraints and header matching annotations, leaving `DiscoveredRoute.Method` and `DiscoveredRoute.Headers` blank.
3. **Route Shadowing via Non-Deterministic Arrival Order (CWE-284)**: `controller.go` iterated through Ingresses in the arbitrary order returned by the Kubernetes API server. If a generic baseline Ingress was parsed prior to a canary Ingress, the baseline route matched all incoming requests, completely shadowing the canary route.
4. **Incomplete PrefixRouteSpec Construction**: `PrefixRouteSpec` was instantiated with empty `Method` and `Headers`, preventing the core router from applying HTTP verb or header filtering rules.
5. **Architectural Disparity with OCI Discovery**: A functional gap existed between the advanced 4-dimensional routing in `pkg/discovery` (SEC-34 / REQ-095) and the naive 2-tuple routing in `pkg/ingress`.

### Core Remediation Mechanisms Implemented

The implementation under [`TASK-119`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-119.md) and [`ADR-096`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-096.md) establishes complete architectural parity and resolves all prior vulnerabilities:

1. **Dual-Ecosystem Annotation Parsing**: `TranslateIngress` natively parses Toron annotations (`toron.io/method`, `toron.io/header.<Name>`, `toron.io/headers` in CSV and JSON formats) and standard Ingress-NGINX Canary annotations (`nginx.ingress.kubernetes.io/canary*`), populating `DiscoveredRoute.Method` and `Headers`.
2. **Multi-Dimensional `CompositeRouteKey`**: Routes are grouped by:
   $$\text{CompositeRouteKey} = (\text{Host}, \text{Prefix}, \text{Method}, \text{CanonicalHeaders})$$
   where `CanonicalHeaders` alphabetizes and lowercases header keys to guarantee deterministic grouping across synchronization cycles.
3. **Strict Canary vs Baseline Target Segregation**: Canary Ingresses and Baseline Ingresses produce distinct composite keys, aggregating pod endpoints into separate reverse proxy target pools with zero cross-contamination.
4. **ADR-005 Specificity Sorting**: Ingress route specifications are sorted by specificity (Longest prefix $\to$ Specific host $\to$ Header constraint count $\to$ Method constraint $\to$ Deterministic tie-break) before updating the router table. More specific Canary routes are guaranteed to evaluate ahead of generic Baseline routes, eliminating route shadowing.
5. **Declarative Method Constraint Enforcement**: `PrefixRouteSpec.Method` is populated from `toron.io/method` and enforced in `ServeHTTP`, returning HTTP 405 Method Not Allowed on method mismatch.
6. **Non-Destructive Scale-Down and Clean Teardown**: Scaling down pods updates the target pool without dropping routes or connections to healthy pods. Deleting Ingresses triggers `pr.proxy.Close()`, cleanly halting active health check tickers (`StopActiveHealthCheck`) and closing idle TCP connection pools.

## Detailed Vulnerability & Mitigation Analysis

### 1. Canary vs Baseline Ingress Variant Isolation & Elimination of Traffic Contamination

- **Vulnerability Mechanism**:
  In [`pkg/ingress/controller.go:L143-L192`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L143-L192), routes were grouped using `routeKey{host: host, prefix: cleanPrefix}`. When an Ingress resource with `nginx.ingress.kubernetes.io/canary: "true"` shared the same `(Host, Path)` as a baseline Ingress, both Ingresses resolved to the exact same `routeKey`. As a result, `targetsByKey[k]` merged Canary pod IPs and Baseline pod IPs into a single slice, distributing traffic randomly across both variants regardless of whether the request contained the Canary header.
- **Remediation Verification**:
  - In [`pkg/ingress/translator.go:L86-L95`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go#L86-L95), `TranslateIngress` parses `nginx.ingress.kubernetes.io/canary: "true"`, extracting the header key and value (defaulting to `"always"` if unspecified), and populates `DiscoveredRoute.Headers`.
  - In [`pkg/ingress/controller.go:L17-L23, L48-L61`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L17-L23), `CompositeRouteKey` is defined as:
    ```go
    type CompositeRouteKey struct {
        Host             string
        Prefix           string
        Method           string
        CanonicalHeaders string
    }
    ```
  - Baseline Ingress produces `CanonicalHeaders == ""` while Canary Ingress produces `CanonicalHeaders == "x-version=canary"`.
  - In `syncIngresses`, `targetsByKey` is indexed by `CompositeRouteKey`. Because the keys are distinct, Baseline pod targets and Canary pod targets are aggregated into separate slices.
  - Exactly one `PrefixRouteSpec` is generated per composite key, producing separate reverse proxies.
  - Verified by `TestIngressController_CanaryBaselineStrictSegregation`:
    - Deployed baseline service (`svc-baseline` on `api.example.com/v1`) and canary service (`svc-canary` on `api.example.com/v1` with `X-Version: canary`).
    - Dispatched 20 requests with `X-Version: canary`: 100% routed to `svc-canary` (`canaryHits == 20`, `baselineHits == 0`).
    - Dispatched 20 requests without headers: 100% routed to `svc-baseline` (`baselineHits == 20`).
    - Dispatched 10 requests with mismatched headers (`X-Version: v1`): 100% routed to `svc-baseline` (`baselineHits == 30`).
    - Zero traffic bleeding occurred between Canary and Baseline backends.
- **Verdict**: **Mitigated**. Strict variant isolation is enforced.

### 2. Elimination of Route Shadowing via ADR-005 Specificity Sorting (CWE-284)

- **Vulnerability Mechanism**:
  In `router.ServeHTTP`, prefix routes are evaluated sequentially. Previously, `controller.go` preserved the arbitrary order of Ingress objects returned by the Kubernetes API server (`keyOrder`). If the baseline Ingress appeared in `keyOrder` before the canary Ingress, incoming client requests with `X-Version: canary` matched the unconstrained baseline route first. The canary route was never evaluated, resulting in complete canary bypass.
- **Remediation Verification**:
  - In [`pkg/ingress/controller.go:L253-L255`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L253-L255), `syncIngresses` explicitly sorts `specs` before updating the router:
    ```go
    // Specificity sort (ADR-005, ADR-096, REQ-096-AC-07)
    router.SortPrefixRouteSpecs(specs)
    ```
  - In [`pkg/router/router.go:L286-L368`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L286-L368), `comparePrefixRouteSpecs` enforces the 5-tier specificity hierarchy:
    1. **Prefix Length**: Longest prefix first.
    2. **Host Specificity**: Explicit domain host before wildcard/empty host.
    3. **Header Specificity**: Greater number of header constraints before fewer constraints (`len(Headers)` descending).
    4. **Method Specificity**: Explicit method constraint before any-method (`""`).
    5. **Deterministic Tie-Breaking**: Alphabetical comparison on Host, CanonicalHeaders, Method, Prefix.
  - In `ReplacePrefixRoutesBySource`, `sortPrefixRoutes(r.prefixRoutes)` is also executed under write lock as a defense-in-depth guarantee.
  - Verified by `TestIngressController_SpecificityOrdering_NoCanaryShadowing`:
    - Mock API server deliberately returned Baseline FIRST (`1-baseline`) and Canary SECOND (`2-canary`).
    - Inspection of internal router table verified that `routes[0]` was the Canary route (`len(Headers) == 1`) and `routes[1]` was the Baseline route (`len(Headers) == 0`).
    - Requests with `X-Version: canary` reached the Canary backend (`canary`).
    - Requests without the header fell through to the Baseline backend (`baseline`).
    - Tested complex 5-tier specificity ranking across `/api/v1/auth`, `/api/v1`, `/api` with Host + Header, `/api` with Host, and `/api` unhosted. Ordering strictly matched ADR-005.
- **Verdict**: **Mitigated**. Header-constrained Canary Ingresses can never be shadowed by generic Baseline Ingresses.

### 3. Elimination of Single-Pod Starvation & Load Balancing Defeat (CWE-400)

- **Vulnerability Mechanism**:
  If pod endpoints were registered as individual single-target routes, first-match linear prefix matching would route 100% of requests to pod replica #1, starving replicas #2 through $M$ and defeating Kubernetes horizontal scaling.
- **Remediation Verification**:
  - In [`pkg/ingress/controller.go:L214-L223`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L214-L223), all pod IP endpoints for a given `CompositeRouteKey` are collected and deduplicated using `seenTarget[k][targetURL]`.
  - Target URLs are deterministically sorted via `sort.Strings(targetsByKey[k])`.
  - Exactly **one** `PrefixRouteSpec` is generated per composite key, configured with `Algorithm: proxy.AlgorithmRoundRobin`.
  - In `pkg/proxy/proxy.go`, `RoundRobinBalancer` distributes requests evenly across all targets:
    $$\text{Traffic Share} \approx \frac{1}{M} \quad \forall \text{ replica } i \in \{1, \dots, M\}$$
  - Verified by `TestIngressController_CompositeRouteKeyAggregation`:
    - Deployed 3 pod backends (`pod-1`, `pod-2`, `pod-3`) with duplicate target injected to test deduplication.
    - Verified router table contained exactly 1 aggregated `k8s-ingress` route.
    - Dispatched 30 sequential HTTP requests: exactly 10 requests were delivered to `pod-1`, 10 to `pod-2`, and 10 to `pod-3` (33.3% share each).
- **Verdict**: **Mitigated**. Fair horizontal load balancing is enforced; single-pod starvation is eliminated.

### 4. Clean Resource Teardown & Socket Exhaustion Prevention (CWE-775)

- **Vulnerability Mechanism**:
  When Ingress resources were deleted or updated, discarded reverse proxies with active health check tickers (`UpstreamTarget.StartActiveHealthCheck`) lingered in heap memory, leaking background goroutines and file descriptors (`EMFILE`).
- **Remediation Verification**:
  - In [`pkg/router/router.go:L522-L541`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L522-L541), `ReplacePrefixRoutesBySource` isolates evicted routes matching `source == "k8s-ingress"`.
  - Outside the write lock, it iterates through evicted routes:
    ```go
    for _, pr := range evicted {
        if pr.proxy != nil {
            pr.proxy.Close()
        }
    }
    ```
  - In [`pkg/proxy/proxy.go:L596-L600`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L596-L600), `ReverseProxy.Close()` calls `p.Balancer.Stop()`, which in turn calls `t.StopActiveHealthCheck()` on all upstream targets, stopping the ticker goroutine and closing idle TCP connection pools.
  - In `controller.go`, deleting an Ingress removes it from `ingList` and `specs`. The subsequent `ReplacePrefixRoutesBySource` call evicts the route and triggers clean proxy closure.
  - Verified by `TestIngressController_PodScaleDown_ZeroDowntime`:
    - Active health check configured at 20ms interval (`/healthz`). Probes verified running.
    - Simulated Ingress deletion: `r.GetPrefixRoutes()` dropped to 0.
    - Verified probe counter ceased incrementing immediately post-deletion (`pAfter <= pBefore + 2`).
    - Subsequent requests to the deleted path immediately returned HTTP 404 Not Found.
- **Verdict**: **Mitigated**. Clean resource teardown eliminates goroutine and socket leaks.

### 5. Ingress Annotation Input Validation & Malformed Input Resilience (CWE-20)

- **Vulnerability Mechanism**:
  Malformed container or Ingress annotations (such as invalid JSON in `toron.io/headers`, unescaped CSV delimiters, or invalid HTTP methods) could cause unhandled panics, crashing the Ingress reconciliation loop.
- **Remediation Verification**:
  - In [`pkg/ingress/translator.go:L46-L109`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go#L46-L109):
    - `AnnotationMethod`: Trimmed and normalized to uppercase via `strings.ToUpper(strings.TrimSpace(rawMethod))`.
    - `AnnotationHeaders`:
      - JSON format: Enclosed in `{...}`. `json.Unmarshal` is executed. If JSON is malformed, the error is handled safely without panicking, and the malformed string is bypassed.
      - CSV format: Split by `,`, then each pair split by `=` via `strings.SplitN(pair, "=", 2)`. Malformed tokens lacking `=` are safely skipped.
    - `AnnotationHeaderPrefix`: Keys trimmed of prefix and values trimmed; merges additively and overrides conflicting keys in grouped headers.
    - NGINX Canary: Default value `"always"` applied if `canary-by-header-value` is empty.
    - Path Security Guards (TASK-087/088): Rejects unhosted root (`/` with empty host), protected internal paths (`/internal`, `/api/status`), and unhosted telemetry endpoints (`/health`, `/metrics`).
  - Verified by `TestTranslateIngress_MethodAndHeaderAnnotations` across all 10 test scenarios, including scenario 1.9 (`{"X-Env":"staging", malformed`) and scenario 1.10 (unannotated Ingress).
- **Verdict**: **Mitigated**. Input validation is resilient, comprehensive, and panic-free.

### 6. Declarative HTTP Method Filtering Support (`PrefixRouteSpec.Method`)

- **Vulnerability Mechanism**:
  Ingress routes previously matched all HTTP verbs indiscriminately. Operators could not restrict Ingress paths to specific verbs (e.g. `POST`), allowing unauthorized HTTP verbs to bypass perimeter controls.
- **Remediation Verification**:
  - In [`pkg/ingress/translator.go:L46-L50, L227`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go#L46-L50), `toron.io/method` is extracted and set on `DiscoveredRoute.Method`.
  - In [`pkg/ingress/controller.go:L241`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L241), `spec.Method = k.Method`.
  - In [`pkg/router/router.go:L824-L827, L844-L846`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L824-L827), `ServeHTTP` checks `pr.method`. If the HTTP verb does not match, `methodMismatch = true` is recorded. If no other route matches, `targetHandler = r.MethodNotAllowed` (HTTP 405 Method Not Allowed) is returned.
  - Verified by `TestIngressController_PrefixRouteSpec_MethodFiltering`:
    - Registered POST-only Ingress on `/submit`.
    - `POST /submit` $\to$ HTTP 200 OK (`post-handled`).
    - `GET /submit` $\to$ HTTP 405 Method Not Allowed.
    - `PUT /submit` $\to$ HTTP 405 Method Not Allowed.
    - Added any-method fallback Ingress on `/submit`: POST matched POST route; GET fell through to fallback route and returned 200 OK.
- **Verdict**: **Mitigated**. Declarative HTTP verb filtering operates correctly.

### 7. Concurrency Safety, Lock Hierarchy, and Data Race Invariants

- **Vulnerability Mechanism**:
  Continuous watch events and 30-second resync loops mutating router state concurrently with runtime HTTP request routing in `router.ServeHTTP` risk data races and lock contention.
- **Remediation Verification**:
  - **Reconciliation Serialization**: `c.syncMu` serializes `syncIngresses` executions, preventing concurrent reconciliations from colliding.
  - **Lock Ordering**: Discovery state lock (`c.mu`) is acquired only to update `c.activeRoutes` and is never nested with `r.mu`.
  - **Sub-Microsecond Write Lock**: In `ReplacePrefixRoutesBySource`, proxy compilation occurs out of lock. Under `r.mu.Lock()`, only pointer swaps and slice partitioning occur. Evicted proxies are closed after releasing `r.mu.Unlock()`.
  - **Runtime Readers**: Request routing in `router.ServeHTTP` safely acquires `r.mu.RLock()`.
  - Verified by `TestIngressController_ConcurrentEventsAndRouting_RaceClean`:
    - 5 churn goroutines rapidly toggled canary Ingresses and scaled pod counts while triggering `syncIngresses`.
    - 20 HTTP client workers dispatched continuous parallel requests (GET, POST, PUT with/without canary headers) for 500ms.
    - Result: 0 data races, 0 deadlocks, 0 unexpected status codes under Go race detector.
- **Verdict**: **Mitigated**. Thread safety is complete and verified.

### 8. Zero Third-Party Dependencies Compliance

- All annotation parsers, composite key formatters, pod target aggregators, and specificity sorters strictly utilize Go standard library packages (`context`, `encoding/json`, `fmt`, `log`, `net`, `net/http`, `net/url`, `path`, `sort`, `strconv`, `strings`, `sync`, `sync/atomic`, `time`).
- `go.mod` and `go.sum` remain unmodified, preserving Toron's zero-dependency pure Go architectural mandate.
- **Verdict**: **Mitigated**.
