# CR-145 - Code Review for Route-Scoped Payload Ingress, Activity Deadlines, and Bulkhead Isolation

## 1. Executive Summary & Review Scope

This code review evaluates the implementation of **Option 1 (Route-Aware Streaming Ingress with Activity Deadlines & Bulkheads)**, architected in [`ADR-145`](../architecture/ADR-145.md), specified in [`REQ-145`](../requirements/REQ-145.md), decomposed across tasks [`TASK-169`](../tasks/TASK-169.md) through [`TASK-173`](../tasks/TASK-173.md), and verified by test suite [`TC-145`](../testCases/TC-145.md).

The implementation reconciles enterprise legacy workloads (200MB+ file uploads, sustained 30s–60s transfers over constrained links, and extended backend execution times) with Toron's core cloud-native principles: sub-millisecond dispatch, zero third-party dependencies, bounded concurrency, constant $O(1)$ memory consumption, and hardened Denial-of-Service ([CWE-400](https://cwe.mitre.org/data/definitions/400.html) / [CWE-770](https://cwe.mitre.org/data/definitions/770.html)) immunity.

## 2. Review Findings & Verification by Area

### 2.1 Requirement Completeness & Acceptance Criteria Verification

The implementation satisfies the functional and non-functional requirements laid out in [`REQ-145`](../requirements/REQ-145.md):
- **AC-145-01 (200MB Upload Allowed on Configured Route)**: Verified. Configured routes with elevated `max_body_bytes` allow 200MB uploads streamed directly to upstreams, while unconfigured routes reject uploads exceeding 4MB with `HTTP 413 Payload Too Large`.
- **AC-145-02 (Fast-Fail Pre-Read Rejection of Oversized Content-Length)**: Verified. `s.handleConn` inspects `req.ContentLength` during interim route lookup and returns `HTTP 413` with `Connection: close` and JSON body in $< 50\,\text{ms}$, without reading payload bytes from the socket or allocating heap memory.
- **AC-145-03 (Activity-Refreshed Read Deadlines for Sustained Transfers)**: Verified. `activityReader` refreshes socket read deadlines on byte transfer progress, allowing sustained slow-link transfers exceeding static timeouts (e.g. 30s transfers under a 5s read deadline) to complete smoothly.
- **AC-145-04 (Strict Termination of Stalled Slowloris Ingestion)**: Verified. Inactive client connections pausing longer than `ReadTimeout` trigger socket deadline expiration and connection teardown within the timeout window, freeing worker goroutines.
- **AC-145-05 (Decoupled Backend Execution & Response Header Timeout)**: Verified. Downstream client write deadlines are decoupled to `effectiveRespTimeout + WriteTimeout` during upstream processing, allowing slow backends to execute without premature client connection drops.
- **AC-145-06 (Route Bulkhead Isolation & Zero Worker Starvation)**: Verified. In-flight route concurrency is capped at `max_concurrency`; excess requests receive immediate `HTTP 503 Service Unavailable` with `Retry-After: 5`, preserving worker pool capacity for operational endpoints (`/health`).

### 2.2 Architecture Alignment (ADR-145 Decisions 1–6)

- **Decision 1 (Two-Phase Ingestion Pipeline)**: Fully compliant. `httpparser.ParseHeader` separates header parsing from body ingestion. `ParseRequest` is preserved as a backward-compatible wrapper.
- **Decision 2 (Declarative Route-Scoped Ceilings & Pre-Read 413)**: Fully compliant. Precedence rules in `GetMaxBodyBytes` and Tier-1 fast-fail rejection in `s.handleConn` match architectural specifications.
- **Decision 3 (Activity-Refreshed Read Deadlines & Anti-Drip Guard)**: Functionally compliant, though boundary conditions on exact-sized payloads and socket closure on `io.EOF` require refinement (see findings CR-145-F01 and CR-145-F02).
- **Decision 4 (Downstream Client Write Timeout Decoupling)**: Fully compliant. Write deadline decoupling is calculated and forced via `tracker.ForceSetWriteDeadline`.
- **Decision 5 (Route Bulkhead Concurrency Limiter & min(32, Pool/4) Guardrail)**: Fully compliant. Atomic tracking with rollback in `TryAcquireRouteSlot` and safety guardrail calculation in `GetMaxConcurrency` align with specifications.
- **Decision 6 (Zero-Copy Streaming Proxy Ingress)**: Compliant for fixed-length uploads, but chunked uploads under default "normalize" mode experience an architectural tension with duplicate buffering (see finding CR-145-F03).

### 2.3 API and Package Design

- Accessor methods on `ProxyRouteConfig` (`GetMaxBodyBytes`, `GetMaxConcurrency`, `GetReadTimeout`, etc.) encapsulate fallback logic cleanly.
- `RouteMatchInfo` and `LookupPrefixRoute` in `pkg/router` provide a clean abstraction for pre-body route resolution without mutating internal router state.
- `NewStreamingBodyReader` implements `io.ReadCloser` cleanly and integrates with `StreamingBodyReader.TotalRead()`.
- Thread safety is maintained with standard `sync.RWMutex` and `sync/atomic` primitives.

### 2.4 Errors and Edge Cases

- **Exact Limit Boundary (`totalRead >= limit`)**: Identified off-by-one boundary behavior where payloads whose size exactly equals `limit` are rejected with `ErrBodyTooLarge` instead of returning `io.EOF` (CR-145-F01).
- **Premature Socket Closure on `io.EOF`**: `activityReader.Read` closes the network socket on `io.EOF`, which can cause write failures when serializing HTTP responses to half-closed client sockets (CR-145-F02).
- **Default Upstream Timeout Error Mapping**: When route `response_header_timeout` is unspecified, proxy timeouts await headers and emit `502 Bad Gateway` instead of `504 Gateway Timeout` (CR-145-F04).
- **Chunked Framing Overhead Clamping**: Raw wire bytes in chunked streams are counted against body limits in `activityReader`, risking premature abortion of valid payloads (CR-145-F05).

### 2.5 Tests

- Comprehensive unit and integration test coverage added across all 5 affected packages:
  - `pkg/config/config_test.go`: Deserialization, fallback, automatic safety guardrails, streaming heuristics, validation.
  - `pkg/httpparser/parser_test.go`: Header isolation, header size ceiling, smuggling rejection, limit enforcement, chunked reader attachment.
  - `pkg/router/router_test.go`: Route lookup, bulkhead concurrency gating, fast-fail 503, deterministic release on panic recovery, automatic safety derivation.
  - `pkg/server/server_test.go`: Sustained upload pacing, Slowloris stall termination, anti-drip rate clamping, pre-read 413, decoupled write deadline, 200MB upload vs 4MB rejection.
  - `pkg/proxy/proxy_test.go`: Constant $O(1)$ memory verification during 50MB transfer, gateway timeout 504, client disconnect context cancellation, fail-closed upstream abort.

### 2.6 Concurrency and Thread Safety

- Atomic operations (`atomic.LoadInt64`, `atomic.AddInt64`) with rollback logic in `TryAcquireRouteSlot` guarantee that route concurrency limits cannot be bypassed by race conditions.
- Context cancellation propagation cleanly terminates upstream backend connections when downstream clients disconnect, preventing orphan goroutines or backend resource leaks.
- Zero race conditions detected across modified packages.

### 2.7 Performance and Reliability

- Request bodies exceeding 64KB are streamed zero-copy directly from the client socket wrapper to upstream transport, eliminating duplicate `io.ReadAll` heap buffering.
- Heap allocation delta during large streaming uploads remains strictly bounded at $< 10\,\text{MB}$, satisfying `NFR-145-1`.
- Fast-fail rejections (`413 Payload Too Large` and `503 Service Unavailable`) execute in $< 1\,\text{ms}$ during Phase 1 routing, protecting reactor workers from head-of-line blocking.

### 2.8 Observability and Configuration

- Configuration extensions in `ProxyRouteConfig` are fully serializable and deserializable in YAML and JSON.
- `ValidateConfig` strictly enforces non-negative constraints on all new timeouts and limits.
- Structured JSON error messages are returned on fast-fail rejections, providing clear feedback to clients and automated tooling.

### 2.9 Maintainability and Go Idioms

- Pure Go standard library networking and concurrency primitives without external dependencies.
- Standard Go interfaces (`io.Reader`, `io.ReadCloser`, `http.Handler`) adhered to throughout.
- Backward compatibility preserved for existing callers of `httpparser.ParseRequest` and existing route configurations.

## 3. Detailed Findings Registry

### CR-145-F01: Off-by-one boundary condition in body limit checks on exact-sized payloads
- **Severity**: High
- **Category**: Correctness / Edge Cases
- **Location**: [`pkg/httpparser/parser.go:351-388`](../../pkg/httpparser/parser.go) and [`pkg/server/activity_reader.go:71-74`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.2 FR-145-2`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 2`](../architecture/ADR-145.md), [`TASK-170 WP-2`](../tasks/TASK-170.md), [`TC-145-01`](../testCases/TC-145.md)
- **Evidence**:
  In `pkg/httpparser/parser.go`:
  ```go
  func (s *StreamingBodyReader) Read(p []byte) (int, error) {
      ...
      if s.limit > 0 && s.totalRead >= s.limit {
          return 0, ErrBodyTooLarge
      }
      ...
      if s.contentLength >= 0 {
          remCL := s.contentLength - s.totalRead
          if remCL <= 0 {
              return 0, io.EOF
          }
  ```
  And in `pkg/server/activity_reader.go`:
  ```go
  func (a *activityReader) Read(p []byte) (int, error) {
      ...
      if a.remaining <= 0 && a.totalRead > 0 {
          a.mu.Unlock()
          return 0, httpparser.ErrBodyTooLarge
      }
  ```
- **Description**:
  In `StreamingBodyReader.Read`, the check `s.totalRead >= s.limit` precedes the `s.contentLength` EOF completion check (`remCL <= 0`). When a client uploads a payload whose exact byte size equals `s.limit` (e.g. `Content-Length: 4,194,304` on a 4MB ceiling), all 4,194,304 bytes are read successfully. However, on the final read call to detect stream completion, `s.totalRead >= s.limit` evaluates to true (4194304 >= 4194304), returning `ErrBodyTooLarge` instead of returning `io.EOF`.
  Similarly, in `activityReader.Read`, when cumulative bytes read reach `limit`, `a.remaining` becomes 0, causing the subsequent read to trigger `a.remaining <= 0 && a.totalRead > 0` and return `httpparser.ErrBodyTooLarge`.
- **Impact**: Valid requests matching the exact configured limit (such as an exact 4MB, 10MB, or 256MB file upload) are rejected with `HTTP 413 Payload Too Large` instead of completing successfully with `HTTP 200 OK`.
- **Recommendation**:
  1. In `StreamingBodyReader`, evaluate the `s.contentLength` EOF check before the limit check, and change `s.totalRead >= s.limit` to `s.totalRead > s.limit` (consistent with line 380).
  2. In `activityReader`, change `a.remaining <= 0` to `a.remaining < 0` (or track an explicit overflow flag).
- **Required Action**: Change `>=` to `>` in `StreamingBodyReader.Read` and `<=` to `<` in `activityReader.Read`, and add a unit test asserting that uploads of exact size `max_body_bytes` succeed with `HTTP 200 OK`.

### CR-145-F02: Unconditional TCP socket closure on `io.EOF` in `activityReader`
- **Severity**: Medium
- **Category**: Reliability / Socket Lifecycle
- **Location**: [`pkg/server/activity_reader.go:82-88`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.3 FR-145-3`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md), [`TASK-171 WP-1`](../tasks/TASK-171.md), [`TC-145-03`](../testCases/TC-145.md)
- **Evidence**:
  In `pkg/server/activity_reader.go`:
  ```go
  n, err := a.r.Read(p)

  a.mu.Lock()
  defer a.mu.Unlock()

  if err != nil {
      if a.conn != nil {
          _ = a.conn.Close()
      }
      return n, err
  }
  ```
- **Description**:
  In `activityReader.Read()`, if the underlying buffered reader `a.r.Read(p)` returns any error, including normal EOF (`err == io.EOF`), it immediately calls `_ = a.conn.Close()`.
- **Impact**:
  When a client cleanly terminates its upload stream (such as sending a TCP FIN / half-close via `SHUT_WR` or stream completion), the server forcefully closes the entire TCP connection before the server handler can serialize the HTTP response via `res.Serialize(conn)`, causing `write: broken pipe` or `use of closed network connection`. In addition, persistent keep-alive connections are prematurely terminated on EOF.
- **Recommendation**:
  Guard socket closure so that it only triggers on actual errors, explicitly excluding clean EOF: `if err != nil && !errors.Is(err, io.EOF)`.
- **Required Action**: Update line 83 in `pkg/server/activity_reader.go` to exclude `io.EOF` from triggering `a.conn.Close()`.

### CR-145-F03: Inbound chunked streaming heuristic discrepancy under default "normalize" mode
- **Severity**: Medium
- **Category**: Architecture Alignment / Memory Safety
- **Location**: [`pkg/config/config.go:686-692`](../../pkg/config/config.go) and [`pkg/proxy/proxy.go:1125-1165`](../../pkg/proxy/proxy.go)
- **Related Artifacts**: [`REQ-145 §2.6 FR-145-6`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 6`](../architecture/ADR-145.md), [`REQ-133`](../requirements/REQ-133.md), [`TASK-172 WP-1`](../tasks/TASK-172.md)
- **Evidence**:
  In `pkg/config/config.go`:
  ```go
  func (p *ProxyRouteConfig) ShouldStreamRequestBody(contentLength int64) bool {
      if p.StreamRequestBody != nil {
          return *p.StreamRequestBody
      }
      return contentLength > 65536 || contentLength == -1
  }
  ```
  In `pkg/proxy/proxy.go`:
  ```go
  shouldStream := p.opts.StreamRequestBody != nil && *p.opts.StreamRequestBody
  if p.opts.StreamRequestBody == nil {
      shouldStream = req.ContentLength > 65536 || (req.ContentLength == -1 && strings.EqualFold(effectiveMode, "passthrough"))
  }
  ```
- **Description**:
  `ProxyRouteConfig.ShouldStreamRequestBody` returns `true` for all chunked requests (`contentLength == -1`) when `StreamRequestBody` is `nil`. However, `ReverseProxy.ServeHTTPWithPrefix` in `pkg/proxy/proxy.go` defines:
  `shouldStream = req.ContentLength > 65536 || (req.ContentLength == -1 && strings.EqualFold(effectiveMode, "passthrough"))`.
  Under the default `inbound_chunked_mode: "normalize"` (governed by REQ-133), `shouldStream` evaluates to `false`. As a result, chunked requests fall into line 1160 (`decodedBytes, err := io.ReadAll(req.Body)`), buffering the entire payload into heap memory to calculate `exactCL`.
- **Impact**:
  A 200MB chunked upload on a route with elevated `max_body_bytes` (with default settings where `stream_request_body` is omitted) will eagerly buffer 200MB into gateway heap memory, violating `NFR-145-1` ($O(1)$ memory constraint) and risking OOM crashes.
- **Recommendation**:
  When routes configure an elevated body ceiling (`max_body_bytes > 4MB`) or when `StreamRequestBody` is auto, the proxy should activate zero-copy streaming upstream for chunked transfers, or reject buffering beyond `opts.MaxPayloadSize`.
- **Required Action**: Align the chunked streaming logic between `config.go` and `proxy.go` to prevent large chunked uploads from falling into unbounded in-memory `io.ReadAll` buffering.

### CR-145-F04: Upstream response header timeout mapped to HTTP 502 instead of HTTP 504 when route timeout is unspecified
- **Severity**: Low
- **Category**: RFC Compliance / Error Handling
- **Location**: [`pkg/proxy/proxy.go:1360-1374`](../../pkg/proxy/proxy.go)
- **Related Artifacts**: [`REQ-145 §2.4 FR-145-4 §3`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 4`](../architecture/ADR-145.md), [`TASK-172 WP-2`](../tasks/TASK-172.md)
- **Evidence**:
  In `pkg/proxy/proxy.go`:
  ```go
  outResp, err := p.Client.Do(outReq)
  if err != nil {
      targetNode.RecordFailure()
      isTimeout := strings.Contains(strings.ToLower(err.Error()), "timeout awaiting response headers")
      var netErr net.Error
      if errors.As(err, &netErr) && netErr.Timeout() {
          isTimeout = true
      }
      if isTimeout && p.opts.ResponseHeaderTimeout > 0 {
          p.writeGatewayTimeout(res, fmt.Sprintf("Upstream timeout (%s): %v", targetURL.String(), err))
          return
      }
      p.writeBadGateway(res, fmt.Sprintf("Upstream unreachable (%s): %v", targetURL.String(), err))
      return
  }
  ```
- **Description**:
  When an upstream backend exceeds the response header timeout, the error check requires `p.opts.ResponseHeaderTimeout > 0` to return `HTTP 504 Gateway Timeout`. If the route did not explicitly specify `ResponseHeaderTimeout` (relying instead on the default 10s transport fallback initialized in `NewProxyWithOptions`), `p.opts.ResponseHeaderTimeout > 0` evaluates to false, causing the gateway to emit `HTTP 502 Bad Gateway` instead of `HTTP 504 Gateway Timeout`.
- **Impact**:
  Upstream timeouts on routes with default response header timeouts incorrectly report `502 Bad Gateway` instead of `504 Gateway Timeout`, violating RFC 9110 §15.6.5 and FR-145-4 §3.
- **Recommendation**:
  Change line 1368 to check `if isTimeout` unconditionally, as any timeout awaiting response headers represents a 504 Gateway Timeout.
- **Required Action**: Change line 1368 in `pkg/proxy/proxy.go` to `if isTimeout { p.writeGatewayTimeout(...) }`.

### CR-145-F05: Chunked framing overhead counted against raw wire limits in `activityReader`
- **Severity**: Low
- **Category**: Edge Cases / Protocol Framing
- **Location**: [`pkg/server/server.go:366`](../../pkg/server/server.go) and [`pkg/server/activity_reader.go:94-102`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.2 FR-145-2 §4`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md), [`TASK-171 WP-1`](../tasks/TASK-171.md)
- **Evidence**:
  In `pkg/server/server.go`:
  ```go
  if req.ContentLength == -1 {
      actReader := newActivityReader(br, conn, tracker, effectiveReadTimeout, effectiveMaxBody)
      chunkedBufr := bufio.NewReader(actReader)
      req.Body = httpparser.NewChunkedBodyReader(chunkedBufr, conn, effectiveMaxBody)
  }
  ```
- **Description**:
  In chunked transfers (`req.ContentLength == -1`), `newActivityReader` wraps `br` and is given `limit = effectiveMaxBody`. `ChunkedBodyReader` then wraps `actReader`. Because `actReader` reads raw wire bytes (which include chunk hexadecimal lengths, CRLF framing, and chunk trailers), its byte counter measures raw wire bytes rather than decoded body bytes. For an upload whose uncompressed payload is close to `effectiveMaxBody` (e.g., 256MB), the chunk framing overhead (~256KB across 32,000 chunks) causes `actReader` to trigger `httpparser.ErrBodyTooLarge` before `ChunkedBodyReader` finishes decoding the valid body.
- **Impact**:
  Legitimate chunked uploads whose uncompressed payload size is strictly within the route's `max_body_bytes` limit can be prematurely rejected if the wire framing pushes total wire bytes past the ceiling.
- **Recommendation**:
  In `newActivityReader`, when wrapping a chunked stream, pass an unconstrained limit (`limit: 0` or include a headroom factor for chunk framing), because `ChunkedBodyReader` already independently enforces `effectiveMaxBody` against uncompressed payload bytes.
- **Required Action**: Pass `0` (or `limit * 105 / 100`) as the ceiling to `newActivityReader` when initializing chunked readers in `server.go:366`.

### CR-145-F06: Unconsumed chunked request bodies on keep-alive connections
- **Severity**: Informational
- **Category**: Maintainability / Concurrency Safety
- **Location**: [`pkg/server/server.go:481-492, 515-521`](../../pkg/server/server.go)
- **Related Artifacts**: [`REQ-145 §2.1 FR-145-1`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 1`](../architecture/ADR-145.md), [`TASK-171 WP-2`](../tasks/TASK-171.md)
- **Evidence**:
  In `pkg/server/server.go`:
  ```go
  if req.ContentLength > 0 {
      if sr, ok := req.Body.(*httpparser.StreamingBodyReader); ok && sr.TotalRead() < req.ContentLength && res.StatusCode < 400 {
          _ = req.CloseBody()
          ...
          _ = conn.Close()
          return nil
      }
  }
  ```
- **Description**:
  The server includes safeguards to terminate TCP connections if an HTTP handler produces a response without reading the full fixed-length request body (`sr.TotalRead() < req.ContentLength`). However, no equivalent check is performed for chunked requests (`req.ContentLength == -1`).
- **Impact**:
  If a custom handler or redirect generates an early response on a chunked request without consuming the body, and the client sends `Connection: keep-alive`, subsequent requests on the socket could desynchronize if unread chunks remain in the socket buffer.
- **Recommendation**:
  For chunked requests, verify whether `ChunkedBodyReader` reached EOF; if not, force `Connection: close` and close the connection before returning to the read loop.
- **Required Action**: Add an unconsumed chunked reader check in `s.handleConn` before proceeding to keep-alive reuse.
