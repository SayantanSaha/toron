# AN-008 - Alert Dashboard Event Homogeneity and Operational Alert Suppression Analysis

## 1. Problem Statement

Operators monitoring the Toron Edge Gateway Control Center (`#/alerts`) have submitted the following operational defect report:
> *"The current alert dashboard is showing no events other than blocked."*

When navigating to the Alerts & Threat Defense view (`public/js/views/alerts.js`), operators observe that the primary events feed ("Active Alerts & WAF Incidents") renders exclusively red security events marked with the status badge **`Blocked`**. No non-blocked events are displayed:
1. Operational system health alerts (failing upstream pool instances, route 5xx error rate spikes exceeding the 2% threshold, and failing ACME SSL certificate renewals) never render in the alert feed whenever security incidents are present, despite being flagged on the top KPI card, navigation badge, and Overview dashboard.
2. The WAF telemetry pipeline emits zero detection-only anomalies (`Action: "logged"`) under default configuration.
3. Automated IP ban events (`Action: "banned"`) emitted by the auto-ban subsystem are mislabeled as `Logged` by client badging logic.
4. Client rate-limiting rejections (HTTP 429 Too Many Requests) emit no telemetry to the security incident logger.
5. Clicking the "Warning" severity facet chip displays *"Zero security incidents match active filters"*, leaving operators with the impression that non-critical defensive signals, warning-level telemetry, and infrastructure degradations are entirely missing or failing to register.

---

## 2. Observed Behavior

### 2.1 Complete Disappearance of Operational System Alerts
- In [`public/js/model.js`](../../public/js/model.js), `buildDataModel()` detects active infrastructure degradations and populates `D.alerts`:
  - `upstream_${p.id}`: Upstream pool degradation when healthy backend instances drop.
  - `route_${r.id}`: High 5xx error rate alerts when errors exceed 2%.
  - `cert_${c.id}`: ACME certificate renewal failures.
- When an upstream server fails or 5xx errors spike:
  - The left navigation badge (`#nav button[data-nav="alerts"] .badge`) displays `1`.
  - The Overview banner (`#/overview`) reports `1 Active Alert: Upstreams Unhealthy`.
  - The top KPI strip on `#/alerts` displays `1` in the "Active Incidents / Alerts" card.
- However, inside the primary card titled **"Active Alerts & WAF Incidents"** (`#alIncList`), **zero operational alerts are displayed**. Instead, only previous WAF security blocks (e.g., SQL injection, XSS) appear in the list. The operational issue that triggered the alert badge is completely invisible on the Alerts page.

### 2.2 Exclusively "Blocked" Security Telemetry
- In default gateway deployments, every row rendered in the incidents feed displays:
  - Red failure icon (`ICON('i-x')`).
  - Red status badge: `<span class="st s5">Blocked</span>`.
- There are no entries with amber warning indicators or green informational indicators.
- Under the severity filter chips:
  - Clicking **`All`**: Displays only `Blocked` events.
  - Clicking **`Critical`**: Displays the exact same `Blocked` events.
  - Clicking **`Warning`**: Displays the empty state message: `Zero security incidents match active filters.`

### 2.3 Auto-Ban Events Misrepresented
- When an abusive client IP exceeds the violation threshold within the rate window, `AutoBanManager` in [`pkg/waf/auto_ban.go`](../../pkg/waf/auto_ban.go) emits an audit event with `Action: "banned"`.
- In [`public/js/views/alerts.js`](../../public/js/views/alerts.js), the badging logic evaluates:
  ```javascript
  const isBlocked = inc.action === 'blocked';
  ```
- Because `inc.action === 'banned'` is not `'blocked'`, `isBlocked` evaluates to `false`. The badge renders as `<span class="st s4">Logged</span>`, misrepresenting a severe firewall quarantine action as an unblocked monitoring log.

### 2.4 Lack of Telemetry for Rate Limiting and Route Ingress Throttling
- When clients violate route-level token bucket limits configured via `rate_limit` (e.g., `10/sec`), [`pkg/router/rate_limiter.go`](../../pkg/router/rate_limiter.go) drops the connection with `429 Too Many Requests` and sets `Retry-After`.
- No security event is dispatched to `AuditLogger`, meaning traffic drops due to volumetric rate limiting do not appear in the alert dashboard.

## 3. Expected Behavior

1. **Holistic Alerts & Incidents Visibility**:
   - The primary feed in the Alerts view must present all operational alerts requiring administrative attention (upstream down, route error budget burned, certificate expiry) alongside security incidents.
   - Incoming WAF security events must not displace or suppress active operational system alerts.
2. **Accurate Action Badging**:
   - The UI must distinguish between different defense actions:
     - `Blocked`: Request dropped due to WAF rule match, IP ACL, or protocol violation.
     - `Logged`: Request allowed to pass but recorded due to detection mode or sub-threshold anomaly.
     - `Banned`: Offending IP address added to the automated firewall quarantine list.
     - `Throttled`: Volumetric rate limit exceeded (HTTP 429).
     - `Degraded`: Operational infrastructure health degradation.
3. **Functional Faceted Severity Filtering**:
   - The `Critical` facet chip should filter for critical system failures, active bans, and blocked high-severity threats.
   - The `Warning` facet chip should surface sub-threshold anomalies, detection mode alerts, high-latency warnings, and temporary rate throttles.
4. **Context-Sensitive Drill-Down**:
   - Clicking an operational alert should navigate to the affected resource (`#/upstreams`, `#/routes`, or `#/certs`) or display diagnostic health probe history.
   - Clicking a security incident should open the forensic drawer displaying rule metadata, parameter location, and payload snippet.

## 5. Scope and Impact

### 5.1 Operational Impact
- **Blindness to Infrastructure Degradations**: When an operator sees an alert badge on the navigation bar, clicking through to `#/alerts` hides the operational degradation behind older WAF block events. Operators cannot quickly determine which upstream instance failed or which route has elevated 5xx error rates.
- **Operator Misdirection & Alarm Fatigue**: Operators observe an overwhelming list of identical red `Blocked` events. Because `Warning` facet filtering displays 0 events, operators assume the warning/detection engine is non-operational.
- **Forensic Ambiguity**: Permanent and temporary IP quarantine actions are displayed as `Logged`, obscuring the true defensive state of threat actors.

### 5.2 Technical & Architectural Scope
- **Presentation Layer**:
  - `public/js/views/alerts.js`: Needs structural separation or unified aggregation between `model.alerts` and `model.incidents`, along with multi-state action badging (`Blocked`, `Logged`, `Banned`, `Operational`).
  - `public/js/components/drawer.js`: Needs support for operational alert navigation and correct `Banned` action rendering.
  - `public/js/model.js`: Needs clear schema normalization so operational alerts can coexist cleanly with security incidents.
- **Backend Telemetry Layer (Optional Enhancement)**:
  - `pkg/router/rate_limiter.go`: Integration of security audit logging for volumetric 429 events.
  - `pkg/waf/middleware.go`: Clarification of detection telemetry emission.

## 7. Analysis

### 7.1 The Ternary Fallback Antipattern (Root Cause of Operational Alert Suppression)
In commit `501f994`, the engineering team implemented [REQ-146](../requirements/REQ-146.md) to fix alert badge inflation caused by injecting banned IPs into `D.alerts`.
The resulting architectural separation in [`public/js/model.js`](../../public/js/model.js) properly split data into:
- `D.alerts`: Operational health degradations (`upstream_*`, `route_*`, `cert_*`).
- `D.incidents`: WAF security audit events.
- `D.bannedIps`: Firewall ban entries.

However, in the view implementation ([`public/js/views/alerts.js`](../../public/js/views/alerts.js)), the developer treated `D.alerts` not as a distinct operational feed or merged stream, but as a fallback:
```javascript
const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);
```
Because production edge nodes continuously receive automated internet scanner requests (e.g. vulnerability probes on `/wp-login.php`, `/.env`, `/actuator/health`), the WAF intercepts these probes and stores up to 50 events in `AuditLogger`.
Thus, `model.incidents.length` is almost always $> 0$.
**As a result, `model.alerts` is permanently suppressed from view.**

### 7.2 Why All Emitted WAF Events Are "Blocked"
Under Toron's default configuration:
1. `WAFConfig.Mode == "enforce"`
2. `WAFConfig.AnomalyThreshold == 5`
3. Every built-in OWASP rule has `Score: 5`.

When an inspection matches a rule, `score` is calculated as $\sum \text{rule.Score} \ge 5$.
In enforce mode:
$$\text{blocked} = (\text{score} \ge \text{AnomalyThreshold}) \land (\text{mode} == \text{"enforce"})$$
Since $\text{score} \ge 5$ and $\text{AnomalyThreshold} = 5$, $\text{blocked}$ is unconditionally `true`.
The detection logging branch:
```go
if score > 0 && !blocked {
    logger.LogEvent(SecurityEvent{..., Action: "logged"})
}
```
requires $\text{blocked} == \text{false}$, which is only possible if:
- `mode == "detection"` (audit-only mode), or
- A rule matches with $\text{Score} < 5$ while no other rules match.

Because neither condition is met in a standard out-of-the-box configuration, **100% of WAF events are logged as `Action: "blocked"`**.

### 7.3 Why the "Warning" Severity Filter Is Always Empty
In [`public/js/views/alerts.js`](../../public/js/views/alerts.js):
```javascript
} else if (state.alSev === 'warning') {
  const isWarn = inc.action === 'logged' || (inc.anomaly_score != null && Number(inc.anomaly_score) < 10) || inc.sev === 'warning';
  if (!isWarn) return false;
}
```
Because:
1. Operational alerts (`sev: 'warning'` or `sev: 'critical'`) are discarded by line 192;
2. All WAF events have `action: 'blocked'`;
3. Even if an incident has `anomaly_score: 5` ($< 10$), if `state.alSev === 'warning'`, wait:
   Notice that if `inc.anomaly_score < 10`, `isWarn` is `true`!
   **Why did the user see no events other than blocked under Warning?**
   Because even when `isWarn` matches, the rendered list item in line 239 still displays:
   `<span class="st ${isBlocked ? 's5' : 's4'}">${isBlocked ? 'Blocked' : 'Logged'}</span>`!
   Even when an incident has score 5 and matches the Warning filter, **its status badge still reads `Blocked`**!
   Therefore, every single visible item across both Critical and Warning filters says `Blocked`!

## 8. Root Cause

### Confirmed
1. **Frontend Alert Feed Mutual Exclusion Bug ([`public/js/views/alerts.js#L192`](../../public/js/views/alerts.js))**:
   `const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);`
   This ternary conditional suppresses and drops `model.alerts` whenever any security incident exists. Operational alerts (upstream degradation, route error rates, cert renewal failures) are silenced.
2. **Binary Action Badging Bug ([`public/js/views/alerts.js#L229`](../../public/js/views/alerts.js) & [`public/js/components/drawer.js#L35`](../../public/js/components/drawer.js))**:
   The frontend uses a binary check `${isBlocked ? 'Blocked' : 'Logged'}`. Any non-blocked event (such as `action: "banned"` from auto-ban, or operational alerts without an `action` property) is mislabeled as `Logged`. Furthermore, any blocked event matching a lower anomaly score still renders the badge `Blocked`.
3. **WAF Scoring Saturation in Enforce Mode ([`pkg/waf/waf.go`](../../pkg/waf/waf.go), [`pkg/waf/rules.go`](../../pkg/waf/rules.go), [`pkg/waf/middleware.go`](../../pkg/waf/middleware.go))**:
   Every built-in OWASP rule has `Score: 5`, matching `AnomalyThreshold: 5`. Under default enforce mode, every rule match meets the threshold and triggers a block. Sub-threshold detection events (`Action: "logged"`) cannot occur for built-in rules without reconfiguring the engine mode to detection or defining custom rules.
4. **Fast-Path Action Homogeneity ([`pkg/waf/middleware.go`](../../pkg/waf/middleware.go))**:
   All fast-path security defenses (`auto_ban_drop`, `ip_acl_block`, `protocol_violation`, `waf_block`) explicitly log `Action: "blocked"`.

### Probable
1. **Telemetry Absence in Router Rate Limiter**:
   Volumetric rate-limiting rejections (HTTP 429) do not emit security events to `AuditLogger`, meaning non-WAF threat mitigation events are entirely absent from the alerts telemetry stream.

### Unknown
1. Whether the user also expected standard HTTP 4xx client errors (e.g. 404 Not Found, 401 Unauthorized) to appear as alert events (standard practice reserves alerts for actionable anomalies and degradations, while access logs belong in `#/logs`).

## 9. Options

### Option 1: Dual-Card UI Structure (Dedicated Operational Alerts Card + Dedicated Security Incidents Feed)
Restructure `public/js/views/alerts.js` into two clear, distinct cards:
1. **Operational System Alerts Card** (rendered conditionally or persistently above the incidents feed):
   - Renders `model.alerts` (upstream failures, 5xx route spikes, cert renewals).
   - Each item includes action buttons to navigate directly to the affected pool (`#/upstreams`), route (`#/routes`), or certificate (`#/certs`).
   - If zero operational alerts exist, displays a compact green banner: `✓ All systems operational`.
2. **Security Incidents & Threat Defense Feed**:
   - Renders `model.incidents` with search, severity filtering, and pagination.
   - Updates badging to multi-action: `Blocked` (red), `Logged` (blue/amber), `Banned` (purple/red), `Throttled` (amber).
   - In the drawer (`public/js/components/drawer.js`), correctly displays the action pill and forensic details.

*Pros*:
- Clean architectural separation: eliminates schema conflation between operational alerts and WAF security events.
- Highly actionable: operational alerts provide direct links to resolve infrastructure issues rather than pretending to be WAF rules.
- Directly resolves the user report: operational alerts are never hidden by security blocks.

*Cons*:
- Slightly increases vertical layout height on `#/alerts`.

---

### Option 2: Unified Merged Feed with Normalized Event Schema
Merge `model.alerts` and `model.incidents` into a single chronological feed `incs`:
```javascript
const operationalEvents = (model.alerts || []).map(a => ({
  id: a.id,
  timestamp: a.timestamp,
  category: a.title,
  action: 'operational',
  sev: a.sev || 'critical',
  path: a.go ? `/${a.go}` : '/',
  rule_id: 'SYSTEM',
  client_ip: 'system',
  detail: a.detail
}));

const incs = [...operationalEvents, ...(model.incidents || [])].sort((a, b) => {
  return new Date(b.timestamp) - new Date(a.timestamp);
});
```
Update list rendering and drawer to handle `action === 'operational'` cleanly.

*Pros*:
- Retains the exact single-feed UI layout of the current redesign.
- Single search bar and pagination controls cover both operational and security events.

*Cons*:
- Conflates system infrastructure health with security attack forensics.
- Requires synthetic placeholder properties (`client_ip: 'system'`, `rule_id: 'SYSTEM'`) to fit the security table template.

---

### Option 3: Option 1 + Backend Telemetry Enrichment (Full-Stack Alignment)
In addition to Option 1 (Dual-Card UI structure and multi-action badging):
1. **Rate Limiting Telemetry**: Extend [`pkg/router/rate_limiter.go`](../../pkg/router/rate_limiter.go) to optionally accept `*waf.AuditLogger` and emit a `SecurityEvent` (`Event: "rate_limit_drop"`, `Action: "throttled"`, `Category: "rate_limit"`).
2. **Sub-Threshold Anomaly Logging**: In [`pkg/waf/middleware.go`](../../pkg/waf/middleware.go), if a custom or future rule has score below threshold, ensure it logs as `Action: "logged"`.
3. **Multi-Action Drawer**: Support `banned` and `throttled` actions in `drawer.js`.

*Pros*:
- Comprehensive end-to-end telemetry resolution.
- Populates the `Warning` facet filter with genuine warning-level telemetry (rate limiting and detection events).

*Cons*:
- Involves both backend Go changes and frontend JavaScript changes.

## 10. Recommendation

**Adopt Option 1 (with frontend multi-action badging) immediately as Phase 1, followed by Option 3 backend rate-limiting telemetry as Phase 2.**

### Phase 1 (Frontend Architectural Remediation)
1. **Eliminate the Mutual Exclusion Fallback**:
