# TC-120 - Test Specification for Heterogeneous Multi-Hop Live Docker Harness Network Execution

## 1. Test Suite Overview & Objectives

### 1.1 Executive Summary & Problem Context
During end-to-end master benchmark validation (`./benchmarks/run_all.sh --auto-start --docker`), the Heterogeneous Multi-Hop Backend Origin Testbed ([`REQ-113`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-113.md), `BMK-03`) terminated abruptly with a fatal runtime panic:
```text
panic: runtime error: invalid memory address or nil pointer dereference at benchmarks/multihop/runner.go:687
```

As detailed in [`REQ-120`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-120.md) and [`ADR-120`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-120.md), the crash stemmed from four architectural defects:
1. **Uninstantiated Backend Descriptors in Live Mode**: Running `runner.go` with `-standalone=false` left `env.NodeBackend`, `env.PyBackend`, and `env.GoBackend` pointers `nil`, triggering a nil pointer dereference during scenario loops.
2. **In-Memory Server Invocation on Non-Existent In-Process Server**: Five HTTP/2 scenarios invoked `env.EdgeServer.HTTP2AdapterHandler().ServeHTTP(...)` directly, failing with a nil dereference in live Docker mode and completely bypassing the physical network stack.
3. **In-Memory Upstream Header Leakage Verification**: `VECTOR-08` inspected pseudo-header stripping by acquiring a mutex on `targetBackend.Mu` and reading in-memory struct fields (`targetBackend.LastHeaders`), which is impossible against external containerized backends.
4. **Divergent Execution Semantics**: In-memory abstractions in standalone mode diverged from wire-level networking required in live Docker mode.

### 1.2 Test Suite Objectives
This test specification defines the verification procedures to ensure that:
1. Live mode backend descriptors are non-nil, fully populated with runtime metadata, and safe against nil pointer dereferences.
2. All HTTP/2 attack and baseline vectors execute as physical wire-level requests over cleartext TCP/h2c to `env.EdgeAddr`, reliably capturing edge gateway rejections ($400\text{ Bad Request}$, stream resets).
3. Upstream header isolation (`VECTOR-08`) is verified over the wire by inspecting the JSON response payload echoed by backend origins, asserting zero leaked `:` pseudo-headers.
4. Stage 2 benign canary checks (`GET /canary`) consistently verify connection pool integrity and zero response desynchronization across all three runtimes (Node.js `llhttp`, Python `uvicorn`/`h11`, Go `net/http`).
5. Complete 30-scenario parity ($10\text{ vectors} \times 3\text{ backends}$) is achieved across both Standalone In-Process mode and Live Multi-Container mode.
6. Execution is completely race-free under Go's race detector.
7. Benchmark reports conform strictly to [`REQ-119`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-119.md) historical run retention rules and atomic manifest tracking.

## 2. Test Setup & Environmental Requirements

### 2.1 Target Topologies

The test suite evaluates Toron across two distinct execution topologies:

```
                      +-------------------------------------------------------------+
                      |                 Multi-Hop Testbed Execution                 |
                      +-------------------------------------------------------------+
                                     |                               |
                   Standalone Mode   |                               | Live Docker Mode
                   (--standalone)    |                               | (--docker / -standalone=false)
                                     v                               v
                      +-----------------------------+ +-------------------------------+
                      | In-Process Testbed          | | Docker Compose Bridge Network |
                      | - Toron Edge (dynamic port) | | - toron-edge:8080 (h2c)       |
                      | - Node mock origin          | | - toron-node-origin:9101      |
                      | - Python mock origin        | | - toron-python-origin:9102    |
                      | - Go mock origin            | | - toron-go-origin:9103        |
                      +-----------------------------+ +-------------------------------+
                                     |                               |
                                     +---------------+---------------+
                                                     |
                                                     v
                                      +-----------------------------+
                                      | Wire-Level Protocol Engine  |
                                      | - Prior Knowledge h2c       |
                                      | - Raw TCP Socket Probes     |
                                      | - Echo JSON Payload Parser  |
                                      +-----------------------------+
```

### 2.2 Environmental Prerequisites & Dependencies
- **Go Toolchain**: Go 1.24+ with `-race` support.
- **External Dependencies**: Zero external Go packages outside `go.mod` (strictly standard library and `golang.org/x/net/http2`).
- **Container Environment** (for Live Docker Mode):
  - Docker Engine 24.0+ and Docker Compose v2.
  - Bridge network: `multihop-net`.
  - Exposed edge port: `127.0.0.1:8080`.
  - Backend origins: Node.js 20 LTS (port 9101), Python 3.11 (port 9102), Go 1.24 (port 9103).
- **Socket Timeouts**:
  - Connect/Dial Timeout: $\le 2.0\text{ seconds}$.
  - Socket Read / Probe Timeout: $\le 3.0\text{ seconds}$.

## 3. Test Case Specifications

### TC-120-01: Live Mode Backend Descriptor Initialization
- **Identifier**: `TC-120-01`
- **Target Subsystem**: Multi-Hop Testbed Runner Core ([`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go))
- **Test Implementation**: `TestMultiHop_LiveModeInitialization` in [`benchmarks/multihop/multihop_test.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/multihop_test.go)
- **Objective**: Verify that when initialized with `-standalone=false -edge-addr <host:port>`, the runner properly constructs non-nil backend descriptors for Node.js, Python, and Go, populates all required evaluation metadata, and that server teardown handles unstarted in-process servers safely without panic.
- **Preconditions**: Standalone flag set to `false`; target edge address supplied (e.g. `127.0.0.1:8080`).
- **Inputs**:
  - `standalone`: `false`
  - `edgeAddr`: `"127.0.0.1:8080"`
- **Execution Steps**:
  1. Invoke the live environment initialization logic (or construct `TestbedEnvironment` with `IsLive: true`).
  2. Assert that `env.NodeBackend != nil`, `env.PyBackend != nil`, and `env.GoBackend != nil`.
  3. Validate descriptor fields:
     - `NodeBackend.Runtime == "Node.js 20 LTS"`, `NodeBackend.ParserEngine == "llhttp (C-based)"`, `NodeBackend.Prefix == "node"`
     - `PyBackend.Runtime == "Python 3.11"`, `PyBackend.ParserEngine == "uvicorn / h11"`, `PyBackend.Prefix == "python"`
     - `GoBackend.Runtime == "Go 1.24"`, `GoBackend.ParserEngine == "net/http"`, `GoBackend.Prefix == "go"`
  4. Assert that `sb.Server == nil` for all three descriptors.
  5. Call `sb.Close()` on each unstarted descriptor and call `env.Teardown()`.
  6. Pass the constructed environment into `RunAllScenarios(env)` against a mock live listener to confirm that iterating over `backends := []*SimulatedBackend{env.NodeBackend, env.PyBackend, env.GoBackend}` and accessing `b.Runtime` on line 687 does not panic.
- **Expected Outcomes**:
  - No nil pointer dereference or runtime panic occurs.
  - All descriptors contain correct, non-empty runtime, parser engine, and routing prefix strings.
  - `sb.Close()` and `env.Teardown()` execute cleanly as no-ops when `sb.Server == nil`.
- **Boundary & Negative Conditions**:
  - Test invocation with empty or malformed `edgeAddr`.
  - Calling `sb.Close()` multiple times consecutively on an unstarted backend descriptor.

### TC-120-02: Live Wire Protocol Execution for HTTP/2 Vectors
- **Identifier**: `TC-120-02`
- **Target Subsystem**: Wire-Level Protocol Execution Adapters ([`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go))
- **Test Implementation**: `TestMultiHop_LiveWireExecution` in [`benchmarks/multihop/multihop_test.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/multihop_test.go)
- **Objective**: Verify that HTTP/2 attack vectors (`VECTOR-01` [H2.TE], `VECTOR-02` [H2.CL-Duplicate], and `VECTOR-03` [H2.CL-Mismatch]) execute strictly over physical TCP/h2c sockets to `env.EdgeAddr` without calling in-memory adapter handlers, and that the edge gateway enforces RFC 7540 / RFC 9113 compliance by returning `400 Bad Request` or protocol stream errors.
- **Preconditions**: Toron edge gateway running and accepting cleartext HTTP/2 connections on `env.EdgeAddr`.
- **Inputs**:
  - `VECTOR-01`: Cleartext h2c request to `POST /<prefix>/echo` containing header `Transfer-Encoding: chunked`.
  - `VECTOR-02`: Cleartext h2c request to `POST /<prefix>/echo` containing duplicate `Content-Length` headers (`5` and `10`).
  - `VECTOR-03`: Cleartext h2c request to `POST /<prefix>/echo` containing declared `Content-Length: 50` but supplying only 5 body bytes (`"short"`).
- **Execution Steps**:
  1. Open a raw TCP connection to `env.EdgeAddr` with dial timeout $\le 2\text{s}$.
  2. For each vector, dispatch the HTTP/2 frame stream (Connection Preface `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` + `SETTINGS` + `HEADERS` / `DATA` frame) or dispatch via prior knowledge `http2.Transport`.
  3. Capture the edge gateway response over the wire.
  4. Verify that `env.EdgeServer.HTTP2AdapterHandler().ServeHTTP(...)` is never called.
  5. Verify that the response code is `400 Bad Request` or the connection receives an HTTP/2 `RST_STREAM` / `GOAWAY` frame.
  6. Assert `res.Stage1EdgeStatus == 400` and `res.Stage1Passed == true`.
- **Expected Outcomes**:
  - Malformed HTTP/2 frames are intercepted and rejected at the edge gateway over the wire.
  - Zero bytes of the malformed or ambiguous payload reach backend origins.
  - Socket read deadline completes within $\le 3\text{s}$ without hanging.
- **Boundary & Negative Conditions**:
  - Edge gateway unceremoniously closes TCP socket (`RST` or `FIN`) upon encountering framing errors; harness must treat stream reset or connection drop on invalid frame as a valid rejection (`res.Stage1Passed = true`).

### TC-120-03: CRLF Header Injection Wire Verification (VECTOR-07)
- **Identifier**: `TC-120-03`
- **Target Subsystem**: Header Sanitization & Protocol Validation ([`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go))
- **Test Implementation**: `TestMultiHop_VectorsIndividual/node/VECTOR-07` (and corresponding python/go subtests) in [`benchmarks/multihop/multihop_test.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/multihop_test.go)
- **Objective**: Verify that an HTTP/2 or HTTP request containing embedded `\r\n` characters in header values (`VECTOR-07`) is rejected over the wire with `400 Bad Request` or stream error, preventing HTTP response splitting and header injection into upstream HTTP/1.1 connections.
- **Preconditions**: Edge gateway listening on `env.EdgeAddr`.
- **Inputs**:
  - Request Path: `POST /<prefix>/echo`
  - Injected Header: `X-Custom: val\r\nInjected-Header: evil`
  - Body: `"test"`
- **Execution Steps**:
  1. Transmit the request with CRLF byte injection over the wire to `env.EdgeAddr`.
  2. If using standard client libraries that sanitize headers client-side, deliver raw HPACK-encoded `HEADERS` frame or raw HTTP wire bytes directly.
  3. Record the gateway response status and socket state.
  4. Assert that `res.Stage1EdgeStatus == 400` or stream error occurred.
  5. Assert that no injected header (`Injected-Header: evil`) reached the upstream backend.
  6. Assert `res.Stage1Passed == true`.
- **Expected Outcomes**:
  - Edge gateway detects illegal carriage return / newline in header value and rejects request with status 400.
  - Upstream backend connection pool remains unpolluted.
- **Boundary & Negative Conditions**:
  - Test CRLF variations: `\r`, `\n`, and `\r\n\t` (line folding attempts).

### TC-120-04: Pseudo-Header Upstream Stripping Wire Verification (TestMultiHop_PseudoHeaderEchoVerification)
- **Identifier**: `TC-120-04`
- **Target Subsystem**: Upstream Header Translation & Isolation ([`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go))
- **Test Implementation**: `TestMultiHop_PseudoHeaderEchoVerification` in [`benchmarks/multihop/multihop_test.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/multihop_test.go)
- **Objective**: Verify that `VECTOR-08` validates HTTP/2 pseudo-header stripping exclusively by parsing the JSON response payload returned by `POST /<prefix>/echo` over the wire, asserting that zero colon-prefixed (`:`) keys leak upstream, with no access to in-memory mutexes or struct fields.
- **Preconditions**: Edge gateway and backend origin running; backend origin implements the `POST /echo` contract returning JSON object `{"headers": {...}}`.
- **Inputs**:
  - Protocol: HTTP/2 (Cleartext h2c)
  - Endpoint: `POST /<prefix>/echo`
  - Pseudo-Headers: `:protocol: websocket`, `:custom-pseudo: invisible`, `:path: /<prefix>/echo`, `:authority: localhost`, `:scheme: http`
  - Body: `"valid-body"`
- **Execution Steps**:
  1. Send h2c request containing valid and custom pseudo-headers to `env.EdgeAddr`.
  2. Read the full HTTP 200 response body over the wire.
  3. Unmarshal the response body into a JSON map (`map[string]any`).
  4. Extract the `"headers"` key as a map of header names to values.
  5. Iterate across all keys in the `"headers"` map.
  6. Assert that **zero** keys start with `:` (colon).
  7. Confirm `res.Stage1Passed == true` and `res.Stage1EdgeStatus == 200`.
  8. *Negative Test*: Feed a simulated response payload containing `":leaked-pseudo": "bad"` into the parser; assert that the parser marks `res.Stage1Passed = false` and sets `res.FailureReason = "pseudo-header leaked to upstream: :leaked-pseudo"`.
- **Expected Outcomes**:
  - Legitimate pseudo-headers are stripped by Toron during HTTP/2 to HTTP/1.1 translation per RFC 7540 §8.1.2.1.
  - Echoed JSON headers contains only valid standard HTTP/1.1 headers.
  - The verification algorithm depends 100% on the wire response payload and 0% on in-process memory.
- **Boundary & Negative Conditions**:
  - Upstream backend returns uppercase or mixed-case header keys; parser must normalize or check prefix case-insensitively.
  - Malformed or truncated JSON response body handled gracefully without panic.

### TC-120-05: Stage 2 Benign Canary Verification
- **Identifier**: `TC-120-05`
- **Target Subsystem**: Two-Stage Desynchronization Protocol ([`benchmarks/multihop/runner.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/runner.go))
- **Test Implementation**: `TestMultiHop_VectorsIndividual` in [`benchmarks/multihop/multihop_test.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/multihop/multihop_test.go)
- **Objective**: Verify that immediately following every Stage 1 attack vector ($r_{\text{poison}}$), a benign canary request ($r_{\text{benign}}$: `GET /<prefix>/canary`) transmitted over the wire returns HTTP `200 OK` with body `"canary_ok"`, proving that connection pools were not desynchronized or poisoned.
- **Preconditions**: Stage 1 probe completed across all 10 vectors and 3 runtimes.
- **Inputs**:
  - Request: `GET /<prefix>/canary HTTP/1.1`
  - Headers: `Host: <edgeAddr>`, `Connection: keep-alive`
- **Execution Steps**:
  1. Immediately after Stage 1 probe execution, dispatch `GET /<prefix>/canary` over HTTP/1.1 to `env.EdgeAddr`.
  2. Ingest status code and body.
  3. Verify `res.Stage2CanaryStatus == 200`.
  4. Verify body contains `"canary_ok"`.
  5. Verify `res.Stage2CanaryPassed == true`.
  6. Verify `res.Desynchronization == false` and `res.PoolIntegrity == true`.
- **Expected Outcomes**:
  - 100% of canary probes succeed ($30/30$).
  - `DesynchronizationCount` is exactly `0`.
  - `PoolPoisoningCount` is exactly `0`.
- **Boundary & Negative Conditions**:
  - Canary timeout ($\le 3\text{s}$); if a poisoned socket hangs, the canary must fail fast with a timeout error rather than deadlock.

  - Execution with one backend simulated as failing; confirm that `FailedScenarios == 10`, `OverallVerdict == "FAIL"`, and runner exits with code 1.

```bash
go test -v -race -count=1 ./benchmarks/multihop/...
```

Execute the multi-hop testbed runner script in standalone in-process mode:
```bash
bash benchmarks/multihop/run_multihop.sh --standalone
```

```bash
cat benchmarks/results/multihop_report.json | jq .overall_verdict
cat benchmarks/results/multihop_report.json | jq .total_scenarios
```

```bash
bash benchmarks/multihop/run_multihop.sh --docker
```

Execute the complete master benchmark suite with auto-start and docker flags enabled:
```bash
./benchmarks/run_all.sh --auto-start --docker
```
