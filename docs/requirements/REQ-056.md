# REQ-056 - Single Page Application (SPA) HTML5 History Fallback Support for Static Routes

## Description

The Toron web server shall support Single Page Application (SPA) HTML5 History routing fallback for static routes (equivalent to Nginx's `try_files $uri $uri/ /index.html;`).

In modern web applications built using frameworks such as React, Vue, Angular, and Svelte, client-side routing relies on the HTML5 History API (`pushState`, `replaceState`). URLs such as `/kite/signin`, `/kite/devops`, or `/kite/business` represent virtual client-side view states rather than physical files or directories on the server's disk. When a client performs a page refresh, accesses a bookmark, or directly navigates to an internal deep route, the web server receives an HTTP request for a path that does not physically exist. Without SPA fallback support, the server responds with an HTTP 404 Not Found error.

To support SPAs seamlessly, Toron's static route engine shall support `spa` and `fallback` configuration options in `routes.yaml` and `config.yaml`. When SPA fallback is enabled on a static route:
- If a requested path does not map to a physical file or directory on disk, and the request does not specify a static file extension (or is an SPA navigation request), Toron shall serve the fallback file (defaulting to `index.html`) with an HTTP 200 OK status.
- If a requested path has a file extension (e.g., `.js`, `.css`, `.png`, `.jpg`, `.svg`, `.json`) and the physical file does not exist on disk, Toron shall return an HTTP 404 Not Found status to prevent masking missing asset errors.

## Acceptance Criteria

1. **Configuration Attributes**:
   - Static routes in `routes.yaml` / `config.yaml` accept an optional boolean field `spa: true | false`.
   - Static routes accept an optional string field `fallback: "<filename>"` specifying the relative fallback file name within the static directory.
   - When `spa: true` is enabled without an explicit `fallback`, the system defaults to serving `index.html`.
   - When `fallback` is configured, `spa` mode is enabled with the designated fallback file.

2. **Client-Side Route Fallback Handling**:
   - For incoming `GET` and `HEAD` requests matching a static route with SPA enabled, if the requested path does not exist as a physical file or directory on disk, and the request path does not contain a file extension, the server shall serve the fallback file (e.g., `index.html`) with an HTTP 200 OK response and `Content-Type: text/html; charset=utf-8`.
   - SPA navigation requests under nested route prefixes (e.g., prefix `/kite` with request `/kite/devops/settings`) correctly serve the route's configured fallback file (e.g., `/kite/index.html`).

3. **Asset Protection (Non-Masking of Missing Physical Assets)**:
   - If a requested path contains a file extension (e.g., `/app/bundle.js`, `/app/styles.css`, `/app/logo.png`, `/app/data.json`) and the target file does not exist on disk, the server shall return HTTP 404 Not Found.
   - Missing static asset requests must never be served the fallback HTML document, preventing browser script/style execution failures and MIME-type syntax errors (`text/html` treated as script/stylesheet).

4. **Security & Sandboxing**:
   - The fallback file must be strictly verified against path traversal and symlink escape attacks, ensuring it remains contained within the static route's directory root.
   - Non-existent fallback files or fallback paths that fail traversal checks shall yield HTTP 403 Forbidden or HTTP 404 Not Found as appropriate.

5. **Backward Compatibility**:
   - Static routes that do not specify `spa: true` or `fallback` preserve existing behavior without modification, returning HTTP 404 Not Found whenever a requested file or directory does not exist on disk.
   - Directory requests with existing `index.html` files continue to serve the directory index as before.

## Rationale

Modern Single Page Applications (SPAs) are standard across enterprise and consumer web applications. Hosting front-end applications directly on Toron without requiring an intermediate Nginx or Caddy instance reduces operational complexity and improves latency. At the same time, differentiating between navigation routes and missing static assets is vital: returning an HTML fallback for a missing `.js` or `.css` bundle causes front-end applications to fail cryptically due to MIME-type mismatches, while degrading cache and diagnostic observability.

## Constraints

- Only HTTP `GET` and `HEAD` methods are eligible for static file and fallback serving; other HTTP methods shall receive HTTP 405 Method Not Allowed.
- The fallback file resolution must operate with minimal I/O overhead, executing only when initial file/directory discovery fails.
- The fallback file must be located within the configured static root directory.

## Open Questions

- Should requests with file extensions be evaluated against an explicit allowlist of known static extensions, or should any non-empty extension suffix (`filepath.Ext(path) != ""`) be treated as an asset?
- Should client `Accept` headers (e.g., `Accept: text/html`) be used to disambiguate edge cases where an SPA route might contain a dot in the path?
