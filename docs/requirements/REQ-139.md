# REQ-139 - Distinct Upstream Route Pool Rendering, Hierarchical Telemetry Aggregation, and Live Metric Derivation in Control Center Dashboard

## 1. Description & Problem Statement

### 1.1 Context & Background
The Toron Edge Gateway Control Center dashboard ([`public/app.js`](../../public/app.js)) provides high-density operational observability across reverse proxy routes, traffic topology, security incidents, and upstream backend health.

Under [`REQ-135`](REQ-135.md), Toron introduced an interactive control center featuring SVG traffic flow diagrams, live request tailing, and upstream pool health cards. Under [`REQ-137`](REQ-137.md) and [`REQ-138`](REQ-138.md), telemetry timestamp fidelity, source IP visibility, and deterministic multi-level sorting were added.

### 1.2 Identified Defects & Root Cause Analysis
During live operational audits of the Toron Control Center at `https://sayantansaha.in/internal/dashboard/#/upstreams`, several critical defects were identified in the data adapter and rendering logic of [`public/app.js`](../../public/app.js):

1. **Upstream Route Collapse Anti-Pattern**:
   - Multiple upstream routes defined in configuration (e.g., `/kite/callback`, `/kite/api`, `/kite/broker`, `/kite/auth`) route to the same backend target address (`http://127.0.0.1:8080`).
   - In [`public/app.js`](../../public/app.js), the function `buildDataModel()` groups upstream nodes into pools by filtering routes matching target addresses (`r.pool.includes(targetAddr)` or `r.targets.some(...)`).
   - Because all four routes target `127.0.0.1:8080`, the filter returns all of them for every health probe entry. The logic then assigns `primaryRoute = matchingRoutes[0]` (the first declared route, `/kite/callback`) and keys the pool by `primaryRoute.id` (`_kite_callback`).
   - Subsequent upstream routes (`/kite/api`, `/kite/broker`, `/kite/auth`) are absorbed into the `/kite/callback` pool, and the secondary registration loop skips them because `targetAddr` is already recorded in `pool.insts`.
   - As a result, `/kite/api`, `/kite/broker`, and `/kite/auth` are completely absent from the Upstreams view (`#/upstreams`). Operators cannot view health check strips, probe latencies, or status codes for these distinct ingress routes.

2. **Telemetry Field Mismatch & Static Metric Fallbacks**:
   - In [`public/app.js`](../../public/app.js), route and pool metric computations attempt to read non-existent property names from `rawApiStatus.metrics`:
     - `m.by_route` (non-existent; actual field in [`pkg/metrics/metrics.go`](../../pkg/metrics/metrics.go) is `requests_by_route`)
     - `m.rate_per_sec` (non-existent; actual rate is in `rawApiStatus.timeseries.A.rps`)
     - `m.latency_p95_ms` (non-existent; actual latency is in `rawApiStatus.timeseries.A.p95` and `/internal/api/upstreams/health` `latency_ms`)
     - `m.err_rate` (non-existent; actual error rate is in `rawApiStatus.timeseries.A.err` and `/internal/api/upstreams/health` `http_code` / `status`)
   - Because these property lookups evaluate to `undefined`, all route and pool computations silently fall back to hardcoded static initial values:
     - **Requests**: `0.0/s`
     - **p95 Latency**: `2.5 ms`
     - **5xx Error Rate**: `0.0%`
   - Every upstream pool card in `#/upstreams` and every route row in `#/routes` displays identical, static metrics (`0.0/s`, `2.5 ms`, `0.0%`), masking live traffic load, backend latency degradation, and circuit-breaker events.

3. **Subpath Fragmentation in Telemetry**:
   - In [`pkg/router/router.go`](../../pkg/router/router.go), requests are recorded in `requests_by_route` keyed by the full incoming request path (e.g. `/kite/api/v1/business`, `/kite/api/v1/trades`, `/kite/api/v1/auth`).
   - Looking up only the exact configured prefix `requests_by_route[r.prefix]` returns `0` or `1` request, completely ignoring thousands of legitimate requests distributed across subpaths.
   - Route and pool calculations require **hierarchical prefix aggregation**: summing all keys `k` in `requests_by_route` where `k === prefix || k.startsWith(prefix + '/')`.

4. **Internal Polling Dilution of External Throughput**:
   - Over 91% (48,000+ of 53,000+) of recorded requests are internal dashboard polling requests targeting `/internal/api/*` (`/internal/api/status`, `/internal/api/upstreams/health`, etc.).
   - Computing a user route's throughput share as `route_requests / total_requests` dilutes the ratio by more than an order of magnitude against internal polling volume, rounding external route live RPS down to `0.0/s`.
   - Internal management requests (`/internal/api/*` or `/internal/*`) must be excluded from the denominator when calculating user route traffic ratios.

5. **Instantaneous RPS Oscillation**:
   - Dashboard polling executes every 2 seconds, causing instantaneous `tsA.rps` points to alternate between `0` and `6` due to bursty polling intervals.
   - A smoothed moving average of recent samples (e.g. `avg(tsA.rps.slice(-5))`) is required to present a stable, representative real-time rate.

6. **Lack of Cumulative Request Volume Visibility**:
   - When an upstream service is legitimately idle (0.0/s live traffic), operators cannot distinguish between an idle healthy backend, an unrouted service, or missing telemetry data.
   - Displaying the cumulative request volume alongside live RPS in upstream cards (e.g. `0.0/s (1.7k total)`) provides essential operational context and verification.

## 2. Functional Requirements

### 2.1 Distinct Upstream Route Pool Disaggregation
- **FR-1**: The dashboard data model in [`public/app.js`](../../public/app.js) MUST maintain distinct pool entries for each configured upstream proxy route (e.g., `/kite/callback`, `/kite/api`, `/kite/broker`, `/kite/auth`), even when multiple routes share an identical backend target URL or IP:port (such as `http://127.0.0.1:8080`).
- **FR-2**: In `buildDataModel()`, matching of health check probe entries (`rawApiUpstreams`) to routes MUST prioritize the specific route label (`u.route`) over generic target address matching:
  - If `u.route` matches `r.path`, `r.short`, or `r.host + r.path`, `u` MUST be assigned to that specific route's pool.
  - Target address matching (`targetAddr` / `u.name`) MUST only serve as a secondary fallback when `u.route` is empty or unassigned.
- **FR-3**: Pool keys (`poolKey`) MUST be unique per route or unique per `(route_id, target_address)` tuple, preventing collisions and preventing one route from swallowing other routes targeting the same backend server.
- **FR-4**: The fallback route registration loop MUST ensure that all configured upstream routes (`type !== 'static'` and possessing targets) that are not yet registered in `poolMap` are instantiated as independent pool cards.

### 2.2 Hierarchical Prefix Aggregation & Internal Polling Exclusion
- **FR-5**: [`public/app.js`](../../public/app.js) MUST replace all references to `rawApiStatus.metrics.by_route` with `rawApiStatus.metrics.requests_by_route`.
- **FR-6 (Hierarchical Subpath Prefix Aggregation)**:
  - Because [`pkg/router/router.go`](../../pkg/router/router.go) records requests keyed by full request path, the dashboard data model MUST aggregate request counts hierarchically for each route prefix:
    $$\text{aggregated\_requests}(r.\text{prefix}) = \sum_{\{k \in \text{keys}(\text{requests\_by\_route}) \mid k = r.\text{prefix} \lor k.\text{startsWith}(r.\text{prefix} + '/')\}} \text{requests\_by\_route}[k]$$
  - All subpath calls (e.g., `/kite/api/v1/business`, `/kite/api/v1/trades`, `/kite/api/v1/auth`) MUST be rolled up into their parent route prefix (`/kite/api`).
- **FR-7 (Internal Polling Filter & Denominator Normalization)**:
  - When calculating route traffic throughput ratios, all internal endpoints (`k.startsWith('/internal/')`) MUST be excluded from the external requests denominator:
    $$\text{total\_external\_requests} = \sum_{\{k \in \text{keys}(\text{requests\_by\_route}) \mid \neg k.\text{startsWith}('/internal/')\}} \text{requests\_by\_route}[k]$$
  - If $\text{total\_external\_requests} = 0$, external route throughput ratios MUST default cleanly to `0.0`.
- **FR-8 (Smoothed Moving Average RPS)**:
  - To eliminate 2-second polling oscillation (e.g. alternating between 0 and 6 req/s), the gateway throughput base MUST be calculated as a moving average of recent rolling samples from `rawApiStatus.timeseries.A.rps`:
    $$\text{smoothed\_rps} = \text{avg}(\text{tsA.rps.slice}(-5))$$
  - If fewer than 5 points are available, average all available points in `tsA.rps`.
  - For each route `r`, the instantaneous throughput MUST be computed as:
    $$\text{curRPS} = \text{smoothed\_rps} \times \left(\frac{\text{aggregated\_requests}(r.\text{prefix})}{\max(1, \text{total\_external\_requests})}\right)$$

### 2.3 Upstream Pool Requests Metric & Cumulative Volume Visibility
- **FR-9 (Live RPS & Cumulative Volume Display)**:
  - Upstream pool cards in `poolCard(p)` MUST compute live throughput as $\text{p.rps} = \sum_{r \in p.\text{routes}} r.\text{cur.rps}$.
  - Upstream pool cards MUST also calculate total cumulative requests processed as $\text{p.totalReqs} = \sum_{r \in p.\text{routes}} r.\text{totalReqs}$.
  - The Requests metric header on the upstream card MUST display both the real-time rate and formatted cumulative volume:
    $$\text{"\$\{fmt.n(p.rps)\}/s (\$\{fmt.n(p.totalReqs)\} total)"}$$
  - When live traffic is idle (`0.0/s`), the cumulative request count (e.g. `0.0/s (1.7k total)`) immediately confirms whether the backend is functioning and has historically served requests.

### 2.4 Live Health Probe Latency & Percentile Derivation
- **FR-10**: In each upstream instance row (`i`) within `poolCard(p)`, latency MUST be bound directly to `i.latency` (derived from `/internal/api/upstreams/health` `u.latency_ms`).
- **FR-11**: The pool card summary p95 Latency (`p.p95`) MUST be dynamically derived:
  - If active instance probe latencies exist (`i.latency > 0`), the pool latency MUST reflect the real probe round-trip latency (e.g., maximum or weighted average across healthy instances).
  - If gateway-wide request percentiles exist in `rawApiStatus.timeseries.A.p95`, route-level request latency MUST incorporate `tsA.p95[tsA.p95.length - 1]`.
  - The hardcoded constant `2.5 ms` MUST NOT be used when live probe or telemetry measurements are available.

### 2.5 Error Rate & Health State Derivation
- **FR-12**: The instance health state (`i.state`) MUST accurately reflect probe results:
  - `i.state = 'down'` when `u.status === 'UNREACHABLE'`, `u.http_code >= 500`, or `u.status` indicates circuit breaker open.
  - `i.state = 'up'` when `u.status === 'HEALTHY'`, `u.status === 'UP'`, or `u.http_code < 400`.
- **FR-13**: The pool card summary 5xx Error Rate (`p.err5`) MUST be dynamically derived from:
  - The ratio of failed probes in `i.history` (e.g. failing tick percentage), and/or
  - Live 5xx error rate from `rawApiStatus.timeseries.A.err` (`tsA.err[tsA.err.length - 1]`), and/or
  - The ratio of 5xx status codes from `rawApiStatus.metrics.requests_by_status` ($\sum 5xx / \text{total\_requests}$).
- **FR-14**: If any upstream instance in a pool is down or failing probes, the pool card tone MUST escalate to `warn` or `err`, and the error percentage MUST display the actual failure rate rather than static `0.0%`.

### 2.6 Overview Traffic Flow (Sankey) & Routes View Parity
- **FR-15**: The SVG Traffic Flow Sankey diagram in `#/overview` (`flow()`) MUST render distinct links and nodes for each upstream pool, ensuring routes like `/kite/api`, `/kite/broker`, and `/kite/auth` are visually distinct and correctly connected to their upstream destinations.
- **FR-16**: The Routes table in `#/routes` (`rtUpdate()`) MUST display the corrected, dynamically derived `curRPS`, `p95`, and `err5` for every individual route.

## 3. Non-Functional Requirements

- **NFR-1 (Zero External Dependencies)**: All data transformations, route aggregation, and metric derivations MUST execute in native vanilla JavaScript within [`public/app.js`](../../public/app.js) with zero external libraries.
- **NFR-2 (Execution Performance)**: Data model construction in `buildDataModel()` MUST complete in under 2 milliseconds ($\mathcal{O}(R + U)$ where $R$ is routes count and $U$ is upstreams count), maintaining smooth 60fps rendering during 1-second dashboard polling.
- **NFR-3 (Defensive Resilience & Fallback Safety)**: When the gateway is starting up, backends are idle, or metrics arrays are empty, the dashboard MUST handle zero values gracefully without raising `TypeError`, `NaN`, or breaking UI execution.
- **NFR-4 (Strictly Relative Documentation Links)**: In compliance with project standards, all links within requirements, design specifications, and test cases MUST be strictly relative paths without absolute filesystem prefixes or leading slashes.

## 4. Acceptance Criteria

1. **Discrete Pool Card Rendering**:
   - Navigating to `#/upstreams` renders separate, distinct pool cards for `/kite/callback`, `/kite/api`, `/kite/broker`, and `/kite/auth`.
   - No route targeting `http://127.0.0.1:8080` is collapsed, hidden, or omitted.
2. **Correct Route Labeling & Matching**:
   - Each pool card displays its own route prefix, match host, middleware chips, and target address.
3. **Hierarchical Subpath Aggregation**:
   - All subpath requests (e.g., `/kite/api/v1/business`, `/kite/api/v1/trades`, `/kite/api/v1/auth`) are rolled up into the parent route prefix (`/kite/api`).
   - Route request counters reflect total aggregated subpath traffic instead of 0 or 1.
4. **Internal Polling Isolation**:
   - Internal dashboard polling requests (`/internal/api/*`) are excluded from external throughput denominator calculations.
   - External user routes receive their true proportional traffic shares without dilution from internal dashboard API requests.
5. **Moving Average RPS Stability**:
   - Live RPS values in route rows and pool cards utilize a moving average of recent time-series points (`avg(tsA.rps.slice(-5))`), eliminating alternating 0 to 6 RPS oscillations between 2-second polls.
6. **Cumulative Volume Visibility**:
   - Upstream pool cards display both live rate and cumulative historical volume in the Requests metric (e.g. `0.0/s (1.7k total)` or `1.4/s (4.2k total)`).
   - Legitimately idle upstreams clearly show their historical request volume, confirming route activity.
7. **Live Health Probe Latency**:
   - Each instance row displays the actual round-trip latency (`latency_ms`) returned by `/internal/api/upstreams/health`.
   - Pool card headers display realistic latency derived from probe measurements and `timeseries.A.p95`, eliminating the static `2.5 ms` default.
8. **Real-Time Error Rate & Tone Indication**:
   - When an upstream service fails or returns HTTP 502/503/504, the affected pool card reflects the non-zero error rate, sets instance status to Down/Unreachable, and applies `warn`/`err` visual styling.
   - When all probes and requests succeed, error rate accurately reflects `0.0%` based on telemetry rather than hardcoded fallbacks.
9. **Traffic Flow & Routes Consistency**:
   - The Overview Sankey diagram renders distinct flows for each upstream route without conflating them into a single node.
   - The Routes table renders accurate, live sparklines and percentile values for all routes.
10. **Quality & Test Verification**:
    - Frontend console reports zero runtime JavaScript errors or unhandled exceptions.
    - Existing Go unit test suites (`go test ./pkg/...`) continue to pass with 100% success.

## 5. Rationale

In microservice and edge gateway environments, multiple endpoints frequently target the same container, daemon, or loopback port (e.g. `127.0.0.1:8080`) while serving different business functions with distinct SLAs, authentication requirements, and rate limits.

Collapsing multiple routes into the first declared route prevents operators from identifying which endpoint is experiencing latency spikes or probe failures. Furthermore, referencing nonexistent metric fields causes the dashboard to display placeholder values, defeating the purpose of an observability control plane. Resolving subpath fragmentation, isolating internal polling requests, smoothing instantaneous sample oscillation, and displaying cumulative volumes provides operators with complete visibility into individual route health, historical traffic volumes, and probe response times.
