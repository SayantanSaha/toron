# REQ-136 - Native Dynamic 2-Stage WAF Auto-Ban Engine with Persistent Storage & OS-Level IP Banning

## 1. Executive Summary

When Toron operates on public ingress interfaces, automated attack bots and scanners frequently unleash rapid-fire bursts of path traversal, SQL injection, XSS, and exploit payloads. While Toron's WAF successfully detects and blocks these individual malicious requests, continuing to evaluate full regex rules on repeated abusive traffic consumes CPU cycles.

This requirement defines an autonomous, in-process **2-Stage Dynamic Auto-Ban Engine** for Toron's WAF that:
1. **Stage 1 (Temporary Ban)**: Temporarily blocks an IP for `ban_duration` when it reaches `max_violations` within a sliding time `window`.
2. **Stage 2 (Permanent Escalation)**: If an IP accumulates repeated temporary bans $\ge \text{max\_temporary\_bans}$ ($X$ times), the engine automatically escalates the IP to a **Permanent Ban**.
3. **Persistent Storage**: Automatically serializes active and permanent bans to a persistent JSON state file (e.g. `/etc/toron/banned_ips.json` or `persistence_file`) with atomic file writes so ban states and strike histories persist across server restarts.
4. **Management & Observability**: Exposes live ban management to the internal API and observability dashboard with 1-click unban and manual ban capabilities.
5. **Multi-Platform OS-Level IP Banning Integration**: Provides comprehensive documentation and recipes for kernel-level firewall drops (Fail2ban for Linux, `pfctl` for macOS, and PowerShell / Windows Defender Firewall for Windows).

## 2. Functional Requirements

### 2.1 Two-Stage Progressive Auto-Ban Reactor
- **FR-1**: Toron MUST track strike violations per client IP address when an incoming request triggers a WAF violation (anomaly score $\ge$ threshold) or rate limit violation.
- **FR-2 (Stage 1 - Temporary Ban)**: When an IP accumulates $\ge \text{max\_violations}$ within the configured sliding time $\text{window}$ (e.g. 3 violations in 60s), the engine MUST automatically place the IP into a **Temporary Ban** state for `ban_duration` (e.g. 1 hour).
- **FR-3 (Stage 2 - Permanent Ban Escalation)**: The engine MUST maintain a historical temporary ban counter per IP. If an IP is temporarily banned $\ge \text{max\_temporary\_bans}$ times (e.g. 3 times), the engine MUST automatically escalate the IP to a **Permanent Ban** state (never expiring unless manually unbanned by an administrator).
- **FR-4 (Fast-Path Rejection)**: Banned IP addresses (both temporary and permanent) MUST have all subsequent requests rejected immediately in $\mathcal{O}(1)$ time with `HTTP 403 Forbidden` (`{"error":"403 Forbidden","message":"Client IP address has been banned due to repeated security violations","ban_type":"temporary|permanent"}`) before request body streaming, WAF regex inspection, or router dispatching occurs.
- **FR-5 (Allowlist Protection)**: An immutable CIDR allowlist (`whitelist`) MUST be supported to guarantee that loopback (`127.0.0.1`, `::1`), private management subnets, or designated trusted IPs are never auto-banned under any circumstance.

### 2.2 Persistent Storage & State Sync
- **FR-6**: The auto-ban engine MUST persist the ban table and strike history to a local JSON state file (configurable via `persistence_file`, defaulting to `/etc/toron/banned_ips.json` or `./data/banned_ips.json`).
- **FR-7**: On startup, Toron MUST load existing bans and permanent blocks from the persistence file, immediately reinstating all unexpired temporary bans and permanent bans.
- **FR-8**: On ban, unban, escalation, or expiration events, the engine MUST atomically serialize the state to disk using a temporary file + atomic rename (`.tmp` $\to$ target) to prevent corruption during power failure or sudden termination.

### 2.3 Configuration Schema (`config.yaml`)
- **FR-9**: The WAF configuration MUST support the 2-stage auto-ban and persistence schema:
  ```yaml
  server:
    waf:
      enabled: true
      mode: enforce
      anomaly_threshold: 5
      auto_ban:
        enabled: true
        max_violations: 3           # Number of blocked requests within window to trigger temp ban
        window: 60s                 # Sliding window for strike tracking
        ban_duration: 1h            # Duration of Stage 1 temporary ban
        max_temporary_bans: 3       # Number of temporary bans before Stage 2 permanent ban
        persistence_file: /etc/toron/banned_ips.json  # File path to persist bans across restarts
        whitelist:
          - "127.0.0.1/32"
          - "::1/128"
  ```

### 2.4 Management APIs & Observability Dashboard
- **FR-10**: `GET /internal/api/security/banned-ips` MUST return all active temporary bans, permanent bans, strike counts, remaining TTLs, ban type (`temporary` or `permanent`), and triggering rule categories.
- **FR-11**: `POST /internal/api/security/unban` MUST allow administrators to immediately unban an IP address on-demand, clearing its active ban and resetting its temporary ban escalation count, updating the persistent storage file.
- **FR-12**: `POST /internal/api/security/ban` MUST allow administrators to manually ban an IP address (with option for temporary or permanent duration).
- **FR-13**: The Observability Dashboard UI (`/internal/dashboard/`) MUST include a dedicated **"Banned IPs & Threat Defense"** control view displaying active bans, ban tier (Stage 1 Temp vs. Stage 2 Perm), and a 1-click **"Unban"** action.

### 2.5 Multi-Platform OS-Level IP Banning Documentation
- **FR-14**: The project documentation MUST provide comprehensive, ready-to-run recipes for kernel-level firewall drops based on Toron's structured JSON security log output:
  - **Linux**: Fail2ban jail + filter configuration interacting with `iptables` / `nftables`.
  - **macOS**: `pfctl` (Packet Filter) automated anchor and table-based dropping.
  - **Windows**: PowerShell automation script interacting with `New-NetFirewallRule` / Windows Defender Firewall.

## 3. Non-Functional Requirements

- **NFR-1 (Performance & Zero Allocation)**: Fast-path IP ban checks MUST execute in under 1 microsecond ($\mathcal{O}(1)$ RWMutex / sync.Map lookup) without heap allocation on the hot request path.
- **NFR-2 (Thread Safety & Concurrency)**: All strike tracking, ban escalations, and disk write queues MUST be strictly thread-safe under concurrent multi-worker gateway operations.
- **NFR-3 (Fail-Secure & Resilient)**: Corrupted or missing persistence files must fail gracefully (logging warning and starting with empty in-memory state without crashing the gateway).
- **NFR-4 (Zero External Dependencies)**: The native 2-stage auto-ban engine MUST run entirely in-process in Go standard library without requiring external databases or CGO.

## 4. Acceptance Criteria

1. An IP making 3 WAF violations within 60s is temporarily banned for `ban_duration` (Stage 1).
2. The 4th request from that IP is rejected in $< 0.05\text{ms}$ with HTTP 403.
3. If the IP is temporarily banned 3 times, it is escalated to a **Permanent Ban** (Stage 2).
4. Restarting the Toron server (`systemctl restart toron`) retains both active temporary bans (with remaining TTL) and permanent bans from the persistence file.
5. Calling `POST /internal/api/security/unban` unbans the IP immediately and removes it from disk.
6. Whitelisted IPs (`127.0.0.1`, `::1`) are never banned under any circumstances.
7. Automated tests with race detector pass (`go test -race ./pkg/waf/...`).
8. Fail2ban jail is configured on `sayantansaha.in` and documentation covers Linux, macOS, and Windows.
