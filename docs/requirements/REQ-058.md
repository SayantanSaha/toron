# REQ-058 - Config-Based Multi-Stream Logging with Route-Level Overrides and System Logrotate Support

## Description

The Toron web server and edge gateway shall provide comprehensive, configuration-driven multi-stream logging across three distinct operational categories:
1. **Server Logs**: Operational, lifecycle, startup/shutdown, listener status, worker pool notifications, background watcher events, and internal runtime errors or panics.
2. **Access Logs**: HTTP request and response execution logs, recording client IP, timestamp, HTTP method, request path, protocol version, HTTP status code, response duration, bytes sent, User-Agent, and tracing identifiers.
3. **Security Logs**: Security-relevant events, including Web Application Firewall (WAF) blocks and anomaly score trips, authentication failures (JWT, API key, Basic auth), rate limit rejections, CIDR IP ACL blocks, and HTTP protocol integrity violations.

Default log destinations for each stream shall be declaratively configured in `config.yaml`. To accommodate multi-tenant, microservice, and compliance-sensitive deployments, Toron shall support overriding access and security log file paths on a per-route basis in `routes.yaml`.

Furthermore, all log files must be fully compatible with daily system log rotators (such as Linux `logrotate` or macOS `newsyslog`) without dropping connections or corrupting log records. This includes opening files in append mode (`O_APPEND`) to support `copytruncate`, and handling operating system reload signals (`SIGHUP`) to seamlessly close and reopen file descriptors after external rotation.

## Acceptance Criteria

### 1. Global Logging Configuration (`config.yaml`)
- The `logging` configuration block in `config.yaml` shall support the following parameters:
  - `level` (string): Minimum log severity level (`"debug"`, `"info"`, `"warn"`, `"error"`, defaulting to `"info"`).
  - `format` (string): Output serialization format (`"text"` or `"json"`, defaulting to `"text"`).
  - `server_log` (string): File path for server lifecycle and operational logs (e.g. `"logs/server.log"`, `"stdout"`, or `"stderr"`).
  - `access_log` (string): Default file path for HTTP access logs (e.g. `"logs/access.log"`, `"stdout"`, or `"off"`).
  - `security_log` (string): Default file path for security incidents and WAF audit events (e.g. `"logs/security.log"`, `"stdout"`, or `"off"`).
- When a path is empty or omitted, it falls back to standard output (`stdout`) or standard Go logger behavior.
- Nested parent directories for configured log paths shall be created automatically if they do not exist.

### 2. Per-Route Logging Overrides (`routes.yaml`)
- Every route entry in `routes.yaml` (and embedded routes in `config.yaml`) shall support optional route-level overrides:
  - `access_log` (string): Specifies a custom file path for access logs matching this route (e.g. `"logs/api_access.log"`). Setting this to `"off"` or `"none"` disables access logging for the route. If omitted or empty, the route inherits the global `logging.access_log` setting.
  - `security_log` (string): Specifies a custom file path for security events triggered within this route (e.g. `"logs/api_security.log"`). Setting this to `"off"` or `"none"` disables security logging for the route. If omitted or empty, the route inherits the global `logging.security_log` setting.
- Route-level overrides apply to all route types (`static`, `upstream`, `proxy`).

### 3. System Log Rotator Compatibility (`logrotate`)
- **Append Mode**: All log files must be opened using `os.O_CREATE|os.O_WRONLY|os.O_APPEND` with secure permissions (`0640` or `0644`). This ensures compatibility with rotators using the `copytruncate` strategy without race conditions or pointer resets.
- **Signal-Based Reopen (`SIGHUP`)**: Toron must listen for `SIGHUP` signals. Upon receipt of `SIGHUP`, Toron shall atomically flush, close, and re-open all active log file descriptors across global and per-route sinks without disrupting active network listeners or client connections.
- **Logrotate Configuration Template**: Toron shall provide a production-ready `logrotate` configuration file (`etc/logrotate.d/toron`) configured for daily rotation, keeping 7 archives, compressing rotated logs, and issuing a `kill -HUP` postrotate command.

### 4. Concurrency & Performance
- All log writes must be thread-safe across concurrent goroutines and reactor workers.
- Log writing operations should be buffered or optimized to minimize I/O latency on high-throughput request paths.

## Rationale

Decoupling server, access, and security logs into dedicated, configurable streams enables operators to pipe high-volume request logs to analytics engines, forward security audit events to SIEM platforms (e.g. Splunk, Datadog), and keep server diagnostics separate. Allowing per-route overrides enables isolation for compliance (e.g., PCI-DSS cardholder data routes logging to isolated audit files). Native logrotate compatibility avoids introducing bulky third-party rotation dependencies while fitting standard Linux operational practices.

## Constraints

- Toron's zero external runtime dependency principle must be maintained (use standard Go library `os`, `sync`, `fmt`, `time`, `syscall`).
- SIGHUP processing must not interrupt socket listeners or abort in-flight HTTP connections.
- Corrupted or unparseable log file paths must be validated at startup and during dry-run configuration checks (`-test-config`).

## Open Questions

None. The requirements align with standard UNIX server logging practices and Toron's existing architecture.
