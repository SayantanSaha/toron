# ADR-142 - Unified Management API Security & Client Authentication Lifecycle

## 1. Context & Problem Statement

As established in [`AN-001`](../analysis/AN-001.md) and required by [`REQ-142`](../requirements/REQ-142.md), the Toron Edge Gateway Control Center dashboard and management endpoints (`/internal/api/*`) require robust, defense-in-depth access controls.

Currently:
1. Without configuration, `/internal/api/*` is accessible to unauthenticated callers.
2. When administrative authentication is enabled on the server, the client dashboard in `public/js/` has no mechanism to supply credentials or intercept HTTP 401 Unauthorized responses, rendering the dashboard inoperable.
3. Administrative operations (firewall IP ban/unban mutations and diagnostic endpoint proxy-tests) must be protected against unauthorized execution and SSRF abuse.

---

## 2. Decision & Architecture Design

Adopt a **Unified Defense-in-Depth Authentication Protocol** encompassing backend credential verification, client 401 response interception, volatile session credential persistence, and UI challenge workflows.

### 2.3 Key Technical Invariants

1. **Multi-Scheme Compatibility**:
   - `X-Toron-Admin-Key`: Designed for programmatic agents and straightforward browser client headers.
   - `Authorization: Bearer <token>`: Standard RFC 6750 bearer token format.
   - `Authorization: Basic <base64>`: Standard RFC 7617 username:password format, enabling seamless native browser auth dialogs.
2. **Timing Attack Protection**:
   - All credential comparisons in Go execute via `subtle.ConstantTimeCompare` to eliminate timing side-channels during key or password evaluation.
3. **Session Credential Hygiene**:
   - In accordance with CWE-312 and OWASP recommendations, tokens MUST NOT be persisted to `localStorage` (which survives tab closures and is vulnerable to persistent client-side data leaks).
   - Tokens reside exclusively in memory and `sessionStorage` (cleared automatically when the browser tab or window is terminated).
4. **Graceful Demo Fallback**:
   - If an unauthenticated operator wishes to inspect the dashboard shell without modifying server data, an optional "Demo Mode" fallback button is provided in the modal dialog, rendering static demonstration telemetry without polling.
5. **Zero External Dependencies**:
   - No external authentication libraries, JWT decoders, or modal frameworks are added. The implementation relies entirely on native browser APIs (`crypto.subtle`, `fetch()`, `sessionStorage`, DOM) and standard Go libraries (`crypto/subtle`, `net`).

## 3. Alternatives Considered

### Option 1: HTTP Basic Auth Only
- *Pros*: Native browser prompt; zero modal code needed in frontend.
- *Cons*: Cannot be logged out without browser restart or tricky dummy credentials; awkward for API token workflows.
- *Verdict*: **Rejected as exclusive mechanism**, but retained as a supported scheme within the hybrid protocol.

### Option 2: Full OpenID Connect (OIDC) / OAuth2 SSO
- *Pros*: Centralized corporate identity integration (Okta, Keycloak, Google).
- *Cons*: Requires external identity providers, redirect endpoints, complex token exchange pipelines, and large runtime dependencies. Disproportionate for an autonomous edge appliance (~15 MB).
- *Verdict*: **Rejected**.

### Option 3: Defense-in-Depth Hybrid (Chosen)
- *Pros*: Supports both interactive browser operators (modal + session storage) and automated tools/proxies (`X-Toron-Admin-Key`, Bearer, Basic, and Subnet CIDRs).
- *Verdict*: **Accepted**.

---

## 4. Consequences & Trade-offs

- **Positive**:
  - The Control Center dashboard and management endpoints are fully protected out-of-the-box when administrative security is configured.
  - Fixes the issue where enabling server authentication broke the client dashboard.
  - Zero added runtime weight; adheres strictly to the 100 KB JavaScript budget.
- **Trade-off**:
  - Automated tests that interact with `/internal/api/*` must pass mock authentication credentials when testing secured configurations.
