# ADR-147 - Alerts Control Center Dual-Card Separation, Multi-Action Status Badging, and Rate-Limiting Telemetry

## Context

The Toron Control Center dashboard at `#/alerts` serves as the centralized operations console for real-time edge security monitoring, automated threat defense, and operational infrastructure health awareness. Following the implementation of the Alerts Control Center redesign ([ADR-146](./ADR-146.md) / [REQ-146](../requirements/REQ-146.md)), site reliability engineers and security operators reported a critical visibility defect in production environments:
> *"The current alert dashboard is showing no events other than blocked."*

Root-cause analysis in [AN-008](../analysis/AN-008.md) and requirement specification in [REQ-147](../requirements/REQ-147.md) uncovered five interconnected architectural causes:

1. **Frontend Mutual Exclusion Fallback (`public/js/views/alerts.js`)**:
   The view controller resolved active feed records via a mutual exclusion ternary conditional:
   ```javascript
   const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);
   ```
   Because public-facing edge gateways continuously receive automated internet scanner requests (e.g. vulnerability probes against `/wp-login.php`, `/.env`, `/actuator/health`), the WAF intercepts these probes and retains them in the 50-event circular audit buffer (`AuditLogger`). As a result, `model.incidents` is practically never empty. Consequently, `model.alerts` was relegated to a dead fallback branch and permanently suppressed from screen. Critical operational health degradations (unhealthy upstream pool backends, route 5xx error spikes exceeding 2%, and failing ACME SSL certificate renewals) never appeared on the Alerts page, even while triggering the left navigation badge (`1`), the Overview status banner, and the top KPI strip.

2. **Binary Action Badging Oversimplification**:
   Both `alerts.js` and the slide-out forensic drawer (`public/js/components/drawer.js`) evaluated defensive mitigation using binary logic (`isBlocked ? 'Blocked' : 'Logged'`). Automated IP quarantine events (`Action: "banned"`) emitted by the two-stage auto-ban subsystem were forced into the `Logged` label, misrepresenting active firewall bans as passive audit logs.

3. **WAF Scoring Saturation in Enforce Mode**:
   Under default gateway settings (`Mode == "enforce"`, `AnomalyThreshold == 5`), all built-in OWASP rules carry `Score: 5`. Any rule match immediately meets the threshold and triggers a block (`Action: "blocked"`). Zero detection-only anomalies (`Action: "logged"`) occur under default configuration.

4. **Rate-Limiting Telemetry Void**:
   Volumetric traffic throttling rejections (HTTP 429 Too Many Requests) served by route-level token bucket rate limiters (`pkg/router/rate_limiter.go`) did not emit audit telemetry to `*waf.AuditLogger`. Defensive mitigations against volumetric traffic spikes remained completely absent from security telemetry.

5. **Warning Filter Emptiness**:
   Because operational alerts were suppressed by the ternary conditional, rate-limiting emitted no audit telemetry, and WAF rules triggered blocks, clicking the "Warning" severity facet chip yielded an empty state message (*"Zero security incidents match active filters"*), falsely signaling that warning-level telemetry and anomaly monitoring were non-functional.

This Architecture Decision Record establishes the architectural blueprint, DOM structure, component contracts, data flow, telemetry wiring, and client footprint budget strategies to eliminate event homogeneity and alert suppression.

---

## Decision

We adopt a **Full-Stack Telemetry & Dual-Card Separation Architecture** decomposed across five cohesive decisions:

1. **Dual-Card UI Architecture**: Decouple operational system health degradations from WAF security incidents into two distinct visual cards: a dedicated **Operational System Alerts** card (`#alOpsCard`, `#alOpsList` / `#alOpList`) positioned immediately above the **Security Incidents & Threat Defense Feed** card (`#alActive`, `#alIncList`).
2. **Multi-Action Status Badging Contract**: Establish an explicit four-state defense badging taxonomy (`Blocked`, `Banned`, `Throttled`, `Logged`) uniformly rendered across feeds and the forensic investigation drawer (`#drawer`).
3. **Real-Time Severity Facet Filtering Realignment**: Partition multi-action security events deterministically between `Critical` and `Warning` tiers to prevent empty filter states.
4. **Backend Rate-Limiting Telemetry Wiring**: Wire route-level token bucket rate limiting (`pkg/router/rate_limiter.go`) into the security audit logging subsystem (`*waf.AuditLogger`) to dispatch structured `SecurityEvent` payloads on HTTP 429 drops.
5. **Client JS Budget Invariant Enforcement Strategy**: Implement concise lookup patterns and eliminate redundant templates to strictly guarantee that total client JavaScript across `public/js/` remains $\le 120.0\text{ KB}$ ($122,880\text{ bytes}$).

#### 1.1 Structural Layout & DOM Hierarchy in `public/js/views/alerts.js`
In `alShell()`, the single mixed card is split into two distinct `<section class="card">` elements:


> [!NOTE]
> **DOM Element ID Compatibility**: The primary list container ID is `#alOpsList`. To guarantee seamless backward compatibility across test suites, DOM query selectors in `alUpdate()` shall support `#alOpsList` and `#alOpList` interchangeably (`$('#alOpsList') || $('#alOpList')`).

#### 1.2 Elimination of Mutual Exclusion Fallback
In `alUpdate(D)`, the fallback ternary `const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);` is permanently eliminated.
The data binding is strictly partitioned:
- `#alOpsList` unconditionally renders `model.alerts || []`.
- `#alIncList` unconditionally renders `filteredIncidents` derived from `model.incidents || []`.

#### 1.3 Operational Alert Row Item Contract
For each active operational alert in `model.alerts`:
- **Severity Indicator**:
  - `sev === 'critical'`: `<span class="t-err">${ICON('i-x')}</span>`
  - `sev === 'warning'`: `<span class="t-warn">${ICON('i-alert')}</span>`
- **Title**: Rendered as bold typography (e.g. `Upstream Degradation: api-pool`, `High 5xx Error Rate: /v1/auth`, `Certificate Renewal Failed: toron.io`).
- **Detail Description**: Informative text detailing backend health or threshold breaches (e.g. `2/3 instances unreachable`, `5xx rate 4.2% > 2.0% SLO threshold`).
- **Calendar Timestamp**: Full calendar formatting via `dtFmt(alert.timestamp)` adhering to [REQ-137](../requirements/REQ-137.md).
- **Actionable Navigation Target**: Clickable row or button with `data-go="${esc(alert.go || 'overview')}"` (e.g. `data-go="upstreams"`, `data-go="routes"`, `data-go="certs"`), utilizing native SPA hash routing in `public/js/app.js`.

#### 1.4 Zero-State Operational Health Banner
When `(model.alerts || []).length === 0`:
The Operational System Alerts card renders a compact, positive operational health indicator:
```html
<li class="empty" style="text-align:center;padding:16px 12px;color:var(--ink-2);display:flex;align-items:center;justify-content:center;gap:8px">
  <span class="t-ok">${ICON('i-check')}</span>
  <span>All upstream services, routes, and certificates operating normally.</span>
</li>
```

#### 1.5 Feed Independence Guarantee
1. Populated security incidents shall **never** hide, suppress, or modify the Operational System Alerts card.
2. Typing into `#alIncSearch`, toggling `#alSevChips`, or paginating `#alIncList` shall **never** affect the rendering or visibility of operational alerts in `#alOpsList`.

### 2. Multi-Action Status Badging Contract

#### 2.1 Defense Action Taxonomy Mapping
The application discontinues binary `Blocked` vs `Logged` badging. Defense actions map deterministically across status badges, visual tones, and SVG icons:

| Action Identifier (`inc.action`) | Badge Label | CSS Badge Class | Tone Class / Tone String | SVG Icon | Trigger Source & Semantics |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`blocked`** | `Blocked` | `st s5` | `t-err` / `'err'` | `i-x` | Request dropped/terminated by WAF rule match, IP ACL blacklist, or protocol check (`pkg/waf/middleware.go`). |
| **`banned`** | `Banned` | `st s5` | `t-err` / `'err'` | `i-x` | Offending client IP quarantined in firewall by `AutoBanManager` (`pkg/waf/auto_ban.go`). |
| **`throttled`** | `Throttled` | `st s4` | `t-warn` / `'warn'` | `i-alert` | Request rejected with HTTP 429 Too Many Requests by route token bucket rate limiter (`pkg/router/rate_limiter.go`). |
| **`logged`** | `Logged` | `st s4` | `t-warn` / `'warn'` | `i-alert` | Request inspected and permitted, recorded for auditing (detection-only mode or sub-threshold anomaly). |

#### 2.2 Forensic Drawer Contract (`public/js/components/drawer.js`)
When an operator clicks an incident row, `openDrawer('incident', id)` updates the slide-out inspector:
1. **Subtitle Pill (`#dwSub`)**: Renders `${pill(actionTone, actionLabel)}` where `actionTone` is `'err'` for `Blocked` and `Banned`, and `'warn'` for `Throttled` and `Logged`.
2. **Key Metrics Grid (`#dwStats`)**: Action metric item displays `esc(actionLabel)`.
3. **Forensic KV Table (`dl.kv`)**: "Action Taken" renders `<span class="st ${actionClass}">${esc(actionLabel)}</span>`.
4. **Header Category Fallback**: If `inc.category` is empty, defaults to `Rate Limit Ingress` (when `action === 'throttled'`) or `WAF Security Incident`.
5. **Quick Action "Ban Client IP"**: When initiated from a throttled incident, pre-fills reason with `Rate Limit Throttling: ${inc.path}`.

### 3. Real-Time Severity Facet Filtering Realignment

#### 3.1 Predicate Logic & Boundary Partitioning
In `alUpdate()` within `public/js/views/alerts.js`, the incident filtering pipeline partitions records across three severity facets:

```javascript
const filteredIncidents = (model.incidents || []).filter(inc => {
  if (state.alSev === 'critical') {
    const isCrit = inc.action === 'blocked' ||
                   inc.action === 'banned' ||
                   (inc.anomaly_score != null && Number(inc.anomaly_score) >= 10) ||
                   inc.sev === 'critical';
    if (!isCrit) return false;
  } else if (state.alSev === 'warning') {
    const isWarn = inc.action === 'throttled' ||
                   inc.action === 'logged' ||
                   (inc.action !== 'blocked' && inc.action !== 'banned') ||
                   (inc.anomaly_score != null && Number(inc.anomaly_score) < 10) ||
                   inc.sev === 'warning';
    if (!isWarn) return false;
  }

  if (state.alIncQ) {
    const q = state.alIncQ.toLowerCase();
    const cat = (inc.category || inc.title || '').toLowerCase();
    let aliases = '';
    if (cat.includes('sql') || inc.rule_id === '942100') aliases += ' sqli';
    if (cat.includes('cross-site') || inc.rule_id === '941100') aliases += ' xss';
    if (cat.includes('traversal') || inc.rule_id === '930100') aliases += ' traversal lfi';
    if (cat.includes('rate') || inc.rule_id === 'rate_limit') aliases += ' 429 throttle';
    const targetStr = `${inc.client_ip || inc.ip || ''} ${inc.rule_id || ''} ${inc.path || ''} ${cat} ${inc.payload_snippet || ''} ${aliases}`.toLowerCase();
    if (!targetStr.includes(q)) return false;
  }
  return true;
});
```

#### 3.2 State Synchronization & Empty State Fidelity
- **Pagination Reset**: Clicking any `.al-sev-chip` button sets `state.alSev`, resets `state.alIncPage = 1`, and triggers `alUpdate(model)`.
- **Summary & Indicator**: Pagination controls display `Showing 1–N of N` corresponding strictly to the filtered subset.
- **Empty State**: When zero incidents match active filters, `#alIncList` renders:
  ```html
  <li class="empty" style="text-align:center;padding:24px 12px;color:var(--ink-2)">
    ${ICON('i-check')}<span style="margin-left:6px">Zero security incidents match active filters.</span>
  </li>
  ```

### 4. Backend Rate-Limiting Telemetry Wiring

#### 4.1 Interface Contract Coupling (`pkg/router/rate_limiter.go`)
Extend `RateLimiterOptions` to accept an optional security audit logger pointer:

```go
type RateLimiterOptions struct {
    MaxBuckets     int
    IdleTTL        time.Duration
    TrustedProxies []string
    AuditLogger    *waf.AuditLogger
}
```

On `RateLimiter`:
- Retain `auditLogger *waf.AuditLogger` as a private field.
- In `NewRateLimiter(ratePerSec float64, burst int, opts ...RateLimiterOptions)`:
  If `len(opts) > 0`, assign `rl.auditLogger = opts[0].AuditLogger`.
- In `NewRateLimitMiddleware(rateLimitStr string, opts ...RateLimiterOptions)`:
  Forward `opts...` to `NewRateLimiter`.

#### 4.2 SecurityEvent Construction & Dispatch on HTTP 429
When a client token bucket is exhausted (`!allowed`):
```go
if !allowed {
    retrySecs := int(math.Ceil(retryAfter.Seconds()))
    if retrySecs < 1 {
        retrySecs = 1
    }

    if limiter.auditLogger != nil {
        clientIP := clientKey
        if strings.HasPrefix(clientIP, "ip:") {
            clientIP = strings.TrimPrefix(clientIP, "ip:")
        }
        limiter.auditLogger.LogEvent(waf.SecurityEvent{
            Event:          "rate_limit_drop",
            Action:         "throttled",
            Category:       "rate_limit",
            ClientIP:       clientIP,
            Method:         req.Method,
            Path:           req.Path,
            AnomalyScore:   0,
            RuleID:         "rate_limit",
            PayloadSnippet: fmt.Sprintf("Rate limit exceeded: retry after %d seconds", retrySecs),
        })
    }

    res.SetStatus(http.StatusTooManyRequests)
    res.Header.Set("Content-Type", "application/json")
    res.Header.Set("Retry-After", fmt.Sprintf("%d", retrySecs))
    _, _ = res.WriteString(fmt.Sprintf(`{"error":"429 Too Many Requests","retry_after":%d}`, retrySecs))
    return
}
```

#### 4.3 Router Wiring in `pkg/router/router.go`
1. Extend `Router` struct with:
   ```go
   type Router struct {
       // ... existing fields ...
       auditLogger *waf.AuditLogger
   }

   func (r *Router) SetAuditLogger(al *waf.AuditLogger) {
       r.mu.Lock()
       defer r.mu.Unlock()
       r.auditLogger = al
   }

   func (r *Router) AuditLogger() *waf.AuditLogger {
       r.mu.RLock()
       defer r.mu.RUnlock()
       return r.auditLogger
   }
   ```
2. In `compilePrefixRoute`:
   When building route rate limiter middleware:
   ```go
   if strings.TrimSpace(spec.Opts.RateLimit) != "" {
       rlOpts := RateLimiterOptions{
           TrustedProxies: spec.Opts.TrustedProxies,
           AuditLogger:    r.auditLogger,
       }
       // If route has its own WAF engine or specific audit logger, prioritize route logger
       if routeWafEngine != nil && routeWafEngine.AuditLogger() != nil {
           rlOpts.AuditLogger = routeWafEngine.AuditLogger()
       }
       rlMw, err := NewRateLimitMiddleware(spec.Opts.RateLimit, rlOpts)
       if err != nil {
           if px != nil {
               px.Close()
           }
           return prefixRoute{}, fmt.Errorf("router: invalid rate_limit %q for prefix %q: %w", spec.Opts.RateLimit, spec.Prefix, err)
       }
       handler = rlMw(handler)
   }
   ```
3. In `cmd/toron/main.go`:
   Assign `r.SetAuditLogger(auditLogger)` when global WAF audit logging is initialized.

#### 4.4 Invariants & Performance Guarantees
- **Nil Safety**: If `limiter.auditLogger == nil` or audit logging is disabled (`cfg.Enabled == false`), logging is bypassed with zero panics.
- **Zero-Allocation**: No dynamic heap allocations occur on the bypass path.
- **Bounded Ring Buffer**: `AuditLogger.LogEvent` records into an in-memory ring buffer of maximum 50 events (`maxEvents: 50`), ensuring bounded memory regardless of ingress request volume.
- **REST Visibility**: Throttled events are automatically visible via the existing frozen REST API endpoint `GET /internal/api/security/incidents`.

### 5. Client JS Budget Invariant Enforcement Strategy

#### 5.1 Headroom Analysis & Target Ceiling
Per system analysis [AN-008](../analysis/AN-008.md), uncompressed client JavaScript in `public/js/` measures $119.7\text{ KB}$ ($122,544\text{ bytes}$) against the hard ceiling of $120.0\text{ KB}$ ($122,880\text{ bytes}$), leaving approximately $336\text{ bytes}$ of uncompressed headroom before optimization.

#### 5.2 Architectural Strategy for Headroom Preservation
To maintain a safe buffer of $> 500\text{ bytes}$ (targeting total footprint $< 119.5\text{ KB}$ / $< 122,368\text{ bytes}$), frontend developers shall execute the following compression techniques:

1. **Compact Action Metadata Helper**:
   Avoid redundant `switch` or `if/else` statements. Use an inline ternary mapper in `alerts.js`:
   ```javascript
   const getActionMeta = a => (a === 'blocked' || a === 'banned')
     ? { cls: 's5', tone: 't-err', pTone: 'err', icon: 'i-x', lbl: a === 'banned' ? 'Banned' : 'Blocked' }
     : { cls: 's4', tone: 't-warn', pTone: 'warn', icon: 'i-alert', lbl: a === 'throttled' ? 'Throttled' : 'Logged' };
   ```
2. **Dead Code & Template Pruning**:
   - Delete the legacy fallback expression: `const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);`.
   - Remove duplicate variable declarations and repetitive inline styling in `alerts.js`.
   - Reuse existing utilities (`esc`, `dtFmt`, `ICON`, `pill`) from `public/js/utils.js` and `public/js/components/icons.js`.
3. **Automated Guardrail Verification**:
   The automated test suite (`tests/dashboard_telemetry_test.js`) verifies total file sizes across `public/js/`:
   ```javascript
   assert.ok(totalBytes <= 120 * 1024, `Total JS size (${totalBytes} bytes) must be <= 120 KB budget`);
   ```

## Alternatives

### Alternative 1: Unified Merged Feed with Synthetic Schema
Merge `model.alerts` and `model.incidents` into a single unified array sorted chronologically:
```javascript
const operationalEvents = (model.alerts || []).map(a => ({
  id: a.id,
  timestamp: a.timestamp,
  category: a.title,
  action: 'operational',
  sev: a.sev || 'critical',
  rule_id: 'SYSTEM',
  client_ip: 'system'
}));
const incs = [...operationalEvents, ...(model.incidents || [])];
```
- **Evaluation**: Rejected.
  - Conflates infrastructure health monitoring (e.g. backend pool health checks) with malicious adversary forensics (SQL injection, XSS).
  - Injecting synthetic fields (`rule_id: 'SYSTEM'`, `client_ip: 'system'`) pollutes forensic search filters and creates misleading drawer views.
  - SREs and security engineers have distinct operational workflows: SREs resolve upstream connections, whereas SecOps engineers ban abusive CIDR blocks.

### Alternative 2: Collapsible Accordion for Operational Alerts
Render the Operational System Alerts card as a collapsible accordion that collapses to zero height when healthy.
- **Evaluation**: Rejected.
  - Fails the core UI principle of instant situational awareness.
  - A compact, single-line positive health banner (`✔ All upstream services, routes, and certificates operating normally`) provides reassuring confirmation without consuming vertical screen real estate or hiding state changes behind manual user clicks.

### Alternative 3: Dedicated Rate-Limiting Telemetry REST Endpoint (`/internal/api/security/rate-limits`)
Create a separate REST API and client-side data model collection for rate limit violations.
- **Evaluation**: Rejected.
  - Unnecessarily fragments the threat telemetry stream.
  - Volumetric rate-limiting drops are genuine edge defense events that fit naturally into the existing `SecurityEvent` schema (`Action: "throttled"`, `Category: "rate_limit"`).
  - Reusing `/internal/api/security/incidents` maintains zero changes to frozen API contracts and requires zero extra polling requests.

---

## Rationale

1. **Elimination of Alert Suppression**: Decoupling the Operational System Alerts card guarantees that infrastructure emergencies are permanently visible to operators regardless of active WAF incident counts or background scanner traffic.
2. **Defensive Clarity**: Differentiating `Blocked`, `Banned`, `Throttled`, and `Logged` actions provides operators with precise situational awareness regarding whether an attack was dropped, firewalled, rate-throttled, or passively monitored.
3. **No Empty Filter Misleading**: Realigning the `Warning` facet to include `throttled`, `logged`, and sub-threshold anomalies ensures that selecting Warning displays meaningful telemetry rather than an empty state.
4. **Zero Performance Overhead**: Routing rate-limiter drops into `AuditLogger` leverages an existing $O(1)$ circular ring buffer without introducing additional locks, background goroutines, or heap allocations.
5. **Architectural Purity**: Preserves Toron's core design tenets—zero third-party dependencies, native ES2022+ modules, zero build step, and an uncompressed client footprint under 120.0 KB.

## Consequences

### Positive
- **Guaranteed Operational Visibility**: Critical infrastructure failures (unhealthy upstream backends, 5xx error spikes, ACME certificate renewal failures) can never be suppressed by incoming WAF blocks.
- **Deterministic Action Badging**: Auto-ban IP quarantines are clearly identified as `Banned`, and route rate-limiting drops are clearly identified as `Throttled`.
- **Actionable Remediation**: Operators can navigate directly from an operational alert row to the resolving dashboard view (`#/upstreams`, `#/routes`, or `#/certs`) via `data-go` click delegation.
- **Functional Severity Filtering**: The `Warning` facet displays genuine rate throttling and detection anomalies rather than an empty list.
- **Non-Breaking API Compatibility**: Reuses existing frozen REST API schemas (`/internal/api/security/incidents`) and data model structures.

### Trade-offs & Mitigations
- **Vertical Viewport Growth**: Adding a dedicated Operational System Alerts card slightly increases vertical height on `#/alerts`.
  - *Mitigation*: When zero operational alerts exist, the card collapses into a compact, single-line positive health banner ($48\text{px}$ height), ensuring minimal vertical consumption.
- **Telemetry Buffer Overwrite under Extreme Volumetric Traffic**: Under extreme volumetric DDoS attacks generating thousands of 429 drops per second, rate limit events could rapidly rotate the 50-event circular buffer.
  - *Mitigation*: The 50-event circular buffer drops oldest events cleanly ($O(1)$ array overwrite), preventing memory exhaustion. For persistent telemetry, events are written to the configured security log sink (`SecurityLog`).

## Constraints & Invariants

1. **Client JS Footprint Budget**: Total combined uncompressed size of all `.js` files in `public/js/` MUST NOT exceed 120.0 KB (122,880 bytes).
2. **Zero External Runtime Dependencies**: Vanilla ECMAScript 2022+ modules and standard CSS3 only. Zero npm dependencies, frameworks, or client-side build bundlers.
3. **Strictly Relative Links**: All documentation and codebase Markdown links MUST strictly use relative links (`../requirements/REQ-147.md`, `../../public/js/views/alerts.js`). Absolute filesystem paths or root URI schemes are strictly prohibited.
4. **Non-Blocking Telemetry Dispatch**: Rate-limiter telemetry dispatch must be non-blocking, $O(1)$ in time complexity, and guarded against nil-pointer dereferences.
5. **Deterministic Collation & Datetime Standards**: Operational alerts and throttled incidents must preserve `YYYY-MM-DD HH:MM:SS` calendar formatting per [REQ-137](../requirements/REQ-137.md) and deterministic secondary tie-breaking per [REQ-138](../requirements/REQ-138.md) / [ADR-138](./ADR-138.md).
6. **Backward Compatibility**: All existing automated verification test cases (`TC-146-01` through `TC-146-10`) must continue to pass without regression.
