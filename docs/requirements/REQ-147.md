# REQ-147 - Alerts Control Center Dual-Card Separation, Multi-Action Status Badging, and Rate-Limiting Telemetry

## 1. Description & Problem Statement

### 1.1 Operational Context & Background
In the Toron Edge Gateway Control Center, the Alerts & Threat Defense view (`#/alerts`, served via `public/js/views/alerts.js`) provides security and site reliability engineers with centralized situational awareness across infrastructure degradations, WAF rule violations, automated firewall bans, and traffic throttling. 

Following the implementation of the Alerts Control Center redesign ([REQ-146](./REQ-146.md)), operators monitoring active edge deployments reported an operational defect:
> *"The current alert dashboard is showing no events other than blocked."*

A root-cause investigation documented in [AN-008](../analysis/AN-008.md) uncovered several structural factors contributing to event homogeneity and alert suppression:
1. **Frontend Mutual Exclusion Fallback**: In `public/js/views/alerts.js`, the incident list selector uses a mutual exclusion ternary conditional:
   ```javascript
   const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);
   ```
   Whenever `model.incidents` contains at least one record (which is standard due to internet background scanners and the 50-event circular audit buffer), `model.alerts` is discarded. As a consequence, critical operational health alerts (unhealthy upstream pool instances, route 5xx error rate spikes exceeding 2%, and failing ACME SSL certificate renewals) are suppressed from the feed, despite triggering the top KPI strip, the left navigation badge (`1`), and the Overview dashboard status banner.
2. **Binary Action Badging Oversimplification**: Both `alerts.js` and the forensic investigation drawer (`public/js/components/drawer.js`) evaluate defensive actions using binary logic:
   ```javascript
   const isBlocked = inc.action === 'blocked';
   // renders either 'Blocked' or 'Logged'
   ```
   Any non-blocked event is forced into the `Logged` label. Crucially, automated IP quarantine events (`Action: "banned"`) emitted by the auto-ban subsystem are mislabeled as `Logged`, obscuring active firewall quarantines.
3. **WAF Scoring Saturation in Enforce Mode**: Under default gateway configuration (`Mode == "enforce"`, `AnomalyThreshold == 5`), all built-in OWASP rules carry `Score: 5`. Any rule match reaches the threshold and triggers a block (`Action: "blocked"`). Zero detection-only anomalies (`Action: "logged"`) occur under default settings.
4. **Rate-Limiting Telemetry Void**: Volumetric traffic throttling rejections (HTTP 429 Too Many Requests) served by route-level token bucket rate limiters (`pkg/router/rate_limiter.go`) do not dispatch audit events to `AuditLogger`, leaving rate mitigation entirely unrepresented in security telemetry.
5. **Warning Filter Emptiness**: Because operational alerts are suppressed by the mutual exclusion ternary, rate-limiting emits no events, and WAF rules trigger blocks, selecting the "Warning" severity facet chip yields an empty state message (*"Zero security incidents match active filters"*), giving operators the false impression that warning-level telemetry and anomaly monitoring are broken.

This requirement formalizes the specification for a dual-card architectural presentation on `#/alerts`, multi-action status badging across feeds and drawers, realigned faceted severity filtering, and backend rate-limiting telemetry emission.

## 2. Functional Requirements

### 2.1 FR-147-1: Dual-Card UI Structure for Operational Alerts and Security Incidents
1. The Alerts & Threat Defense view (`#/alerts`) shall decouple operational system health degradations from WAF security incidents into two distinct visual cards:
   - **Card 1: Operational System Alerts Card**: Positioned immediately above the Security Incidents feed.
   - **Card 2: Security Incidents & Threat Defense Feed**: Dedicated to security anomalies, WAF rule matches, firewall quarantines, and rate throttling.
2. **Operational System Alerts Card Specifications**:
   - The card header shall display the title **"Operational System Alerts"** and a descriptive subtitle (e.g. *"Active upstream degradations, route error rate spikes, and certificate renewal failures"*).
   - The card body shall render active items from `model.alerts` (or `D.alerts`).
   - Each operational alert row shall display:
     - Severity indicator icon (`i-x` in red for `sev === 'critical'`, `i-alert` in amber for `sev === 'warning'`).
     - Alert title (e.g. `Upstream Degradation: <pool>`, `High 5xx Error Rate: <route>`, `Certificate Renewal Failed: <domain>`).
     - Informative detail description describing failure count, threshold breach, or domain name.
     - Calendar timestamp formatted via `dtFmt(alert.timestamp)`.
     - Direct actionable navigation target (`data-go="upstreams"`, `data-go="routes"`, or `data-go="certs"`), allowing operators to click the alert row or button to jump directly to the resolving dashboard view.
3. **Zero-State Operational Health Banner**:
   - When no operational alerts are present (`model.alerts.length === 0`), the Operational System Alerts card shall display a compact, positive health status summary:
     - Checkmark icon (`ICON('i-check')` in `var(--ok)`).
     - Informational label: *"All upstream services, routes, and certificates operating normally."*
4. **Coexistence and Elimination of Mutual Exclusion**:
   - The Security Incidents feed shall consume `model.incidents` independently.
   - Populated security incidents shall NEVER suppress, hide, or alter the rendering of operational system alerts.
   - Active operational alerts shall remain visible in their dedicated card regardless of active search queries, facet filters, or pagination states applied to the Security Incidents feed.

### 2.2 FR-147-2: Multi-Action Status Badging (Incidents Feed & Forensic Drawer)
1. The Alerts view and investigation drawer shall discontinue binary action badging (`Blocked` vs `Logged`) and implement an explicit multi-action status badging taxonomy covering four distinct defensive actions:
   - **`Blocked`**: Request was terminated/rejected due to a WAF rule violation, IP ACL blacklist, or protocol violation (`action: "blocked"`).
     - Status badge: `<span class="st s5">Blocked</span>` (red).
     - Row tone icon: `<span class="t-err">${ICON('i-x')}</span>`.
   - **`Banned`**: Offending client IP was quarantined in the automated firewall quarantine list by the auto-ban subsystem (`action: "banned"`).
     - Status badge: `<span class="st s5">Banned</span>` (red/purple).
     - Row tone icon: `<span class="t-err">${ICON('i-x')}</span>`.
   - **`Throttled`**: Request was rejected with HTTP 429 Too Many Requests due to route-level volumetric token bucket rate limiting (`action: "throttled"`).
     - Status badge: `<span class="st s4">Throttled</span>` (amber/orange).
     - Row tone icon: `<span class="t-warn">${ICON('i-alert')}</span>`.
   - **`Logged`**: Request was inspected and allowed to proceed, but recorded for auditing due to detection-only mode or sub-threshold anomaly (`action: "logged"`).
     - Status badge: `<span class="st s4">Logged</span>` (amber/blue).
     - Row tone icon: `<span class="t-warn">${ICON('i-alert')}</span>`.
2. **Forensic Drawer Alignment (`public/js/components/drawer.js`)**:
   - When an operator clicks an incident item, the slide-out investigation drawer (`#drawer`) shall display the accurate multi-action status badge and tone in:
     - Subtitle action pill (`#dwSub`): `pill(tone, actionLabel)` where `tone` is `'err'` for `Blocked` and `Banned`, and `'warn'` for `Throttled` and `Logged`.
     - Key metrics summary (`#dwStats`): Action metric item displays `Blocked`, `Banned`, `Throttled`, or `Logged`.
     - Forensic Key-Value table (`dl.kv`): "Action Taken" renders `<span class="st s5">` for `Blocked`/`Banned` or `<span class="st s4">` for `Throttled`/`Logged`.

---

### 2.3 FR-147-3: Real-Time Faceted Severity Filter Partitioning
1. The severity facet filter chips (`All`, `Critical`, `Warning`) located in the Security Incidents toolbar shall partition multi-action events deterministically:
   - **`All`**: Displays all security events regardless of action or score.
   - **`Critical`**: Displays events representing severe threats and active enforcements:
     - Any event with `action === 'blocked'` OR
     - Any event with `action === 'banned'` OR
     - Any event with `anomaly_score >= 10` OR
     - Any event with explicit `sev === 'critical'`.
   - **`Warning`**: Displays events representing sub-critical warnings, detections, and rate throttles:
     - Any event with `action === 'throttled'` OR
     - Any event with `action === 'logged'` OR
     - Any event with `action !== 'blocked' && action !== 'banned'` OR
     - Any event with `anomaly_score < 10` (when not blocked or banned) OR
     - Any event with explicit `sev === 'warning'`.
2. Selecting a severity chip shall immediately update the incident list DOM and reset the incident pagination to Page 1.
3. If no security incidents match the selected severity filter, the list shall display:
   - `Zero security incidents match active filters.`

### 2.4 FR-147-4: Backend Rate-Limiting Telemetry Integration
1. The route-level rate-limiting middleware (`pkg/router/rate_limiter.go`) shall integrate with the security audit logging subsystem (`*waf.AuditLogger`).
2. When an incoming request violates the configured token bucket capacity and is rejected with HTTP 429 Too Many Requests:
   - In addition to setting `Retry-After` header and returning `{"error":"429 Too Many Requests","retry_after":...}`, the middleware shall emit a structured `SecurityEvent` to `AuditLogger`:
     - `Event`: `"rate_limit_drop"`
     - `Action`: `"throttled"`
     - `Category`: `"rate_limit"`
     - `ClientIP`: Offending client IP address (or client key)
     - `Method`: HTTP request method (e.g. `GET`, `POST`)
     - `Path`: Request target path (e.g. `/api/v1/resource`)
     - `AnomalyScore`: `0`
     - `RuleID`: `"rate_limit"`
     - `PayloadSnippet`: Diagnostic message specifying the rate limit violation and retry delay (e.g. `"Rate limit exceeded: retry after X seconds"`).
3. The emitted event shall be recorded in the in-memory circular event buffer (max 50 events) and exposed via `GET /internal/api/security/incidents`.
4. If `AuditLogger` is nil or disabled, the rate limiter shall safely bypass telemetry logging without throwing nil-pointer panics or disrupting request processing.

---

### 2.5 FR-147-5: Executive KPI Strip and Navigation Badge Cohesion
1. **Navigation Badge**: The left navigation badge (`#nav button[data-nav="alerts"] .badge`) shall strictly reflect the count of unresolved operational alerts (`model.alerts.length`).
2. **Overview Health Banner**: The system status banner on `#/overview` shall continue to reflect operational degradations (unhealthy pools, 5xx spikes, cert renewal failures).
3. **Alerts KPI Strip**:
   - `alKpiActive` ("Active Incidents / Alerts"): Sum of active operational alerts (`model.alerts.length`) plus recent security incidents (`model.incidents.length`).
   - `alKpiBlocks` ("Recent WAF Blocks"): Count of security events where `action === 'blocked'`.
   - `alKpiTemp` ("Stage 1 Temp Bans"): Count of active temporary IP bans (`type === 'temporary'`).
   - `alKpiPerm` ("Stage 2 Permanent Bans"): Count of active permanent IP bans (`type === 'permanent'`).

## 3. Non-Functional Requirements

### 3.1 NFR-147-1: Client JavaScript Footprint Budget Invariant (<= 120.0 KB)
- The total combined uncompressed size of all `.js` files in `public/js/` (including all subdirectories) MUST NOT exceed 120.0 KB (122,880 bytes).
- All new UI rendering, badging helpers, and event listeners must be authored with maximum conciseness:
  - Reusing existing helper functions (`esc`, `dtFmt`, `ICON`, `pill`).
  - Avoiding redundant boilerplate, excessive string templates, or duplicated style rules.

### 3.2 NFR-147-2: Zero External Runtime & Build Dependencies
- In accordance with Toron core architectural principles, all modifications must use native ECMAScript Modules (ESM) and standard CSS3.
- No third-party npm packages, client-side frameworks (React, Vue, Svelte), or bundler compilation steps (Webpack, Vite, Rollup) are permitted.

### 3.3 NFR-147-3: Non-Blocking Execution & High Rendering Performance
- Rendering the dual-card layout, multi-action status badges, and filtered incident lists must execute within 16 ms (targeting 60 fps DOM updates) for incident lists of up to 500 records.
- Slicing and rendering must never cause UI thread freezing, layout thrashing, or background telemetry polling interruption.

### 3.4 NFR-147-4: Telemetry Pipeline Throughput & Memory Bounds
- Rate-limiting security telemetry dispatch must execute with $O(1)$ time complexity and zero unbounded memory allocations.
- The recent security events circular buffer must remain strictly bounded to 50 events (`maxEvents: 50`) to prevent memory leaks in long-running edge nodes.

### 3.5 NFR-147-5: Backward Compatibility & Invariant Preservation
- Existing backend REST API contracts (`/internal/api/security/incidents`, `/internal/api/security/banned-ips`, `/internal/api/security/ban`, `/internal/api/security/unban`) must remain 100% backward-compatible.
- All existing automated verification test cases (`TC-146-01` through `TC-146-10`) in `tests/dashboard_telemetry_test.js` must continue to pass without regression.

## 4. Acceptance Criteria

### AC-147-01: Dual-Card UI Separation and Permanent Operational Alert Visibility
- **Given** a gateway state with 2 active operational alerts (1 upstream degradation and 1 route 5xx error rate spike) and 10 WAF security incidents in `model.incidents`,
- **When** the operator navigates to the Alerts view (`#/alerts`),
- **Then** the view must render two distinct cards:
  1. An **Operational System Alerts** card containing exactly 2 operational alert rows, each displaying the alert title, description, timestamp, and navigation action.
  2. A **Security Incidents & Threat Defense** card containing the paginated list of security incidents.
  The 10 security incidents must NOT suppress or replace the 2 operational alerts in the DOM.

### AC-147-02: Operational System Alerts Zero-Alert Health Summary
- **Given** a gateway state with 0 operational alerts (`model.alerts.length === 0`) and 5 security incidents,
- **When** the operator views the Alerts page,
- **Then** the Operational System Alerts card must remain visible and render the positive status indicator (`ICON('i-check')`) with text *"All upstream services, routes, and certificates operating normally"*, while the Security Incidents card renders the 5 security incidents below it.

### AC-147-03: Multi-Action Status Badging in Incidents Feed
- **Given** an incidents feed containing four distinct events:
  - Event A: `action: "blocked"`
  - Event B: `action: "banned"`
  - Event C: `action: "throttled"`
  - Event D: `action: "logged"`
- **When** the incidents feed is rendered into `#alIncList`,
- **Then**:
  - Event A must render badge text `Blocked` with class `s5` and icon `i-x`.
  - Event B must render badge text `Banned` with class `s5` and icon `i-x`.
  - Event C must render badge text `Throttled` with class `s4` and icon `i-alert`.
  - Event D must render badge text `Logged` with class `s4` and icon `i-alert`.
  None of Events B, C, or D shall be mislabeled as `Blocked`, and Event B must not be mislabeled as `Logged`.

### AC-147-04: Multi-Action Status Badging and Telemetry in Forensic Drawer
- **Given** an incident item with `action: "throttled"` and category `"rate_limit"`,
- **When** the operator clicks the incident item in `#alIncList` to open the inspection drawer (`#drawer`),
- **Then** `#dwTitle` must display `rate_limit`, the header pill in `#dwSub` must render with warning tone and label `Throttled`, `#dwStats` must display Action as `Throttled`, and the forensic key-value table must display Action Taken as `<span class="st s4">Throttled</span>`.

### AC-147-05: Real-Time Severity Facet Filtering (Critical vs. Warning Partitioning)
- **Given** an incidents feed containing:
  - 2 events with `action: "blocked"`
  - 1 event with `action: "banned"`
  - 2 events with `action: "throttled"`
  - 1 event with `action: "logged"`
- **When** the operator clicks the `Critical` severity facet chip,
  **Then** exactly 3 events (`blocked` and `banned`) must be displayed in the list, and pagination must show `Showing 1–3 of 3`.
- **When** the operator clicks the `Warning` severity facet chip,
  **Then** exactly 3 events (`throttled` and `logged`) must be displayed in the list, and pagination must show `Showing 1–3 of 3`.
- **When** the operator clicks the `All` severity facet chip,
  **Then** all 6 events must be displayed.

### AC-147-06: Backend Rate-Limiting Telemetry Dispatch on HTTP 429
- **Given** a route configured with a rate limit of `10/sec` and an active `*waf.AuditLogger`,
- **When** a client exceeds the token bucket limit and receives an HTTP 429 response,
- **Then** the rate limiter middleware must dispatch a `SecurityEvent` to `AuditLogger` with `Event: "rate_limit_drop"`, `Action: "throttled"`, `Category: "rate_limit"`, `RuleID: "rate_limit"`, and `AnomalyScore: 0`, and this event must appear in `GET /internal/api/security/incidents`.

### AC-147-07: Operational Alert Direct Resource Navigation
- **Given** an operational alert for upstream pool degradation with `go: "upstreams"`,
- **When** an operator clicks the alert row or its action link,
- **Then** the application must trigger navigation to `#/upstreams` (via existing `[data-go]` routing handlers in `app.js`).

### AC-147-08: Client JavaScript Footprint Budget (<= 120.0 KB)
- **Given** all changes across `public/js/` implementing dual-card rendering, multi-action badging, and drawer updates,
- **When** the total size of all `.js` files in `public/js/` is computed,
- **Then** the sum must not exceed 122,880 bytes (120.0 KB), and `TC-146-09` must pass.

### AC-147-09: Strictly Relative Links Invariant in Documentation
- **Given** the documentation file `docs/requirements/REQ-147.md`,
- **When** scanned for absolute link paths (protocol URIs or leading `/`),
- **Then** zero absolute links must be found, and all internal references must resolve using relative paths (`./` or `../`).

## 7. Open Questions

1. **Operational Alerts Card Collapsibility**:
   - Should the Operational System Alerts card offer an optional collapse toggle when in the healthy zero-alert state, or remain persistently open as a compact single-line green status banner?
   - *Working assumption*: A compact single-line green banner (`✓ All upstream services, routes, and certificates operating normally`) provides clear positive confirmation without taking up significant vertical space.
2. **Rate-Limiter Telemetry Aggregation / Sampling**:
   - Under heavy distributed denial-of-service (DDoS) traffic where rate limits are exceeded thousands of times per second, should the rate limiter log every 429 drop into the 50-event circular buffer, or implement sliding-window rate throttling on the logger itself (e.g. max 5 events/sec per client IP)?
   - *Working assumption*: In-memory circular buffer drops oldest events cleanly ($O(1)$ buffer overwrite), but logger sampling under extreme volume can prevent log flooding if disk/stdout sinks are enabled.
