# TC-100 - Verification Suite for RFC 8555 Token Syntax & Length Validation and HTTP Method Hardening in ACME HTTP-01 Challenge Handler

## 1. Test Suite Objectives & Scope

Verify that Toron Edge Gateway's Automated Certificate Management Environment (ACME) HTTP-01 challenge responder handler ([`pkg/acme/acme.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go)) strictly adheres to **[RFC 8555 §8.3](https://datatracker.ietf.org/doc/html/rfc8555#section-8.3) base64url token syntax restrictions, length bounding ($1 \le \text{len} \le 128$), strict HTTP method filtering with HTTP 405 enforcement, and [RFC 7231 §4.3.2](https://datatracker.ietf.org/doc/html/rfc7231#section-4.3.2) `HEAD` method semantics**, completely resolving the input validation and protocol compliance deficiencies tracked under security audit [`SR-091 Finding 8`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L235-L251) and vulnerability assessment [`SEC-38`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L539-L547) ([CWE-20: Improper Input Validation](https://cwe.mitre.org/data/definitions/20.html) and [CWE-703: Improper Handling of Exceptional Conditions](https://cwe.mitre.org/data/definitions/703.html)).

This test specification validates the architectural remediations defined in [`REQ-100`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-100.md), [`ADR-100`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-100.md), and [`TASK-123`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-123.md) across [`pkg/acme/acme.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go) and [`pkg/acme/acme_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme_test.go), confirming that:

1. **RFC 8555 Base64URL Character Set Validation**: Every token character belongs strictly to the unpadded base64url alphabet (`[a-zA-Z0-9_-]`). Invalid characters, including base64 padding (`=`), path separators (`/`, `\`), directory traversal dots (`..`), symbols (`@`, `+`, `*`), whitespace, control characters, and unicode bytes are rejected immediately with HTTP `400 Bad Request`.
2. **Strict Token Length Bounding ($1 \le \text{len} \le 128$)**: Empty tokens (`len == 0`) and tokens exceeding 128 bytes (`len > 128`) are rejected with HTTP `400 Bad Request`. Boundary tokens of exactly 1 byte and 128 bytes validate successfully.
3. **Zero Whitespace Tolerance**: The handler eliminates silent whitespace trimming (`strings.TrimSpace`). Any token with leading, trailing, or internal whitespace fails validation and produces HTTP `400 Bad Request`.
4. **HTTP Method Filtering & RFC 7231 §6.5.5 Compliance**: Only `GET` and `HEAD` requests are permitted. Non-idempotent or unauthorized verbs (`POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `CONNECT`, etc.) are rejected with HTTP `405 Method Not Allowed`, setting the mandatory `Allow: GET, HEAD` header and `Content-Type: text/plain`.
5. **RFC 7231 §4.3.2 `HEAD` Method Semantics**: Requests using `HEAD` with a valid, registered token return HTTP `200 OK`, `Content-Type: text/plain`, `Content-Length` matching the key authorization length, and strictly an empty response body (`res.Body.Len() == 0`).
6. **RFC 8555 GET Resolution**: Valid `GET` requests return HTTP `200 OK`, `Content-Type: text/plain`, `Content-Length`, and write the exact key authorization payload string into `res.Body`.
7. **Non-Existent Token Handling**: Valid tokens not present in the active challenge registry return HTTP `404 Not Found` (with error body on `GET`, and empty body on `HEAD`).
8. **Fail-Fast Lock Isolation**: Malformed tokens or disallowed methods fail immediately before calling `GetHTTP01Challenge`, avoiding read-lock acquisition on `m.mu` and shielding internal challenge state from hash churn and DoS flooding.
9. **Zero Third-Party Dependencies & Concurrency Safety**: Pure Go standard library implementation executing 100% race-free under `go test -race ./pkg/acme/...`.

## 3. Detailed Test Case Specifications

### TC-100-01: Valid Token `GET` Returns HTTP 200 OK with Key Authorization Body

- **Objective**: Verify that a standard HTTP `GET` request presenting a syntactically valid base64url challenge token currently registered in `m.http01Tokens` returns HTTP status `200 OK`, `Content-Type: text/plain`, exact `Content-Length` header matching the payload size, and the full key authorization string in the response body.
- **Traceability**: [`REQ-100-AC-01`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-100.md#L110-L132), [`REQ-100-AC-05`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-100.md#L181-L196), [`ADR-100 §1, §3`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-100.md), [`TASK-123 §1, §3`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-123.md).
- **Target Function**: `TestACME_HTTP01_ValidToken_GET_Success(t *testing.T)` in `pkg/acme/acme_test.go`.
- **Preconditions**:
  - `ACMEManager` initialized with temporary cache directory.
  - Valid RFC 8555 base64url token registered: `token := "LoqXcYV8q5ONbJQxWtGtTK-GwfeqST3gahAuhKhBpDU"`.
  - Corresponding key authorization registered via `mgr.SetHTTP01Challenge(token, keyAuth)`.
- **Action & Test Steps**:
  1. Construct GET request:
     ```go
     req, err := httpparser.NewRequest("GET", "/.well-known/acme-challenge/"+token, "HTTP/1.1")
     res := httpparser.NewResponse()
     ```
  2. Invoke `mgr.ServeHTTP01Handler(req, res)`.
  3. Assert `res.StatusCode == http.StatusOK` (200).
  4. Assert `res.Header.Get("Content-Type") == "text/plain"`.
  5. Assert `res.Header.Get("Content-Length") == strconv.Itoa(len(expectedKeyAuth))`.
  6. Assert `res.Body.String() == expectedKeyAuth`.
- **Verifiable Assertions**:
  1. HTTP status code is strictly 200.
  2. `Content-Type` header is `"text/plain"`.
  3. `Content-Length` header strictly matches byte length of `expectedKeyAuth`.
  4. Body equals `expectedKeyAuth` with zero data corruption or truncation.

### TC-100-06: HTTP Method Hardening & 405 Rejection

- **Objective**: Verify that `ServeHTTP01Handler` strictly restricts allowed HTTP methods to `GET` and `HEAD`. ### TC-100-09: High-Concurrency Race Safety under `go test -race`

- **Objective**: Verify that concurrent execution of `ServeHTTP01Handler` (handling a mixture of valid GET requests, valid HEAD requests, malformed tokens, disallowed methods, and 404 misses) in parallel with background token registration (`SetHTTP01Challenge`) and cleanup (`RemoveHTTP01Challenge`) is 100% thread-safe and executes without data races under `go test -race`.
- **Traceability**: [`REQ-100-AC-07`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-100.md#L212-L216), [`ADR-100 §4`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-100.md), [`TASK-123 §4`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-123.md).
- **Target Function**: `TestACME_HTTP01_HighConcurrency_RaceSafety(t *testing.T)` in `pkg/acme/acme_test.go`.
- **Preconditions**:
  - `ACMEManager` running.
  - Test executed under Go race detector: `go test -race ./pkg/acme/...`.
- **Test Setup & Execution Steps**:
  1. Spawn 20 reader goroutines, each executing 50 iterations:
     - Worker 1: GET with valid token (assert status 200 or 404).
     - Worker 2: HEAD with valid token (assert empty body).
     - Worker 3: Disallowed POST/PUT (assert status 405).
     - Worker 4: Malformed invalid token (assert status 400).
  2. Concurrently spawn 2 writer goroutines continuously registering and removing temporary challenges:
     ```go
     for j := 0; j < 50; j++ {
         token := fmt.Sprintf("dynamic_token_%d", j)
         mgr.SetHTTP01Challenge(token, "dynamic_auth")
         time.Sleep(1 * time.Millisecond)
         mgr.RemoveHTTP01Challenge(token)
     }
     ```
  3. Wait for all goroutines to complete with `sync.WaitGroup`.
  4. Verify zero race conditions or panics detected.
- **Verifiable Assertions**:
  1. Readers and writers execute simultaneously with zero race conditions under `go test -race`.
  2. Lock synchronization via `m.mu.RLock()` and `m.mu.Lock()` ensures state integrity.
  3. Zero panics or memory corruption under high concurrency.
