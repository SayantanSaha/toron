# TC-104 - Verification Suite for Differential Fuzzer Report Formatting and Baseline Invariant

## 1. Test Suite Objectives

Verify that `benchmarks/fuzzer/diff_fuzzer.go` dynamically computes expected HTTP status code strings, formats single status codes with their canonical RFC status phrase (`200 OK`), formats multiple acceptable status codes as slash-separated values (`400/501`, `400/403`), and correctly renders `BASELINE-001` as `200 OK` in Markdown report outputs without hardcoded fallback constants.

## 2. Test Cases

### TC-104-01: Canonical Single-Code Status Formatting
- **Objective**: Verify that `formatExpectedStatus` formats single status code slices (e.g. `[]int{200}`) into canonical string representation with RFC status text (`"200 OK"`).
- **Expected Outcome**: `formatExpectedStatus([]int{200}) == "200 OK"`, `formatExpectedStatus([]int{400}) == "400 Bad Request"`, `formatExpectedStatus([]int{403}) == "403 Forbidden"`.

### TC-104-02: Multi-Code Slash-Delimited Formatting
- **Objective**: Verify that `formatExpectedStatus` formats multi-code slices (e.g. `[]int{400, 501}`) into slash-delimited representation (`"400/501"`).
- **Expected Outcome**: `formatExpectedStatus([]int{400, 501}) == "400/501"`, `formatExpectedStatus([]int{400, 403}) == "400/403"`.

### TC-104-03: BASELINE-001 Expected Status Rendering in Report
- **Objective**: Verify that when reporting on `BASELINE-001`, the generated Markdown and JSON reports display `200 OK` as the expected status.
- **Expected Outcome**: `TestResult.ExpectedStatusStr == "200 OK"` for `BASELINE-001`, and the generated Markdown table contains `| `BASELINE-001` | ... | `200 OK` |`.

### TC-104-04: Removal of Hardcoded 400/501 Fallbacks
- **Objective**: Confirm that arbitrary test cases with novel expected statuses (e.g. `[]int{414}`) render accurately (`"414 URI Too Long"`) without falling back to `"400/501"`.
- **Expected Outcome**: `formatExpectedStatus([]int{414}) == "414 URI Too Long"`.
