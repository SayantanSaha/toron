# REQ-094 - Bounded Route Table Lifecycle, Atomic Source Replacement, and Multi-Target Pod Aggregation in Kubernetes Ingress Controller

## 1. Context & Business Value

Toron Edge Gateway provides a native, zero-dependency Kubernetes Ingress Controller ([`pkg/ingress/controller.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go)) designed to watch `networking.k8s.io/v1` `Ingress` and `Endpoints` resources from the Kubernetes API server, translate them into upstream reverse proxies, and dynamically register prefix routes within the core routing engine ([`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go)).

During comprehensive security review [`SR-091 Finding 3`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L130-L152) and vulnerability assessment [`SEC-33`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L449-L457) ([CWE-400 Uncontrolled Resource Consumption](https://cwe.mitre.org/data/definitions/400.html), [CWE-670 Use of Incorrect Operator / Control Flow](https://cwe.mitre.org/data/definitions/670.html), [CWE-1059 Incomplete Technical Documentation](https://cwe.mitre.org/data/definitions/1059.html)), a critical flaw was uncovered in how route registration, route updates, and route deletions are synchronized between [`pkg/ingress/controller.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go), [`pkg/ingress/translator.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go), and [`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go).

### Problem Statement & Failure Modes

In [`pkg/ingress/controller.go:L111-L161`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L111-L161), `syncIngresses` executes periodically (default every 30 seconds via `periodicResyncWorker`) and reactively upon consuming watch events (`consumeEventsWorker`). Within `syncIngresses`:
```go
for _, ing := range ingList {
    routes, ok := TranslateIngress(ing, c.cfg.IngressClass, endpointsMap)
    if !ok {
        continue
    }
    for _, r := range routes {
        newRoutes[r.ContainerID] = r
        if c.router != nil {
            opts := proxy.ProxyOptions{
                Targets: []string{r.TargetURL()},
            }
            _ = c.router.RoutePrefix("upstream", r.Host, r.Prefix, nil, "", opts)
        }
    }
}
```

In [`pkg/router/router.go:L235-L247`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L235-L247):
```go
r.mu.Lock()
defer r.mu.Unlock()
r.prefixRoutes = append(r.prefixRoutes, prefixRoute{
    routeType:    string(normType),
    host:         strings.ToLower(strings.TrimSpace(host)),
    prefix:       cleanPrefix,
    headers:      headers,
    redirectHTTP: opts.RedirectHTTP,
    accessLog:    strings.TrimSpace(opts.AccessLog),
    securityLog:  strings.TrimSpace(opts.SecurityLog),
    handler:      handler,
})
```

This interaction produces four cascading failure modes:

1. **Unbounded Memory Leak**: `c.router.RoutePrefix` unconditionally appends entries to `r.prefixRoutes` on every sync cycle. Because periodic resync triggers every 30 seconds, a cluster with 50 Ingress routes appends 100 new entries per minute, or **144,000 duplicate route entries per 24 hours**. Over hours and days of operation, this leads to monotonic heap memory growth, router cache bloat, GC pressure, and eventual Out-Of-Memory (OOM) termination.
2. **Zombie Route Persistence**: When an Ingress resource or route path is deleted from the Kubernetes cluster, `syncIngresses` updates its local `activeRoutes` map, but performs no pruning on `r.prefixRoutes`. As a result, deleted Ingress routes persist indefinitely in the router table ("zombie routes"). Client traffic sent to those paths continues to be proxied to decommissioned or repurposed backends.
3. **Stale Endpoint Shadowing**: In [`pkg/router/router.go:L523-L541`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L523-L541), `router.ServeHTTP` iterates through `r.prefixRoutes` linearly and dispatches to the *first matching route*. When a pod is rescheduled, restarted, or updated with a new IP, the new endpoint route is appended to the *end* of `r.prefixRoutes`. The obsolete route entry at the beginning of the slice continues to intercept all traffic, forwarding requests to dead IPs and causing persistent `502 Bad Gateway` or connection timeouts.
4. **Multi-Pod Replica Starvation**: In [`pkg/ingress/translator.go:L110-L123`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/translator.go#L110-L123), `TranslateIngress` iterates through each IP in `targetIPs` and returns individual 1-target `DiscoveredRoute` records. In `syncIngresses`, each record is registered as an independent prefix route with a single target. Because `router.ServeHTTP` matches the first entry in `r.prefixRoutes`, **pod replica #1 receives 100% of the traffic**, while all other replicas receive 0% traffic. Horizontal scaling is completely defeated, and single pod replicas are subjected to cascading overload crashes.

### Exploitability & Security Impact

- **Denial of Service (DoS)**: Memory exhaustion from unbounded slice growth causes gateway nodes to crash under standard operating conditions.
- **Route Hijacking & Information Disclosure**: Zombie routes and stale endpoints allow deleted or retired tenant routes to remain active, intercepting traffic meant for other services or routing traffic to stale containers reassigned to other tenants.
- **Service Disruption**: Inability to balance traffic across multiple pod replicas forces all load onto a single instance, inducing server errors and defeating Kubernetes high availability.

Remediating `SEC-33` establishes an **atomic, bounded route lifecycle** in Toron's core router and Kubernetes Ingress Controller, guaranteeing $O(K)$ bounded memory, zero zombie routes, immediate endpoint cutover, and fair multi-target round-robin load balancing.

## 2. Non-Goals & Scope Exclusions

1. **OCI Container Discovery Lifecycle (`SEC-34`)**: Dynamic route reconciliation for standalone OCI/Docker container discovery ([`pkg/discovery/manager.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/discovery/manager.go)) is tracked as a separate security finding (`SEC-34`) and will be governed by [`REQ-095`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-095.md). While the underlying source-tagging mechanism in `pkg/router` is designed to support multiple sources (e.g. `"container-discovery"`), `REQ-094` strictly governs the Kubernetes Ingress Controller (`pkg/ingress`).
2. **Kubernetes Gateway API (`gateway.networking.k8s.io`)**: Support for the Kubernetes Gateway API is out of scope; `REQ-094` applies to standard Kubernetes `networking.k8s.io/v1` `Ingress` resources.
3. **External Dynamic DNS & BGP Integration**: Dynamic DNS provider updates and BGP route announcements for Ingress IP addresses are excluded.
4. **Third-Party Client SDKs**: Incorporating `k8s.io/client-go` or other external dependencies is strictly prohibited. All synchronization and routing must use Toron's zero-dependency standard library client ([`pkg/ingress/client.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/client.go)).

## 3. Requirements & Acceptance Criteria

### REQ-094-AC-01: Source-Tagged Prefix Routing in Router Subsystem
- The internal `prefixRoute` structure in [`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go) MUST include a `source string` metadata field designating the originating subsystem (e.g., `"k8s-ingress"`).
- Existing route registration functions (e.g., [`RoutePrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L163)) MUST remain backward-compatible, assigning a default source identifier (such as `""` or `"config"`) when unspecified.
- The router MUST provide an interface or registration parameter allowing callers to register prefix routes tagged with an explicit `source` identifier.
- The router inspection helper [`PrefixRoutes()`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L740-L755) and `RouteSnapshot` MUST expose the route `Source` field for telemetry, debugging, and audit logging.

### REQ-094-AC-02: Atomic Prefix Route Replacement by Source (`ReplacePrefixRoutesBySource`)
- The `Router` struct in [`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go) MUST provide a public atomic replacement method:
  ```go
  ReplacePrefixRoutesBySource(source string, routes []PrefixRouteConfig) error
  ```
  *(or an equivalent atomic batch replacement API accepting source-tagged route definitions).*
- Under the router's exclusive write lock (`r.mu.Lock()`):
  1. All existing prefix routes matching `pr.source == source` MUST be identified and removed from `r.prefixRoutes`.
  2. All new prefix routes supplied in the replacement batch MUST be validated and appended to `r.prefixRoutes` with their `source` set to the specified `source`.
  3. All existing prefix routes belonging to other sources (e.g., static file routes, configuration-driven routes, administrative endpoints) MUST remain completely intact, uninterrupted, and in their existing relative order.
  4. If the replacement slice is empty, all routes belonging to `source` MUST be pruned, leaving other routes unaffected.
- The transition between the old route set and new route set MUST be atomic: incoming requests dispatched via `ServeHTTP` MUST observe either the complete prior route set or the complete new route set, with zero partial or inconsistent routing states.

### REQ-094-AC-03: Bounded Route Table Invariant Across Sync Cycles
- In [`pkg/ingress/controller.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go), `syncIngresses` MUST synchronize all translated routes into `router.Router` using `ReplacePrefixRoutesBySource` (or equivalent source-scoped atomic replacement) with `source: "k8s-ingress"`.
- **Bounded Table Invariant**: Given an unchanged set of $K$ active Kubernetes Ingress rules, executing $N$ consecutive synchronization cycles (whether triggered by periodic resync or watch events) MUST guarantee:
  $$\text{Count}(r.prefixRoutes, \text{source} = \text{"k8s-ingress"}) = K \quad \forall N \ge 1$$
- Monotonic growth of `r.prefixRoutes` across sync cycles is strictly prohibited. The memory consumption of `r.prefixRoutes` MUST be $O(K)$ with respect to active Ingress rules, and strictly $O(1)$ with respect to synchronization cycle iterations.

### REQ-094-AC-04: Automatic Pruning of Deleted Ingress Routes (Zombie Route Elimination)
- When a Kubernetes Ingress resource, host rule, or path rule is deleted from the cluster:
  - On the subsequent synchronization cycle (`syncIngresses`), the deleted route MUST NOT be included in the new route set passed to `ReplacePrefixRoutesBySource`.
  - The router MUST immediately prune the deleted route from `r.prefixRoutes`.
  - Subsequent HTTP requests matching the deleted `(Host, Prefix)` MUST NOT be forwarded to the old upstream target and MUST return HTTP `404 Not Found` (or trigger fallback handlers if configured).

### REQ-094-AC-05: Multi-Target Pod Endpoint Aggregation & Load Balancing
- For every Ingress path rule backed by a Kubernetes Service with multiple pod endpoints (e.g. $M$ pod IPs):
  - Ingress translation and synchronization MUST aggregate all healthy pod target URLs (`http://<ip>:<port>`) for a given `(Host, Prefix)` into a single multi-target `proxy.ProxyOptions{ Targets: [...] }`.
  - The controller MUST register exactly **one** prefix route entry in `router.Router` per unique `(Host, Prefix)`.
  - The underlying reverse proxy MUST utilize Toron's built-in `RoundRobinBalancer` (or configured load balancing algorithm) across all $M$ target endpoints.
  - Successive requests sent to that `(Host, Prefix)` MUST be distributed evenly across all $M$ healthy pod targets ($\approx 1/M$ traffic per replica), eliminating single-pod replica starvation.

### REQ-094-AC-06: Immediate Endpoint Traffic Redirection Without Shadowing
- When the endpoint addresses of a Kubernetes Service change (such as during pod rollouts, restarts, scaling, or migrations):
  - `syncIngresses` MUST construct the new multi-target proxy with the updated pod IPs and atomically replace the `"k8s-ingress"` routes.
  - The obsolete route entry containing old pod IPs MUST be completely removed from `r.prefixRoutes` rather than remaining ahead of the new route.
  - Requests arriving immediately after the atomic replacement MUST route exclusively to the updated pod IPs. Zero requests shall be forwarded to stale or decommissioned pod IPs.

### REQ-094-AC-07: Resource Cleanup for Discarded Load Balancers & Health Checkers
- When prefix routes are replaced or pruned during synchronization:
  - The system MUST ensure that any background goroutines, active health checkers (`targetNode.StartActiveHealthCheck`), or open transport connections associated with discarded `ReverseProxy` and `LoadBalancer` instances are cleanly terminated.
  - Discarded reverse proxy handlers that implement a `Close()` or `Stop()` interface MUST have their cleanup methods invoked upon eviction or replacement.
  - Route replacement MUST NOT leak active health check ticker goroutines or persistent keep-alive connections.

### REQ-094-AC-08: Concurrency Safety and Thread Safety Invariant
- All route replacement operations, endpoint translations, active route map updates, and request dispatching MUST be strictly thread-safe.
- Concurrent execution of high-volume HTTP requests through `router.ServeHTTP` while `syncIngresses` executes in the background MUST operate with zero data races, zero panics, and zero dropped connections under `go test -race ./pkg/ingress/... ./pkg/router/...`.

### REQ-094-AC-09: Zero Third-Party Dependencies Invariant
- All routing table manipulations, slice replacements, endpoint aggregation algorithms, and synchronization workflows MUST strictly use the Go standard library (`sync`, `net/http`, `net/url`, `time`, `context`, `strings`, `path`, etc.).
- No external dependencies are permitted.

### REQ-094-AC-10: Automated Test Coverage and Verification (`TC-094`)
- A comprehensive test suite MUST be implemented in `pkg/router` and `pkg/ingress` verifying:
  1. `TestRouter_ReplacePrefixRoutesBySource`: Verifies that `ReplacePrefixRoutesBySource` updates only routes with matching source, preserves all other sources, and prunes routes when given an empty slice.
  2. `TestIngressController_BoundedRouteTable`: Verifies that executing 50 consecutive sync cycles with 3 active Ingress rules results in exactly 3 prefix routes in `router.prefixRoutes`.
  3. `TestIngressController_ZombieRoutePruning`: Verifies that deleting an Ingress from the mock API server immediately prunes the route from the router on the next sync and produces HTTP `404 Not Found`.
  4. `TestIngressController_MultiPodLoadBalancing`: Verifies that an Ingress path backed by 3 pod replicas creates a single route and distributes sequential requests evenly across all 3 backend instances.
  5. `TestIngressController_EndpointUpdateNoShadowing`: Verifies that updating pod endpoint IPs immediately routes traffic to the new IP with zero shadowing or stale IP routing.
  6. `TestIngressController_HealthCheckCleanupOnRouteReplace`: Verifies that active health check goroutines associated with replaced upstreams are stopped cleanly without leaks.
  7. `TestIngressController_ConcurrentSyncAndRouting_RaceClean`: High-concurrency test executing parallel `ServeHTTP` requests while repeatedly triggering `syncIngresses`, verifying race-free execution under `go test -race`.

## 4. Rationale & Threat Model

| Threat Scenario | Vulnerability / Root Cause | Prior Behavior (Vulnerable) | Remediated Behavior (REQ-094) |
| :--- | :--- | :--- | :--- |
| **Unbounded Memory Exhaustion (CWE-400)** | Periodic resync (30s) and watch events invoke `c.router.RoutePrefix`, appending to `r.prefixRoutes` indefinitely. | Route table grows by 144,000 entries/day per 50 routes. Memory steadily leaks, leading to OOM crash and severe request latency. | `ReplacePrefixRoutesBySource` atomically replaces `"k8s-ingress"` routes. Route table size remains strictly bounded at $K$ entries. |
| **Zombie Route Hijacking & Traffic Leakage (CWE-670)** | Ingress deletion in K8s does not prune previously registered routes from `r.prefixRoutes`. | Deleted Ingress routes persist indefinitely in the router. Traffic continues to proxy to decommissioned or repurposed backends. | Disappeared Ingresses are omitted from the replacement batch and immediately removed from `r.prefixRoutes`, returning HTTP 404. |
| **Stale Endpoint Shadowing** | Updated pod IPs appended to end of `r.prefixRoutes`; `router.ServeHTTP` selects first match. | Old route entry matches first. Requests sent to terminated pod IPs, causing persistent 502/504 errors. | Old route entries removed atomically. New route with updated pod IPs is active immediately with zero shadowing. |
| **Multi-Pod Replica Starvation** | `TranslateIngress` emits 1-target routes per pod; first route matches in `ServeHTTP`. | Replica #1 receives 100% traffic; Replicas #2..M receive 0% traffic. Single pod overloaded, zero horizontal scaling. | All pod target URLs for `(Host, Prefix)` aggregated into a single route with `RoundRobinBalancer`, distributing traffic evenly ($\approx 1/M$). |
| **Goroutine & Connection Leaks on Route Updates** | Evicted reverse proxies with active health checkers left running in memory. | Background health checker goroutines and idle connections linger indefinitely, leaking sockets (EMFILE) and memory. | Discarded `ReverseProxy` and `LoadBalancer` instances have `Close()` / `Stop()` called, terminating background checkers cleanly. |

## 5. Constraints & Non-Functional Requirements

- **Memory Bound Invariant**: Routing table memory footprint MUST be strictly $O(K)$ where $K$ is the number of active Ingress rules. The memory footprint MUST NOT grow as a function of synchronization iterations ($O(1)$ with respect to sync count $N$).
- **Atomic Read Non-Blocking**: Route replacement MUST NOT corrupt read paths. Readers acquiring `r.mu.RLock()` during `ServeHTTP` MUST experience bounded lock acquisition latency.
- **Fair Load Distribution**: Multi-target routes MUST distribute requests evenly across healthy upstream pods with zero starvation.
- **Zero Third-Party Dependencies**: Pure Go standard library only (`sync`, `net/http`, `net/url`, `time`, `context`, `strings`, `path`).
- **Thread Safety**: 100% data-race-free under `go test -race ./...`.

## 6. Open Questions

- *Open Question 1*: Should `ReplacePrefixRoutesBySource` accept pre-constructed route handlers or route configuration descriptors?
  - *Resolution*: Providing a structured route specification (e.g. `PrefixRouteConfig` or `RoutePrefixWithSource`) allows `pkg/router` to encapsulate handler creation, reverse proxy instantiation, and source tagging consistently while maintaining full control over route lifecycle and resource cleanup.
- *Open Question 2*: How should `ActiveRoutes()` in `Controller` reflect multi-target routes?
  - *Resolution*: `ActiveRoutes()` can return the aggregated discovered route representing the service endpoint group, or individual targets can be inspected via the underlying reverse proxy's `Balancer.Targets()`.
