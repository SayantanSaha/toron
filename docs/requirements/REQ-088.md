# REQ-088 - Maximum Idle Deadline Enforcement on Upgraded Protocol and WebSocket Connections

## Description

The Toron HTTP server engine ([`Server`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go)) MUST enforce configurable maximum idle deadlines and bidirectional activity tracking on all upgraded protocol streams—including HTTP/1.1 protocol switching (RFC 6455 WebSocket upgrades and raw bidirectional tunnels) and HTTP/2 Extended CONNECT streams (RFC 8441). When data transfer in both directions ceases for longer than the configured timeout, the server MUST deterministically terminate client and upstream sockets, unblocking relay goroutines and reclaiming operating system socket file descriptors (`FD`s). This remediates vulnerability [`SEC-27`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L384-L392) (CWE-400), preventing Slowloris socket exhaustion and file descriptor starvation (`EMFILE`).

## Problem Statement

As documented in [`SEC-27`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L384-L392) and [`SR-081 Finding 5`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-081.md#L142-L150), Toron's connection handling for upgraded protocol connections lacks maximum idle timeouts and deadline enforcement:

### 1. HTTP/1.1 Upgraded Connection Deficiencies ([`pkg/server/server.go:L272-L294`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L272-L294))
- **Permanent Deadline Clearance**: When an HTTP/1.1 connection completes a protocol upgrade (`101 Switching Protocols`), existing read and write deadlines on both client socket (`conn`) and upstream backend socket (`res.UpgradedConn`) are permanently stripped via `conn.SetDeadline(time.Time{})` and `res.UpgradedConn.SetDeadline(time.Time{})`.
- **Indefinite Blocking in Stream Copying**: The bidirectional relay relies on unbounded `io.Copy(res.UpgradedConn, conn)` and `io.Copy(conn, res.UpgradedConn)` calls. If both client and upstream peers stop transmitting without cleanly sending a TCP `FIN` or `RST` (e.g., dead client, half-open connection, network partition, or deliberate Slowloris attack), both goroutines remain blocked indefinitely.
- **Permanent Socket and Goroutine Leaks**: Each abandoned connection permanently leaks two operating system socket file descriptors and two Go runtime worker goroutines. Under an adversary opening hundreds of idle WebSocket connections, host file descriptors are rapidly exhausted (`socket: too many open files` - `EMFILE`), crashing or hanging the gateway and rejecting legitimate traffic.

### 2. HTTP/2 Extended CONNECT Deficiencies ([`pkg/server/server.go:L365-L376`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L365-L376))
- **Unbounded HTTP/2 Stream Relay**: In [`http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L310-L382), extended CONNECT WebSockets (RFC 8441) pipe the HTTP/2 stream body (`r.Body`) and upstream socket (`res.UpgradedConn`) using unrestricted `io.Copy` operations without deadline monitoring.
- **Missing Activity Timeout**: If upstream or client ceases transmission, the upstream socket (`res.UpgradedConn`) and forwarding goroutines remain blocked without timeout expiration or cleanup, accumulating leaked resources across multiplexed HTTP/2 streams.

### 3. Lack of Configurable Idle Deadline Schema
- Neither [`server.Config`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/config.go#L6-L30) nor [`ServerConfig`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L214-L237) provides a dedicated configuration field for upgraded connection idle timeouts (`UpgradeIdleTimeout`). The existing `IdleTimeout` applies solely to HTTP keep-alive intervals between successive discrete request-response cycles.

## Acceptance Criteria

1. **Configurable Upgraded Connection Idle Timeout Schema (`UpgradeIdleTimeout`)**:
   - [`server.Config`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/config.go#L6-L30) in `pkg/server/config.go` MUST include:
     - `UpgradeIdleTimeout time.Duration`: Maximum permissible duration of bidirectional inactivity on an upgraded connection or stream before automatic termination.
   - [`DefaultConfig()`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/config.go#L33-L54) in `pkg/server/config.go` MUST set `UpgradeIdleTimeout` to a sensible production default of `60 * time.Second`.
   - [`ServerConfig`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L214-L237) in `pkg/config/config.go` MUST be extended with:
     - `UpgradeIdleTimeout time.Duration` (`yaml:"upgrade_idle_timeout,omitempty" json:"upgrade_idle_timeout,omitempty"`).
   - [`DefaultAppConfig()`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L494-L577) in `pkg/config/config.go` MUST set `Server.UpgradeIdleTimeout` to `60 * time.Second`.
   - [`ToServerConfig()`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L580-L610) MUST map `UpgradeIdleTimeout` from `ServerConfig` to `server.Config`. If `UpgradeIdleTimeout <= 0`, it MUST fall back to `ServerConfig.IdleTimeout`. If `IdleTimeout` is also `<= 0`, it MUST fall back to `60 * time.Second`.
   - [`pkg/config/loader.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/loader.go) MUST validate that `UpgradeIdleTimeout` (if explicitly provided in configuration) is not negative (`< 0`).

2. **Bidirectional Activity-Refreshed Deadline Relay for HTTP/1.1 Upgrades**:
   - In [`pkg/server/server.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go), unconditional clearance of deadlines via unbounded `conn.SetDeadline(time.Time{})` MUST be replaced with an active deadline relay enforcing `UpgradeIdleTimeout`.
   - The relay MUST monitor bidirectional data flow between client connection (`conn`) and upstream connection (`res.UpgradedConn`).
   - Every chunk of data successfully read and transferred in either direction (client-to-upstream or upstream-to-client) MUST refresh the activity timestamp and extend read/write deadlines by `UpgradeIdleTimeout`.
   - If no data is transferred in **either** direction for the duration of `UpgradeIdleTimeout`:
     - Both client and upstream connections MUST be terminated immediately.
     - All relay goroutines MUST exit promptly without hanging or leaking.
     - Both socket file descriptors MUST be returned to the operating system.
   - Half-closed connection states (e.g., client sends `TCP FIN` or closes write-side) MUST continue to honor `UpgradeIdleTimeout` while draining remaining upstream responses until completion or timeout.

3. **Idle Deadline Enforcement for HTTP/2 Extended CONNECT Upgrades**:
   - In [`http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L310-L382), bidirectional data transfer between the client HTTP/2 stream (`r.Body` / `w`) and upstream socket (`res.UpgradedConn`) MUST enforce `UpgradeIdleTimeout`.
   - Data transfer activity MUST refresh deadlines and activity timestamps.
   - If inactivity exceeds `UpgradeIdleTimeout`:
     - Upstream socket (`res.UpgradedConn`) MUST be closed.
     - Upstream and downstream copying goroutines MUST unblock and terminate cleanly.
     - The HTTP/2 stream MUST be closed without leaking memory or hanging background tasks.
   - Cancellation of the client request context (`r.Context().Done()`) MUST immediately trigger upstream socket closure and goroutine termination.

4. **Heartbeat, Ping/Pong, and Application Keep-Alive Transparency**:
   - The idle timeout enforcement MUST operate at the byte/frame transfer layer and MUST NOT interfere with application protocols.
   - WebSocket control frames (RFC 6455 Ping and Pong frames), periodic heartbeat messages, and data frames exchanged between client and upstream MUST refresh the idle deadline.
   - Legitimate long-lived WebSocket sessions that exchange periodic heartbeats or ping/pong messages within `UpgradeIdleTimeout` MUST remain active indefinitely without premature termination.

5. **Deterministic Teardown and Graceful Socket Synchronization**:
   - Socket closing across concurrent forwarding directions MUST be synchronized using `sync.Once` (or equivalent safe synchronization primitive) to eliminate race conditions, double-close errors, or panics.
   - When one side encounters a non-timeout error or `io.EOF`, the counterpart connection MUST be closed cleanly, allowing all goroutines associated with the upgraded stream to return.

6. **Runtime Observability and Diagnostic Logging**:
   - When an upgraded connection or stream is terminated due to exceeding `UpgradeIdleTimeout`, the server MUST emit a diagnostic log message (e.g. `[Server] Upgraded connection idle timeout reached (%s), terminating stream`).
   - The log entry MUST include remote peer identifiers (client address and, where available, upstream address) to facilitate operator troubleshooting.
   - Normal, clean terminations (e.g., standard WebSocket Close handshake or peer disconnection) MUST NOT be logged as idle timeout errors.

7. **Zero Third-Party Dependencies & Concurrency Race Invariants**:
   - All components MUST be implemented exclusively with Go standard library packages (`net`, `sync`, `sync/atomic`, `time`, `io`, `fmt`, `log`, `errors`, `net/http`). Zero external dependencies are permitted.
   - All connection tracking, atomic timestamp updates, and socket cleanup routines MUST be completely race-free and pass `go test -race ./pkg/server/... ./pkg/config/...` without data races, deadlocks, or goroutine leaks.
   - Standard HTTP/1.1 request handling, keep-alive pipelining, and non-upgraded responses MUST remain unaffected.

8. **Automated Verification Suite (`TC-088`)**:
   - An automated test suite in `pkg/server/server_test.go` MUST verify:
     a. **Idle Connection Termination**: An idle upgraded HTTP/1.1 connection with no data transmission is terminated automatically after `UpgradeIdleTimeout`, releasing both client and upstream sockets within a tight tolerance window.
     b. **Heartbeat / Active Stream Survival**: An upgraded connection that continuously exchanges data or heartbeats at intervals shorter than `UpgradeIdleTimeout` remains alive beyond the timeout duration without interruption.
     c. **Peer Close Teardown**: Immediate closure by either peer (client or upstream) promptly terminates the opposite socket and completes all relay goroutines.
     d. **HTTP/2 Extended CONNECT Idle Teardown**: An idle RFC 8441 HTTP/2 WebSocket stream terminates after `UpgradeIdleTimeout`.
     e. **Concurrency & Race Freedom**: All upgraded connection lifecycle tests pass under `-race` with no race conditions detected.

## Rationale

Permanently clearing socket deadlines upon protocol switching creates a severe Slowloris vulnerability (CWE-400). An attacker can open thousands of idle WebSocket upgrade handshakes, consuming file descriptors until host limits are reached (`EMFILE`), completely denying service to legitimate API gateway traffic. Introducing a configurable, activity-refreshed `UpgradeIdleTimeout` guarantees deterministic socket reclamation and prevents goroutine leaks while fully supporting legitimate persistent WebSockets via ping/pong heartbeats.
