# AN-003 - System Analysis & Redesign Options for Dashboard Requests (/log) View

## 1. Problem Statement

The user states:
> *"look at the resquests(/log) section of the dashboard. Its listing all the requests received. Soon the list will be ome too long. We need to redesign the page. Use system analyst agent to come up with some options"*

In the Toron Control Center dashboard, the **Requests** view (`#log`, handled by [`public/js/views/logs.js`](../../public/js/views/logs.js)) serves as the primary live telemetry feed for HTTP requests processed by the gateway. 

As the gateway processes real-world production traffic, the current design exhibits significant structural, operational, and user experience limitations:
1. **Unbounded Visual Growth / "Firehose Effect"**: The UI attempts to render individual raw requests in a single flat table. In production environments (hundreds or thousands of requests per second), incoming requests push existing rows downward continuously. Operators trying to inspect a trace or click a row find the target moving out from under their cursor.
2. **Noise vs Signal Drowning**: Routine high-frequency traffic (such as automated container health checks `GET /health` or static assets) clutters the list, obscuring critical slow requests, upstream timeouts, or 4xx/5xx security anomalies.
3. **Absence of Aggregation & Faceting**: There is no top-level summary indicating which endpoints generate the most volume, which routes suffer the highest latency, or which upstreams are failing. Operators must manually sift through individual rows to understand traffic distribution.
4. **Lack of Navigation Controls**: The view lacks pagination, page-size selection, and multi-column sorting (e.g., sorting by Duration to quickly identify bottlenecks).
5. **Buffer Inefficiency**: The backend currently supplies a fixed recent snapshot (`GlobalTraceBuffer.GetRecent(100)`), while the frontend truncates to `slice(0, 70)`, preventing operators from searching or navigating historical requests across time windows.

## 2. Current Architecture & Implementation Inspection

### 2.1 Backend Ring Buffer & API Layer
- **Ring Buffer ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go#L117-L138))**:
  - `GlobalTraceBuffer` is a fixed-capacity circular memory buffer (`DefaultTraceCapacity = 300`).
  - Holds structured `TraceLogEntry` objects including timestamp (`ts`), method, path, route, status code, latency (`ms`), upstream node (`up`), trace ID, client IP, payload bytes, error message, and execution phase waterfall spans (`spans`).
- **Endpoint `GET /internal/api/logs` ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go#L534-L545))**:
  - Executes `GlobalTraceBuffer.GetRecent(100)`.
  - Returns JSON payload: `{ "timestamp": "...", "total": 100, "logs": [...] }`.
  - Does not currently support query parameters (such as `limit`, `offset`, `since`, `status`, `route`, or `search`).

### 2.2 Frontend View Architecture
- **View Module ([`public/js/views/logs.js`](../../public/js/views/logs.js))**:
  - Toolbar contains: Search field (`#lgQ`), status filter chips (`2xx`, `3xx`, `4xx`, `5xx`), "Over SLO" chip (`#lgSlow`), route dropdown (`#lgRoute`), and Pause/Resume tail button (`#lgPause`).
  - Update cycle: On every poll cycle (every 2 seconds) or input event, `lgUpdate` filters `rawApiLogs` by status, route, and text search, sorts primarily by `ts` desc, and writes up to 70 rows into `#lgBody`.
  - Inspection Drawer ([`public/js/components/drawer.js`](../../public/js/components/drawer.js#L35-L60)): Clicking a row opens a slide-out drawer displaying the waterfall span breakdown, headers, trace ID, upstream node, and response payload size.

## 3. Core Functional & Non-Functional Requirements for Redesign

1. **Performance & DOM Stability**:
   - The DOM node count must remain constant and bounded (under 50 rows per page view), regardless of whether 100 or 10,000 requests pass through the gateway.
   - Tail updates must not shift active selections or disrupt user interaction when hovering or inspecting.
2. **Aggregated Insights & Noise Reduction**:
   - Provide summary metrics/facets so operators can immediately see request rates, error distributions, and top/slowest routes at a glance without reading raw logs.
   - Provide noise suppression (e.g., filter out routine `/health` probes or collapse repetitive requests).
3. **Explorability & Sorting**:
   - Multi-column sortable table (sort by Time, Duration/Latency, Status Code, Path).
   - Structured pagination (Page Size selector: 25 / 50 / 100, Next/Previous controls, page number jump).
4. **Preservation of Mobile & Responsive Ergonomics**:
   - Must adhere to the existing design system (IBM Plex fonts, dark/light theme tokens, responsive column hiding on mobile/tablet, slide-out drawer).

### Option 1: Dual-Pane "Analytics & Top Facets + Virtualized / Paginated Live Tail"

* **Description**:
  Combines high-level analytical visibility with a stable, paginated raw request stream:
  1. **Top Analytics Strip**:
     - **Throughput & Status Spark-Histogram**: A compact, responsive bar chart visualizing request volume by status category (2xx green, 4xx amber, 5xx red) across the buffered timeline.
     - **Quick Facet Pills / Summary**: Highlights **Top 3 Endpoints**, **P95 Latency & Slowest Route**, and **Error Rate**. Clicking an endpoint pill immediately filters the table below.
  2. **Stable Paginated Live Stream**:
     - Replaces unconstrained slicing with controlled pagination: **25, 50, or 100 rows per page**.
     - **Stable Tailing**: Incoming requests update the background buffer and histogram; if the user is on Page 1 and tailing is active, rows update smoothly without layout shifts; if paused or browsing Page > 1, the view is completely stationary.
     - **Column Sorting**: Interactive column headers allowing sorting by Duration (`ms` desc), Status, or Time.
* **Pros**:
  - Maximum operational clarity: Operators diagnose problems in seconds by seeing the histogram spikes and facet summaries before even searching logs.
  - Retains full granular trace inspection via the existing drawer.
  - Zero DOM jank; predictable performance.
* **Cons**:
  - Higher UI density; requires careful layout structuring for smaller mobile screens.

---

### Option 2: Two-Mode Segmented View ("Endpoint Rollup" vs "Live Request Stream")

* **Description**:
  Introduces a segmented toggle button in the toolbar allowing operators to switch between two distinct mental models:
  1. **Mode A: Endpoint Rollup (Default)**:
     - Aggregates requests by Route / Endpoint Path (e.g., `/kite/api`, `/kite/callback`, `/health`, `/kite/auth`).
     - Columns: `Method + Path`, `Total Requests`, `RPS`, `p50 Latency`, `p95 Latency`, `Error Rate (4xx / 5xx)`, and `Status Sparkline`.
     - Clicking an endpoint opens a list of recent traces for that specific endpoint or opens the route inspector drawer.
  2. **Mode B: Live Stream**:
     - The detailed chronological request log table, equipped with pagination controls (25 / 50 per page), status filter chips, and search.
* **Pros**:
  - Eliminates noise completely: 90% of operational questions ("is an API degrading?") are answered instantly on the Rollup tab without ever viewing a raw log line.
  - Very clean and uncluttered UI.
* **Cons**:
  - Requires toggling tabs to correlate an endpoint's aggregate latency with an individual request's trace waterfall.

---

### Option 3: High-Fidelity Queryable Ledger with Time Windows & Sorting

* **Description**:
  Transforms the requests view into a structured query ledger (similar to Datadog Log Explorer or AWS CloudWatch Insights):
  1. **Time Window & Expressive Filtering**:
     - Time window selector: `Last 1 min`, `Last 5 mins`, `Last 15 mins`, `All Buffer`.
     - Quick filter buttons: `Errors Only (4xx/5xx)`, `Slow (> 100ms)`, `Non-Health Traffic` (excludes `/health`).
  2. **Sortable Paginated Ledger**:
     - Strict pagination: 25 or 50 items per page with `First`, `Prev`, `Page X of Y`, `Next`, `Last`.
     - Clicking table headers toggles sorting (Time asc/desc, Duration asc/desc, Status asc/desc, Path asc/desc).
     - **Freeze on Hover / Select**: Moving the mouse over the table immediately suspends live tailing so the operator can inspect rows without disruption.
* **Pros**:
  - Highly intuitive for operators accustomed to standard audit ledgers or APM tools.
  - Clean implementation within existing table structures without adding heavy new UI components.
* **Cons**:
  - Does not offer visual histogram / time-series charts on the requests page itself (relies purely on tabular data).

---

### Option 4: Smart Deduplication & In-Place Grouping (Minimalist Refactor)

* **Description**:
  Preserves the single-table layout but introduces smart client-side grouping and deduplication:
  1. **Collapsible Repetitive Traffic**:
     - Consecutive identical requests (e.g. 50 successful `GET /health` requests from the container orchestrator) are collapsed into a single summary row: `GET /health · 200 OK · [50 requests] · Avg: 0.8ms · [Expand ▼]`.
  2. **Fixed Page Size & Freeze-on-Interaction**:
     - Capped at 25 or 50 rows per page with basic Next/Prev buttons.
     - Hovering over a row freezes tailing.
* **Pros**:
  - Minimal code footprint; fastest to implement.
  - Solves the immediate symptom of healthcheck noise and page scrolling.
* **Cons**:
  - Consecutive grouping only works when traffic arrives in homogeneous bursts; interleaved multi-tenant traffic may not collapse cleanly.
  - Lacks higher-level throughput and error rate visualization.

## 5. Comparative Trade-off Matrix

| Criterion | Option 1 (Dual-Pane Facets + Tail) | Option 2 (Endpoint Rollup vs Stream) | Option 3 (Queryable Ledger & Window) | Option 4 (Smart Dedup / Minimal) |
|---|---|---|---|---|
| **Noise Reduction** | High (Facets isolate anomalies) | Very High (Rollup hides raw logs) | High (Filters for non-health/slow) | Moderate (Collapses repeats) |
| **High Traffic Scalability** | Excellent (Paginated + Aggregated) | Excellent (Grouped by route) | Very Good (Paginated) | Good (Buffered cap) |
| **Operational Speed** | Fastest (Visual spikes clickable) | Fast (Metrics first) | Fast (Sort by duration/error) | Moderate (Manual scrolling) |
| **Visual Ergonomics** | Modern APM / Rich | Clean & Structured | Standard Ledger | Compact |
| **Implementation Complexity** | Medium (New facet strip + paging) | Medium (Segmented tabs + rollup) | Low-Medium (Paging + sort headers) | Low (Deduplication + paging) |
| **Mobile Responsiveness** | Good (Facets wrap vertically) | Excellent (Tabbed view fits mobile) | Excellent (Standard table) | Excellent |
| **Zero-Dependency Budget** | Maintained (Native SVG/DOM) | Maintained (Native DOM) | Maintained (Native DOM) | Maintained (Native DOM) |

## 6. System Analyst Recommendation

**Recommended Approach: Option 1 (Dual-Pane "Analytics & Top Facets + Paginated Live Tail")**, with elements of Option 3:
1. **Top Analytics Strip**:
   - A mini SVG status-code distribution histogram (2xx, 4xx, 5xx volume bars across recent seconds/minutes).
   - Quick actionable facets:
     - **Top Routes by Volume** (clicking a route sets the filter).
     - **Slowest Requests / P95 Latency**.
     - **Quick Filter Chips**: `All`, `2xx`, `3xx`, `4xx`, `5xx`, `Over SLO`, and `Exclude Health (/health)`.
2. **Paginated & Interactive Request Table**:
   - Fixed page sizes: `25`, `50`, or `100` rows per page.
   - Interactive column sorting (click column header to sort by Duration, Status, Time, or Path).
   - "Freeze on Hover" so live updates do not disrupt row selection or drawer inspection.
   - Retain full trace waterfall drawer for drill-down.

This provides the best balance of immediate executive insight, noise suppression, high-traffic stability, and granular trace inspection.
