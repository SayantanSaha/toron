# SR-071 - Security Review of HTTP Header Field-Name Whitespace Rejection (RFC 7230 §3.2.4)

## Description

Security evaluation of the implementation for `TASK-073` / `SEC-14` (HTTP header field-name whitespace smuggling vulnerability).

## Scope

- Files reviewed:
  - `pkg/httpparser/parser.go`
  - `pkg/httpparser/parser_test.go`

## Security Evaluation & Analysis

1. **RFC 7230 §3.2.4 Compliance**:
   - RFC 7230 §3.2.4 explicitly mandates that no whitespace is permitted between the header field-name and colon, and any request violating this rule MUST be rejected with `400 Bad Request`.
   - In `pkg/httpparser/parser.go`, `k := lineTrimmed[:colonIdx]` is checked for empty string or presence of `" \t\r\n"`.
   - If whitespace exists, the parser returns `fmt.Errorf("%w: whitespace in header field-name", ErrBadRequest)`.
2. **Neutralization of Request Smuggling Vectors**:
   - Attacks exploiting `Transfer-Encoding : chunked` or `Host\t: example.com` are caught immediately during header line tokenization.
   - The server closes the underlying connection (`Connection: close`), preventing socket desynchronization or pipelined smuggle payloads from polluting subsequent requests.
3. **Exploit Verification**:
   - Verified that `Transfer-Encoding : chunked` is rejected with `ErrBadRequest`.
   - Verified that `Host\t: example.com` is rejected with `ErrBadRequest`.
   - Verified that leading whitespace on header lines (` Host: ...`) and empty header names (`: ...`) are safely rejected.
   - Verified that valid header values containing whitespace (`X-Custom:  value with spaces  `) continue to be parsed accurately with trimmed field values.

## Conclusion

`SEC-14` is fully mitigated. The implementation adheres strictly to RFC 7230 §3.2.4 and eliminates header whitespace smuggling. Approved.
