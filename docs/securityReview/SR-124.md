# SR-124 - Security Review of Configurable Distributed Tracing in Reverse Proxy Transport Engine

## 1. Executive Summary

A rigorous security audit was conducted on the implementation of configurable distributed tracing under [`REQ-124`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-124.md) and [`ADR-124`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-124.md).

The change allows disabling automated W3C traceparent generation for raw-speed performance while preserving cryptographically secure W3C Trace Context generation when enabled.

**Verdict**: **APPROVED (0 Vulnerabilities, 0 Security Regressions, High Concurrency Safe)**.

---

## 2. Threat Modeling & Vulnerability Analysis

### 2.1 CWE-330: Use of Insufficiently Random Values
- **Threat**: If a non-cryptographic pseudo-random number generator (e.g. `math/rand`) were introduced to accelerate trace ID generation, attackers could predict future trace IDs and correlate sessions across tenants.
- **Analysis**: Toron does **not** replace `crypto/rand` with an insecure PRNG. Instead, when `tracing: false`, Toron completely suppresses trace generation. When `tracing: true`, Toron continues using `crypto/rand.Read` in `pkg/metrics/tracing.go`, guaranteeing 128 bits of cryptographic entropy for `trace_id` and 64 bits for `span_id`.
- **Verdict**: Fully mitigated.

### 2.2 CWE-400: Uncontrolled Resource Consumption (CSPRNG System Call Starvation)
- **Threat**: Under high-concurrency saturation loads (24.5k+ RPS), unconditional invocation of `crypto/rand.Read` on every HTTP request forces ~49,000 OS system calls per second (`getrandom` / `/dev/urandom`), causing kernel context switches and mutex lock contention in Go runtime.
- **Analysis**: Configurable tracing (`tracing: false` in `raw_speed` profile) neutralizes this resource drain completely without sacrificing protocol security.
- **Verdict**: Significant resilience enhancement.

### 2.3 CWE-113: HTTP Response / Request Splitting & CRLF Injection
- **Threat**: If untrusted client `traceparent` headers are forwarded without validation when `tracing: false`, could malicious CRLF sequences be injected into upstream requests?
- **Analysis**: Incoming request headers are strictly sanitized by `httpparser.ParseRequest` ([`pkg/httpparser/request.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go)) and CRLF-validated before being added to `outReq`.
- **Verdict**: No header injection risk.

## 3. Verification & Conclusion

Automated race detection (`go test -race ./pkg/...`) confirms clean concurrency. All security controls are preserved.
