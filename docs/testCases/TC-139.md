# TC-139 - Test Specification for Disaggregated Upstream Route Pooling and Live Telemetry Metric Derivation in Dashboard

## 1. Verification Scope & Objectives

### 1.1 Scope
This document specifies the verification strategy, test suites, execution procedures, and pass/fail criteria for the Toron Edge Gateway Control Center dashboard ([`public/app.js`](../../public/app.js)). It verifies the resolution of the Upstream Route Collapse Anti-Pattern and Telemetry Field Mismatch defects specified in [`REQ-139`](../requirements/REQ-139.md), designed in [`ADR-139`](../architecture/ADR-139.md), and implemented in [`TASK-162`](../tasks/TASK-162.md).

### 1.2 Verification Goals
1. **Upstream Route Disaggregation**: Ensure that distinct ingress proxy routes sharing a physical backend socket (`127.0.0.1:8080`) are rendered as isolated, independent pool cards without route conflation or omission.
2. **Exhaustive Route Coverage**: Ensure that unmapped proxy routes are created as independent fallback pools with passive health checking.
3. **Telemetry Alignment & Live Metric Derivation**: Ensure that instantaneous route throughput (RPS), p95 latency, and 5xx error rates are dynamically derived from live backend payloads ([`pkg/metrics/metrics.go`](../../pkg/metrics/metrics.go) and `/internal/api/upstreams/health`) without static fallbacks (`0.0/s`, `2.5 ms`, `0.0%`).
4. **Health State & Circuit Breaker Visibility**: Ensure that probe degradation, 5xx HTTP responses, and `UNREACHABLE` statuses trigger visual tone escalation (`ok` $\rightarrow$ `warn` $\rightarrow$ `err`) and alert dispatch.
5. **Cross-View Visual Parity**: Guarantee rendering parity between the Upstreams card grid (`#/upstreams`), the Overview SVG Sankey traffic flow diagram (`#/overview`), and the Routes table (`#/routes`).
6. **Defensive Robustness & Performance Budget**: Verify sub-2ms model transformation ($\mathcal{O}(R + U)$) and zero runtime exceptions under cold-start, missing field, or zero-request conditions.

## 3. Comprehensive Test Case Specifications

### TC-139-01: Distinct Upstream Route Pool Rendering for Shared Target IP:Port
- **Test ID**: `TC-139-01`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-1, FR-2, FR-3), [`TASK-162`](../tasks/TASK-162.md) (3.1), [`ADR-139`](../architecture/ADR-139.md) (3.1)
- **Category**: Functional Verification / Data Adapter & DOM Component
- **Objective**: Verify that multiple proxy routes configured with the exact same backend socket (`http://127.0.0.1:8080`) produce distinct, isolated upstream pool cards and are not collapsed into the first declared route.
- **Preconditions**:
  - `rawApiRoutes` contains Fixture 1 (routes `/kite/callback`, `/kite/api`, `/kite/broker`, `/kite/auth`).
  - `rawApiUpstreams` contains Fixture 2 (probes for each of the 4 routes).
  - `rawApiStatus` contains Fixture 3.
- **Execution Procedure**:
  1. Initialize test environment and load `public/app.js` data adapter functions.
  2. Invoke `buildDataModel()`.
  3. Inspect `D.pools` array returned by the model builder.
  4. Invoke `upUpdate(D)` to generate the DOM tree inside `#poolGrid`.
- **Expected Results & Assertions**:
  1. `D.pools.length` MUST be $\ge 4$ (at least 4 pools for the 4 Kite routes, plus any unmapped routes).
  2. The pool map MUST contain 4 distinct keys: `_kite_callback`, `_kite_api`, `_kite_broker`, `_kite_auth`.
  3. Pool `_kite_callback` MUST NOT contain routes `_kite_api`, `_kite_broker`, or `_kite_auth` in its `routes` array. Each pool must isolate its specific route:
     ```javascript
     assert.strictEqual(poolCallback.routes.length, 1);
     assert.strictEqual(poolCallback.routes[0].id, '_kite_callback');
     assert.strictEqual(poolApi.routes.length, 1);
     assert.strictEqual(poolApi.routes[0].id, '_kite_api');
     assert.strictEqual(poolBroker.routes.length, 1);
     assert.strictEqual(poolBroker.routes[0].id, '_kite_broker');
     assert.strictEqual(poolAuth.routes.length, 1);
     assert.strictEqual(poolAuth.routes[0].id, '_kite_auth');
     ```
  4. In the rendered DOM (`#poolGrid`):
     - Distinct card containers MUST exist: `#pool-_kite_callback`, `#pool-_kite_api`, `#pool-_kite_broker`, `#pool-_kite_auth`.
     - Card `#pool-_kite_callback` header MUST display `Match: sayantansaha.in /kite/callback`.
     - Card `#pool-_kite_api` header MUST display `Match: sayantansaha.in /kite/api`.
     - Card `#pool-_kite_broker` header MUST display `Match: sayantansaha.in /kite/broker`.
     - Card `#pool-_kite_auth` header MUST display `Match: sayantansaha.in /kite/auth`.
  5. Route header chips MUST display their respective service tags (`X-Service=kite-callback`, `X-Service=kite-api`, etc.).
- **Pass/Fail Criteria**: Passes if all 4 pool cards render independently with discrete route metadata and zero route absorption.

### TC-139-02: Fallback Route Pool Creation for Unmapped Upstream Routes

     ```javascript
     const p = D.pools.find(p => p.id === '_kite_orders');

     assert.strictEqual(p.insts[0].history.length, 48);
     ```
  3. DOM element `#pool-_kite_orders` MUST exist in `#poolGrid`.
- **Pass/Fail Criteria**: Passes if unmapped proxy routes are 100% visible in the Upstreams view with passive health check markers.

### TC-139-03: Dynamic Real-Time RPS Derivation from Telemetry
- **Test ID**: `TC-139-03`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-5, FR-6, FR-7), [`TASK-162`](../tasks/TASK-162.md) (3.2), [`ADR-139`](../architecture/ADR-139.md) (3.2)
- **Category**: Quantitative / Math Verification & Schema Alignment
- **Objective**: Verify that route and pool throughput (RPS) are dynamically calculated from `rawApiStatus.metrics.requests_by_route` and `rawApiStatus.timeseries.A.rps`, replacing static `0.0/s` placeholders.
- **Preconditions**:
  - `rawApiStatus` contains Fixture 3:
    - `timeseries.A.rps` latest bucket $= 120.0$ req/s.
    - `metrics.total_requests` $= 10,000$.
    - `metrics.requests_by_route`:
      - `"/kite/callback"`: $5,000$ (50%)
      - `"/kite/api"`: $3,000$ (30%)
      - `"/kite/broker"`: $2,000$ (20%)
      - `"/kite/auth"`: $0$ (0%)
- **Execution Procedure**:
  1. Call `buildDataModel()`.
  2. Inspect derived `cur.rps` on each route in `D.routes`.
  3. Inspect derived `rps` on each pool in `D.pools`.
  4. Call `upUpdate(D)` and inspect DOM rendered text in `<dl class="pool-sum">`.
- **Expected Mathematical Calculations**:
  $$\text{curRPS}(r) = \text{total\_rps} \times \left(\frac{\text{requests\_by\_route}[r.\text{prefix}]}{\text{total\_requests}}\right)$$
  - `/kite/callback`: $120.0 \times \frac{5000}{10000} = 60.0 \text{ req/s}$
  - `/kite/api`: $120.0 \times \frac{3000}{10000} = 36.0 \text{ req/s}$
  - `/kite/broker`: $120.0 \times \frac{2000}{10000} = 24.0 \text{ req/s}$
  - `/kite/auth`: $120.0 \times \frac{0}{10000} = 0.0 \text{ req/s}$
- **Expected Results & Assertions**:
  1. Route RPS:
     ```javascript
     const rCb = D.routes.find(r => r.path === '/kite/callback');
     const rApi = D.routes.find(r => r.path === '/kite/api');
     const rBr = D.routes.find(r => r.path === '/kite/broker');
     const rAu = D.routes.find(r => r.path === '/kite/auth');

     assert.strictEqual(rCb.cur.rps, 60.0);
     assert.strictEqual(rApi.cur.rps, 36.0);
     assert.strictEqual(rBr.cur.rps, 24.0);
     assert.strictEqual(rAu.cur.rps, 0.0);
     ```
  2. Conservation of Throughput:
     $$\sum_{r \in \text{routes}} \text{curRPS}(r) = 60.0 + 36.0 + 24.0 + 0.0 = 120.0 = \text{total\_rps}$$
  3. Pool Requests Header:
     - Pool `_kite_callback` `<dd>` MUST contain `60/s` or `60.0/s`.
     - Pool `_kite_api` `<dd>` MUST contain `36/s` or `36.0/s`.
     - Pool `_kite_broker` `<dd>` MUST contain `24/s` or `24.0/s`.
     - Pool `_kite_auth` `<dd>` MUST contain `0.0/s`.
  4. Elimination of Static Defaults: None of the active routes (`/kite/callback`, `/kite/api`, `/kite/broker`) display static `0.0/s`.
- **Pass/Fail Criteria**: Passes if derived throughput matches mathematical proportions with zero deviation and updates pool headers accurately.

### TC-139-05: Dynamic p95 Latency Derivation Without Static Fallbacks
- **Test ID**: `TC-139-05`
- **Verifies**: [`REQ-139`](../requirements/REQ-139.md) (FR-9), [`TASK-162`](../tasks/TASK-162.md) (3.3), [`ADR-139`](../architecture/ADR-139.md) (3.3)
- **Category**: Functional / Fallback Elimination
- **Objective**: Verify that the pool summary p95 latency (`p.p95`) and route p95 latency (`r.cur.p95`) are dynamically derived from active probe latencies or time-series percentiles, completely eliminating the static `2.5 ms` constant when live measurements exist.
- **Test Sub-Scenarios**:
  - **TC-139-05a (Probe Latencies Available)**:
    - Route has active health probe with `latency_ms = 18.75`.
    - Assertion: Derived `r.cur.p95` equals `18.75` (or matches probe latency), and pool `p.p95` equals `18.75`. Neither evaluates to `2.5`.
  - **TC-139-05b (Probe Latency Absent, Gateway Time-Series Available)**:
    - Route has no probe latency (`latency_ms: 0` or missing).
    - Gateway time-series has `rawApiStatus.timeseries.A.p95 = [..., 14.8]`.
    - Assertion: Derived latency incorporates `14.8 ms` from time-series buffer. Header renders `15 ms` or `14.8 ms`, not `2.5 ms`.
  - **TC-139-05c (Cold Start Initial Nominal Fallback)**:
    - Both probe latencies and time-series are empty (`timeseries.A.p95 = []`, `latency_ms = 0`).
    - Assertion: Data model safely falls back to default initial `2.5 ms` without producing `NaN`, `undefined`, or exceptions.
- **Pass/Fail Criteria**: Passes if static `2.5 ms` is strictly suppressed whenever live probe or time-series telemetry is present.

### TC-139-06: Dynamic Error Rate Calculation and Visual Tone Escalation

- **Category**: Behavioral / Health State & Visual Escalation
- **Objective**: Verify that upstream node failures, probe errors (`UNREACHABLE`), and HTTP 5xx responses correctly classify instance health (`down`), derive non-zero error rates, and escalate visual tone from `ok` to `warn` or `err`.
- **Preconditions**:
  - Route `/kite/broker` in Fixture 2:
