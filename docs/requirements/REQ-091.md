# REQ-091 - Direct Parameterized Subpath Routing and Elimination of Empty Prefix Proxy in REST-to-gRPC Transcoder

## 1. Context & Business Value

Toron Edge Gateway features a native, zero-dependency REST-to-gRPC Transcoding Engine ([`pkg/transcoder`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder)). In real-world microservice deployments, clients access RESTful endpoints with URL path parameters, such as `GET /v1/users/:id` or `GET /v1/orgs/:orgId/users/:userId`.

During security audit review [`SR-081 Finding 8`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-081.md#L185-L202) and [`SEC-30`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L411-L419) ([CWE-284 Improper Access Control](https://cwe.mitre.org/data/definitions/284.html), [CWE-400 Uncontrolled Resource Consumption / Denial of Service](https://cwe.mitre.org/data/definitions/400.html)), a critical subpath routing bug was discovered in [`pkg/transcoder/transcoder.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L68-L94):
- In `Engine.registerRoutes()`, the engine invokes:
  ```go
  _ = e.router.RoutePrefix("upstream", "", cleanPrefix, nil, "", proxy.ProxyOptions{})
  e.router.Handle(rRule.HTTPMethod, cleanPrefix, handler)
  ```
- `RoutePrefix` registers an upstream reverse proxy with empty `ProxyOptions` (zero targets) for `cleanPrefix` (e.g. `/v1/users`). Meanwhile, `e.router.Handle` registers `handler` exclusively for the exact string `cleanPrefix`.
- When an incoming request for a parameterized subpath arrives (e.g. `GET /v1/users/usr-123` via `router.ServeHTTP`):
  1. Exact path match in `r.routes["/v1/users/usr-123"]` fails.
  2. Router falls back to `r.prefixRoutes`, matching the empty upstream proxy on `/v1/users`.
  3. The empty proxy executes and immediately terminates with `HTTP 502 Bad Gateway: No upstream target available`.
  4. The actual transcoder handler (`HandleTranscode`) is never reached.

Remediating `SEC-30` ensures that parameterized REST-to-gRPC requests are directly and deterministically routed to `HandleTranscode` through the edge router, completely eliminating the dummy empty upstream proxy and false 502 errors.

## 2. Requirements & Acceptance Criteria

### REQ-091-AC-01: Elimination of Empty Upstream Proxy Registration
- [`Engine.registerRoutes()`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L68) MUST NEVER invoke `r.RoutePrefix("upstream", ...)` with empty `ProxyOptions`.
- Zero dummy or empty upstream proxies shall be registered on the router by the transcoding engine.

### REQ-091-AC-02: Method-Aware & Pattern-Matching Prefix Routing on Router
- The edge router ([`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go)) MUST provide support for registering prefix handlers with HTTP method gating and optional path pattern matchers (`HandlePrefixWithMatcher` / `HandlePrefix`).
- In [`Router.ServeHTTP`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L453):
  - When matching `prefixRoutes`, if `pr.method != ""`, requests with differing HTTP methods must be bypassed, preserving method segregation across routes sharing the same prefix.
  - If a route provides a custom `matcher func(path string) bool`, requests shall only dispatch to `pr.handler` if `matcher(req.Path)` evaluates to `true`.
  - If a prefix matches but no route accepts the request HTTP method, the router shall respond with `405 Method Not Allowed`.

### REQ-091-AC-03: Deterministic Parameterized Subpath Dispatch via `router.ServeHTTP`
- When an incoming request matching a parameterized route pattern (e.g. `GET /v1/users/:id`) arrives at [`Router.ServeHTTP`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L453) with path `/v1/users/usr-777`:
  - It MUST route directly to the transcoding handler.
  - `HandleTranscode` MUST extract `id = "usr-777"`, build the gRPC frame, forward to upstream, and return `200 OK` (not `502 Bad Gateway`).

### REQ-091-AC-04: Multi-Route Segregation & Pattern Length Containment
- Requests matching the prefix of a parameterized route but having differing segment counts or invalid literals (e.g. `GET /v1/users` or `GET /v1/users/usr-777/extra/extra` when only `/v1/users/:id` is registered) MUST NOT accidentally match or trigger corrupted gRPC frames.
- Distinct routes sharing identical prefixes (e.g. `GET /v1/users/:id` and `GET /v1/users/:id/orders/:orderId`) MUST route to their respective distinct gRPC RPCs without shadowing or collision.

### REQ-091-AC-05: Non-Parameterized Exact Route Compatibility
- Non-parameterized routes (e.g. `POST /v1/users` or `GET /v1/health`) MUST register directly as exact routes on [`Router.Handle`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L105), maintaining maximum lookup performance and zero prefix overhead.

### REQ-091-AC-06: Verification & Race Safety
- All new and existing routing pathways must execute cleanly with zero data races under `go test -race ./...`.
- Automated tests verifying parameterized dispatch through `router.ServeHTTP` (`TestTranscoder_ParameterizedSubpathDispatch`) MUST be implemented.

### REQ-091-AC-07: Zero Third-Party Dependencies Invariant
- All routing and pattern matching logic must strictly use Go standard library packages (`strings`, `net/http`, `sync`, `net/url`).
