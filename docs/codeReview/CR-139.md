# CR-139 - Code Review for Distinct Upstream Route Pool Rendering, Hierarchical Telemetry Aggregation, and Live Metric Derivation

## 1. Executive Summary

This code review evaluates the updated v1.1 implementation of disaggregated upstream route pool rendering, hierarchical subpath telemetry aggregation, internal polling isolation, moving average temporal smoothing, and live metric derivation across the Toron Control Center dashboard ([`public/app.js`](../../public/app.js)), the upstream health monitoring endpoint ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go)), and the automated test verification suite ([`tests/dashboard_telemetry_test.js`](../../tests/dashboard_telemetry_test.js)).

The implementation resolves six interconnected operational observability defects specified in [`REQ-139`](../requirements/REQ-139.md) (v1.1), architected in [`ADR-139`](../architecture/ADR-139.md) (v1.1), decomposed in [`TASK-162`](../tasks/TASK-162.md) (v1.1), and verified by [`TC-139`](../testCases/TC-139.md) (v1.1):
1. **Upstream Route Collapse Anti-Pattern**: Distinct proxy routes targeting the same backend socket (e.g. `/kite/callback`, `/kite/api`, `/kite/broker`, `/kite/auth` proxying to `http://127.0.0.1:8080`) were previously conflated into the first declared route on both server and client.
2. **Telemetry Field Mismatch & Static Fallbacks**: Lookups against non-existent metric properties (`by_route`, `rate_per_sec`, `latency_p95_ms`, `err_rate`) caused route and pool cards to silently fall back to static constants (`0.0/s`, `2.5 ms`, `0.0%`).
3. **Subpath Fragmentation in Telemetry**: Because [`pkg/router/router.go`](../../pkg/router/router.go) records requests keyed by full incoming request path, querying only the exact prefix `requests_by_route[r.prefix]` dropped legitimate subpath traffic (e.g. `/kite/api/v1/business`, `/kite/api/v1/trades`, `/kite/api/v1/auth`).
4. **Internal Polling Dilution of External Throughput**: High-volume internal dashboard polling requests targeting `/internal/api/*` (>91% of total recorded requests) diluted the external route traffic ratio, falsely rounding external RPS down to `0.0/s`.
5. **Instantaneous RPS Oscillation**: Bursty 2-second polling intervals caused instantaneous `tsA.rps` points to alternate between 0 and 6 req/s.
6. **Lack of Cumulative Volume Visibility**: Operators viewing idle backends (`0.0/s`) had no visibility into whether a service was healthy and routed, or unrouted and missing telemetry.

## 2. Review Scope

The scope of this code review covers all modified files and components:
- **Server Upstream Health Endpoint** ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go)):
  - Route-scoped target deduplication (`key := fmt.Sprintf("%s|%s", rInfo.Prefix, cleanTarget)`) in `handleUpstreamHealth`, preventing server-side drop of multiple routes targeting the same socket.
  - Route label attachment (`routeLabel := rInfo.Prefix` or `fmt.Sprintf("%s%s", rInfo.Host, rInfo.Prefix)`), exporting distinct probe entries for each proxy route.
- **Frontend Controller** ([`public/app.js`](../../public/app.js)):
  - `buildDataModel()`:
    - Route-first probe matching prioritizing explicit route labels (`u.route`) over socket target addresses.
    - Unique route-scoped pool key generation (`poolKey = primaryRoute.id`).
    - Exhaustive fallback route loop for unmapped proxy routes.
    - Hierarchical subpath prefix aggregation helper `getRouteTotalReqs(prefix)` rolling up nested paths (`k === prefix || k.startsWith(prefix + '/')`).
    - Internal polling exclusion calculating `totalExternalRequests` by stripping all `/internal/` keys from the traffic denominator.
    - Temporal smoothing via trailing 5-sample moving average gateway RPS (`avg(tsA.rps.slice(-5))`).
    - Proportional route throughput derivation (`curRPS = effectiveTotalRps * (routeCumulative / totalExternalRequests)`).
    - Upstream pool aggregation summing both live rate (`p.rps`) and cumulative volume (`p.totalReqs`).
    - Instance health state classification (`down`, `up`, `warn`) and dynamic 5xx error rate calculation from probe history ticks.
    - Dynamic pool p95 latency derivation from active probe measurements.
  - `poolCard(p)`:
    - Dual rate and cumulative volume rendering in the Requests metric: `${fmt.n(p.rps)}/s ${p.totalReqs > 0 ? '(' + fmt.n(p.totalReqs) + ' total)' : ''}`.
    - Instance row latency bound directly to `u.latency_ms` formatted to one decimal place.
    - Visual tone escalation (`ok` $\rightarrow$ `warn` $\rightarrow$ `err`) and circuit breaker alert notices.
  - `flow(host, D)`:
    - Overview Sankey traffic flow diagram disaggregating route-to-pool ribbons and carrying error tones.
  - `rtUpdate(D)`:
    - Routes view table displaying live sparklines, derived metrics, and multi-level column sorting.
- **Automated Verification Suite** ([`tests/dashboard_telemetry_test.js`](../../tests/dashboard_telemetry_test.js)):
  - Headless Node.js VM sandbox with simulated DOM interfaces.
  - Test cases TC-139-01 through TC-139-13 covering all functional, architectural, edge-case, and non-functional requirements.

## 4. Detailed Technical Findings

### Finding 1: Upstream Route Disaggregation on Shared Sockets (FR-1, FR-2, FR-3, FR-4)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  1. **Server-Side Disaggregation** ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go)):
     In `handleUpstreamHealth`, target deduplication was updated to key on both route prefix and socket address:
     ```go
     key := fmt.Sprintf("%s|%s", rInfo.Prefix, cleanTarget)
     if seenTargets[key] {
         continue
     }
     seenTargets[key] = true
     ```
     This ensures that multiple routes pointing to `127.0.0.1:8080` each emit an independent `UpstreamNodeHealth` record with their respective `route` label.
  2. **Client-Side Route-First Matching** ([`public/app.js`](../../public/app.js)):
     In `buildDataModel()`, probe records are matched against configured routes by explicit route label first, falling back to socket addresses only if route matching yields zero results:
     ```javascript
     const routeMatches = routes.filter(r => {
       if (!u.route) return false;
       return r.short === u.route || r.path === u.route || (r.host + r.path) === u.route ||
              r.short.includes(u.route) || (r.host + r.path).includes(u.route) ||
              u.route.includes(r.path) || u.route.includes(r.short);
     });
     ```
     Pool keys are generated from `primaryRoute.id` (sanitized alphanumeric route ID), and the exhaustive fallback loop instantiates cards for any unmapped proxy routes (e.g. `/kite/orders`).
- **Verification**: Verified by `TC-139-01` and `TC-139-02`. All 4 Kite routes sharing `127.0.0.1:8080` render discrete pool cards with route-specific headers, match paths, and headers summaries.

### Finding 2: Hierarchical Subpath Rollup & Prefix Aggregation (FR-5, FR-6)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  Because [`pkg/router/router.go`](../../pkg/router/router.go) records requests keyed by full request path, exact prefix lookup (`requests_by_route[r.prefix]`) previously returned `0` or `1`. In `public/app.js`, `buildDataModel()` now implements hierarchical aggregation:
  ```javascript
  const prefix = r.prefix || path;
  function getRouteTotalReqs(pfx) {
    if (!pfx) return 0;
    if (pfx === '/') {
      return Object.entries(reqByRoute).reduce((acc, [k, count]) => {
        if (!k.startsWith('/internal/')) return acc + (Number(count) || 0);
        return acc;
      }, 0);
    }
    return Object.entries(reqByRoute).reduce((acc, [k, count]) => {
      if (k === pfx || k.startsWith(pfx + '/')) {
        return acc + (Number(count) || 0);
      }
      return acc;
    }, 0);
  }
  const routeCumulative = getRouteTotalReqs(prefix);
  ```
  The condition `k === pfx || k.startsWith(pfx + '/')` strictly aggregates nested subpaths (e.g. `/kite/api/v1/business` [1800], `/kite/api/v1/trades` [800], `/kite/api/v1/auth` [400]) into `/kite/api` (totaling 3000), while safely rejecting sibling prefixes (e.g. `/kite/api-v2/other`).
- **Verification**: Verified by `TC-139-03`. Route `/kite/api` evaluates to exactly 3000 cumulative requests, `/kite/callback` to 5000, `/kite/broker` to 2000, and `/kite/auth` to 0.

### Finding 3: Internal Telemetry Polling Isolation & Denominator Normalization (FR-7)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  Over 91% of recorded gateway requests in production are internal dashboard polling calls (`/internal/api/status`, `/internal/api/routes`, etc.). In `public/app.js`, the throughput ratio denominator strips all internal endpoints:
  ```javascript
  const totalExternalRequests = Object.entries(reqByRoute).reduce((acc, [k, count]) => {
    if (!k.startsWith('/internal/')) {
      return acc + (Number(count) || 0);
    }
    return acc;
  }, 0);
  ```
  In the fixture (58,500 total requests, of which 48,500 are internal), `totalExternalRequests` evaluates to exactly 10,000. Each external route receives its true proportional traffic share (e.g. `/kite/api` receives $3000 / 10000 = 30\%$) rather than being diluted by an order of magnitude against internal polling volume.
- **Verification**: Verified by `TC-139-04`. Proportional traffic calculation and boundary conditions (when 100% of requests are internal) execute cleanly without `NaN`.

### Finding 4: Temporal Smoothing via Trailing Moving Average Gateway RPS (FR-8)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  To eliminate 2-second dashboard polling oscillation (where instantaneous `tsA.rps[last]` alternates between 0 and 6 req/s), gateway throughput is computed as a 5-point trailing moving average:
  ```javascript
  const recentRpsSamples = (tsA && tsA.rps && tsA.rps.length > 0) ? tsA.rps.slice(-5) : [];
  const avgRecentRps = recentRpsSamples.length > 0 ? avg(recentRpsSamples) : 0;
  const effectiveTotalRps = avgRecentRps > 0 ? avgRecentRps : totalRPS;
  ```
  Route RPS is then computed as:
  ```javascript
  let curRPS = 0;
  if (totalExternalRequests > 0 && effectiveTotalRps > 0) {
    curRPS = effectiveTotalRps * (routeCumulative / totalExternalRequests);
  } else if (effectiveTotalRps > 0 && rawApiRoutes.length > 0) {
    curRPS = effectiveTotalRps / rawApiRoutes.length;
  }
  ```
- **Verification**: Verified by `TC-139-05`. Evaluated across active traffic (120 req/s), low-traffic oscillation (`[0, 6, 0, 6, 0]` $\rightarrow$ 2.4 req/s), and short arrays (< 5 samples).

### Finding 5: Dual Rate and Cumulative Volume Display in Pool Cards (FR-9)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  1. Both live rate and total historical volume are aggregated across pool routes:
     ```javascript
     const rps = sum(rs.map(r => r.cur.rps));
     const totalReqs = sum(rs.map(r => r.totalReqs || (r.cur && r.cur.totalReqs) || 0));
     ```
  2. In `poolCard(p)`, the Requests metric renders both dimensions:
     ```javascript
     <div>
       <dt>Requests</dt>
       <dd>${fmt.n(p.rps)}/s ${p.totalReqs > 0 ? `<span class="mut" style="font-size:11px;font-weight:400">(${fmt.n(p.totalReqs)} total)</span>` : ''}</dd>
     </div>
     ```
  For active routes, this renders e.g. `60/s (5.0k total)` or `36/s (3.0k total)`. For an idle service with historical traffic, this renders `0.0/s (1.7k total)`, immediately verifying that the route is functional and routed. For a brand new route with 0 requests, `(0 total)` is cleanly suppressed.
- **Verification**: Verified by `TC-139-06`.

### Finding 6: Dynamic Probe Latency Binding & Percentile Derivation (FR-10, FR-11)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  - In `poolCard(p)`, instance latency formats `i.latency` (derived from `/internal/api/upstreams/health` `u.latency_ms`):
    ```javascript
    <span>Latency: <b>${(i.latency && i.latency > 0) ? i.latency.toFixed(1) + ' ms' : fmt.ms(p.p95)}</b></span>
    ```
  - Pool p95 latency dynamically selects `Math.max(...activeProbeLats)` or route average / time-series p95, eliminating the static `2.5 ms` constant when real measurements exist.
- **Verification**: Verified by `TC-139-07` and `TC-139-08`.

### Finding 7: Health State, Error Rate & Tone Escalation (FR-12, FR-13, FR-14)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  - Instance health state evaluates both probe status strings and HTTP codes:
    ```javascript
    const isDown = u.status === 'UNREACHABLE' || u.status === 'DOWN' || (u.http_code && u.http_code >= 500);
    const isUp = (u.status === 'HEALTHY' || u.status === 'UP') && (!u.http_code || u.http_code < 400);
    const instState = isDown ? 'down' : (isUp ? 'up' : 'warn');
    ```
  - Failing probes trigger `down` status, calculate probe failure ratios from `i.history`, escalate pool tone to `err`, and inject the circuit-breaker alert notice into the card.
- **Verification**: Verified by `TC-139-09`. Unreachable broker pool displays red status pills, 25.0% error rate, and triggers critical upstream alerts in `D.alerts`.

### Finding 8: Overview Flow Sankey Parity & Routes View Parity (FR-15, FR-16)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  - In `flow(host, D)`, pool nodes are derived from `D.pools`, and route matching connects ribbons to their specific upstream pool blocks. Failing pools route ribbons with `class="rb err"`.
  - In `rtUpdate(D)`, the Routes table renders live sparklines, derived `cur.rps`, `cur.p95`, `cur.err5`, and supports multi-level sorting.
- **Verification**: Verified by `TC-139-11` and `TC-139-12`.

### Finding 9: Automated Verification Suite (TC-139-01 to TC-139-13)
- **Severity**: Informational / Verified
- **Implementation Detail**:
  [`tests/dashboard_telemetry_test.js`](../../tests/dashboard_telemetry_test.js) establishes a lightweight Node.js virtual machine sandbox executing `public/app.js` with simulated DOM interfaces. It systematically verifies all 13 test cases from [`TC-139`](../testCases/TC-139.md), including edge conditions (cold startup, missing metric objects, division-by-zero guards) and a 100-iteration performance benchmark.
