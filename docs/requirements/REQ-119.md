# REQ-119 - Benchmark Result Retention and Historical Run Manifest Architecture

## 1. Description & Problem Statement

### 1.1 Executive Summary & Problem Context
The Toron research evaluation suite comprises six rigorous benchmarking and validation subsystems:
1. HTTP parser microbenchmarks (`testing.B`, `microbenchmarks.raw.txt`).
2. High-throughput and tail-latency evaluation (`wrk2`/`loadgen.go`, `benchmark_c100_r5000.json`, `.csv`, `.raw.txt`).
3. High-concurrency saturation stress testing with adversarial injection (`run_saturation_stress.sh`, `saturation_stress_report.json`, `.md`).
4. Differential protocol security fuzzer (`run_fuzzer.sh`, `diff_fuzzer.go`, `differential_fuzz_report.json`, `.md`).
5. Heterogeneous multi-hop origin testbed (`run_multihop.sh`, `runner.go`, `multihop_report.json`, `.md`).
6. Controlled ablation experiment suite (`run_ablation.sh`, `ablation_study_report.json`, `.md`).

Prior to this requirement, both the master orchestrator ([`benchmarks/run_all.sh`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/run_all.sh)) and individual harness scripts wrote benchmark artifacts directly into the root directory [`benchmarks/results/`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/results/), unconditionally overwriting existing files from preceding runs. This created several critical deficiencies:
1. **Destructive Overwrite of Prior Runs**: Any subsequent benchmark execution obliterated empirical data, timestamps, and percentile distributions from earlier executions, preventing longitudinal analysis.
2. **Lack of Run Traceability**: Researchers and developers could not compare performance distributions across git commits, parameter variations, or configuration changes.
3. **Absence of Central Indexing**: There was no structured manifest recording historical executions, test parameters, hardware/environment metadata, or completion statuses.
4. **Risk of Stale or Orphaned Artifacts**: When running partial or individual benchmarks, older files from other benchmarks remained in `benchmarks/results/` without indication of which run generated which file.

### 1.2 User Decision & Architectural Directive
Following user consultation and architectural confirmation, the system shall adopt a **Dual-Path Retention Architecture**:
> *"Timestamped run directories in `benchmarks/results/history/<timestamp>/` with an index manifest (`manifest.json`), while maintaining latest results at `benchmarks/results/` for backward compatibility."*

This dual-path model guarantees that:
1. **Immutable Historical Telemetry**: Every execution session generates a timestamped directory `benchmarks/results/history/<timestamp>/` (formatted as `YYYY-MM-DD_HH-MM-SS`) containing all generated artifacts for that run.
2. **Persistent Structured Index**: A machine-readable manifest at `benchmarks/results/history/manifest.json` tracks every benchmark session, including timestamp, suite/subsystem, execution parameters, git commit, generated files, and execution status.
3. **Zero-Breaking-Change Backward Compatibility**: The canonical root files in `benchmarks/results/` are always updated with the outputs of the most recent run, preserving existing academic paper references, Markdown documentation links, and automated CI/CD consumers.

## 3. Functional Requirements

### FR-1: Deterministic Timestamped Directory Provisioning
- The benchmark suite shall generate unique historical run directories under `benchmarks/results/history/<timestamp>/`.
- The timestamp format shall strictly adhere to `YYYY-MM-DD_HH-MM-SS` (e.g., `2026-09-12_12-30-00`).
- If a directory with the exact timestamp already exists (e.g. sub-second repeated invocation), the system shall append an incremental suffix `_<N>` (e.g., `2026-09-12_12-30-00_1`).
- The directory shall be created with standard directory permissions (`0755` / `rwxr-xr-x`).

### FR-2: Master Suite Session Retention (`benchmarks/run_all.sh`)
- When `run_all.sh` executes:
  1. A single session timestamp `SESSION_TS` shall be initialized at the start of the master benchmark run.
  2. The session historical directory `benchmarks/results/history/${SESSION_TS}/` shall be created.
  3. All intermediate and final artifacts from all 6 evaluation stages shall be written to or replicated in `benchmarks/results/history/${SESSION_TS}/`.
  4. Upon completion of each stage or at the conclusion of the suite, the session manifest `manifest.json` shall be updated with an entry for the master execution session.
  5. A summary of retained historical artifacts and the manifest path shall be printed in the terminal output.

### FR-3: Standalone Benchmark Script Retention
- Each standalone benchmark execution script:
  - `benchmarks/wrk2/run_wrk2.sh`
  - `benchmarks/wrk2/run_saturation_stress.sh`
  - `benchmarks/fuzzer/run_fuzzer.sh`
  - `benchmarks/multihop/run_multihop.sh`
  - `benchmarks/ablation/run_ablation.sh`
- Shall support standalone execution retention:
  1. If invoked standalone (without an externally passed session directory), the script shall automatically create its own timestamped directory `benchmarks/results/history/<timestamp>/`, save its artifacts there, update `benchmarks/results/` with latest copies, and record an entry into `manifest.json`.
  2. If invoked as part of `run_all.sh` (via an environment variable such as `TORON_BENCHMARK_SESSION_DIR` or a CLI option `--session-dir`), the script shall direct its historical outputs to the active master session directory to consolidate the suite run into a single unified directory.

### FR-4: Canonical Latest File Backward Compatibility
- For every generated benchmark artifact, the canonical path under `benchmarks/results/` shall continue to exist and be refreshed with the latest run output:
  - `benchmarks/results/microbenchmarks.raw.txt`
  - `benchmarks/results/benchmark_c100_r5000.json`
  - `benchmarks/results/benchmark_c100_r5000.csv`
  - `benchmarks/results/benchmark_c100_r5000.raw.txt`
  - `benchmarks/results/saturation_stress_report.json`
  - `benchmarks/results/saturation_stress_report.md`
  - `benchmarks/results/differential_fuzz_report.json`
  - `benchmarks/results/differential_fuzz_report.md`
  - `benchmarks/results/multihop_report.json`
  - `benchmarks/results/multihop_report.md`
  - `benchmarks/results/ablation_study_report.json`
  - `benchmarks/results/ablation_study_report.md`
- Existing references in LaTeX manuscripts (`paper1_agentic_systems.tex`), documentation (`docs/wiki/`), and external validation scripts must remain fully functional without path modifications.

### FR-5: Structured Historical Manifest (`manifest.json`)
- The manifest at `benchmarks/results/history/manifest.json` shall be a valid JSON document with the following schema:
  ```json
  {
    "schema_version": "1.0",
    "updated_at": "2026-09-12T12:30:00+05:30",
    "total_runs": 1,
    "runs": [
      {
        "run_id": "run_2026-09-12_12-30-00",
        "timestamp": "2026-09-12T12:30:00+05:30",
        "directory": "history/2026-09-12_12-30-00",
        "suite": "all",
        "command": "./benchmarks/run_all.sh --auto-start",
        "git_commit": "abcdef1234567890",
        "git_branch": "main",
        "go_version": "go1.24.0",
        "status": "success",
        "duration_seconds": 45.2,
        "stages": [
          {
            "name": "microbenchmarks",
            "status": "success",
            "artifacts": ["microbenchmarks.raw.txt"]
          },
          {
            "name": "wrk2",
            "status": "success",
            "parameters": {"concurrency": 100, "rate": 5000, "duration": "5s"},
            "artifacts": [
              "benchmark_c100_r5000.json",
              "benchmark_c100_r5000.csv",
              "benchmark_c100_r5000.raw.txt"
            ]
          },
          {
            "name": "saturation_stress",
            "status": "success",
            "parameters": {"concurrency": 50, "rate": 5000, "duration": "5s", "attack_ratio": 0.10},
            "artifacts": [
              "saturation_stress_report.json",
              "saturation_stress_report.md"
            ]
          },
          {
            "name": "differential_fuzzer",
            "status": "success",
            "parameters": {"trials": 1000, "warmup": 50},
            "artifacts": [
              "differential_fuzz_report.json",
              "differential_fuzz_report.md"
            ]
          },
          {
            "name": "multihop",
            "status": "success",
            "parameters": {"mode": "standalone"},
            "artifacts": [
              "multihop_report.json",
              "multihop_report.md"
            ]
          },
          {
            "name": "ablation",
            "status": "success",
            "parameters": {"tasks": 10},
            "artifacts": [
              "ablation_study_report.json",
              "ablation_study_report.md"
            ]
          }
        ]
      }
    ]
  }
  ```
- If `manifest.json` does not exist, it shall be automatically created.
- If `manifest.json` already exists, new execution runs shall be appended to the `runs` array, preserving chronological history.

### FR-6: Atomic Manifest Serialization & Concurrency Protection
- All modifications to `manifest.json` must be atomic:
  - Write updated JSON to a temporary file (`manifest.json.tmp.<pid>`).
  - Flush and sync to disk.
  - Atomically rename (`os.Rename` or `mv`) into `manifest.json`.
- This guarantees that concurrent or interrupted benchmark runs cannot corrupt the manifest index.

### FR-7: Per-Session Metadata File
- In addition to the global `manifest.json`, each timestamped directory shall contain a lightweight `session_meta.json` recording the specific details of that execution session, enabling self-contained archiving and inspection of individual run directories.

### FR-8: CLI Options & Configurability
- The benchmark orchestrator and scripts shall support:
  - `--no-history`: Disable historical archiving for ephemeral test passes or debugging (only write canonical latest files).
  - `--session-name <name>`: Optional custom tag/label appended to the timestamp directory (e.g. `2026-09-12_12-30-00_baseline_eval`).

## 4. Non-Functional Requirements

- **NFR-1: Zero External Dependencies**: The retention mechanism and manifest updater must rely exclusively on POSIX Bash utilities (`mkdir`, `cp`, `mv`, `date`) and the Go standard library (`encoding/json`, `os`, `time`, `path/filepath`). No external packages, npm modules, or third-party binaries are permitted.
- **NFR-2: Performance & Overhead**: Archival copying and manifest appending must incur less than 100ms of overhead per benchmark execution.
- **NFR-3: Race-Clean Concurrency**: Go test harnesses verifying retention logic must pass `go test -race -count=1 ./...` with zero race conditions.
- **NFR-4: Data Integrity & Error Resilience**: If copying to the historical directory fails or if disk space is exhausted, the benchmark runner must log a clear warning to stderr without crashing or truncating canonical latest files.
- **NFR-5: Backward Compatibility**: Existing scripts, CI pipelines, and manual executions calling `run_all.sh` or individual scripts without new flags must continue to succeed seamlessly.
