# TC-145 - Test Cases for Route-Scoped Ingress, Activity Deadlines, and Bulkhead Isolation

## 1. Test Suite Overview & Architectural Objectives

### 1.1 Executive Summary & Problem Context

Toron enforces strict global security defaults designed to protect the gateway against Denial-of-Service attacks and memory exhaustion:
- Maximum request body ceiling: `4 MB` (`max_body_bytes: 4194304`).
- Static connection timeouts: `read_timeout: 5s`, `write_timeout: 5s`, `idle_timeout: 30s`.
- Reverse proxy upstream response header timeout: `10s` (`ResponseHeaderTimeout`).
- Fixed reactor worker pool: `128` workers (`worker_pool_size: 128`).
- Eager in-memory body allocation: Payloads $> 64\,\text{KB}$ are eagerly buffered into heap memory before route matching occurs.

While these baseline controls defend against [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Slowloris, Slow Read) and [CWE-770](https://cwe.mitre.org/data/definitions/770.html) (Out-Of-Memory exhaustion, [`SEC-28`](../architecture/ADR-084.md)), they break compatibility with enterprise legacy workloads detailed in [AN-006](../analysis/AN-006.md) and [REQ-145](../requirements/REQ-145.md):
1. **Large File Uploads**: Multipart and raw uploads exceeding `200 MB` are rejected at the HTTP parser layer with `HTTP 413 Payload Too Large` before routing rules can be evaluated.
2. **High-Latency Backend Execution**: Monolithic reporting engines and batch ETL endpoints require `15s` to `60s+` to produce response headers, exceeding static write deadlines (`5s`) and upstream transport timeouts (`10s`).
3. **Sustained Uploads over Constrained Links**: Legitimate `200 MB` uploads over broadband or WAN links take `15s` to `60s+`. Toron's static `5s` read deadline aborts these transfers mid-stream with `i/o timeout`.
4. **Reactor Worker Pool Saturation**: Multiple concurrent slow requests bind worker goroutines for extended durations, starving health checks (`/health`) and fast microservice routes.

### 1.2 Purpose of Test Specification

This test specification validates the architectural solutions established in [REQ-145](../requirements/REQ-145.md) and [ADR-145](../architecture/ADR-145.md):
- **Two-Phase Request Ingestion Pipeline**: Decoupling header parsing (`ParseHeader`) from body ingestion, permitting route-scoped limits to be resolved before reading socket payload bytes.
- **Fast-Fail Content-Length Rejection**: Immediate `HTTP 413` during interim route lookup with zero payload bytes read and zero heap memory allocated.
- **Progress-Based Activity-Refreshed Read Deadlines**: Allowing sustained high-volume uploads over slow links while terminating stalled connections within `ReadTimeout`.
- **Downstream Write Deadline Decoupling**: Permitting extended backend execution windows up to route `response_header_timeout` without downstream socket termination.
- **Route Bulkhead Concurrency Limiter**: Bounding concurrent in-flight requests on legacy routes with fast-fail `HTTP 503` / `Retry-After: 5`, guaranteeing zero worker starvation on operational endpoints (`/health`).
- **Zero-Copy Streaming Proxy Ingress**: Direct socket-to-upstream piping with constant $O(1)$ memory ($\le 64\,\text{KB}$).

  - `TestProxy_Streaming_200MBUpload` in `pkg/proxy/proxy_test.go`
- **Traceability**:
  - [`REQ-145 §4 AC-145-01`](../requirements/REQ-145.md)
  - [`REQ-145 §2.1 FR-145-1`](../requirements/REQ-145.md) (Two-Phase Parsing)
  - [`REQ-145 §2.2 FR-145-2`](../requirements/REQ-145.md) (Route-Scoped Ceilings)
  - [`REQ-145 §2.6 FR-145-6`](../requirements/REQ-145.md) (Zero-Copy Streaming)

- **Preconditions**:
  1. Toron server initialized with global ceiling `server.max_body_bytes: 4194304` (4MB).
  2. Route `/legacy/upload` configured with `max_body_bytes: 268435456` (256MB) and upstream pointing to mock backend.
  3. Default route `/api/data` configured without route-specific `max_body_bytes` (inherits global 4MB ceiling).
  4. Mock upstream HTTP backend running on loopback TCP socket, designed to read inbound request streams to completion and respond with `HTTP 200 OK` and JSON body `{"bytes_received": 209715200}`.
- **Inputs & Test Data**:
  - **Stream A (Configured Route)**:
    - Target URI: `POST /legacy/upload`
    - Headers:
      ```http
      POST /legacy/upload HTTP/1.1
      Host: localhost
      Content-Type: application/octet-stream
      Content-Length: 209715200
      Connection: keep-alive
      ```
    - Payload: Exactly $200\,\text{MB}$ ($209,715,200\,\text{bytes}$) generated via continuous $32\,\text{KB}$ buffer chunks.
  - **Stream B (Unconfigured Route)**:
    - Target URI: `POST /api/data`
    - Headers:
      ```http
      POST /api/data HTTP/1.1
      Host: localhost
      Content-Type: application/octet-stream
      Content-Length: 5242880
      Connection: close
      ```
    - Payload: $5\,\text{MB}$ ($5,242,880\,\text{bytes}$, exceeding global 4MB ceiling).
- **Execution Steps**:
  1. Start the mock backend server and Toron gateway.
  2. Establish a TCP connection from client to Toron.
  3. **Execute Stream A**:
     a. Transmit HTTP request line and headers for `POST /legacy/upload`.
     b. Verify gateway executes Phase 1 `httpparser.ParseHeader` without buffering or allocating body memory.
     c. Verify router resolves route prefix `/legacy/upload` and applies effective ceiling `256 MB`.
     d. Stream the 200MB body over the connection in $32\,\text{KB}$ chunks.
     e. Read gateway response from client socket.
  4. Establish a separate TCP connection to Toron.
  5. **Execute Stream B**:
     a. Transmit HTTP request line and headers for `POST /api/data`.
     b. Verify router matches `/api/data` and falls back to global ceiling `4 MB`.
     c. Read gateway response from client socket.
- **Expected Outcomes**:
  - **Stream A**:
    - Gateway accepts and streams the entire 200MB payload to mock backend.
    - Status code is `HTTP 200 OK`.
    - Response body verifies `bytes_received == 209715200`.
    - Gateway does NOT raise `HTTP 413 Payload Too Large`.
  - **Stream B**:
    - Gateway immediately rejects the request with `HTTP 413 Payload Too Large`.
    - Gateway terminates or closes the socket without reading the 5MB payload into memory.
- **Pass / Fail Criteria**:
  - **Pass**: Stream A completes with `HTTP 200 OK` and 200MB relayed; Stream B is rejected with `HTTP 413`; zero heap memory spikes observed.
  - **Fail**: Stream A receives `HTTP 413`, or terminates prematurely with `i/o timeout`; or Stream B allows $> 4\,\text{MB}$ upload.

- **Traceability**:
  - [`REQ-145 §4 AC-145-02`](../requirements/REQ-145.md)
  - [`REQ-145 §2.2 FR-145-2 §3`](../requirements/REQ-145.md) (Pre-Read Fast-Fail)
  - [`ADR-145 §2 Decision 1, Decision 2`](../architecture/ADR-145.md)
  - [`ADR-084`](../architecture/ADR-084.md) / `SEC-28` (Monolithic Heap Allocation Defense)
  - [`CWE-770`](https://cwe.mitre.org/data/definitions/770.html) (Allocation of Resources Without Limits)
  - [`TASK-170`](../tasks/TASK-170.md), [`TASK-171`](../tasks/TASK-171.md)
- **Preconditions**:
  1. Route `/legacy/upload` configured with `max_body_bytes: 268435456` (256MB).
  2. Mock upstream server configured for `/legacy/upload` with request recording hook.
  3. Client connected over raw TCP socket (`net.Dial`).
- **Inputs & Test Data**:
  - Request headers transmitted over raw TCP:
    ```http
    POST /legacy/upload HTTP/1.1\r\n
    Host: localhost\r\n
    Content-Type: application/octet-stream\r\n
    Content-Length: 314572800\r\n
    Connection: close\r\n
    \r\n
    ```
  - Crucial Test Condition: Client sends **ONLY** the headers and transmits **ZERO** request body bytes.
- **Execution Steps**:
  1. Record baseline runtime memory stats (`runtime.ReadMemStats`).
  2. Client transmits the HTTP request headers with `Content-Length: 314572800` (300MB, exceeding 256MB route limit).
  3. Client starts a high-resolution timer and blocks on reading the socket response.
  4. Measure elapsed duration until the first byte of response arrives.
  5. Parse the HTTP response line, headers, and response body.
  6. Assert client socket is closed or drained by gateway.
  7. Verify mock upstream server received zero requests.
  8. Inspect runtime memory delta on gateway server.
- **Expected Outcomes**:
  - Gateway responds immediately with status `HTTP 413 Payload Too Large`.
  - Response headers include:
    - `Connection: close`
    - `Content-Type: application/json`
  - Response body contains structured error:
    `{"error":"413 Payload Too Large: request Content-Length exceeds effective route limit"}`
  - Response elapsed time is $< 50\,\text{ms}$ (instant fast-fail, no socket read blocking).
  - Mock upstream receives 0 incoming connection attempts.
  - Gateway heap allocation delta is $\approx 0\,\text{bytes}$ (specifically $< 64\,\text{KB}$, zero allocation of the 300MB payload).
- **Pass / Fail Criteria**:
  - **Pass**: `HTTP 413` received in $< 50\,\text{ms}$; 0 body bytes read; mock backend not dialed; zero memory allocation.
  - **Fail**: Server hangs waiting for body data; server returns `HTTP 200` or `500`; or server attempts monolithic allocation `make([]byte, 314572800)`.

- **Traceability**:

  - [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md) (Progress-Based Activity-Refreshed Read Deadlines)
  - [`REQ-126 §2.3`](../requirements/REQ-126.md) (Streaming Deadline Invariants)
  - [`TASK-171`](../tasks/TASK-171.md)
- **Preconditions**:
  1. Route `/legacy/upload` configured with `read_timeout: 5s` and `max_body_bytes: 268435456` (256MB).
  2. Mock upstream backend configured to ingest incoming stream and return `HTTP 200 OK`.
  3. Client connected to Toron gateway over local TCP socket.
- **Inputs & Test Data**:
  - Total payload size: $30\,\text{MB}$ ($31,457,280\,\text{bytes}$) in test harness, or $200\,\text{MB}$ in end-to-end suite.
  - Pacing configuration:
    - Total transfer duration: $30.0\,\text{seconds}$.
    - Number of intervals: 30 iterations.
    - Chunk per iteration: $1\,\text{MB}$ ($1,048,576\,\text{bytes}$).
    - Sleep interval between chunks: $1.0\,\text{second}$.
  - Crucial condition: Inter-chunk interval ($1.0\,\text{s}$) is strictly less than `read_timeout` ($5.0\,\text{s}$), but cumulative transfer time ($30\,\text{s}$) is $6\times$ longer than the static timeout.
- **Execution Steps**:
  1. Establish TCP connection to Toron.
  2. Send request headers:
     ```http
     POST /legacy/upload HTTP/1.1\r\n
     Host: localhost\r\n
     Content-Type: application/octet-stream\r\n
     Content-Length: 31457280\r\n
     Connection: keep-alive\r\n
     \r\n
     ```
  3. Start test timer ($T_0$).
  4. Execute upload loop for $i = 1 \dots 30$:
     a. Write $1\,\text{MB}$ chunk to TCP socket.
     b. Sleep for $1.0\,\text{second}$.
  5. Await and parse HTTP response from Toron.
  6. Measure total elapsed transfer duration ($T_{\text{elapsed}} = T_{\text{end}} - T_0$).
- **Expected Outcomes**:
  - Upon each read operation where bytes are received from socket, `activityReader` refreshes socket read deadline forward by `read_timeout` ($5.0\,\text{s}$).
  - Connection remains open continuously throughout all 30 seconds of transmission.
  - Transfer completes successfully; response status is `HTTP 200 OK`.
  - Total elapsed duration is $\ge 30.0\,\text{seconds}$.
  - Zero `i/o timeout` errors encountered.
- **Pass / Fail Criteria**:
  - **Pass**: Transfer completes with `HTTP 200 OK` after $\ge 30\,\text{s}$ of sustained streaming; zero socket read timeouts.
  - **Fail**: Connection terminated at $t \approx 5.0\,\text{s}$ with `i/o timeout` (static absolute deadline defect).

    ```http
    POST /legacy/upload HTTP/1.1\r\n

    Content-Length: 209715200\r\n
    Connection: keep-alive\r\n
    \r\n
    ```

  - Stall event: Client halts transmission entirely and goes idle for $6.5\,\text{seconds}$ (exceeding $5\,\text{s}$ `read_timeout`).
- **Execution Steps**:
  1. Record baseline worker goroutine count.
  2. Client transmits HTTP headers and initial $64\,\text{KB}$ chunk.
  3. Client halts transmission and starts stopwatch at $T_0$.

  8. Verify gateway terminates worker goroutine and reclaims all socket resources.

  - Socket deadline fires upon reaching $5.0\,\text{seconds}$ of inactivity.
  - Gateway catches `net.Error` with `Timeout() == true` and immediately closes client socket.
  - Connection teardown occurs precisely within $5.0\,\text{s} \le \Delta T \le 5.5\,\text{s}$ from stall onset.
  - Client socket receives EOF or reset within $5.5\,\text{seconds}$.
  - Worker goroutine yields back to reactor worker pool; zero goroutines or file descriptors are leaked.
- **Pass / Fail Criteria**:
  - **Pass**: Connection forcibly closed between $5.0\text{s}$ and $5.5\text{s}$ of silence; worker goroutines return to baseline.
  - **Fail**: Connection remains open past $6.0\text{s}$, or server goroutine remains pinned indefinitely.

### TC-145-08: Anti-Drip Progress Rate Clamping Defense Against Low-Rate Slowloris

- **Identifier**: `TC-145-08`
- **Target Subsystem & Component**:
  - Activity Reader Subsystem ([`pkg/server/server.go`](../../pkg/server/server.go) - `activityReader`)
- **Target Go Test Functions**:
  - `TestServer_ActivityReader_AntiDrip_RateClamping` in `pkg/server/server_test.go`
- **Traceability**:
  - [`REQ-145 §2.3 FR-145-3 §4`](../requirements/REQ-145.md) (Progress Rate Clamping)
  - [`REQ-145 §3.4 NFR-145-4`](../requirements/REQ-145.md) (Slowloris Immunity)
  - [`CWE-400`](https://cwe.mitre.org/data/definitions/400.html)
  - [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md)
  - [`TASK-171`](../tasks/TASK-171.md)
- **Preconditions**:
  1. Route configured with `read_timeout: 5s` and minimum progress threshold of $1\,\text{KB}$ per renewal window (`minRateBytes: 1024`).
  2. Client connected over raw TCP socket.
- **Inputs & Test Data**:
  - Drip-feed attack pattern: Transmit exactly $1\,\text{byte}$ every $4.8\,\text{seconds}$ (staying within the 5-second deadline window, but yielding cumulative progress of only $2\,\text{bytes}$ over $9.6\,\text{seconds}$, well below the $1\,\text{KB}$ minimum rate threshold).
- **Execution Steps**:
  1. Transmit HTTP headers for `POST /legacy/upload` with `Content-Length: 10485760`.
  2. Transmit byte 1 at $t = 0.0\,\text{s}$.
  3. Sleep $4.8\,\text{seconds}$.
  4. Transmit byte 2 at $t = 4.8\,\text{s}$.
  5. Attempt to transmit byte 3 at $t = 9.6\,\text{s}$.
  6. Observe whether `activityReader` permits deadline extension or triggers anti-drip rate clamp.
- **Expected Outcomes**:
  - Although the interval between individual bytes ($4.8\,\text{s}$) is less than `read_timeout` ($5.0\,\text{s}$), the cumulative bytes transferred across the deadline evaluation window ($2\,\text{bytes}$) is strictly below $1\,\text{KB}$.
  - The gateway detects sub-threshold progress, denies deadline extension, terminates the TCP connection, and reclaims worker resources.
- **Pass / Fail Criteria**:
  - **Pass**: Connection terminated due to insufficient rate progress; worker goroutine freed.
  - **Fail**: Connection kept alive indefinitely by 1-byte periodic transmissions.
