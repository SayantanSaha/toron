# SR-145 - Security Review of Route-Scoped Payload Ingress, Activity Deadlines, and Bulkhead Isolation Architecture (Option 1)

## 1. Executive Summary & Review Scope

The Security Analyst (AGENT-008) has executed an evidence-based security architecture and vulnerability assessment of the **Option 1 (Route-Aware Streaming Ingress with Activity Deadlines & Bulkheads)** implementation across the Toron gateway codebase.

This review evaluates the implementation against requirements specified in [`REQ-145`](../requirements/REQ-145.md), architectural decisions formulated in [`ADR-145`](../architecture/ADR-145.md), work package deliverables across [`TASK-169`](../tasks/TASK-169.md) through [`TASK-173`](../tasks/TASK-173.md), code review assessments in [`CR-145`](../codeReview/CR-145.md), and test specifications in [`TC-145`](../testCases/TC-145.md).

## 2. Threat Vector Assessment & Security Invariants Verification

### 2.1 CWE-400 / Uncontrolled Resource Consumption: Slowloris & Starvation Defenses

#### 2.1.1 Anti-Drip Progress Rate Clamping & Stall Enforcement
Under [`REQ-145 §2.3`](../requirements/REQ-145.md) and [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md), `activityReader` transforms static socket read deadlines into progress-refreshed deadlines while mitigating low-rate drip-feeding Slowloris attacks (e.g., transmitting 1 byte every 4.8 seconds within a 5-second deadline).
- **Audit Result**: `activityReader.Read` maintains `windowBytes` and `minRateBytes` (default: 1 KB per window). Deadlines are refreshed forward only when `windowBytes >= effectiveMinRate`. If a client pauses longer than `timeout`, the OS kernel socket timer fires, severing the connection and reclaiming worker goroutines.
- **Vulnerabilities Identified**:
  1. On HTTP/1.1 keep-alive connections, when moving from idle state to body ingestion, the socket deadline is not reset to `effectiveReadTimeout` if the route relies on default read timeouts, leaving connections subject to a relaxed 30s `IdleTimeout` (see [`SR-145-F06`](#sr-145-f06)).
  2. Exact-sized payloads trigger false-positive DoS aborts due to off-by-one boundary operators (see [`SR-145-F07`](#sr-145-f07)).
  3. `activityReader` unconditionally closes the TCP socket on clean `io.EOF`, prematurely terminating connections before the HTTP response can be serialized (see [`SR-145-F08`](#sr-145-f08)).

#### 2.1.2 Reactor Worker Pool Bulkhead Isolation
Under [`REQ-145 §2.5`](../requirements/REQ-145.md) and [`ADR-145 §2 Decision 5`](../architecture/ADR-145.md), Toron enforces route-level concurrency caps (`max_concurrency`) to isolate slow legacy routes from the fixed 128-worker reactor pool.
- **Audit Result**: `router.TryAcquireRouteSlot` uses atomic test-and-set with rollback (`atomic.AddInt64(&pr.activeRequests, 1)`) to cap concurrency deterministically. If saturated, requests immediately receive `HTTP 503 Service Unavailable` with `Retry-After: 5` in $< 1\,\text{ms}$ during Phase 1 routing, before reading payload bodies or dialing upstream.
- **Worker Reservation Guarantee**: Elevated routes omitting `max_concurrency` automatically enforce $\min(32, \text{WorkerPoolSize} / 4)$, ensuring $\ge 75\%$ of reactor workers remain permanently reserved for operational probes (`/health`, `/metrics`) and microservices.
- **Vulnerabilities Identified**:
  1. In `server.go`, `slotRelease` is invoked manually across return paths rather than bound to a deferred closure, risking slot leakage under unexpected panic unwinding (see [`SR-145-F11`](#sr-145-f11)).
  2. The HTTP/2 adapter completely bypasses the bulkhead concurrency gate before buffering bodies (see [`SR-145-F02`](#sr-145-f02)).

### 2.2 CWE-770 / Allocation of Resources Without Limits: OOM Vulnerability Analysis

#### 2.2.1 Two-Phase Parsing & Fast-Fail Pre-Read Rejection
Under [`REQ-145 §2.1`](../requirements/REQ-145.md) and [`ADR-145 §2 Decision 1, Decision 2`](../architecture/ADR-145.md), request parsing is decoupled into `httpparser.ParseHeader` and Phase 2 body ingestion.
- **Audit Result**: For standard HTTP/1.1 fixed-length requests, `s.handleConn` inspects declared `Content-Length` immediately after interim route resolution. If `req.ContentLength > effectiveMaxBody`, the server immediately returns `HTTP 413 Payload Too Large` with zero bytes read and zero heap memory allocated.
- **Vulnerabilities Identified**:
  1. **Chunked Normalize Mode OOM**: When `inbound_chunked_mode` is set to `"normalize"` (the default!), `proxy.go:1127` disables zero-copy streaming for chunked requests, causing incoming 200MB+ chunked payloads to be buffered into heap memory via `io.ReadAll(req.Body)`. This completely violates `NFR-145-1` ($O(1)$ memory constraint) and creates an instantaneous OOM crash vector (see [`SR-145-F01`](#sr-145-f01)).
  2. **HTTP/2 Eager Allocation**: `s.http2AdapterHandler()` reads up to `maxBodyBytes+1` into heap memory via `io.ReadAll(lr)` for all HTTP/2 requests before route handling, completely bypassing streaming and pre-read fast-fail checks (see [`SR-145-F02`](#sr-145-f02)).

---

### 2.3 CWE-444 / HTTP Request Smuggling & Pipeline Desynchronization

#### 2.3.1 Grammar & Smuggling Guards in `ParseHeader`
`httpparser.ParseHeader` adheres to RFC 7230 §3.3.3 and RFC 9112 §6.3:
- Rejects requests containing both `Transfer-Encoding` and `Content-Length` with `ErrBadRequest`.
- Validates and normalizes multiple `Content-Length` headers, rejecting conflicting values.
- Rejects malformed transfer codings, bare CR/LF characters, and control characters in header keys/values.
- Enforces `opts.MaxHeaderBytes` (default: 8 KB) using pooled line buffers.

#### 2.3.2 Keep-Alive Pipeline Desynchronization Vulnerability
- **Audit Result (CRITICAL DEFECT)**: While `s.handleConn` validates that fixed-length streaming bodies are fully consumed before allowing keep-alive reuse (`sr.TotalRead() < req.ContentLength`), **no validation is performed for chunked requests (`req.ContentLength == -1`)**.
- If a handler generates an early response without consuming the chunked body, the connection remains open for keep-alive reuse. The unconsumed chunk frames in `br` are read as the start of the next HTTP request, enabling classic **HTTP Request Smuggling / Pipelining Desynchronization** (see [`SR-145-F03`](#sr-145-f03)).

---

### 2.4 Fail-Closed Semantics, Timeouts, and Context Propagation

#### 2.4.1 Downstream Write Timeout Decoupling
- **Design**: While waiting for slow upstream backends, the downstream write deadline is extended to $\text{effectiveRespTimeout} + \text{writeTimeout}$.
- **Defect Identified**: Due to a string comparison mismatch (`pr.routeType` is `"upstream"`, but `server.go:387` checks `routeInfo.RouteType == "proxy"`), write deadline decoupling is completely skipped for all proxy routes that rely on default response header timeouts (see [`SR-145-F05`](#sr-145-f05)).

#### 2.4.2 Bidirectional Context Cancellation & Orphaned Backend Execution
- **Design**: Downstream client disconnects must cancel upstream backend contexts within 100ms.
- **Defect Identified**: Toron does not monitor downstream TCP socket closures while waiting on slow backend responses for requests without unread body data (e.g. GET/HEAD or after body streaming completes). Backend queries continue executing as zombies for up to 60 seconds (see [`SR-145-F04`](#sr-145-f04)).

#### 2.4.3 Upstream Timeout RFC Compliance
- **Defect Identified**: Upstream backend header timeouts on routes with default response timeouts emit `HTTP 502 Bad Gateway` instead of `HTTP 504 Gateway Timeout`, violating RFC 9110 §15.6.5 and triggering unwarranted thundering-herd retries (see [`SR-145-F09`](#sr-145-f09)).

## 3. Detailed Security Findings Registry

### SR-145-F01: Unbounded Heap Memory Buffering and OOM Crash via Inbound Chunked Request Ingestion under Default "Normalize" Mode

- **Finding ID**: `SR-145-F01`
- **Severity**: **High**
- **Category / CWE**: [CWE-770](https://cwe.mitre.org/data/definitions/770.html) (Allocation of Resources Without Limits) / [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Uncontrolled Resource Consumption)
- **Location**: [`pkg/proxy/proxy.go:1125-1165`](../../pkg/proxy/proxy.go) and [`pkg/config/config.go:680-691`](../../pkg/config/config.go)
- **Related Artifacts**: [`REQ-145 §2.6 FR-145-6`](../requirements/REQ-145.md), [`REQ-145 §3.1 NFR-145-1`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 6`](../architecture/ADR-145.md), [`TASK-172 WP-1`](../tasks/TASK-172.md), [`TC-145-07`](../testCases/TC-145.md), [`ADR-084`](../architecture/ADR-084.md) (SEC-28), [`CR-145`](../codeReview/CR-145.md) (CR-145-F03)
- **Evidence**:
  In [`pkg/config/config.go:686-691`](../../pkg/config/config.go):
  ```go
  func (p *ProxyRouteConfig) ShouldStreamRequestBody(contentLength int64) bool {
      if p.StreamRequestBody != nil {
          return *p.StreamRequestBody
      }
      return contentLength > 65536 || contentLength == -1
  }
  ```
  In [`pkg/proxy/proxy.go:1125-1127`](../../pkg/proxy/proxy.go):
  ```go
  shouldStream := p.opts.StreamRequestBody != nil && *p.opts.StreamRequestBody
  if p.opts.StreamRequestBody == nil {
      shouldStream = req.ContentLength > 65536 || (req.ContentLength == -1 && strings.EqualFold(effectiveMode, "passthrough"))
  }
  ```
  In [`pkg/proxy/proxy.go:1160-1164`](../../pkg/proxy/proxy.go):
  ```go
  // Inbound Chunked "normalize": Buffer verified body, strip Transfer-Encoding, add exact Content-Length
  decodedBytes, err := io.ReadAll(req.Body)
  ```
- **Description**:
  Under Toron's default configuration, `inbound_chunked_mode` is set to `"normalize"` (per [`REQ-133`](../requirements/REQ-133.md)). When a route specifies an elevated payload ceiling (e.g. `max_body_bytes: 256MB`) without explicitly setting `stream_request_body: true`, `p.opts.StreamRequestBody` is `nil` (automatic heuristic mode).
  While `config.go` specifies that chunked uploads (`contentLength == -1`) should stream automatically, `proxy.go:1126` restricts chunked streaming to `effectiveMode == "passthrough"`.
  Under default `"normalize"` mode, `shouldStream` evaluates to `false`. The proxy then executes `io.ReadAll(req.Body)` on line 1160, buffering the entire 200MB+ payload into gateway heap memory.
- **Impact**:
  Violates `NFR-145-1` ($O(1)$ constant memory $\le 64\,\text{KB}$). When concurrent clients transmit large chunked payloads, heap allocations explode, driving the gateway into Linux kernel OOM killing (`SIGKILL 9`) and causing a complete service outage.
- **Recommendation**:
  In `pkg/proxy/proxy.go:1126`, align chunked streaming heuristics with `ADR-145 Decision 6`:
  `shouldStream = req.ContentLength > 65536 || req.ContentLength == -1`.
  For chunked streaming uploads on proxy routes, stream chunked frames directly upstream without intermediate in-memory `io.ReadAll` buffering. If normalization is explicitly forced, clamp buffered size to `opts.MaxPayloadSize` and reject oversized chunked uploads with `HTTP 413`.
- **Required Action**: Update `proxy.go:1126` to enable zero-copy streaming for chunked uploads when `opts.StreamRequestBody == nil`, and add an automated test verifying $O(1)$ memory consumption on chunked uploads under default configuration.

### SR-145-F02: Unbounded Heap Buffering, Lack of Pre-Read 413 Fast-Fail, and Bulkhead Bypass in HTTP/2 Adapter

- **Finding ID**: `SR-145-F02`
- **Severity**: **High**
- **Category / CWE**: [CWE-770](https://cwe.mitre.org/data/definitions/770.html) (Allocation of Resources Without Limits) / [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Uncontrolled Resource Consumption)
- **Location**: [`pkg/server/server.go:630-674`](../../pkg/server/server.go)
- **Related Artifacts**: [`REQ-145 §2.1 FR-145-1`](../requirements/REQ-145.md), [`REQ-145 §2.2 FR-145-2`](../requirements/REQ-145.md), [`REQ-145 §2.5 FR-145-5`](../requirements/REQ-145.md), [`REQ-145 §3.1 NFR-145-1`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 1, Decision 2, Decision 5`](../architecture/ADR-145.md), [`ADR-084`](../architecture/ADR-084.md) (SEC-28)
- **Evidence**:
  In [`pkg/server/server.go:636-646`](../../pkg/server/server.go):
  ```go
  if routeInfo, matched := s.router.LookupPrefixRoute(req); matched && routeInfo != nil && routeInfo.MaxBodyBytes > 0 {
      maxBodyBytes = routeInfo.MaxBodyBytes
  }
  lr := io.LimitReader(r.Body, maxBodyBytes+1)
  bodyBytes, err := io.ReadAll(lr)
  ```
- **Description**:
  In `s.http2AdapterHandler()`, the server looks up the matched route's elevated ceiling (`maxBodyBytes = routeInfo.MaxBodyBytes`, e.g. 256MB). However:
  1. It performs eager buffering of the entire body via `io.ReadAll(lr)` into heap memory.
  2. Declared `Content-Length` is not validated *before* reading from the socket. If a client transmits `Content-Length: 500MB`, the adapter reads up to `maxBodyBytes+1` (256MB + 1) into memory before rejecting the request at line 650.
  3. Bulkhead concurrency gating (`s.router.TryAcquireRouteSlot`) is not evaluated before reading body data.
- **Impact**:
  Allows malicious or misbehaved HTTP/2 clients to multiplex concurrent 256MB uploads, bypassing bulkhead limits and triggering massive heap allocations resulting in instant gateway OOM crash.
- **Recommendation**:
  Refactor `http2AdapterHandler` to:
  1. Fast-fail reject requests where `r.ContentLength > maxBodyBytes` with `HTTP 413` before reading body bytes.
  2. Check and acquire route bulkhead slots via `s.router.TryAcquireRouteSlot` before body ingestion.
  3. Avoid `io.ReadAll` for payloads exceeding 64KB, streaming `r.Body` directly through `req.Body = r.Body`.
- **Required Action**: Implement pre-read `Content-Length` validation and bulkhead concurrency gating in `http2AdapterHandler` prior to reading body bytes.

### SR-145-F03: HTTP Request Smuggling and Connection Desynchronization via Unconsumed Chunked Request Bodies on Keep-Alive Connections

- **Finding ID**: `SR-145-F03`
- **Severity**: **High**
- **Category / CWE**: [CWE-444](https://cwe.mitre.org/data/definitions/444.html) (HTTP Request Smuggling) / [CWE-445](https://cwe.mitre.org/data/definitions/445.html) (User-Controlled Delimiter)
- **Location**: [`pkg/server/server.go:481-492, 515-527`](../../pkg/server/server.go)
- **Related Artifacts**: [`REQ-145 §2.1 FR-145-1`](../requirements/REQ-145.md), [`REQ-133`](../requirements/REQ-133.md), [`ADR-145 §2 Decision 1`](../architecture/ADR-145.md), [`TASK-171 WP-2`](../tasks/TASK-171.md), [`CR-145`](../codeReview/CR-145.md) (CR-145-F06)
- **Evidence**:
  In [`pkg/server/server.go:481-492`](../../pkg/server/server.go):
  ```go
  if req.ContentLength > 0 {
      if sr, ok := req.Body.(*httpparser.StreamingBodyReader); ok && sr.TotalRead() < req.ContentLength && res.StatusCode < 400 {
          _ = req.CloseBody()
          ...
          _ = conn.Close()
          return nil
      }
  }
  ```
  And lines 515-521:
  ```go
  if req.ContentLength > 0 {
      if sr, ok := req.Body.(*httpparser.StreamingBodyReader); ok {
          if sr.TotalRead() < req.ContentLength {
              return nil
          }
      }
  }
  ```
- **Description**:
  `s.handleConn` verifies that incoming request bodies with fixed `Content-Length` have been fully consumed before allowing keep-alive connection reuse. However, **chunked requests (`req.ContentLength == -1`) are completely omitted from this safety check**.
  If a handler emits an early response (such as a 302 redirect, 401 unauthorized, 403 forbidden, or error response) without reading the chunked body to the terminating `0\r\n\r\n` chunk, `s.handleConn` continues to line 527 and loops back to `httpparser.ParseHeader(br, opts)`.
  The unread chunk bytes remaining in the buffered reader `br` are read as the request line and headers of the subsequent request on the reused TCP socket.
- **Impact**:
  Enables HTTP Request Smuggling (CWE-444). An attacker can smuggle arbitrary HTTP requests within unconsumed chunked bodies on persistent connections, bypassing WAF rules, route access controls, and administrative authentication.
- **Recommendation**:
  For chunked requests (`req.ContentLength == -1`), verify whether the `*httpparser.ChunkedBodyReader` reached clean EOF. If unconsumed chunks remain on the connection, force `Connection: close`, terminate the socket, and do not reuse the connection.
- **Required Action**: Add an unconsumed chunked reader check in `s.handleConn` that severs the connection if a chunked request was not read to completion.

### SR-145-F04: Missing Downstream Socket Disconnect Detection during Extended Upstream Execution

- **Finding ID**: `SR-145-F04`
- **Severity**: **Medium**
- **Category / CWE**: [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Uncontrolled Resource Consumption) / [CWE-772](https://cwe.mitre.org/data/definitions/772.html) (Missing Release of Resource after Effective Lifetime)
- **Location**: [`pkg/server/server.go:376-412`](../../pkg/server/server.go) and [`pkg/proxy/proxy.go:1360`](../../pkg/proxy/proxy.go)
- **Related Artifacts**: [`REQ-145 §2.6 FR-145-6 §3`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 6 §3, §4`](../architecture/ADR-145.md), [`TASK-172 WP-3`](../tasks/TASK-172.md), [`TC-145-10`](../testCases/TC-145.md)
- **Evidence**:
  In [`pkg/server/server.go:376`](../../pkg/server/server.go):
  ```go
  reqCtx, reqCancel := context.WithCancel(ctx)
  if slotRelease != nil {
      reqCtx = context.WithValue(reqCtx, router.RouteSlotAcquiredContextKey, true)
  }
  req.SetContext(reqCtx)
  ...
  s.router.ServeHTTP(req, res)
  ```
- **Description**:
  `reqCtx` is derived directly from the server root context `ctx`. `reqCancel` is only called synchronously after `s.router.ServeHTTP` returns.
  While disconnects during active request body uploading are detected by `activityReader`, for requests without an active body stream (e.g. GET/HEAD queries or after payload upload completes), there is no mechanism monitoring the downstream client TCP socket while waiting for the upstream backend to respond.
  If a client terminates the connection, closes the browser, or experiences network failure while waiting for a 30-second report or database query, Toron continues to wait on the upstream backend until the response completes or `ResponseHeaderTimeout` expires.
- **Impact**:
  Orphaned backend resource consumption (zombie execution). Legacy backends continue to execute expensive, multi-second transactions unnecessarily, holding reactor workers and bulkhead slots.
- **Recommendation**:
  In `s.handleConn` (or in `ReverseProxy.ServeHTTPWithPrefix`), inspect downstream socket health while awaiting upstream response headers, canceling `reqCancel()` if the downstream socket closes.
- **Required Action**: Implement client connection closure monitoring during upstream response header wait to cancel `outReq.Context()` upon downstream abort.

### SR-145-F06: Slowloris Read Deadline Vulnerability on Keep-Alive Connections Due to Missing Clamping from IdleTimeout

  In [`pkg/server/server.go:234-239`](../../pkg/server/server.go):

  timeout := s.config.ReadTimeout

  // Phase 2: Governed Body Ingestion

  Consequently, `_ = tracker.SetAmortizedReadDeadline(effectiveReadTimeout)` is NOT invoked. The socket read deadline remains set to 30 seconds instead of the expected 5 seconds.
- **Impact**:
  Slowloris defense degradation. Clients on keep-alive connections can pause body transmission for up to 30 seconds before triggering a timeout, tying up reactor workers 6x longer than intended.
- **Recommendation**:
  In `pkg/server/server.go:358`, unconditionally enforce `_ = tracker.SetAmortizedReadDeadline(effectiveReadTimeout)` whenever `(req.ContentLength > 0 || req.ContentLength == -1) && effectiveReadTimeout > 0`.
- **Required Action**: Remove the `routeInfo != nil && routeInfo.ReadTimeout > 0` check and enforce `SetAmortizedReadDeadline(effectiveReadTimeout)` unconditionally before Phase 2 body reading.

### SR-145-F07: Denial of Service via Exact-Sized Payload Rejection in Streaming and Activity Readers

- **Finding ID**: `SR-145-F07`
- **Severity**: **Medium**
- **Category / CWE**: [CWE-193](https://cwe.mitre.org/data/definitions/193.html) (Off-by-one Error) / [CWE-398](https://cwe.mitre.org/data/definitions/398.html) (Incorrect Boundary Handling)
- **Location**: [`pkg/httpparser/parser.go:358-384`](../../pkg/httpparser/parser.go) and [`pkg/server/activity_reader.go:71-74`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.2 FR-145-2`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 2`](../architecture/ADR-145.md), [`TASK-170 WP-2`](../tasks/TASK-170.md), [`TASK-171 WP-1`](../tasks/TASK-171.md), [`TC-145-01`](../testCases/TC-145.md), [`CR-145`](../codeReview/CR-145.md) (CR-145-F01)
- **Evidence**:
  In [`pkg/httpparser/parser.go:358`](../../pkg/httpparser/parser.go):
  ```go
  if s.limit > 0 && s.totalRead >= s.limit {
      return 0, ErrBodyTooLarge
  }
  ```
  In [`pkg/server/activity_reader.go:71-74`](../../pkg/server/activity_reader.go):
  ```go
  if a.remaining <= 0 && a.totalRead > 0 {
      a.mu.Unlock()
      return 0, httpparser.ErrBodyTooLarge
  }
  ```
- **Description**:
  In `StreamingBodyReader.Read`, the check `s.totalRead >= s.limit` precedes the `s.contentLength` EOF completion check. When a client uploads a payload whose exact byte size equals `s.limit` (e.g. exactly 4,194,304 bytes on a 4MB ceiling), all 4,194,304 bytes are read successfully. However, on the final read call to detect stream completion, `s.totalRead >= s.limit` evaluates to true, returning `ErrBodyTooLarge` instead of returning `io.EOF`.
  Similarly, in `activityReader.Read`, when cumulative bytes read reach `limit`, `a.remaining` reaches 0, causing the subsequent read to trigger `a.remaining <= 0 && a.totalRead > 0` and return `httpparser.ErrBodyTooLarge`.
- **Impact**:
  False-positive Denial of Service: Legitimate client uploads whose size exactly matches the configured limit are rejected with `HTTP 413 Payload Too Large` instead of succeeding with `HTTP 200 OK`.
- **Recommendation**:
  Evaluate the `contentLength` EOF check before the limit check in `StreamingBodyReader`, change `>=` to `>`, and in `activityReader` change `<=` to `<`.
- **Required Action**: Fix the boundary comparison operators in `StreamingBodyReader.Read` and `activityReader.Read` and add unit tests verifying exact-limit uploads succeed.

### SR-145-F08: Unconditional Socket Termination on Clean Stream EOF in Activity Reader

- **Finding ID**: `SR-145-F08`
- **Severity**: **Medium**
- **Category / CWE**: [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Uncontrolled Resource Consumption) / [CWE-775](https://cwe.mitre.org/data/definitions/775.html) (Missing Release of File Descriptor or Handle)
- **Location**: [`pkg/server/activity_reader.go:82-87`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.3 FR-145-3`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md), [`TASK-171 WP-1`](../tasks/TASK-171.md), [`CR-145`](../codeReview/CR-145.md) (CR-145-F02)
- **Evidence**:
  In [`pkg/server/activity_reader.go:82-87`](../../pkg/server/activity_reader.go):
  ```go
  n, err := a.r.Read(p)
  a.mu.Lock()
  defer a.mu.Unlock()
  if err != nil {
      if a.conn != nil {
          _ = a.conn.Close()
      }
      return n, err
  }
  ```
- **Description**:
  In `activityReader.Read()`, if the underlying buffered reader returns any error, including normal EOF (`err == io.EOF`), it immediately calls `_ = a.conn.Close()`.
  When a client cleanly finishes its upload stream (e.g. sending a TCP FIN / half-close via `SHUT_WR`), `activityReader` immediately closes the entire socket.
  When the server subsequently attempts to write the HTTP response via `res.Serialize(conn)` (e.g. `server.go:498`), the write fails with `use of closed network connection` or `broken pipe`. In addition, persistent keep-alive connections are prematurely terminated on stream EOF.
- **Impact**:
  Prevents clean HTTP response transmission to streaming clients and breaks keep-alive connection reuse.
- **Recommendation**:
  Update `activityReader.Read` to exclude `io.EOF` from triggering socket closure: `if err != nil && !errors.Is(err, io.EOF)`.
- **Required Action**: Modify `activityReader.go:83` to ensure clean `io.EOF` does not close the client connection.

### SR-145-F10: Wire Framing Overhead Miscalculated Against Uncompressed Body Limit in Chunked Ingestion

- **Finding ID**: `SR-145-F10`
- **Severity**: **Low**
- **Category / CWE**: [CWE-20](https://cwe.mitre.org/data/definitions/20.html) (Improper Input Validation / Framing Overhead Clamping)
- **Location**: [`pkg/server/server.go:365-367`](../../pkg/server/server.go) and [`pkg/server/activity_reader.go:94-102`](../../pkg/server/activity_reader.go)
- **Related Artifacts**: [`REQ-145 §2.2 FR-145-2 §4`](../requirements/REQ-145.md), [`ADR-145 §2 Decision 3`](../architecture/ADR-145.md), [`TASK-171 WP-1`](../tasks/TASK-171.md), [`CR-145`](../codeReview/CR-145.md) (CR-145-F05)
- **Evidence**:
  In [`pkg/server/server.go:365-367`](../../pkg/server/server.go):
  ```go
  actReader := newActivityReader(br, conn, tracker, effectiveReadTimeout, effectiveMaxBody)
  chunkedBufr := bufio.NewReader(actReader)
  req.Body = httpparser.NewChunkedBodyReader(chunkedBufr, conn, effectiveMaxBody)
  ```
- **Description**:
  `activityReader` measures raw socket wire bytes (which include chunk hexadecimal lengths, CRLF delimiters, and trailing chunks) against `effectiveMaxBody`. However, `effectiveMaxBody` represents the uncompressed HTTP payload body limit. For large chunked uploads near the ceiling (e.g. 256MB), the protocol framing overhead pushes total wire bytes past `effectiveMaxBody`, causing `activityReader` to abort with `ErrBodyTooLarge` before `ChunkedBodyReader` decodes the valid payload.
- **Impact**:
  Valid chunked uploads whose uncompressed body is strictly within `max_body_bytes` can be prematurely aborted due to framing overhead.
- **Recommendation**:
  Pass `0` (or `limit * 105 / 100`) as the ceiling to `activityReader` when wrapping chunked streams, allowing `ChunkedBodyReader` to govern the decoded payload body limit.
- **Required Action**: Pass `0` to `newActivityReader` in `server.go:365` when initializing chunked readers.

## 6. Review Verdict & Recommendations

### **Status**: `approved_with_findings`

The implementation of Option 1 demonstrates exceptional engineering quality and sound core architecture. The two-phase ingestion pipeline, pre-read fast-fail checks, activity-refreshed read deadlines, and route bulkhead isolation successfully fulfill the primary security requirements of [`REQ-145`](../requirements/REQ-145.md) and [`ADR-145`](../architecture/ADR-145.md).

However, three **High** severity vulnerabilities and five **Medium** severity defects must be resolved before releasing this feature to production environments:
1. **SR-145-F01**: Align chunked streaming heuristics between `config.go` and `proxy.go` to eliminate `io.ReadAll` heap buffering on chunked uploads.
2. **SR-145-F02**: Implement pre-read `Content-Length` validation and bulkhead concurrency gating in `http2AdapterHandler`.
3. **SR-145-F03**: Prevent HTTP request smuggling by closing connections with unconsumed chunked bodies.
4. **SR-145-F04**: Implement downstream socket closure monitoring to cancel upstream backend contexts during extended execution.
5. **SR-145-F05**: Fix the `routeInfo.RouteType` comparison in `server.go:387` to ensure write deadline decoupling applies to standard upstream routes.
6. **SR-145-F06**: Clamp socket read deadlines to `effectiveReadTimeout` prior to body reading on keep-alive connections.
7. **SR-145-F07**: Fix off-by-one operators in `StreamingBodyReader` and `activityReader` to prevent exact-limit payload rejections.
8. **SR-145-F08**: Exclude clean `io.EOF` from triggering socket closure in `activityReader`.
