# TC-147 - Test Cases for Alerts Control Center Dual-Card Separation, Multi-Action Status Badging, and Rate-Limiting Telemetry

## 1. Description & Overview

### 1.1 Executive Summary & Problem Context
The Toron Control Center dashboard at `#/alerts` serves as the centralized operations console for edge security monitoring, automated threat defense, and operational infrastructure health awareness. Following the implementation of the Alerts Control Center redesign ([REQ-146](../requirements/REQ-146.md) / [ADR-146](../architecture/ADR-146.md)), site reliability engineers and security operators reported a critical visibility defect in active edge deployments:
> *"The current alert dashboard is showing no events other than blocked."*

Root-cause analysis in [AN-008](../analysis/AN-008.md) and requirement analysis in [REQ-147](../requirements/REQ-147.md) established five structural factors causing event homogeneity and alert suppression:
1. **Frontend Mutual Exclusion Fallback (`public/js/views/alerts.js`)**: The incident list controller evaluated a ternary fallback:
   ```javascript
   const incs = (model.incidents && model.incidents.length > 0) ? model.incidents : (model.alerts || []);
   ```
   Because public-facing gateways continuously intercept background web scanners and keep up to 50 events in the in-memory circular buffer (`AuditLogger`), `model.incidents` is virtually never empty. As a result, `model.alerts` was discarded. Critical operational health alerts (unhealthy upstream pool backends, route 5xx error spikes exceeding 2%, and failing ACME SSL certificate renewals) were completely suppressed from the feed, despite triggering the top KPI strip, the navigation badge (`1`), and the Overview status banner.
2. **Binary Action Badging Oversimplification**: Both `alerts.js` and the forensic investigation drawer (`public/js/components/drawer.js`) evaluated defensive mitigation using binary logic (`isBlocked ? 'Blocked' : 'Logged'`). Automated IP quarantine events (`Action: "banned"`) emitted by the auto-ban subsystem were mislabeled as `Logged`, obscuring active firewall quarantines.
3. **WAF Scoring Saturation in Enforce Mode**: Under default gateway settings (`Mode == "enforce"`, `AnomalyThreshold == 5`), all built-in OWASP rules carry `Score: 5`. Any rule match triggers a block (`Action: "blocked"`), yielding zero detection-only anomalies (`Action: "logged"`).
4. **Rate-Limiting Telemetry Void**: Volumetric traffic throttling rejections (HTTP 429 Too Many Requests) served by route-level token bucket rate limiters (`pkg/router/rate_limiter.go`) did not emit audit telemetry to `AuditLogger`, leaving rate mitigation entirely unrepresented in threat telemetry.
5. **Warning Filter Emptiness**: Because operational alerts were suppressed by the ternary conditional, rate limiting emitted no events, and WAF rules triggered blocks, selecting the "Warning" severity facet chip yielded an empty state message (*"Zero security incidents match active filters"*), falsely signaling that warning-level telemetry and anomaly monitoring were non-functional.

### 1.2 Purpose of Test Specification
This test specification defines the formal verification suite for [REQ-147](../requirements/REQ-147.md), [ADR-147](../architecture/ADR-147.md), and [TASK-175](../tasks/TASK-175.md), establishing focused, executable, and traceable test cases to validate that:
- Operational health alerts and security incidents are decoupled into a dual-card presentation where operational alerts are permanently visible and never suppressed by incidents.
- When zero operational alerts exist, the Operational System Alerts card renders a compact, positive health status summary (*"All upstream services, routes, and certificates operating normally"*).
- The incidents feed and forensic drawer implement an explicit 4-action defense taxonomy (`Blocked`, `Banned`, `Throttled`, `Logged`) with dedicated badge classes and tone icons.
- Real-time severity facet chips deterministically partition events between `Critical` and `Warning` tiers, eliminating the empty warning filter defect and resetting pagination.
- Route-level token bucket rate limiting dispatches structured `SecurityEvent` payloads to `*waf.AuditLogger` upon HTTP 429 drops, appearing in `GET /internal/api/security/incidents`.
- Operational alert rows provide actionable `data-go` targets routing directly to upstream, route, or certificate management views.
- Total client JavaScript across `public/js/` strictly adheres to the $\le 120.0\text{ KB}$ ($122,880\text{ bytes}$) hard ceiling.
- All existing verification test cases in `TC-146` (`TC-146-01` through `TC-146-10`) continue to pass with zero regressions.
- Documentation links strictly adhere to relative path rules.

### TC-147-01: Dual-Card UI Separation & Operational Alert Non-Suppression

- **Identifier**: `TC-147-01`
- **Target Component**: [`public/js/views/alerts.js`](../../public/js/views/alerts.js) (`alShell`, `alUpdate`)
- **Verifies**:
  - [`REQ-147 §4 AC-147-01`](../requirements/REQ-147.md)

  - [`TASK-175 §3 SUBTASK-175-1`](../tasks/TASK-175.md)
  - [`ADR-147 §1 Decisions 1.1, 1.2, 1.5`](../architecture/ADR-147.md)
- **Preconditions**:
  1. Simulated DOM environment initialized with view container `#view`.
  2. Data model contains:
     - 2 active operational alerts in `model.alerts`:
       - Alert 1: `{ id: 'upstream_api_pool', sev: 'critical', title: 'Upstream Degradation: api-pool', desc: '2/3 instances unreachable', timestamp: '2026-09-29T08:00:00Z', go: 'upstreams' }`
       - Alert 2: `{ id: 'route_5xx_auth', sev: 'warning', title: 'High 5xx Error Rate: /v1/auth', desc: '5xx rate 4.2% > 2.0% SLO', timestamp: '2026-09-29T08:05:00Z', go: 'routes' }`
     - 10 active security incidents in `model.incidents` (simulating active WAF scanner intercepts).
- **Test Data & Inputs**:
  ```javascript
  const mockAlerts = [
    {
      id: "upstream_api_pool",
      sev: "critical",
      title: "Upstream Degradation: api-pool",
      desc: "2/3 instances unreachable",
      timestamp: "2026-09-29T08:00:00Z",
      go: "upstreams"
    },
    {
      id: "route_5xx_auth",
      sev: "warning",
      title: "High 5xx Error Rate: /v1/auth",
      desc: "5xx rate 4.2% > 2.0% SLO",
      timestamp: "2026-09-29T08:05:00Z",
      go: "routes"
    }
  ];
  const mockIncidents = Array.from({ length: 10 }, (_, i) => ({
    id: `inc-waf-${i + 1}`,
    client_ip: `198.51.100.${i + 1}`,
    rule_id: "942100",
    category: "SQL Injection",
    action: "blocked",
    anomaly_score: 15,
    timestamp: "2026-09-29T08:10:00Z"
  }));
  ```
- **Execution Steps**:
  1. Mount the alerts view shell via `alShell()`.
  2. Assert DOM contains two distinct `<section class="card">` containers:
     a. Card 1 (`#alOpsCard`): Operational System Alerts card positioned above Card 2.
     b. Card 2 (`.al-inc-card`): Security Incidents & Threat Defense feed card.
  3. Execute `alUpdate({ alerts: mockAlerts, incidents: mockIncidents, bannedIps: [] })`.
  4. Query the operational alerts container: `$('#alOpsList') || $('#alOpList')`.
  5. Assert operational alert list item count equals exactly 2.
  6. Query the security incidents container: `$('#alIncList')`.
  7. Assert security incident list item count equals 10 (matching the page size).
  8. Inspect the rendered operational alert rows:
     a. Row 1 renders title `Upstream Degradation: api-pool`, description `2/3 instances unreachable`, error tone icon (`t-err` `i-x`), and `data-go="upstreams"`.
     b. Row 2 renders title `High 5xx Error Rate: /v1/auth`, description `5xx rate 4.2% > 2.0% SLO`, warning tone icon (`t-warn` `i-alert`), and `data-go="routes"`.
  9. Simulate typing into incident search input (`#alIncSearch`) or clicking severity facet chips (`#alSevChips`).
  10. Assert `#alOpsList` remains completely unchanged with exactly 2 operational alerts visible.
- **Expected Results**:
  - Operational health alerts and security incidents render simultaneously in dedicated cards.
  - Presence of 10 security incidents in `model.incidents` does NOT suppress or hide `model.alerts`.
  - Mutual exclusion ternary fallback is completely eliminated.
- **Pass / Fail Criteria**:
  - **Pass**: `#alOpsList` contains exactly 2 operational alerts and `#alIncList` contains 10 incidents; search/filtering on incidents leaves operational alerts intact.
  - **Fail**: Operational alerts card is absent, `#alOpsList` has 0 rows when incidents exist, or operational alerts disappear when incidents are populated.

This provides instant visual confirmation of system health without consuming excessive screen real estate.
3. **Circular Ring Buffer Under Volumetric DDoS**:
   - *Assumption*: Route-level rate limiter drops write directly into `AuditLogger`'s 50-event ring buffer with $O(1)$ overwrite. Under high-velocity attacks, oldest events are dropped cleanly without memory leaks or unbounded growth.
