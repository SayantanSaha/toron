# ADR-087 - Physical Connection Identity Binding & Trusted Proxy Gating

## Context & Problem Statement

Toron Edge Gateway supports multi-protocol ingress, including high-performance HTTP/1.1 cleartext/TLS via a custom non-blocking reactor, multiplexed HTTP/2 streams via standard library adapters, and HTTP/3 over QUIC UDP datagrams ([`server.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go)).

During security audit [`SR-091 Finding 1`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L78-L99) and vulnerability assessment [`SEC-31`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L428-L436) ([CWE-290 Authentication Bypass by Spoofing](https://cwe.mitre.org/data/definitions/290.html), [CWE-345 Insufficient Verification of Data Authenticity](https://cwe.mitre.org/data/definitions/345.html), [CWE-693 Protection Mechanism Failure](https://cwe.mitre.org/data/definitions/693.html)), a critical systemic vulnerability was discovered across Toron's core request model and protocol ingress layer:

1. **Missing Physical Address in Request Model**: In [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70), client network identity was coupled solely to the physical socket descriptor field `RawConn net.Conn`. The struct lacked an explicit `RemoteAddr string` field.
2. **Adapter Address Disconnect in HTTP/2 and HTTP/3**: In [`http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L313-L353) and [`ListenAndServeH3`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L406-L437), incoming requests arrive as standard library `*http.Request` instances and are transformed into Toron requests via [`httpparser.NewRequestFromStd(r)`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L124). Because multiplexed HTTP/2 streams and HTTP/3 QUIC datagrams do not map 1:1 to dedicated TCP socket connections, `req.RawConn` was left as `nil`. Furthermore, `NewRequestFromStd(r)` discarded `r.RemoteAddr`.
3. **Incomplete HTTP/1.1 Reactor Binding**: In [`handleConn`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L240), `req.RawConn = conn` was set, but no `RemoteAddr` string was populated on `req`.
4. **Catastrophic Header Fallback Across Security Perimeter**: Throughout the gateway, security-critical modules checked `if req.RawConn != nil`. Because `req.RawConn` is always `nil` for HTTP/2 and HTTP/3 traffic:
   - **WAF IP Access Control** ([`ip_acl.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L112-L164)): Evaluated `req.RawConn == nil` as true and immediately trusted client-supplied `X-Forwarded-For` and `X-Real-IP` headers.
   - **Internal Management API Subnet Enforcement** ([`internal_api.go:wrapHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L194-L224)): Fell back to parsing unverified `X-Forwarded-For` headers.
   - **Token Bucket Rate Limiting** ([`rate_limiter.go:extractClientKeyInternal`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L286-L325)): Line 314 explicitly evaluated `if peerIsTrusted || req.RawConn == nil`. For all HTTP/2 and HTTP/3 requests, `req.RawConn == nil` evaluated to `true`, causing the rate limiter to unconditionally trust client-supplied `X-Forwarded-For`, `X-API-Key`, and `Authorization` headers.
   - **Reverse Proxy Forwarding** ([`proxy.go:ServeHTTPWithPrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L816-L857)): Because `req.RawConn` was `nil`, `peerIP` remained empty, causing lines 853-857 to forward untrusted client `X-Forwarded-For` and `X-Real-IP` headers directly to upstream targets.
   - **Structured Access Logging** ([`manager.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/logging/manager.go#L498-L531)): Fell back to client-supplied `X-Forwarded-For` and `X-Real-IP` when `req.RawConn == nil`, allowing spoofed headers to pollute audit logs.

### Exploitability & Threat Model

| Threat Vector | Attack Scenario | Consequence |
| :--- | :--- | :--- |
| **WAF IP ACL Bypass** | An attacker blocked by WAF IP ACL connects via HTTP/2 or HTTP/3 and supplies `X-Forwarded-For: 198.51.100.1` to impersonate an unblocked IP. | Total bypass of IP blacklists and allowlists. |
| **Admin API Subnet Evasion** | An unauthenticated external client hits `/internal/api/*` via HTTP/2 with `X-Forwarded-For: 10.0.0.5`. | Complete circumvention of CIDR restrictions on admin management endpoints. |
| **Distributed DoS via Rate Limit Evasion** | An attacker issues high-volume HTTP/2 requests while rotating `X-Forwarded-For: 10.0.X.Y` or `X-API-Key: key-X` on each request. | Toron allocates a fresh rate limiter bucket per request, defeating rate limiting entirely. |
| **Upstream Log & Audit Poisoning** | An untrusted HTTP/2 client injects spoofed IP headers forwarded untouched to upstream microservices. | Poisoned backend audit trails, compromised regulatory compliance, and spoofed internal trust chains. |

## Architectural Decisions

### 1. Request Model Extension & Address Resolution Helpers (`pkg/httpparser/request.go`)

We extend [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70) with an exported `RemoteAddr string` field and two physical resolution methods:

```go
type Request struct {
    Method        string
    RequestURI    string
    URL           *url.URL
    Path          string
    Proto         string
    Header        Header
    QueryParams   url.Values
    Body          io.Reader
    ContentLength int64
    RawConn       net.Conn
    RemoteAddr    string // Physical client network address ("IP:port") assigned at transport ingress
}
```

#### Physical Address Resolution Helpers

- **`RemoteHost() string`**:
  1. If `r.RemoteAddr` is non-empty:
     - Extracts host via `net.SplitHostPort(r.RemoteAddr)`.
     - If `net.SplitHostPort` returns an error (e.g. bare IP without port or malformed port syntax), falls back to `strings.TrimSpace(r.RemoteAddr)`.
  2. If `r.RemoteAddr` is empty and `r.RawConn != nil && r.RawConn.RemoteAddr() != nil`:
     - Extracts host from `r.RawConn.RemoteAddr().String()` via `net.SplitHostPort` with bare string fallback.
  3. Returns `""` if neither `RemoteAddr` nor `RawConn` provides an address.

- **`RemoteIP() net.IP`**:
  1. Obtains the host string by calling `r.RemoteHost()`.
  2. Strips surrounding IPv6 square brackets (`"["` and `"]"`) if present.
  3. Parses the string via `net.ParseIP`.
  4. Returns a valid `net.IP` (supporting IPv4 and IPv6) or `nil` if the string is empty or unparseable.

#### Invariant: Request Immutability & Concurrency Safety
`RemoteAddr` is populated once during request construction at transport ingress and remains immutable throughout the request lifecycle. Middlewares, router handlers, transcoders, and reverse proxies perform read-only access on `RemoteAddr`, `RemoteHost()`, and `RemoteIP()`, guaranteeing zero data races under concurrent execution (`go test -race ./...`).

### 2. Ingress Protocol Binding & Protocol Parity (`pkg/server/server.go`)

We establish complete protocol parity across all transport ingress handlers:

1. **Standard Library Request Conversion (`pkg/httpparser/request.go:NewRequestFromStd`)**:
   ```go
   req := &Request{
       Method:      r.Method,
       RequestURI:  reqURI,
       URL:         r.URL,
       Path:        path,
       Proto:       r.Proto,
       Header:      make(Header),
       QueryParams: queryParams,
       Body:        bytes.NewReader(nil),
       RemoteAddr:  r.RemoteAddr, // Preserve physical transport address
   }
   ```
2. **HTTP/2 Ingress Adapter (`pkg/server/server.go:http2AdapterHandler`)**:
   All incoming HTTP/2 requests converted via `NewRequestFromStd(r)` inherit `r.RemoteAddr` from the underlying TLS connection. Multiplexed streams sharing a connection have identical, verified `RemoteAddr` bindings.
3. **HTTP/3 QUIC Ingress Adapter (`pkg/server/server.go:ListenAndServeH3`)**:
   HTTP/3 QUIC requests handled through `http2AdapterHandler` inherit `r.RemoteAddr` corresponding to the client's UDP datagram address (`IP:port`).
4. **HTTP/1.1 Native Server Reactor (`pkg/server/server.go:handleConn`)**:
   When accepting and processing HTTP/1.1 connections:
   ```go
   req.RawConn = conn
   if conn != nil && conn.RemoteAddr() != nil {
       req.RemoteAddr = conn.RemoteAddr().String()
   }
   ```

### 3. Hardened Security Perimeter Enforcement Across Subsystems

We systematically eliminate unverified header trust across all perimeter modules, anchoring client identity to verified physical connection metadata unless originating from an authenticated `trusted_proxies` CIDR:

#### 3.1. WAF IP Access Control (`pkg/waf/ip_acl.go:ExtractClientIP`)
- Ground client IP extraction in `req.RemoteIP()`, falling back to `req.RemoteAddr` and `req.RawConn`.
- Client-supplied `X-Forwarded-For` and `X-Real-IP` headers MUST NOT be evaluated when a physical remote address is present, unless the physical IP is verified against configured `trusted_proxies`.
- For synthetic unit test requests without physical connection information (`req.RemoteAddr == ""` and `req.RawConn == nil`), safe fallback to forwarded headers is preserved for test harnesses only.
- Fail-secure invariant: If client IP cannot be extracted and an IP allowlist is enforced, access is denied by default.

#### 3.2. Internal Management API Subnet Gate (`pkg/server/internal_api.go:wrapHandler`)
- Ground client IP validation in `req.RemoteIP()` / `req.RemoteAddr` / `req.RawConn`.
- Completely eliminate the insecure fallback to `X-Forwarded-For` when `req.RawConn == nil`.
- Only evaluate `X-Forwarded-For` if the physical peer IP is confirmed to belong to a configured trusted proxy subnet.
- Fail-closed invariant: If client IP cannot be resolved or does not fall within `parsedSubnets`, reject immediately with `403 Forbidden` (`{"error":"403 Forbidden","message":"Access denied by administrative subnet policy"}`).

#### 3.3. Token Bucket Rate Limiting (`pkg/router/rate_limiter.go:extractClientKeyInternal`)
- Eliminate the insecure condition `peerIsTrusted || req.RawConn == nil`.
- Resolve `socketIP` and `socketHost` by inspecting `req.RemoteIP()` / `req.RemoteAddr` alongside `req.RawConn`.
- Check `socketIP` against configured `trustedProxies`.
- **Untrusted Peer Enforcement**:
  - If `peerIsTrusted == false`:
    - When a physical remote address is present (`socketHost != ""`), anchor the rate limit key strictly to `"ip:" + socketHost`.
    - Client-supplied `X-Forwarded-For`, `X-API-Key`, and `Authorization` headers MUST be ignored for bucket selection. Rotating headers from an untrusted peer maps to the same client bucket, preventing rate limit bypass.
- **Trusted Peer Delegation**:
  - If `peerIsTrusted == true`:
    - Honor `X-Forwarded-For`, `X-API-Key`, or `Authorization` headers as requested.
- For synthetic test requests lacking network metadata, maintain safe non-evadable defaults.

#### 3.4. Reverse Proxy Forwarding & Header Sanitization (`pkg/proxy/proxy.go:ServeHTTPWithPrefix`)
- Resolve `peerIP` and `isTrusted` by inspecting `req.RemoteAddr` and `req.RawConn.RemoteAddr()`.
- Derive protocol (`X-Forwarded-Proto`) accurately for HTTP/2 and HTTP/3 (`https`).
- **Untrusted Peer Sanitization**:
  - When `isTrusted == false`:
    - Outgoing upstream `X-Forwarded-For` is set strictly to `peerIP`.
    - Outgoing upstream `X-Real-IP` is set strictly to `peerIP`.
    - Client-supplied `X-Forwarded-For` and `X-Real-IP` headers are stripped and discarded.
- **Trusted Proxy Header Chaining**:
  - When `isTrusted == true`:
    - If incoming `X-Forwarded-For` exists, append `peerIP` (`existingXFF + ", " + peerIP`).
    - If incoming `X-Real-IP` exists, preserve it.

#### 3.5. Structured Access Logging (`pkg/logging/manager.go:ExtractClientIP`)
- Inspect `req.RemoteHost()` / `req.RemoteAddr` and `req.RawConn` before inspecting forwarded headers.
- Return the true physical remote client IP for untrusted connections, preventing spoofed headers from corrupting audit logs.

### 4. Non-Goal Enforcement & Mobile Roaming Session Affinity (`pkg/proxy/sticky.go`)

> [!IMPORTANT]
> **Strict Scope Boundary**: Under NO circumstances shall [`pkg/proxy/sticky.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/sticky.go) be modified under REQ-092 or this ADR.

#### Architectural Separation: Security Perimeter vs. Traffic Steering
1. **Security Enforcement Components** ([`ip_acl.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go), [`internal_api.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go), [`rate_limiter.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go), [`proxy.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go), [`manager.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/logging/manager.go)):
   - Guard system trust boundaries, access control, and audit integrity.
   - Must strictly bind to physical network addresses unless explicitly authenticated via `trusted_proxies`.
2. **Session Affinity Load Balancer** ([`sticky.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/sticky.go)):
   - Performs application-level traffic steering to preserve stateful upstream session affinity ([`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md)).
   - Mobile devices connecting via cellular carriers routinely experience dynamic IP churn due to CGNAT re-assignment, tower handoffs, and Wi-Fi/LTE transitions.
   - Forcing `sticky.go` to bind strictly to physical socket addresses would cause mobile clients to lose upstream session persistence on every network handoff.
   - Preserving `pkg/proxy/sticky.go:extractClientIP` guarantees full backward compatibility and strict compliance with [`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md).

## Alternatives Considered & Trade-offs

### Alternative 1: Synthetic `net.Conn` Wrapper for HTTP/2 Streams and HTTP/3 Datagrams
- **Description**: Wrap the multiplexed stream or datagram connection inside a dummy `net.Conn` implementation that provides a non-nil `RemoteAddr() net.Addr`, attaching it to `req.RawConn`.
- **Trade-offs & Drawbacks**:
  - Violates the core transport abstraction: multiplexed streams are not byte-stream TCP connections.
  - Calling `Read`, `Write`, `Close`, `SetDeadline` on a synthetic `net.Conn` leads to undefined behavior, resource leaks, or unexpected stream terminations.
  - Clutters connection ownership and complicates clean socket shutdown routines.
- **Decision**: **Rejected**. Explicitly exposing `RemoteAddr string` on `httpparser.Request` cleanly decouples network address identity from physical socket descriptor ownership.

### Alternative 2: Ingress Middleware Context Rewriting
- **Description**: Execute a router-level middleware that inspects incoming requests, parses the client IP, rewrites headers or sets request context values, and passes the modified request downstream.
- **Trade-offs & Drawbacks**:
  - Modifying headers at router ingress mutates client request headers before routing decisions are made, destroying header provenance and violating audit trail fidelity.
  - Adding Go `context.Context` allocations per request introduces garbage collection pressure on high-throughput hot paths.
  - If any internal handler or protocol bypasses the router middleware (e.g. administrative endpoints or health checks), the protection is lost.
- **Decision**: **Rejected**. Embedding physical binding directly in `httpparser.Request` ensures immutable, ubiquitous availability across all router and server pathways with zero heap allocations.

### Alternative 3: Universal Physical Binding Across ALL Components (Including `sticky.go`)
- **Description**: Update `pkg/proxy/sticky.go:extractClientIP` to strictly bind to physical socket address, ignoring client-supplied headers unconditionally.
- **Trade-offs & Drawbacks**:
  - Breaks mobile roaming session affinity ([`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md)). Mobile users traversing cellular towers or transitioning between Wi-Fi and 5G experience IP churn, causing session hash drift and constant session drops.
  - Conflates load balancing steering with security authorization.
- **Decision**: **Rejected**. `sticky.go` is preserved untouched pursuant to REQ-092 Non-Goals.

### Alternative 4: Unconditional Private IP / RFC 1918 Heuristic Trust
- **Description**: Trust `X-Forwarded-For` whenever the incoming socket IP falls within private IP ranges (e.g. `10.0.0.0/8`, `192.168.0.0/16`) without requiring explicit `trusted_proxies` configuration.
- **Trade-offs & Drawbacks**:
  - In cloud environments, VPCs, and Kubernetes clusters, untrusted tenants or compromised pods frequently share private subnets. Blindly trusting RFC 1918 addresses creates an immediate security vulnerability in shared infrastructure.
- **Decision**: **Rejected**. Strict CIDR matching against explicitly configured `trusted_proxies` is required.

## Constraints & Security Invariants

1. **Protocol Parity**: Security controls MUST enforce identical client IP authentication guarantees across HTTP/1.1, HTTP/2, and HTTP/3.
2. **Fail-Closed & Fail-Secure Defaults**:
   - Administrative subnet checks in [`internal_api.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go) MUST fail closed with `403 Forbidden` if client IP cannot be extracted or verified.
   - WAF IP allowlists MUST fail secure, denying access when client IP cannot be resolved.
3. **Immutability & Race Freedom**:
   - `req.RemoteAddr` is set once upon request construction and remains read-only.
   - Zero data races under `go test -race ./...`.
4. **Zero Third-Party Dependencies**:
   - Strictly pure Go standard library packages (`net`, `net/http`, `strings`, `sync`). Zero external dependencies.
5. **Zero Performance Regression**:
   - Address resolution helpers use `net.SplitHostPort` and zero-allocation string slicing, introducing zero measurable latency overhead on request hot paths.
