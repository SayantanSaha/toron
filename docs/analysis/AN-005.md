# AN-005 - Bug Analysis: WAF Hot-Reload AutoBanManager Pointer Desynchronization & False Positive Lockout

## 1. Executive Summary

- **Bug Identifier**: `BUG-WAF-001`
- **Component**: `pkg/waf` (`WAFEngine`, `AutoBanManager`), `pkg/server` (`InternalAPIConfig`), and `cmd/toron` (`main.go`).
- **Severity**: **High** (Causes administrative lockout and prevents unbanning blocked IP addresses after configuration hot reloads).
- **Symptom**: When an administrator or client triggers an auto-ban rule during testing or normal operation, and the configuration file (`config.yaml`) is subsequently reloaded (or was reloaded prior to the ban), attempting to unban the IP via `POST /internal/api/security/unban` reports success (`{"status":"ok"}`), yet incoming requests from that IP remain rejected with `HTTP 403 Forbidden` (`{"ban_type": "temporary"}`). The ban cannot be lifted via API and re-persists to disk on the next sweeper cycle.
- **Root Cause**: During zero-downtime hot reload, `WAFEngine.Reload()` instantiates a brand new `AutoBanManager` instance (`e.autoBanMgr = autoBan`) and closes the previous instance. However, `InternalAPIConfig.AutoBanManager` in the server layer retains a static pointer to the initial instance created at application startup. Consequently:
  1. Administrative management mutations (`/internal/api/security/unban`) operate exclusively on the orphaned, closed instance.
  2. Active traffic inspection in `WAFMiddleware` queries the active `WAFEngine.AutoBanManager()`, continuing to enforce the in-memory ban.
  3. Periodic background sweeper flushes (`sweepExpiredBans()`) from the active manager overwrite `/etc/toron/banned_ips.json` with the active in-memory state, canceling out any disk modifications made by the orphaned manager.
- **Resolution**:
  1. Add dynamic resolver `AutoBanManagerFunc func() *waf.AutoBanManager` and accessor `GetAutoBanManager()` to `InternalAPIConfig`.
  2. Implement in-place configuration updates via `AutoBanManager.UpdateConfig()` so that `WAFEngine.Reload()` preserves the existing manager instance, in-memory strikes, and active bans without recreating objects or orphaning pointers.

---

## 2. Problem Statement & Symptoms

### 2.1. Observed Behavior
1. A client IP triggers a WAF security rule (for example, a test request matching a custom rule).
2. Because `auto_ban.max_violations` is reached (e.g. set to `1`), the client IP is automatically assigned a temporary ban.
3. The administrator attempts to unban the IP via the Control Center dashboard or management API (`POST /internal/api/security/unban`).
4. The API responds with:
   ```json
   {
     "status": "ok",
     "message": "IP successfully unbanned"
   }
   ```
5. Despite the successful API response, all subsequent requests from the client IP continue to fail with:
   ```json
   {
     "error": "Forbidden",
     "message": "Client IP address has been banned due to repeated security violations",
     "ban_type": "temporary"
   }
   ```
6. Inspecting the persistence file (`banned_ips.json`) reveals that even if the IP was temporarily cleared, it reappears in the file within 30 seconds.

---

## 3. Detailed Root Cause Analysis

### 3.1. Pointer Invalidation During Hot Reload
Toron provides zero-downtime hot reloading via `config.ConfigWatcher`. When `config.yaml` changes on disk:

1. `ConfigWatcher` invokes the reload callback in `cmd/toron/main.go`:
   ```go
   globalWafEngine.Reload(globalWafCfg)
   ```

2. Inside `pkg/waf/waf.go` (`Reload`), a completely new `AutoBanManager` was constructed from scratch:
   ```go
   var autoBan *AutoBanManager
   if cfg.AutoBan.Enabled {
       autoBan, err = NewAutoBanManager(cfg.AutoBan, logger)
   }
   // ...
   if e.autoBanMgr != nil {
       _ = e.autoBanMgr.Close()
   }
   e.autoBanMgr = autoBan
   ```

3. However, during server bootstrap in `cmd/toron/main.go`, `srvCfg.AutoBanManager` captured the pointer returned at initialization:
   ```go
   srvCfg := server.Config{
       AutoBanManager: func() *waf.AutoBanManager {
           if globalWafEngine != nil {
               return globalWafEngine.AutoBanManager()
           }
           return nil
       }(),
   }
   ```

4. `server.New(srvCfg, r)` stored this initial pointer inside `InternalAPIConfig.AutoBanManager`.

### 3.2. Bifurcated State Graph

The system entered a split-brain state:

```
[ Incoming Request ]
        │
        ▼
[ WAF Middleware ] ───> engine.AutoBanManager() ───> [ Active AutoBanManager (Instance B) ]
                                                           │ (IP is still banned in memory)
                                                           │
                                                           ▼
                                                    HTTP 403 Forbidden

[ Admin POST /unban ]
        │
        ▼
[ Internal API Handler ] ───> cfg.AutoBanManager ───> [ Orphaned AutoBanManager (Instance A) ]
                                                           │ (Closed, detached from traffic)
                                                           │
                                                           ▼
                                                    HTTP 200 "OK" (Mutates Instance A only)
```

### 3.3. Persistence Clobbering
`AutoBanManager` runs a periodic background cleanup sweeper every 30 seconds (`sweepLoop` -> `sweepExpiredBans`). When changes occur, or when state is saved:
```go
func (m *AutoBanManager) saveStateLocked() error {
    state := PersistentBanState{
        Bans:    m.bans,
        Strikes: m.strikes,
    }
    // Writes state to persistencePath via atomic rename
}
```
Because the active manager (`Instance B`) still had the client IP in its `m.bans` map, any write operation by `Instance B` overwrote `banned_ips.json`, wiping out any deletion executed by `Instance A`.

## 4. Architectural Solution Design

To eliminate the split-brain state and ensure reliable operation across hot reloads, the architecture requires two coordinated mechanisms:

### 4.1. Dynamic Provider Pattern in Server Layer
Replace the static struct field dependency with a dynamic provider function:
```go
type InternalAPIConfig struct {
    // ...
    AutoBanManager     *waf.AutoBanManager        `json:"-"`
    AutoBanManagerFunc func() *waf.AutoBanManager `json:"-"`
}

func (c *InternalAPIConfig) GetAutoBanManager() *waf.AutoBanManager {
    if c.AutoBanManagerFunc != nil {
        return c.AutoBanManagerFunc()
    }
    return c.AutoBanManager
}
```
All management API handlers (`/internal/api/security/*`) call `cfg.GetAutoBanManager()`. In `main.go`, `AutoBanManagerFunc` resolves `globalWafEngine.AutoBanManager()` dynamically on every request.

### 4.2. In-Place Configuration Updates in WAF Engine
Hot-reloading `config.yaml` should not destroy active security runtime state. Modify `AutoBanManager` to support live reconfiguration:

```go
func (m *AutoBanManager) UpdateConfig(cfg AutoBanConfig, logger *AuditLogger)
```

In `WAFEngine.Reload(cfg)`:
- If `e.autoBanMgr != nil` and `cfg.AutoBan.Enabled`:
  Call `e.autoBanMgr.UpdateConfig(cfg.AutoBan, logger)`.
  The existing manager instance is preserved; in-memory strikes and active bans remain intact; no goroutines are orphaned; pointer addresses remain stable.
- If `e.autoBanMgr == nil` and `cfg.AutoBan.Enabled`:
  Instantiate `NewAutoBanManager`.
- If `e.autoBanMgr != nil` and `!cfg.AutoBan.Enabled`:
  Call `e.autoBanMgr.Close()` and set `e.autoBanMgr = nil`.
