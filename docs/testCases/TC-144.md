# TC-144 - Test Suite for AutoBanManager Lifecycle Synchronization Across Hot Reloads

## 1. Test Case Overview

Verifies that the `AutoBanManager` lifecycle, in-memory state, and administrative mutation APIs remain synchronized and fully functional across WAF hot reloads.

---

## 2. Test Cases

### TC-144.1: In-Place AutoBanManager Reconfiguration
- **File**: `pkg/waf/auto_ban_test.go`
- **Method**: `TestAutoBanManager_UpdateConfig`
- **Procedure**:
  1. Initialize `AutoBanManager` with initial thresholds (e.g. `MaxViolations=5`).
  2. Record a violation and create an active ban.
  3. Call `UpdateConfig` with updated thresholds (e.g. `MaxViolations=2`, new whitelist CIDR).
  4. Assert that existing active bans and strike counters are preserved.
  5. Assert that updated thresholds and whitelists take immediate effect.

### TC-144.2: WAF Engine Reload Preserves AutoBanManager
- **File**: `pkg/waf/reload_test.go`
- **Method**: `TestWAFEngine_Reload_PreservesAutoBanManager`
- **Procedure**:
  1. Initialize `WAFEngine` with `AutoBan.Enabled=true`.
  2. Fetch initial `AutoBanManager` pointer.
  3. Add an active ban to the manager.
  4. Invoke `engine.Reload(newCfg)`.
  5. Assert that `engine.AutoBanManager()` returns the identical pointer (`ptrA == ptrB`).
  6. Assert that the pre-existing ban is still present and actively enforced.

### TC-144.3: Management API Dynamic Provider Across Reload
- **File**: `pkg/server/internal_api_test.go`
- **Method**: `TestInternalAPI_AutoBan_DynamicProviderAcrossReload`
- **Procedure**:
  1. Set up test server with `AutoBanManagerFunc`.
  2. Ban an IP address.
  3. Trigger an engine reload.
  4. Send `POST /internal/api/security/unban`.
  5. Assert status 200 and verify that the IP is completely unbanned in the active engine.
