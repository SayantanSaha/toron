# REQ-118 - Latency Distributional Metric Calibration in Report Generation (HARN-02)

## 1. Description & Problem Statement

### 1.1 Executive Summary & Review Critique
In academic and technical peer reviews of the Toron research manuscript (`docs/research/paper1_agentic_systems.tex`), formal review dossiers—specifically the Associate Editor Report ([`AER-001.md`](file:///Users/sneha/Developer/toron-research/docs/research/paperReview/AER-001.md), Adjudication 3 & Issue 2), the Managing Editor Dossier ([`MSR-001.md`](file:///Users/sneha/Developer/toron-research/docs/research/paperReview/MSR-001.md), Defect 1 & FIX-01), and Academic Reviewer Assessment ([`AR-001.md`](file:///Users/sneha/Developer/toron-research/docs/research/paperReview/AR-001.md), FALS-02)—identified critical empirical inconsistencies and distributional reporting ambiguities in Section 5.2.

Specifically, Section 5.2 claimed:
> *"Evaluated across $K=1,000$ repeated statistical trials with a 50-run warm-up discard (BMK-02), Toron achieved a 100.0% invariant pass rate (19/19 tests) with a mean fail-fast rejection latency of 398.71 µs ($p50 = 210.92\ \mu\text{s}$, $p99 = 712.08\ \mu\text{s}$)."* (`paper1_agentic_systems.tex`, lines 434–435)

Auditing of the underlying benchmark harness ([`benchmarks/fuzzer/diff_fuzzer.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/fuzzer/diff_fuzzer.go)) and the committed benchmark artifact ([`benchmarks/results/differential_fuzz_report.json`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/results/differential_fuzz_report.json)) revealed three major methodological discrepancies:
1. **Mode Conflation**: The committed benchmark telemetry was generated in single-shot mode (`trials_per_test: 1`, `warmup_runs_per_test: 0`), yet the manuscript described the resulting cross-vector metrics as if they were derived from $K=1,000$ repeated statistical trials with warm-up discard.
2. **Percentile Mislabeling**: In the 19-vector empirical dataset, $712.08\ \mu\text{s}$ is the 90th percentile ($p90$, corresponding to vector `CONTROL-002`), while the true 99th percentile ($p99$) and tail maximum across all 19 vectors is $2,378.00\ \mu\text{s}$ (corresponding to vector `BASELINE-001`). Mislabelling $p90$ as $p99$ in the manuscript and generating ambiguous summary tables suppressed disclosure of the actual tail distribution.
3. **Conflation of Rejection Defense vs. Baseline Traffic**: The 19 vectors consist of **18 adversarial rejection vectors** (which fail fast with `400 Bad Request`, `403 Forbidden`, `413 Payload Too Large`, `431 Request Header Fields Too Large`, or `501 Not Implemented` and close the connection) and **1 benign baseline vector** (`BASELINE-001`, which returns `200 OK` with `Connection: keep-alive` and transfers full HTTP body payload). `BASELINE-001` took $2,378.00\ \mu\text{s}$, whereas adversarial fail-fast rejections executed between $87.29\ \mu\text{s}$ and $712.08\ \mu\text{s}$. Conflating benign traffic with fail-fast security rejections in aggregated summary metrics distorted both the characterization of defense latency and the cross-vector tail latency.
4. **Suppression of Metrics in Single-Shot Mode**: In `diff_fuzzer.go`, the terminal summary and Markdown report generator suppressed $p50$, $p90$, and $p99$ whenever executed in single-shot mode (`*trials == 1`), only rendering percentiles when `*trials > 1`. Furthermore, when rendered, the Markdown header combined $p90$ and $p99$ into a single line (`Tail Latency (p90 / p99): 712.08 µs / 2378.00 µs`) without separate columnar or contextual breakdown.

### 1.2 Reviewer Citations & Mandates
- **`AER-001.md` (Adjudication 3 & Directive 2)**:
  > *"Either execute `diff_fuzzer.go` with `-trials 1000 -warmup 50` to generate genuine repeated-trial distributions with confidence intervals, or correct Section 5.2 to accurately report single-shot cross-vector metrics, correctly distinguishing $p90$ (712.08 µs) from $p99$ (2,378 µs)."*
- **`MSR-001.md` (Defect 1 & Action FIX-01)**:
  > *"The reported 398.71 µs is the arithmetic mean across 19 single-shot test cases, and the reported 712.08 µs is actually the 90th percentile ($p90$) across those 19 single-shot runs, while the true 99th percentile ($p99$) in that data file is 2,378 µs. Calibrate reporting in `diff_fuzzer.go`."*
- **`AR-001.md` (FALS-02)**:
  > *"Align BMK-02 Claim with Empirical Telemetry... correctly separating cross-vector percentile distribution from repeated trial distribution."*
- **`ReviewTaskSummary.md` (HARN-02 & REV-02)**:
  > *"Update summary table generator in `diff_fuzzer.go` to output $p50$, $p90$, and $p99$ distinctly, matching the actual empirical distribution... Disaggregate fail-fast defense latency (N=18) from baseline traffic (N=19)."*

## 2. Technical Scope & Distributional Taxonomy

To permanently resolve these defects, [`benchmarks/fuzzer/diff_fuzzer.go`](file:///Users/sneha/Developer/toron-research/toron/benchmarks/fuzzer/diff_fuzzer.go) must be calibrated to provide mathematically rigorous, disaggregated, and unambiguous distributional reporting across all execution modes.

```
+--------------------------------------------------------------------------------------------------+
|                            Differential Fuzzer Metric Reporting Pipeline                         |
+--------------------------------------------------------------------------------------------------+
                                                 |
         +---------------------------------------+---------------------------------------+
         |                                                                               |
         v                                                                               v
[ Cohort A: Fail-Fast Defense ]                                         [ Cohort B: Comprehensive Suite ]
  - N = 18 Adversarial Vectors                                            - N = 19 Total Vectors (incl. BASELINE-001)
  - Intercepted with 400/403/413/431/501                                  - Combines rejections + 200 OK baseline
  - Socket closed immediately (conn:closed)                               - Evaluates full testbed response profile
  - Metrics: Mean, p50, p90, Max                                          - Metrics: Mean, p50, p90, p99, Max
```

### 2.1 Cohort Disaggregation: Fail-Fast Rejection vs. Comprehensive Traffic
1. **Fail-Fast Defense Cohort ($N=18$)**:
   - Comprises all adversarial attack and invariant vectors designed to trigger active security enforcement:
     - `SMUGGLE-001` to `SMUGGLE-004` (CWE-444)
     - `WHITESPACE-001` to `WHITESPACE-003` (CWE-444, CWE-436)
     - `CONTROL-001` to `CONTROL-003` (CWE-117)
     - `TRAVERSAL-001` to `TRAVERSAL-003` (CWE-22)
     - `RESOURCE-001` to `RESOURCE-002` (CWE-400)
     - `CACHE-001` and `CACHE-003` (CWE-524)
   - Characteristic: Result in active rejection (`400`, `403`, `413`, `431`, `501`) and connection termination.
   - Evaluated Metrics: Arithmetic Mean, Median ($p50$), 90th percentile ($p90$), and Maximum ($Max$).
2. **Cross-Vector Comprehensive Cohort ($N=19$)**:
   - Comprises the full suite of 19 test cases, including benign reference traffic (`BASELINE-001`, `200 OK`, `Connection: keep-alive`) and passive cache compliance (`CACHE-002`, `200 OK`).
   - Evaluated Metrics: Arithmetic Mean, Median ($p50$), 90th percentile ($p90$), 99th percentile ($p99$), and Maximum ($Max$).

### 2.2 Dual-Mode Percentile Calibration
The fuzzer operates in two distinct execution modes:
- **Mode 1: Single-Shot Verification ($K=1$, $W=0$)**:
  - Each vector executes a single timed run.
  - The distributions reflect **cross-vector variation** across the protocol suite.
  - Percentiles ($p50$, $p90$, $p99$) MUST be calculated across vectors and explicitly output in both the terminal summary and the generated Markdown report.
- **Mode 2: Repeated Statistical Trials ($K > 1$, $W \ge 0$)**:
  - Each vector executes $K$ measured trials following $W$ discarded warm-up runs.
  - Distribution metrics (Mean, StdDev, $p50$, $p90$, $p99$, $p99.9$, 95% Confidence Intervals) are calculated per-vector.
  - Cross-vector distributions are calculated across per-vector median latencies.
  - Terminal and Markdown outputs MUST present both per-vector distributions and cross-vector summary percentiles.

## 3. Functional Requirements

### FR-1: Disaggregated Metric Computation Engine
- `diff_fuzzer.go` shall maintain separate sample sets for:
  1. Fail-fast defensive rejections (all test results where `ActualStatus != 200` and `Passed == true`, or `TestCase.Category != "RFC Conformance Baseline"` and `ActualStatus` indicates rejection).
  2. Cross-vector comprehensive results (all $N=19$ test cases).
- The computation engine shall calculate:
  - For Fail-Fast Defense ($N=18$):
    - `mean_rejection_latency_us`: Arithmetic mean of fail-fast latencies.
    - `p50_rejection_latency_us`: Median (50th percentile) of fail-fast latencies.
    - `p90_rejection_latency_us`: 90th percentile of fail-fast latencies ($712.08\ \mu\text{s}$ under reference data).
    - `max_rejection_latency_us`: Maximum fail-fast latency ($712.08\ \mu\text{s}$ under reference data).
  - For Cross-Vector Comprehensive ($N=19$):
    - `mean_comprehensive_latency_us`: Arithmetic mean across all 19 vectors ($398.71\ \mu\text{s}$ under reference data).
    - `p50_comprehensive_latency_us`: Median across all 19 vectors ($208.75\ \mu\text{s}$ / $210.92\ \mu\text{s}$).
    - `p90_comprehensive_latency_us`: 90th percentile across all 19 vectors ($712.08\ \mu\text{s}$).
    - `p99_comprehensive_latency_us`: 99th percentile tail across all 19 vectors ($2,378.00\ \mu\text{s}$).
    - `max_comprehensive_latency_us`: Maximum latency across all 19 vectors ($2,378.00\ \mu\text{s}$).

### FR-2: Unconditional Distributional Reporting Across Both Execution Modes
- Regardless of whether `*trials == 1` or `*trials > 1`:
  - The fuzzer MUST compute and output $p50$, $p90$, and $p99$ distinctly in:
    1. The standard output (terminal summary).
    2. The generated Markdown report (`differential_fuzz_report.md`).
    3. The generated JSON report (`differential_fuzz_report.json`).
  - Suppression of $p50$, $p90$, or $p99$ in single-shot mode is strictly prohibited.

### FR-3: Calibrated Terminal Summary Output
- The `FUZZER EXECUTION SUMMARY` block printed to stdout shall explicitly display both metric cohorts:
  ```
  ================================================================================
                           FUZZER EXECUTION SUMMARY                               
  ================================================================================
   Total Invariant Tests:  19
   Passed Assertions:      19
   Failed Assertions:      0
   Security Pass Rate:     100.00%
  --------------------------------------------------------------------------------
   Fail-Fast Defense Latency (N=18 Rejection Vectors):
     Mean Latency:         288.75 µs
     Median (p50):         200.72 µs
     Tail Latency (p90):   712.08 µs
     Max Rejection Lat:    712.08 µs
  --------------------------------------------------------------------------------
   Cross-Vector Comprehensive Latency (N=19 Vectors, incl. Baseline 200 OK):
     Mean Latency:         398.71 µs
     Median (p50):         208.75 µs
     Percentile (p90):     712.08 µs
     Tail Latency (p99):   2378.00 µs
     Max Latency:          2378.00 µs
  ================================================================================
  ```

### FR-4: Calibrated Markdown Report Generation (`differential_fuzz_report.md`)
- The Markdown report generator in `diff_fuzzer.go` shall format the header and summary sections with distinct, unambiguous labels:
  - **Fail-Fast Rejection Latency (N=18 Vectors)**:
    - Mean: `%.2f µs`
    - Median (p50): `%.2f µs`
    - 90th Percentile (p90): `%.2f µs`
    - Max Rejection: `%.2f µs`
  - **Cross-Vector Comprehensive Latency (N=19 Vectors, incl. Baseline 200 OK)**:
    - Mean: `%.2f µs`
    - Median (p50): `%.2f µs`
    - 90th Percentile (p90): `%.2f µs`
    - Tail Latency (p99): `%.2f µs`
    - Max Latency: `%.2f µs`
- The summary matrix table and detailed test results table shall clearly distinguish single-shot latency from repeated-trial distribution metrics.

### FR-5: Calibrated JSON Telemetry Serialization (`differential_fuzz_report.json`)
- `DifferentialReport` struct shall be augmented with structured sub-metrics while maintaining full backwards compatibility for existing consumer scripts:
  ```go
  type CohortMetrics struct {
      Count           int     `json:"count"`
      MeanLatencyUs   float64 `json:"mean_latency_us"`
      MedianLatencyUs float64 `json:"median_latency_us"`
      P90LatencyUs    float64 `json:"p90_latency_us"`
      P99LatencyUs    float64 `json:"p99_latency_us,omitempty"`
      MaxLatencyUs    float64 `json:"max_latency_us"`
  }
  ```
- Top-level fields `average_latency_us`, `median_latency_us`, `p90_latency_us`, and `p99_latency_us` shall continue to be populated with cross-vector values to ensure backwards compatibility with existing evaluation scripts.
- Additional explicit fields `fail_fast_defense` and `comprehensive_suite` of type `CohortMetrics` shall be populated.

### FR-6: Re-Execution of Benchmark Harness & Artifact Regeneration
- `benchmarks/fuzzer/run_fuzzer.sh` shall be executed to regenerate:
  - `benchmarks/results/differential_fuzz_report.json`
  - `benchmarks/results/differential_fuzz_report.md`
- The regenerated artifacts must reflect the calibrated distributional metrics and confirm 100% invariant pass rate (19/19 tests).

### FR-7: Alignment with Manuscript Section 5.2 and Directive REV-02
- The exported data and structure must provide exact empirical grounding for Section 5.2 of `docs/research/paper1_agentic_systems.tex`:
  - Fail-fast rejection latency: $p90 = 712.08\ \mu\text{s}$, $Max = 712.08\ \mu\text{s}$.
  - Cross-vector comprehensive latency: Mean $= 398.71\ \mu\text{s}$, $p50 = 208.75\ \mu\text{s}$ (or $210.92\ \mu\text{s}$), $p90 = 712.08\ \mu\text{s}$, $p99 = 2,378.00\ \mu\text{s}$.

## 4. Non-Functional Requirements

- **NFR-1: Zero External Dependencies**: All statistical calculations (percentiles, medians, means) must use Go standard library (`math`, `sort`). No third-party statistics libraries are permitted.
- **NFR-2: Thread Safety & Race-Free Execution**: The fuzzer harness and report generator must pass `go test -race -count=1 ./benchmarks/fuzzer/...` without any race conditions.
- **NFR-3: Deterministic Percentile Calculation**: Percentiles must be calculated using consistent, standard nearest-rank or linear index calculation (`math.Ceil(p * N) - 1`), with appropriate bounds clamping (`0 <= idx < N`).
- **NFR-4: Backwards Compatibility**: Scripts parsing `differential_fuzz_report.json` must continue to function without schema errors.
