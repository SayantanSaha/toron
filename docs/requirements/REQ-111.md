# REQ-111 - Bounded Worker Pool Connection Dispatching in Event Reactor (SRC-03)

## 1. Description

Academic peer reviews of Paper 1 and Paper 2 (`AER-001`, `PDR-001`, `ReviewTaskSummary.md` item `SRC-03`) revealed a critical divergence between Toron's documented architectural claims and its concrete connection dispatching implementation:

1. **Unbounded Goroutine Spawning Under Connection Load**:
   In `pkg/reactor/reactor.go` (lines 154–159), `Reactor.Serve` accepts incoming TCP connections in a loop and immediately executes:
   ```go
   r.trackConn(conn, true)
   r.wg.Add(1)
   go func(c net.Conn) {
       defer r.wg.Done()
       defer r.trackConn(c, false)
       r.processConn(c)
   }(conn)
   ```
   For every incoming connection, a new goroutine is spawned unconditionally. Under connection floods, slowloris attacks, or SYN/TCP flood scenarios, this unbounded spawning causes explosive goroutine growth, memory exhaustion (OOM), scheduler thrashing, and process termination.

2. **Unused `WorkerPoolSize` Configuration Field**:
   While `reactor.Config` defines `WorkerPoolSize int` (defaulting to 128 in `DefaultConfig()` and validated in `New()`), this parameter is **completely unread** in connection scheduling. Academic reviewers explicitly challenged this discrepancy (*"Why is this characterized as an 'event-driven non-blocking reactor with bounded worker pools' when `WorkerPoolSize` is never used in scheduling?"*).

3. **Mandatory Remediation (`SRC-03`)**:
   Toron must implement a true bounded worker dispatch queue using a worker channel pool of size `WorkerPoolSize` in `pkg/reactor/reactor.go`. The accept loop will dispatch accepted sockets into a bounded queue, serviced by exactly `WorkerPoolSize` worker goroutines, strictly bounding concurrency and eliminating unbounded goroutine spawning while preserving non-blocking graceful shutdown semantics.

## 2. Acceptance Criteria

### AC-1: Fixed Bounded Worker Pool Architecture
- In `pkg/reactor/reactor.go`:
  1. Add a bounded connection task channel `tasks chan net.Conn` sized according to `MaxQueueSize` (or defaulting to `WorkerPoolSize * 4` if unspecified).
  2. In `Serve(ln net.Listener)`, launch exactly `WorkerPoolSize` worker goroutines:
     ```go
     for i := 0; i < r.config.WorkerPoolSize; i++ {
         r.workerWg.Add(1)
         go r.workerLoop()
     }
     ```
  3. Workers continuously pull connections from `r.tasks` and execute `r.processConn(conn)`.
  4. At no time shall the number of concurrent goroutines actively processing connections exceed `WorkerPoolSize`.

### AC-2: Deterministic Dispatching & Ingress Backpressure
- In `pkg/reactor/reactor.go:Serve`:
  1. For each accepted socket `conn`:
     - If the reactor is shutting down (`r.isShutdown.Load()`), immediately close `conn` and return `ErrServerClosed`.
     - Otherwise, track the connection (`r.trackConn(conn, true)`) and dispatch to `r.tasks`:
       ```go
       select {
       case r.tasks <- conn:
       case <-r.ctx.Done():
           r.trackConn(conn, false)
           _ = conn.Close()
           return ErrServerClosed
       }
       ```
  2. When the task queue reaches capacity, `r.tasks <- conn` blocks in `Serve`, applying backpressure to the OS TCP accept queue (`SO_BACKLOG`) rather than spawning unbounded goroutines.

### AC-3: Safe Teardown & Graceful Shutdown Draining
- In `pkg/reactor/reactor.go:Shutdown`:
  1. Signal shutdown atomically (`r.isShutdown.CompareAndSwap(false, true)`).
  2. Cancel `r.ctx` to unblock any pending queue dispatch in `Serve`.
  3. Close `r.listener` to interrupt blocking `ln.Accept()`.
  4. Concurrently close all active sockets in `r.conns` under `connsMu`, unblocking any worker blocked in `conn.Read` or `conn.Write`.
  5. In `Serve`, close `r.tasks` upon loop termination.
  6. Workers cleanly exit when `r.tasks` is closed or drain remaining closed connections.
  7. Graceful shutdown waits for `r.wg.Wait()` (or respects `ctx.Done()` timeout).

### AC-4: Concurrency Invariant & Observability APIs
- In `pkg/reactor/reactor.go`:
  1. Track active worker count with `r.activeWorkers atomic.Int64`.
  2. Expose `ActiveWorkers() int` returning the current number of workers executing `processConn`.
  3. Expose `QueueLen() int` returning `len(r.tasks)`.
  4. Ensure invariant: `0 <= r.ActiveWorkers() <= r.config.WorkerPoolSize` holds under all workloads.

### AC-5: Comprehensive Verification & Regression Test Suite
- In `pkg/reactor/reactor_test.go`:
  1. **Worker Pool Bound Enforcement Test (`TC-111-01`)**: Connect $N > \text{WorkerPoolSize}$ concurrent clients and assert that `r.ActiveWorkers()` never exceeds `WorkerPoolSize`.
  2. **Task Queuing and Sequential Servicing Test (`TC-111-02`)**: Verify queued connections are processed as workers become available without dropped connections.
  3. **Graceful Shutdown with Queued Tasks Test (`TC-111-03`)**: Verify clean shutdown when tasks are waiting in the queue without leaks or deadlocks.
  4. **Keep-Alive Concurrency Update (`TC-111-04`)**: Update `TestReactor_KeepAliveConcurrencyAndShutdown` to configure `WorkerPoolSize` commensurate with the tested concurrency (e.g. `WorkerPoolSize = 32`), confirming correct handling of concurrent keep-alive sessions.
  5. **Dispatch Microbenchmark (`TC-111-05`)**: Update `BenchmarkReactor_ConnectionDispatch` in `reactor_bench_test.go` to measure realistic throughput of bounded queue dispatching.

### AC-6: Zero-Dependency & Race-Clean Invariant
- Pure Go standard library only (`sync`, `sync/atomic`, `net`, `context`, `errors`, `time`, `io`).
- Entire repository test suite passes with `go test -race -count=1 ./...`.

---

## 3. Rationale

Bounding worker concurrency is a core tenet of robust systems engineering and high-availability edge networking. Unbounded goroutine allocation under traffic spikes can lead to memory exhaustion, CPU thrashing, and sudden service collapse. By enforcing `WorkerPoolSize` with a bounded dispatch channel, Toron achieves deterministic resource consumption, provides natural backpressure via TCP flow control, and resolves the peer review critique regarding architecture-code divergence.

---

## 4. Constraints

- Zero third-party runtime dependencies (pure Go standard library).
- Backward compatibility: `reactor.Config` fields and defaults remain functional.
- Zero data races under `-race`.
- Idempotent and clean shutdown under all network states.
