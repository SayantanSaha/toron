# ADR-043 - Service Mesh Sidecar Architecture for Pod-to-Pod mTLS and Traffic Splitting

## Context

Microservices deployed in cloud-native environments require pod-to-pod encrypted communications (mTLS) and canary traffic splitting (e.g. 80/20 v1/v2 releases). Importing Envoy or Istio sidecars adds massive resource overhead (hundreds of MBs of RAM per pod). Toron requires a lightweight (<10MB RAM) sidecar proxy package (`pkg/sidecar`) built natively in Go.

## Decision

1. **Weighted Traffic Splitter (`pkg/sidecar/splitter.go`)**:
   - Implement thread-safe weighted target selector using atomic counter increments (`uint64`) over cumulative backend weight thresholds.
2. **Pod-to-Pod mTLS Engine (`pkg/sidecar/mtls.go`)**:
   - Enforce Mutual TLS (`client_auth: "require_and_verify"`) using standard Go `crypto/tls.Config`.
   - Support dynamic cert/key loading for SPIFFE / local CA cert pools.
3. **Sidecar Proxy Engine (`pkg/sidecar/proxy.go`)**:
   - Operate on dedicated local ports (Ingress: 15006, Egress: 15001).
   - Ingress Mode: Decrypts inbound mTLS traffic and forwards HTTP plain requests to local app container (`127.0.0.1:8080`).
   - Egress Mode: Intercepts outbound app requests, applies weighted traffic splitting, encrypts requests via mTLS, and forwards to peer sidecars.

## Consequences

- **Positive**: Lightweight (<10MB RAM overhead per pod), instant boot time (<5ms), zero external dependencies.
- **Positive**: Full support for canary deployments and pod-to-pod zero-trust security.
- **Negative**: Requires configuring sidecar ports (`15001`/`15006`) in pod environment or iptables redirect.
