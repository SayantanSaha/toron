# REQ-086 - Configurable Request Body Limit and Truncation Rejection in Service Mesh Sidecar Proxy

## Description

The Toron Service Mesh Sidecar Proxy ([`pkg/sidecar/proxy.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go)) MUST enforce configurable request body size limits, preventing silent payload truncation and upstream data corruption. When an incoming request payload exceeds the configured limit, the sidecar proxy MUST immediately reject the request with HTTP 413 Request Entity / Payload Too Large (`http.StatusRequestEntityTooLarge`), close the request body, and refuse to forward partial or corrupted data upstream, remediating vulnerability [`SEC-25`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L366-L374).

## Problem Statement

In [`pkg/sidecar/proxy.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L201-L210), [`ProxyEngine.proxyToURL`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L189-L223) adapts incoming Go standard library [`http.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L189) payloads to Toron [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go) instances. Currently, request body ingestion is governed by a hardcoded limit:

```go
const maxSidecarBody = 10 * 1024 * 1024 // 10 MB limit
bodyBytes, err := io.ReadAll(io.LimitReader(r.Body, maxSidecarBody+1))
if err == nil {
    toronReq.Body = bytes.NewReader(bodyBytes)
    toronReq.ContentLength = int64(len(bodyBytes))
}
```

This implementation suffers from several critical defects identified in [`SEC-25`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L366-L374) (CWE-436, CWE-400):
1. **Hardcoded Body Limit**: The maximum payload size is fixed at 10 MB (`10 * 1024 * 1024` bytes) and cannot be adjusted via configuration by operators or deployment manifests.
2. **Silent Body Truncation**: When a client sends a payload exceeding `maxSidecarBody`, `io.LimitReader` reads up to 10 MB + 1 byte and truncates the remaining stream. Instead of returning an error or rejecting the request, the proxy overrides `toronReq.ContentLength` with the truncated length and forwards the corrupted payload upstream.
3. **Upstream Data Corruption & Desynchronization**: Upstream microservices receive malformed, partial payloads (e.g. truncated JSON or chopped file uploads) while assuming complete transmission, leading to application errors, partial writes, or protocol desynchronization.
4. **Missing Fail-Fast Error Semantics**: Oversized payloads are not rejected at the sidecar boundary with standard HTTP status codes (`413 Payload Too Large`), violating RFC HTTP semantics and failing to protect upstream services from resource consumption.

## Acceptance Criteria

1. **Configurable Maximum Body Size (`SidecarConfig`)**:
   - The sidecar configuration ([`SidecarConfig`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L103)) MUST provide a field to configure the maximum allowable request body size in bytes (`MaxBodyBytes int64`).
   - If `MaxBodyBytes` is unset, zero (`0`), or negative (`<= 0`), the sidecar proxy engine MUST default to 10 MB (`10 * 1024 * 1024` bytes, or 10,485,760 bytes).
   - If `MaxBodyBytes` is explicitly set to a positive value (e.g., `1048576` for 1 MB or `52428800` for 50 MB), the sidecar proxy engine MUST enforce that specific threshold.

2. **Immediate HTTP 413 Rejection on Overflow**:
   - If an incoming request body exceeds the configured maximum byte limit (whether declared via `Content-Length` header exceeding the limit or detected during stream reading), the sidecar proxy MUST:
     a. Immediately abort proxying the request.
     b. Respond to the client with HTTP status code `413 Request Entity Too Large` (`http.StatusRequestEntityTooLarge`).
     c. Close the incoming request body (`r.Body.Close()`).
     d. Ensure NO request data (partial or truncated) is forwarded to the upstream target.

3. **Byte-Fidelity Forwarding for Valid Payloads**:
   - Inbound mutating requests (`POST`, `PUT`, `PATCH`, etc.) whose body size is less than or equal to the configured maximum byte limit MUST be forwarded intact to the upstream target with 100% byte fidelity.
   - The forwarded request MUST preserve accurate `ContentLength` and provide the full payload to upstream handlers.

4. **Bypass for Non-Mutating and Empty Requests**:
   - Requests using HTTP methods that do not conventionally carry bodies (e.g., `GET`, `HEAD`) or requests where `r.Body == nil` or body length is zero MUST bypass body buffering and be forwarded directly without allocating payload buffers or triggering 413 errors.

5. **Diagnostic Logging**:
   - When an oversized request is rejected with HTTP 413, the sidecar proxy MUST emit an informative log entry noting the payload rejection, the configured limit, and the target or request path.

6. **Regression Invariants & Concurrency**:
   - Existing sidecar capabilities—including mTLS termination, plain HTTP ingress/egress proxying, and weighted traffic splitting—MUST remain fully functional.
   - All sidecar proxy operations MUST be safe for concurrent execution and pass Go race detection tests (`go test -race ./pkg/sidecar/...`) without memory leaks or race conditions.
