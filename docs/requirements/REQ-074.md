# REQ-074 - Multiple and Conflicting Content-Length Rejection (RFC 7230 §3.3.2)

## Description

The Toron HTTP parser shall enforce RFC 7230 §3.3.2 protocol compliance regarding the `Content-Length` header. Incoming HTTP requests containing multiple `Content-Length` headers, comma-separated length lists, or conflicting payload length values shall be rejected with `HTTP 400 Bad Request`.

## Acceptance Criteria

### 1. Verification of Content-Length Multiplicity
- `httpparser.ParseRequest` shall verify the cardinality of `Content-Length` headers received in the request.
- If multiple `Content-Length` headers are present (e.g. `Content-Length: 0` and `Content-Length: 45`):
  - If the values represent distinct numbers, the parser shall reject the request with `HTTP 400 Bad Request`.
  - If a single `Content-Length` header contains a comma-separated list with distinct numbers (e.g. `Content-Length: 0, 45`), the parser shall reject the request.
  - If multiple headers declare the identical numeric value, the parser may normalize them to a single value or reject them.

### 2. Elimination of CL.CL Desynchronization
- The parser shall never silently select only the first `Content-Length` entry while discarding subsequent conflicting entries on the same request.
- When an invalid or ambiguous `Content-Length` is detected, the persistent connection loop shall terminate to prevent residual socket byte parsing.

## Rationale

CL.CL request smuggling exploits differences between front-end and back-end proxies when resolving ambiguous `Content-Length` values. Permitting multiple conflicting `Content-Length` headers leaves unconsumed request bodies on the socket, which are parsed as subsequent requests on pooled connections.

## Constraints

- Pure Go standard library.
- Zero performance regressions on standard single `Content-Length` requests.
