# REQ-106 - Latency Benchmark Timing Alignment (Eq. 7) and Repeated Statistical Distribution Trials

## 1. Description

Peer review audits of Paper 2 (`AER-002`, `MSR-002`, `BMK-01`, `BMK-02`) revealed critical methodological and statistical discrepancies in the differential security benchmark harness (`benchmarks/fuzzer/diff_fuzzer.go`):

1. **BMK-01 (Equation 7 Timing Alignment & Dial Conflation)**:
   In `diff_fuzzer.go`, `start := time.Now()` was captured immediately *before* calling `net.DialTimeout("tcp", targetHost, 3*time.Second)`. Consequently, the recorded latency measurement included operating system client TCP socket creation (`socket(2)`), TCP three-way handshake (`SYN` $\rightarrow$ `SYN-ACK` $\rightarrow$ `ACK`), loopback network stack scheduling jitter, and server-side socket accept handling. This directly violated the formal mathematical definition of rejection latency defined in Section 4.1, Equation 7 of the manuscript:
   $$T_{\text{rejection}} = t_{\text{status\_line\_read}} - t_{\text{socket\_write\_start}}$$
   To strictly adhere to Equation 7, the benchmark harness must establish the TCP connection first, set deadlines, and capture `start := time.Now()` immediately prior to issuing `conn.Write([]byte(finalPayload))` on the probe connection.

2. **BMK-02 (Repeated Statistical Trials $K \ge 1,000$ & Distributional Percentiles)**:
   The prior benchmark executed only a single-shot ($K=1$) sequential probe per test vector on an idle loopback socket ($N=16$ total observations). A single execution pass lacks statistical dispersion metrics, confidence intervals, and tail latency percentiles, rendering the reported arithmetic mean ($298.88\,\mu\text{s}$) vulnerable to cold-start outliers (e.g., initial socket dial at $646\,\mu\text{s}$).
   To satisfy systems benchmarking standards (Hoefler & Belli 2015, Tene 2015) and academic peer review requirements (USENIX Security / ACM CCS):
   - The fuzzer must support configurable repeated trials via CLI flag (`-trials K`, default `1` for rapid CI/smoke testing, recommended `1000` for empirical evaluations).
   - The fuzzer must support a configurable discarded warm-up phase (`-warmup W`, default `0` for $K=1$, default `50` when $K > 1$ or explicitly configured) to stabilize runtime goroutine pools and kernel socket states before metric recording.
   - For each vector across $K$ valid trials, the harness shall record the full latency distribution and calculate:
     - Arithmetic Mean ($\bar{x}$)
     - Sample Standard Deviation ($s = \sqrt{\frac{1}{K-1} \sum (x_i - \bar{x})^2}$)
     - Median ($p50$)
     - Tail percentiles: $p90$, $p99$, $p99.9$
     - 95% Confidence Interval: $\left[ \bar{x} - 1.96 \cdot \frac{s}{\sqrt{K}}, \ \bar{x} + 1.96 \cdot \frac{s}{\sqrt{K}} \right]$
   - Update `TestResult` and `DifferentialReport` structs and serialize these metrics to both JSON and Markdown report outputs.

## 2. Acceptance Criteria

### AC-1: Equation 7 Timing Alignment Compliance (BMK-01)
- In `benchmarks/fuzzer/diff_fuzzer.go`, for all single-stage and multi-stage test vectors, the timing start timestamp (`start := time.Now()`) shall be captured **immediately prior to** `conn.Write([]byte(finalPayload))` on the probe TCP connection.
- TCP dial setup (`net.DialTimeout`) and multi-stage preparatory requests (`sendAndDrain`) shall execute entirely outside the timed interval.
- Rejection latency shall be measured as the duration between the start of probe payload write and completion of reading the HTTP response status line (`reader.ReadString('\n')`).

### AC-2: Repeated Statistical Trials Execution & Warm-up Phase (BMK-02)
- The fuzzer CLI shall introduce the following command-line flags:
  - `-trials <int>`: Total measured trials $K$ per test case (default: `1`, minimum: `1`).
  - `-warmup <int>`: Discarded warm-up trials $W$ per test case (default: `0` when `trials == 1`, default: `50` when `trials > 1`).
- When $W > 0$, the harness shall execute $W$ preliminary iterations of the test vector and discard all latency measurements before beginning the timed evaluation loop.
- The harness shall then execute $K$ timed iterations, recording the latency duration of each trial into a slice of float64 microsecond samples.

### AC-3: Rigorous Statistical Distribution & Percentile Calculations (BMK-02)
- For each test case with $K \ge 1$ trials, the system shall compute:
  - **Mean ($\bar{x}$)**: $\bar{x} = \frac{1}{K} \sum_{i=1}^K x_i$
  - **Sample Standard Deviation ($s$)**: $s = \sqrt{\frac{1}{K-1} \sum_{i=1}^K (x_i - \bar{x})^2}$ for $K > 1$, and $0.0$ for $K = 1$.
  - **Median ($p50$)**: Middle value of sorted latency samples.
  - **Tail percentiles**: $p90$, $p99$, and $p99.9$ computed deterministically from the sorted latency distribution.
  - **95% Confidence Interval**: $[\bar{x} - \text{margin}, \bar{x} + \text{margin}]$ where $\text{margin} = 1.96 \cdot \frac{s}{\sqrt{K}}$ for $K > 1$, and $0.0$ for $K = 1$.
- In the aggregated `DifferentialReport`, summary metrics shall include overall Average Latency, Median Latency, p90, p99, and p99.9 across all executed test vectors.

### AC-4: Data Model & Report Struct Schema Extension
- `TestResult` struct shall be extended with:
  - `Trials int` (`json:"trials"`)
  - `WarmupRuns int` (`json:"warmup_runs"`)
  - `MeanLatencyUs float64` (`json:"mean_latency_us"`)
  - `StdDevLatencyUs float64` (`json:"std_dev_latency_us"`)
  - `MedianLatencyUs float64` (`json:"median_latency_us"`)
  - `P90LatencyUs float64` (`json:"p90_latency_us"`)
  - `P99LatencyUs float64` (`json:"p99_latency_us"`)
  - `P999LatencyUs float64` (`json:"p999_latency_us"`)
  - `CI95LowerUs float64` (`json:"ci95_lower_us"`)
  - `CI95UpperUs float64` (`json:"ci95_upper_us"`)
  - `LatencyUs int64` (`json:"latency_us"`) retained as `int64(math.Round(MedianLatencyUs))` for backward compatibility.
- `DifferentialReport` struct shall be extended with:
  - `TrialsPerVector int` (`json:"trials_per_vector"`)
  - `WarmupPerVector int` (`json:"warmup_per_vector"`)
  - `MedianLatencyUs float64` (`json:"median_latency_us"`)
  - `P90LatencyUs float64` (`json:"p90_latency_us"`)
  - `P99LatencyUs float64` (`json:"p99_latency_us"`)
  - `P999LatencyUs float64` (`json:"p999_latency_us"`)
- Markdown report generator shall output an expanded **Detailed Invariant Test Results** table containing columns:
  - `Test ID`, `Vector Name`, `CWE`, `Expected Status`, `Actual Status`, `Conn Closed`, `Median Latency`, `Mean ± StdDev`, `p90 / p99 / p99.9`, `95% CI`, `Result`.

### AC-5: Shell Harness Flag Forwarding & Backward Compatibility
- `benchmarks/fuzzer/run_fuzzer.sh` shall be updated to accept `-k <trials>` and `-w <warmup>` flags, passing `-trials` and `-warmup` downstream to `go run diff_fuzzer.go`.
- Default execution (`bash benchmarks/fuzzer/run_fuzzer.sh`) without flags shall run $K=1$, maintaining instant test execution for local unit testing and continuous integration.

### AC-6: Zero-Dependency & Race-Clean Invariant
- All mathematical and statistical computations shall use exclusively Go standard library packages (`math`, `sort`, `time`, `flag`, `fmt`).
- Code must pass with zero race warnings under `go test -v -race -count=1 ./benchmarks/fuzzer/...`.

## 3. Rationale

Accurate, low-jitter benchmarking is fundamental to USENIX Security and ACM CCS peer review. Conflating TCP socket allocation with state machine parsing inflated rejection latencies by orders of magnitude. Aligning the measurement point with Equation 7 directly addresses the scientific criticism in `AER-002` and `MSR-002`. Furthermore, executing $K \ge 1,000$ repeated trials with warm-up eliminates cold-start anomalies and yields robust tail latency distributions and narrow confidence intervals, establishing rigorous empirical defensibility.

## 4. Constraints

- Zero external third-party dependencies (strictly Go standard library).
- Must preserve backward compatibility with existing test cases (`SMUGGLE-001..004`, `WHITESPACE-001..003`, `CONTROL-001..003`, `TRAVERSAL-001..003`, `RESOURCE-001..002`, `BASELINE-001`, `CACHE-001..003`).
- In multi-stage requests (`CACHE-001..003`), preparatory requests must execute before each probe trial to maintain consistent state machine cache conditions.
