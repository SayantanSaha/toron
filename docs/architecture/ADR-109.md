# ADR-109 - RFC 7230 §3.2 Header Field-Name Token Lookup Table

## 1. Context & Problem Statement

In HTTP/1.1 message parsing, header field-names are defined by RFC 7230 §3.2 as `token`, where `token = 1*tchar` (RFC 7230 §3.2.6). Previously, Toron's `httpparser.ParseRequest` validated header names using `k == "" || strings.ContainsAny(k, " \t\r\n")`.

This permissive check allowed non-token delimiters (such as `@`, `(`, `)`, `;`, `[`, `]`, `?`, `=`, `{`, `}`), control characters, and high-bit bytes. In a reverse proxy or edge gateway setting, accepting non-token characters creates a semantic mismatch with upstream backends (e.g. Node.js `llhttp`, NGINX, Python Uvicorn/Gunicorn, Go standard library), creating attack surfaces for HTTP request smuggling (CWE-444) and header injection (CWE-113).

## 2. Decision

We implement **Static 256-Byte Array Lookup Table Validation**:

### 2.1 Precomputed Lookup Table (`validHeaderTokenTable`)
Instead of regex engines or dynamic string searches, we instantiate a package-level static lookup table of type `[256]bool`:
```go
var validHeaderTokenTable = func() [256]bool {
    var table [256]bool
    // DIGIT
    for c := '0'; c <= '9'; c++ {
        table[c] = true
    }
    // ALPHA
    for c := 'a'; c <= 'z'; c++ {
        table[c] = true
    }
    for c := 'A'; c <= 'Z'; c++ {
        table[c] = true
    }
    // Specific RFC 7230 §3.2.6 tchar symbols:
    // ! # $ % & ' * + - . ^ _ ` | ~
    for _, c := range []byte("!#$%&'*+-.^_`|~") {
        table[c] = true
    }
    return table
}()
```

### 2.2 $O(N)$ Zero-Allocation Scanning & Fail-Fast Error Wrapping
During request parsing, each extracted header field-name `k` is scanned byte-by-byte:
```go
if k == "" {
    return nil, fmt.Errorf("%w: empty header field-name", ErrBadRequest)
}
for i := 0; i < len(k); i++ {
    b := k[i]
    if !validHeaderTokenTable[b] {
        if b == ' ' || b == '\t' || b == '\r' || b == '\n' {
            return nil, fmt.Errorf("%w: whitespace in header field-name", ErrBadRequest)
        }
        return nil, fmt.Errorf("%w: invalid header field-name token grammar", ErrBadRequest)
    }
}
```
- **Time Complexity**: Strictly $O(N)$ where $N = \text{len}(k)$ (typically < 32 bytes).
- **Space Complexity**: 0 allocations ($0\text{ B/op}$) on heap.
- **Error Semantics**: Preserves `%w: whitespace in header field-name` when whitespace is detected to maintain backward compatibility with existing tests and error checks, while emitting `%w: invalid header field-name token grammar` for all other non-token characters. Both wrap `ErrBadRequest`.

## 3. Considered Alternatives

- **Alternative 1: Regular Expressions (`regexp.MustCompile("^[!#$%&'*+-.^_`|~0-9a-zA-Z]+$")`)**:
  Rejected because regex execution incurs heap allocations, lock overhead, and orders-of-magnitude higher execution latency (~200ns vs ~3ns).
- **Alternative 2: Bitmask (`[4]uint64`)**:
  Evaluated. A 256-bit bitmask saves 192 bytes of static memory compared to `[256]bool`, but requires shift and bitwise operations (`(mask[b>>6] & (1 << (b & 63))) != 0`). The 256-byte table occupies negligible static memory and yields single direct memory indexing (`validHeaderTokenTable[b]`).
- **Alternative 3: `strings.IndexFunc`**:
  Rejected because closure calls in standard library functions may introduce compiler escape analysis overhead.

## 4. Consequences

- **Positive**:
  - Full adherence to RFC 7230 §3.2 and §3.2.6 token grammar specifications.
  - Complete elimination of header token semantic gaps with upstream backends.
  - Nanosecond-level fail-fast rejection with zero heap allocations.
  - Complete backward compatibility with existing whitespace rejection assertions.
- **Negative / Operational Considerations**:
  - Any non-compliant legacy HTTP clients transmitting non-token characters in header names will now be rejected with `HTTP 400 Bad Request`.
