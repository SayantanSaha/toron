# ADR-112 - HTTP/2 Translation Invariant Guards (H2.CL / H2.TE)

## 1. Context & Problem Statement

Toron acts as a multi-protocol edge gateway, accepting downstream HTTP/2 connections and proxying requests to upstream HTTP/1.1 or microservice origins. When converting an HTTP/2 request into an internal representation for upstream dispatch, a dangerous semantic translation gap arises:

1. **Protocol Framing Asymmetry**: HTTP/2 uses length-prefixed binary frames, whereas HTTP/1.1 uses text delimiters (`\r\n`) and in-band framing (`Content-Length` or `Transfer-Encoding: chunked`).
2. **H2.TE Smuggling**: Attackers include `Transfer-Encoding: chunked` in an HTTP/2 request. HTTP/2 endpoints ignore it because frame lengths govern message boundaries. However, when forwarded to an HTTP/1.1 origin, the origin gives precedence to `Transfer-Encoding`, reading the request body as chunked framing and smuggling an embedded second request into the connection pool.
3. **H2.CL Smuggling**: Attackers declare multiple conflicting `Content-Length` headers, or declare a `Content-Length` differing from the actual HTTP/2 payload byte count.
4. **CRLF & NUL Binary Injection**: Binary HPACK encoding allows `\r`, `\n`, or `0x00` in header values. When translated into HTTP/1.1 wire format, these characters split header fields or forge new requests.
5. **Pseudo-Header Leakage**: HTTP/2 pseudo-headers (e.g. `:protocol`) leaking into HTTP/1.1 wire requests corrupt upstream parser state.

## 2. Decision

We establish an **In-Line Multi-Protocol Translation Invariant Enforcement Gate**:

### 2.1 RFC 7540 §8.1.2.2 Connection-Specific Header Rejection
Before any HTTP/2 request is dispatched to the router:
- Inspect header keys for connection-specific tokens:
  - `transfer-encoding` $\rightarrow$ unconditionally reject with `400 Bad Request`.
  - `connection`, `keep-alive`, `proxy-connection` $\rightarrow$ reject with `400 Bad Request`.
  - `upgrade` $\rightarrow$ reject with `400 Bad Request`, unless the request is an extended CONNECT handshake containing the `:protocol` pseudo-header (RFC 8441).

### 2.2 Content-Length Invariant & Discrepancy Verification (H2.CL)
- Check `Content-Length` header formatting:
  - Reject requests containing multiple `Content-Length` headers or comma-separated values.
  - Reject non-numeric, signed, or malformed values.
- Check actual payload length:
  - After ingesting body bytes from `r.Body`, if `ContentLength >= 0` and `int64(len(bodyBytes)) != ContentLength`, reject immediately with `400 Bad Request`.

### 2.3 Zero-Allocation CRLF & NUL Binary Scanner
- Perform a fast linear scan ($O(N)$) over:
  - Request method, URL path, raw query, host/authority, and scheme.
  - Every header field name and field value.
- If any byte equals `\r` (`0x0D`), `\n` (`0x0A`), or `0x00`, immediately reject the request with `400 Bad Request`.

### 2.4 Upstream Reverse Proxy Pseudo-Header Isolation
In `pkg/proxy/proxy.go`:
- During header replication for both standard HTTP proxying (`ServeHTTPWithPrefix`) and WebSocket handshake forwarding (`proxyRawStream`), discard all header keys starting with `:`:
  ```go
  if strings.HasPrefix(key, ":") {
      continue
  }
  ```
- Guaranteed prevention of pseudo-header leakage into HTTP/1.1 upstream wire format.

## 4. Alternatives Considered

1. **Relying solely on Go's `x/net/http2` default handling**:
   - *Rejected*: Standard library permits `Transfer-Encoding` or passes it into `r.Header` without validating cross-protocol translation invariants, leaving the gateway vulnerable to H2.CL and H2.TE desynchronization.
2. **Converting to HTTP/1.1 wire text and re-parsing with `httpparser`**:
   - *Rejected*: Redundant serialization/deserialization degrades edge gateway throughput and increases GC allocation overhead. Direct translation invariant validation provides zero-allocation, sub-microsecond protection.

## 5. Rationale & Constraints

- Pure Go standard library; zero external dependencies.
- Zero data races under `-race`.
- Complies strictly with RFC 7540 §8.1.2 and RFC 8441.
