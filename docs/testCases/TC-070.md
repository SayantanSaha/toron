# TC-070 - Verification of Host Header Validation in Cleartext HTTP-to-HTTPS Redirection

## Objective

Verify that cleartext HTTP-to-HTTPS redirection validates incoming `Host` headers against recognized domain registries (explicit `AllowedHosts`, `DefaultHost`, `SNIRegistry`, and router host rules), prevents Open Redirect (CWE-601) by rejecting unrecognized hostnames with `HTTP 400 Bad Request`, or falls back safely to a configured `DefaultHost`.

## Test Cases

### TC-070-01: Recognized Domain Standard 301 Redirection
- **Setup**: Start redirect server with `HTTPRedirectAllowedHosts: ["example.com"]`.
- **Action**: Client sends `GET /dashboard HTTP/1.1` with `Host: example.com`.
- **Expected Outcome**:
  - Response returns `301 Moved Permanently`.
  - `Location` header is `https://example.com/dashboard`.

### TC-070-02: Unrecognized Host Header Rejection
- **Setup**: Using the server from TC-070-01 with no `DefaultHost`.
- **Action**: Client sends `GET /dashboard HTTP/1.1` with `Host: attacker.com`.
- **Expected Outcome**:
  - Response returns `400 Bad Request`.
  - Response body indicates unrecognized host error.
  - No `Location` header is emitted.

### TC-070-03: DefaultHost Fallback
- **Setup**: Configure redirect server with `HTTPRedirectDefaultHost: "canonical.example.com"`.
- **Action**: Client sends `GET /dashboard HTTP/1.1` with `Host: attacker.com`.
- **Expected Outcome**:
  - Response returns `301 Moved Permanently`.
  - `Location` header redirects to `https://canonical.example.com/dashboard`.
  - Attacker's domain is not reflected.
