# AN-001 - End-to-End Security Analysis and Threat Exposure of Control Center Dashboard and Management APIs

## 1. Problem Statement

The user reports: *"currently the dashboard is not secured. use system-analyst to secure the dashboard"*.

In default installations of the Toron Edge Gateway, the web-based Control Center dashboard served at `/internal/dashboard` and its supporting operational management APIs (`/internal/api/*`) are completely accessible to any client on the network without authentication, authorization, or IP access controls. Unauthenticated actors can inspect sensitive operational data, view real-time request traces, trigger arbitrary endpoint probes, and mutate security policies (such as banning and unbanning IP addresses).

---

## 2. Observed Behavior

1. **Unprotected Static Dashboard**:
   - In [`routes.yaml`](../../routes.yaml), `/internal/dashboard` is configured as a static route without an `auth` block:
     ```yaml
     - type: "static"
       prefix: "/internal/dashboard"
       dir: "./public"
     ```
   - Navigating to `http://<gateway>:8080/internal/dashboard/` immediately serves `index.html` and all modular assets (`public/js/*.js`) without challenging the client for credentials.
2. **Unprotected Management APIs**:
   - In [`pkg/server/internal_api.go`](../../pkg/server/internal_api.go), `RegisterInternalAPIRoutes` only enforces authentication if `authRequired` evaluates to true:
     ```go
     authRequired := cfg.AdminAuthEnabled || cfg.AdminToken != "" || len(cfg.AdminAPIKeys) > 0 || cfg.AdminUsername != "" || len(cfg.AdminUsers) > 0
     ```
   - In [`config.yaml`](../../config.yaml) and the default configuration in [`pkg/config/config.go`](../../pkg/config/config.go), `admin_auth` is disabled by default (`Enabled: false`, no token, no users).
   - Consequently, all endpoints under `/internal/api/*` return full administrative data to any unauthenticated caller.
3. **Frontend Telemetry Ingestion Lacks Credential Handling**:
   - In [`public/js/api.js`](../../public/js/api.js), the background poller executes unauthenticated `fetch()` requests against `/internal/api/*` without attaching headers:
     ```javascript
     fetch('/internal/api/status')
     ```
   - If an administrator explicitly enables `admin_auth: true` on the backend, the backend correctly returns `401 Unauthorized` for `/internal/api/*`. However, the frontend has no login interface, no credential prompt, and no credential injection mechanism. The dashboard silently fails to display live telemetry and falls back to static sample data.
4. **Unprotected Management Mutations**:
   - `POST /internal/api/security/ban` and `POST /internal/api/security/unban` mutate the gateway firewall auto-ban state.
   - `POST /internal/api/proxy-test` allows sending arbitrary HTTP probes with custom headers and paths, creating a Server-Side Request Forgery (`SSRF`) vector if unprotected.

---

## 3. Expected Behavior

1. **Restricted Dashboard Access**:
   - The dashboard UI at `/internal/dashboard` must only be accessible to authorized operators.
2. **Enforced Management API Authorization**:
   - All `/internal/api/*` endpoints must reject unauthorized requests with HTTP `401 Unauthorized` (or HTTP `403 Forbidden` if denied by subnet policy).
3. **Seamless Dashboard Authentication & Session Integration**:
   - Authorized operators must be able to authenticate (via HTTP Basic Auth, Admin API Key, or Bearer Token).
   - The frontend dashboard client must properly convey credentials on every background polling cycle and management action, ensuring telemetry and admin actions succeed when backend security is enabled.
4. **Configurable Administrative Access Control**:
   - Operators can secure the control plane via configuration (`config.yaml`), environment variables (`TORON_ADMIN_KEY`), and IP subnet allowlists (`admin_subnets`).

---

## 4. Evidence

- **Route Configuration ([`routes.yaml`](../../routes.yaml:5-7))**:
  ```yaml
  routes:
    - type: "static"
      prefix: "/internal/dashboard"
      dir: "./public"
  ```
  *Evidence*: No `auth` block configured for the static dashboard prefix.

- **Gateway Bootstrap ([`cmd/toron/main.go`](../../cmd/toron/main.go:367-386))**:
  ```go
  AdminAuthEnabled: appCfg.Server.AdminAuth.Enabled ||
      os.Getenv("TORON_ADMIN_KEY") != "" ||
      appCfg.Server.AdminAuth.Token != "" || ...
  ```
  *Evidence*: If neither `admin_auth.enabled` is set in `config.yaml` nor `TORON_ADMIN_KEY` is present in the environment, `AdminAuthEnabled` is `false`.

- **Internal API Middleware Guard ([`pkg/server/internal_api.go`](../../pkg/server/internal_api.go:380-389))**:
  ```go
  if authRequired {
      if !validateAdminAuth(req, cfg) {
          res.SetStatus(http.StatusUnauthorized)
          ...
      }
  }
  ```
  *Evidence*: When `authRequired` is false, request processing proceeds directly to the handler without authentication.

- **Frontend API Poller ([`public/js/api.js`](../../public/js/api.js:23-30))**:
  ```javascript
  const [statusRes, routesRes, upstreamsRes, incidentsRes, logsRes, bansRes] = await Promise.allSettled([
    fetch('/internal/api/status'),
    fetch('/internal/api/routes'),
    fetch('/internal/api/upstreams/health'),
    fetch('/internal/api/security/incidents'),
    fetch('/internal/api/logs'),
    fetch('/internal/api/security/banned-ips')
  ]);
  ```
  *Evidence*: No `Authorization` or `X-Toron-Admin-Key` headers are provided; requests rely entirely on unauthenticated access.

## 5. Scope and Impact

### 5.1 Security & Threat Impact
| Threat Vector | CWE | Severity | Impact |
|---|---|---|---|
| **Sensitive Data Exposure** | CWE-200 / CWE-319 | **High** | Attackers on the network can view all configured proxy routes, backend upstreams, internal IP topology, health statuses, and active WAF security incidents. |
| **Telemetry & Log Snooping** | CWE-532 / CWE-200 | **High** | Live request tailing (`/internal/api/logs`) reveals incoming client IP addresses, endpoints visited, HTTP methods, headers, and trace IDs in real-time. |
| **Unauthorized Firewall Manipulation** | CWE-306 / CWE-862 | **Critical** | Any client can invoke `POST /internal/api/security/ban` to deny service to legitimate IP addresses (Denial of Service) or `POST /internal/api/security/unban` to unban malicious threat actors. |
| **Server-Side Request Forgery (SSRF)** | CWE-918 | **High** | Any client can use `POST /internal/api/proxy-test` to craft arbitrary HTTP requests through the gateway to probe internal network addresses. |

### 5.2 Technical & Architectural Impact
- **Backend Components**:
  - `pkg/config/`: Configuration schema and validation for administrative dashboard security.
  - `cmd/toron/`: Route registration wiring for `/internal/dashboard` with authentication options.
  - `pkg/server/`: Enforcement of authentication on both the static dashboard shell and API endpoints.
- **Frontend Components**:
  - `public/js/api.js`: Inclusion of credentials in background requests and handling of HTTP 401 responses.
  - `public/js/views/alerts.js`: Credential inclusion for IP ban/unban mutations.
  - `public/js/views/console.js`: Credential inclusion for diagnostic proxy-test requests.
  - `public/js/state.js` & `public/js/components/`: Authentication state, login dialog/modal, and session management.

## 6. Root Cause Analysis

- **Confirmed Root Cause 1 (Default Insecure Configuration)**:
  `AdminAuth.Enabled` defaults to `false` in `DefaultConfig()`. Without an explicit configuration file directive or environment variable, the gateway assumes an insecure local development posture.
- **Confirmed Root Cause 2 (Decoupled Dashboard vs API Route Security)**:
  The static dashboard route `/internal/dashboard` is treated as a generic static route (`RouteTypeStatic`), completely disconnected from `internalCfg.AdminAuthEnabled`.
- **Confirmed Root Cause 3 (Absence of Frontend Authentication Layer)**:
  The SPA dashboard client was constructed assuming open network access to `/internal/api/*` and does not implement a credential persistence mechanism or HTTP 401 interception workflow.

## 7. Options Analysis

### Option 1: Browser-Native HTTP Basic Authentication for Dashboard & APIs
- **Mechanism**:
  - Secure `/internal/dashboard` and `/internal/api/*` under the same HTTP Basic Auth realm (`Toron Control Center`).
  - When accessing `/internal/dashboard`, the browser presents its native credentials prompt.
  - Browsers automatically cache and propagate the `Authorization: Basic <base64>` header to all same-origin subresource requests (`fetch('/internal/api/*')`).
- **Pros**:
  - Zero custom login UI required in frontend.
  - Native browser security; credentials are not stored in JavaScript `localStorage` or `sessionStorage`.
  - Fully supported by existing `validateAdminAuth` in `pkg/server/internal_api.go` and `pkg/router/auth.go`.
- **Cons**:
  - Browser logout is cumbersome (requires clearing browser HTTP auth cache).
  - Basic Auth does not support token expiration or API key workflows cleanly.

### Option 2: Frontend Token/Key Modal with In-Memory / Session Storage
- **Mechanism**:
  - Serve `/internal/dashboard` static files publicly (or behind basic auth), but display a sleek authentication modal if `/internal/api/*` returns `401 Unauthorized`.
  - The administrator inputs their Admin API Key or Bearer Token.
  - Stored in memory (or `sessionStorage`), and appended as `X-Toron-Admin-Key` or `Authorization: Bearer` to all `api.js`, `alerts.js`, and `console.js` requests.
  - Includes a "Lock / Logout" button in the dashboard navigation rail.
- **Pros**:
  - High usability, polished modern enterprise UX.
  - Directly compatible with `TORON_ADMIN_KEY` environment variables.
  - Allows easy key rotation and logout.
- **Cons**:
  - Requires adding a lightweight authentication modal and credential state in `public/js/`.

### Option 3: Defense-in-Depth Hybrid (Recommended)
- **Mechanism**:
  1. **Backend Route-Level Security**:
     - Allow securing `/internal/dashboard` static route via `routes.yaml` using existing `auth` block (Basic or APIKey) and CIDR subnet restrictions (`admin_subnets`).
  2. **Mandatory/Default Administrative Auth in Production**:
     - Automatically require authentication when `TORON_ADMIN_KEY` is set, or generate a random one-time admin token on gateway startup if enabled.
  3. **Frontend Smart Auth Adapter**:
     - Update `public/js/api.js` to intercept 401 responses.
     - Provide an authentication dialog in the dashboard allowing entry of an Admin API Key / Token (stored in `sessionStorage`).
     - Automatically include credentials on all `fetch()` calls.
     - Support browser-cached Basic Auth seamlessly via `credentials: 'same-origin'`.
- **Pros**:
  - Maximum flexibility: supports headless automation (curl with Bearer/Basic/Key) and interactive browser operators.
  - Defense-in-depth: network-level subnet isolation + cryptographic authentication.
  - Fixes the bug where enabling admin auth breaks the dashboard client.

---

## 8. Recommendation

Adopt **Option 3 (Defense-in-Depth Hybrid)**:

1. **Backend Enhancements**:
   - Wire `routes.yaml` static dashboard route to enforce authentication when administrative security is enabled.
   - Ensure `pkg/server/internal_api.go` returns standard `WWW-Authenticate` headers so both browsers and API clients can negotiate credentials.
2. **Frontend Client Enhancements**:
   - Update `public/js/api.js` to include configured credentials (`X-Toron-Admin-Key` or `Authorization`) in all requests.
   - Detect 401 responses and render an interactive **Admin Authentication Dialog** to prompt for credentials rather than failing silently.
   - Add a key/logout control to `public/js/app.js` chrome navigation.
3. **Configuration & Documentation**:
   - Provide clear configuration examples in `config.yaml` and `routes.yaml`.
   - Update [`observability-dashboard.md`](../wiki/features/observability-dashboard.md) with security guidelines.

## 10. Risks & Open Questions

- **Risk**: Storing administrative tokens in `localStorage` persists across browser sessions and is vulnerable to XSS.
  - *Mitigation*: Store tokens only in volatile in-memory state or `sessionStorage` (which is scoped to the current tab and cleared on close).
- **Risk**: Existing test scripts expecting unauthenticated access to `/internal/api/*` in test fixtures.
  - *Mitigation*: Ensure test harnesses pass `AdminAuthEnabled: false` in mock configs or provide mock tokens in `dashboard_telemetry_test.js`.
- **Open Question for User**:
  - Does the team prefer entering an **Admin Token / API Key** in a dashboard modal, or using **HTTP Basic Auth** (username/password), or supporting both?
