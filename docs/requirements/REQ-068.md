# REQ-068 - Wire Frame Size Bounding and Memory Allocation Protection in gRPC Transcoder

## Description

The Toron REST-to-gRPC transcoding engine shall enforce explicit upper-bound limits on incoming and outgoing gRPC 5-byte wire frame lengths during frame deserialization.

The frame decoder in `pkg/transcoder/framer.go` shall validate the declared payload length before allocating memory buffers, preventing excessive heap allocations, Out-Of-Memory (OOM) panics, and worker crashes caused by hostile or corrupted upstream responses.

## Acceptance Criteria

### 1. Maximum Frame Size Validation
- The `DecodeGRPCFrame` function shall validate the 4-byte `length` value against a configured or sensible default maximum limit (e.g. 4 MB or 16 MB) prior to buffer allocation.
- If the declared length exceeds the maximum threshold, the decoder shall abort immediately, return a descriptive error, and refrain from executing `make([]byte, length)`.

### 2. Graceful Error Handling on Oversized Frames
- When an oversized gRPC frame is received from an upstream service, the transcoder shall return HTTP `502 Bad Gateway` to the client and log the anomaly.
- The transcoder shall not crash or trigger an unhandled runtime panic under any incoming length value (including `0xFFFFFFFF`).

### 3. Configurable Payload Limits
- Toron shall allow the maximum gRPC frame size to be configured in `config.yaml` under `transcoder.max_frame_size` with a safe default of 4 MB.

## Rationale

Unchecked memory allocations based on wire protocol headers allow compromised or faulty upstream microservices to trigger memory allocation panics by declaring multi-gigabyte payload sizes.

## Constraints

- Seamless integration with existing `framer.go` wire format logic.
- Compatibility with standard gRPC framing rules ([1 byte compressed-flag] + [4 bytes big-endian length]).

## Open Questions
