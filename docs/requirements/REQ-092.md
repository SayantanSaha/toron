# REQ-092 - Unauthenticated Client IP Spoofing and Security Bypass via Missing Physical RemoteAddr Binding in HTTP/2 and HTTP/3 Adapters

## 1. Context & Business Value

Toron Edge Gateway supports multi-protocol ingress, including high-throughput HTTP/1.1 cleartext/TLS via a custom non-blocking reactor, HTTP/2 multiplexing via standard library adapters, and HTTP/3 over QUIC UDP datagrams ([`pkg/server`](file:///Users/sneha/Developer/toron-research/toron/pkg/server)).

During comprehensive security audit [`SR-091 Finding 1`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L78-L99) and vulnerability assessment [`SEC-31`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L428-L436) ([CWE-290 Authentication Bypass by Spoofing](https://cwe.mitre.org/data/definitions/290.html), [CWE-345 Insufficient Verification of Data Authenticity](https://cwe.mitre.org/data/definitions/345.html), [CWE-693 Protection Mechanism Failure](https://cwe.mitre.org/data/definitions/693.html)), a critical vulnerability was uncovered in Toron's core request model and protocol adapter layer:

1. **Missing Physical Address in Request Model**: In [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70), client network identity was coupled solely to the physical socket descriptor field `RawConn net.Conn`. The struct lacked an explicit `RemoteAddr string` field.
2. **Adapter Address Disconnect**: In the HTTP/2 adapter ([`http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L313-L353)) and HTTP/3 adapter ([`ListenAndServeH3`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L406-L437)), incoming requests arrive as Go standard library `*http.Request` instances and are converted into Toron requests via [`httpparser.NewRequestFromStd(r)`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L124). Because multiplexed HTTP/2 streams and HTTP/3 QUIC datagrams do not map 1:1 to standard raw TCP connections, `req.RawConn` was left as `nil`. Furthermore, `NewRequestFromStd(r)` completely discarded `r.RemoteAddr`.
3. **Incomplete HTTP/1.1 Reactor Binding**: In HTTP/1.1 connection handling ([`server.go:handleConn`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L240)), `req.RawConn = conn` was set, but no `RemoteAddr` string was populated on `req`.
4. **Catastrophic Header Fallback Across Security Perimeter**: Throughout the codebase, security-critical modules evaluated client IP identity by checking `if req.RawConn != nil`. Because `req.RawConn` is always `nil` for HTTP/2 and HTTP/3 traffic:
   - **WAF IP Access Control** ([`pkg/waf/ip_acl.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L112-L164)): With `req.RawConn == nil`, the function immediately fell back to trusting unverified client headers `X-Forwarded-For` and `X-Real-IP`.
   - **Internal Management API Subnet Enforcement** ([`pkg/server/internal_api.go:wrapHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L194-L224)): In the absence of `RawConn`, subnet validation fell back to parsing `X-Forwarded-For`.
   - **Token Bucket Rate Limiting** ([`pkg/router/rate_limiter.go:extractClientKeyInternal`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L286-L325)): Line 314 explicitly checked `if peerIsTrusted || req.RawConn == nil`. For all HTTP/2 and HTTP/3 requests, `req.RawConn == nil` evaluated to `true`, causing the rate limiter to unconditionally trust client-supplied `X-Forwarded-For`, `X-API-Key`, and `Authorization` headers.
   - **Reverse Proxy Header Forwarding** ([`pkg/proxy/proxy.go:ServeHTTPWithPrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L816-L857)): Because `req.RawConn` was `nil`, `peerIP` remained empty, causing lines 853-857 to forward untrusted client `X-Forwarded-For` and `X-Real-IP` headers directly to upstream services.
   - **Structured Access Logging** ([`pkg/logging/manager.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/logging/manager.go#L498-L531)): Fell back to client-supplied `X-Forwarded-For` and `X-Real-IP` when `req.RawConn == nil`, allowing spoofed headers to pollute security audit logs.

### Exploitability & Security Impact

Any unauthenticated external attacker connecting to Toron over HTTP/2 or HTTP/3 could send spoofed `X-Forwarded-For: 127.0.0.1` (or any whitelisted CIDR IP) to:
- Completely bypass WAF IP blacklists and access restricted resources.
- Circumvent administrative subnet policies protecting internal management APIs (`/internal/api/*`).
- Evade route-level token bucket rate limiting indefinitely by rotating arbitrary IP strings on each request.
- Inject forged client IP addresses into upstream services, poisoning backend audit logs and security decisions.

Remediating `SEC-31` establishes an unambiguous, tamper-proof binding to the physical remote network address across all supported protocols (HTTP/1.1, HTTP/2, HTTP/3), strictly gating forwarded headers behind verified `trusted_proxies`.

## 2. Non-Goals & Scope Exclusions

### Explicit Exclusion of Sticky Session Load Balancing (`pkg/proxy/sticky.go`)
- **Traffic Steering vs. Security Perimeter**: Sticky session affinity ([`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md)) is an application-level load balancing mechanism designed to route requests from the same client session consistently to an upstream target. It is **NOT** an access control or security authorization perimeter.
- **Mobile Roaming Session Preservation**: Mobile clients connecting over cellular networks frequently experience dynamic physical IP churn as they move between cell towers or transition between cellular networks and Wi-Fi. In `ip_hash` load balancing, inspecting client-level identifiers (such as `X-Forwarded-For` from forward proxies or carrier CGNAT) allows session hashing to remain stable across mobile hops. Forcing `sticky.go` to strictly bind to physical socket address would cause mobile users to repeatedly lose session affinity.
- **Scope Boundary**: `pkg/proxy/sticky.go` was not part of finding `SEC-31` and SHALL NOT be modified under `REQ-092`. The existing implementation of `pkg/proxy/sticky.go:extractClientIP` remains unchanged, preserving full fidelity with [`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md).

## 3. Requirements & Acceptance Criteria

### REQ-092-AC-01: RemoteAddr Binding & Resolution Helper in `httpparser.Request`
- The request struct [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70) MUST include an exported `RemoteAddr string` field.
- The request struct MUST provide helper method(s) (e.g. `RemoteIP() net.IP` and `RemoteHost() string` or equivalent):
  - Safely extract the host portion of `RemoteAddr` using `net.SplitHostPort`, falling back to the raw string if no port is present.
  - Parse and return the physical client `net.IP` (supporting both IPv4 and IPv6).
  - If `RemoteAddr` is unpopulated, inspect `RawConn` (`RawConn.RemoteAddr()`) to extract and parse the IP.
  - Return `nil` (or empty string) if neither `RemoteAddr` nor `RawConn` provides a parseable IP address.

### REQ-092-AC-02: RemoteAddr Population in HTTP/2 and HTTP/3 Protocol Adapters
- In [`pkg/httpparser/request.go:NewRequestFromStd(r *http.Request)`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L124), the parser MUST populate `req.RemoteAddr = r.RemoteAddr`.
- In [`pkg/server/server.go:http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L313-L353), all incoming HTTP/2 requests converted via `NewRequestFromStd(r)` MUST preserve the physical client remote address in `req.RemoteAddr`.
- In [`pkg/server/server.go:ListenAndServeH3`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L406-L437), all incoming HTTP/3 QUIC requests processed via `http2AdapterHandler` MUST preserve the client remote address in `req.RemoteAddr`.

### REQ-092-AC-03: RemoteAddr Population in Native HTTP/1.1 Server Reactor
- In [`pkg/server/server.go:handleConn`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L240), when accepting and processing HTTP/1.1 connections:
  - In addition to setting `req.RawConn = conn`, the server MUST populate `req.RemoteAddr = conn.RemoteAddr().String()` whenever `conn != nil && conn.RemoteAddr() != nil`.

### REQ-092-AC-04: Centralized & Spoof-Proof Physical IP Extraction Across Security Modules
- **WAF IP Access Control** ([`pkg/waf/ip_acl.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L112-L164)):
  - MUST inspect the physical remote address (`req.RemoteIP()` / `req.RemoteAddr` / `req.RawConn`) as the primary client IP.
  - Client-supplied `X-Forwarded-For` and `X-Real-IP` headers MUST NOT be trusted or evaluated when a physical remote address is present, unless the physical remote IP is explicitly verified against configured `trusted_proxies`.
- **Internal Management API Subnet Enforcement** ([`pkg/server/internal_api.go:wrapHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L194-L224)):
  - MUST extract client IP from the physical connection (`req.RemoteIP()` / `req.RemoteAddr` / `req.RawConn`).
  - MUST NOT fall back to client-supplied `X-Forwarded-For` unless originating from a confirmed trusted proxy.
  - If the client IP cannot be verified or does not fall within `parsedSubnets`, access MUST be denied with `403 Forbidden` (`{"error":"403 Forbidden","message":"Access denied by administrative subnet policy"}`).
- **Structured Access Logging** ([`pkg/logging/manager.go:ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/logging/manager.go#L498-L531)):
  - MUST inspect `req.RemoteAddr` and `req.RawConn` before inspecting forwarded headers, logging the true physical client IP when headers are untrusted.

### REQ-092-AC-05: Strict Forwarded Header Gating Against Configured `trusted_proxies`
- Client-supplied forwarded headers (`X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto`) MUST ONLY be trusted if the physical remote peer IP is verified to match a configured `trusted_proxies` CIDR list.
- If no trusted proxies are configured, or if the physical remote IP is not contained in `trusted_proxies`, client-supplied forwarded headers MUST NOT be trusted.
- **Token Bucket Rate Limiting** ([`pkg/router/rate_limiter.go:extractClientKeyInternal`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L286-L325)):
  - The insecure condition `peerIsTrusted || req.RawConn == nil` MUST be eliminated.
  - The rate limiter MUST determine `socketIP` / `socketHost` by inspecting `req.RemoteIP()` / `req.RemoteAddr` as well as `req.RawConn`.
  - If a physical remote IP is present and untrusted, the client key MUST anchor strictly to `ip:<physicalHost>`.
  - Client-supplied headers (`X-Forwarded-For`, `X-API-Key`, `Authorization`) MUST ONLY be utilized for rate limit keying if `peerIsTrusted == true` (physical peer matches configured `trustedProxies`).
  - For synthetic test requests where physical network metadata is absent (`req.RemoteAddr == ""` and `req.RawConn == nil`), fallback behavior MUST NOT allow bypassing rate limits.
- **Reverse Proxy Header Forwarding** ([`pkg/proxy/proxy.go:ServeHTTPWithPrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L816-L857)):
  - Derive `peerIP` and `isTrusted` inspecting `req.RemoteAddr` as well as `req.RawConn.RemoteAddr()`.
  - If `peerIP` is untrusted (or `isTrusted == false`):
    - Outgoing upstream `X-Forwarded-For` MUST be set strictly to `peerIP`.
    - Outgoing upstream `X-Real-IP` MUST be set strictly to `peerIP`.
    - Client-supplied `X-Forwarded-For` and `X-Real-IP` headers MUST be discarded and MUST NOT be forwarded to upstream targets.
  - If and only if `isTrusted == true`:
    - If incoming `X-Forwarded-For` is present, append `peerIP` (`existingXFF + ", " + peerIP`).
    - If incoming `X-Real-IP` is present, preserve it or set it according to proxy configuration.

### REQ-092-AC-06: Fail-Secure Defaults on Missing or Unresolvable Remote Address
- If both `req.RemoteAddr` and `req.RawConn` are missing or unparseable, administrative subnet checks in `internal_api.go` MUST fail closed, denying access with `403 Forbidden`.
- In WAF IP Access Control, requests with unresolvable client IP MUST NOT be allowed to bypass active IP allowlists (aligning with fail-closed security invariants).

### REQ-092-AC-07: Concurrency & Data Race Safety Invariant
- All additions and modifications MUST execute with zero data races under `go test -race ./...`.
- `req.RemoteAddr` MUST be assigned upon request instantiation and remain immutable during concurrent read access by router handlers, middlewares, and proxy engines.

### REQ-092-AC-08: Zero Third-Party Dependencies Invariant
- All network address manipulation, host/port splitting, and CIDR subnet verification MUST strictly use Go standard library packages (`net`, `net/http`, `strings`, `sync`).

### REQ-092-AC-09: Automated Verification & Test Suite Coverage (`TC-092`)
- Automated unit and integration tests MUST verify:
  1. HTTP/2 requests with spoofed `X-Forwarded-For` cannot bypass WAF IP blacklists (`TestServer_H2_WAF_SpoofingRejected`).
  2. HTTP/2 requests with spoofed `X-Forwarded-For` cannot bypass internal management API subnet restrictions (`TestServer_H2_InternalAPI_SubnetEnforcement`).
  3. HTTP/2 requests rotating `X-Forwarded-For` are properly rate-limited to a single physical client bucket (`TestServer_H2_RateLimiter_AntiSpoofing`).
  4. Reverse proxy discards spoofed `X-Forwarded-For` from HTTP/2 and HTTP/3 clients and sets upstream headers strictly to physical `RemoteAddr` when peer is untrusted (`TestServer_H2_ReverseProxy_HeaderSanitization`).
  5. Reverse proxy properly appends physical peer IP when arriving from a configured `trusted_proxies` CIDR (`TestServer_H2_ReverseProxy_TrustedProxyAppended`).
  6. HTTP/3 requests processed through `http2AdapterHandler` / QUIC have physical `RemoteAddr` bound and spoofing rejected (`TestServer_H3_RemoteAddrBinding`).

## 4. Rationale & Threat Model

| Threat Vector | Attack Scenario | Mitigated By |
| :--- | :--- | :--- |
| **WAF Blacklist Evasion** | An attacker blocked by WAF IP ACL connects via HTTP/2 and sends `X-Forwarded-For: 198.51.100.1` to impersonate an unblocked IP. | REQ-092-AC-01, REQ-092-AC-02, REQ-092-AC-04 |
| **Admin API Subnet Bypass** | An external attacker hits `/internal/api/*` via HTTP/2 with `X-Forwarded-For: 10.0.0.5`, bypassing administrative CIDR restrictions. | REQ-092-AC-01, REQ-092-AC-04, REQ-092-AC-06 |
| **Rate Limiting Evasion (DoS)** | An attacker issues 10,000 HTTP/2 requests/second, rotating `X-Forwarded-For: 10.0.X.Y` each time. Since `RawConn == nil`, the rate limiter treats each request as a distinct client. | REQ-092-AC-01, REQ-092-AC-05 |
| **Upstream Log & Auth Poisoning** | An untrusted HTTP/2 client injects false IPs into `X-Forwarded-For`. The reverse proxy forwards these to upstream services, poisoning audit logs and backend security filters. | REQ-092-AC-05 |

### Architectural Boundary: Security Enforcement vs. Application Traffic Steering
A strict distinction is maintained between:
1. **Security Enforcement Components** (`waf/ip_acl.go`, `server/internal_api.go`, `router/rate_limiter.go`, `proxy/proxy.go`, `logging/manager.go`): These components guard perimeter security boundaries and establish trust. They MUST anchor client identity to verified physical connection metadata unless the physical peer is authenticated against `trusted_proxies`.
2. **Session Affinity Load Balancer** (`proxy/sticky.go`): This component performs application traffic distribution. In accordance with [`REQ-030`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-030.md), `ip_hash` balancing must remain resilient to mobile network roaming and upstream CDN routing. It is intentionally excluded from `REQ-092`.

## 5. Constraints & Non-Functional Requirements

- **Protocol Parity**: Security controls MUST enforce identical client IP authentication guarantees across HTTP/1.1, HTTP/2, and HTTP/3.
- **Performance**: Host/port parsing MUST use standard library `net.SplitHostPort` or zero-allocation string slicing, introducing zero measurable latency overhead on request hot paths.
- **Standard Library Only**: Strictly standard library packages (`net`, `net/http`, `strings`, `sync`). Zero external third-party dependencies.
- **Thread Safety**: Fully thread-safe under concurrent requests; verified clean under `go test -race ./...`.
