# REQ-064 - Rate Limiter Memory Bounding, State Eviction, and Client Identity Verification

## Description

The Toron token bucket rate-limiting middleware shall enforce strict memory bounds, automated entry eviction, and verified client identity derivation to prevent Denial of Service (DoS) memory exhaustion and rate limit evasion.

The rate limiter shall guarantee that high volumes of requests with distinct or spoofed headers cannot allocate unbounded memory buckets on the server heap, and that untrusted client headers cannot be used to circumvent rate throttling.

## Acceptance Criteria

### 1. Bounded Bucket Storage & Capacity Limits
- The in-memory bucket store in `RateLimiter` shall have an explicit maximum capacity limit (e.g. 10,000 buckets per route).
- When the storage capacity is reached, the limiter shall evict stale or least-recently-used (LRU) buckets rather than allowing memory consumption to grow without bound.

### 2. Time-To-Live (TTL) State Eviction
- Idle token buckets that have remained full and untouched for longer than a configurable TTL (e.g. 10 minutes) shall be automatically purged by a background sweeper or lazily evicted on access.

### 3. Untrusted Client Header Protection
- The rate limiter shall derive the client's rate-limiting key strictly from the trusted physical socket `RemoteAddr` by default.
- Client-supplied headers (such as `X-Forwarded-For` or `X-Real-IP`) shall only be evaluated if the physical connection originates from an explicitly configured trusted proxy CIDR.
- Unverified `X-API-Key` or `Authorization` headers shall not grant an unauthenticated client an isolated rate bucket unless the key has been validated against active authentication credentials.

### 4. Memory Exhaustion Mitigation
- The rate limiter shall fail-safe: under extreme memory pressure or capacity overflow, it shall not panic with an Out-Of-Memory (OOM) error.

## Rationale

Unconstrained maps storing client state allow attackers to exhaust server heap memory simply by rotating randomized `X-Forwarded-For` or fake API key headers, bypassing rate limits while crashing the host process.

## Constraints

- Zero external datastore dependency (must work reliably in-memory for standalone instances).
- Thread-safe synchronization with minimal lock contention.
