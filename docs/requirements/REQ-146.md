# REQ-146 - Alerts and Threat Defense Control Center Redesign (Deduplication, Search, Pagination, Incident Drawer, and Metrics)

## 1. Description & Problem Statement

### 1.1 Operational Context & Background
The Toron Edge Gateway Control Center delivers real-time telemetry, routing management, and security observability directly from the embedded dashboard at `#/alerts` (served via `public/js/views/alerts.js` under the modular architecture defined in [REQ-141](./REQ-141.md)). Under active production workloads, Toron's Web Application Firewall (WAF) inspects incoming requests using OWASP Core Rules and custom regex patterns, while the automated two-stage threat defense reactor quarantines abusive actors (Stage 1: temporary 1-hour ban, Stage 2: permanent firewall ban).

As traffic volume and security anomaly events increase, operators have reported severe visual clutter, performance degradation, and workflow friction:
> *"The alerts list and blocked ips list are getting very long. We need to redesign this page."*

A comprehensive architectural and functional analysis in [AN-007](../analysis/AN-007.md) identified six structural defects in the current implementation:
1. **Data Model Duplication & Badge Distortion**: Active IP bans are injected simultaneously into both `D.alerts` and `D.bannedIps` within `public/js/model.js`. Consequently, every banned IP renders twice on the screen and falsely inflates the primary navigation alert badge and the Overview dashboard health status banner.
2. **Missing Pagination and Data Filtering**: Neither the active alerts/incidents list nor the banned IPs table provides client-side pagination, search input, or severity/tier facet filtering. High incident volumes generate hundreds of unorganized DOM elements, forcing excessive vertical scrolling.
3. **Responsive Header Layout Collisions**: The manual IP ban input form is placed directly inside the card header flex row (`.card-h`), causing wrapping and layout breakage on viewports below 1200px width.
4. **Thread-Blocking Synchronous Dialogs**: Unban operations trigger browser-native `confirm()` and `alert()` modals, freezing JavaScript execution, interrupting background telemetry polling, and preventing headless automation.
5. **Inaccessible Forensic Telemetry**: Backend WAF audit events contain rich forensic metadata (rule ID, category, anomaly score, matched parameter location, and payload snippet via `pkg/waf/audit.go`), but the UI drawer (`public/js/components/drawer.js`) only supports route details and request log traces.
6. **Absence of High-Level Operational Metrics**: The view lacks an executive Key Performance Indicator (KPI) metrics strip to provide security operators with immediate situational awareness of threat volumes, block rates, and ban tier distributions.

This requirement defines the formal contract for redesigning the Alerts & Threat Defense Control Center into a high-density, ergonomic, and forensic-grade security cockpit without introducing external runtime dependencies.

## 2. Functional Requirements

### 2.1 FR-146-1: Data Model Normalization and Deduplication
1. The client data model builder (`public/js/model.js`) shall strictly isolate operational system alerts, WAF security incidents, and active firewall bans into distinct, cohesive properties on the computed data model `D`:
   - `D.alerts`: Strictly limited to unresolved operational system health degradations (e.g. failing upstream pool instances, 5xx error rate spikes exceeding thresholds, failing ACME SSL certificate renewals) and active unmitigated security anomalies.
   - `D.incidents`: Dedicated array containing structured WAF security incidents parsed from `/internal/api/security/incidents`.
   - `D.bannedIps`: Dedicated array containing active IP firewall bans parsed from `/internal/api/security/banned-ips`.
2. **Elimination of Duplicate Ban Injections**:
   - The model builder shall NOT push banned IP records (`rawApiBannedIps`) into `D.alerts`.
   - Banned IPs shall exist exclusively within `D.bannedIps`.
3. **Navigation Badge & Overview Status Integrity**:
   - The navigation badge count for Alerts (`#nav button[data-nav="alerts"] .badge`) and the Overview status banner (`#/overview`) shall reflect only active unresolved alerts and unmitigated incidents.
   - Mitigated actors already quarantined in `D.bannedIps` shall not inflate active operational alert counts.

---

### 2.2 FR-146-2: Unified Data Navigation (Search, Filtering, and Pagination)
1. **Client-Side Pagination**:
   - The Alerts & Threat Defense view shall implement client-side pagination for both the active alerts/incidents feed and the banned IPs table, matching the interaction pattern established in `public/js/views/logs.js`.
   - Supported configurable page sizes: 10, 25, and 50 records per page (defaulting to 10 for alerts/incidents and 25 for banned IPs).
   - Pagination controls shall provide First (`«`), Previous (`‹`), Next (`›`), and Last (`»`) buttons, an interactive page size dropdown, a current page indicator (`Page X / Y`), and a summary text string (`Showing start–end of total items`).
   - Slicing shall be non-blocking and execute immediately within the client without triggering backend round-trips.
2. **Real-Time Text Search**:
   - A search input control (`<input type="search">`) shall filter records in real time based on user typing.
   - For Incidents: Search query matches against Client IP, Rule ID, Path, Category, and Payload text.
   - For Banned IPs: Search query matches against Client IP, Reason, and Category.
   - Search matching shall be case-insensitive and perform substring evaluation across all relevant attributes.
   - Applying or updating a search query shall reset pagination to Page 1.
3. **Faceted Filter Chips**:
   - The UI shall provide toggleable facet filter chips:
     - **Severity Filter**: `All`, `Critical`, `Warning`.
     - **Ban Tier Filter**: `All`, `Stage 1 (1h Temp)`, `Stage 2 (Permanent)`.
   - Activating a facet filter chip shall immediately filter the active view and reset pagination to Page 1.

---

### 2.3 FR-146-3: Multi-Level Deterministic Interactive Column Sorting
1. The Banned IPs table shall support interactive sorting on all primary data columns:
   - `Client IP` (lexicographical / numeric IP collation).
   - `Ban Tier` (Stage 1 Temporary vs. Stage 2 Permanent).
   - `Created At` (calendar timestamp).
   - `Temp Bans` (strike count integer).
   - `Reason / Category` (textual description).
   - `TTL / Expiry` (remaining duration integer).
2. **Sort Direction & Visual Indicators**:
   - Clicking a sortable column header (`<th>`) shall toggle sorting between descending (`desc`) and ascending (`asc`).
   - The active sort column shall display a visible directional indicator (`▲` for ascending, `▼` for descending).
3. **Deterministic Multi-Level Tie-Breaking**:
   - Sorting shall comply with [REQ-138](./REQ-138.md) and [ADR-138](../architecture/ADR-138.md). When two or more records share identical values in the primary sort column, the system shall apply a deterministic secondary tie-breaker by sorting on `ip` ascending (`localeCompare` with `{ numeric: true }`).

---

### 2.4 FR-146-4: Ergonomic & Responsive Manual Ban Controls
1. The manual IP ban interface shall be decoupled from the table header flex row (`.card-h`) and relocated into an ergonomic management toolbar or dedicated action modal/card.
2. **Form Input Specifications**:
   - **Client IP Input**: Single-line text input with client-side syntax validation verifying valid IPv4 (dotted decimal) or IPv6 (colon hexadecimal) format before dispatch.
   - **Ban Tier & Preset Duration Selection**: Support quick preset selections (`15m`, `1h`, `6h`, `24h`, `7d`, and `Permanent`), automatically configuring Stage 1 Temporary (with the specified duration) or Stage 2 Permanent, alongside an optional custom duration input.
   - **Reason Description**: Text input allowing operators to provide context (e.g. `Credential stuffing on /v1/auth`, `Automated vulnerability scanner`).
3. **Action Submission**:
   - Submitting the ban shall dispatch `POST /internal/api/security/ban` with JSON payload `{ ip, type, duration, reason }`.
   - Upon successful response, the form inputs shall clear and the view shall trigger an immediate data refresh.

---

### 2.5 FR-146-5: Non-Blocking Confirmations and Feedback
1. **Elimination of Synchronous Primitives**:
   - The application shall contain zero calls to browser-native `window.confirm()` and `window.alert()`.
2. **In-App Unban Confirmation**:
   - Unbanning an IP shall require an explicit user confirmation executed via a non-blocking in-app mechanism (such as an in-app confirmation modal utilizing `#scrim`, or an inline two-step confirmation button state that reverts after an inactivity timeout).
3. **Non-Blocking Toast / Callout Notifications**:
   - Unban success, manual ban success, and backend API errors shall be communicated through non-blocking in-app toast banners or callout notifications.
   - Notifications shall automatically dismiss or offer a manual close button, without blocking the browser event loop or background timers.

---

### 2.6 FR-146-6: Deep Forensic Incident Investigation Drawer
1. The application slide-out drawer (`public/js/components/drawer.js`) shall support `kind === 'incident'`.
2. **Drawer Invocation**:
   - Clicking any incident row or item in the active incidents feed shall open `#drawer` populated with the corresponding security event metadata.
3. **Forensic Telemetry Rendering**:
   - The incident drawer shall display:
     - **Header**: Incident title, rule category, and severity pill badge.
     - **Core Forensics**: OWASP/Custom Rule ID, Anomaly Score, Action taken (`blocked` vs `logged`), and HTTP Request Method.
     - **Target Endpoint**: Full Request Path and URI parameters.
     - **Actor Provenance**: Client IP address with copy convenience action.
     - **Detection Location**: Parameter location (e.g. `query`, `header`, `body`, `cookie`).
     - **Temporal Context**: Full calendar datetime (`YYYY-MM-DD HH:MM:SS`) and relative elapsed time.
     - **Attack Payload Snippet**: Raw payload snippet rendered in a dedicated preformatted syntax container (`<pre class="cs-pre">`) with horizontal overflow handling.
4. **Integrated Quick Actions**:
   - **"Ban Client IP" Button**: Opens the manual ban form pre-filled with the incident's client IP, severity-recommended tier, and rule-derived reason.
   - **"Filter Logs for IP" Button**: Navigates directly to `#/logs` with the search filter pre-populated with the offending client IP.

---

### 2.7 FR-146-7: Executive Security Telemetry & KPI Metrics Strip
1. The top of the Alerts & Threat Defense view (`#/alerts`) shall render a 4-card Key Performance Indicator (KPI) metrics strip:
   - **Card 1: Active Incidents / Alerts**: Total count of active unresolved operational alerts and recent security incidents.
   - **Card 2: Recent WAF Blocks**: Total threats intercepted and dropped by WAF rules in the current telemetry window.
   - **Card 3: Stage 1 Temp Bans**: Total count of client IP addresses currently undergoing 1-hour quarantine.
   - **Card 4: Stage 2 Permanent Bans**: Total count of repeat offender client IP addresses permanently blocked in the firewall.
2. Each KPI card shall display the numeric metric value, a descriptive label, and visual status tone indicators matching the Toron design system.

## 3. Non-Functional Requirements

### 3.1 NFR-146-1: Performance & Rendering Responsiveness
- Client-side pagination, search filtering, and column sorting must execute in under 16 ms (targeting 60 fps DOM updates) for ban lists up to 2,000 entries and incident buffers up to 500 events.
- Slicing and DOM construction must not cause layout thrashing or dropped frames.

### 3.2 NFR-146-2: Zero External Runtime & Build Dependencies
- In accordance with Toron core principles and [REQ-141](./REQ-141.md), all frontend modifications must use standard vanilla browser ECMAScript Modules (ESM) and native CSS.
- Zero npm dependencies, zero frontend frameworks (React, Vue, Svelte), and zero bundler build steps (Webpack, Vite, Rollup) are permitted.

### 3.3 NFR-146-3: UI Thread Liveness and Non-Blocking Concurrency
- The frontend execution loop must never be blocked by synchronous JavaScript primitives.
- Background telemetry polling (`api.js`), chart rendering, live log tailing, and websocket/timer ticks must continue uninhibited during user confirmation workflows.

### 3.4 NFR-146-4: Viewport Adaptability & Responsive Design
- The redesigned view must adapt seamlessly across desktop monitors, laptop screens, and tablet viewports down to a minimum width of 768px (with readable layout support down to 320px).
- Tables must feature horizontal scroll wrappers (`.tscroll`) to prevent layout clipping on constrained displays.

### 3.5 NFR-146-5: Backward Compatibility
- Backend REST endpoints (`/internal/api/security/incidents`, `/internal/api/security/banned-ips`, `/internal/api/security/ban`, `/internal/api/security/unban`) must not undergo breaking schema changes.
- Overview page indicators, route inspection, and log tailing must continue to operate seamlessly alongside the redesigned alerts view.

## 4. Acceptance Criteria

### AC-146-01: Data Model Normalization and Ban Deduplication
- **Given** the gateway has 1 failing upstream pool, 10 active temporary IP bans, and 5 permanent IP bans recorded in backend APIs,
- **When** `buildDataModel()` constructs the client telemetry model `D`,
- **Then** `D.alerts` must contain exactly 1 entry corresponding to the upstream failure, `D.bannedIps` must contain exactly 15 entries, no banned IP shall appear within `D.alerts`, and the navigation badge for Alerts must display `1` rather than `16`.

### AC-146-02: Client-Side Pagination for Incidents and Banned IPs
- **Given** a list of 45 banned IP addresses and a page size setting of 10,
- **When** the operator views the Banned IPs table,
- **Then** the table must display exactly rows 1 through 10, the pagination indicator must display `Page 1 / 5`, the summary must indicate `Showing 1–10 of 45`, the `Previous` and `First` buttons must be disabled, and clicking `Next` must transition the view to display rows 11 through 20 with `Page 2 / 5`.

### AC-146-03: Real-Time Multi-Attribute Search and Faceted Filtering
- **Given** a populated list of 30 security incidents containing diverse client IPs and attack categories (e.g. `SQLi`, `XSS`, `Path Traversal`),
- **When** the operator enters `sqli` into the incident search input,
- **Then** the displayed list must immediately filter to show only incidents where the category, rule ID, path, or payload snippet contains `sqli` (case-insensitive), and the pagination must automatically reset to Page 1.

### AC-146-04: Deterministic Multi-Level Interactive Column Sorting
- **Given** the Banned IPs table displaying multiple records with identical creation timestamps,
- **When** the operator clicks the `Client IP` column header,
- **Then** the table rows must sort alphabetically/numerically by IP address, the column header must display the ascending indicator `▲`, and clicking the header a second time must reverse the sort order to descending with indicator `▼`; furthermore, when sorting by `Created At`, records with identical timestamps must break ties deterministically by sorting on `ip` ascending.

### AC-146-05: Decoupled Ergonomic Manual Ban Form with Input Validation
- **Given** the redesigned manual ban controls on `#/alerts`,
- **When** an operator inputs an invalid IP format (e.g. `999.999.999.999` or `invalid-ip`) and clicks `Ban IP`,
- **Then** the client must reject the submission with an inline validation message without dispatching a network request; and **When** a valid IPv4 or IPv6 address is entered with tier `Stage 1` and reason `Scanning probe`, the client must dispatch `POST /internal/api/security/ban` with valid JSON payload and refresh the threat table upon success.

### AC-146-06: Non-Blocking In-App Confirmation and Toast Feedback for Unban
- **Given** an active banned IP in the threat defense table,
- **When** the operator clicks the `Unban` action button,
- **Then** the UI must trigger a non-blocking in-app confirmation (modal dialog or two-step confirmation state) without calling `window.confirm()`, background polling timers must continue executing without interruption, and upon confirming unban, a non-blocking toast notification must report completion status.

### AC-146-07: Forensic Incident Investigation Drawer with Attack Telemetry and Quick-Ban
- **Given** an active WAF incident item in the incidents list,
- **When** the operator clicks the incident item,
- **Then** the slide-out inspector drawer (`#drawer`) must open with `kind === 'incident'`, displaying the triggering OWASP Rule ID, Anomaly Score, Action taken, Parameter Location, HTTP Method, Target Path, Client IP, and the raw attack payload snippet inside a `<pre class="cs-pre">` block; and clicking the `Ban Client IP` action button inside the drawer must open the ban workflow pre-populated with the incident's IP and category.

### AC-146-08: Executive Security KPI Metrics Calculation
- **Given** the gateway reporting 2 active operational alerts, 18 recent WAF rule block events, 7 Stage 1 temporary bans, and 3 Stage 2 permanent bans,
- **When** the operator navigates to `#/alerts`,
- **Then** the top KPI strip must render 4 distinct metric cards displaying `2` for Active Incidents/Alerts, `18` for Recent WAF Blocks, `7` for Stage 1 Temp Bans, and `3` for Stage 2 Permanent Bans.

## 6. Constraints & Invariants

1. **Zero External Frontend Dependencies**: All styling, templating, pagination, search algorithms, and modal interactions must be implemented in native vanilla JavaScript (ES2022+) and CSS3 without npm packages or CDNs.
2. **Zero Backend API Breaking Changes**: The frontend redesign must interface cleanly with the existing endpoints in `pkg/server/internal_api.go`:
   - `GET /internal/api/security/incidents`
   - `GET /internal/api/security/banned-ips`
   - `POST /internal/api/security/ban`
   - `POST /internal/api/security/unban`
3. **No UI Freezing**: Synchronous `window.confirm()` and `window.alert()` are strictly prohibited.
4. **Strictly Relative Links**: All documentation and code references must strictly use relative links. Absolute file paths and machine URIs are forbidden.

## 7. Open Questions

1. **Circular Incident Buffer Depth**:
   - Backend `AuditLogger` currently maintains a circular buffer of the most recent 50 events (`maxEvents: 50`). If operational demands require inspecting a deeper event horizon, should `maxEvents` be configurable via server startup configuration? *(Analysis: 50 events provides ample coverage for live edge anomaly inspection; historical logging is persisted to stdout/disk logs).*
2. **Preset Ban Durations**:
   - Should temporary ban durations offer standard quick-select presets (e.g. 15m, 1h, 6h, 24h, 7d) in addition to arbitrary duration strings? *(Analysis: Standard presets with a custom duration fallback offer optimal ergonomics and prevent input syntax errors).*
