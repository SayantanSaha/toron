# TC-129 - Test Specification for Streaming by Default Reverse Proxy Architecture, RFC 7230 Outbound Chunked Framing, and Memory Boundedness Invariants

## 1. Test Suite Overview & Problem Formulation

### 1.1 Executive Summary & Problem Context
During high-throughput resilience evaluations, streaming architecture audits, and denial-of-service vulnerability assessments of Toron's core reverse proxy and server engines ([`REQ-129`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-129.md), [`TASK-152`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-152.md), [`ADR-129`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-129.md)), four systemic vulnerabilities and architectural bottlenecks were identified:

1. **The Upstream Infinite Stream OOM Bomb ([`SEC-36`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L483-L491), [CWE-400 Uncontrolled Resource Consumption](https://cwe.mitre.org/data/definitions/400.html), [CWE-770 Allocation of Resources Without Limits or Throttling](https://cwe.mitre.org/data/definitions/770.html))**:
   - In [`pkg/proxy/proxy.go:1105`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L1105), streaming eligibility was gated by:
     ```go
     canStream := p.streamResponse && ((!p.routeHasCompression && !p.routeHasCache) || isStreamingMIME || isUnbuffered)
     ```
   - In standard production configurations, web and API gateways attach response caching ([`ResponseCache`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/cache.go#L80)) or transparent compression ([`CompressionMiddleware`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/compression.go#L80)) to routes (e.g. `/api/v1/*`, `/data/*`).
   - Unless an upstream response explicitly declared `Content-Type: text/event-stream` or `X-Accel-Buffering: no` ([`REQ-128`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-128.md)), `canStream` evaluated to `false`.
   - Toron unconditionally fell back to unbounded ingestion via `io.CopyBuffer(res.Body, outResp.Body, *bufPtr)`.
   - When an upstream origin returned an oversized binary file, multi-gigabyte download, continuous telemetry feed, or infinite data stream (e.g. `/dev/urandom`), `res.Body` (`*bytes.Buffer`) expanded dynamically on the Go heap until the operating system Out-Of-Memory (OOM) killer terminated the Toron gateway process, severing ingress traffic for all production services.

2. **HTTP/1.1 Persistent Keep-Alive Connection Degradation on Streaming**:
   - In [`pkg/server/server.go:344-376`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L344-L376), when `res.StreamBody != nil`, the server flushed raw stream chunks to the client socket without RFC 7230 Chunked Transfer Coding framing (`Transfer-Encoding: chunked`).
   - Because dynamic streaming payloads lack a known `Content-Length`, HTTP/1.1 clients could not determine payload boundaries without TCP connection closure.
   - Toron was forced to terminate the client TCP connection upon stream completion (`return nil`), breaking HTTP/1.1 persistent connection reuse (`Connection: keep-alive`). Every streaming transaction incurred fresh TCP three-way handshakes and TLS cryptographic handshakes, inducing latency spikes and `TIME_WAIT` socket exhaustion.

3. **Inbound Request Smuggling Defense Decoupling ([`ADR-056`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-056.md), [`REQ-061`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-061.md), [CWE-444](https://cwe.mitre.org/data/definitions/444.html))**:
   - Toron strictly guards against HTTP Request Smuggling by rejecting inbound client requests declaring `Transfer-Encoding: chunked` with HTTP `501 Not Implemented`.
   - Outbound HTTP/1.1 response chunking must be implemented without modifying or weakening inbound request smuggling defenses. Outbound chunking must be restricted strictly to downstream response serialization in `pkg/server`.

4. **Stream Desynchronization & Socket Descriptor Leaks ([CWE-444](https://cwe.mitre.org/data/definitions/444.html), [CWE-775](https://cwe.mitre.org/data/definitions/775.html))**:
   - If an upstream stream aborts prematurely, times out, or encounters a transport error, emitting a terminal chunk (`0\r\n\r\n`) would falsely signal clean completion, causing downstream clients and caching proxies to accept and store truncated payloads.
   - Abrupt client disconnects must cleanly propagate upstream context cancellation, and upstream response bodies must be closed under all exit paths to prevent file descriptor leaks (`EMFILE`).

### 1.2 Core Architectural Objectives & The 4 Non-Negotiable Invariants

To eliminate these vulnerabilities, [`REQ-129`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-129.md) and [`ADR-129`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-129.md) establish a unified architecture verified by this test specification under 4 Non-Negotiable Invariants:

```
+-----------------------------------------------------------------------------------------+
|                           THE 4 NON-NEGOTIABLE INVARIANTS                               |
|                                                                                         |
|  1. CONSTANT O(1) MEMORY BOUNDEDNESS:                                                   |
|     Per-stream heap allocation strictly <= 32 KB across all payload sizes and types.    |
|     Completely eliminates the Upstream Infinite Stream OOM Bomb (SEC-36, CWE-400).     |
|                                                                                         |
|  2. STRICT INBOUND SMUGGLING GUARD (ADR-056 INTACT):                                    |
|     Inbound client requests with Transfer-Encoding: chunked strictly rejected (HTTP 501)|
|     Outbound chunked framing isolated strictly to response generation in pkg/server.   |
|                                                                                         |
|  3. FAIL-CLOSED FRAMING (ANTI-DESYNCHRONIZATION GUARD, CWE-444):                        |
|     On stream read errors or timeouts, NEVER emit 0\r\n\r\n.                            |
|     Immediately terminate client TCP connection (conn.Close()).                         |
|                                                                                         |
|  4. SLOW-CLIENT PROTECTION VIA ACTIVITY-REFRESHED WRITE DEADLINES:                      |
|     Every chunk write refreshes socket write deadline (REQ-126).                        |
|     Slow Read DoS attacks disconnected deterministically within WriteTimeout.          |
+-----------------------------------------------------------------------------------------+
```

### 3.3 Mathematical Formulations & Latency / Memory Physics

#### 1. Constant Memory Boundedness vs Unbounded Buffer Ingestion
Let $R_{\text{upstream}}(t)$ be the rate of incoming bytes from the upstream origin at time $t$.
Let $T_{\text{end}}$ be the duration of the response stream.

Under the vulnerable fallback implementation (`canStream == false`), memory consumed by `res.Body` was:
$$M_{\text{heap}}(t) = \int_0^t R_{\text{upstream}}(u) \, du$$
For infinite streams ($T_{\text{end}} \to \infty$) or multi-gigabyte downloads ($M_{\text{heap}} > \text{RAM}_{\text{available}}$):
$$\lim_{t \to T_{\text{oom}}} M_{\text{heap}}(t) \ge \text{Host Limit} \implies \text{SIGKILL (Kernel OOM Killer)}$$

Under `ADR-129` dynamic bounded clamping:
$$\forall t \in [0, T_{\text{end}}]: \quad M_{\text{stream}}(t) \le S_{\text{slab}} = 32\,768\text{ bytes} \quad (O(1)\text{ constant bound})$$

#### 2. Dynamic Clamping Decision Predicate
Let $\text{streamResponse} \in \{\text{True}, \text{False}\}$.
Let $\text{hasMW} = \text{routeHasCompression} \lor \text{routeHasCache}$.
Let $L$ be the response body `ContentLength`.
Let $M_{\text{max}}$ be the route's configured `MaxPayloadSize` (default: $1\,048\,576$ bytes / 1 MB).
Let $\text{TE}$ be the upstream `Transfer-Encoding` header.

The dynamic clamping activation condition `canStream` in [`pkg/proxy/proxy.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go) is evaluated as:
$$\text{canStream} = \text{streamResponse} \land \Big( \neg \text{hasMW} \lor \text{isSSE} \lor \text{isUnbuffered} \lor (L < 0 \lor \text{EqualFold}(\text{TE}, \text{"chunked"})) \lor (L > M_{\text{max}}) \Big)$$

#### 3. RFC 7230 §4.1 Outbound Chunk Framing Grammar
Each chunk $k$ of size $N_k > 0$ emitted by the server conforms to:
$$\text{Chunk}_k = \text{Hex}(N_k) + \text{"\textbackslash r\textbackslash n"} + \text{Payload}[0..N_k-1] + \text{"\textbackslash r\textbackslash n"}$$
Terminal clean EOF chunk:
$$\text{Chunk}_{\text{terminal}} = \text{"0\textbackslash r\textbackslash n\textbackslash r\textbackslash n"}$$

#### 4. Fail-Closed Anti-Desynchronization Invariant
Let $E_{\text{stream}}$ be the termination event of `res.StreamBody.Read()`.
$$\text{WireAction}(E_{\text{stream}}) = \begin{cases} 
\text{Emit }\text{"0\textbackslash r\textbackslash n\textbackslash r\textbackslash n"} \land \text{Preserve Keep-Alive Socket} & \text{if } E_{\text{stream}} = \text{io.EOF} \\
\text{Suppress }\text{"0\textbackslash r\textbackslash n\textbackslash r\textbackslash n"} \land \text{conn.Close()} & \text{if } E_{\text{stream}} \ne \text{io.EOF} \text{ (Error / Abort / Timeout)}
\end{cases}$$

## 7. Open Questions & Approvals

- *Open Question 1*: Should the maximum buffering clamp threshold (`MaxPayloadSize`) be configurable per route or globally?
  - *Resolution*: Supported at both levels. `AppConfig.Server.Cache.MaxPayloadSize` and `ProxyOptions.MaxPayloadSize` provide a global default of 1 MB (`1048576` bytes), while route entries in `routes.yaml` can override this via `routes[].max_payload_size`. Verified in TC-129.3 and TC-129.4.
- *Open Question 2*: Should HTTP/1.0 clients receiving a streaming response receive chunked transfer encoding?
  - *Resolution*: RFC 7230 §3.3.1 explicitly specifies that HTTP/1.0 does not support `Transfer-Encoding: chunked`. For HTTP/1.0 clients, the server emits headers without `Transfer-Encoding`, streams raw chunks without chunked framing, and terminates the connection on clean EOF (`Connection: close`). Verified in TC-129.11.
