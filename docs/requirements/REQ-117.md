# REQ-117 - Disaggregated Adversarial Status Classification and Route-Miss Separation in Benchmark Load Generator (HARN-01)

## 1. Description & Problem Statement

### 1.1 Executive Summary & Review Critique
In academic peer reviews of Paper 1 and Paper 2 (documented in `AER-001.md`, `AER-002.md`, and formalized under Directive `REV-03` / Task `HARN-01` of `ReviewTaskSummary.md`), reviewers raised critical methodological challenges against the adversarial stress evaluation reported in Table 6. 

Specifically, Table 6 reported a **100.0% active defense enforcement rate** across all eight adversarial protocol vectors under high-concurrency saturation (5,000+ RPS). However, deep telemetry extraction and status code auditing revealed a severe circular scoring anomaly in the benchmark load generator harness (`benchmarks/wrk2/loadgen.go`):
- In BMK-04 saturation evaluations, **349 probes** targeting vector `ADV-06` (Path Traversal Directory Escape, `GET /../../canary_traversal.txt`) returned HTTP **`404 Not Found`**, not an active security rejection (**`400 Bad Request`**, **`403 Forbidden`**, or **`413 Payload Too Large`**).
- Due to a circular catch-all `else` clause in `loadgen.go` (lines 382–386), these 349 route misses were indiscriminately incremented into `attackRejected` and recorded as successful active defense.
- This conflated passive router non-matching with active security defense, artificially inflating the reported security score to 100.0% and obscuring the underlying path traversal routing bug addressed in `REQ-116`.

Reviewers correctly argued that classifying a `404 Not Found` response as active defense is scientifically invalid:
> *"A 404 response simply denotes that the request did not match a registered URI handler. If an adversarial probe penetrates routing filters and reaches a passive 404 handler, scoring this as an active security defense masks routing vulnerabilities and inflates defense metrics. The benchmark harness must explicitly decouple active defensive rejections from passive route misses."* (`AER-002`, lines 312–318)

### 1.2 Root Cause Analysis of Circular Scoring Anomaly
Inspection of `benchmarks/wrk2/loadgen.go` (lines 375–390) revealed the following implementation:

```go
// Line 375-386 in benchmarks/wrk2/loadgen.go
// Assert active defense enforcement: 400 Bad Request or 403 Forbidden
if code == http.StatusBadRequest || code == http.StatusForbidden || code == http.StatusRequestEntityTooLarge || code == http.StatusNotImplemented {
    attackRejected.Add(1)
    stats.rejected.Add(1)
} else if code == http.StatusOK {
    attackBypassed.Add(1)
    stats.bypassed.Add(1)
} else {
    // Other rejections (e.g. 500, socket drop) still constitute defense block
    attackRejected.Add(1)
    stats.rejected.Add(1)
}
```

The fundamental flaws in this architectural logic are:
1. **The Circular Catch-All**: Any HTTP response code other than `200 OK` (such as `404 Not Found`, `301 Moved Permanently`, `500 Internal Server Error`, or `502 Bad Gateway`) was routed into the `else` branch, incrementing `attackRejected` and `stats.rejected`.
2. **Omission of Valid Active Defense Codes**: Standard HTTP defense codes such as `431 Request Header Fields Too Large` (returned by Toron's parser on oversized headers, `ADV-07`) were omitted from the explicit `if` condition and only captured via the accidental `else` fallback.
3. **Route Miss Conflation**: An attack probe targeting an unmapped endpoint or evading router prefix boundaries to produce a `404 Not Found` was erroneously credited as active defense rather than flagged as an unintercepted route miss.
4. **Lack of Anomaly Isolation**: Internal server panics or unhandled errors producing `500 Internal Server Error` were scored as active defense rather than server crashes or implementation failures.

### 1.3 Empirical Evidence & Table 6 Invalidation
In the raw benchmark artifacts (`benchmarks/results/saturation_stress_report.json`), the status code distribution for the adversarial stream was:
```json
"adversarial_stream": {
    "total_requests": 2431,
    "success_requests": 2431,
    "failed_requests": 0,
    "status_codes": {
        "400": 1819,
        "404": 349,
        "431": 263
    }
}
```
Cross-referencing this against vector telemetry:
- Total probes for `ADV-06` (Path Traversal): exactly **349 probes**.
- All 349 `ADV-06` probes returned `404 Not Found`.
- Total probes for `ADV-07` (Oversized Request Header Block): exactly **263 probes**.
- All 263 `ADV-07` probes returned `431 Request Header Fields Too Large`.
- Because of the catch-all `else`, both `404` (349 probes) and `431` (263 probes) were dumped into `attackRejected`, falsely showing `349/349 (100.0%)` rejection for `ADV-06` in Table 6.

### 1.4 Interplay with Layered Path Traversal Defense (REQ-116)
`REQ-116` establishes layered route-aware path traversal defense inside Toron's WAF and Router, guaranteeing that traversal sequences (`ADV-06`) are actively intercepted with `403 Forbidden` and `Connection: close`. However, the benchmark harness must enforce strict classification independently of the system under test. 

Under `REQ-117`, `loadgen.go` shall permanently disaggregate status classification so that:
- Any `404 Not Found` response emitted in response to an adversarial probe is strictly classified as a **Route Miss** (`attackRouteMiss`), completely disqualified from active defense credit, and explicitly reported in all outputs.
- Any attempt by a server to satisfy an adversarial probe with a `404` will immediately cause the testbed to register a non-100% active defense rate and fail the overall evaluation verdict.

## 2. Status Code Taxonomy & Architectural Disaggregation

To ensure scientific integrity and alignment with RFC standards and MITRE CWE taxonomies, `loadgen.go` shall establish a strict, mutually exclusive four-tier classification system for all adversarial probe responses.

```
+---------------------------------------------------------------------------------------+
|                             Adversarial Response Code                                 |
+---------------------------------------------------------------------------------------+
       |                               |                          |                |
       v                               v                          v                v
[ Active Defense ]              [ Route Miss ]            [ Attack Bypass ]  [ Unhandled Anomaly ]
  - 400 Bad Request               - 404 Not Found           - 200 OK           - 500 Internal Error
  - 403 Forbidden                                           - 2xx / 3xx        - 502 Bad Gateway
  - 413 Payload Too Large                                                      - 503 Unavailable
  - 431 Headers Too Large                                                      - 504 Gateway Timeout
  - 501 Not Implemented                                                        - Non-standard codes
```

### 2.1 The Four-Tier Status Taxonomy

#### Tier 1: Active Defense (`attackRejected` / `stats.rejected`)
An active defense response indicates that the edge gateway's security enforcement layers (L7 WAF, HTTP parser invariants, framing validators, or route boundary guards) explicitly detected a protocol violation or malicious payload and deliberately rejected the connection with a fail-fast error code:
- **`400 Bad Request`**: Malformed HTTP framing, RFC 7230 syntax violations, invalid header token grammar, whitespace-obfuscated delimiters, or null-byte injections.
- **`403 Forbidden`**: Access control violations, WAF threat rule matches, or route-aware path traversal prefix boundary escapes (`REQ-116`).
- **`413 Payload Too Large`**: Maximum request body length exceeded.
- **`431 Request Header Fields Too Large`**: Header buffer exhaustion or oversized header blocks exceeding RFC 6585 limits (`ADV-07`).
- **`501 Not Implemented`**: Unsupported HTTP transfer codings or methods deliberately rejected by the gateway parser.

#### Tier 2: Route Miss (`attackRouteMiss` / `stats.routeMiss`)
A route miss occurs when the edge gateway fails to recognize a security violation and instead treats the request as a normal lookup for a non-existent route:
- **`404 Not Found`**: The gateway's router dispatched the request to the default not-found handler because the path did not match any registered route table entry.
- **Security Implication**: A `404` response does NOT represent an active security defense. The request may have bypassed security inspection, traversed directory hierarchies, or desynchronized routing states, only to miss an arbitrary backend resource. It must be tracked as an operational route miss and strictly excluded from defense rates.

#### Tier 3: Attack Bypass (`attackBypassed` / `stats.bypassed`)
An attack bypass occurs when an adversarial probe is accepted by the gateway and processed as a benign, successful transaction:
- **`200 OK` (and unexpected 2xx/3xx)**: The malicious payload successfully reached an application handler or upstream origin service and returned a success or redirection status.
- **Security Implication**: An absolute invariant failure (security breach or protocol desynchronization).

#### Tier 4: Unhandled / Protocol Anomaly (`attackUnhandled` / `stats.unhandled`)
An unhandled anomaly indicates an unexpected server failure, transport drop, or ambiguous response code:
- **`500 Internal Server Error`**: Gateway panic, unhandled exception, nil-pointer dereference, or internal state corruption under adversarial pressure.
- **`502 Bad Gateway` / `503 Service Unavailable` / `504 Gateway Timeout`**: Upstream gateway disconnects or unhandled timeouts.
- **Ambiguous Status Codes ($< 200$ or unassigned)**: Protocol desynchronization artifacts or truncated status lines.

### 2.2 Formal Status Code Mapping & Justification Matrix

| Status Code | HTTP Status Constant | Architectural Tier | RFC / CWE Specification | Loadgen Metric Counter | Security Evaluation Semantics |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`400`** | `http.StatusBadRequest` | Active Defense | RFC 7230 §3 / CWE-444 | `attackRejected` | Gateway parser rejected malformed syntax / framing |
| **`403`** | `http.StatusForbidden` | Active Defense | RFC 7231 §6.5.3 / CWE-22 | `attackRejected` | Gateway WAF / router actively blocked unauthorized access |
| **`413`** | `http.StatusRequestEntityTooLarge` | Active Defense | RFC 7231 §6.5.11 / CWE-400 | `attackRejected` | Gateway bounded memory limit enforced on body payload |
| **`431`** | `http.StatusRequestHeaderFieldsTooLarge` | Active Defense | RFC 6585 §5 / CWE-400 | `attackRejected` | Gateway bounded header limit enforced on header block |
| **`501`** | `http.StatusNotImplemented` | Active Defense | RFC 7231 §6.6.2 / RFC 7230 | `attackRejected` | Unsupported encoding / method explicitly rejected |

| **`Other`** | Any other status code | Unhandled Anomaly | N/A | `attackUnhandled` | Unexpected status or transport protocol desync |

## 3. Functional Requirements

### FR-1: Elimination of Catch-All Else and Strict Status Code Switch
- In `toron/benchmarks/wrk2/loadgen.go`, the circular `if/else` block inside the adversarial worker execution loop (lines 375–386) shall be completely eliminated.
- It shall be replaced with a strict, exhaustive `switch` statement that dispatches every response status code to its appropriate atomic counter and vector statistic:

```go
// Proposed Architecture for loadgen.go
switch code {
case http.StatusBadRequest,
     http.StatusForbidden,
     http.StatusRequestEntityTooLarge,
     http.StatusRequestHeaderFieldsTooLarge,
     http.StatusNotImplemented:
    attackRejected.Add(1)
    stats.rejected.Add(1)

case http.StatusNotFound:
    attackRouteMiss.Add(1)
    stats.routeMiss.Add(1)

case http.StatusOK:
    attackBypassed.Add(1)
    stats.bypassed.Add(1)

default:
    attackUnhandled.Add(1)
    stats.unhandled.Add(1)
}
```

- No status code may fall through to an ambiguous counter.
- If `executeAttackProbe` encounters an active connection reset or socket closure initiated by the server during header transmission, it shall continue to return `400` as a fail-fast defensive block.

### FR-3: Invariant & Defense Rate Calculation Realignment
The mathematical calculations for defense rates and testbed verdicts shall be strictly realigned to prevent 404 inflation:

1. **Active Defense Rate ($\text{Rate}_{\text{defense}}$)**:
   $$\text{Rate}_{\text{defense}} = \begin{cases} 
   \left(\frac{\text{attackRejected}}{\text{attackTotal}}\right) \times 100.0, & \text{if } \text{attackTotal} > 0 \\ 
   100.0, & \text{if } \text{attackTotal} = 0 
   \end{cases}$$

2. **Route Miss Rate ($\text{Rate}_{\text{routemiss}}$)**:
   $$\text{Rate}_{\text{routemiss}} = \begin{cases} 
   \left(\frac{\text{attackRouteMiss}}{\text{attackTotal}}\right) \times 100.0, & \text{if } \text{attackTotal} > 0 \\ 
   0.0, & \text{if } \text{attackTotal} = 0 
   \end{cases}$$

3. **Per-Vector Active Defense Rate**:
   $$\text{Rate}_{\text{vec\_defense}}(v) = \begin{cases} 
   \left(\frac{\text{rejected}_v}{\text{sent}_v}\right) \times 100.0, & \text{if } \text{sent}_v > 0 \\ 
   100.0, & \text{if } \text{sent}_v = 0 
   \end{cases}$$

4. **Invariant Enforcement Rate**:
   - `InvariantEnforcementRate` shall strictly equal $\text{Rate}_{\text{defense}}$.
   - It shall NOT credit route misses (`attackRouteMiss`) or unhandled codes (`attackUnhandled`).

5. **Overall Testbed Verdict Criteria**:
   The `OverallVerdict` shall evaluate to `"PASS"` if and only if all of the following conditions are simultaneously met:
   - **Zero Starvation Verified**: `benignPercentiles.P99 <= 50.0` AND `benignFailed == 0`.
   - **Zero Attack Bypasses**: `attackBypassed == 0`.
   - **Zero Route Misses**: `attackRouteMiss == 0` (every probe was intercepted by active defense).
   - **Zero Unhandled Anomalies**: `attackUnhandled == 0`.
   - **100% Invariant Enforcement**: `InvariantEnforcementRate == 100.0`.
   If any route miss, bypass, unhandled anomaly, or starvation condition occurs, `OverallVerdict` shall be set to `"FAIL"`.

## 4. Non-Functional Requirements

### NFR-1: Race-Free Concurrent Execution
- All counter operations across concurrent worker goroutines shall utilize 64-bit atomic operations (`sync/atomic.Int64`).
- All reads during report consolidation shall occur after worker termination via `wg.Wait()`.
- The test harness must pass `go test -race -count=1 ./benchmarks/wrk2/...` with zero race warnings.

### NFR-2: Zero External Dependencies
- The implementation shall strictly utilize Go standard library packages:
  - `sync/atomic`
  - `net/http`
  - `encoding/json`
  - `encoding/csv`
  - `fmt`, `os`, `strings`, `time`
- No third-party benchmarking libraries or metrics frameworks shall be introduced.

### NFR-3: Performance & Sub-Nanosecond Hot-Path Overhead Bounds
- The `switch code` classification block operates directly on integer status codes.
- It shall perform zero heap allocations on the critical hot path.
- Overhead per probe classification must remain $< 5$ nanoseconds on modern hardware, ensuring zero measurement distortion at 10,000+ RPS.

### NFR-4: Harness Backward Compatibility & Verification Suite
- The command-line flags (`-url`, `-c`, `-d`, `-rate`, `-attack-ratio`, `-json`, `-csv`, `-md`) shall maintain 100% backward compatibility with `run_saturation_stress.sh`.
- Unit tests in `benchmarks/wrk2/loadgen_test.go` shall verify that simulated responses for all four tiers are mapped with 100% precision.
