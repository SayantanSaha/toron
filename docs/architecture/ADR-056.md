# ADR-056 - HTTP Request Smuggling Prevention & Transfer-Encoding Protocol Guard

## Context & Problem Statement

Toron utilizes a native streaming HTTP/1.1 request parser (`pkg/httpparser/parser.go`) executing over persistent TCP socket connections managed by `pkg/server/server.go`. While the parser currently checks for conflicting `Content-Length` and `Transfer-Encoding` headers, it lacks an internal chunked transfer-encoding decoding state machine.

When a client sends a request declaring only `Transfer-Encoding: chunked`:
1. `req.ContentLength` defaults to `0` and `req.Body` remains `nil`.
2. The chunked payload bytes are left unread in the physical TCP socket buffer.
3. On the next keep-alive loop iteration in `pkg/server/server.go`, the unconsumed chunked payload is deserialized as the start of a subsequent HTTP request.

This enables HTTP Request Smuggling (CWE-444 / CL.TE desync), allowing unauthenticated attackers to poison pooled connections and hijack downstream requests.

## Decision

We decide to implement an immediate **Fail-Fast Protocol Guard** in `pkg/httpparser` and `pkg/server`:

1. **Explicit Error Definition (`pkg/httpparser/parser.go`)**:
   Define `ErrUnsupportedTransferEncoding = errors.New("httpparser: chunked transfer-encoding is not supported")`.
   In `ParseRequest`, if the request contains `Transfer-Encoding` (case-insensitive), immediately abort parsing and return `ErrUnsupportedTransferEncoding`.

2. **Immediate Socket Teardown (`pkg/server/server.go`)**:
   In `handleConn`, if `ParseRequest` returns `ErrUnsupportedTransferEncoding`:
   - Emit `HTTP/1.1 501 Not Implemented\r\nConnection: close\r\nContent-Type: text/plain\r\nContent-Length: 32\r\n\r\n501 Unsupported Transfer-Encoding\n`.
   - Immediately close the underlying TCP connection (`conn.Close()`), discarding any residual bytes in the operating system socket buffer.
   - Increment `metrics.RequestSmugglingRejections` and record a security incident.

## Alternatives Considered

1. **Implement Full RFC 7230 Chunked Decoder in `httpparser`**:
   - *Trade-off*: Requires implementing chunk-size hex parsing, chunk-data buffering, and chunk extension handling. Increases parser surface area, memory allocations, and complexity. For an edge gateway whose primary role is proxying or serving static assets, rejecting inbound chunked cleartext requests is safer and simpler.
2. **Read and Discard the Chunk Body on the Existing Connection**:
   - *Trade-off*: An attacker could send a slow or infinite chunk stream (Slowloris), tying up worker goroutines and socket descriptors. Immediate connection termination is strictly superior for DoS and smuggling prevention.

## Rationale

Immediate connection closure guarantees that no deserialized attacker payload can ever bleed into subsequent pipelined requests on a persistent TCP connection.

## Constraints

- Zero allocations during header inspection.
- Preserves keep-alive performance for standard `Content-Length` and body-less HTTP/1.1 transactions.

## Consequences

### Positive
- Completely neutralizes HTTP Request Smuggling (CL.TE / TE desynchronization).
- Zero memory buffering overhead for malformed or malicious transfer codings.
- Clean connection lifecycle and socket descriptor release.

### Negative / Trade-offs
- Clients requiring chunked request streaming over cleartext HTTP/1.1 will receive HTTP 501 (such clients should upgrade to HTTP/2 or HTTP/3 where framing handles streaming natively).
