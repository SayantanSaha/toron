# REQ-145 - Route-Scoped Payload Ingestion, Activity Deadlines, and Bulkhead Isolation for Legacy Applications

## 1. Description & Problem Statement

### 1.1 Operational Context & The Legacy Ingress Dilemma

Toron is engineered as a cloud-native, high-throughput Layer 4/Layer 7 reverse proxy, web server, and API gateway optimized for low memory overhead and rapid request multiplexing (see [PRD.md](../../PRD.md)). To protect the gateway against Denial-of-Service attacks and memory exhaustion, Toron enforces strict global security defaults:
- Maximum request body ceiling: `4 MB` (`max_body_bytes: 4194304`).
- Static connection timeouts: `read_timeout: 5s`, `write_timeout: 5s`, `idle_timeout: 30s`.
- Reverse proxy upstream response header timeout: `10s` (`ResponseHeaderTimeout`).
- Fixed reactor worker pool: `128` workers (`worker_pool_size: 128`).
- Eager in-memory body allocation: Incoming payloads $> 64\,\text{KB}$ are eagerly buffered into heap memory before route matching or authorization occurs.

While these baseline controls defend against [CWE-400](https://cwe.mitre.org/data/definitions/400.html) (Slowloris, Slow Read) and [CWE-770](https://cwe.mitre.org/data/definitions/770.html) (Out-Of-Memory exhaustion, [`SEC-28`](../architecture/ADR-084.md)), they break compatibility with enterprise legacy workloads detailed in [AN-006](../analysis/AN-006.md):
1. **Large File Uploads**: Multipart/form-data, database dumps, CAD/CAM binaries, and media files exceeding `200 MB` are rejected at the HTTP parser layer with `HTTP 413 Payload Too Large` before routing rules can be evaluated.
2. **High Latency Backend Execution**: Legacy monolithic applications, report generators, complex SQL aggregations, and batch ETL endpoints require `15s` to `60s+` to produce response headers, exceeding Toron's static write deadline (`5s`) and upstream transport timeout (`10s`).
3. **Sustained Upload Durations over Constrained Links**: Legitimate `200 MB` uploads over standard broadband, mobile, or branch WAN links take `15s` to `60s+`. Toron's static `5s` read deadline aborts these transfers mid-stream with `i/o timeout`.
4. **Reactor Worker Pool Saturation**: Multiple concurrent slow requests bind worker goroutines for extended durations, filling the task queue and blocking listener `Accept()`, starving health checks (`/health`) and fast microservice routes.

Relaxing global server parameters (e.g. setting global `max_body_bytes: 500MB` and `read_timeout: 300s`) introduces fatal vulnerabilities: opening the system to instant OOM crashes via concurrent unbuffered allocations and complete worker pool exhaustion by Slowloris attackers.

This requirement defines the formal contract for **Option 1 (Route-Aware Streaming Ingress with Activity Deadlines & Bulkheads)** formulated in [AN-006](../analysis/AN-006.md), establishing route-scoped flexibility for legacy endpoints while keeping global hardened security defaults intact.

## 2. Functional Requirements

### 2.1 FR-145-1: Two-Phase Request Parsing Pipeline

1. The HTTP request ingestion pipeline shall decouple request parsing into two distinct, sequential phases:
   - **Phase 1 (Header Parsing)**: Parse the HTTP request line and headers into a structured request metadata object using pooled line buffers. Phase 1 shall complete with zero heap allocation for the request body. If request headers exceed the configured maximum header limit (default: 8KB), the request shall be rejected with `HTTP 431 Request Header Fields Too Large`.
   - **Interim Route Matching**: Following Phase 1 completion, the server shall match the request method, host, and URL path against registered routes to resolve the target route configuration before reading any payload body bytes from the network socket.
   - **Phase 2 (Governed Body Ingestion)**: Ingest the request body stream according to the resolved route's specific limits, timeout thresholds, and streaming mode.
2. In the event of route matching failure (e.g. 404 Not Found), the server shall reject or handle the request without reading or buffering an unconsumed request body.

---

### 2.2 FR-145-2: Route-Scoped Body Size Ceilings

1. The configuration schema shall support route-level payload size limits (`max_body_bytes`) declared within route definitions.
2. **Hierarchical Precedence**:
   - If a route specifies `max_body_bytes`, that value shall govern request body ingestion for requests matching that route.
   - If a route does not specify `max_body_bytes`, the effective limit shall fall back to the global server ceiling (`server.max_body_bytes`, default: `4 MB` / `4,194,304` bytes).
3. **Fast-Fail Content-Length Validation**:
   - If an incoming request includes a `Content-Length` header exceeding the effective body size ceiling of the matched route, the system shall immediately reject the request with `HTTP 413 Payload Too Large` during Phase 1 routing evaluation.
   - Rejection shall occur before any request body bytes are read from the socket or allocated in memory.
4. **Cumulative Streaming Clamping**:
   - For chunked or streaming uploads where `Content-Length` is omitted, the body reader shall track the cumulative count of uncompressed body bytes ingested.
   - If cumulative bytes exceed the effective body size ceiling, the reader shall immediately abort ingestion, return `HTTP 413 Payload Too Large`, and sever the TCP connection to prevent client flood.

---

### 2.3 FR-145-3: Activity-Refreshed Read Deadlines

1. Socket read deadlines during request body ingestion shall be progress-based rather than absolute static timestamps.
2. **Activity Refresh Mechanics**:
   - The socket read deadline shall be initialized to the effective read timeout prior to reading the body.
   - Upon each read operation where bytes are successfully received from the socket, the read deadline shall be refreshed forward by the configured read timeout duration.
   - This progress-based mechanism shall permit sustained high-volume data transfers (e.g. 200MB+ transfers over constrained links lasting 30s–120s) to complete without premature socket timeout, provided data flows continuously.
3. **Stall & Slowloris Termination (CWE-400 Defense)**:
   - If a client ceases transmitting data, pauses mid-transfer, or advertises an idle window such that no data is read for longer than the effective read timeout, the socket deadline shall expire.
   - The connection shall be immediately closed, unblocking worker goroutines and freeing all associated resources.
4. **Progress Rate Clamping**:
   - The system shall enforce a minimum progress threshold per deadline window to prevent low-rate drip-feeding attacks (e.g. sending 1 byte every 4.9 seconds). If cumulative progress across a renewal window falls below the minimum progress threshold, the connection shall be terminated.
5. **Route-Level Configuration**:
   - Routes shall support an optional route-scoped `read_timeout` attribute, falling back to the global `server.read_timeout` if omitted.
   - Deadline updates shall utilize amortization to prevent excessive operating system syscall overhead.

---

### 2.4 FR-145-4: Decoupled Backend Response Timeouts

1. The reverse proxy transport shall support route-level upstream response header timeouts (`response_header_timeout`), overriding the global transport fallback (default: 10s).
2. **Client Downstream Write Deadline Decoupling**:
   - While Toron waits for an upstream backend to produce response headers, the downstream client connection write deadline shall be decoupled from static downstream write timeouts (`write_timeout: 5s`).
   - The gateway shall not terminate the downstream client socket while the upstream backend is legitimately executing within the route's configured `response_header_timeout`.
3. **Upstream Timeout Handling**:
   - If the upstream backend does not return response headers within the route's configured `response_header_timeout`, the gateway shall abort the upstream request context.
   - The gateway shall return `HTTP 504 Gateway Timeout` to the client.
   - If the upstream backend prematurely terminates or resets the TCP connection during execution, the gateway shall return `HTTP 502 Bad Gateway`.

---

### 2.5 FR-145-5: Route Bulkhead Concurrency Gates

1. The gateway shall support route-scoped bulkhead concurrency limits (`max_concurrency`) to isolate slow or resource-intensive legacy endpoints from the rest of the system.
2. **Active Request Tracking**:
   - Each route with `max_concurrency` configured shall maintain an atomic counter of currently active in-flight requests.
3. **Over-Capacity Fast-Fail**:
   - When a new request matches a route whose active request count is greater than or equal to `max_concurrency`:
     - The gateway shall immediately reject the request with `HTTP 503 Service Unavailable` (or `HTTP 429 Too Many Requests`).
     - The response shall include a `Retry-After: 5` header.
     - The response body shall convey a structured error message indicating route capacity exhaustion.
     - Rejection shall occur immediately after Phase 1 routing, before reading the request body or dialing the upstream backend.
4. **Deterministic Semaphore Release**:
   - The active request counter shall be decremented immediately upon request completion, error response, or client connection termination.
5. **Worker Pool Reservation Guarantee**:
   - Rejection at the bulkhead gate shall prevent reactor worker goroutines from being blocked on slow legacy transfers, guaranteeing that reactor capacity remains available for microservice APIs, static assets, and operational probes (`/health`, `/metrics`).

---

### 2.6 FR-145-6: Zero-Copy Streaming Proxy Ingress

1. The reverse proxy forwarding engine shall support zero-copy streaming proxy ingress for large payload bodies.
2. **Direct Socket-to-Upstream Streaming**:
   - When streaming ingress is active (configured via route `stream_request_body: true` or automatically activated for payloads exceeding 64KB on routes with elevated body ceilings):
     - The proxy shall assign the bounded client body reader directly to the upstream HTTP request body (`outReq.Body = req.Body`).
     - The proxy shall forward `outReq.ContentLength` without buffering the payload into intermediary gateway heap memory slices.
     - Upstream transmission shall stream data directly from the client socket to the upstream transport connection.
3. **Bidirectional Context & Abort Propagation**:
   - If the downstream client disconnects or aborts the transfer midway, the gateway shall immediately cancel the upstream request context (`req.Context()`), causing the upstream connection to close and preventing orphaned backend processing.
   - If the upstream backend aborts or encounters a network error midway through streaming, the gateway shall forcefully terminate the downstream connection (fail-closed) to ensure the client is alerted of payload truncation.

## 3. Non-Functional Requirements

### 3.1 NFR-145-1: Constant $O(1)$ Memory Footprint

- The memory footprint for processing incoming request payloads of arbitrary size (from 1MB up to 2GB+) shall remain bounded at a constant small buffer size ($O(1) \le 64\,\text{KB}$ per active connection).
- The gateway shall strictly prohibit monolithic heap slice allocations (`make([]byte, clInt)`) for streaming payloads, completely neutralizing OOM crash vectors ([CWE-770](https://cwe.mitre.org/data/definitions/770.html), `SEC-28`).

### 3.2 NFR-145-2: Zero Worker Starvation

- Saturation of legacy slow endpoints (large uploads, slow backend queries) shall never starve fast microservice routes or operational endpoints.
- Even when all bulkhead concurrency slots on legacy routes are fully saturated, operational endpoints (`/health`, `/metrics`) and unconstrained routes shall maintain baseline response latencies ($< 5\,\text{ms}$).

### 3.3 NFR-145-3: Backward Compatibility

- All existing route configurations, default behaviors, and security postures shall remain completely backward compatible.
- Routes that do not declare legacy attributes shall continue to enforce the global `4 MB` body ceiling and default static timeouts. Zero breaking changes shall be introduced to existing valid configuration files.

### 3.4 NFR-145-4: Strict Slowloris Immunity

- The gateway shall maintain 100% immunity to Slowloris attacks ([CWE-400](https://cwe.mitre.org/data/definitions/400.html)).
- Any connection that ceases transmitting data or drops below the minimum progress threshold shall be forcibly closed within the configured read timeout window, without leaking goroutines or socket descriptors.

## 4. Acceptance Criteria

### AC-145-01: Two-Phase Parsing & Route-Scoped Body Size Enforcement (200MB Upload Allowed on Configured Route)

- **Given** a route `/legacy/upload` configured with `max_body_bytes: 268435456` (256MB) while the global server configuration maintains `max_body_bytes: 4194304` (4MB),
- **When** a client transmits a valid HTTP POST request to `/legacy/upload` carrying `Content-Length: 209715200` (200MB) and streams the 200MB payload,
- **Then** the server must resolve the route in Phase 1 before reading the body, permit the 200MB upload in Phase 2, stream the payload to the upstream backend, and return the upstream `HTTP 200 OK` response without raising `HTTP 413 Payload Too Large`; furthermore, requests to unconfigured routes exceeding 4MB must continue to be rejected with `HTTP 413`.

### AC-145-02: Fast-Fail Pre-Read Rejection of Oversized Content-Length

- **Given** a route `/legacy/upload` configured with `max_body_bytes: 268435456` (256MB),
- **When** a client transmits an HTTP request to `/legacy/upload` carrying header `Content-Length: 314572800` (300MB),
- **Then** the server must reject the request immediately with `HTTP 413 Payload Too Large` during Phase 1 routing evaluation before reading any body bytes from the network socket, and must close or drain the connection without allocating heap memory for the 300MB payload.

### AC-145-03: Activity-Refreshed Read Deadlines for Sustained Slow-Link Ingestion

- **Given** a route `/legacy/upload` configured with `read_timeout: 5s` and `max_body_bytes: 256MB`,
- **When** a client uploads a 200MB payload continuously over a constrained network connection taking 30 seconds to complete (transferring data steadily such that no interval between reads reaches 5 seconds),
- **Then** the socket read deadline must be refreshed upon read activity, allowing the entire 30-second upload to complete successfully without triggering an `i/o timeout` or connection drop.

### AC-145-04: Strict Termination of Stalled Slowloris Ingestion

- **Given** a route `/legacy/upload` configured with `read_timeout: 5s` and `max_body_bytes: 256MB`,
- **When** a client initiates an upload, sends initial payload bytes, and then pauses transmission for 6 seconds (exceeding the 5-second `read_timeout`),
- **Then** the server must trigger the socket read deadline, forcibly close the connection within 5 seconds of inactivity, terminate the worker routine, and reclaim all connection resources.

### AC-145-05: Decoupled Upstream Processing and Response Header Timeout

- **Given** a route `/legacy/report` configured with `response_header_timeout: 30s` and the server configured with default `write_timeout: 5s`,
- **When** a client submits a request to `/legacy/report` and the upstream backend takes 20 seconds to process the request before emitting response headers,
- **Then** the gateway must maintain the downstream client connection open without socket write timeout expiration during the 20-second upstream processing window, receive the response headers, and relay the response to the client; and **When** an upstream backend fails to respond within 30 seconds, the gateway must abort the upstream call and return `HTTP 504 Gateway Timeout`.

### AC-145-06: Route Bulkhead Concurrency Bounding and Reactor Worker Protection

- **Given** a route `/legacy/slow` configured with `max_concurrency: 16` on a gateway running with a fixed worker pool of 128 workers,
- **When** 16 concurrent slow requests are actively in-flight on `/legacy/slow` and a 17th request arrives matching `/legacy/slow`,
- **Then** the gateway must immediately reject the 17th request with `HTTP 503 Service Unavailable` (or `HTTP 429 Too Many Requests`) containing a `Retry-After: 5` header without reading the request body or dialing upstream; and concurrent requests to `/health` and other routes must continue to respond with baseline latency ($< 5\,\text{ms}$) without worker starvation.

## 6. Approved Architecture & Scope Decisions

1. **Default Bulkhead Capacity when Unspecified**:
   - **Decision (Approved)**: Default `max_concurrency` to safety guardrail $\min(32, \text{WorkerPoolSize} / 4)$ (e.g. 32 on a 128-worker gateway) whenever an elevated `max_body_bytes` ($> 4\,\text{MB}$) or elevated `response_header_timeout` ($> 10\,\text{s}$) is configured on a route but `max_concurrency` is omitted. This ensures legacy routes cannot inadvertently exhaust the fixed reactor worker pool.

2. **Automatic Zero-Copy Streaming Ingress**:
   - **Decision (Approved)**: Automatically activate zero-copy streaming proxy ingress for all request bodies exceeding $64\,\text{KB}$ on proxy routes directly to upstream backends, maintaining constant $O(1)$ memory without requiring manual per-route flags unless explicit in-memory transformation or buffering is configured.

3. **Status Code on Bulkhead Exhaustion**:
   - **Decision (Approved)**: Return `HTTP 503 Service Unavailable` with `Retry-After: 5` header when a route bulkhead concurrency limit is reached, cleanly communicating temporary gateway capacity exhaustion to clients.
