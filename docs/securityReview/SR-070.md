# SR-070 - Complete Codebase Security Audit (Post-Remediation Assessment)

## Description

A complete, systematic security audit of the Toron Web Server and Edge Gateway codebase following the successful remediation of tasks `TASK-061` through `TASK-072`. This audit examines protocol parsing, server reactor concurrency, authentication, authorization, WAF engines, reverse proxy forwarding, container discovery, gRPC transcoding, and dashboard assets.

## Findings

### Finding 1 (SEC-14): HTTP Request Smuggling via Header Name Trailing Whitespace (RFC 7230 §3.2.4)
- **Severity**: **Critical** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N - Score 9.1)
- **Location**: `pkg/httpparser/parser.go:88-104`
- **CWE**: CWE-444
- **Description**:  
  In `httpparser.ParseRequest`, header lines are split on the first colon without rejecting trailing whitespace preceding the colon (`k := lineTrimmed[:colonIdx]`). If a client sends `Transfer-Encoding : chunked` (with a space before the colon), `k` evaluates to `"Transfer-Encoding "`. Because Go standard library `http.Header` does not strip trailing whitespace, `req.Header.Get("Transfer-Encoding")` returns `""`, completely bypassing the Transfer-Encoding protocol guard introduced in `TASK-061`. Downstream HTTP servers or proxies that strip whitespace will interpret the chunked encoding, causing HTTP request smuggling. RFC 7230 §3.2.4 strictly mandates: *"No whitespace is allowed between the header field-name and colon... A server MUST reject any received request message that contains whitespace between a header field-name and colon with a 400 (Bad Request) status code."*
- **Impact**: HTTP request smuggling, cache poisoning, and security filter bypass.
- **Recommendation**: Reject any header with `HTTP 400 Bad Request` if `strings.ContainsAny(k, " \t\r\n")`.

### Finding 2 (SEC-15): HTTP Request Smuggling (CL.CL Desync) via Multiple / Duplicate `Content-Length` Headers
- **Severity**: **Critical** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N - Score 9.1)
- **Location**: `pkg/httpparser/parser.go:107-123`
- **CWE**: CWE-444
- **Description**:  
  `httpparser.ParseRequest` reads `req.Header.Get("Content-Length")`. When multiple `Content-Length` headers are provided (e.g. `Content-Length: 0\r\nContent-Length: 45\r\n`), `Get` returns only the first value. Toron reads 0 bytes and treats the body as complete. On persistent keep-alive connections in `pkg/server/server.go:182-250`, the unconsumed 45 bytes are left on the socket and parsed as the next HTTP request line. RFC 7230 §3.3.2 requires rejecting any message with multiple distinct `Content-Length` values with `HTTP 400 Bad Request`.
- **Impact**: Request desync, cross-user session hijacking, credential harvesting.
- **Recommendation**: Verify that `len(req.Header.Values("Content-Length")) <= 1` or all entries match identical integer values.

### Finding 3 (SEC-16): Denial of Service (OOM) via Unbounded Request Body Ingestion in `http2AdapterHandler`
- **Severity**: **High** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H - Score 7.5)
- **Location**: `pkg/server/server.go:308-313`
- **CWE**: CWE-400, CWE-770
- **Description**:  
  In `http2AdapterHandler()`, the server adapts HTTP/2 requests using `io.ReadAll(r.Body)` without enforcing `s.config.MaxBodyBytes`. Unlike HTTP/1.1 (which enforces `MaxBodyBytes`), an attacker sending an oversized or streaming body over HTTP/2 will force unbounded memory allocation, triggering a kernel Out-Of-Memory (OOM) process kill.
- **Impact**: Process crash, Denial of Service affecting the entire server.
- **Recommendation**: Wrap `r.Body` with `io.LimitReader` or `http.MaxBytesReader` bounded to `s.config.MaxBodyBytes`.

### Finding 4 (SEC-17): Connection Starvation & Denial of Service via Reactor Worker Pool Monopolization
- **Severity**: **High** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H - Score 7.5)
- **Location**: `pkg/reactor/reactor.go:128-176`, `pkg/server/server.go:182-301`
- **CWE**: CWE-400
- **Description**:  
  The reactor dispatches accepted connections to a fixed pool of workers (`WorkerPoolSize`, default 128). Each worker synchronously runs `srv.handleConn`, which loops over keep-alive requests for up to `IdleTimeout` (default 30s). If 128 clients establish persistent connections and remain idle, all 128 workers are blocked. After 512 pending connections fill `r.tasks`, `r.Serve()` blocks, and `ln.Accept()` ceases accepting new connections.
- **Impact**: Complete ingress outage caused by minimal connection traffic.
- **Recommendation**: Handle idle keep-alive states asynchronously or allocate goroutines per connection.

### Finding 5 (SEC-18): Global Authentication & WAF Bypass via Root / Empty Path Exclusions
- **Severity**: **High** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N - Score 8.6)
- **Location**: `pkg/router/auth.go:314-320`, `pkg/waf/middleware.go:29-35`
- **CWE**: CWE-287, CWE-693
- **Description**:  
  Path exclusion checks in `auth.go` and `middleware.go` use `strings.HasPrefix(req.Path, strings.TrimSuffix(p, "/")+"/")`. If an exclusion contains `""` or `"/"`, `strings.TrimSuffix(p, "/")+"/"` evaluates to `"/"`. Because every valid HTTP path begins with `"/"`, all incoming requests match the exclusion, completely bypassing authentication and WAF security checks globally.
- **Impact**: Total bypass of authentication and threat inspection.
- **Recommendation**: Discard empty exclusion strings; require exact equality when `p == "/"`.

### Finding 6 (SEC-19): Ingress Route Hijacking via Unrestricted Container Discovery Labels
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:L/I:L/A:L - Score 6.0)
- **Location**: `pkg/discovery/parser.go:33-40`, `pkg/discovery/manager.go:206-233`
- **CWE**: CWE-284
- **Description**:  
  Any container with `toron.enable=true` on the local Docker engine can declare `toron.prefix: "/"` or shadow sensitive routes (`/api`, `/admin`). `m.router.RoutePrefix` will register this route and hijack inbound traffic.
- **Impact**: Ingress traffic hijacking, sensitive route shadowing.
- **Recommendation**: Validate container labels against allowed namespaces and prohibit root (`/`) or administrative path registration.

### Finding 7 (SEC-20): WAF Path Traversal Bypass via Uppercase Percent-Encoding in `TRAVERSAL-001`
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N - Score 5.3)
- **Location**: `pkg/waf/rules.go:61-67`
- **CWE**: CWE-693, CWE-22
- **Description**:  
  Rule `TRAVERSAL-001` lacks the case-insensitive `(?i)` flag (`(\.\./|\.\.\\|%2e%2e/|%2e%2e%2f)`). When inspecting raw headers and request bodies, payloads with uppercase percent-encoding (`%2E%2E/`) evade detection.
- **Impact**: Bypass of WAF traversal detection.
- **Recommendation**: Add `(?i)` flag and include backslash encodings.

### Finding 8 (SEC-21): Request Body Dropping in Sidecar Proxy Engine
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L - Score 5.3)
- **Location**: `pkg/sidecar/proxy.go:199-202`, `pkg/httpparser/request.go:141`
- **CWE**: CWE-436
- **Description**:  
  `httpparser.NewRequestFromStd(r)` initializes `Body: bytes.NewReader(nil)`. In `pkg/sidecar/proxy.go`, `toronReq` is created via `NewRequestFromStd(r)` without populating the request body from `r.Body`. Consequently, all POST, PUT, and PATCH payloads passing through the sidecar are lost.
- **Impact**: Upstream data loss and API malfunction.
- **Recommendation**: Transfer `r.Body` into `toronReq.Body` in `sidecar/proxy.go`.

### Finding 9 (SEC-13): Stored DOM-based XSS in Security Control Center Dashboard
- **Severity**: **Critical** (CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:N - Score 9.3)
- **Location**: `public/app.js:421-431`
- **CWE**: CWE-79
- **Description**:  
  `fetchIncidentLogs()` renders unescaped incident fields (`inc.path`, `inc.client_ip`) into `tbody.innerHTML`. An attacker sending an XSS payload in a URI that triggers a WAF violation causes JavaScript execution in the administrator's browser upon viewing the dashboard.
- **Impact**: Full administrative browser compromise, session hijacking.
- **Recommendation**: Use DOM `textContent` or strict HTML escaping before rendering.

### Finding 10 (SEC-22): Missing Expiration (`exp`) Claim Enforcement in JWT Verification
- **Severity**: **Low** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N - Score 4.3)
- **Location**: `pkg/router/auth.go:171-185`
- **CWE**: CWE-613
- **Description**:  
  `VerifyJWT` only verifies `exp` if present in claims. Tokens issued without an `exp` claim remain valid indefinitely.
- **Impact**: Persistent replay risk for non-expiring credentials.
- **Recommendation**: Require `exp` claim by default or add an explicit configuration option.

## Positive Observations

1. **Remediation Integrity**: All 12 previously remediated vulnerabilities (`SEC-01` through `SEC-12`) remain robustly guarded with zero regression.
2. **Standard Library Purity**: Zero external runtime dependencies; all cryptography and parsing rely solely on Go's standard library.
3. **Concurrency Safety**: Verified clean with `go test -race ./...` across all packages.
4. **Header Sanitization**: Access logging CRLF sanitization and hop-by-hop stripping operate efficiently with zero unnecessary allocations.

## Conclusion & Next Steps

This post-remediation security audit identified 10 distinct security findings: 3 Critical (`SEC-13`, `SEC-14`, `SEC-15`), 3 High (`SEC-16`, `SEC-17`, `SEC-18`), 3 Medium (`SEC-19`, `SEC-20`, `SEC-21`), and 1 Low (`SEC-22`). 

Remediation should prioritize protocol desync guards (`SEC-14`, `SEC-15`), HTTP/2 memory bounds (`SEC-16`), worker starvation (`SEC-17`), and exclusion bypass (`SEC-18`).
