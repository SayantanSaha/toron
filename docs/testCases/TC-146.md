# TC-146 - Test Cases for Alerts and Threat Defense Control Center Redesign

## 1. Description & Overview

### 1.1 Executive Summary & Problem Context
The Toron Control Center dashboard at `#/alerts` serves as the primary operations cockpit for real-time edge security monitoring and threat mitigation. Under active production workloads, Toron's Web Application Firewall (WAF) inspects incoming requests using OWASP ModSecurity Core Rules and custom regex patterns, while an automated two-stage threat defense reactor quarantines abusive actors (Stage 1: temporary 1-hour quarantine; Stage 2: permanent IP firewall ban).

As traffic volume and security events increased, operations reported severe UI friction:
> *"The alerts list and blocked ips list are getting very long. We need to redesign this page."*

Architectural and functional analysis in [`AN-007`](../analysis/AN-007.md), requirements analysis in [`REQ-146`](../requirements/REQ-146.md), and architectural decisions in [`ADR-146`](../architecture/ADR-146.md) identified six structural defects in the legacy implementation:
1. **Data Model Duplication & Cardinality Distortion**: In [`public/js/model.js`](../../public/js/model.js), banned IP records from `rawApiBannedIps` were injected into both `D.alerts` and `D.bannedIps`. Every banned IP rendered twice on screen and falsely inflated the global navigation alert badge and Overview health status banner.
2. **Missing Pagination & Data Filtering**: Unpaginated rendering of incident feeds and ban tables led to unbounded DOM growth, excessive vertical scrolling, and an inability to search by IP or filter by severity/tier.
3. **Responsive Header Layout Collisions**: The manual ban input form was crammed into the card header flex row (`.card-h`), wrapping and breaking alignment on screens narrower than 1200px.
4. **Thread-Blocking Synchronous Dialogs**: Unban operations triggered browser-native `window.confirm()` and `window.alert()`, freezing the browser execution loop, stopping background telemetry polling, and breaking automated headless testing.
5. **Inaccessible Forensic Telemetry**: Backend WAF security audit events contained rich forensic metadata (`rule_id`, `anomaly_score`, `category`, `location`, `payload_snippet` via `pkg/waf/audit.go`), but the drawer controller ([`public/js/components/drawer.js`](../../public/js/components/drawer.js)) only supported route metrics and HTTP request logs.
6. **Absence of High-Level Operational Metrics**: Operators lacked an executive Key Performance Indicator (KPI) metrics strip summarizing active threats, WAF block counts, and ban tier distributions.

### 1.2 Purpose of Test Specification
This test specification establishes the formal verification suite for [`REQ-146`](../requirements/REQ-146.md) and [`TASK-174`](../tasks/TASK-174.md), validating that:
- Data model normalization isolates operational alerts, security incidents, and firewall bans into separate properties, eliminating badge count distortion.
- Client-side pagination, real-time multi-attribute search, and faceted filtering execute with sub-millisecond responsiveness without backend round-trips.
- Multi-level interactive column sorting deterministically resolves ties on IP address using numeric collation per [`REQ-138`](../requirements/REQ-138.md) and [`ADR-138`](../architecture/ADR-138.md).
- Ergonomic manual ban controls enforce client-side IPv4/IPv6 syntax validation before network dispatch.
- Unban workflows use non-blocking in-app confirmation modals and toast notifications, preserving background telemetry polling.
- Slide-out drawer renders deep WAF forensic telemetry (`rule_id`, `anomaly_score`, `location`, payload snippet) with 1-click ban and log filtering actions.
- Executive KPI metrics strip displays accurate counts for active incidents, WAF blocks, and ban tiers.
- Frontend JavaScript footprint remains strictly within the $\le 120\text{ KB}$ budget with zero external runtime or build dependencies.
- All documentation and code links strictly adhere to relative path rules.

### TC-146-01: Data Model Normalization and Deduplication

- **Identifier**: `TC-146-01`
- **Target Component**: [`public/js/model.js`](../../public/js/model.js) (`buildDataModel`), [`public/js/app.js`](../../public/js/app.js) (`#nav button[data-nav="alerts"] .badge`), [`public/js/views/overview.js`](../../public/js/views/overview.js)
- **Verifies**:
  - [`REQ-146 §4 AC-146-01`](../requirements/REQ-146.md)
  - [`REQ-146 §2.1 FR-146-1`](../requirements/REQ-146.md) (Data Model Normalization & Deduplication)
  - [`TASK-174 §3 WP-1`](../tasks/TASK-174.md)
  - [`ADR-146 §1 Decision 1`](../architecture/ADR-146.md)
- **Preconditions**:
  1. Backend API mock or telemetry fixtures initialized with:
     - 1 failing upstream pool instance (`status: 'UNREACHABLE'`, `http_code: 502`).
     - 10 active temporary IP bans (`type: 'temporary'`).
     - 5 active permanent IP bans (`type: 'permanent'`).
     - 5 active WAF security incidents.
  2. Browser DOM scope provides navigation container `#nav` with button `[data-nav="alerts"]` containing `.badge`.
- **Test Data & Inputs**:
  ```javascript
  const fixtureUpstreams = [
    { name: "10.0.1.10:8080", route: "/api", status: "UNREACHABLE", http_code: 502, history: Array(48).fill(false) }
  ];
  const fixtureBannedIps = [
    ...Array.from({ length: 10 }, (_, i) => ({
      ip: `192.0.2.${i + 1}`,
      type: "temporary",
      created_at: "2026-09-28 08:00:00",
      remaining_seconds: 1800,
      reason: "Rate limit exceeded"
    })),
    ...Array.from({ length: 5 }, (_, i) => ({
      ip: `198.51.100.${i + 1}`,
      type: "permanent",
      created_at: "2026-09-28 07:00:00",
      remaining_seconds: 0,
      reason: "Repeated SQLi attacks"
    }))
  ];
  const fixtureIncidents = Array.from({ length: 5 }, (_, i) => ({
    id: `inc-${i + 1}`,
    client_ip: `192.0.2.${i + 1}`,
    rule_id: "942100",
    category: "SQL Injection",
    action: "blocked",
    anomaly_score: 15,
    timestamp: "2026-09-28T08:15:00Z"
  }));
  ```
- **Execution Steps**:
  1. Inject fixtures into backend response cache: `rawApiUpstreams = fixtureUpstreams`, `rawApiBannedIps = fixtureBannedIps`, `rawApiIncidents = fixtureIncidents`.
  2. Invoke `buildDataModel()`.
  3. Inspect `D.alerts`:
     a. Assert `D.alerts.length === 1`.
     b. Assert the single record corresponds to the failing upstream (`upstream_10.0.1.10:8080`).
     c. Assert zero banned IP entries (`ban_*`) are present within `D.alerts`.
  4. Inspect `D.bannedIps`:
     a. Assert `D.bannedIps.length === 15`.
     b. Verify all 10 temporary bans and 5 permanent bans are contained.
  5. Inspect `D.incidents`:
     a. Assert `D.incidents.length === 5`.
  6. Evaluate navigation badge counter:
     a. Query badge text from `#nav button[data-nav="alerts"] .badge`.
     b. Assert badge displays `1` (reflecting only true operational alerts) instead of `16` (`1 + 15`).
  7. Evaluate Overview dashboard health banner:
     a. Assert status banner reflects 1 upstream degradation and does NOT register 15 false system emergencies.
- **Expected Results**:
  - `D.alerts` strictly isolates operational failures; no banned IPs exist in `D.alerts`.
  - `D.bannedIps` contains all 15 active quarantine records.
  - `D.incidents` contains all 5 security incidents.
  - The navigation badge displays `1` instead of `16`.
- **Pass / Fail Criteria**:
  - **Pass**: `D.alerts` has length 1, contains 0 bans; `D.bannedIps` has length 15; badge text equals `'1'`.
  - **Fail**: Banned IPs appear in `D.alerts`, `D.alerts.length > 1`, or navigation badge displays `'16'`.

### TC-146-02: Client-Side Pagination for Incidents and Banned IPs

- **Identifier**: `TC-146-02`
- **Target Component**: [`public/js/views/alerts.js`](../../public/js/views/alerts.js), [`public/js/state.js`](../../public/js/state.js)
- **Verifies**:
  - [`REQ-146 §4 AC-146-02`](../requirements/REQ-146.md)
  - [`REQ-146 §2.2 FR-146-2 §1`](../requirements/REQ-146.md) (Client-Side Pagination)
  - [`TASK-174 §3 WP-3 §3`](../tasks/TASK-174.md)
  - [`ADR-146 §1 Decision 3.3`](../architecture/ADR-146.md)
- **Preconditions**:
  1. Data model initialized with 45 banned IP records (`198.51.100.1` through `198.51.100.45`).
  2. Data model initialized with 25 security incidents.
  3. `state.alBanPageSize = 10`, `state.alBanPage = 1`.
  4. View mounted with DOM elements: `#alBanBody`, `#alBanPageInd`, `#alBanSummary`, `#alBanFirst`, `#alBanPrev`, `#alBanNext`, `#alBanLast`, `#alBanPageSize`.
- **Test Data & Inputs**:
  - 45 mock ban objects with sequential IP addresses.
  - Page size dropdown options: `10`, `25`, `50`.
- **Execution Steps**:
  1. Invoke `alUpdate(D)` to render page 1 of Banned IPs table.
  2. **Verify Page 1 State**:
     a. Assert `#alBanBody tr` row count is exactly 10.
     b. Assert first rendered row displays `198.51.100.1` and 10th row displays `198.51.100.10`.
     c. Assert `#alBanPageInd.textContent` equals `'Page 1 / 5'`.
     d. Assert `#alBanSummary.textContent` contains `'Showing 1–10 of 45'`.
     e. Assert `#alBanFirst.disabled === true` and `#alBanPrev.disabled === true`.
     f. Assert `#alBanNext.disabled === false` and `#alBanLast.disabled === false`.
  3. **Transition to Page 2**:
     a. Click `#alBanNext` (or set `state.alBanPage = 2` and call `alUpdate(D)`).
     b. Assert `#alBanBody tr` row count is exactly 10.
     c. Assert rows display records 11 through 20 (`198.51.100.11` to `198.51.100.20`).
     d. Assert `#alBanPageInd.textContent` equals `'Page 2 / 5'`.
     e. Assert `#alBanSummary.textContent` contains `'Showing 11–20 of 45'`.
     f. Assert all 4 buttons (`First`, `Prev`, `Next`, `Last`) are enabled (`disabled === false`).
  4. **Transition to Last Page (Page 5)**:
     a. Click `#alBanLast` (or set `state.alBanPage = 5` and call `alUpdate(D)`).
     b. Assert `#alBanBody tr` row count is exactly 5 (rows 41 through 45).
     c. Assert `#alBanPageInd.textContent` equals `'Page 5 / 5'`.
     d. Assert `#alBanSummary.textContent` contains `'Showing 41–45 of 45'`.
     e. Assert `#alBanNext.disabled === true` and `#alBanLast.disabled === true`.
     f. Assert `#alBanFirst.disabled === false` and `#alBanPrev.disabled === false`.
  5. **Page Size Dropdown Modification**:
     a. Change page size dropdown `#alBanPageSize` value to `25` (`state.alBanPageSize = 25`).
     b. Assert `state.alBanPage` resets to `1`.
     c. Trigger `alUpdate(D)`.
     d. Assert total pages becomes $\lceil 45 / 25 \rceil = 2$.
     e. Assert `#alBanPageInd.textContent` equals `'Page 1 / 2'`.
     f. Assert `#alBanSummary.textContent` contains `'Showing 1–25 of 45'`.
  6. **Incidents Feed Pagination Parity**:
     a. Repeat pagination validation on `#alIncList` with 25 incidents and `state.alIncPageSize = 10`.
     b. Verify 3 total pages, correct item slicing (10, 10, 5), and boundary button behavior.
- **Expected Results**:
  - Non-blocking client-side array slicing partitions records with $O(1)$ memory overhead.
  - Page indicator displays `Page X / Y` and summary indicates `Showing start–end of total`.
  - Boundary buttons (`First`, `Prev`, `Next`, `Last`) disable correctly at extremes.
  - Changing page size resets active page to 1 and recalculates total page count.
- **Pass / Fail Criteria**:
  - **Pass**: All pages display exact item ranges; indicators and boundary buttons match expected values; zero server requests triggered.
  - **Fail**: Incorrect row count per page; pagination indicator shows wrong page count; or extreme buttons remain active.

### TC-146-03: Real-Time Multi-Attribute Search and Faceted Filtering

- **Identifier**: `TC-146-03`
- **Target Component**: [`public/js/views/alerts.js`](../../public/js/views/alerts.js), [`public/js/state.js`](../../public/js/state.js)
- **Verifies**:
  - [`REQ-146 §4 AC-146-03`](../requirements/REQ-146.md)

     - Categories: `SQL Injection` (12), `Cross-Site Scripting` (10), `Path Traversal` (8).
     - Rule IDs: `942100` (SQLi), `941100` (XSS), `930100` (Traversal).

     - Payload Snippets: `' OR 1=1--`, `<script>alert(1)</script>`, `../../etc/passwd`.
     - Actions: 18 `blocked`, 12 `logged`.
  2. Banned IPs table populated with 20 records (12 temporary, 8 permanent).
- **Test Data & Inputs**:
  - Search queries: `'sqli'`, `'192.168'`, `'<script'`, `'passwd'`.
  - Facet chips:
    - Severity: `all`, `critical` (anomaly $\ge 10$ or action `'blocked'`), `warning` (anomaly $< 10$).
    - Ban Tier: `all`, `temporary`, `permanent`.
- **Execution Steps**:
  1. Set active page `state.alIncPage = 3`.
  2. **Execute Text Search on Incidents**:
     a. Set search query `state.alIncQ = 'sqli'`.
     b. Assert `state.alIncPage` resets to `1`.
     c. Trigger `alUpdate(D)`.
     d. Assert all rendered incident rows contain `'SQL Injection'` or rule ID `'942100'`.
     e. Assert zero XSS or Path Traversal records are displayed.
     f. Inspect summary string: confirms filtered count matches 12 items.
  3. **Execute Payload Substring Search**:
     a. Set search query `state.alIncQ = 'passwd'`.
     b. Trigger `alUpdate(D)`.
     c. Assert all rendered records correspond to Path Traversal incidents containing `../../etc/passwd`.
  4. **Execute Faceted Severity Chip Filtering**:
     a. Clear search query `state.alIncQ = ''`.
     b. Set `state.alSev = 'critical'`.
     c. Trigger `alUpdate(D)`.
     d. Assert all rendered incident rows have `action === 'blocked'` or `anomaly_score >= 10`.
     e. Assert chip button for `Critical` has `aria-pressed="true"`.
  5. **Execute Banned IPs Search & Tier Filtering**:
     a. Set `state.alBanPage = 2`.
     b. Set ban search query `state.alBanQ = '192.168'`.
     c. Assert `state.alBanPage` resets to `1`.
     d. Trigger `alUpdate(D)`.
     e. Assert rendered rows in `#alBanBody` only contain IPs matching `192.168.*`.
     f. Set ban tier filter `state.alTier = 'permanent'`.
     g. Assert only permanent bans are displayed; temporary bans are omitted.
- **Expected Results**:
  - Search performs real-time case-insensitive substring matching across client IP, rule ID, path, category, and payload snippet for incidents; and IP, reason, category for bans.
  - Severity and tier chips accurately filter datasets.
  - Applying search text or toggling filter chips immediately resets the active page index to 1.
- **Pass / Fail Criteria**:
  - **Pass**: Search accurately filters across all 5 attributes; filter chips restrict records accurately; pagination resets to 1 upon every query change.
  - **Fail**: Search misses matches in payload or rule ID; case mismatch causes false rejection; or active page does not reset to 1.

     - Record 4: `ip: "192.168.1.1"`, `created_at: "2026-09-28 09:00:00"`, `temp_ban_count: 1`, `remaining_seconds: 300`

- **Test Data & Inputs**:
  - Sort headers: `Client IP` (`ip`), `Ban Tier` (`type`), `Created At` (`created_at`), `Temp Bans` (`temp_ban_count`), `TTL / Expiry` (`remaining_seconds`).
- **Execution Steps**:

     b. Trigger `alUpdate(D)`.
     c. Inspect order of rendered IP addresses:
        - Position 1: `10.0.0.1`
        - Position 2: `10.0.0.2`
        - Position 3: `10.0.0.10` (natural numeric collation: `10.0.0.2` before `10.0.0.10`)
        - Position 4: `10.0.0.15`
        - Position 5: `192.168.1.1`
     d. Assert header displays ascending indicator `▲`.
     e. Click the same header again (toggles `state.alBanSortDir = 'desc'`).
     f. Trigger `alUpdate(D)`.
     g. Assert rendered order is reversed (`192.168.1.1` first, `10.0.0.1` last) and header displays `▼`.
  2. **Test Multi-Level Deterministic Secondary Tie-Breaking on `created_at`**:
     a. Set `state.alBanSort = 'created_at'`, `state.alBanSortDir = 'desc'`.
     b. Trigger `alUpdate(D)`.
     c. Verify Record 4 (`09:00:00`) is placed last.
     d. For Records 1, 2, 3, 5 with identical `created_at` (`10:00:00`), verify secondary tie-breaker sorts on `ip` ascending:
        - First among ties: Record 3 (`10.0.0.1`)
        - Second: Record 1 (`10.0.0.2`)
        - Third: Record 2 (`10.0.0.10`)
        - Fourth: Record 5 (`10.0.0.15`)
  3. **Test Deterministic Tie-Breaking on `temp_ban_count`**:
     a. Set `state.alBanSort = 'temp_ban_count'`, `state.alBanSortDir = 'desc'`.
     b. Trigger `alUpdate(D)`.
     c. Record 2 (count 5) is first.
     d. For Records 1, 3, 5 (all count 2), verify tie-breaking orders them strictly: `10.0.0.1`, `10.0.0.2`, `10.0.0.15`.
- **Expected Results**:
  - Interactive header clicking toggles direction between `asc` and `desc`.
  - IP collation uses numeric comparison (`localeCompare(..., undefined, { numeric: true })`).
  - Ties on any primary sort column deterministically resolve by sorting on `ip` ascending per [`REQ-138`](../requirements/REQ-138.md) and [`ADR-138`](../architecture/ADR-138.md).
- **Pass / Fail Criteria**:
  - **Pass**: All columns sort accurately; numeric IP collation prevents `10.0.0.10` from preceding `10.0.0.2`; identical keys break ties deterministically on IP ascending.
  - **Fail**: Lexicographical IP sorting produces `10.0.0.10` before `10.0.0.2`; or tied rows exhibit unstable, non-deterministic ordering.

### TC-146-05: Decoupled Ergonomic Manual Ban Form with Input Validation

- **Identifier**: `TC-146-05`
- **Target Component**: [`public/js/views/alerts.js`](../../public/js/views/alerts.js), [`public/js/api.js`](../../public/js/api.js)
- **Verifies**:
  - [`REQ-146 §4 AC-146-05`](../requirements/REQ-146.md)
  - [`REQ-146 §2.4 FR-146-4`](../requirements/REQ-146.md) (Ergonomic Manual Ban Controls)
  - [`TASK-174 §3 WP-3 §5`](../tasks/TASK-174.md)
  - [`ADR-146 §1 Decision 3.5`](../architecture/ADR-146.md)
- **Preconditions**:
  1. Manual ban form mounted in decoupled toolbar outside of `.card-h`.
  2. Mock HTTP network interceptor configured to record requests to `/internal/api/security/ban`.
  3. Form elements available: `#alBanIp`, `#alBanTier`, `#alBanReason`, `#alBanBtn`, `#alBanError`.
- **Test Data & Inputs**:
  - Invalid IP formats: `'999.999.999.999'`, `'192.168.1'`, `'invalid-ip'`, `'1.2.3.4.5'`, `':::zzz'`.

  - Duration presets: `'15m'`, `'1h'`, `'6h'`, `'24h'`, `'7d'`, `'Permanent'`.
  - Ban reason: `'Scanning probe on /v1/auth'`.
- **Execution Steps**:
  1. **Negative Validation - Invalid IP Syntax**:

## 6. Open Questions

1. **Circular Buffer Incident Depth**:
   - Backend `AuditLogger` maintains a 50-incident in-memory ring buffer. For high-velocity attacks where incidents churn rapidly, client-side pagination covers up to 50 active events (5 pages of 10). If deeper horizons are required in future releases, server-side log streaming via `#/logs` provides historical traces.
2. **Preset Ban Durations**:
   - Presets (`15m`, `1h`, `6h`, `24h`, `7d`, `Permanent`) cover $> 99\%$ of edge operations; custom duration input handles non-standard intervals.
