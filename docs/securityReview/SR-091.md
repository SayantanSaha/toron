# SR-091 - Comprehensive Codebase Security Audit (Phase 6 Audit & Extended Subsystems Assessment)

## Description

## Executive Summary & Prior Fix Verification

The prior 30 identified vulnerabilities (`SEC-01` through `SEC-30`) were re-audited and confirmed **100% Resolved**:
1. **SEC-01..12**: HTTP request smuggling rejection, management API auth, shared cache isolation, bounded rate-limiting LRU, TLS verification in WebSockets, CRLF log sanitization, path traversal defense, gRPC frame bounding, CORS wildcard controls, open redirect elimination, proxy header integrity, and query parameter pollution protection remain fully functional.
2. **SEC-13..22**: Stored DOM XSS prevention in dashboard UI, header whitespace smuggling defenses, multiple Content-Length rejection, HTTP/2 body bounding, reactor worker pool non-blocking dispatch, strict path exclusion matching, container route shadowing guards, case-insensitive traversal regex, sidecar body preservation, and JWT `exp` enforcement remain verified and intact.
3. **SEC-23 (Ingress Watch Deadlock)**: Watch worker channel consumption with debounced resync prevents deadlock on high event volume.
4. **SEC-24 (Ingress Route Shadowing)**: Unhosted root routes and administrative prefixes are strictly rejected in `TranslateIngress`.
5. **SEC-25 (Sidecar Body Truncation)**: Configurable `MaxBodyBytes` with fast-fail `Content-Length` checks and stream over-read bounding returns HTTP 413.
6. **SEC-26 (L4 Proxy Uncontrolled Concurrency)**: Bounded worker pool in UDP proxy and connection capacity gating with bidirectional idle deadlines in TCP proxy mitigate resource exhaustion and Slowloris.
7. **SEC-27 (WebSocket / Upgrade Idle Deadlines)**: Bidirectional activity-refreshed deadlines prevent hanging sockets and goroutine leaks on silent upgraded connections.
8. **SEC-28 (Transcoder Request Body Bounding)**: Tiered body ingestion enforcement in REST-to-gRPC transcoder returns HTTP 413 on payload overflow.
9. **SEC-29 (Transcoder Hop-by-Hop Leakage)**: Strict stripping of hop-by-hop headers and sanitization of `TE: trailers` prior to gRPC upstream dispatch.
10. **SEC-30 (Transcoder Subpath Interception)**: Direct prefix routing with method and segment-pattern matchers eliminates empty dummy upstream proxy interceptions.

During this fresh, comprehensive audit across all subsystems, **8 new security findings** (`SEC-31` through `SEC-38`) have been uncovered.

## Findings

### Finding 1 (SEC-31): Unauthenticated Client IP Spoofing & Security Bypass via Missing Physical RemoteAddr Binding in HTTP/2 and HTTP/3 Adapters
- **Severity**: **High** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N - Score 8.2)
- **Location**: [`pkg/server/server.go:L314-L316`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L314-L316), [`pkg/httpparser/request.go:L58-L70, L122-L163`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70), [`pkg/waf/ip_acl.go:L112-L164`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L112-L164), [`pkg/server/internal_api.go:L194-L224`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L194-L224), [`pkg/router/rate_limiter.go:L286-L325`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L286-L325), [`pkg/proxy/proxy.go:L816-L852`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L816-L852)
- **CWE**: CWE-290, CWE-345, CWE-693
- **Description**:  
  In Toron's core request model [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70), client connection metadata is anchored solely to the physical socket descriptor field `RawConn net.Conn`. In the HTTP/2 adapter ([`http2AdapterHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L313-L353)) and HTTP/3 integrations, incoming requests are converted from Go's standard library `*http.Request` via [`httpparser.NewRequestFromStd(r)`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L124).
  However, `NewRequestFromStd(r)` fails to bind the physical socket address (`r.RemoteAddr`), leaving `req.RawConn` as `nil`.
  Consequently, all security-critical modules in Toron that resolve the client's identity:
  1. **WAF IP Access Control** ([`waf.ExtractClientIP`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L112-L164))
  2. **Internal Management API Subnet Enforcement** ([`validateAdminAuth` / `wrapHandler`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L194-L224))
  3. **Token Bucket Rate Limiting** ([`extractClientKeyInternal`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L286-L325))
  4. **Reverse Proxy Client IP Forwarding** ([`ReverseProxy.ServeHTTPWithPrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L816-L852))
  observe `req.RawConn == nil`. In the absence of `RawConn`, these components unconditionally fall back to trusting client-supplied headers such as `X-Forwarded-For` and `X-Real-IP`.
- **Impact**:  
  Any external untrusted client communicating over HTTP/2 or HTTP/3 can supply a spoofed `X-Forwarded-For: 127.0.0.1` (or any authorized CIDR IP) to:
  - Completely bypass WAF IP blacklists and CIDR access restrictions.
  - Bypass administrative subnet restrictions protecting `/internal/api/*` management endpoints.
  - Evade route-level token bucket rate limiting by rotating arbitrary `X-Forwarded-For` addresses on each request.
  - Inject forged client IPs into `X-Forwarded-For` headers relayed to backend upstreams.
- **Recommendation**:  
  Add a `RemoteAddr string` field to [`httpparser.Request`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L58-L70). Ensure [`httpparser.NewRequestFromStd(r)`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/request.go#L124) populates `req.RemoteAddr = r.RemoteAddr`. Update `ExtractClientIP`, `extractClientKeyInternal`, `internal_api.go`, and `proxy.go` to prioritize `req.RemoteAddr` (or `req.RawConn.RemoteAddr()`), and only trust `X-Forwarded-For` if the physical peer address is verified against `trusted_proxies`.

### Finding 2 (SEC-32): Fail-Open WAF IP Access Control Bypass on Unidentifiable Client IP
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N - Score 6.5)
- **Location**: [`pkg/waf/middleware.go:L58-L63`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/middleware.go#L58-L63), [`pkg/waf/ip_acl.go:L75-L78`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L75-L78)
- **CWE**: CWE-284, CWE-1188, CWE-693
- **Description**:  
  In [`pkg/waf/middleware.go:L58-L63`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/middleware.go#L58-L63):
  ```go
  if acl := engine.IPAccessList(); acl != nil && acl.HasRules() {
      if ip := ExtractClientIP(req); ip != nil {
          allowed, reason := acl.CheckIP(ip)
          if !allowed { ... }
      }
  }
  ```
  And in [`pkg/waf/ip_acl.go:L75-L78`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L75-L78):
  ```go
  if acl == nil || !acl.HasRules() || ip == nil {
      return true, ""
  }
  ```
  When an administrator configures an IP allowlist (`allowed_ips` / `allowedSubnets`), any incoming request where the client IP cannot be determined (`ExtractClientIP(req) == nil`) skips the access check entirely because `ip != nil` evaluates to false. Furthermore, `CheckIP(nil)` returns `true, ""` (fail-open).
- **Impact**:  
  Requests with missing, unparseable, or stripped socket and proxy header addresses completely bypass configured strict IP whitelist policies.
- **Recommendation**:  
  When an allowlist is configured (`len(acl.allowedSubnets) > 0 || len(acl.allowedIPs) > 0`), if `ip == nil`, `CheckIP` must return `false, "client IP could not be verified against allowed IP whitelist"`. In `middleware.go`, evaluate `CheckIP(ip)` directly whenever `acl.HasRules()` is true, rejecting unidentifiable clients if an allowlist is active.

### Finding 3 (SEC-33): Unbounded Routing Table Memory Leak & Zombie Route Persistence in Kubernetes Ingress Controller
- **Severity**: **High** (CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:H - Score 8.1)
- **Location**: [`pkg/ingress/controller.go:L138-L161`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L138-L161), [`pkg/router/router.go:L232-L244`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L232-L244)
- **CWE**: CWE-400, CWE-670, CWE-1059
- **Description**:  
  In [`pkg/ingress/controller.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go), [`syncIngresses`](file:///Users/sneha/Developer/toron-research/toron/pkg/ingress/controller.go#L111-L161) executes periodically (default every 30s) and upon receiving Kubernetes Ingress watch events. In lines 151-157:
  ```go
  opts := proxy.ProxyOptions{
      Targets: []string{r.TargetURL()},
  }
  _ = c.router.RoutePrefix("upstream", r.Host, r.Prefix, nil, "", opts)
  ```
  [`RoutePrefix`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L163-L245) unconditionally appends a new `prefixRoute` to `r.prefixRoutes` on every invocation.
  This causes three critical failure modes:
  1. **Unbounded Memory Leak**: `r.prefixRoutes` grows monotonically on every periodic resync. A cluster with 50 Ingress routes resyncing every 30s adds 144,000 entries per day, steadily leaking memory and slowing down router linear scans.
  2. **Zombie Route Persistence**: When an Ingress resource is deleted from Kubernetes, `syncIngresses` never cleans up or removes the previous route from `r.prefixRoutes`. The router retains the route indefinitely, forwarding client traffic to decommissioned backends.
  3. **Stale Endpoint Shadowing**: When a service endpoint IP changes, the old target remains in `r.prefixRoutes` earlier in the slice, continuing to receive all traffic due to first-match routing.
- **Impact**:  
  Progressive server memory exhaustion, routing performance degradation, route hijacking by decommissioned services, and failure to process Kubernetes Ingress deletions or updates.
- **Recommendation**:  
  Implement a dynamic route registry in the router or provide atomic route replacement (`ReplacePrefixRoutesBySource` or route map keyed by `(host, prefix)`). In `Controller.syncIngresses`, prune deleted Ingress routes from the router and update existing routes atomically.

### Finding 4 (SEC-34): Premature Route Deletion & Load-Balancing Failure Across Multi-Replica Containers in OCI Discovery Engine
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H - Score 7.5)
- **Location**: [`pkg/discovery/manager.go:L207-L256`](file:///Users/sneha/Developer/toron-research/toron/pkg/discovery/manager.go#L207-L256), [`pkg/router/router.go:L755-L773`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L755-L773)
- **CWE**: CWE-400, CWE-284, CWE-662
- **Description**:  
  When multiple replica containers run for a service (e.g. 3 container instances sharing `toron.host: api.example.com` and `toron.prefix: /v1`), `handleContainerStart` in [`pkg/discovery/manager.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/discovery/manager.go#L207-L239) registers each container individually as a separate `RoutePrefix` with a single target: `Targets: []string{route.TargetURL()}`.
  Because `router.ServeHTTP` selects the first matching prefix route and stops, only the first replica receives traffic; subsequent replicas are starved.
  Furthermore, when any single replica container stops or restarts, `handleContainerStop` invokes:
  ```go
  m.router.RemovePrefixRoute(route.Host, route.Prefix)
  ```
  [`RemovePrefixRoute`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L755-L773) iterates through `r.prefixRoutes` and purges ALL prefix routes matching `(host, prefix)` indiscriminately.
- **Impact**:  
  Stopping or restarting a single container replica immediately removes the route for all surviving replicas, causing an immediate denial of service (HTTP 404) for that service despite remaining healthy instances.
- **Recommendation**:  
  In `discovery.Manager`, aggregate targets across all active containers matching `(Host, Prefix)`. When a container starts or stops, recalculate the combined target list and update the router's load balancer atomically.

### Finding 5 (SEC-35): Insecure Default `InsecureSkipVerify = true` in Sidecar Client TLS Configuration
- **Severity**: **High** (CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N - Score 8.1)

- **Description**:

  if cfg.CAFile != "" {

### Finding 6 (SEC-36): Memory Exhaustion via Unbounded Upstream Response Buffering in Internal API Proxy Test Probe
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H - Score 6.5)
- **Location**: [`pkg/server/internal_api.go:L493, L624-L638`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L493)
- **CWE**: CWE-400, CWE-770
- **Description**:  
  In `POST /internal/api/proxy-test` ([`pkg/server/internal_api.go:L490-L642`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L490-L642)), an operator can test diagnostic endpoints or configured upstream routes. When probing the target URL:
  ```go
  respBodyBytes, _ := io.ReadAll(httpResp.Body)
  ```
  `io.ReadAll` reads the entire upstream response into memory without any size bound or `io.LimitReader`. If the tested endpoint returns an unbounded stream or a large binary file, the server reads the payload into memory until the process exhausts available RAM and crashes with an Out-Of-Memory (OOM) panic.
- **Impact**:  
  Memory exhaustion and server crash when probing large upstream resources.
- **Recommendation**:  
  Limit upstream response ingestion in `proxy-test` using `io.LimitReader(httpResp.Body, maxProbeBytes)` (e.g. 1 MB or 2 MB), truncating large responses safely.

### Finding 7 (SEC-37): Unbounded HTTP Client & Transport Allocation per Request in Service Mesh Sidecar Proxy
- **Severity**: **Medium** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H - Score 7.5)
- **Location**: [`pkg/sidecar/proxy.go:L192-L202`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L192-L202)
- **CWE**: CWE-400, CWE-772
- **Description**:  
  In [`ProxyEngine.proxyToURL`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L192-L251), every incoming HTTP request executes:
  ```go
  opts := proxy.ProxyOptions{
      Targets: []string{targetURL},
  }
  px, err := proxy.NewProxyWithOptions(opts)
  ```
  `proxy.NewProxyWithOptions` initializes a brand new `*http.Transport` and `*http.Client` with its own connection pool (`MaxIdleConns: 100`, keepalive timers).
  The created `ReverseProxy` (`px`) is discarded immediately after handling the request. The underlying `http.Transport` is never closed, leaving idle connections, sockets, and background goroutines lingering in memory.
- **Impact**:  
  Rapid socket, file descriptor (EMFILE), and memory leak under sustained or concurrent traffic through the sidecar proxy.
- **Recommendation**:  
  Cache and reuse `ReverseProxy` instances or maintain a shared `http.Client` / `http.Transport` across sidecar proxy requests instead of allocating a new transport per request.

### Finding 8 (SEC-38): Missing Token Syntax and Length Validation in ACME HTTP-01 Challenge Handler
- **Severity**: **Low** (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L - Score 3.7)
- **Location**: [`pkg/acme/acme.go:L193-L208`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L193-L208)
- **CWE**: CWE-20, CWE-703
- **Description**:  
  In [`ACMEManager.ServeHTTP01Handler`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L193-L208):
  ```go
  token := strings.TrimPrefix(req.Path, "/.well-known/acme-challenge/")
  token = strings.TrimSpace(token)
  keyAuth, exists := m.GetHTTP01Challenge(token)
  ```
  RFC 8555 §8.3 strictly mandates that ACME HTTP-01 challenge tokens MUST contain only base64url characters (`[a-zA-Z0-9_-]+`) and must not be empty. The current implementation performs no syntax or length validation on `token`, allowing empty strings, traversal tokens (`..`), or arbitrarily large strings to query the internal synchronized map.
- **Impact**:  
  Deviation from RFC 8555 specification; unvalidated user-controlled strings querying internal token cache.
- **Recommendation**:  
  Validate that `token` is non-empty, has a reasonable length (<= 128 characters), and contains only characters in `[a-zA-Z0-9_-]`. If invalid, immediately return `400 Bad Request`.
