# CR-093 - Code Review of Secure Default Certificate Validation and Explicit InsecureSkipVerify Opt-In in Sidecar Client TLS Configuration (SEC-35)

## Review Summary

- **Components Reviewed**:
  - [`pkg/config/config.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config.go#L103-L115): Configuration schema extension adding `InsecureSkipVerify bool` with `yaml:"insecure_skip_verify" json:"insecure_skip_verify"` tags to `SidecarConfig`, explicit `false` initialization in `defaultConfig()`, zero-value initialization guarantees, and YAML file loading tests in [`pkg/config/config_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/config/config_test.go#L58-L99).
  - [`pkg/sidecar/mtls.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/mtls.go#L47-L77): Client TLS constructor refactor in `BuildClientTLSConfig`: complete removal of hardcoded `InsecureSkipVerify = true` default, strict assignment `tlsConfig.InsecureSkipVerify = cfg.InsecureSkipVerify`, host system trust roots fallback when `CAFile == ""` (`tlsConfig.RootCAs = nil`), custom CA bundle loading via `x509.NewCertPool()` and `caPool.AppendCertsFromPEM`, high-visibility security audit warning log on insecure opt-in, client identity cert/keypair loading via `tls.LoadX509KeyPair`, and protocol floor enforcement (`tls.VersionTLS12`).
  - [`pkg/sidecar/sidecar_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/sidecar_test.go#L878-L1478): Automated test suite implementing all 7 verification scenarios defined in [`TC-097`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-097.md) (`TC-097-01` through `TC-097-07`), including test CA generation, certificate minting, untrusted server handshake failure, custom CA handshake success, explicit opt-in warning log interception, client identity cert loading, TLS 1.2 minimum version enforcement, and high-concurrency race detection under `go test -race`.
  - `go.mod` / `go.sum`: Verification of zero third-party dependencies (100% pure Go standard library).
- **Security & Architectural Invariant Verifications**:
  - **Complete Remediation of CWE-295**: The hardcoded `else { tlsConfig.InsecureSkipVerify = true }` branch has been entirely eliminated. Bypassing certificate verification is no longer possible by simply omitting `CAFile`.
  - **Secure-by-Default Invariant**: `InsecureSkipVerify` strictly evaluates to `false` in default configuration files, `DefaultAppConfig()`, and Go zero-value struct instantiation (`SidecarConfig{}`).
  - **System Trust Root Fallback**: When `CAFile == ""` and `InsecureSkipVerify == false`, `tlsConfig.RootCAs` remains `nil`, enabling Go's `crypto/tls` runtime to validate peer certificate chains against the host operating system's trust store.
  - **Custom CA Certificate Pool Loading**: When `CAFile != ""`, the certificate bundle is parsed and loaded into `tlsConfig.RootCAs`, while `InsecureSkipVerify` remains `false`.
  - **Mandatory Security Audit Warning**: When `cfg.InsecureSkipVerify: true` is explicitly configured, `BuildClientTLSConfig` emits a prominent warning log: `[SIDECAR] WARNING: InsecureSkipVerify is enabled for sidecar egress TLS. Certificate verification is disabled.`
  - **Client Identity & Protocol Floor**: Client keypair (`CertFile`, `KeyFile`) is loaded independently into `tlsConfig.Certificates`, and `tlsConfig.MinVersion = tls.VersionTLS12` is unconditionally enforced across all permutations.
  - **Zero Third-Party Dependencies**: Pure Go standard library (`crypto/tls`, `crypto/x509`, `fmt`, `log`, `os`).
  - **Concurrency Safety & Race-Freedom**: 100% thread safety verified under high parallel request loads and concurrent config generation.
- **Verdict**: **APPROVED WITH RECOMMENDATIONS (Status: approved)**.

### Background & Root Cause Analysis (SEC-35 / CWE-295)

During security audit [`SR-091 Finding 5`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L173-L195) and vulnerability tracking [`SEC-35`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L474-L482) ([CWE-295: Improper Certificate Validation](https://cwe.mitre.org/data/definitions/295.html), CVSS:3.1 Score 8.1 - High), a severe vulnerability was identified in [`pkg/sidecar/mtls.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/mtls.go).

Previously, `BuildClientTLSConfig` contained the following logic:

```go
// Vulnerable implementation prior to TASK-120
if cfg.CAFile != "" {
    caBytes, err := os.ReadFile(cfg.CAFile)
    if err != nil {
        return nil, fmt.Errorf("failed to read sidecar ca cert: %w", err)
    }
    caPool := x509.NewCertPool()
    caPool.AppendCertsFromPEM(caBytes)
    tlsConfig.RootCAs = caPool
} else {
    // Default to insecure verify if custom CA is omitted in test environments
    tlsConfig.InsecureSkipVerify = true
}
```

When an operator deployed Toron in a standard production environment relying on host operating system certificate authorities (such as Let's Encrypt, DigiCert, AWS ACM, or Google Cloud CAs), `cfg.CAFile` was intentionally omitted (`""`). This caused the function to take the `else` branch, silently enabling `InsecureSkipVerify = true`.

### Vulnerability Impact

1. **Complete TLS Validation Bypass**: Go's `crypto/tls` package disables all certificate chain validation, expiration checking, and hostname matching when `InsecureSkipVerify` is `true`.
2. **Egress Man-in-the-Middle (MITM) Interception**: Any attacker located on the same Kubernetes node, adjacent container, Docker network, or local network path could intercept outbound egress traffic, present any self-signed or invalid certificate, and transparently capture or modify sensitive plaintext payloads, Bearer tokens, API credentials, and customer data.
3. **Violation of Secure-by-Default Principle**: Security best practices mandate that cryptographic verification must be strictly enforced by default. Bypassing verification must require an intentional, explicit configuration opt-in by the operator, paired with high-visibility audit warnings.

### 2. Elimination of Hardcoded Insecure Verification in `BuildClientTLSConfig` (`pkg/sidecar/mtls.go`)

- **Implementation**:
  [`pkg/sidecar/mtls.go:48-77`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/mtls.go#L48-L77):
  ```go
  func BuildClientTLSConfig(cfg config.SidecarConfig) (*tls.Config, error) {
      tlsConfig := &tls.Config{
          MinVersion:         tls.VersionTLS12,
          InsecureSkipVerify: cfg.InsecureSkipVerify,
      }

      if cfg.InsecureSkipVerify {
          log.Printf("[SIDECAR] WARNING: InsecureSkipVerify is enabled for sidecar egress TLS. Certificate verification is disabled.")
      }

      if cfg.CertFile != "" && cfg.KeyFile != "" {
          cert, err := tls.LoadX509KeyPair(cfg.CertFile, cfg.KeyFile)
          if err != nil {
              return nil, fmt.Errorf("failed to load sidecar client tls cert/key pair: %w", err)
          }
          tlsConfig.Certificates = []tls.Certificate{cert}
      }

      if cfg.CAFile != "" {
          caBytes, err := os.ReadFile(cfg.CAFile)
          if err != nil {
              return nil, fmt.Errorf("failed to read sidecar ca cert: %w", err)
          }
          caPool := x509.NewCertPool()
          caPool.AppendCertsFromPEM(caBytes)
          tlsConfig.RootCAs = caPool
      }

      return tlsConfig, nil
  }
  ```
- **Evaluation against REQ-097-AC-02 / ADR-097 §2**:
  - The vulnerable `else { tlsConfig.InsecureSkipVerify = true }` branch has been eliminated completely.
  - `tlsConfig.InsecureSkipVerify` is assigned `cfg.InsecureSkipVerify` at initialization time.
  - No code path exists where omitting `CAFile` forces `InsecureSkipVerify` to `true`.
- **Verdict**: **COMPLIANT**.

### 3. System Trust Root Fallback & Untrusted Server Rejection (`REQ-097-AC-03` / `ADR-097 §3`)

- **Implementation Analysis**:
  - When `cfg.CAFile == ""` and `cfg.InsecureSkipVerify == false`, `tlsConfig.RootCAs` remains `nil`.
  - In Go's `crypto/tls` standard library, when `tls.Config.RootCAs == nil`, the TLS handshake implementation automatically calls `x509.SystemCertPool()`, verifying server certificates against the host operating system's root certificate bundle.

The client attempts a request through `tlsConfig`, which fails during handshake with `x509.UnknownAuthorityError`, receiving zero HTTP response bytes.
- **Verdict**: **COMPLIANT**.

## Findings & Recommendations

### Finding 1: Unchecked Return Value on `caPool.AppendCertsFromPEM(caBytes)`

- **Severity**: Low (Code Quality / Defensive Parsing)
- **Location**: [`pkg/sidecar/mtls.go:72`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/mtls.go#L72)
- **Related Artifact**: [`REQ-097-AC-04`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-097.md#L125-L131), [`ADR-097 §4`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-097.md#L206-L215)
- **Description**:
  In `BuildClientTLSConfig`:
  ```go
  caBytes, err := os.ReadFile(cfg.CAFile)
  if err != nil {
      return nil, fmt.Errorf("failed to read sidecar ca cert: %w", err)
  }
  caPool := x509.NewCertPool()
  caPool.AppendCertsFromPEM(caBytes)
  tlsConfig.RootCAs = caPool
  ```
  The method `caPool.AppendCertsFromPEM(caBytes)` returns a boolean indicating whether any certificates were parsed. If `cfg.CAFile` points to an existing file that contains malformed data, an empty PEM block, or an invalid certificate format, `AppendCertsFromPEM` returns `false`, leaving `caPool` empty.
- **Impact**:
  An empty cert pool (`RootCAs`) results in all outbound TLS handshakes failing with certificate verification errors at runtime, rather than failing fast at startup with a descriptive configuration error.
- **Recommendation**:
  Validate the return value of `AppendCertsFromPEM`:
  ```go
  if !caPool.AppendCertsFromPEM(caBytes) {
      return nil, fmt.Errorf("failed to parse any valid CA certificates from %s", cfg.CAFile)
  }
  ```

### Finding 2: Asymmetric Client Identity Keypair Validation (`CertFile` vs `KeyFile`)

- **Severity**: Low (Defensive Validation)
- **Location**: [`pkg/sidecar/mtls.go:58`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/mtls.go#L58)
- **Related Artifact**: [`REQ-097-AC-06`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-097.md#L140-L145), [`ADR-097 §6.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-097.md#L228-L233)
- **Description**:
  The condition `if cfg.CertFile != "" && cfg.KeyFile != ""` loads the keypair only when both fields are non-empty. If an operator misconfigures their environment by specifying `cert_file` while omitting `key_file` (or vice versa), the block is silently skipped without any error or warning. The sidecar then proceeds without client identity certificates.
- **Impact**:
  The sidecar fails to authenticate during upstream mTLS handshakes, leading to upstream connection rejections that can be difficult to diagnose.
- **Recommendation**:
  Add an explicit configuration validation check:
  ```go
  if (cfg.CertFile != "" && cfg.KeyFile == "") || (cfg.CertFile == "" && cfg.KeyFile != "") {
      return nil, fmt.Errorf("both cert_file and key_file must be specified together for sidecar client mTLS")
  }
  ```

### Finding 3: `ProxyEngine.proxyToURL` Ingress/Egress TLS Option Propagation Gap

- **Severity**: Low (Architectural Enhancement)
- **Location**: [`pkg/sidecar/proxy.go:193-197`](file:///Users/sneha/Developer/toron-research/toron/pkg/sidecar/proxy.go#L193-L197)
- **Related Artifact**: [`REQ-081`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-081.md), [`ADR-097`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-097.md)
- **Description**:
  In `pkg/sidecar/proxy.go`, `ProxyEngine.proxyToURL` constructs reverse proxy options:
  ```go
  opts := proxy.ProxyOptions{
      Targets: []string{targetURL},
  }
  px, err := proxy.NewProxyWithOptions(opts)
  ```
  `proxyToURL` does not currently pass `p.cfg.InsecureSkipVerify` or the CA pool from `BuildClientTLSConfig` to `opts.InsecureSkipVerify` and `opts.TLSCACertPool`.
- **Impact**:
  Because `proxy.NewProxyWithOptions` defaults to `InsecureSkipVerify: false` with `TLSCACertPool: nil`, outbound egress requests through `ProxyEngine` validate against host OS system trust roots (secure by default, preventing MITM). However, if an operator defines a custom internal mesh CA via `cfg.CAFile` or explicitly enables `insecure_skip_verify: true`, those settings are not propagated to `ProxyOptions` inside `proxyToURL`.
- **Recommendation**:
  In a subsequent maintenance task, enhance `proxyToURL` to plumb `p.cfg.InsecureSkipVerify` and `p.cfg.CAFile` into `proxy.ProxyOptions`, or construct a shared `http.Transport` initialized with `BuildClientTLSConfig(p.cfg)`.
