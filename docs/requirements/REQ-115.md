# REQ-115 - 10-Task Controlled Ablation Experiment Suite (BMK-05)

## 1. Description

Academic peer reviews of Paper 1 (`AER-001` lines 67, 81–82, 191, 235, 313, 326; `MSR-001` lines 41, 75–81, 231, 304; `PDR-001` lines 46, 167–181, 254, 371–372, 392; and `AR-001` lines 207–213, 265, 285, 299) identified a fundamental methodological vulnerability regarding the causal attribution of system quality and architectural stability:

1. **The Absence of Comparative Baselines and Counterfactual Controls**:
   The manuscript asserts that the proposed artifact-anchored multi-agent software engineering methodology—featuring formal Architectural Decision Record (ADR) contracts and an 8-stage role-specialized pipeline—eliminates *specification drift*, prevents *architectural erosion*, and suppresses *unverified defect propagation*.
   However, reviewers across all disciplines noted that **not a single baseline experiment or ablation control was executed**:
   > *"Without an experimental baseline (e.g., single-agent prompting or MetaGPT on the same tasks) or an ablation removing ADR contracts, what empirical evidence demonstrates that the absence of specification drift was caused by the ADR artifact mechanism rather than the capabilities of the underlying LLM or human prompt guidance?"* (`PDR-001`, lines 371–372)
   > *"In empirical software engineering and computer science, comparative superiority claims cannot be supported by rhetoric or conceptual contrast alone. Without controlled baseline comparisons and component ablations, it is impossible to determine whether Toron's successful synthesis was caused by: (i) formal ADR contracts; (ii) the natural memory safety and standard library abstractions of the Go language; (iii) the quality of prompt instructions; or (iv) the underlying LLM's pre-trained knowledge of HTTP server patterns."* (`MSR-001`, line 81)

2. **Associate Editor Adjudication & Mandatory Revision Mandate**:
   In `AER-001` (lines 81–82), the Associate Editor ruled:
   > *"The Associate Editor sides with Reviewer 1... Demanding that authors re-implement this entire server three additional times from scratch across alternative agent frameworks is disproportionate. However, the authors must: (a) retract all claims asserting comparative superiority over ChatDev and MetaGPT; and (b) execute a targeted ablation on a bounded, representative subset of 10 tasks (e.g., HTTP parsing and cache hardening) comparing ADR-governed multi-agent handoffs against direct single-agent prompting."*

3. **Mandatory Remediation (`BMK-05`)**:
   Toron must establish a rigorous, reproducible 10-task controlled ablation experiment suite evaluated on `TASK-061` through `TASK-070` comparing:
   - **Condition A (Proposed Pipeline)**: Artifact-anchored multi-agent pipeline with formal ADR contracts, task decomposition, test specification contracts, developer implementation, and parallel code and security reviews.
   - **Condition B (Baseline Control)**: Direct single-agent prompting of the same foundation LLM with identical task requirements, but without intermediate ADR contracts, task breakdowns, test designers, or adversarial reviews.
   The suite must capture complete execution traces, raw prompts, model responses, code patches, and test outcomes, computing quantitative metrics for specification drift, defect injection, test pass rates, token expenditure, and reviewer flaw arrest rates.

## 3. Acceptance Criteria

### AC-1: Rigorous Condition Definitions & Experimental Protocol
- **Condition A (Artifact-Anchored Multi-Agent Pipeline)**:
  1. Each task follows the formal 8-stage lifecycle: `REQ` $\to$ User Approval Gate $\to$ `TASK` $\to$ `ADR` $\to$ `TC` $\to$ `Developer` $\to$ Parallel Reviews (`CR` + `SR`) $\to$ `Document Writer`.
  2. Implementations are bound by explicit ADR architectural contracts governing package boundaries, forbidden imports, memory allocation semantics, and error handling.
  3. Pre-merge defects identified by Code Reviewer and Security Analyst are arrested and corrected prior to final integration.
- **Condition B (Direct Single-Agent Baseline Prompting)**:
  1. Identical task specifications and acceptance criteria provided to the same underlying foundation LLM in a single direct prompt.
  2. No intermediate ADR contracts, task decomposition, test specification contracts, or multi-agent review iterations are provided.
  3. The single agent is requested to output a unified code patch or implementation directly from the requirement.
  4. Real, authentic prompt and execution logs are captured for all 10 tasks.

### AC-2: Data Archival & Reproducibility Harness
- In `toron/benchmarks/ablation/`:
  1. **`data/condition_a/`**: Reference metadata, architectural contracts, test specifications, review findings, and commit references for `TASK-061` through `TASK-070`.
  2. **`data/condition_b/`**: Dedicated subdirectories `task_061/` through `task_070/` containing:
     - `prompt.txt`: Full raw input prompt provided to the single agent.
     - `response_raw.md`: Unmodified output emitted by the single agent.
     - `patch.diff`: Unified git patch generated by the single agent.
     - `test_execution.log`: Comprehensive test execution log (`go test -v -race`) when evaluating the patch against the test harness.
     - `telemetry.json`: Quantitative metadata including prompt tokens, completion tokens, total tokens, execution time, and defect classifications.

### AC-3: Quantitative Evaluation Metrics
- The automated evaluation harness must compute and report the following 5 core metrics across all 10 tasks and compare conditions:
  1. **Specification Drift Rate (%)**: Percentage of specified acceptance criteria violated, ignored, or incompletely implemented.
  2. **Defect Injection Count**: Number of distinct bugs, protocol edge-case omissions, security vulnerabilities (CWEs), regressions, or concurrency hazards introduced.
  3. **Unit & Integration Test Pass Rate (%)**: Percentage of verification assertions passing cleanly under `go test -race -count=1`.
  4. **Token Expenditure & Cost Ratio**: Input, output, and total token consumption for both conditions, along with the overhead cost ratio ($\text{Cost}_A / \text{Cost}_B$).
  5. **Reviewer Flaw Arrest Rate (%)**: Percentage of potential defects identified and arrested by `CR` and `SR` during Condition A prior to code merge.

### AC-4: Automated Evaluator & Report Generation
- Provide Go evaluation engine (`benchmarks/ablation/runner.go` or `evaluator.go`) and shell runner (`benchmarks/ablation/run_ablation.sh`):
  1. Parses task definitions, Condition A records, and Condition B outputs.
  2. Executes verification tests and validates patches.
  3. Emits `benchmarks/results/ablation_study_report.json` with machine-readable statistical aggregates.
  4. Emits `benchmarks/results/ablation_study_report.md` formatted as a publication-ready academic artifact featuring:
     - Executive summary directly answering peer review critiques (`AER-001`, `MSR-001`, `PDR-001`).
     - Side-by-side comparative metric matrix across all 10 tasks.
     - Statistical summary table (Mean, Standard Deviation, Relative Improvement / Efficacy).
     - Qualitative failure analysis detailing specific architectural failures observed under Condition B (e.g., missing socket teardown, bypassable regex, unbounded memory growth).

### AC-5: Zero External Dependencies & Race Cleanliness
- The entire ablation evaluation harness and runner must use only Go standard library packages.
- Must execute cleanly with zero race warnings under `go test -race -count=1 ./benchmarks/ablation/...`.

---

## 4. Rationale

The core theoretical premise of Toron's methodology is that large language models suffer from unconstrained drift and catastrophic forgetting when navigating complex, distributed architectural invariants without explicit structural scaffolding. By running a controlled ablation across 10 mission-critical networking and security tasks, the empirical evaluation provides the counterfactual evidence demanded by the Associate Editor and reviewers, demonstrating that ADR contracts and role-specialized review gates provide a statistically measurable defense against defect injection and specification drift.

---

## 5. Constraints

- Pure Go standard library (zero external dependencies).
- Zero data races under `go test -race`.
- Authentic single-agent execution logs and telemetry.
- Identical underlying model capabilities used for comparison.
