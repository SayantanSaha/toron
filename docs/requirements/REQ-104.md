# REQ-104 - Differential Fuzzer Report Formatting Bug Fix for Baseline Request

## 1. Description

In [`benchmarks/fuzzer/diff_fuzzer.go`](benchmarks/fuzzer/diff_fuzzer.go), the report generation logic for the differential security fuzzer used static fallback strings for the expected status column in the markdown report (`differential_fuzz_report.md`). As a result, the benign baseline test case `BASELINE-001` (Standard Valid HTTP/1.1 GET Request) erroneously displayed `400/501` as its expected status instead of `200 OK`.

This requirement mandates dynamic expected status formatting based on each test case's actual `ExpectedStatus` slice, canonically formatting `BASELINE-001` as `200 OK` across both Markdown and JSON reporting artifacts.

## 2. Acceptance Criteria

### AC-1: Dynamic Expected Status Resolution
- In `diff_fuzzer.go`, the expected status representation in `differential_fuzz_report.md` must be computed dynamically from the `TestCase.ExpectedStatus` field.
- Hardcoded status code string constants (e.g., `"400/501"`) must be removed from markdown table generation.

### AC-2: Canonical Status Code & Text Representation
- For single expected status codes (e.g. `200`), the markdown table must format the value canonically with its RFC status phrase (e.g., `200 OK`) using pure Go standard library `http.StatusText(code)`.
- For multiple expected status codes (e.g. `[400, 501]` or `[400, 403]`), the format must render the slashed list (e.g., `400/501` or `400/403`).

### AC-3: Explicit Baseline Test Case Formatting
- For `BASELINE-001`, the markdown table must render `200 OK` in the `Expected Status` column.

### AC-4: Automated Verification
- Unit tests in `benchmarks/fuzzer/diff_fuzzer_test.go` must assert the formatted status string generation logic.
