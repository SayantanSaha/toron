# ADR-111 - Bounded Worker Pool Connection Dispatching

## 1. Context & Problem Statement

In academic peer review audits of Toron's core edge gateway design (`AER-001`, `PDR-001`, `SRC-03`), reviewers identified a fundamental divergence between the published architecture description (*"event-driven non-blocking TCP reactor with bounded worker pools"*) and the concrete implementation in `pkg/reactor/reactor.go`:

1. **Unbounded Goroutines**: `Serve()` executed `go r.processConn(c)` for every accepted TCP socket. Under heavy traffic spikes or connection flood attacks, the server would spawn an arbitrary number of goroutines, resulting in unbounded memory growth and Go runtime scheduler overhead.
2. **Unread Configuration**: `WorkerPoolSize` in `reactor.Config` was completely unread in connection scheduling, reducing it to a dead configuration parameter.
3. **Absence of Ingress Backpressure**: Without a bounded queue or worker limit, the gateway accepted sockets as fast as the OS delivered them without backpressure, shifting memory exhaustion from the operating system's bounded TCP socket buffers to the Go heap.

## 2. Decision

We establish a **True Bounded Channel-Based Worker Pool Engine** in `pkg/reactor/reactor.go`:

### 2.1 Bounded Worker Dispatch Architecture
1. **Bounded Task Queue**:
   Introduce a task channel `tasks chan net.Conn` with capacity `MaxQueueSize` (configured via `Config.MaxQueueSize`, defaulting to `WorkerPoolSize * 4`).
2. **Pre-Spawned Worker Pool**:
   In `Serve(ln net.Listener)`, launch exactly `WorkerPoolSize` worker goroutines:
   ```go
   for i := 0; i < r.config.WorkerPoolSize; i++ {
       r.workerWg.Add(1)
       go r.workerLoop()
   }
   ```
3. **Deterministic Job Execution**:
   Workers pull from `r.tasks`, process connections synchronously via `r.processConn(conn)`, untrack sockets upon completion, and loop for subsequent tasks.

### 2.2 Ingress Dispatching & TCP Backpressure
In `Serve(ln net.Listener)`:
```go
select {
case r.tasks <- conn:
case <-r.ctx.Done():
    r.trackConn(conn, false)
    _ = conn.Close()
    return ErrServerClosed
}
```
When all `WorkerPoolSize` workers are busy and `tasks` is full, `r.tasks <- conn` blocks in the `ln.Accept()` loop. This applies backpressure to the kernel's TCP accept backlog (`SOMAXCONN` / `listen(backlog)`), pausing TCP three-way handshakes and throttling client ingress deterministically.

### 2.3 Teardown Synchronization & Anti-Deadlock Guarantees
During graceful shutdown (`Shutdown(ctx)`):
1. Atomically set `r.isShutdown` to `true` and cancel `r.ctx`.
2. Close `r.listener` to interrupt blocking `ln.Accept()`.
3. Under `r.connsMu`, iterate and close all active sockets in `r.conns`. This immediately breaks any worker blocked in `conn.Read()` or `conn.Write()`.
4. When `Serve` exits, its deferred cleanup closes `r.tasks` and waits on `r.workerWg`.
5. Workers seeing `r.tasks` closed cleanly exit, ensuring zero goroutine leaks and zero deadlock hazards.

### 2.4 Concurrency Observability APIs
Track worker utilization via atomic state:
- `ActiveWorkers() int`: returns the number of worker goroutines currently executing `r.processConn(conn)`.
- `QueueLen() int`: returns the number of buffered sockets awaiting worker acquisition (`len(r.tasks)`).
- **Invariant**: Under all load scenarios, `0 <= ActiveWorkers() <= WorkerPoolSize`.

## 4. Alternatives Considered

1. **Unbounded Per-Connection Goroutines (`go r.processConn(c)`)**:
   - *Pros*: Trivial implementation; idle keep-alive sockets do not block other connections.
   - *Cons*: Severe vulnerability to connection floods and DoS; completely ignores `WorkerPoolSize`; rejected by academic peer reviewers as inconsistent with an event reactor architecture.
2. **Channel Semaphore on Dynamic Goroutines**:
   - *Pros*: Limits active handlers.
   - *Cons*: Continuously creates and destroys goroutines, incurring stack allocation and scheduler churn. Pre-spawned worker loops maintain warm OS thread associations and zero per-task allocation overhead.

## 5. Rationale & Constraints

- **Pure Go Standard Library**: Relies solely on Go channels, mutexes, and `sync.WaitGroup`. Zero external dependencies.
- **Backpressure**: Prevents server OOM by shifting overload buffering to the TCP network layer.
- **Race-Clean**: Guaranteed free of race conditions under `go test -race`.
