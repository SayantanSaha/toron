# REQ-108 - Persistent bufio.Reader Preservation for HTTP/1.1 Pipelining and Connection Keep-Alive

## 1. Description

Peer review audits of Paper 1 and Paper 2 (`SRC-02`, `ReviewTaskSummary.md`, `AER-001`, `AER-002`) identified a critical protocol buffering defect in Toron's HTTP/1.1 connection handling loop:

1. **Buffer Eviction on Persistent Connections (`ParseRequest`)**:
   In `pkg/httpparser/parser.go` (line 44), `httpparser.ParseRequest` constructs a fresh `bufio.NewReader(r)` on every invocation. When reading from a network socket (`net.Conn`), `bufio.Reader` reads chunks into an internal 4 KB buffer (default `defaultBufSize = 4096`). If a client pipelines multiple HTTP requests within a single TCP packet or segment (RFC 7230 §6.3.2), the first call to `ParseRequest` parses the first HTTP request headers and body, but the remaining unconsumed bytes corresponding to subsequent pipelined requests remain trapped inside the internal buffer of the ephemeral `*bufio.Reader`. When `ParseRequest` returns, that `*bufio.Reader` reference is discarded.

2. **Socket Desynchronization in Server Loop (`handleConn`)**:
   In `pkg/server/server.go` (line 199), `handleConn` loops over persistent keep-alive connections by passing the raw underlying `net.Conn` directly to `httpparser.ParseRequest(conn, opts)` on each iteration. Because the previous `bufio.Reader` instance was dropped, any buffered bytes belonging to subsequent pipelined requests are irreversibly lost. On the subsequent iteration, `ParseRequest` creates another new `bufio.Reader(conn)` and attempts to read from the raw kernel TCP socket buffer, which no longer contains the discarded bytes. Consequently, the server either hangs waiting for read deadlines or errors with unexpected EOF / malformed request line syntax errors.

3. **Interactions with Inactivity Deadlines and Stream Upgrades**:
   - **Idle Deadlines**: When pipelined requests have already been ingested into the user-space buffer (`br.Buffered() > 0`), applying socket-level idle read deadlines (`IdleTimeout`) can cause premature timeouts or fail to recognize that pipelined data is immediately available for parsing without waiting on network I/O.
   - **Protocol Upgrades (WebSockets / HTTP Switching Protocols)**: If an HTTP/1.1 request negotiates a protocol upgrade (e.g. `101 Switching Protocols`), any residual unread bytes buffered in `bufio.Reader` must be prepended back onto the raw stream (via `prefixConn`) so the upgraded stream relay (`relayUpgradedStreams`) receives all transmitted frames without data loss.
   - **Error Handling**: When a parser error or security violation occurs, error serialization must write the terminating HTTP response (`Connection: close`) and cleanly terminate the connection loop, disposing of the buffered stream.

---

## 2. Acceptance Criteria

### AC-1: Transparent `*bufio.Reader` Reuse in `ParseRequest`
- In `pkg/httpparser/parser.go`:
  1. `ParseRequest(r io.Reader, opts ParserOptions) (*Request, error)` shall accept any `io.Reader`.
  2. If `r` already implements or can be type-asserted to `*bufio.Reader` (`bufr, ok := r.(*bufio.Reader)`), `ParseRequest` must reuse `bufr` directly without allocating or wrapping it in a new `bufio.NewReader(r)`.
  3. If `r` is not a `*bufio.Reader` (e.g., standard `*bytes.Buffer`, `*strings.Reader`, or custom stream), `ParseRequest` shall wrap `r` in `bufio.NewReader(r)`.
  4. Existing benchmarks and tests calling `ParseRequest` must maintain 100% backward compatibility and zero interface breakage.

### AC-2: Single Persistent `*bufio.Reader` per Connection Lifecycle
- In `pkg/server/server.go` (`handleConn`):
  1. Construct a single persistent `*bufio.Reader` (`br := bufio.NewReader(conn)`) once per connection lifecycle prior to entering the request dispatch loop.
  2. In every iteration of the persistent request loop, pass `br` to `httpparser.ParseRequest(br, opts)`.
  3. Ensure all buffered unconsumed bytes from previous read operations remain intact in `br` across consecutive requests.

### AC-3: Bounded Inactivity & Idle Deadline Management
- In `pkg/server/server.go`:
  1. When determining the read deadline for subsequent requests on a persistent connection:
     - If `br.Buffered() > 0`, buffered pipelined data is immediately ready for consumption; the server must not block or stall on idle timeouts. If `ReadTimeout > 0`, the deadline should be set to `time.Now().Add(s.config.ReadTimeout)`.
     - If `br.Buffered() == 0`, the connection is truly idle awaiting network packets; if `!firstRequest && s.config.IdleTimeout > 0`, the deadline should be set to `time.Now().Add(s.config.IdleTimeout)`.
  2. If `ReadTimeout == 0` and `IdleTimeout == 0`, deadlines remain disabled.

### AC-4: Residual Buffer Preservation on Protocol Upgrades
- In `pkg/server/server.go`:
  1. If a request results in a protocol upgrade (`res.UpgradedConn != nil` or `res.StatusCode == http.StatusSwitchingProtocols`):
     - Check if `br.Buffered() > 0`.
     - If unconsumed bytes remain in `br`, extract them via `unconsumed := make([]byte, br.Buffered()); br.Read(unconsumed)` and wrap `conn` with `prefixConn{Conn: conn, prefix: unconsumed}` before invoking `relayUpgradedStreams(conn, res.UpgradedConn, idleTimeout)`.
     - Ensure no client-sent frames following the HTTP upgrade handshake are dropped.

### AC-5: Error Response Serialization and Socket Teardown
- In `pkg/server/server.go`:
  1. On any parser error (`ErrHeaderTooLarge`, `ErrBodyTooLarge`, `ErrBadRequest`, etc.):
     - The server must format the appropriate error response, set `Connection: close`, serialize the response payload directly to `conn`, and immediately terminate `handleConn`.
     - Socket closure terminates the connection and purges any buffered state.

### AC-6: HTTP/1.1 Pipelining Multi-Request Verification
- Unit and integration tests in `pkg/httpparser` and `pkg/server`:
  1. **Dual Pipelined GET Requests**: Verify that two HTTP/1.1 `GET` requests sent in a single `conn.Write()` call are both parsed, handled, and responded to in strict FIFO order with `200 OK`.
  2. **Multi-Request Pipeline with Body**: Verify that a `POST` request with a `Content-Length` body followed immediately by a `GET` request in the same segment is correctly parsed without body byte leakage or corruption.
  3. **Pipelining with Connection Close**: Verify that if the first request contains `Connection: close`, the connection closes immediately after the first response, discarding subsequent pipelined requests.
  4. **Pipelined Upgrade Preservation**: Verify that data sent immediately after a WebSocket / upgrade request is relayed to the upstream socket without loss.

### AC-7: Zero-Dependency & Race-Clean Invariant
- All modifications must strictly adhere to the Go standard library (`bufio`, `net`, `io`, `time`, `errors`).
- Full test suite execution (`go test -v -race -count=1 ./...`) must pass cleanly with zero data races.

---

## 3. Rationale

HTTP/1.1 pipelining (RFC 7230 §6.3.2) permits clients to send multiple HTTP requests without waiting for each response. While modern browsers rarely enable pipelining by default, high-throughput benchmarking tools (`wrk`, `wrk2`, Lua pipeline scripts), reverse proxy intermediaries, and enterprise API consumers actively rely on pipelining over persistent connections. Recreating `bufio.NewReader` per request is an anti-pattern that evicts buffered data and corrupts connection framing. Reusing a single `*bufio.Reader` per connection restores full RFC 7230 compliance and eliminates socket desynchronization.

---

## 4. Constraints

- Zero third-party dependencies; pure Go standard library implementation.
- API compatibility: `httpparser.ParseRequest(io.Reader, ParserOptions)` signature must remain unchanged to avoid breaking existing callers.
- Memory efficiency: Avoid superfluous buffer allocations by reusing the existing 4 KB buffer across the connection lifetime.
