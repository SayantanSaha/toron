# TC-056 - SPA HTML5 History Fallback Routing Verification

## Description

Verify that Toron's static route handler and configuration engine correctly implement Single Page Application (SPA) HTML5 History fallback routing (equivalent to Nginx's `try_files $uri $uri/ /index.html;`), as specified in [REQ-056](file:///Users/sneha/Developer/toron/docs/requirements/REQ-056.md), [TASK-056](file:///Users/sneha/Developer/toron/docs/tasks/TASK-056.md), and [ADR-051](file:///Users/sneha/Developer/toron/docs/architecture/ADR-051.md).

This test suite validates:
1. Configuration loading and unmarshaling of the `spa` (`bool`) and `fallback` (`string`) fields in `pkg/config`.
2. Serving existing physical assets with their correct MIME types and HTTP 200 OK.
3. Fallback resolution to `index.html` (or custom fallback) for client-side navigation paths lacking file extensions with HTTP 200 OK and `Content-Type: text/html; charset=utf-8`.
4. Asset protection (strict non-masking): returning HTTP 404 Not Found for missing static assets having file extensions (e.g., `.js`, `.css`, `.png`), preventing browser runtime syntax and MIME errors.
5. Backward compatibility: preserving standard HTTP 404 Not Found responses for missing paths when SPA fallback is not enabled.
6. Path traversal and symlink boundary containment enforcement (returning HTTP 404 or HTTP 403).
7. Test suite execution and race detection across packages (`go test ./...` and `go test -race ./...`).

## Preconditions

1. Go 1.22+ installed and workspace dependencies accessible.

3. Router instances initialized with appropriate static route configurations (`spa: true`, custom `fallback`, or SPA disabled).

## Test Scenarios & Detailed Steps

### TC-056.1: Configuration Parsing for SPA Attributes
**Target**: `pkg/config/config_test.go` (`TestConfig_SPARouteConfig`)  
**Objective**: Verify YAML and JSON parsing of `spa` and `fallback` properties into `ProxyRouteConfig`.

#### Steps
1. Create temporary YAML configuration files defining routes with:
   - `spa: true` with default fallback.
   - `spa: true` and `fallback: "app.html"`.
   - `fallback: "portal.html"` without explicit `spa: true`.
   - Standard static route without `spa` or `fallback`.
2. Load configurations using `config.LoadFromFile` and `config.LoadFromFiles`.
3. Assert field values on `cfg.Proxy.Routes`:
   - `Route[0].SPA == true`, `Route[0].Fallback == ""` (or defaults).
   - `Route[1].SPA == true`, `Route[1].Fallback == "app.html"`.
   - `Route[2].Fallback == "portal.html"`.
   - `Route[3].SPA == false`, `Route[3].Fallback == ""`.

#### Expected Results
- Config structs populate `SPA` and `Fallback` fields accurately from YAML definitions without unmarshal errors.

### TC-056.2: Physical File Serving on SPA Routes
**Target**: `pkg/router/router_test.go` (`TestRouter_SPA_PhysicalFileServing`)  
**Objective**: Ensure existing physical assets continue serving directly with optimal status and correct MIME type.

#### Steps
1. Register route prefix `/kite` pointing to fixture directory with `proxy.ProxyOptions{SPA: true, Fallback: "index.html"}`.
2. Issue HTTP `GET /kite/assets/style.css`.
3. Issue HTTP `GET /kite/` (root index).
4. Issue HTTP `GET /kite/dashboard/` (nested directory index).

#### Expected Results
- `GET /kite/assets/style.css` returns HTTP `200 OK`, `Content-Type: text/css; charset=utf-8` (or detected CSS MIME), body equals `body { margin: 0; background: #fafafa; }`.
- `GET /kite/` returns HTTP `200 OK`, body equals `index.html` content.
- `GET /kite/dashboard/` returns HTTP `200 OK`, body equals `dashboard/index.html` content.

## Acceptance Criteria

1. **Deterministic SPA Fallback**: Client-side virtual navigation paths without file extensions return the configured fallback document with HTTP 200 OK and `Content-Type: text/html; charset=utf-8`.
2. **Asset Masking Immunity**: Any missing physical asset request containing a file extension (`filepath.Ext(path) != ""`) yields HTTP 404 Not Found, never returning fallback HTML.
3. **Flexible Fallback Configuration**: Supports default (`index.html`) or custom fallback documents via YAML/JSON configuration.
4. **Security Sandboxing**: All fallback resolution is strictly confined within the configured static root directory, preventing directory traversal.
5. **Zero Regression**: Non-SPA static routes maintain standard 404 behavior; all existing unit and race tests pass cleanly.

---

## Results

PASSED. All tests in `pkg/config` and `pkg/router` passed with 0 failures and 0 race conditions (`go test -v ./pkg/config ./pkg/router` and `go test -race ./pkg/config ./pkg/router`).

## Rationale

Without native SPA fallback, users hosting modern single-page applications (React, Vue, Svelte) on Toron encounter 404 errors upon browser reload or direct URL entry. A naive rewrite mechanism risks asset masking, breaking browser runtime parsing of scripts and stylesheets. This test case validates both the fallback behavior and the asset isolation mechanism, ensuring production-grade SPA hosting reliability.

---

## Constraints

- Static routes and fallback handling strictly permit HTTP `GET` and `HEAD` methods; other methods receive `405 Method Not Allowed`.
- Fallback resolution must only trigger on cache/filesystem misses (`os.IsNotExist(err)`), maintaining optimal throughput on physical hits.
- Fallback document must exist within the static root directory.
