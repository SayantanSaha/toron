# ADR-113 - Heterogeneous Multi-Hop Backend Origin Testbed (BMK-03)

## 1. Context & Problem Statement

Academic peer reviews of Paper 2 (`AER-002` Issue 6, `AR-002` Alternative Explanation 3, and `ReviewTaskSummary.md` item `BMK-03`) exposed a critical architectural and empirical blindspot in Toron's security evaluation:

1. **The Multi-Hop Inter-Node Blindspot**:
   HTTP Request Smuggling is an **inter-node relational vulnerability** ($\mathcal{P}_{\text{edge}} \neq \mathcal{P}_{\text{origin}}$) across shared persistent connection pools ($\mathcal{M}$). Testing Toron in isolation on localhost with synthetic fuzzer probes only observes edge rejection; it does not evaluate whether:
   - Malformed probes bypass edge translation and desynchronize real downstream parsers.
   - Edge transport teardown guarantees zero residual bytes leaking into backend connection pools.
   - Forwarded legitimate traffic remains unpoisoned when multiplexed over persistent connections.

2. **Downstream Engine Diversity**:
   Production backends use fundamentally different HTTP parsing engines with distinct tolerances:
   - **Node.js**: The C-based `llhttp` parser (Node 20 LTS), which strictly enforces chunked framing, header whitespace, and CRLF boundaries.
   - **Python**: ASGI servers (`uvicorn`, `h11`, `httptools` under Python 3.11), interpreting headers according to Python ASGI specs.
   - **Go**: Canonical `net/http` standard library (Go 1.24), normalizing header cases and managing connection pools through `http.Transport`.

---

## 2. Decision

We establish an automated, publication-grade **Heterogeneous Multi-Hop Backend Origin Testbed** (`benchmarks/multihop/`) embodying the following architectural principles:

```
                  ┌────────────────────────────────────────────────────────┐
                  │                 Toron Edge Gateway                     │
                  │             (Multi-Protocol Event Loop)                │
                  └──────┬───────────────────┬────────────────────┬────────┘
                         │                   │                    │
                   /node │             /python │              /go │
                         ▼                   ▼                    ▼
                ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
                │    Node.js     │   │     Python     │   │       Go       │
                │  Node 20 LTS   │   │  Python 3.11   │   │    Go 1.24     │
                │(llhttp parser) │   │ (uvicorn/h11)  │   │  (net/http)    │
                │   Port: 9101   │   │   Port: 9102   │   │   Port: 9103   │
                └────────────────┘   └────────────────┘   └────────────────┘
```

### 2.1 Heterogeneous Backend Topologies
Three dedicated containerized and standalone origin services:
- `benchmarks/multihop/backends/node/`: Node.js 20 LTS HTTP origin (`server.js`, `package.json`, `Dockerfile`).
- `benchmarks/multihop/backends/python/`: Python 3.11 ASGI origin (`server.py`, `requirements.txt`, `Dockerfile`).
- `benchmarks/multihop/backends/go/`: Go 1.24 `net/http` origin (`main.go`, `Dockerfile`).
Each backend provides:
- `GET /health`: Liveness probe returning backend engine metadata.
- `GET /canary`: Canary probe verifying connection pool sequence numbers and absence of residual smuggling bytes.
- `POST /echo`: Request body and header introspection endpoint.

### 2.2 Two-Stage Desynchronization Evaluation Protocol ($r_{\text{poison}} \,\|\, r_{\text{benign}}$)
For each test vector $v \in V$ across each backend runtime $b \in \{\text{Node.js}, \text{Python}, \text{Go}\}$:
1. **Stage 1: Smuggling Probe ($r_{\text{poison}}$)**:
   - Send crafted protocol violation probe through Toron destined for backend $b$.
   - Record edge response status $S_{\text{edge}}$, transport teardown status $T_{\text{closed}}$, and backend received counter $C_1$.
2. **Stage 2: Benign Canary ($r_{\text{benign}}$)**:
   - Transmit benign request `GET /canary` over the connection session.
   - Record canary response status $S_{\text{canary}}$ and canary payload body $B_{\text{canary}}$.
3. **Verdict Assessment**:
   - **Attack Vectors**: Pass if edge blocks ($S_{\text{edge}} \in \{400, 413, 501\}$), transport closes when required, zero residual bytes corrupt backend, and canary yields $200\text{ OK}$ with valid canary payload.
   - **Baseline Vectors**: Pass if edge transparently forwards ($S_{\text{edge}} = 200$), backend processes body intact, and subsequent canary yields $200\text{ OK}$.

### 2.3 Dual Execution Architecture
1. **Live Containerized Mode (`docker-compose.multihop.yml`)**:
   - Runs four containers (`toron-edge`, `node-origin`, `python-origin`, `go-origin`) on an isolated Docker bridge network (`multihop-net`).
   - Invoked via `bash benchmarks/multihop/run_multihop.sh --docker`.
2. **Standalone In-Process Mode (`multihop_test.go`)**:
   - Built with pure Go standard library.
   - Instantiates simulated backend listeners faithfully tracking connection streams, sequence IDs, and raw headers.
   - Boots in-process Toron reverse proxy routes.
   - Executes $10 \times 3 = 30$ full test sequences under `go test -race -count=1 ./benchmarks/multihop/...`.
   - Guarantees 100% CI/CD reproducibility without requiring Docker daemon permissions.

### 2.4 Structured Telemetry Artifacts
- `benchmarks/results/multihop_report.json`: Comprehensive machine-readable execution telemetry.
- `benchmarks/results/multihop_report.md`: Publication-grade Markdown matrix (Vector $\times$ Runtime $\times$ Verdict $\times$ Desync Observed).

---

## 3. Consequences & Invariants

- **Zero Desynchronization**: Desync count must be strictly $0$ across all runtimes.
- **Fail-Fast Isolation**: Rejected connections must not leave lingering unread bytes in upstream connection pools.
- **Zero Third-Party Go Dependencies**: Test runner and simulated harnesses must remain 100% Go standard library.
- **Academic Rigor**: Formally addresses `AER-002` Issue 6 and `AR-002` Alternative Explanation 3.
