# SR-072 - Security Review of Multiple & Conflicting Content-Length Rejection (RFC 7230 §3.3.2)

## Description

Security evaluation of the implementation for `TASK-074` / `SEC-15` (HTTP request smuggling and desynchronization via multiple/conflicting Content-Length headers).

## Scope

- Files reviewed:
  - `pkg/httpparser/request.go`
  - `pkg/httpparser/parser.go`
  - `pkg/httpparser/parser_test.go`

## Security Evaluation & Analysis

1. **RFC 7230 §3.3.2 Compliance**:
   - RFC 7230 §3.3.2 mandates that if a message is received with multiple Content-Length header fields having different field-values, or with a single field containing a list of different values, the recipient MUST reject it with `400 Bad Request`.
   - `req.Header.Values("Content-Length")` now retrieves every occurrence of the header.
   - All comma-separated values within every header occurrence are parsed into integer values.
2. **CL.CL Request Smuggling Elimination (CWE-444)**:
   - Evaluated the scenario where `Content-Length: 0` and `Content-Length: 45` are provided. The parser detects the mismatch between values and immediately returns `ErrBadRequest`.
   - Evaluated comma-separated values (`Content-Length: 10, 20`). Mismatched tokens are immediately rejected.
   - Evaluated duplicate identical headers (`Content-Length: 10` and `Content-Length: 10`). These are safely deduplicated and normalized to a single canonical `Content-Length: 10` header.
3. **Connection Termination**:
   - As with all `ErrBadRequest` errors returned by `ParseRequest`, the server responds with HTTP 400 and sends `Connection: close`, aborting persistent socket reuse so residual bytes cannot be parsed.

## Conclusion

`SEC-15` is fully mitigated. CL.CL HTTP request smuggling vectors are neutralized. Approved.
