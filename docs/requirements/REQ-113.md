# REQ-113 - Heterogeneous Multi-Hop Backend Origin Testbed (BMK-03)

## 1. Description

Academic peer reviews of Paper 2 (`AER-002` Issue 6, `AR-002` Alternative Explanation 3, and `ReviewTaskSummary.md` item `BMK-03`) identified a fundamental methodological blindspot in Toron's security evaluation:

1. **The Multi-Hop Ecological Blindspot**:
   HTTP Request Smuggling and cross-protocol desynchronization are by definition **inter-node relational vulnerabilities** arising from asymmetric grammar interpretation between an edge gateway ($\mathcal{P}_{\text{edge}}$) and an upstream origin parser ($\mathcal{P}_{\text{origin}}$) across shared persistent connection pools ($\mathcal{M}$). In prior evaluations, Toron was evaluated solely in isolation on `127.0.0.1` without live backend origin servers. Academic reviewers emphasized that demonstrating rejection on an isolated edge proxy does not prove that forwarded requests or rejected connections cannot poison real-world backend connection pools.

2. **Downstream Re-Serialization & Protocol Translation**:
   In Toron's reverse proxy (`pkg/proxy/proxy.go`), incoming requests (whether HTTP/1.1 or HTTP/2) are converted and forwarded to upstream servers. Different backend runtimes utilize radically different HTTP parsing engines with distinct tolerances:
   - **Node.js**: Uses the C-based `llhttp` parser (Node.js 20 LTS), which strictly validates chunked extensions and whitespace.
   - **Python**: Uses `h11` / `httptools` under ASGI (Uvicorn / FastAPI), which handles transfer encoding and header boundaries according to Python WSGI/ASGI specifications.
   - **Go**: Uses standard library `net/http`, featuring canonical header normalization and Go runtime connection pooling.

3. **Mandatory Remediation (`BMK-03`)**:
   Toron must establish an automated, reproducible heterogeneous multi-hop evaluation testbed in `benchmarks/multihop/` fronting live Node.js, Python, and Go backends. The harness must execute a two-stage desynchronization evaluation protocol ($r_{\text{poison}} \,\|\, r_{\text{benign}}$) across all three runtimes, empirically proving that:
   - Security rejections tear down transport sockets without leaking residual bytes into backend pools.
   - Forwarded traffic maintains 100% connection pool integrity without response poisoning or desynchronization.
   - Empirical findings are rendered into publication-grade artifacts (`multihop_report.json` and `multihop_report.md`).

## 2. Acceptance Criteria

### AC-1: Heterogeneous Backend Infrastructure & Containerization
- In `benchmarks/multihop/backends/`:
  1. **Node.js Origin (`node`)**:
     - Standalone HTTP server on Node.js 20 LTS (`llhttp` parser engine).
     - Endpoints: `GET /health`, `GET /canary`, `POST /echo`.
     - Maintains request sequence counters, logs received raw headers, and returns connection sequence metadata.
     - Provided with a minimal `Dockerfile` and `server.js`.
  2. **Python Origin (`python`)**:
     - Standalone ASGI/HTTP server on Python 3.11 with Uvicorn (`h11`/`httptools`).
     - Endpoints: `GET /health`, `GET /canary`, `POST /echo`.
     - Tracks request counters, logs headers, and returns connection sequence metadata.
     - Provided with a minimal `Dockerfile`, `requirements.txt`, and `server.py`.
  3. **Go Origin (`go`)**:
     - Standalone HTTP server on Go 1.24 (`net/http` standard library).
     - Endpoints: `GET /health`, `GET /canary`, `POST /echo`.
     - Tracks request counters and connection sequence metadata.
     - Provided with a minimal `Dockerfile` and `main.go`.
  4. **Multi-Hop Orchestration**:
     - Provide `docker-compose.multihop.yml` orchestrating all three backends on an isolated bridge network.
     - Provide `routes.multihop.yaml` routing prefix `/node/*` to Node.js origin, `/python/*` to Python origin, and `/go/*` to Go origin.
     - Provide `config.multihop.yaml` configuring Toron edge gateway reverse proxy policies.

### AC-2: Two-Stage Desynchronization Evaluation Engine ($r_{\text{poison}} \,\|\, r_{\text{benign}}$)
- In `benchmarks/multihop/`:
  1. Implement an automated desynchronization test harness (`multihop_runner.go`) that executes the formal two-stage attack sequence across all three backend origins:
     - **Stage 1 ($r_{\text{poison}}$)**: Transmit a crafted desynchronization probe through Toron destined for the target backend.
     - **Stage 2 ($r_{\text{benign}}$)**: Immediately transmit a pristine canary request (`GET /canary`) over the same socket or connection session.
  2. Implement comprehensive test vectors derived from literature and peer reviews:
     - `VECTOR-01` (H2.TE): HTTP/2 request with `Transfer-Encoding: chunked`.
     - `VECTOR-02` (H2.CL-Duplicate): HTTP/2 request with duplicate conflicting `Content-Length`.
     - `VECTOR-03` (H2.CL-Mismatch): HTTP/2 request with declared `Content-Length` differing from actual payload bytes.
     - `VECTOR-04` (H1-CL.TE): HTTP/1.1 request with both `Content-Length` and `Transfer-Encoding`.
     - `VECTOR-05` (H1-TE.CL-Obfuscated): HTTP/1.1 request with whitespace-obfuscated `Transfer-Encoding : chunked`.
     - `VECTOR-06` (H1-Pipelined-Smuggle): Pipelined request sequence attempting residual buffer injection.
     - `VECTOR-07` (CRLF-Header-Injection): Header containing embedded `\r\n` targeting HTTP/1.1 wire splitting.
     - `VECTOR-08` (Pseudo-Header-Isolation): Translated HTTP/2 request with `:protocol` and pseudo-headers asserting zero leakage to upstream.
     - `VECTOR-09` (Baseline-GET): Benign GET verifying transparent round-trip proxying.
     - `VECTOR-10` (Baseline-POST): Benign POST verifying body integrity and round-trip proxying.

### AC-3: Connection Pool & Response Integrity Invariants
- For every vector executed against each backend origin:
  1. **Edge Enforcement**: Toron must either block malformed vectors ($400$ / $413$ / $501$) or reject with fail-fast transport socket closure (`conn_closed == true`).
  2. **Zero Backend Leakage**: In rejected attack requests, zero smuggled bytes may reach the backend origin parser.
  3. **Canary Verification**: The canary request ($r_{\text{benign}}$) MUST succeed ($200\text{ OK}$), returning the expected canary response without receiving a smuggled response, 400 bad request, or response desynchronization.
  4. **Connection Pool Integrity**: Upstream connection pools must remain unpoisoned across all test runs.

### AC-4: Structured Publication Reporting Artifacts
- In `benchmarks/results/`:
  1. **`multihop_report.json`**: Machine-readable JSON artifact containing full execution telemetry, backend runtimes, vector IDs, edge status codes, socket teardown status, backend sequence counters, and pool integrity verdicts.
  2. **`multihop_report.md`**: Publication-grade GitHub-flavored markdown report featuring:
     - Executive summary of multi-hop evaluation findings.
     - Comprehensive cross-runtime matrix (Vector ID $\times$ Backend Runtime $\times$ Verdict).
     - Formal confirmation of zero desynchronization across Node.js (`llhttp`), Python (`h11`), and Go (`net/http`).

### AC-5: In-Process & Standalone Test Runner Compatibility
- The harness must provide dual execution modes:
  1. **Live Multi-Container Mode**: Connects to live Docker containers orchestrated via `docker-compose.multihop.yml`.
  2. **Automated Standalone Mode**: Provides in-process / local standalone listeners simulating the framing and sequence tracking behaviors of all three backend engines, ensuring `go test ./benchmarks/multihop/...` executes deterministically in any CI/CD environment with zero dependency on Docker daemon availability.

### AC-6: Zero-Dependency & Race-Clean Invariant
- The test harness and runner must strictly use Go standard library packages (`net`, `net/http`, `context`, `sync`, `time`, `encoding/json`, `fmt`).
- 100% clean under `go test -race -count=1 ./...`.

---

## 3. Rationale

Demonstrating immunity to HTTP request smuggling requires evaluating the full multi-hop pipeline. By fronting Toron against three of the most widely deployed production web runtimes—Node.js (`llhttp`), Python (`h11`/Uvicorn), and Go (`net/http`)—Toron empirically refutes the "multi-hop blindspot" critique, verifies that upstream connection pools cannot be corrupted, and proves that fail-fast transport teardown completely isolates backend services from desynchronization.

---

## 4. Constraints

- Pure Go standard library for the benchmark runner and harness.
- Docker containers must be lightweight and build in seconds using official standard base images (`node:20-alpine`, `python:3.11-alpine`, `golang:1.24-alpine`).
- Zero data races under `-race`.
