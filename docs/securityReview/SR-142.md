# SR-142 - Security Review of Defense-in-Depth Authentication and Access Controls for Dashboard and Management APIs

## 1. Executive Summary

The Security Analyst (AGENT-008) has conducted a security architecture review and threat mitigation assessment for the defense-in-depth authentication mechanisms implemented under [`REQ-142`](../requirements/REQ-142.md), [`TASK-165`](../tasks/TASK-165.md), and [`ADR-142`](../architecture/ADR-142.md).

This review addresses the security gaps analyzed in [`AN-001`](../analysis/AN-001.md), evaluating the effectiveness of:
1. **Broken Access Control & Information Disclosure (CWE-200 / CWE-306)**
2. **Timing Side-Channel Vulnerabilities (CWE-208 / CWE-385)**
3. **Insecure Credential Storage & Token Retention (CWE-312 / CWE-922)**
4. **Server-Side Request Forgery & Mutation Hardening (CWE-918)**
5. **CIDR Subnet Enforcement & IP Spoofing Prevention**

Based on rigorous analysis and 100% pass across [`TC-142`](../testCases/TC-142.md) and Go race-detection suites, the security controls are robust, well-isolated, and adhere to zero-trust principles. The security posture is **APPROVED**.

---

## 2. Threat Vector Assessment & Mitigation Verification

### 2.1 Mitigation of Broken Access Control & Information Disclosure (CWE-200 / CWE-306)
- **Problem**: Previously, unauthenticated callers could reach `/internal/api/*` and read sensitive network topology, upstream targets, and transaction logs.
- **Mitigation**: All endpoints under `/internal/api/*` are guarded by `wrapHandler` in `pkg/server/internal_api.go`. When `AdminAuthEnabled` is true, calls without valid administrative credentials are immediately rejected with HTTP `401 Unauthorized` and standard `WWW-Authenticate` challenge headers.
- **Verification**: Verified by unit test `Unauthenticated request returns 401` in `internal_api_test.go` and simulated client interception in `tests/dashboard_telemetry_test.js` (TC-142-06).

### 2.2 Neutralization of Timing Attacks (CWE-208 / CWE-385)
- **Problem**: String equality comparisons (`==`) leak execution time proportional to matching prefix length, enabling remote key extraction via timing statistical analysis.
- **Mitigation**: All token, API key, username, and password evaluations in `validateAdminAuth()` utilize `crypto/subtle.ConstantTimeCompare()`, guaranteeing $O(1)$ constant execution time irrespective of credential match accuracy.
- **Verification**: Code analysis of `pkg/server/internal_api.go:223-264` confirms constant-time comparison across all supported credential formats (`X-Toron-Admin-Key`, Bearer token, and Basic Auth).

### 2.3 Credential Hygiene & Session Scoping (CWE-312 / CWE-922)
- **Problem**: Storing API keys or tokens in persistent `localStorage` exposes them to XSS attacks across domains and persists credentials indefinitely across browser sessions and shared terminal machines.
- **Mitigation**:
  - Administrative credentials reside strictly in memory and `sessionStorage`.
  - Credentials automatically evaporate when the browser tab or window closes.
  - An explicit session lock control (`#authLockBtn`) allows operators to instantly revoke and purge credentials from browser storage.
- **Verification**: Verified by automated test `TC-142-08` in `tests/dashboard_telemetry_test.js`, ensuring `localStorage` is never written to.

### 2.4 Mutation & SSRF Defense Hardening (CWE-918)
- **Problem**: Unauthenticated mutations on firewall rules (`/internal/api/security/ban`, `/internal/api/security/unban`) and arbitrary HTTP request generation (`/internal/api/proxy-test`) present severe denial-of-service and SSRF risks.
- **Mitigation**:
  - Firewall ban/unban mutations require administrative authentication; requests without valid credentials are automatically rejected before invoking the WAF auto-ban manager.
  - Proxy test probes strictly validate against `AllowedProxyTestPaths`, disallowing requests to `/internal/*` management paths, and enforce a 15-second timeout and 1 MB bounded response buffer to prevent socket exhaustion and memory exhaustion attacks.
  - Client view modules (`alerts.js` and `console.js`) route all mutations through `authenticatedFetch()`.
- **Verification**: Verified across `pkg/server/internal_api_test.go` and `tests/dashboard_telemetry_test.js`.

### 2.5 Subnet Policy & IP Filtering
- **Problem**: Compromised administrative tokens could be reused by external attackers from arbitrary internet IP addresses.
- **Mitigation**: In addition to token verification, `AdminSubnets` CIDR filtering blocks any client whose physical or trusted-proxy client IP is not allowlisted, responding with HTTP `403 Forbidden`.
- **Verification**: Verified by `TestInternalAPI_SubnetRestriction` in `pkg/server/internal_api_test.go`.

## 3. Residual Risks & Operational Guidance

1. **HTTPS Enforcement in Production**:
   - In production environments, administrators must configure TLS certificates (either via automated ACME Let's Encrypt or custom certificates in `config.yaml`) so credentials transmitted in `X-Toron-Admin-Key` and `Authorization` headers are protected against transit eavesdropping on untrusted local networks.
2. **Reverse Proxy Header Trust**:
   - When deploying Toron behind upstream layer-7 reverse proxies or load balancers, `trusted_proxies` MUST be configured to prevent client IP spoofing via manipulated `X-Forwarded-For` headers.

## 4. Conclusion & Sign-Off

The defense-in-depth security layer satisfies all security requirements outlined in REQ-142 and ADR-142. Zero high- or medium-severity security issues remain open.

**Security Sign-Off**: **APPROVED**.
