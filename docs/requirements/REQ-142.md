# REQ-142 - Defense-in-Depth Authentication and Access Control for Control Center Dashboard and Management APIs

## 1. Description & Problem Statement

### 1.1 Context & Background
As analyzed in [`AN-001`](../analysis/AN-001.md), default installations of the Toron Edge Gateway serve the web-based Control Center dashboard at `/internal/dashboard` and its backing management APIs (`/internal/api/*`) without mandatory access controls. Unauthenticated network actors can view sensitive routing configurations, upstream topologies, live transaction logs, and WAF security anomalies, as well as execute mutations (banning/unbanning IP addresses and executing diagnostic route probes).

Furthermore, when an administrator enables `admin_auth` in `config.yaml`, the backend returns `401 Unauthorized` for all `/internal/api/*` endpoints, but the frontend dashboard (`public/js/`) lacks a credential prompt or authentication handling mechanism, causing the dashboard to silently fail and fall back to static demo data.

### 1.2 Objective & Solution Approach
Implement a **Defense-in-Depth Hybrid Authentication** architecture:
1. **Multi-Scheme Backend Verification**: Enforce access control across `/internal/api/*` supporting Admin Token (`X-Toron-Admin-Key`), Bearer Token (`Authorization: Bearer <token>`), and HTTP Basic Authentication (`Authorization: Basic <base64>`), alongside CIDR subnet allowlisting (`admin_subnets`).
2. **Interactive Dashboard Authentication Modal**: In the frontend SPA, intercept `401 Unauthorized` responses and present an in-page **Admin Authentication Modal** allowing operators to supply their Admin API Key or Bearer Token.
3. **Seamless Credential Injection**: Automatically attach active credentials to all background telemetry polling cycles (`fetchBackendData`) and management action requests (`ban`, `unban`, `proxy-test`).
4. **Session Scoping & Lockout Control**: Retain credentials in volatile browser `sessionStorage` (cleared when the browser tab closes) and provide an explicit "Lock / Switch Key" action in the navigation chrome.
5. **Configurable Static Route Protection**: Allow optional route-level Basic Auth or token protection directly on `/internal/dashboard` in `routes.yaml`.

## 2. Functional Requirements

### 2.1 Backend Management API Security
- **REQ-142.1: Multi-Scheme Credential Verification**:
  All endpoints under `/internal/api/*` MUST validate incoming requests against configured administrative credentials when administrative authentication is enabled (`AdminAuthEnabled`):
  - `X-Toron-Admin-Key` header matching `AdminToken` or any key in `AdminAPIKeys`.
  - `Authorization: Bearer <token>` matching `AdminToken` or any key in `AdminAPIKeys`.
  - `Authorization: Basic <base64>` matching configured username and password in `AdminUsername`/`AdminPassword` or `AdminUsers`.
- **REQ-142.2: Standardized 401 Challenge Responses**:
  When a request to `/internal/api/*` lacks valid credentials and authentication is required:
  - The server MUST respond with HTTP `401 Unauthorized`.
  - The server MUST include the header:
    ```http
    WWW-Authenticate: Bearer realm="Toron Management", Basic realm="Toron Management"
    ```
  - The response payload MUST return a structured JSON error:
    ```json
    {"error":"401 Unauthorized","message":"Authentication required for internal management API"}
    ```
- **REQ-142.3: Subnet Allowlisting Enforcement**:
  When `AdminSubnets` are configured:
  - The server MUST evaluate the physical or trusted-proxy client IP against allowed CIDR blocks.
  - Non-matching clients MUST receive HTTP `403 Forbidden` with:
    ```json
    {"error":"403 Forbidden","message":"Access denied by administrative subnet policy"}
    ```

### 2.2 Frontend Client Security & Authentication Lifecycle
- **REQ-142.4: 401 Response Interception & Auth Trigger**:
  In [`public/js/api.js`](../../public/js/api.js), if any `/internal/api/*` request receives HTTP `401 Unauthorized`:
  - The background poller MUST pause automatic interval polling.
  - The application MUST emit an authentication-required signal and display the **Admin Authentication Modal**.
- **REQ-142.5: Interactive Authentication Modal Component**:
  The dashboard MUST feature an accessible, responsive in-page modal dialog:
  - Form fields: Admin API Key / Token input field (masked/password style with reveal toggle).
  - Actions: "Authenticate" (primary) and "Continue in Demo Mode" (optional fallback view).
  - Validation: When submitted, the client attempts a probe request to `GET /internal/api/status` with the provided credential.
  - Error feedback: Invalid credentials display an inline error alert (`Invalid Admin Key`).
  - Success feedback: On successful verification, the modal dismisses, the credential is saved into the active session, and polling immediately resumes.
- **REQ-142.6: Automatic Credential Header Injection**:
  All client-to-server HTTP requests (`public/js/api.js`, `alerts.js`, `console.js`) MUST automatically attach active credentials:
  - If a token is stored in the session, attach `X-Toron-Admin-Key: <token>` and `Authorization: Bearer <token>`.
  - Set `credentials: 'same-origin'` on all `fetch()` calls to permit browser-cached HTTP Basic Auth credentials to pass automatically.
- **REQ-142.7: Secure Session Scoping & Logout**:
  - Administrative credentials MUST NOT be stored in persistent `localStorage`.
  - Credentials MAY be stored in memory and `sessionStorage` (scoped strictly to the current tab session).
  - A "Lock / Switch Key" action MUST be added to the dashboard sidebar/chrome, allowing the operator to clear stored credentials and re-lock the control center.

## 3. Non-Functional Requirements

- **REQ-142.8: Zero External Frontend Dependencies**:
  The authentication modal, state management, and HTTP interceptors MUST be implemented purely in native ES modules and vanilla CSS within the existing `public/js/` directory structure.
- **REQ-142.9: Backward Compatibility with Unauthenticated Dev Mode**:
  If administrative authentication is explicitly disabled (`admin_auth.enabled: false`, no token, no keys), `/internal/api/*` endpoints MUST remain accessible without credentials, and the frontend MUST NOT prompt for authentication.
- **REQ-142.10: Strictly Relative Links**:
  All documentation and code links MUST strictly use relative links (`../...`, `./...`). Never use absolute filesystem paths.

## 4. Acceptance Criteria

- [x] **AC-1 (Unauthenticated Rejection)**:
  - **Given** administrative auth is enabled (`AdminAuthEnabled: true`),
  - **When** an unauthenticated client requests `GET /internal/api/status`,
  - **Then** the server responds with HTTP `401 Unauthorized` and `WWW-Authenticate` challenge headers.

- [x] **AC-2 (Token & Key Authentication)**:
  - **Given** an admin token is configured,
  - **When** a client supplies `X-Toron-Admin-Key: <token>` or `Authorization: Bearer <token>`,
  - **Then** the request is accepted with HTTP `200 OK` and returns telemetry JSON.

- [x] **AC-3 (Basic Authentication)**:
  - **Given** admin users are configured,
  - **When** a client supplies valid HTTP Basic credentials,
  - **Then** the request is accepted with HTTP `200 OK`.

- [x] **AC-4 (Frontend 401 Interception & Modal)**:
  - **Given** administrative auth is enabled and the dashboard has no saved session token,
  - **When** the dashboard loads `/internal/dashboard/`,
  - **Then** the 401 response from `/internal/api/status` triggers the Admin Authentication Modal.

- [x] **AC-5 (Successful Frontend Authentication Flow)**:
  - **Given** the Admin Authentication Modal is displayed,
  - **When** the user enters a valid admin key and clicks "Authenticate",
  - **Then** the key is verified, stored in `sessionStorage`, the modal closes, and live telemetry renders across all views.

- [x] **AC-6 (Secured Mutations)**:
  - **Given** administrative auth is enabled,
  - **When** a user performs an IP ban in Alerts or executes a proxy probe in API Console,
  - **Then** the request includes the admin credentials and succeeds; unauthenticated mutation requests return HTTP 401.

- [x] **AC-7 (Session Lock / Logout)**:
  - **Given** an authenticated dashboard session,
  - **When** the operator clicks "Lock / Switch Key",
  - **Then** session credentials are removed, polling pauses, and the authentication modal reappears.

- [x] **AC-8 (Subnet Policy Rejection)**:
  - **Given** `admin_subnets` is set to `127.0.0.1/32`,
  - **When** a request originates from an untrusted IP (e.g., `192.168.1.50`),
  - **Then** the server immediately rejects the request with HTTP `403 Forbidden`.
