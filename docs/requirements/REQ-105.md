# REQ-105 - In-Process HTTP Parser Microbenchmarks for Fail-Fast Rejection Latency

## 1. Description

Peer review evaluation (`TST-05`, `AER-002`, `PDR-002`) identified a critical methodological discrepancy in the empirical evaluation of Toron's HTTP security mechanisms. Previously, invariant rejection latencies were only measured over loopback TCP sockets (`127.0.0.1`) in `benchmarks/fuzzer/diff_fuzzer.go`. This reported a mean rejection latency of approximately 298.88 $\mu$s, which conflated operating system TCP socket buffer allocation, network stack round-trip time, TCP handshake/teardown mechanics, and Go runtime goroutine scheduling with pure HTTP parser state machine execution time.

To resolve this ambiguity and empirically prove the sub-microsecond fail-fast invariant of Toron's state machine, the system shall provide in-process Go parser microbenchmarks (`testing.B`) in `pkg/httpparser/parser_test.go`. The microbenchmarks must isolate in-memory parsing execution from transport-layer overhead, measure heap allocations (`b.ReportAllocs()`), and utilize zero-allocation reader resetting (`bytes.NewReader` initialized outside the timing loop and reset via `r.Reset(payload)` on each iteration) to eliminate benchmark harness allocation artifacts.

## 2. Acceptance Criteria

### AC-1: RFC 7230 §3.2.4 Header Whitespace Rejection Benchmark
- The test suite shall implement `BenchmarkParseRequest_WhitespaceRejection(b *testing.B)` in `pkg/httpparser/parser_test.go`.
- The benchmark shall feed malformed HTTP requests containing illegal whitespace (space or horizontal tab) preceding the colon in a header field-name (e.g. `Host : example.com` or `Transfer-Encoding : chunked`).
- The benchmark shall measure nanosecond-level fail-fast termination before request body processing.

### AC-2: RFC 7230 §3.3.2 Conflicting Multiple Content-Length Rejection Benchmark
- The test suite shall implement `BenchmarkParseRequest_MultipleCL(b *testing.B)` in `pkg/httpparser/parser_test.go`.
- The benchmark shall feed requests containing conflicting multiple `Content-Length` headers (e.g. `Content-Length: 5` and `Content-Length: 10`).
- The benchmark shall verify rapid rejection upon header validation prior to reading or buffering the payload body.

### AC-3: Valid RFC 7230 HTTP/1.1 Request Baseline Benchmark
- The test suite shall implement `BenchmarkParseRequest_ValidBaseline(b *testing.B)` in `pkg/httpparser/parser_test.go`.
- The benchmark shall measure the baseline parsing latency and memory allocation profile of a well-formed RFC 7230 HTTP/1.1 GET request to provide an empirical ablation comparator against malformed rejection paths.

### AC-4: Zero-Allocation Harness Resetting Invariant
- All benchmark functions shall report heap allocations via `b.ReportAllocs()`.
- Benchmark loops shall initialize reader instances outside `b.ResetTimer()` and invoke `r.Reset(payload)` on each iteration (`for i := 0; i < b.N; i++`), ensuring zero heap allocations originate from reader instantiation inside the timed section.

### AC-5: Zero External Dependency Compliance
- The implementation shall depend strictly on the Go standard library (`testing`, `bytes`, `toron/pkg/httpparser`), preserving the project's zero-third-party-dependency invariant.

## 3. Rationale

Loopback TCP latency measurements overstate pure state machine execution time by over three orders of magnitude (~298 $\mu$s vs <1 $\mu$s). Establishing standard in-process microbenchmarks enables reproducible, nanosecond-precision ablation analysis across valid baseline parsing and defensive rejection paths, satisfying academic artifact evaluation standards (USENIX Security / ACM CCS).

## 4. Constraints

- Must not alter production parser behavior in `pkg/httpparser/parser.go`.
- Must execute cleanly within standard Go tooling: `go test -bench=BenchmarkParseRequest -benchmem ./pkg/httpparser/...`.
- Must remain race-clean (`go test -race -count=1 ./pkg/httpparser/...`).
