# TC-127 - Verification of Explicit Client Socket TCP_NODELAY Configuration and Serialization Buffer Recycling

## 1. Test Suite Overview & Architectural Objectives

### 1.1 Executive Summary & Problem Context
In the multi-proxy differential benchmark ([`REQ-121`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-121.md)), industry-standard reverse proxies NGINX (~34.1k RPS) and HAProxy (~32.3k RPS) demonstrated a throughput and latency advantage over Toron (~24.5k RPS). Comprehensive socket telemetry, kernel tracepoints, and runtime CPU profiling (`pprof`) under [`REQ-127`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-127.md) uncovered two foundational architectural gaps in Toron's socket lifecycle and HTTP response formatting pipelines:

1. **Implicit TCP Socket Options & Catastrophic Nagle Buffering Latency**:
   - In [`pkg/reactor/reactor.go:178`](file:///Users/sneha/Developer/toron-research/toron/pkg/reactor/reactor.go#L178), Toron accepts incoming client sockets via `ln.Accept()` without explicitly configuring transport-layer socket options.
   - Sockets default to operating system standard behavior with **Nagle's algorithm (RFC 896)** enabled. Nagle inhibits congestion by holding outgoing segments smaller than the Maximum Segment Size (MSS, ~1460 bytes) in the kernel send buffer until an acknowledgment (ACK) is received for earlier segments.
   - Concurrently, modern client TCP stacks implement the **TCP Delayed Acknowledgment algorithm (RFC 1122 §4.2.3.2)**, which deliberately delays sending ACKs by 40ms to 200ms when waiting for piggybacked application return traffic.
   - For interactive HTTP microservices (small JSON payloads, health-check probes) and especially for **real-time streaming architectures** (such as Server-Sent Events / SSE `text/event-stream` enabled in [`REQ-125`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-125.md) and [`TASK-148`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-148.md)), event updates are emitted as small text frames (e.g. `data: {"id":123,"status":"running"}\n\n`), typically 20 to 200 bytes in size.
   - Without `TCP_NODELAY`, each individual SSE event frame stalls in the kernel send queue waiting for the client's 40ms–200ms delayed-ACK timer to expire, destroying real-time streaming fidelity and inflating P90/P99 latency percentiles.

2. **Half-Open Socket Leaks During Quiet Streaming Intervals ([CWE-400](https://cwe.mitre.org/data/definitions/400.html))**:
   - Persistent streaming connections (SSE, live telemetry feeds, long-polling HTTP/1.1 sessions) frequently endure quiet intervals between event emissions.
   - If a client abruptly disappears without an orderly TCP FIN/RST handshake (e.g., laptop lid close, mobile cellular handover, or silent stateful NAT timeout), the socket enters a half-open state.
   - Without explicit TCP keep-alive configuration (`SetKeepAlive(true)` and `SetKeepAlivePeriod(60s)`), the server reactor cannot detect dropped sockets during quiet periods, pinning worker goroutines, upstream proxy connections, and file descriptors indefinitely.

3. **Response Serialization Heap Allocations & GC Pause Churn**:
   - In [`pkg/httpparser/response.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/response.go), formatting HTTP/1.1 status lines and headers in `res.Serialize(conn)` dynamically allocated temporary buffers or string conversions.
   - At 24.5k RPS, this generates **~24,500 heap allocations per second**, triggering garbage collection (GC) pause spikes, cache line evictions, and tail latency degradation.

### 1.2 The Explicit Socket Tuning & Slab Recycling Paradigm
To resolve these bottlenecks while strictly preserving Toron's zero third-party dependency model, [`ADR-127`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-127.md) and [`TASK-150`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-150.md) formulate an integrated three-pillar engineering architecture:

1. **Recursive Socket Unwrapping & Transport Tuning (`ExtractTCPConn` & `ConfigureTCPSocket`)**:
   - Implement an iterative socket unwrapper [`ExtractTCPConn`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go) that traverses through arbitrary wrapper hierarchies (including `*tls.Conn` via `NetConn()`, [`connDeadlineTracker`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/deadline.go) via `Unwrap()`, and `prefixConn` via `Unwrap()`) to extract the base `*net.TCPConn`.
   - Implement [`ConfigureTCPSocket`](file:///Users/sneha/Developer/toron-research/toron/pkg/reactor/reactor.go) to enforce `SetNoDelay(true)`, `SetKeepAlive(true)`, and `SetKeepAlivePeriod(60 * time.Second)` immediately upon connection acceptance in `pkg/reactor` and safeguarded in `pkg/server`.
2. **WebSocket-Aligned SSE Real-Time Streaming Synergy (`res.StreamBody`)**:
   - Pair `TCP_NODELAY` with the WebSocket-aligned `res.StreamBody` streaming hand-off model ([`REQ-125`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-125.md)), guaranteeing that discrete SSE text frames reach the wire immediately ($< 1\text{ms}$) without kernel buffering stalls.
   - TCP keep-alive probes actively patrol quiet streaming connections, tearing down dead sockets within 60s without server resource leaks.
3. **Zero-Allocation Buffer Slab Recycling (`responseBufPool`)**:
   - Deploy a high-speed `sync.Pool` buffer slab [`responseBufPool`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/response.go) providing recycled 4KB (`*[]byte`) byte slices for status line and header formatting.
   - Combine static status line byte constants (`statusLine200`, `statusLine404`, etc.), fast integer formatting via `strconv.AppendInt`, and fast zero-allocation CRLF checking (`strings.IndexByte`) with a zero-copy dual-write wire emission path, achieving $\le 1$ alloc/op in `res.Serialize`.

### 2.3 Mathematical Model, Physical Invariants & Latency Physics

#### 1. Nagle's Algorithm vs. TCP Delayed ACK Latency Equation
Let $S_{\text{MSS}}$ denote the TCP Maximum Segment Size (~1460 bytes).
Let $L$ denote the payload length of an outgoing application frame (e.g. an SSE event frame where $L \approx 30\text{ bytes}$).
Let $U$ denote the volume of outstanding unacknowledged data in flight.

Under Nagle's algorithm (RFC 896), the socket transmission condition is:
$$\text{TransmitImmediate} \iff (U == 0) \lor (L \ge S_{\text{MSS}})$$

When an SSE stream transmits Frame 1, $U = 0$, so Frame 1 is sent immediately.
The client TCP stack receives Frame 1 and arms its Delayed ACK timer per RFC 1122 §4.2.3.2:
$$T_{\text{delack}} \in [40\text{ms}, 200\text{ms}]$$

When the server generates Frame 2 shortly thereafter ($T_{\text{gen}} \approx 2\text{ms}$):
$$U > 0 \quad \text{and} \quad L < S_{\text{MSS}}$$

Therefore, Nagle's algorithm **blocks** Frame 2 in the kernel send buffer. The total delivery latency $T_{\text{delivery}}$ for Frame 2 is bounded by the client delayed ACK expiration:
$$T_{\text{delivery}} = T_{\text{gen}} + T_{\text{delack}} \approx 42\text{ms} \text{ to } 202\text{ms}$$

By setting `TCP_NODELAY` (`SetNoDelay(true)`), Nagle's condition is bypassed:
$$\forall L > 0: \quad \text{TransmitImmediate} \equiv \text{True}$$
$$T_{\text{delivery}} = T_{\text{gen}} + \frac{\text{RTT}}{2} \approx 2.1\text{ms}$$
This eliminates $> 98\%$ of the transmission stall, stabilizing streaming throughput and P99 latency.

#### 2. Response Serialization Memory Allocation Bound
Let $A$ denote the number of dynamic heap allocations executed during `res.Serialize(w)`.
Let $H_{\text{size}}$ denote the byte size of formatted status lines and headers.

Under the naive implementation:
$$A_{\text{naive}} \ge 4 \quad (\text{bytes.Buffer struct, backing array grow, status line string, header keys})$$

Under `responseBufPool` with 4KB slab recycling:
$$\forall H_{\text{size}} \le 4096: \quad A_{\text{pooled}} \le 1.0 \quad (\le 1 \text{ for io.Writer interface boxing, 0 on hot-path})$$

### TC-127.1: Underlying Socket Extraction & Unwrapping (`ExtractTCPConn`)

- **Traceability**: [`REQ-127 §2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-127.md#L75-L83), [`TASK-150 Subtask 1.1`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-150.md#L99-L131), [`ADR-127 §2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-127.md#L128-L170).

  - In-memory pipe (`net.Pipe()`) representing a non-TCP connection.
- **Action**:
  - **Subtest 1A (Direct TCP Connection)**:
    1. Accept raw connection `rawConn` from TCP listener.
    2. Invoke `tcpConn := ExtractTCPConn(rawConn)`.
    3. Assert `tcpConn != nil`.
    4. Assert `tcpConn == rawConn.(*net.TCPConn)`.
  - **Subtest 1B (Standard TLS Connection Simulation)**:
    1. Create wrapper `tlsMock` wrapping `rawConn` with method `NetConn() net.Conn`.
    2. Invoke `tcpConn := ExtractTCPConn(tlsMock)`.
    3. Assert `tcpConn != nil` and points to the base `rawConn`.
  - **Subtest 1C (Deadline Tracker Wrapper)**:
    1. Wrap `rawConn` with `tracker := newConnDeadlineTracker(rawConn)`.
    2. Invoke `tcpConn := ExtractTCPConn(tracker)`.
    3. Assert `tcpConn != nil` and matches the base `rawConn`.
  - **Subtest 1D (HTTP/2 Prefix Connection Wrapper)**:
    1. Wrap `rawConn` with `pConn := &prefixConn{Conn: rawConn, prefix: []byte("PRI")}`.
    2. Invoke `tcpConn := ExtractTCPConn(pConn)`.
    3. Assert `tcpConn != nil` and matches the base `rawConn`.
  - **Subtest 1E (Multi-Level Nested Wrappers)**:
    1. Construct 4-level wrapper chain:
       `tracker` wraps `pConn` wraps `tlsMock` wraps `rawConn`.
    2. Invoke `tcpConn := ExtractTCPConn(tracker)`.
    3. Assert `tcpConn != nil` and correctly unwraps through all 4 layers to `rawConn`.
  - **Subtest 1F (Non-TCP and Edge Cases)**:
    1. Pipe connection: `c1, _ := net.Pipe()`. Assert `ExtractTCPConn(c1) == nil`.
    2. Nil check: Assert `ExtractTCPConn(nil) == nil`.
    3. Custom opaque struct implementing `net.Conn` without unwrap methods: Assert returns `nil` safely without panic.
- **Expected Outcomes**:
  - `ExtractTCPConn` returns genuine `*net.TCPConn` pointer across all single and multi-level wrappers.
  - Returns `nil` cleanly for non-TCP connections and `nil` parameters.
  - Zero panics or infinite recursion loops.

### TC-127.5: Immediate Small Frame Wire Delivery (SSE Nagle Elimination)
- **Identifier**: `TC-127.5`
- **Target Subsystem**: Real-Time Streaming & Socket Layer ([`pkg/server/server.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go), [`pkg/httpparser/response.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/httpparser/response.go))

- **Objective**: Verify that small Server-Sent Events frames (30 bytes each) emitted sequentially across a persistent HTTP/1.1 streaming connection arrive at the client immediately with $< 15\text{ms}$ inter-frame latency, completely eliminating the 40ms–200ms delayed-ACK stall caused by Nagle's algorithm.
- **Traceability**: [`REQ-127 §1.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-127.md#L54-L57), [`REQ-127 §2.1`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-127.md#L84-L87), [`TASK-150 Subtask 3.2`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-150.md#L273-L281), [`ADR-127 §1.2`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-127.md#L51-L95), [`ADR-127 §3.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-127.md#L368-L406).
- **Setup & Preconditions**:
  - Toron server running on localhost TCP port.
  - Endpoint `GET /sse-fast` registered, emitting 5 discrete SSE frames via an `io.Pipe`:
    - Frame 1 ($T = 0\text{ms}$): `data: {"seq":1}\n\n` (20 bytes)
    - Frame 2 ($T = 2\text{ms}$): `data: {"seq":2}\n\n` (20 bytes)
    - Frame 3 ($T = 4\text{ms}$): `data: {"seq":3}\n\n` (20 bytes)
    - Frame 4 ($T = 6\text{ms}$): `data: {"seq":4}\n\n` (20 bytes)
    - Frame 5 ($T = 8\text{ms}$): `data: {"seq":5}\n\n` (20 bytes)
  - Upstream handler writes each frame with `2ms` sleep in between.
- **Action**:
  1. Test client establishes raw TCP connection (`net.Dial("tcp", srvAddr)`).
  2. Client transmits `GET /sse-fast HTTP/1.1\r\nHost: localhost\r\n\r\n`.
  3. Client reads status line and headers (`Content-Type: text/event-stream`).
  4. Client enters frame read loop:
     - Read Frame 1, record timestamp $T_1$.
     - Read Frame 2, record timestamp $T_2$.
     - Read Frame 3, record timestamp $T_3$.
     - Read Frame 4, record timestamp $T_4$.
     - Read Frame 5, record timestamp $T_5$.
  5. Calculate inter-frame arrival intervals:
     $$\Delta T_{1\to 2} = T_2 - T_1, \quad \Delta T_{2\to 3} = T_3 - T_2, \quad \Delta T_{3\to 4} = T_4 - T_3, \quad \Delta T_{4\to 5} = T_5 - T_4$$
  6. Assert that for every interval $k \in \{1, 2, 3, 4\}$:
     $$\Delta T_k \le 15\text{ms}$$
  7. Assert total time for all 5 frames is $< 30\text{ms}$.
- **Expected Outcomes**:
  - Every individual frame is received within $< 15\text{ms}$ of its emission.
  - Total elapsed time for all 5 frames is $< 30\text{ms}$.
  - Under Nagle without `TCP_NODELAY`, total time would exceed $160\text{ms} - 800\text{ms}$ ($4 \times 40\text{ms}$ delayed ACK).
  - Proves `TCP_NODELAY` is active and completely eliminates Nagle buffering stalls.
