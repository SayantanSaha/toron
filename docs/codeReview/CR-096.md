# CR-096 - Code Review of RFC 8555 Token Syntax & Length Validation and HTTP Method Hardening in ACME HTTP-01 Challenge Handler (SEC-38)

## Review Summary

- **Components Reviewed**:
  - [`pkg/acme/acme.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L200-L262): Implementation of public zero-allocation token validator [`IsValidACMEToken(token string) bool`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L202-L218) enforcing [RFC 8555 §8.3](https://datatracker.ietf.org/doc/html/rfc8555#section-8.3) base64url characters and $1 \le \text{len} \le 128$; hardened [`ACMEManager.ServeHTTP01Handler`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L222-L262) restricting HTTP methods to `GET` and `HEAD` with `405 Method Not Allowed`, removing silent whitespace trimming, enforcing fail-fast `400 Bad Request` prior to map lock acquisition, implementing RFC 7231 `HEAD` method semantics (`res.Body.Len() == 0`, `Content-Length` populated), and clean `404 Not Found` responses.
  - [`pkg/acme/acme_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme_test.go#L100-L672): Comprehensive automated test suite implementing `TC-100-01` through `TC-100-09` and dedicated validator tests (`TestACME_IsValidACMEToken`), validating GET success, empty tokens, length boundaries, invalid character rejections, path traversal rejections, HTTP 405 method enforcement, HEAD semantics, 404 handling, and high-concurrency race freedom.
  - `go.mod` / `go.sum`: Verification of zero third-party dependencies (100% pure Go standard library).
- **Security & Architectural Invariant Verifications**:
  - **Zero-Allocation Byte-Level Validation**: `IsValidACMEToken` performs an in-place single-pass byte scan over the token string without heap allocations ($O(1)$ auxiliary space, $O(N)$ time), rejecting any character outside `[a-zA-Z0-9_-]`.
  - **Removal of Silent Whitespace Sanitization**: Removed `strings.TrimSpace(token)`, ensuring tokens with leading, trailing, or embedded whitespace strictly trigger `400 Bad Request`.
  - **HTTP Method Restricton & RFC 7231 §6.5.5 Compliance**: Disallowed methods (`POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `CONNECT`, `TRACE`) immediately yield `405 Method Not Allowed` with mandatory headers `Allow: GET, HEAD` and `Content-Type: text/plain`.
  - **Fail-Fast Map & Lock Isolation (CWE-20 / CWE-400)**: Method validation and syntax/length validation execute before invoking `m.GetHTTP01Challenge(token)`, eliminating reader lock acquisition (`m.mu.RLock()`) and hash computation on invalid external requests.
  - **RFC 7231 §4.3.2 HEAD Semantics**: Valid `HEAD` requests return status `200 OK`, `Content-Type: text/plain`, and exact `Content-Length`, while strictly omitting the response body (`res.Body.Len() == 0`).
  - **Zero Third-Party Dependencies**: Pure Go standard library (`crypto/*`, `net/http`, `strconv`, `strings`, `sync`, `time`, and internal `toron/pkg/httpparser`).
  - **Concurrency Safety & Race Freedom**: All reads and writes to `m.http01Tokens` are thread-safe under `m.mu` (`sync.RWMutex`), and `IsValidACMEToken` is pure and stateless.
- **Verdict**: **APPROVED (Status: approved)**.

### Background & Root Cause Analysis (SEC-38 / CWE-20, CWE-400, CWE-703)

During security audit [`SR-091 Finding 8`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L235-L251) and vulnerability tracking [`SEC-38`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L539-L547) ([CWE-20: Improper Input Validation](https://cwe.mitre.org/data/definitions/20.html), [CWE-400: Uncontrolled Resource Consumption](https://cwe.mitre.org/data/definitions/400.html), [CWE-703: Improper Handling of Exceptional Conditions](https://cwe.mitre.org/data/definitions/703.html)), multiple architectural and protocol compliance flaws were identified in Toron's ACME HTTP-01 challenge responder handler ([`pkg/acme/acme.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go)).

Previously, `ServeHTTP01Handler` was implemented as:

```go
// Vulnerable implementation prior to TASK-123
func (m *ACMEManager) ServeHTTP01Handler(req *httpparser.Request, res *httpparser.Response) {
    token := strings.TrimPrefix(req.Path, "/.well-known/acme-challenge/")
    token = strings.TrimSpace(token)

    keyAuth, exists := m.GetHTTP01Challenge(token)
    if !exists {
        res.SetStatus(http.StatusNotFound)
        res.Header.Set("Content-Type", "text/plain")
        _, _ = res.WriteString("404 ACME Challenge Token Not Found")
        return
    }

    res.SetStatus(http.StatusOK)
    res.Header.Set("Content-Type", "text/plain")
    _, _ = res.WriteString(keyAuth)
}
```

### Vulnerability Analysis & Structural Flaws

1. **Unvalidated Token Querying & Core Lock Contention (CWE-20, CWE-400)**:
   The handler extracted the trailing segment of `req.Path` and directly invoked `m.GetHTTP01Challenge(token)`. This acquired a read lock (`m.mu.RLock()`) over `m.http01Tokens` for any arbitrary, potentially adversarial string payload received from external clients. An external attacker could flood the endpoint with randomized or multi-megabyte paths, inducing hash calculation overhead, CPU churn, and lock contention on the gateway's core lock.
2. **Violation of RFC 8555 §8.3 Base64URL Character Set Restrictions**:
   Under [RFC 8555 §8.3](https://datatracker.ietf.org/doc/html/rfc8555#section-8.3), ACME HTTP-01 challenge tokens MUST consist strictly of characters from the unpadded base64url alphabet ([RFC 4648 §5](https://datatracker.ietf.org/doc/html/rfc4648#section-5)):
   $$\text{Alphabet} = \{ \text{'a'-'z'}, \text{'A'-'Z'}, \text{'0'-'9'}, \text{'-'}, \text{'_'} \}$$
   Characters including base64 padding (`=`), path separators (`/`, `\`), directory traversal tokens (`..`), symbols (`@`, `+`, `*`), whitespace, control characters (`0x00`-`0x1F`), and UTF-8 multi-byte sequences were accepted without validation.
3. **Unbounded Input Length (CWE-400)**:
   Standard ACME challenge tokens contain bounded entropy (typically 128 bits represented in 22 or 43 base64url characters, capped at 128 characters). The prior handler accepted arbitrary string sizes, allowing large payloads to trigger map hashing and heap churn.
4. **Permissive HTTP Method Acceptance (RFC 8555 Non-Compliance)**:
   Non-idempotent or arbitrary HTTP verbs (`POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `CONNECT`, `TRACE`) were processed identically to `GET`, returning `200 OK` and leaking challenge responses on arbitrary methods.
5. **Missing RFC 7231 `HEAD` Support**:
   [RFC 8555 §8.3](https://datatracker.ietf.org/doc/html/rfc8555#section-8.3) and [RFC 7231 §4.3.2](https://datatracker.ietf.org/doc/html/rfc7231#section-4.3.2) permit automated CA validation probes to execute `HEAD` requests to verify status and headers without receiving the body. The prior handler unconditionally wrote the response body string, violating RFC 7231.
6. **Silent Whitespace Forgiveness**:
   Calling `strings.TrimSpace(token)` masked malformed tokens with whitespace. Under RFC 8555, whitespace in tokens is invalid and must be rejected with `400 Bad Request`.

## Detailed Code Review & Invariant Analysis

### 1. Zero-Allocation RFC 8555 Base64URL & Length Validator (`IsValidACMEToken`)

- **Implementation**:
  [`pkg/acme/acme.go:200-218`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L200-L218):
  ```go
  // IsValidACMEToken reports whether token conforms strictly to RFC 8555 §8.3 base64url alphabet without padding.
  // Valid tokens must satisfy 1 <= len(token) <= 128 and contain only characters [a-zA-Z0-9_-].
  func IsValidACMEToken(token string) bool {
  	n := len(token)
  	if n < 1 || n > 128 {
  		return false
  	}
  	for i := 0; i < n; i++ {
  		b := token[i]
  		if (b >= 'a' && b <= 'z') ||
  			(b >= 'A' && b <= 'Z') ||
  			(b >= '0' && b <= '9') ||
  			b == '-' || b == '_' {
  			continue
  		}
  		return false
  	}
  	return true
  }
  ```
- **Evaluation against REQ-100-AC-01 / ADR-100 §1**:
  - **Length Boundary Constraint**: Bounded strictly to $1 \le \text{len}(token) \le 128$. Tokens with `len < 1` (empty string) or `len > 128` immediately return `false`.
  - **Character Set Restriction**: The single-pass byte loop iterates directly over string bytes (`token[i]`). Each byte must belong to `'a'-'z'`, `'A'-'Z'`, `'0'-'9'`, `'-'` (`0x2D`), or `'_'` (`0x5F`).
  - **Explicit Character Rejection**:
    - Padding character `'='` (`0x3D`) returns `false`.
    - Path characters `'/'`, `'\\'`, `'.'` return `false`.
    - Whitespace characters (`' '`, `'\t'`, `'\r'`, `'\n'`) return `false`.
    - Control characters (`0x00`-`0x1F`, `0x7F`) return `false`.
    - High-order / multi-byte UTF-8 bytes (`>= 0x80`) return `false`.
  - **Zero Allocations & Performance**: Operates in $O(N)$ time with strictly $O(1)$ space and 0 heap allocations. Does not use regular expressions, avoiding regex engine compilation or backtracking overhead.
- **Verdict**: **COMPLIANT**.

### 2. HTTP Method Hardening & 405 Method Not Allowed Enforcement

- **Implementation**:
  [`pkg/acme/acme.go:223-230`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L223-L230):
  ```go
  // 1. Method restriction (only GET and HEAD permitted)
  if req.Method != "GET" && req.Method != "HEAD" {
  	res.SetStatus(http.StatusMethodNotAllowed)
  	res.Header.Set("Allow", "GET, HEAD")
  	res.Header.Set("Content-Type", "text/plain")
  	_, _ = res.WriteString("405 Method Not Allowed: Only GET and HEAD methods are permitted")
  	return
  }
  ```
- **Evaluation against REQ-100-AC-02 / ADR-100 §2**:
  - **Execution Placement**: Executed as the very first operation in `ServeHTTP01Handler`, before token extraction, path slicing, or mutex locking.
  - **Allowed Methods**: Only `"GET"` and `"HEAD"` are accepted.
  - **Disallowed Methods**: Any other HTTP method (`POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `CONNECT`, `TRACE`, etc.) triggers:
    1. HTTP status code `405 Method Not Allowed`.
    2. Mandatory `Allow: GET, HEAD` header conforming to [RFC 7231 §6.5.5](https://datatracker.ietf.org/doc/html/rfc7231#section-6.5.5).
    3. `Content-Type: text/plain` header.
    4. Explanatory error body `"405 Method Not Allowed: Only GET and HEAD methods are permitted"`.
    5. Immediate `return` bypassing challenge lookup.
- **Verdict**: **COMPLIANT**.

### 4. Fail-Fast Token Syntax & Length Rejection Prior to Mutex Contention

- **Implementation**:
  [`pkg/acme/acme.go:235-241`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L235-L241):
  ```go
  // 3. Fail-fast syntax and length validation before map lookup or lock acquisition
  if !IsValidACMEToken(token) {
  	res.SetStatus(http.StatusBadRequest)
  	res.Header.Set("Content-Type", "text/plain")
  	_, _ = res.WriteString("400 Bad Request: Invalid ACME Challenge Token")
  	return
  }
  ```
- **Evaluation against REQ-100-AC-03 / ADR-100 §1, §2**:
  - Any token failing `IsValidACMEToken(token)` (empty token, length > 128, invalid character) triggers:
    1. HTTP status code `400 Bad Request`.
    2. `Content-Type: text/plain` header.
    3. Standardized error body `"400 Bad Request: Invalid ACME Challenge Token"`.
    4. Immediate `return` without calling `m.GetHTTP01Challenge(token)`.
  - **Lock Isolation**: Because `IsValidACMEToken` runs before `m.GetHTTP01Challenge`, invalid requests never acquire `m.mu.RLock()` and never compute hash keys for `m.http01Tokens`, providing complete resilience against hash flooding and lock starvation DoS attacks.
- **Verdict**: **COMPLIANT**.

### 5. RFC 7231 HEAD Method Semantics & RFC 8555 GET Resolution

- **Implementation**:
  [`pkg/acme/acme.go:243-262`](file:///Users/sneha/Developer/toron-research/toron/pkg/acme/acme.go#L243-L262):
  ```go
  // 4. Token challenge lookup
  keyAuth, exists := m.GetHTTP01Challenge(token)
  if !exists {
  	res.SetStatus(http.StatusNotFound)
  	res.Header.Set("Content-Type", "text/plain")
  	if req.Method == "GET" {
  		_, _ = res.WriteString("404 ACME Challenge Token Not Found")
  	}
  	return
  }

  // 5. Success response (RFC 7231 HEAD vs GET handling)
  res.SetStatus(http.StatusOK)
  res.Header.Set("Content-Type", "text/plain")
  res.Header.Set("Content-Length", strconv.Itoa(len(keyAuth)))

  if req.Method == "GET" {
  	_, _ = res.WriteString(keyAuth)
  }
  ```
- **Evaluation against REQ-100-AC-04, REQ-100-AC-05 / ADR-100 §3, §4**:
  - **HEAD on Registered Token**:
    - Status: `200 OK`.
    - Headers: `Content-Type: text/plain`, `Content-Length: len(keyAuth)` via `strconv.Itoa(len(keyAuth))`.
    - Body: Guarded by `if req.Method == "GET"`. For `HEAD`, `res.WriteString` is NOT called, ensuring strictly `res.Body.Len() == 0` and empty body string in compliance with [RFC 7231 §4.3.2](https://datatracker.ietf.org/doc/html/rfc7231#section-4.3.2).
  - **GET on Registered Token**:
    - Status: `200 OK`.
    - Headers: `Content-Type: text/plain`, `Content-Length: len(keyAuth)`.
    - Body: Exact `keyAuth` string written to `res.Body`.
- **Verdict**: **COMPLIANT**.
