# REQ-107 - Fail-Fast Transport Socket Teardown Enforcement on Security Rejections

## 1. Description

Formal peer review audits of Paper 1 and Paper 2 (`SRC-01`, `AER-001`, `AER-002`, `ReviewTaskSummary.md`) identified a critical transport security vulnerability in Toron's connection handling lifecycle:

1. **Keep-Alive Smuggling Vector on Security Rejection**:
   When the Toron Web Application Firewall (WAF) or Router security filters intercept an unauthorized, malicious, or malformed HTTP request (e.g., CIDR IP ACL blocks, RFC protocol integrity violations such as `CONTROL-001..003`, resource exhaustion attempts `RESOURCE-002`, or filesystem path traversals `TRAVERSAL-001..003`), the engine writes an appropriate HTTP error payload (`400 Bad Request`, `403 Forbidden`, `413 Payload Too Large`). However, the handlers currently fail to explicitly mark the outgoing response with `Connection: close`.

2. **Asymmetric Connection Header Inspection in Server Loop**:
   In `pkg/server/server.go`, the persistent connection loop (`handleConn`) inspects solely the client's ingress request header (`strings.ToLower(req.Header.Get("Connection")) == "close"`). It completely neglects the server's egress response headers (`res.Header.Get("Connection")`). Consequently, even if an attacker issues a malicious request without an explicit `Connection: close` header, Toron's default HTTP/1.1 keep-alive behavior leaves the underlying physical TCP connection open on the reactor event loop.

3. **Reactor Loop & Resource Exhaustion Risks**:
   Retaining persistent TCP connections from adversarial or compromised clients enables connection-hold slowloris attacks, subsequent request pipeline smuggling attempts over desynchronized sockets, and wasted server file descriptor resources. Security best practices and RFC 7230 §6.1 dictate that on security rejections and protocol violations, the transport layer must fail fast, emit `Connection: close`, and immediately tear down the physical TCP transport socket.

---

## 2. Acceptance Criteria

### AC-1: Unconditional WAF Security Rejection Connection Teardown
- In `pkg/waf/middleware.go`, on every security rejection path:
  1. **IP ACL Block**: When an unauthorized remote IP is blocked via CIDR rules (`403 Forbidden`), the middleware must unconditionally execute `res.Header.Set("Connection", "close")`.
  2. **Protocol Integrity Violation**: When `ValidateProtocolIntegrity` fails (`400 Bad Request` or `413 Payload Too Large`), the middleware must unconditionally execute `res.Header.Set("Connection", "close")`.
  3. **Layer 7 Threat Inspection Block**: When `engine.InspectToron(req)` triggers an active block (`403 Forbidden`), the middleware must unconditionally execute `res.Header.Set("Connection", "close")`.

### AC-2: Router Static File Path Traversal Security Rejection Teardown
- In `pkg/router/router.go`, on every path traversal rejection path in the static file server handler (`opts.SPA`, standard static routes, and fallback evaluations):
  1. **Canonical Path Traversal Block**: When escaping root directory is detected (`403 Forbidden: Path Traversal Disallowed`), execute `res.Header.Set("Connection", "close")`.
  2. **Symlink Path Traversal Block**: When escaping symlink target is detected (`403 Forbidden: Symlink Path Traversal Disallowed`), execute `res.Header.Set("Connection", "close")`.

### AC-3: Server Egress Response-Driven Socket Teardown Enforcement
- In `pkg/server/server.go` (`handleConn`):
  1. Immediately after routing (`s.router.ServeHTTP(req, res)` or `s.serveHTTPRedirect(req, res)`), and after response serialization (`res.Serialize(conn)`), the server loop must inspect both the client header and the server response header.
  2. If `strings.ToLower(req.Header.Get("Connection")) == "close"` OR `strings.ToLower(res.Header.Get("Connection")) == "close"`, the connection loop must terminate immediately (`return nil`).
  3. Terminating `handleConn` guarantees that the reactor's deferred `conn.Close()` executes, immediately terminating the physical TCP socket.

### AC-4: Differential Security Fuzzer Alignment (TST-01 / SRC-01)
- In `benchmarks/fuzzer/diff_fuzzer.go`, the test oracle specifications for security rejection vectors shall be updated to mandate physical socket termination:
  - `CONTROL-001`, `CONTROL-002`, `CONTROL-003`: `ExpectClose: true`
  - `RESOURCE-002`: `ExpectClose: true`
  - `TRAVERSAL-001`, `TRAVERSAL-002`, `TRAVERSAL-003`: `ExpectClose: true`
- All security rejection vectors in the benchmark suite must pass with active physical socket closure verification (`ConnectionClose: true`).

### AC-5: Zero-Dependency & Race-Clean Invariant
- All changes must strictly use Go standard library packages (`net`, `strings`, `bytes`).
- All unit and integration test suites (`go test -v -race -count=1 ./pkg/...` and `./benchmarks/fuzzer/...`) must execute with zero race conditions and 100% pass rate.

---

## 3. Rationale

Failing fast on protocol and security boundary violations is essential for zero-trust edge gateways. Allowing malicious clients to keep TCP sockets alive after firing exploit payloads invites pipeline desynchronization and Slowloris-style state table exhaustion. By making connection closure response-driven, WAF modules and route guards gain deterministic authority to terminate adversary connections at the transport boundary without leaking TCP state.

---

## 4. Constraints

- Zero external third-party dependencies (strictly Go standard library).
- Benign requests (`200 OK`, valid API calls) that do not trigger WAF or router security blocks must continue to support HTTP/1.1 persistent keep-alive connections unless the client explicitly requests `Connection: close`.
- Response serialization (`res.Serialize(conn)`) must complete before closing the connection so the client receives the structured JSON error body and `Connection: close` header.
