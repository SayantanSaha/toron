## Executive Vulnerability Assessment

### Remediation Status: 100% Resolved

The critical security vulnerability identified as [`SEC-31`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L428-L436) has been **comprehensively remediated** across all layers of the Toron Edge Gateway.

Prior to this remediation, `httpparser.Request` coupled client network identity solely to `RawConn net.Conn`. For multiplexed HTTP/2 streams and HTTP/3 QUIC datagrams, `RawConn` was `nil`, and `httpparser.NewRequestFromStd(r)` discarded `r.RemoteAddr`. Because perimeter modules (WAF IP ACL, internal management API, token bucket rate limiter, reverse proxy, logging) contained explicit checks for `if req.RawConn == nil`, any untrusted external client connecting over HTTP/2 or HTTP/3 could supply spoofed `X-Forwarded-For` or `X-Real-IP` headers to:
1. Bypass WAF blacklists and allowlists.
2. Circumvent administrative subnet policies protecting `/internal/api/*`.
3. Indefinitely evade route rate limiting by rotating client IP headers.
4. Poison upstream microservice audit logs and authorization chains.

The remediation establishes an explicit `RemoteAddr string` field in `httpparser.Request`, populates it at transport ingress across HTTP/1.1, HTTP/2, and HTTP/3, provides robust standard-library parsing helpers (`RemoteHost()` and `RemoteIP()`), and systematically anchors all security enforcement to verified physical connection metadata unless originating from explicitly configured `trusted_proxies`.

## Detailed Vulnerability & Mitigation Analysis

### 1. CWE-290 (Authentication Bypass by Spoofing)
- **Vulnerability Mechanism**: Untrusted external clients could claim arbitrary IP identities by injecting spoofed `X-Forwarded-For` or `X-Real-IP` headers into HTTP/2 and HTTP/3 requests. Because `req.RawConn` was `nil`, perimeter modules treated these requests as headless or proxied, granting access to restricted administrative subnets (`internal_api.go`) and evading IP access control (`ip_acl.go`).
- **Remediation Verification**:
  - In [`pkg/server/internal_api.go:L215-L248`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L215-L248), client IP validation evaluates `physicalIP := req.RemoteIP()`. If `physicalIP` does not match an entry in `parsedTrustedProxies`, client-supplied headers are completely ignored, and `clientIP` is set strictly to `physicalIP`. An external client connecting from `198.51.100.44` sending `X-Forwarded-For: 10.50.1.1` is evaluated strictly as `198.51.100.44` and rejected with `403 Forbidden` (`{"error":"403 Forbidden","message":"Access denied by administrative subnet policy"}`).
  - In [`pkg/waf/ip_acl.go:L165-L188`](file:///Users/sneha/Developer/toron-research/toron/pkg/waf/ip_acl.go#L165-L188), `ExtractClientIP` returns `physicalIP` when present, evaluating forwarded headers only if `isTrustedProxy(physicalIP, tp)` evaluates to `true`.
- **Verdict**: **Mitigated**. Complete elimination of CWE-290 across all protocols.

### 2. CWE-345 (Insufficient Verification of Data Authenticity)
- **Vulnerability Mechanism**: The reverse proxy ([`pkg/proxy/proxy.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go)) forwarded client-supplied `X-Forwarded-For` and `X-Real-IP` directly to upstream backends without checking whether the client was an authorized proxy, allowing external callers to forge provenance data consumed by backend services.
- **Remediation Verification**:
  - In [`pkg/proxy/proxy.go:L815-L870`](file:///Users/sneha/Developer/toron-research/toron/pkg/proxy/proxy.go#L815-L870), `peerIP` and `isTrusted` are derived from `req.RemoteHost()` and `req.RemoteIP()`.
  - When `isTrusted == false`, the reverse proxy strips client-supplied `X-Forwarded-For` and `X-Real-IP` headers and overwrites them strictly with `peerIP`.
  - Only when `isTrusted == true` does the proxy append `peerIP` to incoming `X-Forwarded-For` and preserve `X-Real-IP`.
  - Protocol derivation correctly sets `X-Forwarded-Proto: https` for HTTP/2 and HTTP/3 traffic.
- **Verdict**: **Mitigated**. Forwarded header authenticity is strictly enforced.

### 3. CWE-693 (Protection Mechanism Failure)
- **Vulnerability Mechanism**: Rate limiting ([`pkg/router/rate_limiter.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go)) contained an insecure condition: `if peerIsTrusted || req.RawConn == nil`. For all HTTP/2 and HTTP/3 requests, `req.RawConn == nil` was `true`, causing the rate limiter to unconditionally trust client-supplied `X-Forwarded-For`, `X-API-Key`, and `Authorization` headers. Attackers could evade rate limiting indefinitely by rotating headers on each request.
- **Remediation Verification**:
  - The vulnerable check `if peerIsTrusted || req.RawConn == nil` was eliminated ([`pkg/router/rate_limiter.go:L306-L325`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L306-L325)).
  - For untrusted connections (`peerIsTrusted == false`), when physical connection metadata is present (`socketHost != ""`), the rate limiter anchors the key strictly to `"ip:" + socketHost`.
  - Client-supplied `X-Forwarded-For`, `X-API-Key`, and `Authorization` headers are ignored for bucket selection. Rapid requests rotating headers are contained within the exact same bucket, exhausting tokens and returning `429 Too Many Requests`.
- **Verdict**: **Mitigated**. Abuse prevention mechanism failure is eliminated.

## Findings

No Critical, High, or Medium security findings were identified in the remediation. All vulnerabilities documented under `SEC-31` have been resolved.

### Finding 1: Optional Subnet-Level CIDR Keying for IPv6 Rate Limiting

- **Severity**: **Informational**
- **Location**: [`pkg/router/rate_limiter.go:L320-L325`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/rate_limiter.go#L320-L325)
- **Related Requirement**: `REQ-041`, `REQ-092`
- **Description**:  
  When an untrusted client connects over IPv6, `req.RemoteHost()` returns the host portion (e.g., `"2001:db8:cafe::1"`), and the rate limiter keys the token bucket strictly as `"ip:2001:db8:cafe::1"`.
  Under standard per-IP rate limiting, each distinct IPv6 `/128` address receives its own token bucket. In scenarios where a malicious actor has access to an entire `/64` prefix, they could rotate through billions of distinct `/128` addresses on the same network interface, effectively creating a separate bucket per request while still technically binding to their physical socket address.
- **Impact**:  
  Very low in typical deployments where rate limiting is combined with upstream ISP egress controls or WAF rate rules, but sophisticated attackers with routed IPv6 prefixes could cycle addresses.
- **Recommendation**:  
  Consider introducing an optional configuration parameter in `RateLimiterOptions` (e.g. `IPv6SubnetMaskBits: 64`) to mask IPv6 addresses to `/64` CIDR blocks before generating `"ip:<maskedHost>"` keys, grouping IPv6 addresses from the same subscriber subnet into a single token bucket.

## Rationale

Anchoring client network identity to physical listener connection metadata is the foundational prerequisite for edge security. Multiplexed protocols like HTTP/2 and HTTP/3 abstract transport connections into streams and datagrams; without explicit `RemoteAddr` propagation in the request model, security enforcement defaults to unverified client headers. The implemented solution decouples connection descriptor ownership (`RawConn`) from network identity (`RemoteAddr`), securing the gateway perimeter against unauthenticated spoofing while preserving application routing performance and mobile session resilience.

- Pure Go standard library packages (`net`, `net/http`, `strings`, `sync`). Zero external third-party dependencies.
- `req.RemoteAddr` is immutable after request initialization, ensuring thread-safe concurrent reads.
- `pkg/proxy/sticky.go` remains untouched with 0 diffs.
- Fail-closed security default: unresolvable addresses deny administrative access and fall back safely in WAF.
