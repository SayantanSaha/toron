# ADR-141 - Native ECMAScript Modules Architecture for Control Center Dashboard

## 1. Context & Problem Statement

The Toron Edge Gateway Control Center dashboard ([`public/app.js`](../../public/app.js)) has evolved into an extensive real-time observability control plane spanning 8 interactive views, responsive SVG charts, vector Sankey flow diagrams, live request tailing with waterfall inspectors, and security incident management.

Currently, all 1,663 lines reside in a single monolithic script file. This structure impedes maintenance, testing isolation, and concurrent engineering. However, adopting a modern frontend framework (React, Vue, Svelte) would require introducing Node.js build pipelines into [`Dockerfile`](../../Dockerfile), increasing container image size and expanding supply-chain vulnerability attack surfaces.

An architectural decision is required to transition the dashboard into a modular, maintainable, and cleanly encapsulated structure without compromising Toron's zero-dependency, ultra-lightweight operational model.

---

## 2. Decision & Technical Architecture

Toron adopts a **Native Browser ECMAScript Modules (`ESM`)** architecture served directly by the gateway static asset router.

### 2.1 Layered Module Dependency Hierarchy

The frontend is organized into 4 strictly ordered dependency layers to prevent circular dependencies:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   Layer 3: Application Orchestration                   │
│                          public/js/app.js                              │
│              (Router, lifecycle, event listeners, boot)               │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
┌───────────────────────────────────▼────────────────────────────────────┐
│                        Layer 2: View Controllers                       │
│                        public/js/views/*.js                            │
│   overview.js · routes.js · upstreams.js · logs.js · certs.js          │
│                modules.js · alerts.js · console.js                     │
└──────────────────┬─────────────────────────────────┬───────────────────┘
                   │                                 │
┌──────────────────▼──────────────────┐   ┌──────────▼───────────────────┐
│     Layer 1b: Visual Components     │   │   Layer 1a: Telemetry Engine │
│      public/js/components/*.js      │   │    public/js/{api,model}.js  │
│    charts.js · sankey.js · drawer.js│   │  (Polling, rollup, smoothing)│
└──────────────────┬──────────────────┘   └──────────┬───────────────────┘
                   │                                 │
┌──────────────────▼─────────────────────────────────▼───────────────────┐
│                       Layer 0: Foundational Primitives                 │
│                          public/js/*.js                                │
│       utils.js (DOM, formatters) · state.js · components/icons.js      │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Layer 0 (Foundational Primitives)**:
   - `utils.js`: Pure helper functions with zero dependencies (`$`, `$$`, `esc`, `fmt`, `dtFmt`, `clamp`).
   - `state.js`: Central mutable state object (`state`), time-range configurations (`RANGES`), and theme detection/toggling.
   - `components/icons.js`: Vector icon renderers (`ICON`, `pill`, `TI`, `TONE`).

2. **Layer 1 (Telemetry Engine & Visual Components)**:
   - `api.js`: Handles asynchronous HTTP polling (`fetchBackendData`) across `/internal/api/*` endpoints.
   - `model.js`: Pure data transformations (`buildDataModel`), subpath aggregations, moving-average temporal smoothing, disaggregated pool keys, and tone escalations.
   - `components/charts.js`: SVG sparklines, timeseries graphs, and latency distribution histograms.
   - `components/sankey.js`: Vector SVG Sankey traffic flow diagram generator.
   - `components/drawer.js`: Slide-out inspector drawer manager (`dw`, `openDrawer`, `closeDrawer`).

3. **Layer 2 (View Controllers - `public/js/views/`)**:
   - Each view exports `{ shell, init, update }` hooks matching the SPA view protocol.
   - Self-contained DOM rendering and view-specific user interaction handling.

4. **Layer 3 (Application Orchestration - `public/js/app.js`)**:
   - Imports all views, components, state, model, and api layers.
   - Registers navigation table (`NAV`, `META`, `VIEWS`), hash routing, live tailing timer, and global event listeners.

---

### 2.2 Unidirectional Data Flow

```text
Timer (2s) ──> api.fetchBackendData()
                      │
                      ▼
              rawApi* updated
                      │
                      ▼
              model.invalidate()
                      │
                      ▼
         refresh() ──> model.buildDataModel()
                              │
                              ▼
                      currentView.update(D)
                              │
                              ▼
                     Native DOM Mutation
```

State mutations occur exclusively via user interactions or background polling ticks. The data adapter (`model.buildDataModel()`) caches derived telemetry within a single tick and invalidates when new raw API snapshots arrive.

---

### 2.3 Browser Entrypoint & Asset Serving

In [`public/index.html`](../../public/index.html), the script declaration is updated to:

```html
<script type="module" src="./js/app.js"></script>
```

Toron's static route handler serves the `public/` directory under `/internal/dashboard/`. Standard MIME type resolution (`text/javascript`) natively handles all `.js` files requested by the browser module loader.

## 3. Alternatives Considered

### Option 1: Single-Page Application Framework (React, Vue, Svelte)
- *Pros*: Declarative component syntax, rich ecosystem.
- *Cons*: Requires Node.js build tools, webpack/vite bundlers, and npm dependencies. Bloats Docker images and introduces supply-chain risk into a zero-allocation Go edge proxy.
- *Verdict*: **Rejected**.

### Option 2: Pre-bundled Single JS File via esbuild/Rollup
- *Pros*: Single HTTP request in production.
- *Cons*: Still requires an active build pipeline and dev-time compilation scripts.
- *Verdict*: **Rejected**. Modern HTTP/2 and HTTP/1.1 keep-alive effortlessly handle the small set (~15) of modular files.

### Option 3: Native Browser ECMAScript Modules (Chosen)
- *Pros*: Zero build tools, 100% native browser support, clean file separation, instant file editing without rebuilds, zero supply chain dependencies.
- *Verdict*: **Accepted**.

---

## 4. Consequences & Trade-offs

- **Positive**:
  - Codebase is partitioned into small, single-purpose files (< 200 lines each).
  - No bundler, no build step, no npm runtime dependencies.
  - Zero impact on Docker appliance footprint or Go compilation.
  - Concurrent contributions can modify individual views without git conflicts.
- **Trade-off**:
  - Automated Node.js test runner ([`tests/dashboard_telemetry_test.js`](../../tests/dashboard_telemetry_test.js)) must accommodate native ES module imports or execute through a lightweight simulation harness.
