# REQ-070 - Host Header Validation and Open Redirect Mitigation in HTTP-to-HTTPS Redirection

## Description

The Toron cleartext HTTP-to-HTTPS redirection handler shall validate incoming `Host` headers against recognized domain configurations and SNI routes before constructing 301/308 redirect `Location` URLs.

The redirect engine shall guarantee that arbitrary client-supplied hostnames (e.g. `Host: evil.com`) cannot be reflected into the redirect destination, preventing Open Redirect vulnerabilities (CWE-601) and credential phishing attacks.

## Acceptance Criteria

### 1. Recognized Host Validation
- In `serveHTTPRedirect`, the incoming request's `Host` header shall be validated against:
  1. The server's registered SNI domain names,
  2. Configured proxy route hostnames, or
  3. An explicitly configured allowed hosts whitelist.
- If the host is recognized, the redirect `Location: https://<host><uri>` shall be generated normally.

### 2. Handling of Unrecognized Host Values
- If the client-supplied `Host` does not match any configured route or domain whitelist, Toron shall:
  - Fall back to a configured primary canonical server hostname (e.g. `https://canonical-host.com<uri>`), or
  - Reject the request with HTTP `400 Bad Request: Unrecognized Host`.
- Unrecognized hostnames shall never be reflected into the redirect `Location` header.

### 3. CRLF and Character Filtering Integrity
- The existing checks rejecting control characters, backslashes, spaces, and CRLF sequences (`\r\n\t /\\`) shall remain active to prevent response splitting (CWE-113).

## Rationale

Edge gateways that blindly reflect incoming `Host` headers into redirect URLs allow attackers to craft phishing links on the trusted gateway IP/port that redirect unsuspecting victims to malicious external login portals.

## Constraints

- Seamless integration with existing `HTTPRedirectConfig` and `serveHTTPRedirect` logic.
- Support for explicit port stripping using `net.SplitHostPort`.

## Open Questions

- Should canonical host fallback be configured at the global server level in `config.yaml`?
