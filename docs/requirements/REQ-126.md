# REQ-126 - Adaptive Socket Deadline Amortization and Slowloris Protection Optimization

## 1. Description & Problem Statement

### 1.1 Problem Context
In [`pkg/server/server.go:199`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L199) and [line 312](file:///Users/sneha/Developer/toron-research/toron/pkg/server/server.go#L312), Toron executes two operating system socket calls on every HTTP transaction within persistent keep-alive connections:
```go
conn.SetReadDeadline(time.Now().Add(timeout))
...
conn.SetWriteDeadline(time.Now().Add(s.config.WriteTimeout))
```

Under high-concurrency benchmarks ([`REQ-121`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-121.md)), Toron processes ~24.5k requests per second per container. At this rate, the server executes **~49,000 socket deadline system calls per second**, triggering repeated kernel context switches and CPU instruction cache evictions.

Furthermore, architectural analysis of long-lived streaming connections (such as Server-Sent Events / SSE, live telemetry feeds, or chunked transfer streaming) exposed a critical interplay between static socket deadlines and persistent streams:
1. In `pkg/server/server.go:312`, `conn.SetWriteDeadline(time.Now().Add(s.config.WriteTimeout))` sets an absolute, static write deadline (e.g., 5 seconds in the future) prior to emitting the response.
2. For long-lived streaming responses where chunks or events are transmitted over minutes or hours, an un-refreshed static write deadline causes the socket write to fail after 5 seconds, terminating healthy streams prematurely.
3. Conversely, completely eliminating `SetWriteDeadline` on streaming responses leaves Toron defenseless against Slow Read Denial of Service ([CWE-400](https://cwe.mitre.org/data/definitions/400.html)), where malicious or stalled clients read data at 1 byte/minute, pinning server goroutines and proxy resources indefinitely until thread pool exhaustion occurs.

### 1.2 Prior Requirements & Standards Cross-Audit (Conflict Analysis)

Completely eliminating socket deadlines to maximize throughput introduces a **direct, critical security conflict**:

1. **Direct Conflict with [`REQ-005`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-005.md) §2 (Security Controls & Input Protection)**:
   - Mandates: *"Enforces strict read, write, and idle connection timeouts to prevent Slowloris/slow-client resource exhaustion."*
2. **Direct Conflict with [`TASK-004`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-004.md) §3 (Security Guards, Request Limits & Connection Timeouts)**:
   - Mandates: *"Set socket read and write deadlines per connection to prevent Slowloris attacks."*
3. **Direct Conflict with [`ADR-083`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-083.md) & Security Verification Suites [`TC-087`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-087.md) / [`TC-088`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-088.md)**:
   - Eliminating `SetWriteDeadline` opens Toron to Slow Read Denial of Service ([CWE-400](https://cwe.mitre.org/data/definitions/400.html)), where a malicious client advertises a zero TCP window or reads bytes at 1 byte/minute, hanging server worker goroutines indefinitely until worker pool exhaustion occurs.
   - Eliminating `SetReadDeadline` exposes server connections to classic Slowloris socket starvation.

### 1.3 Safe Non-Conflicting Path
To achieve the performance benefits of reduced system calls while maintaining 100% compliance with `REQ-005` Slowloris and Slow-Read immunity:
1. **Adaptive Deadline Amortization**: If a socket deadline was already set for $T$ seconds in the future and the current time is still within a safe threshold (e.g. more than 50% of the timeout remaining), redundant calls to `SetDeadline` are safely bypassed during rapid request bursts.
2. **Idle-State Transition Read Deadline**: `SetReadDeadline` is only refreshed with `IdleTimeout` when transitioning to the idle state waiting for the next request header (`br.Buffered() == 0`). During active parsing, the existing read deadline remains in effect.
3. **Activity-Refreshed Write Deadlines for Streaming Responses**: For persistent streaming responses (such as SSE or direct streaming fast-paths per [`REQ-125`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-125.md)), Toron must refresh the write deadline on each successfully flushed chunk, event, or buffer write (`conn.SetWriteDeadline(time.Now().Add(s.config.WriteTimeout))`). This allows active streams to remain open indefinitely while guaranteeing immediate termination if a client stalls reading for longer than `WriteTimeout`.
4. **Trusted Environment Configuration**: Maintain full support for `read_timeout: 0` and `write_timeout: 0` in `config.yaml` for operators running benchmarks in trusted/isolated environments who want zero deadline overhead.

## 2. Functional Requirements

### 2.1 Amortized Socket Deadline Tracker (`pkg/server`)
1. Introduce connection-level deadline tracking in `pkg/server`:
   ```go
   type connDeadlineTracker struct {
       net.Conn
       lastReadDeadline  time.Time
       lastWriteDeadline time.Time
   }
   ```
2. In `handleConn`:
   - Prior to calling `conn.SetReadDeadline(now.Add(timeout))`, evaluate if `now.Before(lastReadDeadline.Add(-timeout/2))`.
   - If true, skip the `SetReadDeadline` system call because the socket is already covered by a valid future deadline.
   - If false, call `conn.SetReadDeadline(now.Add(timeout))` and update `lastReadDeadline`.
3. Apply identical amortization to `SetWriteDeadline` for discrete static request/response pairs:
   - If `lastWriteDeadline` is still valid and at least half the write timeout remains, skip the redundant system call.

### 2.2 Idle Timeout State Machine Alignment
1. When a request completes and `br.Buffered() == 0` on a persistent keep-alive connection:
   - Explicitly apply `conn.SetReadDeadline(time.Now().Add(s.config.IdleTimeout))`.
   - Clear `lastReadDeadline` amortization cache so the idle timeout is strictly enforced immediately.
2. When the first byte of a new request arrives, reset the read deadline to `s.config.ReadTimeout`.

### 2.3 Activity-Refreshed Write Deadlines for Persistent Streaming
1. For persistent streaming responses (e.g., SSE `text/event-stream`, chunked streaming transfers, or direct socket proxying under `REQ-125`):
   - Toron shall enforce activity-refreshed write deadlines. Upon each successfully written and flushed data frame, event chunk, or buffer iteration, the socket write deadline shall be refreshed:
     ```go
     conn.SetWriteDeadline(time.Now().Add(s.config.WriteTimeout))
     ```
   - This ensures that actively communicating long-lived streams (lasting seconds, minutes, or hours) are not prematurely terminated by the static 5s `write_timeout`.
2. **Preservation of Slow-Read DoS Defense**:
   - If a client ceases reading, advertises a zero TCP window, or throttles reading below the rate needed to consume chunks within `WriteTimeout`, the refreshed write deadline will expire.
   - The connection shall be immediately closed with a write timeout error, terminating the hung goroutine and freeing proxy and server resources.

### 2.4 Strict Security & Timeout Invariants
1. A slow client that stalls transmission must still be terminated within `ReadTimeout` or `IdleTimeout`.
2. A slow client that stalls reading response data must still be terminated within `WriteTimeout`.
3. All Slowloris verification test cases ([`TC-087`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-087.md) and [`TC-088`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-088.md)) must pass with 100% success.

## 3. Non-Functional Requirements

### 3.1 Syscall Reduction & Latency Impact
- Reduce socket deadline system call frequency by $> 80\%$ under keep-alive saturation workloads ($> 20\text{k RPS}$).
- Reduce CPU kernel-mode time by eliminating redundant syscall context switches.
- Guarantee bounded latency and continuous data flow for real-time streaming connections.

### 3.2 Backward Compatibility
- Zero configuration breaking changes. Existing `read_timeout`, `write_timeout`, and `idle_timeout` fields in `config.yaml` continue to function as defined.

## 4. Acceptance Criteria

1. **`pkg/server`**:
   - Connection deadline tracker amortizes redundant `SetReadDeadline` and `SetWriteDeadline` system calls during active request bursts.
   - Idle socket timeouts remain enforced with zero regression.
   - Persistent streaming responses refresh the write deadline upon each chunk transmission, preventing 5s static timeout disconnects on healthy streams.
2. **Automated Unit & Security Tests**:
   - Long-lived streaming integration tests verify that persistent streams (e.g. SSE sending chunks over 15s with a 5s `write_timeout`) remain open and healthy across multiple chunk transmissions.
   - Automated unit tests verify that slow read clients (clients stalling during a streaming or static response) trigger write deadline disconnects within `write_timeout`.
   - Automated unit tests verify that idle connections disconnect after `idle_timeout`.
   - Existing Slowloris test suites in `pkg/proxy/tcp_test.go` and `pkg/server/server_test.go` pass without regression.
3. **Race Safety**:
   - Passes cleanly under `go test -race ./pkg/server/... ./pkg/proxy/...`.
