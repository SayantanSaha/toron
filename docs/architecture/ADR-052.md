# ADR-052 - Declarative Route-Level HTTP Redirection Policy Decoupled from Edge Listeners

## Context

Production edge servers listening on standard web ports (80 for unencrypted HTTP, 443 for encrypted HTTPS / HTTP/3) typically enforce transport layer security by upgrading cleartext requests to HTTPS using an HTTP 301 Moved Permanently redirect.

However, certain real-world workflows require unencrypted HTTP access to specific path prefixes without redirection:
1. **Automated ACME Challenge Validation**: Automated certificate authorities (e.g. Let's Encrypt HTTP-01 challenge) connect over port 80 to `/.well-known/acme-challenge/<token>`.
2. **Private Infrastructure Health Probes**: Network load balancers or container orchestrators performing health checks across internal links without TLS overhead.
3. **Legacy Webhook Ingestion**: Webhook senders unable to perform TLS handshakes.

A naive approach would be to hardcode path checks (such as `strings.HasPrefix(path, "/.well-known/acme-challenge/")`) directly into the cleartext HTTP listener handler. However, hardcoding protocol exceptions violates separation of concerns, couples application-level routing to listener transport code, and prevents operators from exempting arbitrary custom routes.

## Decision

We decide to:
1. **Decouple Protocol Policy into Declarative Route Configuration**:
   Extend `ProxyRouteConfig` with an explicit, optional boolean pointer:
   ```yaml
   redirect_http: false
   ```
   This allows operators to define any route (static directory or upstream reverse proxy) as an unencrypted cleartext exception directly in `routes.yaml`.

2. **Unified Router Querying**:
   The auxiliary HTTP listener does not maintain independent routing tables. Instead, it queries the centralized `Router` via `ShouldRedirectHTTP(req)`.
   - If the request path and host match an active route that specifies `redirect_http: false`, the router dispatches the request to the configured route handler over HTTP.
   - If no route matches, or the matched route defaults to redirection (`redirect_http: true` or omitted), the listener generates an immediate `HTTP/1.1 301 Moved Permanently` response.

3. **Sanitized URL Construction**:
   To eliminate Open Redirect vulnerabilities (CWE-601), the redirect handler extracts and sanitizes the `Host` header, stripping explicit port indicators and rejecting any host value containing control characters, line breaks, or invalid URI tokens.

4. **Lifecycle Coordination**:
   The auxiliary HTTP server runs concurrently with the primary TLS server, both governed by the same application termination context (`SIGINT` / `SIGTERM`) to guarantee zero orphaned sockets or connection leaks on server restart.

## Consequences

### Positive
- Zero hardcoded paths in the server or router implementation.
- Fully declarative: Any route in `routes.yaml` can be exempted from HTTP-to-HTTPS redirect simply by specifying `redirect_http: false`.
- Unified static and proxy routing: The same handler serving static assets or proxying upstream targets handles requests on both port 80 and port 443.
- Robust security: Open redirect and CRLF injection vulnerabilities are actively prevented by strict host validation.

### Negative / Trade-offs
- Slight routing lookup overhead on port 80 before deciding to issue a 301 redirect or dispatch to handler. Given Toron's lock-free read-locked router prefix matching, latency is negligible (< 2 microseconds).
