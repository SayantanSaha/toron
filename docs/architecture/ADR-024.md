# ADR-024 - Token Bucket Rate Limiting Middleware Architecture

## Context

Protecting backend upstream microservices requires configurable route-level rate limiting to prevent traffic spikes, brute-force attacks, and abuse.

## Decision

1. **Configuration Syntax (`pkg/config/config.go`)**:
   - `ProxyRouteConfig` accepts `rate_limit` strings formatted as `<count>/<unit>` (e.g. `10/sec`, `100/min`, `1000/hour`).
   - Standardizes parsing to determine token capacity ($N$) and replenishment rate ($R$ tokens/second).

2. **Token Bucket Rate Limiter (`pkg/router/rate_limiter.go`)**:
   - Maintains an in-memory map of token buckets per client key (`map[string]*TokenBucket`) guarded by `sync.RWMutex`.
   - Client key selection order:
     1. `X-API-Key` or `Authorization` header value if present.
     2. Remote IP address extracted from client socket or `X-Forwarded-For` header.

3. **HTTP Status 429 Response Enforcement**:
   - When token bucket is exhausted (available tokens $< 1$), the middleware intercepts the request before router/proxy execution.
   - Sets HTTP status `429 Too Many Requests`.
   - Sets `Retry-After: <seconds>` header estimating time until next token replenishment.
   - Returns JSON error payload `{"error":"429 Too Many Requests","message":"rate limit exceeded"}`.

4. **Automatic Memory Cleanup**:
   - Stale client buckets (inactive for > 1 hour) are garbage collected periodically to prevent memory leaks from one-off client IP addresses.

## Consequences

- **Positive**: Lightweight, low-overhead DDoS and abuse protection per route; clean client feedback with `429 Too Many Requests` and `Retry-After` headers.
- **Resource Management**: In-memory bucket map is garbage-collected automatically without bloating memory.
