# SR-089 - Security Review of SEC-29 Remediation: Hop-by-Hop Header Sanitization in REST-to-gRPC Transcoder

## Security Evaluation Summary

- **Vulnerability Remediated**: **SEC-29** ([CWE-444: Inconsistent Interpretation of HTTP Requests](https://cwe.mitre.org/data/definitions/444.html), [CWE-436: Interpretation Conflict](https://cwe.mitre.org/data/definitions/436.html))
- **Affected Subsystems**: REST-to-gRPC Transcoder Engine ([`pkg/transcoder/transcoder.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go))
- **CVSS v3.1 Vector**: `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:H` (Base Score: 8.2 &rarr; **0.0 Resolved**)
- **Verdict**: **APPROVED & RESOLVED**

---

## 1. Threat Modeling & Vulnerability Context

In [`pkg/transcoder/transcoder.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go), Toron forwards incoming client HTTP requests as HTTP/2 frames to upstream gRPC microservices.

Prior to remediation, [`Engine.HandleTranscode`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L112) blindly forwarded all client headers to the upstream gRPC request with only a `!strings.HasPrefix(lowerKey, "content-")` filter:
1. **RFC 7540 §8.1.2.2 Violation**:
   HTTP/2 explicitly forbids connection-specific headers:
   > "HTTP/2 does not use the Connection header field to indicate connection-specific header fields; in this protocol, connection-specific metadata is conveyed by other means. An endpoint MUST NOT generate an HTTP/2 message containing connection-specific header fields; any message containing connection-specific header fields MUST be treated as malformed."
2. **Upstream Protocol Error & Denial-of-Service**:
   When an external client sent headers like `Connection: keep-alive`, `Upgrade: websocket`, or `Proxy-Connection: keep-alive`, they leaked directly onto the gRPC HTTP/2 stream. Strict gRPC implementations (e.g. `grpc-go`, Envoy, or Envoy-based sidecars) immediately responded with `RST_STREAM (PROTOCOL_ERROR 0x1)`. This converted harmless client requests into `HTTP 502 Bad Gateway` errors, creating a reliable Denial-of-Service attack vector.
3. **Smuggling / Request Splitting Vector (CWE-444)**:
   By smuggling hop-by-hop headers through intermediate proxies and edge gateways, attackers could manipulate transport state or trigger inconsistent parsing between gateway layers.
4. **TE Header Mutation**:
   RFC 7540 §8.1.2.2 permits the `TE` header in HTTP/2 *only* if its value is exactly `"trailers"`. Client values such as `TE: gzip` violated this invariant.

## 2. Security Analysis of Remediation

### A. Static Hop-by-Hop Header Sanitization
- [`transcoderHopByHopHeaders`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L98) explicitly enumerates all standard hop-by-hop headers:
  `connection`, `keep-alive`, `proxy-authenticate`, `proxy-authorization`, `te`, `trailer`, `trailers`, `transfer-encoding`, `upgrade`, `proxy-connection`, and `host`.
- Every incoming client header is checked against this static map in $O(1)$ time and discarded before building the upstream request.

### B. Dynamic Token Sanitization (RFC 7230 §6.1 / RFC 9110 §7.6.1)
- The engine dynamically parses the client's `Connection` header, extracting comma-separated tokens (e.g. `Connection: X-Foo, X-Bar`).
- Any header field matching these nominated tokens is automatically stripped, neutralizing dynamic hop-by-hop leakage.

### C. Strict `TE: trailers` Invariant Enforcement
- Client `TE` headers are discarded.
- In [`HandleTranscode`](file:///Users/sneha/Developer/toron-research/toron/pkg/transcoder/transcoder.go#L112), `grpcReq.Header.Set("TE", "trailers")` is executed *after* the client header copying loop.
- This guarantees that outgoing gRPC requests always carry strictly single-valued `TE: trailers`, fully satisfying RFC 7540 §8.1.2.2 and RFC 9113 §8.2.2.

### D. Host Header Sanitization
- Client `Host` headers are stripped from `grpcReq.Header`, preventing SNI/Host header mismatch or spoofing against upstream gRPC backends.

### E. Legitimate Application Metadata Passthrough
- Headers such as `Authorization`, `X-Request-Id`, `Traceparent`, `User-Agent`, and custom application headers pass through intact with full byte fidelity.

### F. Race Safety & Zero Dependencies
- Verified race-free under `go test -race ./pkg/transcoder/...` with 50 concurrent requests.
- Strictly pure Go standard library (zero 3rd-party dependencies).

---

## 3. Final Security Verdict

**APPROVED & RESOLVED**. Vulnerability [`SEC-29`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L403-L411) is completely resolved. Outgoing gRPC requests from the transcoder strictly conform to RFC 7230, RFC 7540, and RFC 9113.
