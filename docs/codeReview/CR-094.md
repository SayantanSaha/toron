  - [`pkg/server/internal_api_test.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api_test.go#L351-L1081): Comprehensive automated test suite implementing all 8 verification scenarios defined in [`TC-098`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-098.md) (`TC-098-01` through `TC-098-08`), including normal response under limit, oversized response truncation, infinite chunked stream termination within bounded memory, custom limit enforcement, zero/negative fallback, inbound request body cap enforcement (64 KB boundary, overflow rejection, empty body, invalid JSON), keep-alive socket reuse, and high-concurrency race detection under `go test -race`.
  - `go.mod` / `go.sum`: Verification of zero third-party dependencies (100% pure Go standard library).
- **Security & Architectural Invariant Verifications**:
  - **Complete Remediation of CWE-400 & CWE-770 (Heap Exhaustion)**: Eliminates unbounded `io.ReadAll(req.Body)` and `io.ReadAll(httpResp.Body)`. Inbound payloads are strictly capped at 64 KB; upstream responses are constrained by `maxResponseBytes` (default 1 MB).
  - **Complete Remediation of CWE-775 (Socket Descriptor Leaks)**: Upstream response bodies are safely drained up to 64 KB into `io.Discard` on truncation and closed via `defer httpResp.Body.Close()`, enabling HTTP/1.1 transport connection reuse in Go's keep-alive pool without leaking socket descriptors (`EMFILE`).

  - **Configurable Limit with Safe Fallback**: `MaxProxyTestResponseBytes` defaults to 1 MB (`1048576` bytes) if omitted, set to `0`, or negative.
  - **Zero Third-Party Dependencies**: Pure Go standard library (`io`, `net/http`, `encoding/json`, `fmt`, `time`, `strings`, `bytes`, `path`, `net/url`).
  - **Concurrency Safety & Race Freedom**: 100% thread safety verified under 20 parallel workers executing mixed probe workloads with zero data races.

## Description & Context

This code review evaluates the implementation of [`TASK-121`](file:///Users/sneha/Developer/toron-research/toron/docs/tasks/TASK-121.md) satisfying requirement specification [`REQ-098`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-098.md), architectural decision record [`ADR-098`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-098.md), and test specification [`TC-098`](file:///Users/sneha/Developer/toron-research/toron/docs/testCases/TC-098.md).

### Background & Root Cause Analysis (SEC-36 / CWE-400, CWE-770, CWE-775)

During security audit [`SR-091 Finding 6`](file:///Users/sneha/Developer/toron-research/toron/docs/securityReview/SR-091.md#L197-L212) and vulnerability tracking [`SEC-36`](file:///Users/sneha/Developer/toron-research/toron/SECURITY_AUDIT.md#L483-L491) ([CWE-400: Uncontrolled Resource Consumption](https://cwe.mitre.org/data/definitions/400.html), [CWE-770: Allocation of Resources Without Limits or Throttling](https://cwe.mitre.org/data/definitions/770.html), [CWE-775: Missing Release of File Descriptor or Handle](https://cwe.mitre.org/data/definitions/775.html)), two severe memory buffering flaws and a socket leak vulnerability were identified in `POST /internal/api/proxy-test`.

Previously, `POST /internal/api/proxy-test` performed unbounded memory reads:

```go
// Vulnerable implementation prior to TASK-121
bodyBytes, err := io.ReadAll(req.Body) // Vulnerability 1: Inbound request read without length limit
...
httpResp, err := client.Do(httpReq)
...
respBodyBytes, _ := io.ReadAll(httpResp.Body) // Vulnerability 2: Upstream response read without limit
```

### Vulnerability Impact

1. **Denial of Service via Upstream Heap Exhaustion (CWE-400, CWE-770)**:
   If an administrative probe targeted an endpoint returning a large file download (e.g. a multi-gigabyte ISO), an infinite stream (e.g. `/dev/urandom` or chunked telemetry generator), or an endless Server-Sent Events feed, `io.ReadAll` continuously expanded internal byte slices until process heap memory was exhausted, causing the OS Out-Of-Memory (OOM) killer to abort the Toron gateway process.
2. **Denial of Service via Inbound Client Payload (CWE-400)**:
   An attacker or misconfigured client transmitting an arbitrarily large JSON body (e.g. 500 MB) forced the gateway to allocate large heap buffers before parsing.
3. **Socket Descriptor Exhaustion & Connection Hangs (CWE-775)**:
   If oversized response streams were not safely drained, residual bytes left in TCP socket buffers prevented Go's `http.Transport` from recycling connections into its keep-alive pool, causing connection leaks and `EMFILE` socket exhaustion.

## Detailed Code Review & Invariant Analysis

### 1. Inbound Request Body Ingestion (64 KB Cap)

- **Implementation**:
  [`pkg/server/internal_api.go:522-540`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L522-L540):
  ```go
  const maxRequestBodyBytes = 64 * 1024 // 64 KB
  bodyBytes, err := io.ReadAll(io.LimitReader(req.Body, maxRequestBodyBytes+1))
  if err != nil || len(bodyBytes) == 0 {
      res.SetStatus(http.StatusBadRequest)
      _, _ = res.WriteString(`{"error":"400 Bad Request","message":"Missing or invalid request body"}`)
      return
  }
  if int64(len(bodyBytes)) > maxRequestBodyBytes {
      res.SetStatus(http.StatusBadRequest)
      _, _ = res.WriteString(`{"error":"400 Bad Request","message":"Request body exceeds maximum allowed size of 64KB"}`)
      return
  }

  var testReq ProxyTestRequest
  if err := json.Unmarshal(bodyBytes, &testReq); err != nil {
      res.SetStatus(http.StatusBadRequest)
      _, _ = res.WriteString(`{"error":"400 Bad Request","message":"Invalid JSON body"}`)
      return
  }
  ```
- **Evaluation against REQ-098-AC-04 / ADR-098 §2.1**:
  - `io.LimitReader(req.Body, 64*1024+1)` guarantees that no more than `65537` bytes are ever read into heap memory.
  - Overflow check `int64(len(bodyBytes)) > maxRequestBodyBytes` halts processing immediately before performing any path validation, method checking, or upstream HTTP requests.
  - Returns HTTP 400 Bad Request with exact expected JSON payload.
  - Verified across Scenarios 6.1 through 6.5 in `TestProxyTest_OversizedRequestBody_Rejection` (`TC-098-06`).
- **Verdict**: **COMPLIANT**.

### 3. Bounded Upstream Response Ingestion, Clamping, and Truncation Signaling

- **Implementation**:
  [`pkg/server/internal_api.go:664-670`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L664-L670):
  ```go
  respBodyBytes, _ := io.ReadAll(io.LimitReader(httpResp.Body, maxResponseBytes+1))
  truncated := false
  if int64(len(respBodyBytes)) > maxResponseBytes {
      respBodyBytes = respBodyBytes[:maxResponseBytes]
      truncated = true
      _, _ = io.Copy(io.Discard, io.LimitReader(httpResp.Body, 64*1024))
  }
  ```
  [`pkg/server/internal_api.go:679-686`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L679-L686):
  ```go
  resOut := ProxyTestResponse{
      StatusCode: httpResp.StatusCode,
      StatusText: http.StatusText(httpResp.StatusCode),
      LatencyMS:  latency,
      Headers:    respHeaders,
      Body:       string(respBodyBytes),
      Truncated:  truncated,
  }
  ```
- **Evaluation against REQ-098-AC-02, AC-03 / ADR-098 §2.2, §3**:
  - `io.LimitReader(httpResp.Body, maxResponseBytes+1)` reads at most `maxResponseBytes + 1` bytes, preventing unbounded heap allocation on large or infinite streams.
  - If overflow is detected (`int64(len(respBodyBytes)) > maxResponseBytes`), the buffer is clamped to exactly `maxResponseBytes` and `truncated = true` is populated.
  - If the response is within the limit, `truncated = false` is preserved and the full body is returned.
  - Upstream status code (e.g. 200, 206) and headers are faithfully returned to the diagnostic client.
  - Validated in `TC-098-01` (512 bytes, `truncated: false`), `TC-098-02` (2.5 MB clamped to 1 MB, `truncated: true`), and `TC-098-03` (infinite stream clamped to 1 MB).
- **Verdict**: **COMPLIANT**.

## Findings & Recommendations

### Finding 1: Lack of Upper Ceiling Clamp on Configured `MaxProxyTestResponseBytes`

- **Severity**: Low (Defensive Configuration Hardening)
- **Location**: [`pkg/server/internal_api.go:659-662`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L659-L662)
- **Related Artifact**: [`REQ-098 §6 Open Question 2`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-098.md#L231-L233), [`ADR-098 §1.2`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-098.md#L107-L118)
- **Description**:
  The handler safely handles omitted, zero, or negative configuration values by defaulting to 1 MB:
  ```go
  maxResponseBytes := cfg.MaxProxyTestResponseBytes
  if maxResponseBytes <= 0 {
      maxResponseBytes = 1024 * 1024 // 1 MB default
  }
  ```
  However, there is no upper ceiling sanity clamp. If an operator configures an excessively large limit (e.g. `1024 * 1024 * 1024` for 1 GB), a single probe against a large file download could buffer up to 1 GB into heap memory.
- **Impact**:
  Misconfiguration could inadvertently re-introduce high memory allocations.
- **Recommendation**:
  Enforce a sensible maximum allowable ceiling (e.g. 10 MB or 50 MB):
  ```go
  const maxAllowableResponseBytes = 10 * 1024 * 1024 // 10 MB ceiling
  if maxResponseBytes > maxAllowableResponseBytes {
      maxResponseBytes = maxAllowableResponseBytes
  }
  ```

---

### Finding 2: Latency Measurement Captures Time-To-First-Byte (TTFB) Rather than Time-To-Last-Byte (TTLB)

- **Severity**: Low (Documentation & Observability Clarity)
- **Location**: [`pkg/server/internal_api.go:641-643`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L641-L643)
- **Related Artifact**: [`REQ-047`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-047.md), [`ADR-098 §3.1`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-098.md#L163-L177)
- **Description**:
  `latency` is calculated immediately after `client.Do(httpReq)` returns, before reading or draining the response body:
  ```go
  start := time.Now()
  httpResp, err := client.Do(httpReq)
  latency := float64(time.Since(start).Microseconds()) / 1000.0
  ```
  For large or streaming upstream responses, this metric measures Time-To-First-Byte (TTFB) rather than the complete request-response round-trip duration.
- **Impact**:
  While TTFB is standard and useful for diagnostic latency probes, operators may assume `latency_ms` includes payload transfer time.
- **Recommendation**:
  Add an explanatory comment in `ProxyTestResponse` struct docstring clarifying that `LatencyMS` reflects initial response header arrival time (TTFB).

---

### Finding 3: Residual Stream Drain Discard Overage Not Tracked in Telemetry

- **Severity**: Low (Telemetry Enhancement)
- **Location**: [`pkg/server/internal_api.go:669`](file:///Users/sneha/Developer/toron-research/toron/pkg/server/internal_api.go#L669)
- **Related Artifact**: [`REQ-098-AC-05`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-098.md#L128-L136)
- **Description**:
  When an oversized response is truncated, the handler drains up to 64 KB of residual bytes via `_, _ = io.Copy(io.Discard, io.LimitReader(httpResp.Body, 64*1024))`. The number of drained bytes or total upstream content length (if reported in `Content-Length`) is not exposed in `ProxyTestResponse`.
- **Impact**:
  Operators cannot see how much data was discarded beyond `maxResponseBytes`.
- **Recommendation**:
  In a future enhancement, consider adding an optional `TotalContentLength int64` or `ExcessBytesDiscarded int64` field to `ProxyTestResponse` when `Truncated: true`.
