## Findings

### SEC-146-01: Unescaped Rendering of Fallback Created Timestamp and Incident Anomaly Score
- **Severity**: Low
- **Category**: Cross-Site Scripting (XSS / CWE-79) / Output Encoding Defense-in-Depth
- **Location**: `public/js/views/alerts.js:231`, `public/js/views/alerts.js:305`
- **Related artifacts**: `../requirements/REQ-146.md` (FR-146-2), `../architecture/ADR-146.md` (Decision 3)
- **Evidence**:
  In `public/js/views/alerts.js` line 231:
  ```javascript
  const scoreBadge = (inc.anomaly_score != null) ? `<span class="chipx" style="font-size:11px">Score: ${inc.anomaly_score}</span>` : '';
  ```
  In contrast with `public/js/components/drawer.js:46,52` (which wraps `inc.anomaly_score` in `esc()`), `alerts.js` concatenates `inc.anomaly_score` directly into HTML.
  Furthermore, in `public/js/views/alerts.js` line 305:
  ```javascript
  <td class="td-mono" style="font-size:12px;white-space:nowrap">${dtFmt(b.created_at)}</td>
  ```
  In `public/js/utils.js:26`, if `new Date(d)` is `Invalid Date`, `dtFmt()` returns raw `String(d)`. If `b.created_at` were ever malformed or corrupted to contain HTML meta-characters, the output would be rendered unescaped into the table DOM.
- **Description**: While backend anomaly scores are numerical integers and creation timestamps are RFC3339 formatted strings generated by the Go runtime, client-side template string interpolation should consistently pass all dynamic server variables through `esc()`.
- **Impact**: Minimal in standard deployment because backend APIs validate and format timestamps and scores. However, defense-in-depth principles require unconditional escaping of all untrusted or backend-derived attributes.
- **Recommendation**:
  1. Wrap `inc.anomaly_score` in `esc(String(inc.anomaly_score))` in `public/js/views/alerts.js`.
  2. Wrap `dtFmt(b.created_at)` in `esc()` matching the pattern established on line 248 (`${esc(fullTime)}`).
- **Required action**: Track as a non-blocking hardening task for the next dashboard patch cycle.

### SEC-146-02: Heuristic Client-Side IPv6 Validation Allows Malformed Addresses
- **Severity**: Low
- **Category**: Input Validation / Syntax Verification (CWE-20)
- **Location**: `public/js/views/alerts.js:13-17`
- **Related artifacts**: `../requirements/REQ-146.md` (FR-146-4, AC-146-05), `../architecture/ADR-146.md` (Decision 3.5)
- **Evidence**:
  In `public/js/views/alerts.js`:
  ```javascript
  if (s.includes(':') && !s.includes(':::') && !/[^0-9a-fA-F:]/.test(s)) {
    const p = s.split(':');
    return p.length >= 3 && p.length <= 8 && p.every(x => x.length <= 4);
  }
  ```
  Testing this logic reveals that non-standard addresses pass client validation:
  - Multiple double colons (e.g., `1::2::3`, violating RFC 4291 §2.2).
  - Uncompressed partial addresses with fewer than 8 groups lacking `::` (e.g., `1:2:3`).
  - Leading or trailing single colons (e.g., `:1:2:` or `fe80:1:`).
- **Description**: The client-side IPv6 validation uses a permissive heuristic rather than a full RFC 4291 regex parser. If an operator accidentally enters a malformed IPv6 address, client-side validation passes the address and dispatches `POST /internal/api/security/ban`.
- **Impact**: Negligible security risk because the backend (`pkg/waf/auto_ban.go:401`) parses all IPs with standard library `net.ParseIP(ipStr)`, rejecting invalid entries with HTTP 400 Bad Request and displaying an error toast in the UI. However, the client fails to provide immediate syntax rejection prior to network dispatch.
- **Recommendation**: Refine the client-side IPv6 regular expression to enforce single double-colon compression and strict 8-hextet boundaries, or adopt a standards-compliant regex pattern.
- **Required action**: Non-blocking; backend defense-in-depth prevents persistence of invalid entries.

### SEC-146-03: Session Storage Credential Scope and Administrative Token Access
- **Severity**: Informational
- **Category**: Credential Storage & Privilege Management (CWE-312 / CWE-922)
- **Location**: `public/js/state.js:48-52,56-76`
- **Related artifacts**: `../requirements/REQ-141.md`, `../architecture/ADR-146.md`
- **Evidence**:
  ```javascript
  const AUTH_STORAGE_KEY = 'toron_admin_key';
  // ...
  sessionStorage.setItem(AUTH_STORAGE_KEY, token);
  ```
- **Description**: The dashboard client manages authentication by storing the administrator key or Bearer token in `sessionStorage` and client memory (`state.auth.token`). In the event of a successful Cross-Site Scripting (XSS) attack within the dashboard origin, malicious JavaScript could extract the administrative token and perform unauthorized ban or unban actions.
- **Impact**: Informational. `sessionStorage` correctly isolates credentials from cross-tab and cross-browser persistence (closing the tab purges the token), which is significantly safer than `localStorage`.
- **Recommendation**: For environments requiring high assurance against script credential theft, evaluate migrating management API sessions to HTTP-only, `SameSite=Strict` secure cookies in a future release.
- **Required action**: None required for v1.0.0; existing `sessionStorage` architecture aligns with project specifications.

### SEC-146-04: Absence of Automated Security Test Assertions for XSS Probes in Incident Telemetry
- **Severity**: Informational
- **Category**: Test Coverage & Regression Defenses
- **Location**: `tests/dashboard_telemetry_test.js`
- **Related artifacts**: `../testCases/TC-146.md` (TC-146-03, TC-146-07)
- **Evidence**:
  While `tests/dashboard_telemetry_test.js` covers functional pagination, sorting, search matching, and unban flow, it lacks negative assertions specifically confirming that HTML tags in forensic fields (e.g. `client_ip = "<img src=x onerror=alert(1)>"`, `payload_snippet = "<script>alert(1)</script>"`) are encoded into HTML entities (`&lt;script&gt;`) rather than live DOM nodes.
- **Description**: The test suite validates that `esc(incidentFixture.payload_snippet)` is included in `#dwBody`, but does not test active XSS payload vectors to verify that raw unencoded HTML is never emitted.
- **Impact**: Informational. Manual inspection shows `esc()` is applied across all primary fields, but automated tests should guard against accidental regression during future refactoring.
- **Recommendation**: Add a dedicated automated test case to `tests/dashboard_telemetry_test.js` verifying that hostile strings in `payload_snippet`, `client_ip`, `rule_id`, and `path` do not generate unescaped HTML elements.
- **Required action**: Include security regression test in the next test suite update.

## Positive Observations

1. **Robust Forensic Payload Escaping (`CWE-79` Prevention)**:
   In `public/js/components/drawer.js:61`, the raw attack signature is explicitly escaped before insertion into `<pre class="cs-pre">`:
   ```javascript
   <pre class="cs-pre" style="overflow-x:auto;white-space:pre-wrap;word-break:break-all;">${esc(inc.payload_snippet || '')}</pre>
   ```
   This prevents stored XSS when operators inspect real-world attack vectors (e.g., SQLi, XSS probes, polyglot payloads) intercepted by the WAF.

2. **Safe Error Feedback via `textContent` (`CWE-116` Defense)**:
   In `public/js/views/alerts.js:25` (`showToast`) and `alerts.js:40` (`openUnbanModal`), dynamic server strings and target IP addresses are rendered strictly using `.textContent`:
   ```javascript
   toast.textContent = msg;
   if (el) el.textContent = ip;
   ```
   This eliminates DOM-based injection from untrusted backend error messages or network failure strings.

3. **Complete Elimination of UI Thread Freezing (`DoS / UI Liveness`)**:
   `window.confirm()` and `window.alert()` have been completely purged from the codebase. The modal confirmation workflow operates asynchronously through DOM overlays (`#alConfirmModal`), allowing background telemetry polling, chart rendering, and websocket/timer ticks to continue without interruption.

4. **Race-Condition-Resistant Unban Dispatch**:
   `executeUnban()` immediately dismisses the modal and clears `state.alConfirmBan` prior to initiating the asynchronous `authenticatedFetch` network dispatch. This prevents double-click concurrency and duplicate API calls.

5. **Same-Origin Fetch Isolation (`CSRF` & Credential Hardening)**:
   All network calls to `/internal/api/security/ban` and `/internal/api/security/unban` use `authenticatedFetch()` which enforces `credentials: 'same-origin'` and custom authorization headers (`X-Toron-Admin-Key`, `Authorization: Bearer`), providing strong inherent protection against Cross-Site Request Forgery (CSRF).

6. **Defense-in-Depth Whitelist and Parse Validation**:
   The backend engine in `pkg/waf/auto_ban.go` validates all incoming IP ban requests with `net.ParseIP()` and blocks attempts to ban whitelisted or loopback IP addresses (`IsWhitelisted`), preventing accidental self-lockout by administrators.

## Residual Risk

1. **Client-Side Storage of Admin Bearer Tokens**:
   As in all browser-based Single Page Applications, storing Bearer tokens in client memory and `sessionStorage` exposes the session to exfiltration if a script injection vulnerability were ever introduced elsewhere in the dashboard. This risk is minimized by strict output encoding and CSP compliance.
2. **In-Memory Audit Buffer Horizon**:
   The backend in-memory circular buffer retains the 50 most recent security events (`maxEvents: 50`). During volumetric distributed attacks, events may rotate quickly. Historical forensics must rely on server-side persistent audit logging.

## Conclusion & Verdict

The Alerts & Threat Defense Redesign adheres to secure design principles. Output encoding is consistently applied to untrusted telemetry data, thread-blocking UI primitives have been eliminated, manual quarantine controls are validated, and API communications are authenticated with same-origin scoping.
