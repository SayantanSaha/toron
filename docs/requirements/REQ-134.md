# REQ-134 - RFC 9111 Cache Session Boundary Isolation, Application Path Confusion Scope, and Comprehensive Host Port Routing Invariants

## 1. Description & Problem Statement

### 1.1 Overview & Architectural Context

During an architectural and security audit of Toron's HTTP response caching engine ([`pkg/router/cache.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/cache.go)) and routing subsystem ([`pkg/router/router.go`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go)), two critical architectural concerns were identified regarding cache boundary semantics, upstream application interaction, and host port handling across routing mechanisms:

1. **Web Cache Deception (WCD) vs. RFC 9111 Protocol Session Boundary Isolation**:
   - Prior documentation and test vector descriptions ambiguously characterized Toron's caching controls as an autonomous defense against Web Cache Deception.
   - In classical Web Cache Deception (Gil, 2017), an attacker entices an authenticated victim into requesting a sensitive dynamic endpoint with an appended static file extension (e.g., `https://example.com/api/user/profile.css` or `/account/settings/avatar.jpg`). The vulnerable origin backend strips the `.css` suffix via route parameter normalization, renders the authenticated private profile payload, but **omits `Cache-Control: private` or `no-store`** because its middleware naively classifies `.css` as a public static asset.
   - Toron operates strictly as an RFC 9111-compliant transparent Layer 7 reverse proxy. It does not perform speculative file extension inspection, heuristic MIME-type sniffing, or path suffix stripping on behalf of upstream applications. If an upstream backend fails to emit `Cache-Control: private` on a dynamic response, a standard transparent RFC 9111 proxy cache will treat the response as public and store it.
   - Toron provides bulletproof **RFC 9111 Shared Cache Session Boundary Isolation** when directives are present (`Cache-Control: private`, `no-store`, `no-cache`, `Authorization` refusal without `public`, and dual-stage `Set-Cookie` stripping). However, mitigating application-level path confusion where origins omit `private` directives requires **application framework cooperation** and adhering to a **Shared Responsibility Model**. This boundary must be formalized across all internal project documentation (`docs/wiki/features/response-caching.md`, `docs/wiki/configuration.md`, `docs/wiki/index.md`).

2. **Host Port Invariant & Cross-Port Cache Collision Prevention Across All Routing Methods**:
   - In [`pkg/router/cache.go:199`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/cache.go#L199), the cache lookup key is constructed as:
     ```go
     cacheKey := req.Method + ":" + extractHost(req) + ":" + uri
     ```
   - In [`pkg/router/router.go:967-976`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L967-L976), `extractHost` unconditionally strips port numbers:
     ```go
     func extractHost(req *httpparser.Request) string {
         h := req.Header.Get("Host")
         if h == "" {
             return ""
         }
         if idx := strings.Index(h, ":"); idx != -1 {
             h = h[:idx]
         }
         return strings.ToLower(strings.TrimSpace(h))
     }
     ```
   - Port stripping was originally introduced in [`ADR-015`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-015.md) to facilitate domain-level route table matching (e.g., matching `Host: example.com:8080` against route rule `example.com`).
   - However, reusing a port-stripped host for cache key derivation creates a severe vulnerability ([CWE-524](https://cwe.mitre.org/data/definitions/524.html)): in multi-tenant edge deployments, container clusters, or microservice environments where multiple services or virtual hosts share the same hostname or IP across different ports (e.g., `service.internal:80` for public assets and `service.internal:8080` for private administration, or `api.corp.local:8080` vs `api.corp.local:8443`), requests to both services yield the exact same cache key:
     ```text
     GET:service.internal:/data
     ```
   - Furthermore, in [`pkg/router/router.go:978-991`](file:///Users/sneha/Developer/toron-research/toron/pkg/router/router.go#L978-L991), `headersAndHostMatch` checks `reqHost != strings.ToLower(routeHost)`. Because `reqHost` has its port stripped, if an operator registers an explicit port-specific route (e.g. `routeHost = "service.internal:8080"`), the comparison fails because `"service.internal"` never equals `"service.internal:8080"`.
   - Consequently, Toron must systematically disambiguate **route matching** from **cache key authority derivation** across all 9 routing methods available in the system.

Toron supports 9 distinct routing methods and mechanisms across Layer 7 and Layer 4. The requirement specification must address how each method interacts with `Host` headers, port constraints, route dispatching, and cache key derivation:

The 9 routing methods available in Toron are:

1. **Exact Path Routing (`r.Handle`, `r.GET`, `r.POST`)**:
   - Matches incoming `req.Path` via constant-time hash map lookup `r.routes[req.Path]`.
   - Evaluates registered methods and routes.
   - Host and header matching must cleanly separate domain-only from port-specific registrations.

2. **Prefix Path Routing (`prefixRoutes` with path matching)**:
   - Matches hierarchical URI prefixes (`/api`, `/static`, `/v1`) sorted by specificity (Tier 1: longest prefix length).
   - If exact path matching misses, the router scans sorted `r.prefixRoutes`.
   - Supports path matchers, method constraints, and access/security log overrides.

3. **Domain / Virtual Host Routing (`routeEntry.host` and `prefixRoute.host`)**:
   - Enables multi-tenancy on shared infrastructure.
   - In both exact entries and prefix routes, routes can specify a target host.
   - **Requirement**: Must distinguish between:
     - *Domain-only host* (e.g. `example.com`): matches requests regardless of incoming port.
     - *Port-qualified host* (e.g. `example.com:8080`): matches requests strictly on that port.

4. **Header-Based Routing (`routeEntry.headers` and `prefixRoute.headers`)**:
   - Routes requests based on HTTP headers (e.g., `X-Version: canary`, `X-Environment: staging`).
   - Sorted in Tier 3 of prefix route specificity (more headers take precedence over fewer).
   - Must evaluate headers in conjunction with host and port matching.

5. **Method-Based Routing (`GET`, `HEAD`, `POST`, `PUT`, `DELETE`, etc.)**:
   - Exact route map partitions by HTTP method (`r.routes[path][method]`).
   - Prefix routes validate `pr.method` against `req.Method`, returning `405 Method Not Allowed` when paths match but methods do not.
   - Caching middleware interacts exclusively with idempotent `GET` and `HEAD` methods; all state-changing methods bypass cache lookup and admission.

6. **Reverse Proxy Upstream Routing (`proxy.ReverseProxy` with upstream targets, route-level options, prefix stripping)**:
   - Configured via `ProxyConfig.Routes` or `r.RoutePrefix(RouteTypeUpstream, ...)`.
   - Supports single or multi-target load balancing (Round Robin, Least Connections, Latency, Sticky Cookie, IP Hash).
   - Supports `StripPrefix`, `RewriteRedirects`, `RewriteCookiePath`, active health checks, circuit breaking, and route-level WAF/Auth/Rate-Limiting.
   - When cached, the authority key must reflect the downstream request authority (`Host:Port`), never the upstream backend IP:port, ensuring tenant isolation.

7. **Static File Serving Routing (`RouteTypeStatic`)**:
   - Serves local files from disk via `createStaticHandler` with MIME sniffing, range requests, SPA fallback, and prefix boundary escape guards ([`REQ-116`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-116.md)).
   - Static assets often have long caching lifetimes. Preserving host:port ensures static routes bound to specific virtual hosts or ports do not bleed into other tenants.

8. **Kubernetes Ingress & Container Discovery Routing (`pkg/ingress`, `pkg/discovery`)**:
   - **Kubernetes Ingress**: Translates Kubernetes `networking.k8s.io/v1` Ingress resources with host rules, path rules, canary annotations (`nginx.ingress.kubernetes.io/canary*`), and header annotations (`toron.io/headers`, `toron.io/header.<name>`) into `DiscoveredRoute` objects.
   - **OCI Container Discovery**: Polls Docker/Podman Unix sockets, extracting container labels (`toron.host`, `toron.prefix`, `toron.headers`) into `DiscoveredRoute` objects.
   - Both dynamically update `r.prefixRoutes` via `r.ReplacePrefixRoutesBySource(...)`. Host and port specifications generated by ingress controllers or container labels must be matched accurately without collision.

9. **Multi-Port Gateway Listeners**:
   - Toron runs concurrent listeners across multiple network ports:
     - Cleartext HTTP redirect listener (default port 80).
     - HTTPS TLS listener (default port 443).
     - HTTP/3 QUIC UDP listener (default port 8443).
     - Layer 4 TCP stream proxies on custom ports (`ProxyRouteConfig.ListenPort`, e.g. 9000).
     - Layer 4 UDP datagram proxies on custom ports (`ProxyRouteConfig.ListenPort`, e.g. 9001).
     - Service mesh sidecar listeners (ingress port 15001, egress port 15006).
   - When HTTP requests arrive on distinct ports (e.g. port 80 vs 8080 vs 8443), cache keys derived without the port cause cross-port cache poisoning. Preserving the host port is non-negotiable.

### 1.4 Safe Non-Conflicting Path

1. **Disambiguate Route Matching from Cache Key Authority Derivation**:
   - In `pkg/router/router.go`, update `headersAndHostMatch` to support both domain-only matching (e.g., `example.com` matching incoming `example.com:8080`) and explicit port-specific matching (e.g., `example.com:8080` matching only port 8080).
   - In `pkg/router/cache.go`, introduce a dedicated authority derivation function `extractCacheHostPort(req *httpparser.Request) string` that preserves the port, normalizes hostname to lowercase, trims whitespace, and correctly handles bracketed IPv6 literals (e.g., `[::1]:8080`).
2. **Delineate Gateway Session Boundaries from Application Path Confusion**:
   - Formalize the Shared Responsibility Model in `docs/wiki/features/response-caching.md`.
   - Specify that Toron guarantees RFC 9111 protocol session boundary isolation when headers are present.
   - Acknowledge that upstream application frameworks must actively cooperate by omitting route suffix confusion and emitting `Cache-Control: private, no-store` on authenticated endpoints.
3. **Synchronize All Internal Documentation**:
   - Update `docs/wiki/features/response-caching.md`, `docs/wiki/configuration.md`, and `docs/wiki/index.md` to reflect these guarantees and provide developer guidance.
   - Do NOT reference or modify external files outside the project repository.

## 2. Functional Requirements

### 2.1 FR-1: Disambiguation of Route Matching and Cache Key Authority Derivation

1. **Route Matching Logic (`pkg/router/router.go`)**:
   - `headersAndHostMatch(reqHost string, req *httpparser.Request, routeHost string, expectedHeaders map[string]string) bool` MUST evaluate host matches as follows:
     - If `routeHost` is empty (`""`), it acts as a wildcard and matches any incoming host.
     - If `routeHost` specifies a port (contains `:` outside bracketed IPv6, e.g., `api.example.com:8080` or `[::1]:8080`):
       - It MUST compare against the full incoming request authority (host and port).
       - It matches IF and ONLY IF the incoming request authority matches `routeHost` (case-insensitively).
       - Requests targeting a different port (e.g., `api.example.com:8443`) or omitting the port (`api.example.com`) MUST NOT match this route.
     - If `routeHost` specifies a domain only without port (e.g., `api.example.com` or `[::1]`):
       - It MUST compare against the port-stripped host of the incoming request (`reqHost`).
       - It matches requests to that domain regardless of whether the incoming request contains an explicit port (e.g., `api.example.com`, `api.example.com:80`, `api.example.com:8080`).
   - Header matching (`expectedHeaders`) remains unchanged: all configured key-value pairs must match the request headers exactly.

2. **Cache Key Authority Derivation (`pkg/router/cache.go`)**:
   - Cache key derivation MUST incorporate the full host and port from the incoming request `Host` header (or authority):
     $$\text{CacheKey} = \text{Method} + \texttt{":"} + \text{extractCacheHostPort}(req) + \texttt{":"} + \text{RequestURI} \, [ + \texttt{":ae="} + \text{AcceptEncoding} ]$$
   - Hostname component MUST be normalized to lowercase and whitespace-trimmed.
   - Explicit ports MUST be preserved (e.g., `service.internal:8080`, `localhost:9090`).
   - If port is absent in the `Host` header, the normalized hostname without port MUST be used (e.g., `service.internal`).
   - IPv6 literal addresses (e.g., `[::1]:8080`, `[2001:db8::1]`) MUST be parsed safely, preserving bracket formatting and isolating the trailing port delimiter from internal IPv6 colons.
   - Requests to different ports on the same hostname with identical paths MUST generate distinct cache keys:
     - `GET /items` with `Host: service.local:8080` $\rightarrow$ `"GET:service.local:8080:/items"`
     - `GET /items` with `Host: service.local:8443` $\rightarrow$ `"GET:service.local:8443:/items"`
   - A cached response for `service.local:8080` MUST NEVER produce a cache hit for `service.local:8443`.

### 2.2 FR-2: Verification Across All 9 Routing Methods

Toron's router and caching middleware MUST guarantee correct host matching, route dispatching, and cache key derivation across all 9 routing methods:

| Routing Method | Router Dispatch Behavior | Cache Key Authority Behavior | Collision Prevention Invariant |
| :--- | :--- | :--- | :--- |
| **1. Exact Path Routing** (`r.Handle`, `r.GET`, `r.POST`) | Matches exact path in `r.routes`. Matches domain-only or explicit host:port. | Derives `Method:HostPort:URI`. | Different ports never share cached entries. |
| **2. Prefix Path Routing** (`r.prefixRoutes`) | Scans sorted prefix slice (longest prefix first). Evaluates host and headers. | Derives `Method:HostPort:URI`. | Distinct host:port pairs isolate prefix routes in cache. |
| **3. Domain / VHost Routing** (`routeEntry.host`, `prefixRoute.host`) | Explicit `host:port` routes match target port only. Domain-only routes match any port on that domain. | Preserves explicit port in cache key authority. | Prevents cross-vhost and cross-port data leaks. |
| **4. Header-Based Routing** (`routeEntry.headers`, `prefixRoute.headers`) | Matches exact header key/value pairs (e.g., canary / staging headers). | Headers are evaluated prior to cache lookup. | Cache key incorporates method, authority, and URI. (Variants use `Accept-Encoding`). |
| **5. Method-Based Routing** (`GET`, `HEAD`, `POST`, etc.) | Partitions handlers by method. Returns 405 on method mismatch. | Only idempotent `GET` and `HEAD` requests enter cache. | State-changing methods bypass cache lookup and admission. |
| **6. Reverse Proxy Upstream Routing** (`proxy.ReverseProxy`) | Proxies upstream with load balancing, strip prefix, cookie rewriting. | Cache key uses client `Host:Port`, NOT upstream target IP:port. | Multi-tenant clients proxying through same gateway remain isolated. |
| **7. Static File Serving** (`RouteTypeStatic`) | Serves files from disk with traversal escape guard and SPA fallback. | Cache key uses client `Host:Port` and request URI. | Static routes bound to different virtual hosts do not collide. |
| **8. K8s Ingress & Container Discovery** (`pkg/ingress`, `pkg/discovery`) | Translates Ingress rules and container labels into prefix routes dynamically. | Cache key uses client `Host:Port` specified in rules. | Dynamic route replacements preserve cache authority invariants. |
| **9. Multi-Port Gateway Listeners** (HTTP 80, HTTPS 443, H3 8443, L4 TCP/UDP) | Dispatches requests from concurrent port listeners into shared router. | Explicit listener ports in `Host` header are preserved in cache key. | Port 80, 8080, and 8443 requests never share cache entries. |

### 2.3 FR-3: RFC 9111 Session Boundary Isolation vs. Application Path Confusion

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         WEB CACHE DECEPTION: SHARED RESPONSIBILITY BOUNDARY                      │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                                  │
│    ATTACKER REQUEST                                                                              │
│    GET /api/user/profile.css HTTP/1.1                                                            │
│    Host: example.com                                                                             │
│    Cookie: victim_session                                                                        │
│          │                                                                                       │
│          ▼                                                                                       │
│    ┌────────────────────────────────────────────────────────────────────────┐                    │
│    │                     TORON EDGE GATEWAY (RFC 9111 CACHE)                │                    │
│    │                                                                        │                    │
│    │  [✓] RFC 9111 Protocol Boundary Invariants:                            │                    │
│    │      • Rejects caching if Authorization header present (unless public) │                    │
│    │      • Bypasses cache if origin returns Cache-Control: private         │                    │
│    │      • Bypasses cache if origin returns Cache-Control: no-store        │                    │
│    │      • Bypasses cache if origin returns Cache-Control: no-cache        │                    │
│    │      • Strips Set-Cookie / Set-Cookie2 before storing and on hit       │                    │
│    │      • Isolates cache keys by Host:Port authority                      │                    │
│    │                                                                        │                    │
│    │  [!] Transparent Proxy Scope Limitation:                               │                    │
│    │      • Toron does NOT inspect path extensions (.css, .jpg)             │                    │
│    │      • Toron does NOT guess MIME types or rewrite application URIs     │                    │
│    └──────────────────────────────────┬─────────────────────────────────────┘                    │
│                                       │ (Forwarded Request)                                      │
│                                       ▼                                                          │
│    ┌────────────────────────────────────────────────────────────────────────┐                    │
│    │                    UPSTREAM APPLICATION FRAMEWORK                      │                    │
│    │                                                                        │                    │
│    │  Vulnerability (Gil, 2017):                                            │                    │
│    │    Origin framework strips ".css", renders private profile, but        │                    │
│    │    FAILS to emit "Cache-Control: private"                              │                    │
│    │                                                                        │                    │
│    │  Mandatory Application Framework Cooperation:                          │                    │
│    │    1. Application MUST emit "Cache-Control: private, no-store"         │                    │
│    │       on all authenticated or personalized dynamic endpoints.          │                    │
│    │    2. Application router MUST reject dynamic requests with             │                    │
│    │       unrecognized static extensions (path confusion hygiene).         │                    │
│    └────────────────────────────────────────────────────────────────────────┘                    │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

1. **RFC 9111 Protocol Session Boundary Isolation Enforced by Toron**:
   - **Authorization Refusal (RFC 9111 §3.5)**: Any request bearing an `Authorization` header MUST be refused from shared cache admission and cache lookup, unless the upstream origin response explicitly declares `Cache-Control: public`.
   - **Dual-Stage Cookie Stripping (RFC 9111 §8, CWE-384)**: `Set-Cookie` and `Set-Cookie2` headers MUST be stripped prior to storing a response in `ResponseCache`, and stripped again prior to serving a cache hit to downstream clients.
   - **Directive Enforcement (RFC 9111 §5.2.2)**: Any response specifying `Cache-Control: private`, `no-store`, or `no-cache` MUST NEVER be cached.
   - **Streaming Exemption ([`REQ-128`](file:///Users/sneha/Developer/toron-research/toron/docs/requirements/REQ-128.md))**: Responses with `Content-Type: text/event-stream` or `X-Accel-Buffering: no` unconditionally bypass caching.
   - **Authority Isolation**: In-memory cache entries are partitioned by full `Host:Port` authority, preventing cross-tenant or cross-port session bleed.

2. **Application-Level Path Confusion Scope (Shared Responsibility Model)**:
   - Toron operates strictly as an RFC 9111-compliant shared proxy cache and does not perform heuristic path inspection or speculative MIME-type enforcement.
   - If an upstream origin application receives a path-confused request (e.g., `/profile.php/nonexistent.css`), strips the `.css` extension, returns private user data, but **omits `Cache-Control: private` or `no-store`**, Toron will cache the response in accordance with RFC 9111 shared caching rules.
   - Defending against application-level path confusion fundamentally requires upstream application framework cooperation.

## 4. Acceptance Criteria

- **AC-1 (Route Matching Disambiguation)**:
  - When a route is registered with a domain-only host (e.g. `example.com`), it matches incoming requests with `Host: example.com`, `Host: example.com:80`, and `Host: example.com:8080`.
  - When a route is registered with an explicit host:port (e.g. `example.com:8080`), it matches incoming requests with `Host: example.com:8080`, and MUST NOT match requests with `Host: example.com:8443` or `Host: example.com`.
  - When both an explicit host:port route and a domain-only fallback route are registered for the same path, requests to that port route to the explicit handler.
- **AC-2 (Host:Port Cache Key Preservation)**:
  - When a request includes a `Host` header with an explicit port (e.g., `Host: api.toron.local:8080`), the generated cache key MUST contain the port (`"GET:api.toron.local:8080:/path"`).
  - When a request includes a `Host` header without a port (e.g., `Host: api.toron.local`), the generated cache key MUST contain the hostname without a port (`"GET:api.toron.local:/path"`).
  - When an IPv6 literal host with a port is supplied (e.g., `Host: [::1]:8080`), the cache key MUST preserve the bracketed host and port (`"GET:[::1]:8080:/path"`).
- **AC-3 (Cross-Port Cache Isolation Verification)**:
  - A test case in `pkg/router/cache_test.go` MUST verify that two consecutive requests with identical HTTP methods and URIs but different host ports (e.g., `Host: service.local:8080` and `Host: service.local:9090`) do NOT share cache entries. The second request to port 9090 MUST result in `X-Cache: MISS` and invoke the upstream handler.
- **AC-4 (RFC 9111 Boundary Invariant Verification)**:
  - Verified that `Set-Cookie` and `Set-Cookie2` headers are purged before storage and upon cache delivery.
  - Verified that responses bearing `Cache-Control: private`, `no-store`, or `no-cache` are never admitted to the cache.
  - Verified that requests bearing `Authorization` headers are refused from shared cache unless the origin response explicitly specifies `Cache-Control: public`.
  - Verified that streaming responses (`text/event-stream`, `X-Accel-Buffering: no`) bypass cache storage.
- **AC-5 (Routing Methods Integrity)**:
  - Verified that all 9 routing methods (Exact, Prefix, Domain/VHost, Header, Method, Reverse Proxy, Static File, K8s Ingress / Container Discovery, Multi-Port Gateway Listeners) continue to operate correctly and dispatch requests without regression.
- **AC-6 (Internal Documentation Alignment)**:
  - `docs/wiki/features/response-caching.md`, `docs/wiki/configuration.md`, and `docs/wiki/index.md` are fully updated per FR-4.
  - No references to files outside the project repository are introduced.
- **AC-7 (Zero Regression & Concurrency Cleanliness)**:
  - All unit, integration, and benchmark tests pass with 100% success under the race detector:
    ```bash
    go test -race ./...
    ```

## 5. Rationale & Architecture Analysis

### 5.1 Decoupling Route Matching from Cache Key Authority

In early router design ([`ADR-015`](file:///Users/sneha/Developer/toron-research/toron/docs/architecture/ADR-015.md)), `extractHost(req)` was implemented to normalize the `Host` header by stripping ports:
```go
func extractHost(req *httpparser.Request) string {
    h := req.Header.Get("Host")
    if h == "" { return "" }
    if idx := strings.Index(h, ":"); idx != -1 { h = h[:idx] }
    return strings.ToLower(strings.TrimSpace(h))
}
```
This design was intended to make virtual host matching convenient: an operator registering a route for `myapi.org` expects it to handle traffic whether the client connected via standard port 80/443 or an explicit port 8080.

However, using this port-stripped string for cache key derivation conflates **routing dispatch flexibility** with **origin resource identity**:
- Under RFC 9110 §4.2 and RFC 9111 §2, an HTTP authority is defined by the host and port tuple.
- Two distinct backend services operating on ports 8080 and 8443 on the same physical host are independent network origins.
- Collapsing them into a single cache key leads to cross-port cache poisoning, unauthorized data disclosure, and session confusion.

Furthermore, stripping the port inside `extractHost` prevented the router from supporting port-specific route rules. By updating `headersAndHostMatch` to inspect whether `routeHost` contains a port, Toron achieves the best of both worlds:
1. Operators can register domain-only routes that match any incoming port.
2. Operators can register port-specific routes (e.g., administrative consoles on port 8080) that only match that exact port.
3. The caching engine always derives the cache key using the full `Host:Port` authority, guaranteeing strict origin isolation.

### 5.2 The Shared Responsibility Model in Transparent Proxy Caching

Web Cache Deception exploits an impedance mismatch between how an edge cache and an origin backend parse URLs.
- If a transparent reverse proxy attempts to heuristically block Web Cache Deception by parsing file extensions (e.g. denying caching to any URI ending in `.css` if `Content-Type` is `application/json`), it introduces fragile heuristics that break legitimate dynamic APIs, Single Page Applications, CSS-in-JS endpoints, and download gateways.
- Under RFC 9111, a shared proxy cache is transparent: it relies strictly on HTTP header directives emitted by the origin server (`Cache-Control`, `Vary`, `Expires`).
- Toron enforces absolute protocol isolation when directives are present: `private`, `no-store`, `no-cache`, `Authorization` restrictions, and `Set-Cookie` stripping.
- However, if an upstream application framework strips file extensions and returns private data while failing to declare `Cache-Control: private`, the vulnerability resides in the application framework.
- By formalizing this Shared Responsibility Model and detailing developer best practices in `docs/wiki/features/response-caching.md`, Toron provides clear, actionable guidance to application developers and operators.
