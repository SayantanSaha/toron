# REQ-112 - HTTP/2 Translation Invariant Guards - H2.CL / H2.TE (SRC-06)

## 1. Description

Academic peer review audits of Paper 2 (`AER-002`, `PDR-002`, `AR-002`, `MSR-002`, and `ReviewTaskSummary.md` item `SRC-06`) revealed a critical vulnerability in Toron's multi-protocol translation boundary. While Section 5.3 of Paper 2 asserts that Toron mitigates cross-protocol request smuggling (*"Toron mitigates H2.CL and H2.TE attacks by enforcing identical framing invariant validation on translated HTTP/2 headers before dispatching them to upstream connection pools"*), the concrete implementation in `pkg/server/server.go` (`http2AdapterHandler`) and `pkg/proxy/proxy.go` lacks essential semantic translation validation:

1. **RFC 7540 §8.1.2.2 Violation (Forbidden Connection-Specific Headers)**:
   HTTP/2 strictly prohibits connection-specific headers. Specifically, RFC 7540 §8.1.2.2 mandates that endpoints MUST treat requests containing `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Proxy-Connection`, or `Upgrade` (unless extended CONNECT per RFC 8441) as malformed (`400 Bad Request` or stream error). Currently, `http2AdapterHandler` accepts standard `http.Request` objects from `golang.org/x/net/http2` without validating or rejecting connection-specific headers.

2. **H2.TE and H2.CL Cross-Protocol Desynchronization**:
   When Toron receives an HTTP/2 request containing `Transfer-Encoding: chunked` or conflicting `Content-Length` headers, converting this request into an internal `httpparser.Request` and forwarding it across persistent HTTP/1.1 backend sockets exposes the origin server to HTTP Request Smuggling (Kettle 2021):
   - **H2.TE**: HTTP/2 framing defines message boundaries via binary `DATA` frames, ignoring `Transfer-Encoding`. When forwarded to an HTTP/1.1 backend, the backend prioritizes `Transfer-Encoding: chunked`, misinterpreting the unchunked body as pipelined requests.
   - **H2.CL**: Inconsistent or multiple `Content-Length` headers cause backend HTTP/1.1 parsers to consume truncated or oversized byte streams, desynchronizing the shared backend connection pool.
   - **Payload Length Discrepancy**: When an HTTP/2 request declares a `Content-Length` that does not match the actual byte count received across `DATA` frames before `END_STREAM`, downstream HTTP/1.1 forwarding poisons backend sockets.

3. **CRLF and NUL Injection in HPACK Pseudo-Headers & Regular Headers**:
   HTTP/2 HPACK encodes headers in binary frames with length prefixes, permitting arbitrary octets (including CR `0x0D`, LF `0x0A`, and NUL `0x00`) in header values and pseudo-headers (`:path`, `:authority`, `:method`). If these values are translated naively and serialized into HTTP/1.1 wire format (`%s: %s\r\n`), injected CRLF sequences break HTTP/1.1 framing, forging new requests on upstream sockets.

4. **HTTP/2 Pseudo-Header Leakage into Upstream HTTP/1.1 Sockets**:
   In `pkg/proxy/proxy.go`, request serialization loops over `req.Header` without stripping pseudo-headers (headers with `:` prefix such as `:protocol`, `:path`, `:authority`). When forwarded to an HTTP/1.1 origin, invalid header lines (e.g. `:protocol: websocket\r\n`) corrupt the upstream HTTP/1.1 stream.

## 2. Acceptance Criteria

### AC-1: RFC 7540 §8.1.2.2 Connection Header Rejection Guard
- In `pkg/httpparser` and `pkg/server/server.go`:
  1. Define translation validation logic for incoming HTTP/2 requests before router dispatch.
  2. Reject any HTTP/2 request containing any of the following forbidden connection-specific headers:
     - `Transfer-Encoding` (unconditional rejection with `400 Bad Request`)
     - `Connection`
     - `Keep-Alive`
     - `Proxy-Connection`
     - `Upgrade` (unless `:protocol` pseudo-header is present indicating RFC 8441 extended CONNECT)
  3. Rejection must return status `400 Bad Request` with an explicit JSON error payload and immediately terminate the stream without forwarding.

### AC-2: Content-Length Invariant & H2.CL Desynchronization Guard
- In `pkg/server/server.go:http2AdapterHandler` and `pkg/httpparser`:
  1. Validate `Content-Length` headers in incoming HTTP/2 requests:
     - If multiple `Content-Length` header entries or comma-separated values are present, reject with `400 Bad Request`.
     - If `Content-Length` contains non-digit characters, leading signs, or unparseable integers, reject with `400 Bad Request`.
  2. For non-CONNECT requests with request bodies:
     - Compare the actual read byte count against the declared `Content-Length`.
     - If the received payload length does not match declared `Content-Length`, reject with `400 Bad Request` (`ErrHTTP2ContentLengthMismatch`).

### AC-3: CRLF and NUL Binary Injection Scanner
- In `pkg/httpparser` / `pkg/server/server.go`:
  1. Implement zero-allocation scanner validating that:
     - Request method, URI path, query string, host/authority, and scheme contain zero `\r` (`0x0D`), `\n` (`0x0A`), or `0x00` bytes.
     - All header field names and header field values contain zero `\r`, `\n`, or `0x00` bytes.
  2. Any detection of CRLF or NUL characters MUST immediately trigger a `400 Bad Request` rejection with zero upstream forwarding.

### AC-4: Upstream Pseudo-Header Stripping in Reverse Proxy
- In `pkg/proxy/proxy.go`:
  1. In `ServeHTTPWithPrefix` (standard reverse proxy):
     - Explicitly filter out any header keys beginning with `:` (such as `:protocol`, `:path`, `:authority`, `:method`, `:scheme`) before copying to `outReq.Header`.
  2. In `proxyRawStream` / WebSocket handshake serializer:
     - Explicitly ignore header keys beginning with `:` when constructing `reqBuf` for upstream TCP socket writes.
  3. Ensure no colon-prefixed pseudo-headers ever appear on upstream HTTP/1.1 wire connections.

### AC-5: Automated Verification Test Suite (TC-112)
- In `pkg/server/server_test.go` and `pkg/proxy/proxy_test.go`:
  1. **H2.TE Rejection Test (`TC-112-01`)**: Send HTTP/2 request with `Transfer-Encoding: chunked`; verify strict `400 Bad Request`.
  2. **H2.CL Multiple / Conflicting Rejection Test (`TC-112-02`)**: Send HTTP/2 request with duplicate or comma-separated `Content-Length`; verify `400 Bad Request`.
  3. **H2.CL Length Mismatch Rejection Test (`TC-112-03`)**: Send HTTP/2 request with `Content-Length: 10` and 5-byte body; verify `400 Bad Request`.
  4. **CRLF / NUL Injection Rejection Test (`TC-112-04`)**: Send HTTP/2 request with `\r\n` injected in custom header or `:path`; verify `400 Bad Request`.
  5. **Forbidden Connection Header Test (`TC-112-05`)**: Send HTTP/2 request with `Connection: keep-alive` or `Upgrade: foo`; verify `400 Bad Request`.
  6. **Extended CONNECT Allowance Test (`TC-112-06`)**: Send HTTP/2 extended CONNECT request with `:protocol: websocket`; verify valid processing without rejection.
  7. **Upstream Pseudo-Header Stripping Test (`TC-112-07`)**: Verify downstream HTTP/2 requests with `:protocol` or other pseudo-headers forward cleanly to HTTP/1.1 backend without `:` headers.

### AC-6: Zero-Dependency & Race-Clean Invariant
- Pure Go standard library (`net/http`, `strings`, `bytes`, `errors`, `fmt`).
- 100% clean execution under `go test -race -count=1 ./...`.

## 3. Rationale

Cross-protocol translation (HTTP/2 to HTTP/1.1) is among the most severe attack surfaces in cloud-native ingress architecture. Because HTTP/2 uses binary multiplexed framing and HTTP/1.1 uses text delimiter framing, any divergence in parsing or translation allows attackers to smuggle arbitrary requests through the gateway into backend connection pools (H2.CL and H2.TE attacks). Hardening the translation layer with strict invariant validation eliminates this attack surface, enforces RFC 7540 compliance, and aligns Toron's implementation with its published scientific claims.

---

## 4. Constraints

- Zero external 3rd-party dependencies.
- RFC 8441 extended CONNECT compatibility must be preserved for WebSocket-over-HTTP/2.
- Zero data races under `-race`.
