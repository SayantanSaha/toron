# REQ-138 - Multi-Level Secondary and Tertiary Sorting in Dashboard Alerts and Requests

## Description

The Toron Web Dashboard currently sorts alerts, banned IP records, and request logs primarily by timestamp (latest first). When multiple records share an identical timestamp, the order is currently non-deterministic or arbitrary.

The system shall introduce deterministic multi-level tie-breaking sorting across the alerts and requests views:
1. **Alerts & WAF Incidents (`#/alerts`, `#/overview`)**:
   - Primary sort: `timestamp` descending (newest first).
   - Secondary sort: `client_ip` / `ip` ascending (lexicographical tie-breaker).
2. **Banned IPs Table (`#/alerts`)**:
   - Primary sort: `created_at` timestamp descending (newest first).
   - Secondary sort: `ip` ascending (lexicographical tie-breaker).
3. **Requests Live Tail (`#/logs`)**:
   - Primary sort: `ts` timestamp descending (newest first).
   - Secondary sort: `client_ip` / `ip` ascending (lexicographical tie-breaker).
   - Tertiary sort: `path` ascending (lexicographical tie-breaker).

## Acceptance Criteria

1. **Alerts Multi-Level Sorting**:
   - Every alert object has an associated `ip` field (`inc.client_ip` for incidents, `ban.ip` for banned threats, empty string for system/upstream/cert alerts).
   - When two or more alerts have identical `timestamp` values, they are sorted alphabetically/lexicographically by IP.
2. **Banned IP Multi-Level Sorting**:
   - When two or more banned IPs have identical `created_at` timestamps, they are sorted alphabetically/lexicographically by IP.
3. **Requests Multi-Level Sorting**:
   - Request log entries in `lgUpdate` are sorted with primary priority on `ts` descending.
   - For requests with identical `ts`, secondary sorting is applied based on `ip || client_ip` ascending.
   - For requests with identical `ts` and identical IP, tertiary sorting is applied based on `path` ascending.
4. **Deterministic Rendering**:
   - Sorting order remains stable and deterministic across dashboard refreshes and polling intervals.

## Rationale

Under high-load scenarios or batch ingestion of security events, multiple log entries or security alerts can be generated within the same second or millisecond. Multi-level sorting ensures deterministic visual rendering and grouping of events by source actor and targeted endpoint.

## Constraints

- Zero third-party frontend dependencies; sorting must run directly in native vanilla JavaScript.
- Must not degrade UI rendering performance on large log arrays.
- Backwards-compatible with missing IP or path fields using safe fallbacks.
