# REQ-062 - Access Control, Authentication, and SSRF Hardening for Internal Management APIs

## Description

The Toron edge server shall protect all internal management, telemetry, and debugging endpoints under the `/internal/api/` namespace against unauthorized public access, reconnaissance, and Server-Side Request Forgery (SSRF).

Administrative endpoints—such as `/internal/api/status`, `/internal/api/routes`, `/internal/api/upstreams/health`, `/internal/api/security/incidents`, and `/internal/api/proxy-test`—shall require valid authentication credentials, allow source IP whitelist enforcement, and prevent arbitrary localhost request forgery.

## Acceptance Criteria

### 1. Mandatory Authentication on Management Routes
- All endpoints rooted at `/internal/api/` shall require valid credentials (API key or Basic Auth) when invoked by clients.
- Unauthenticated or unauthorized requests to `/internal/api/*` shall be rejected with HTTP `401 Unauthorized` or HTTP `403 Forbidden`.

### 2. Network & Subnet Binding Restriction
- Toron shall support configuration options to bind internal APIs to a dedicated management interface/port or restrict access strictly to a configurable CIDR subnet (e.g. `127.0.0.1/32` or administrative LAN subnets).
- Requests originating outside the allowed administrative subnet shall be rejected with HTTP `403 Forbidden`.

### 3. SSRF & Privilege Escalation Mitigation on Proxy-Test
- The `/internal/api/proxy-test` debugging endpoint shall strictly restrict test invocations to a predefined whitelist of benign endpoints (e.g. `/health`).
- Client-supplied custom headers in `proxy-test` shall not override security-critical identity headers (such as `X-Authenticated-User`, `X-Forwarded-For`, or authorization credentials) when dispatching requests to localhost.

### 4. Telemetry Privacy
- Internal routing definitions, upstream target IP addresses, filesystem directory paths, and security audit log entries shall not be accessible to unauthenticated edge clients.

## Rationale

Exposing management and debugging endpoints publicly allows external adversaries to map internal network topology, inspect security incident logs, and use `/internal/api/proxy-test` as an internal proxy to bypass perimeter authentication.

## Constraints

- Zero external runtime dependencies.
- Backward compatibility with the existing Control Center dashboard when valid administrative credentials are provided.

## Open Questions

- Should `/internal/api/proxy-test` be disabled entirely in production mode by default?
